Context Engineering

In Module 2 you decided what the agent is allowed to do: the tools, the postures, the sandbox. That is the boundary. This module is about the other half of the same problem: what the agent knows when it acts inside that boundary. A perfectly permissioned agent that misunderstands your repo still ships the wrong change; it just ships it safely. The boundary keeps it from doing damage. The context is what makes its work correct.

Here is the shift. Up to now you have been handing the agent context by hand, in each prompt: "orders-api is the Python service on 8080, inventory-api is Go on 8081, check /readyz not /health." That works for one task. It does not scale to a platform team where the agent runs dozens of times a day across app code, Terraform, and Kubernetes, you cannot re-explain the repo every session, and if you forget one detail the agent fills the gap with a guess. Context engineering is how you make that knowledge durable and scoped instead of retyped and forgotten: a written operating contract the agent loads automatically, rules that change depending on which part of the repo it is working in, evidence it can trust because you told it where the evidence came from, and a memory that remembers across sessions without remembering the wrong things.

That last part is the sharp edge of this module. A memory that persists is only as good as your control over what gets in. The Deep Dive is an incident where a plausible-looking runbook, pasted into a ticket, tries to become a trusted procedure the agent will execute. Getting context right is not just about giving the agent more information. It is about giving it the right information and keeping the wrong information out.

Why context is a budget, not a bucket​

Think about onboarding a strong new engineer to your team. You do not hand them a 400-page wiki and say "read all of this before you touch anything." You give them the one page that matters: here are our services, here is how we run them locally, here is the one rule you must never break, here is where to look for the rest. The good onboarding doc is short on purpose: every extra page is a page they might skim past the important line in.

An agent's context window is exactly this, and stricter. Everything the agent knows about your task (your prompt, the files it read, the command output it collected, its own prior reasoning) shares one finite window. Fill it with a 500-line CLAUDE.md that documents every edge case, and you have not made the agent smarter; you have buried the three rules that actually matter under three hundred that do not, and left less room for the evidence it needs to collect while it works.

Analogy: context is a carry-on bag, not a shipping container. It has a hard size limit, and every item you pack is an item you have to find later under time pressure. You pack the passport and the boarding pass where you can grab them: you do not pad the bag with things "just in case" that make the essentials harder to reach.

So the whole discipline of this module reduces to one principle: spend the budget on signal. A tight CLAUDE.md, rules scoped to where they apply, evidence that arrives structured instead of as a wall of logs, queries that return the ten lines you need instead of ten thousand. Everything below is a technique for staying inside the budget while giving the agent what it actually needs.

The operating contract: CLAUDE.md​

The first and highest-leverage piece of context is a file the agent reads automatically at the start of every session: CLAUDE.md. It lives at the repo root (or .claude/CLAUDE.md), and Claude Code loads it before it does anything else. This is where the knowledge you have been retyping every session goes to live permanently.

Analogy: CLAUDE.md is the operating contract you would give a contractor on their first day, not the full building code, but the specific rules for this site. Where the water shutoff is. Which wall is load-bearing. Who to call before touching the electrical. It is short because it is curated: it is the intersection of "things that are true about this project" and "things the agent will get wrong without being told."

What belongs in it, and what does not, follows directly from the budget principle:

Belongs in CLAUDE.mdDoes not belong
The service map: names, languages, ports, responsibilitiesFull API documentation the agent can read on demand
How to run, test, and check health locallyEvery config option with its default
The non-obvious rules (check /healthz not /health; never terraform apply)Rules the agent would follow anyway from reading the code
Where to find the rest (contracts, runbooks, incidents)The contents of everything it points to

The test for any line is: would the agent get this wrong without it, and is it stable enough to be worth committing? A line that fails either test is bloat. The service map passes: the agent cannot infer that inventory-api's health path differs from orders-api's by reading one file. A paragraph restating what docker-compose.yaml already says fails: the agent can read the compose file when it needs to.

/init: reconnaissance, not the finished contract​

You do not write CLAUDE.md from a blank page. Claude Code ships a command (claude /init) that runs reconnaissance on the repository and drafts a starter contract for you. It reads the file structure, the package manifests (pyproject.toml, go.mod), the config, the README, and produces a first-draft CLAUDE.md describing what it found.

Analogy: /init is the site survey, not the blueprint. A surveyor walks the property and writes down what is physically there: the boundaries, the existing structures, the utilities. That document is essential and it is also not the plan. It tells you the ground truth; you still decide what to build and what rules apply. Treat /init's output the same way: it is an accurate inventory that you then edit down to the curated contract, adding the non-obvious rules a survey cannot know (that /health is a trap, that Terraform is plan-only here) and cutting the generic filler a survey always includes.

The mistake to avoid is committing /init's raw output as if it were done. A generated contract is a strong starting point and a weak finished product: it documents what is there, not what matters, and it does not know the rules that live in your team's heads. The value you add is the editing.

Northstar already ships a CLAUDE.md: so what does /init do here?

The Northstar workspace comes with a root CLAUDE.md and a .claude/CLAUDE.md already written, because a real repo you inherit usually has some contract. Running /init on a repo that already has one lets you compare: what did reconnaissance find that the existing contract missed, and what did the existing contract capture that reconnaissance could never know (the plan-only Terraform rule, the /healthz-not-/health trap)? That gap (between what a survey can see and what a team knows) is exactly the value you add by hand.

Directory-scoped rules: the right rule in the right place​

A single root CLAUDE.md has a scaling problem. Northstar is not one codebase. It is a Python service, a Go service, a Terraform estate, and a Kubernetes/Helm platform, each with rules that are correct here and wrong there. "Run pytest" is right in app/orders-api/ and meaningless in infra/. "Never terraform apply" is critical in infra/ and irrelevant in app/. Put all of it in the root file and every rule pays the budget cost in every session, even the sessions where it does not apply, and the agent has to figure out which rules are live for the directory it is actually in.

Claude Code solves this the way a well-run monorepo solves it: rules can be scoped to a subtree. A CLAUDE.md inside app/orders-api/ applies its rules when the agent works in that directory, on top of the root contract. The root file holds what is true everywhere; each scoped file holds what is true only there.

Analogy: this is the posted rules on a job site. The site-wide sign at the gate says "hard hats required, report to the trailer": that is the root CLAUDE.md, true everywhere. But the electrical room has its own sign ("lockout/tagout before any work") and the chemical store has a different one. You do not put the lockout rule on the front gate, because it only applies in one room; you post it where it applies, so the person standing there sees exactly the rules for where they are and is not scanning a wall of site-wide notices for the one that is relevant.

The payoff is both budget and correctness. Budget, because a session working in app/orders-api/ loads the Python rules and not the Terraform ones. The context stays relevant to the task. Correctness, because the scoped file is where you put the rule that only makes sense there, stated plainly, without diluting it among rules for three other stacks. When you write these in the lab, the discipline is the same as the root file: each line earns its place by being non-obvious and local.

Evidence contracts: knowing where a fact came from​

Now shift from what the agent reads to what it collects. During an investigation the agent gathers facts (a health check result, a log line, a metric) and then reasons from them. But a fact with no provenance is a liability. "inventory-api is down": says who, checked when, with what command, and is that still true? An agent that treats a stale, unsourced observation as current truth will confidently build a fix on a fact that expired ten minutes ago.

In your own incident work you already know this instinct: you do not act on "someone said the database is fine." You act on "I ran this query at 14:32 and got this result." The provenance is the trust. An evidence contract is that instinct written down as a structure the agent fills in every time it collects a fact.

Analogy: an evidence contract is the chain-of-custody label on a lab sample. The sample itself is not enough: the label says who collected it, when, from where, and how it was handled, because without that the sample is not admissible. A number with no label is a rumor; a number with a label is evidence. You want the agent producing labelled evidence, not rumors.

evidence:
  claim: "orders-api is not ready"
  source: "curl -s http://localhost:8080/readyz"     # the exact command, reproducible
  collected_at: "2026-07-26T14:30:00Z"                # when, so staleness is visible
  collector: "agent:sre-investigator"                 # who, human or which agent role
  uncertainty: "point-in-time snapshot; may differ under load or after a restart"
  ttl: "5m"                                           # how long this fact is safe to trust

Every field earns its place by defending against a specific failure:

  • source: the exact command, so any claim is reproducible. If the agent says "not ready," you can run the same command and check. A claim you cannot reproduce is not evidence.
  • collected_at + ttl: together they make staleness visible. A fact collected at 14:30 with a 5-minute TTL is untrustworthy at 14:40, and the agent can see that instead of quietly reusing it.
  • collector: who produced it. A fact a human verified and a fact an agent scraped are not equally trustworthy, and (as the Deep Dive shows) a fact that came from an untrusted source like a pasted ticket must be marked as such so it never gets promoted to trusted knowledge.
  • uncertainty: the honest caveat. "Point-in-time snapshot" tells the agent (and you) not to over-generalize from one reading. This is the difference between "the service is down" and "one probe at one instant returned not-ready."

This connects straight back to the authority matrix from your governance contracts: the sre-investigator role's rules already say "must document evidence before proposing fixes." The evidence contract is what "documenting evidence" concretely means: not a plain text note, but a structured packet with source, time, and uncertainty that the next step (or the next agent, or you) can trust because it says where it came from.

Bounded queries: collecting evidence without drowning the budget​

The agent collects evidence by running commands. The naive way (kubectl get pods -o yaml, kubectl logs with no limit, curl dumping a full response) works exactly once, then poisons the budget. A single unbounded kubectl get pods -o yaml on a busy namespace can be thousands of lines of managed-field noise to answer a question that needed three pod names. That output does not just cost tokens; it buries the signal: the one failing pod is now on line 4,000, and the agent's next reasoning step has to wade through the other 3,999.

Analogy: this is the difference between asking a colleague "which of these three servers is down?" and them replying with the single hostname, versus emailing you the full dmesg of all three and letting you find it. The bounded answer respects your attention. The dump technically contains the answer and is nearly useless because of everything wrapped around it. You want the agent asking bounded questions, for the same reason you want bounded answers from a colleague.

There are four moves, and they compose:

  • Field selection: ask for the field, not the object. kubectl get pods -o jsonpath='{.items[*].metadata.name}' returns names; -o yaml returns everything about everything. curl -s .../readyz | jq '.status' returns the one field you are checking. Pull the fact, not the haystack it lives in.
  • Sampling: take a window, not the whole history. kubectl logs --tail=50 or --since=5m gives you the recent behavior that a live incident is about; the full log since pod start is rarely the question and always the bigger cost.
  • Output caps: put a hard ceiling on anything that could surprise you. | head -100, jq 'limit(10; .[])', --max-count. Even a query you think is small gets a cap, because "I thought it would be small" is how budgets die.
  • Scope by default: reach for the narrow query first and widen only if the narrow one was not enough. The instinct to get -o yaml "to be safe" is backwards: the broad query is the expensive one, and you can always run a second, wider query if the first genuinely missed something.

The reason this matters is not miserliness about tokens for its own sake. It is that a bounded query keeps the agent's window full of signal (the evidence that answers the question) instead of noise, so the reasoning that comes next is done against a clean view. You will measure the difference directly in the lab: the same question, answered from a bounded query and an unbounded one, and the order-of-magnitude gap in what each one costs the budget.

Compaction and memory: when context outlives the window​

Two problems remain, and they are the same problem at different timescales: the window is finite, but the work is not.

Within a session, a long investigation will eventually fill the window. When it does, Claude Code compacts: it summarizes the older parts of the conversation to make room, keeping the thread going. This is necessary and it is lossy: a summary is smaller than what it summarizes, and the detail that gets dropped is chosen by the summarizer, not by you. If a critical piece of evidence (the exact error string, the specific resource ID) lives only in the conversation, compaction can quietly blur it.

Analogy: compaction is the meeting minutes. A three-hour incident call gets distilled to a page of notes so the next shift can catch up. The notes are essential and they are not the recording: whatever the note-taker judged unimportant is simply gone. If a number is going to matter to the next shift, you write it down deliberately during the call; you do not trust it to survive in the minutes by accident.

That deliberate writing-down is the checkpoint: before the window fills, you have the agent save the load-bearing state to a file: the current hypothesis, the evidence collected, the exact strings that matter. A checkpoint is durable in a way the conversation is not; compaction cannot blur a file. The rule of thumb: anything you would be upset to lose to a summary, checkpoint it to disk while you still have it verbatim.

Across sessions, the window resets to nothing: tomorrow's session does not remember today's. Claude Code's memory bridges that gap: a per-project store (under ~/.claude/projects/<project>/memory/) that persists facts, decisions, and patterns from one session to the next. It is how "we already decided the retry budget is three" survives past the conversation that decided it.

And memory is where the whole module comes to a point, because a memory that persists is a memory that can be wrong for a long time. Every memory entry needs provenance (where it came from and when) for exactly the reason evidence needs a source: a remembered fact with no origin is a fact you cannot audit, revise, or distrust. Worse, a memory can be poisoned: a fact that entered from an untrusted source (a pasted ticket, a stale doc, an injected instruction) and then got treated as trusted knowledge because nobody marked its origin. Provenance is what lets you keep an untrusted observation as an untrusted observation, recorded, but never promoted to a procedure the agent will act on. That failure mode is the Deep Dive's incident, and it is why "context engineering" is finally about keeping the wrong information out, not just packing the right information in.

What you'll do in the lab​

You will build Northstar's context pack and measure that it works. You will run /init and read what reconnaissance produced; edit the root CLAUDE.md down to a budgeted, high-signal contract; write directory-scoped CLAUDE.md files for the Python service, the Go service, the Terraform estate, and the platform layer; define an evidence-packet schema the agent can fill in; run bounded versus unbounded queries side by side and measure the budget difference; practice the checkpoint pattern before a compaction; and finally run the same diagnostic prompt with and without the context pack and compare the quality of what you get back.

The boundary from Module 2 decides what the agent may do. The context pack you build here decides whether what it does is right. By the end you will have both, and a way to prove the second one paid off.
