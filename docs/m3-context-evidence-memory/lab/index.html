Lab — Build the Context Pack

In the lesson you learned that context is a budget: a curated CLAUDE.md, rules scoped to where they apply, evidence with provenance, and queries that return signal instead of noise. This lab makes all of it real against the Northstar workspace. You will run /init and see what reconnaissance produces, curate directory-scoped contracts for the four stacks, write an evidence-packet schema, measure the budget gap between bounded and unbounded queries, practice the checkpoint pattern, and finally prove the context pack changed the agent's answer for the better.

Most steps run Claude Code non-interactively with claude -p so the behavior shows up as plain terminal output you can read and grade.

Where you are working

All commands run from the root of the agentic-ops-lab workspace. You are building the same context pack you would ship to a teammate — the CLAUDE.md files and evidence schema you write here are committed artifacts, not throwaway scratch.

Step 0 — Prerequisites and a live stack​

Confirm Claude Code is installed, then bring up the core stack so there is a real service for the agent to probe. The readiness-drift injection points orders-api's dependency check at a path inventory-api does not serve, so the honest answer to "is orders-api ready?" is not ready while inventory-api itself stays healthy. That is the same signature Module 1 taught, reproduced deliberately rather than inherited — Module 1 repaired and merged its version of this bug, so a module that assumed it was still broken would be reading a moving target. It is exactly the diagnostic you will use to prove the context pack works.

claude --version
Expected output
2.1.197 (Claude Code)

Your version will differ — anything recent is fine. If claude is not found, revisit the Environment setup page.

docker compose --profile core up -d
scripts/inject.sh readiness-drift
curl -s http://localhost:8080/readyz | jq '.'
Expected output
{
  "status": "not ready",
  "checks": {
    "inventory_api": false
  }
}

not ready with inventory_api: false is the injected drift, live. inventory-api itself is healthy — orders-api is looking at the wrong path. Keep this fact in mind: a well-contextualized agent should be able to name why without you explaining it.

If the port is not answering, give the containers a few seconds and re-run.

Step 1 — Run /init and read what reconnaissance found​

Northstar already ships a root CLAUDE.md, but you are going to run /init anyway — not to replace the existing contract, but to see the gap between what a survey finds and what a team knows. Generate a fresh reconnaissance draft to a scratch file so you can compare without clobbering the committed contract:

claude -p "Run repository reconnaissance as /init would: inspect the file structure, package manifests (pyproject.toml, go.mod), docker-compose.yaml, and README, then write a starter CLAUDE.md describing the services, how to run them, and the repo layout. Write it to CLAUDE.init-draft.md — do not modify the existing CLAUDE.md." --permission-mode acceptEdits
Expected output

The agent inspects the repo and writes a draft. The exact prose varies run to run; the result is a generated contract that looks something like:

Wrote CLAUDE.init-draft.md — a reconnaissance draft covering the orders-api
(Python/FastAPI, 8080) and inventory-api (Go/chi, 8081) services, docker compose
profiles, the infra/ Terraform layout, and the platform/ Helm assets.

Now read the draft and compare it against the contract Northstar already ships:

wc -l CLAUDE.init-draft.md CLAUDE.md
Expected output
     78 CLAUDE.init-draft.md
     69 CLAUDE.md

Line counts will differ on your run. The point is the content difference, not the length: skim both files and notice what reconnaissance could not know. It correctly maps the services and ports (facts it can read), but it does not know that orders-api's /readyz is currently broken, that Terraform in this repo is plan-only, or that /health is a trap where you must use /healthz. Those are the rules that live in the team's heads — and the rules that make the contract worth having.

Why /init is a draft, not a deliverable

Reconnaissance produces an accurate inventory of what is in the repo. It cannot produce the judgment — the non-obvious rules, the known traps, the "never do this here" — because none of that is visible in the files. Committing /init's raw output as your contract ships the inventory and drops the judgment. The editing is the value.

Remove the scratch draft; you have seen what you needed:

rm -f CLAUDE.init-draft.md

Step 2 — Inspect the root contract you inherited​

Read the committed root contract before you extend it — you are curating an existing budget, not starting from zero.

sed -n '1,40p' CLAUDE.md
Expected output
# Northstar Commerce — Agentic Ops Lab

## About

Multi-service e-commerce platform for learning agentic DevOps with Claude Code.
Includes deliberate defects, fault injection, and incident scenarios for
hands-on SRE, IaC, and Kubernetes labs.

## Services

| Service | Language | Port | Purpose |
|---------|----------|------|---------|
| orders-api | Python/FastAPI | 8080 | Order management + ops dashboard |
| inventory-api | Go/chi | 8081 | Product catalog + fault injection |
| PostgreSQL | - | 5432 | Order persistence |
...

The root contract already carries the high-value, repo-wide facts: the service map, the compose profiles, the scripts table, and a pointer to contracts/ for governance. This is the "true everywhere" layer. What it does not carry — deliberately — are the per-stack rules, because those belong scoped to their directories. That is what you write next.

Step 3 — Have Claude write the directory-scoped contracts​

The root CLAUDE.md has to stay small, so anything stack-specific belongs next to the stack it describes. Claude Code loads a directory's CLAUDE.md when it works on files under that directory — so a Python convention costs nothing while the agent is editing Terraform.

You are going to have the agent write all four. That is not laziness: an agent reading a codebase to describe it is doing exactly the reconnaissance you want captured, and a contract written from the actual files beats one written from your memory of them. Your job is to review what it claims.

Write four directory-scoped CLAUDE.md files, one per stack. Read each stack
before you write its file — describe what is actually there, not what is
conventional.

app/orders-api/CLAUDE.md ALREADY EXISTS — I wrote it in Module 1. Read it first
and EXTEND it. Keep every section that is already there, especially the evidence
rules, the change rules, the verification section and the branch-only rule.
Add to it; do not replace it.

  app/orders-api/CLAUDE.md    — the Python/FastAPI service
  app/inventory-api/CLAUDE.md — the Go service
  infra/CLAUDE.md             — the Terraform estate
  platform/CLAUDE.md          — the Kubernetes and Helm assets

Each one covers three things and nothing else:
  - how to run and test this stack (the real commands, from the real config)
  - the conventions someone would otherwise get wrong
  - the rules — what must never be done here, stated as a prohibition

Two must-haves, because they are the ones that cause incidents:
  - infra/ must state that terraform apply and terraform destroy are not the
    agent's to run
  - platform/ must state that deleting a namespace is never the agent's call

Keep each file under 30 lines. A contract nobody reads is not a contract.

What Claude does. It reads each stack — pyproject.toml, the Go module, the Terraform layout, the Helm chart — and writes four files scoped to what it found. For orders-api it reads your Module 1 file first and adds to it.

Check that it extended rather than replaced. This is the most common way a cumulative workspace loses work: an agent told to "write" a file that already exists will happily write it from scratch, and the loss is invisible because the new file looks fine on its own. Confirm your Module 1 content survived:

grep -ciE 'evidence|change rules|verif' app/orders-api/CLAUDE.md
grep -c 'grade.sh m1' app/orders-api/CLAUDE.md

Both counts must be non-zero. If either is 0, the agent overwrote your Module 1 context file — restore it with git checkout app/orders-api/CLAUDE.md if it was committed, or re-add those sections, then re-run with the extend instruction made louder.

What you observe — and the one to check hardest. Open app/orders-api/CLAUDE.md. Does it name the readiness path at all?

On the run this lab was captured from, it did not. The file was otherwise good — real pytest invocation read out of pyproject.toml, correct async conventions — and it said nothing about /healthz versus /health. That is not a careless miss. The agent described what the code is, and the readiness trap is a fact about what goes wrong, which is not visible in a correct reading of a correct file. An agent documenting a stack will not warn you about a bug the stack does not currently have.

So add it yourself:

Add a readiness section to app/orders-api/CLAUDE.md: health is /healthz and
readiness is /readyz, and the readiness check must probe inventory-api's
/healthz — NOT /health, which does not exist and is the classic bug here.

This is the single most valuable line in the whole context pack, because it stops the next agent re-deriving a diagnosis you already paid for. It is also the part only you could have written: you know it because you debugged it. The agent captures the codebase; you capture the scar tissue. A context pack is worth exactly what it prevents.

Confirm the four exist and carry their prohibitions:

wc -l app/orders-api/CLAUDE.md app/inventory-api/CLAUDE.md infra/CLAUDE.md platform/CLAUDE.md
grep -l 'terraform apply\|terraform destroy' infra/CLAUDE.md
grep -l 'delete namespace' platform/CLAUDE.md
Expected output
      18 app/orders-api/CLAUDE.md
      16 app/inventory-api/CLAUDE.md
      17 infra/CLAUDE.md
      19 platform/CLAUDE.md
      70 total
infra/CLAUDE.md
platform/CLAUDE.md

Line counts will differ — what matters is that each is short and that both prohibitions landed. If either grep prints nothing, the rule is missing and the grader will say so.

Step 4 — Have Claude define the evidence-packet schema​

Evidence needs provenance. The agent needs a schema to fill in whenever it collects a fact, so a claim always arrives with its source, time, and uncertainty attached. Specify the properties the schema must have and let it write the file:

Write contracts/evidence-packet.yaml — the schema every fact an agent collects
during an investigation must be recorded in. A fact without provenance is a
rumour; this schema is what turns one into evidence.

Write it as a plain YAML template with placeholder values — the shape a packet
takes — NOT as a JSON Schema. Downstream tooling greps these field names, so use
exactly these keys under an `evidence_packet:` mapping:

  claim         one line
  source        the exact command that produced it, so anyone can re-run it
  collected_at  ISO-8601 UTC
  collector     who collected it, distinguishing human:<name> from agent:<role>
  trust         trusted | untrusted — untrusted meaning it came from a ticket, a
                stale doc, or any other input we do not control
  uncertainty   an honest caveat
  ttl           how long this fact is safe to reuse before it must be re-collected

Then one worked example under `example:`, using the same keys, filled in from a
real readiness probe of http://localhost:8080/readyz.

Note there is already a contracts/evidence-packet.schema.json describing a
role-to-role handoff. This file is a different granularity — one collected fact,
not a handoff — so say so in a comment at the top rather than merging them.

Explain to me why trust and ttl are separate fields before you write it.

What Claude does. It writes the schema with a worked example.

What you observe. The answer to the closing question is the point of the step. trust is about where a fact came from and never changes; ttl is about how fast it goes stale and is purely about time. A trusted fact can be expired, and an untrusted one can be fresh — collapsing them into a single "is this good?" field is how a stale-but-trusted measurement gets reused as current. Module 13's Deep Dive is an entire incident caused by exactly that collapse.

Now have the agent actually produce a packet in that form from a live probe — this is the schema doing its job:

claude -p "Read contracts/evidence-packet.yaml for the schema. Then collect one piece of evidence: run 'curl -s http://localhost:8080/readyz | jq .' and emit a single filled-in evidence_packet YAML block for the readiness claim. Use trust: trusted and a realistic UTC timestamp. Output only the YAML block." --permission-mode default
Expected output
evidence_packet:
  claim: "orders-api is not ready — inventory_api dependency check failing"
  source: "curl -s http://localhost:8080/readyz | jq ."
  collected_at: "2026-07-26T14:32:07Z"
  collector: "agent:sre-investigator"
  trust: "trusted"
  uncertainty: "point-in-time snapshot; inventory_api reported false at probe time"
  ttl: "5m"

The timestamp and exact wording will differ. What matters is the structure: the agent produced a claim with a reproducible source, a collected_at time, a trust marking, and an honest uncertainty — not a bare "it's down." That packet is auditable; a prose sentence is not.

The trust field is the one that matters most

source, collected_at, and ttl defend against staleness. The trust field defends against something worse: a fact that came from an untrusted origin — a pasted ticket, a stale runbook, an external message — being treated as verified truth. Marking evidence untrusted is what keeps a plausible-looking-but-unauthorized instruction from being promoted into a procedure. You will exploit exactly this in the Deep Dive.

Step 5 — Measure bounded vs. unbounded queries​

The lesson claimed an unbounded query buries the signal and burns the budget. Measure it. You will answer the same question two ways — unbounded and bounded — and compare the sheer volume of output each dumps into the context window.

First, the unbounded way: full container inspection to find one fact (is inventory-api healthy?).

docker inspect $(docker compose ps -q inventory-api) | wc -l
Expected output
     298

Your number will differ, but it is hundreds of lines of JSON — networks, mounts, env, labels, the entire container object — to answer a yes/no health question. Every one of those lines would land in the agent's window if it ran this to check health.

Now the bounded way: ask for exactly the field that answers the question.

docker inspect --format '{{.State.Health.Status}}' $(docker compose ps -q inventory-api) | wc -l
Expected output
       1

One line. Same question, same source, answered with field selection instead of a dump. The bounded query returned the fact; the unbounded one returned the fact plus a few hundred lines of everything else.

See the actual bounded answer — this is what belongs in the agent's window:

docker inspect --format '{{.State.Health.Status}}' $(docker compose ps -q inventory-api)
Expected output
healthy

One word of signal. That is the whole point: the agent now knows inventory-api is healthy (so the readiness failure is orders-api's fault), and it spent one line to learn it instead of three hundred.

The same discipline applies to logs — a window, not all history:

docker compose logs --tail=5 inventory-api | wc -l
Expected output
       5

--tail=5 caps the log to the five most recent lines. Without it, a long-running container could return thousands. During a live incident the recent tail is almost always the question; the full history since start rarely is, and always costs more.

The gap is the lesson

Hundreds of lines versus one, for the identical fact. Multiply that across a dozen probes in a single investigation and the unbounded habit fills the window with noise before the agent has done any reasoning. Bounded queries are not about saving pennies — they keep the window full of signal so the agent's next step is done against a clean view.

Step 6 — Practice the checkpoint pattern​

A long investigation fills the window and Claude Code compacts — summarizing older turns, which can blur exact strings. The defense is to checkpoint load-bearing state to a file before that happens. Have the agent write a checkpoint of the current investigation state:

claude -p "Collect the current state of the orders-api readiness investigation and write it to a checkpoint file at agentops/checkpoint-m3.md. Include: the exact readiness claim, the exact command that produced it, the inventory-api health status, the current hypothesis for the root cause, and a timestamp. Keep it under 25 lines. Then reply CHECKPOINTED." --permission-mode acceptEdits
Expected output
CHECKPOINTED

The agent wrote a durable file. Read it back:

cat agentops/checkpoint-m3.md
Expected output
# Investigation Checkpoint — orders-api readiness (M3)

- Timestamp: 2026-07-26T14:35:00Z
- Claim: orders-api /readyz returns "not ready" (inventory_api: false)
- Source: curl -s http://localhost:8080/readyz | jq .
- inventory-api health: healthy (docker inspect .State.Health.Status)
- Hypothesis: orders-api readiness probes the wrong path on inventory-api
  (/health instead of /healthz); inventory-api itself is fine.
- Next: confirm the path in app/orders-api/src/health.py

Exact wording varies. The value is that the load-bearing facts — the exact command, the exact claim, the hypothesis — now live in a file. Compaction can summarize the conversation freely; it cannot blur this, because it is on disk verbatim. This same file is also how tomorrow's session picks up where today's left off.

Checkpoint is the bridge to memory

A checkpoint survives compaction within a session. The same discipline — write the durable fact to disk, with its source and time — is what makes cross-session memory trustworthy. A memory entry is just a checkpoint that outlives the whole session, and it needs the same provenance to be worth trusting later.

Step 7 — Prove the context pack changed the answer​

Now the payoff: run the same diagnostic prompt with and without the context pack, and compare what you get back. The difference is the whole reason you built the pack.

First, the no-context baseline. Point the agent at a bare temp directory with --add-dir and no CLAUDE.md in scope, and ask it to diagnose from a description alone (no repo access to the code):

claude -p "orders-api reports not ready with inventory_api: false. Without access to the source code, what are the possible causes and what would you check first? Answer in 2-3 sentences." --permission-mode default --tools "Read"
Expected output
Possible causes: inventory-api is down or unreachable, a network/DNS issue
between the services, a wrong URL or port in orders-api's config, or a
readiness check hitting the wrong endpoint. I'd first verify inventory-api's
own health directly, then check what URL/path orders-api uses to probe it.

A competent but generic answer — it lists the whole space of possibilities because it has no Northstar-specific context. It does not know inventory-api is healthy, or that the known trap here is /health vs /healthz. It would get there, but only after ruling things out.

Now the same question with the context pack — the root contract, the scoped app/orders-api/CLAUDE.md you wrote, and the live repo:

claude -p "orders-api reports not ready with inventory_api: false. Using the project context and the code, name the specific root cause and cite the file and line. Answer in 2-3 sentences." --permission-mode default
Expected output
Root cause: orders-api's readiness check probes inventory-api's /health, but
that path does not exist — it must use /healthz (app/orders-api/src/health.py,
in the readyz handler). inventory-api itself is healthy; the failure is the
wrong dependency path, exactly the trap noted in the orders-api CLAUDE.md.

Same question, sharper answer. With the context pack the agent went straight to the specific bug, cited the file, and referenced the very rule you wrote into the scoped contract. The pack turned a generic checklist into a precise, sourced diagnosis. That delta — generic to specific — is what context engineering buys you, and it compounds across every task the agent runs.

Step 8 — Run the grader​

Turn "the outputs looked right" into a deterministic pass. The grader checks that the context pack is actually in place: the scoped contracts exist and carry their local rules, the evidence schema is defined, and the root contract stayed budgeted.

./scripts/grade.sh m3
Expected output
Grading: Module m3
========================

Checking: Context pack

  ✓ root CLAUDE.md present and budgeted (< 150 lines)
  ✓ app/orders-api/CLAUDE.md scopes Python rules (pytest, /healthz)
  ✓ app/inventory-api/CLAUDE.md scopes Go rules (go test)
  ✓ infra/CLAUDE.md forbids terraform apply/destroy
  ✓ platform/CLAUDE.md forbids kubectl delete namespace
  ✓ contracts/evidence-packet.yaml defines source + collected_at + trust

========================
RESULT: PASS (6 passed)

If a scoped-contract check is red, re-run the matching Step 3 heredoc. If the evidence check is red, re-run Step 4. If the budget check is red, your root CLAUDE.md grew past the line cap — trim it back toward the service map and pointers.

What the grader is really asserting

The grader is not checking that files merely exist — it greps each scoped contract for the rule that makes it worth having: /healthz in the orders-api file, terraform apply denial in the infra file, delete namespace denial in the platform file. An empty CLAUDE.md would fail. The context pack is graded on content, because a scoped file with no local rule is budget spent for nothing.

Teardown​

The context pack (CLAUDE.md files and contracts/evidence-packet.yaml) is a real deliverable — later modules build on it, so keep those. Only remove the scratch artifacts this lab created, and stop the stack.

The readiness-drift injection needs no separate reset: it lives as an environment override on the orders-api container, so removing the container clears it. Your next docker compose up starts from the compose defaults with a healthy dependency check.

rm -f CLAUDE.init-draft.md agentops/checkpoint-m3.md
docker compose --profile core down
Expected output
[+] Running 4/4
 ✔ Container agentic-ops-lab-orders-api-1      Removed
 ✔ Container agentic-ops-lab-inventory-api-1   Removed
 ✔ Container agentic-ops-lab-postgres-1        Removed
 ✔ Network agentic-ops-lab_default             Removed

Confirm the context pack is still in place — these files should show as new/untracked, ready to commit:

git status --short | grep CLAUDE.md
Expected output
?? app/inventory-api/CLAUDE.md
?? app/orders-api/CLAUDE.md
?? infra/CLAUDE.md
?? platform/CLAUDE.md

The four scoped contracts you wrote are present and untracked. (If you had cloned a fresh workspace, contracts/evidence-packet.yaml would show here too.) These are the context pack — commit them the way you would ship a boundary to a teammate.

You built Northstar's context pack and measured that it works: a curated root contract, four scoped contracts holding each stack's local rules, an evidence schema with provenance, bounded queries that returned one line instead of three hundred, a checkpoint that outlives compaction, and a diagnostic that went from generic to precise the moment the agent had the pack. The boundary decides what the agent may do; this pack decides whether what it does is right. In the Deep Dive you will use the trust field you built to stop a poisoned memory from becoming an executed action.
