Introduction to Agentic DevOps

In the lab at the end of this module you will clone Northstar Commerce, find something broken, and hand it straight to Claude. About fifteen minutes later the service is fixed, the grader is greener than it was, and you never opened the file.

Then, in the same session, on the same file, you will watch that same agent produce a change that looks completely correct, passes every check you would run by eye, and is wrong.

Both of those outcomes are the module. Getting an agent to change a file is easy, and you will do it almost immediately. Knowing whether the change repaired the fault or hid it is the skill, and it is the difference between an engineer who uses AI safely and one who ships whatever the model suggested and hopes.

This module gives you the vocabulary and the method for both: what Agentic DevOps actually is, why operating systems with an agent is a different job from writing code with one, and the four disciplines that make an agent's work trustworthy.

What Agentic DevOps is​

Three terms are competing for attention in the DevOps + AI space, and they describe different things.

AIOps uses machine learning to detect anomalies, correlate alerts, and predict failures. It watches your systems. It does not change them. AIOps is a sensor layer, valuable but passive.

AgentOps is observability for AI agents themselves. It tracks what your agents did, how long they took, what they spent. AgentOps tells you whether your agents are healthy. It does not do your operational work.

Agentic DevOps is the discipline of using AI agents as working partners who diagnose, change, and verify your infrastructure alongside you. The agent does operational work, within boundaries you define. You hold accountability. The agent holds the wrench.

Assisted is not agentic​

Most engineers are already doing the first version of this. You ask for a script, you read what comes back, you decide what to do with it. The agent suggests; every action stays yours.

Agentic work goes further: the agent reads the live system, makes the change, and runs the check. Your job shifts from producing the change to setting the boundary and reviewing the evidence.

Why the boundary is the product​

That single difference is why this is a discipline and not a feature.

When a tool only advises, being wrong costs a conversation — someone reads the advice, thinks about it, and does something else. When the agent acts, the command has already reached your system. Being wrong there costs a restore window, or a service pulled out of rotation, or the process state you needed for the postmortem.

So the boundary is not a nice-to-have you add later. It is the safety model, and it is what this course spends nineteen modules building.

Northstar Commerce: the platform you inherit​

You are joining the platform team at Northstar Commerce. You inherit one repository: two services (orders-api and inventory-api), a Terraform infrastructure, Kubernetes and Helm assets, a CI pipeline, Prometheus and Alertmanager, incident tickets, and a set of scripts that can inject faults and grade your work.

Every module improves that same repository. Nothing here is a throwaway demo — by the end you have one system, and around it a .claude/ operating layer that governs what agents can see, change, recommend, approve and verify.

The defect already waiting on your desk​

Ask the two services how they are, and they disagree:

// inventory-api /healthz
{"status":"ok"}

// orders-api /readyz
{"status":"not ready","checks":{"inventory_api":false}}

inventory-api is healthy. orders-api says its dependency is down. One of them is wrong about reality, and in Kubernetes this is not cosmetic: a readiness check that reports false pulls a working service out of the load-balancer rotation.

Run the grader before touching anything and it says FAIL (2 passed, 8 failed). That is your baseline, and it is the first number in this course.

It is the layer: context, permissions and hooks, evidence packets and change gates, role subagents, skills, and evaluations that tell you whether all of it still works after you change something.

Your first repair, in fifteen minutes​

Here is what you are about to do, so the lab is not a surprise.

You create a branch, start a session, and paste four lines: the symptom, the evidence that the dependency is healthy, the instruction to find and fix it, and the boundary it must work inside.

orders-api reports itself not ready. inventory-api is healthy — curl
localhost:8081/healthz returns {"status":"ok"} — but orders-api's /readyz says
inventory_api: false.

Find out why and fix it. ./scripts/grade.sh m1 decides whether you succeeded;
run it when you think you are done.

Work only inside app/orders-api/ and platform/. Do not commit anything.

Notice what is in that prompt: the symptom, the evidence, the authority on "done", and the boundary. Nothing about how to fix it.

Before it writes, it asks. Claude proposes the edit and stops at a permission prompt showing the one-line diff — /health becoming /healthz. You read it and approve. That prompt is the entire permission surface in miniature: the agent proposed, you decided. Module 2 takes it apart properly.

Then it finds something you did not know about. The same wrong path exists in a second place, platform/helm/orders-api/values.yaml. Nothing you could observe at the endpoint would have told you that. The grader knew, because it was written to check both, and the count moves from 2 passed to 5 passed.

That part of agentic DevOps sells itself. The rest of this module is about the half that does not.

Why ops is not coding, and why that changes everything​

Most material about coding agents is written for people building software. That work has a property your work does not: a mistake is a bad commit. Tests catch it, review catches it, git revert undoes it. The loop is cheap and reversible, so "let the agent try things and correct it afterwards" is a perfectly sound strategy — which is why nearly every guide you have read recommends exactly that.

Your work does not have that property. In operations, the action is the outcome.

  • A restart destroys the process state you needed for the postmortem.
  • An apply drops a database, and the rollback is a restore window measured in hours.
  • A correct command against the wrong kube context hits production.
  • By the time anyone reviews it, it has already happened.

That single difference has three consequences you will meet in every module.

Intent controls are not enough here. A rule in CLAUDE.md, a skill that says "human-only", a carefully worded prompt — all of these steer what the agent reaches for. When the worst case is a bad commit, that is usually sufficient. When the worst case is irreversible, it is not, because the model's good judgement is a tendency and not a guarantee. You will watch a "human-only" procedure run anyway in Module 6, and then watch a hook refuse the same action under the same conditions in Module 8. Mechanical guardrails are the load-bearing controls in ops work. Intent asks; enforcement refuses.

Autonomy costs something different depending on what you are doing. Running --dangerously-skip-permissions while you build a feature on a branch, in a worktree, on a machine with no production credentials is a good call — the blast radius is a directory you can delete, and approving two hundred edits defeats the point. Carrying that same habit into troubleshooting a live system is where it goes wrong, because an unwanted action is now a restarted service rather than a bad commit. Throughout this course you choose posture from what an unwanted action would cost, never from how tedious the approvals have become.

Verification is not a test suite. "The tests pass" does not tell you whether a change is safe to deploy at 4pm on a Friday with a launch running. Ops correctness is a judgment about blast radius, reversibility and timing — which is why what you build here is evidence packets, change gates, canary verdicts and authority matrices rather than assertions.

None of this makes agents less useful for operations. It makes them useful differently: the value is not the agent moving fast, it is the agent working inside a boundary you can justify to whoever asks why you let software touch production.

The diagnose → change → verify loop​

The loop is the how, and it does not change when an agent runs it. What changes is who performs each step and how you verify the result.

An agent makes the middle step nearly free. That is exactly why the steps on either side matter more, not less. When producing a diff costs seconds, the bottleneck moves to diagnosis (are we fixing the right thing?) and verification (did it actually work?). An agent that can generate ten plausible fixes a minute is a liability unless you have a discipline that says which one is correct and how you know.

Analogy: the technician's checklist versus the tinkerer​

Imagine two people fixing a car that won't start.

The tinkerer pops the hood and starts swapping parts. New battery: still dead. New starter: still dead. Three hours later the car runs, but nobody knows which change fixed it, and two of the "fixes" are now just extra risk sitting in the engine bay.

The technician works a checklist. Read the fault code. Reproduce the symptom. Form one hypothesis. Change one thing. Confirm the symptom is gone. When the car starts, they know why it starts, and the repair record proves it.

Agentic DevOps is the technician's method applied to systems, with an AI holding the wrench. The AI is fast and tireless, but a fast tinkerer is more dangerous than a slow one. The checklist is what keeps speed from turning into chaos.

Red goes back, never forward​

Notice the loop, not the line. When verification comes back red, you do not pile a second change on top of the first. You go back to diagnosis. A red grader means your hypothesis was wrong or incomplete, and stacking fixes on a wrong hypothesis is exactly the tinkerer's trap.

Bounded evidence​

Analogy: a good detective seals off the room before dusting for prints. They don't let the whole precinct trample through. Every extra footprint is noise that hides the one print that matters.

Before you ask anyone, human or agent, to diagnose a problem, you decide what evidence they get to see. This is bounded evidence: you scope the inputs to the smallest set that could contain the answer.

Why bound it? Two reasons that show up in your work every day:

  • Signal. A diagnosis made from the readiness endpoint's output plus the one file that serves it is sharper than a diagnosis made from the entire repository. More context is not more insight; past a point it is just more places to be wrong.
  • Cost and blast radius. When you let an agent read the evidence, the tokens you feed it and the files you expose are both a budget and a risk surface. An agent that has read only health.py cannot confidently propose editing your Terraform. Scoping the input scopes the possible output.

In the lab you write this down, in the repository, next to the service:

## Evidence to collect first
- `curl -s http://localhost:8080/readyz | jq` — what this service says about itself
- `curl -s http://localhost:8081/healthz` — whether inventory-api is actually up
- `app/orders-api/src/health.py` — the readiness implementation

Collect these three and stop.
Bounded evidence is a habit, not a restriction

Bounding evidence is not about hiding things from the agent. It is about giving it a clean, relevant working set so its reasoning, and yours, stays anchored to what actually matters.

Branch-only changes​

Analogy: a surgeon operates in a theatre, not in the hospital lobby. The theatre is isolated on purpose: if something goes wrong, it is contained, and the rest of the hospital keeps running.

You never repair on main directly. Every change lands on a branch first. On a branch you can review the full diff, run the grader, throw the whole thing away with one command when the hypothesis was wrong, and merge only once verification is green.

This matters even more with an agent in the loop. An agent editing files directly on main gives you a changed system and no clean record of what it touched. A branch turns every agent change into a reviewable, revertable proposal. The branch is the boundary between "the agent did something" and "I approved something the agent did."

Deterministic verification: the grader​

Analogy: a lab test result is a number against a reference range, not the nurse saying "you look healthy." "Looks healthy" is a vibe. "Glucose 92 mg/dL, range 70–100" is a fact you can act on.

Here is the most important idea in this module: "it seems to work" is not verification. A change is verified when a deterministic check, the same inputs producing the same pass/fail every time, says so.

Northstar ships a grader for exactly this:

./scripts/grade.sh m1

It does not ask your opinion. It curls the real endpoints, inspects the actual code, checks the Helm probe path, and prints PASS or FAIL with a count. In the lab you watch that count move four times: 2 passed before you start, 5 passed after the agent's fix, 9 passed once you write the context file, and PASS (10 passed) after the merge.

The change that looks right and is wrong​

Once readiness is repaired you will ask for something entirely reasonable: make readiness more resilient, because the deploy keeps flapping when inventory-api is slow. The agent does what you asked — it removes the dependency check.

{"status":"ready","checks":{}}

curl is green. The flapping is gone. And the checks object is empty: the service is no longer reporting that things are fine, it has stopped looking. The grader says FAIL (3 passed, 7 failed) and names precisely what was removed.

The symptom went away because the thing that detects the symptom went away. Had you shipped on the endpoint output — which is what "I checked, it's fine" means in practice — you would have shipped a service that can never again report a dependency failure.

You cannot blame the agent for that one. It did what you asked; the instruction never said the dependency signal had to survive, and "resilient" has more than one honest reading. The gap was in the request, and the only thing that caught it was a check written before the request existed.

Two ways vibes fail​

Vibes-based verification fails in two directions, and an agent amplifies both. It gives false confidence (the agent says "Fixed!" while the symptom is still there under a slightly different request) and false alarm (you distrust a change that actually worked). A deterministic grader takes the agent's opinion, and yours, out of the question of whether the job is done.

Authority: how much of the loop you hand over​

The loop is the how. The last idea in this module is who drives, and that changes with the task.

Analogy: driver assistance in a car. Cruise control holds your speed but you steer. Lane-keeping nudges the wheel but you supervise. Full self-driving takes the whole trip. You would use cruise control on an empty highway and take full manual control in a crowded parking lot. The right level depends on how much can go wrong, and how fast.

Five operational modes​

When you work with an agent you are always setting a dial. There are five positions on it, from least to most autonomous.

ModeThe agent...You...Example
ExplainReads code, surfaces context, answers questionsDrive entirely, the agent is a search engine with reasoning"What does this health check actually probe?"
RecommendAnalyzes a situation and suggests a course of actionEvaluate the suggestion and decide whether to act on it"Given this alert, what should I investigate first?"
Change a branchWrites code, creates a diff on a branchReview the diff, run the grader, approve or discard"Fix the readiness probe path on a feature branch"
Execute with approvalProposes a plan, then acts step by step with your approval at each gateApprove each step, halt if any step looks wrong"Run the incident triage playbook, ask before each remediation"
Narrow closed loopDetects, acts, and verifies within fail-closed guardrails, no human in the loopMonitor outcomes, intervene only on anomalies"Watch for OOMKill events, scale the pod, verify recovery, alert if unresolved"

Your first repair in the lab is Change a branch: the agent writes the diff, you review and approve it, the grader decides whether it worked.

Three strategic levels​

Those five modes sit inside three levels, and this is the vocabulary the rest of the course uses:

LevelWho decidesWho actsOperational modes inside it
ManualHumanHumannone — you write the Terraform, the Helm chart, the runbook
AI AugmentedHumanHuman, Claude assistsExplain, Recommend
AgenticAgent, with varying human oversightAgentChange a branch, Execute with approval, Narrow closed loop

The big jump is not the one people expect. It is not between semi-autonomous and autonomous work — it is the earlier one, between AI as a tool you wield and AI as an agent that acts. Once the agent has agency, the remaining question is simply how far you let it run before it checks in with you.

The three questions​

The choice is a risk decision, not a capability decision. The question is never "can the agent do this?" It is:

  1. If the agent gets this wrong, how bad is it?
  2. How fast will I know?
  3. How easily can I undo it?

A one-line probe fix on a branch with a deterministic grader answers all three well: the diff is small, the grader is trustworthy, and git makes it revertable. A production database migration at peak traffic answers all three badly, no matter how capable the agent is.

As you progress through this course you climb:

  • This module: one graded change on a branch, so the loop is in your hands before you delegate more of it
  • Modules 2–4: you set the boundaries — permissions, sandboxing, context, and cost
  • Modules 5–19: skills, subagents, orchestration and governed workflows, where the agent runs more of the loop under controls you built and tested

The loop stays the same at every level; what changes is how much of it you drive yourself.

What you'll do in the lab​

You will delegate a real defect and then test whether you can tell good agent work from bad. Northstar's orders-api reports itself "not ready" because its readiness check probes the wrong path on inventory-api.

You will start the platform and watch the grader fail, hand the defect to Claude and approve your first permission prompt, watch it find a second surface of the same defect you did not know about, and then ask it for a reasonable-sounding improvement that quietly removes the safety property. curl will say the service is healthy. The grader will disagree, and the grader will be right.

Then you will write down the context that made a governed agent behave differently from an ungoverned one — the first file in the operating layer this course spends nineteen modules building — and prove it by running the same prompt in a control worktree that has none of it.
