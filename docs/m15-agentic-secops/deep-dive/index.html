Deep Dive — Your Agent Has a Supply Chain

Every earlier boundary module in this course asked the same question about the same object: what is my agent allowed to do? Permissions, postures, sandboxes, role files, RBAC, an attestation reconciling three sources of truth about a role. This page asks a different question, about a different object: what did I install, what does it actually do, and how would I know if it changed?

You have installed a third-party plugin with fourteen skills that run with your authority. An MCP server sits between you and a corpus of security findings. Three PreToolUse hooks execute shell on every Bash call you make in this repository. A settings.json file carries a permissions.allow list anyone with commit access could widen. That is a software supply chain, and nothing in Modules 1–14 audits it — this page reuses M3's provenance and trust vocabulary rather than inventing new governance, because the concept (a claim about a component's origin, checked rather than assumed) is the same one; only the object being checked has changed.

Where you are working

You continue in the agentic-ops-lab workspace, auditing this session's real installed stack — the plugins, the MCP server, and the hooks actually configured here — not a toy example. Nothing in this page mutates anything; every command reads.

Audit one: the MCP server's declared tools against what it can actually do​

platform/mcp-servers/secfindings/ is the read-only query interface over the scan corpus this module's lab uses. It declares itself in tools.json:

cat platform/mcp-servers/secfindings/tools.json
Expected output
{
  "server": "secfindings",
  "description": "Read-only query interface over the combined trivy/gitleaks/posture scan corpus (agentops/secops/scan-corpus.json). Query tools only; no write/mutate/rank tool exists.",
  "read_only": true,
  "tools": [
    { "name": "findings_query", "kind": "read", "args": ["component?", "severity?", "tool?", "reachable?"] },
    { "name": "finding_get", "kind": "read", "args": ["id"] },
    { "name": "corpus_summary", "kind": "read", "args": [] }
  ]
}

Three tools, all declared "kind": "read". That is the claim. Do not trust it — check the implementation:

grep -c "writeFile\|appendFile\|fs\.write" platform/mcp-servers/secfindings/server.js
Expected output
0

Zero write calls anywhere in the file that implements the three declared tools. This is the M7 criterion from the lesson made auditable, not just asserted: a capability that does not exist in the code cannot be misused, no matter what a compromised prompt asks for. A server that declared read_only: true while shipping a fourth, undeclared tool with a write verb would be the finding this audit exists to catch — this one, checked, does not have one.

Audit two: a plugin's declared component inventory against what's actually on disk​

You almost certainly ran claude plugin install superpowers@claude-plugins-official earlier in this course. Ask Claude Code itself what that installed:

claude plugin details superpowers
Expected output
superpowers 6.3.0
  Core skills library for Claude Code: TDD, debugging, collaboration patterns, and proven techniques
  Source: superpowers@claude-plugins-official

Component inventory
  Skills (14)  brainstorming, dispatching-parallel-agents, executing-plans, finishing-a-development-branch,
               receiving-code-review, requesting-code-review, subagent-driven-development,
               systematic-debugging, test-driven-development, using-git-worktrees, using-superpowers,
               verification-before-completion, writing-plans, writing-skills
  Agents (0)
  Hooks (1)  SessionStart  (harness-only — no model context cost)
  MCP servers (0)
  LSP servers (0)

Fourteen skills, zero agents, one hook — a SessionStart hook. That last line is the one worth pausing on: a plugin you installed for its skills also ships a hook that fires on every session start, whether or not you ever invoke a single skill from it.

Cross-check the declared skill count against the files actually on disk, rather than trusting the summary line:

find ~/.claude/plugins/cache/claude-plugins-official/superpowers -name "SKILL.md" | wc -l
14

Matches. Now read what that one hook actually runs — a plugin's own hooks.json, not a description of it:

cat ~/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/hooks/hooks.json
Expected output
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|clear|compact",
        "hooks": [
          {
            "type": "command",
            "command": "\"${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd\" session-start",
            "shell": "bash",
            "async": false
          }
        ]
      }
    ]
  }
}

Every session start, every /clear, every context compaction in a workspace with this plugin enabled, run-hook.cmd session-start runs — a real shell command, from a third party, with the same authority your own session has. claude plugin details told you a hook exists; only reading hooks.json tells you when it fires and what it invokes. The declared inventory and the actual trigger are two different facts, and this audit exists because the first one is not proof of the second.

Two of the fourteen skills also ship their own scripts, worth knowing about before you invoke them:

find ~/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills -name "*.sh" -o -name "*.js" | grep skills
.../brainstorming/scripts/helper.js
.../brainstorming/scripts/start-server.sh
.../brainstorming/scripts/stop-server.sh
.../systematic-debugging/find-polluter.sh
.../writing-skills/render-graphs.js

A SKILL.md file is prose the model reads. A .sh or .js file next to it is code that runs. Auditing the plugin means reading both, not just the one that reads like documentation.

Audit three: every hook that executes shell on your commands​

platform/mcp-servers/ and the plugin cache are two supply-chain surfaces. The third is closer to home — the hooks this repository itself registers, which run on every matching tool call you make, including the ones you invoke by hand:

python3 -c "import json; d=json.load(open('.claude/settings.json')); print([h['command'] for h in d['hooks']['PreToolUse'][0]['hooks']])"
Expected output
['$CLAUDE_PROJECT_DIR/scripts/hooks/change-gate.sh', '$CLAUDE_PROJECT_DIR/.claude/hooks/deny-cluster-mutation.sh', '$CLAUDE_PROJECT_DIR/.claude/hooks/release-gate-secops.sh']

Three hooks, all firing on every Bash call. Read what each one actually inspects, in one pass:

grep -h "^# " .claude/hooks/deny-cluster-mutation.sh scripts/hooks/change-gate.sh .claude/hooks/release-gate-secops.sh | head -12

Each header comment states the hook's scope in one line — mutating kubectl verbs, Terraform/kubectl production guardrails plus a .env secret-read block, and this module's own deploy-gate on an unresolved critical. A PreToolUse hook is the highest-leverage thing in this entire audit: it is shell, it runs before every matching tool call in every session in this repository, and none of the plugin or MCP audits above carry that reach. Reading three header comments is not the same as reading the scripts — do that too, the same way you read server.js instead of trusting tools.json in Audit one.

Audit four: diff the permissions baseline, not just the current state​

settings.json's permissions.allow list is committed, which means it has a real history you can diff against — a known-good baseline is not a document you have to invent, it's a prior commit:

git log --oneline -- .claude/settings.json | tail -5
git diff 942fccf HEAD -- .claude/settings.json
Expected output
@@ -34,6 +34,14 @@
           {
             "type": "command",
             "command": "$CLAUDE_PROJECT_DIR/scripts/hooks/change-gate.sh"
+          },
+          {
+            "type": "command",
+            "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/deny-cluster-mutation.sh"
+          },
+          {
+            "type": "command",
+            "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/release-gate-secops.sh"
           }
         ]
       }

Two hooks added since the repository's early state — both are legitimate, reviewed additions in this case, and the diff is how you'd know either way. The permissions.allow array itself carries the wider risk in a real team: anyone with commit access can add a line broadening what runs without a prompt, and unless someone is diffing this file against a baseline the same way you just did, that widening is silent.

Write it down: your supply-chain audit​

Four audits, read but nowhere recorded, are four things the next person on your team has to re-derive from scratch. Save what you found to agentops/secops/supply-chain-audit.md, one section per component, each stating what it declares, what it actually does, and whether the two agree:

mkdir -p agentops/secops
cat > agentops/secops/supply-chain-audit.md <<'EOF'
# Supply-chain audit — agentic-ops-lab, [today's date]

## MCP servers — advertised tools vs. what the code exposes
platform/mcp-servers/secfindings/tools.json declares read_only: true and three tools, all
"kind": "read" (findings_query, finding_get, corpus_summary). Checked server.js, the file that
actually implements those tools, for any write/mutate call: zero matches for writeFile,
appendFile, or fs.write. The advertised manifest and the actual exposed capability agree — no
undeclared write tool exists behind the read-only claim.

## PreToolUse hooks — what shell each one actually executes
.claude/settings.json registers three hooks on every Bash call: change-gate.sh (blocks
terraform apply / kubectl delete on protected namespaces / --all-namespaces / secret-printing
commands / docker push), deny-cluster-mutation.sh (blocks mutating kubectl verbs), and
release-gate-secops.sh (blocks a deploy/apply-shaped command while verdict.json records an
unresolved critical). All three resolve to real, executable files — read, not just registered.

## Plugin component inventory — declared vs. on-disk
superpowers@claude-plugins-official declares 14 skills, 0 agents, 1 hook (SessionStart), 0 MCP
servers. find on the plugin's cache directory confirms 14 SKILL.md files — the count matches.
The one declared hook's own hooks.json shows it fires on startup|clear|compact and runs
run-hook.cmd session-start under bash on every one of those events, not just once at install.

## settings.json permissions.allow — diffed against a known-good baseline
git diff against the repository's early commit (942fccf) for .claude/settings.json shows the
permissions.allow array itself unchanged; the only drift is two new PreToolUse hook entries
(deny-cluster-mutation.sh, release-gate-secops.sh), both legitimate, reviewed additions. No
widening of what commands run without a prompt. Re-run this diff whenever settings.json changes
in review — that is how a silently widened allow list would actually be caught.

## Conclusion
Every component checked today matches its own declaration. That is a point-in-time result, not
a standing guarantee — the next plugin update or MCP server change needs the same four checks
re-run, not assumed to still hold.
EOF

What this audit does and does not prove​

Every check above answers "what does this component declare, and does the code match the declaration, right now." None of them answer "will this still be true after the next npm update or the next time this plugin publishes a version." Provenance, the way M3 defines it, is a claim about origin and trust checked at a point in time — it is not a guarantee that holds forward. A plugin that passed this exact audit today can ship a new hook in its next release; the MCP server's server.js can gain a write function in a future commit. The honest conclusion is not "audited once, therefore safe" — it's "here is what was true when this was last checked, and here is the exact command to re-check it."

Where you will use this​

  • Before installing any plugin, not just after. claude plugin details <name> before you install tells you the component inventory up front — skills, agents, hooks, MCP servers — the same summary you read in Audit two, before you've given it a single session to run in.
  • Any time a session behaves differently than expected right after /clear or a compaction. A SessionStart hook from a plugin you forgot you installed is a real, non-hypothetical explanation, and you now know the exact file to check.
  • Reviewing an MCP server before you add it to .mcp.json. Read its declared tool list the way you read tools.json here, then grep its implementation for a write verb the declaration doesn't mention — the same two-step check, on someone else's server.
  • Auditing settings.json in code review. A widened permissions.allow line is easy to miss reading a diff cold; git log on that one file, over time, is a five-second habit that catches drift the same way this page's fourth audit did.

Write the audit down​

Four audits, one artifact. Record what you found in agentops/secops/supply-chain-audit.md, because a supply chain you audited once and never wrote down is a supply chain you will audit from scratch next quarter — and you will not remember what "normal" looked like.

mkdir -p agentops/secops
$EDITOR agentops/secops/supply-chain-audit.md

Give every component the same three columns, because the whole point is the gap between the middle one and the last one:

ComponentWhat it declaresWhat it actually doesAgree?

Cover all four surfaces you just walked:

  1. Plugin skills — the skills the installed plugin brought in, and for each one whether its SKILL.md description matches what its scripts run.
  2. MCP servers — every server in .mcp.json, its advertised tool list from tools/list, and whether the implementation exposes anything the manifest does not mention. Name the servers.
  3. Hooks — every PreToolUse hook and the shell it actually executes. Name all three: change-gate, deny-cluster-mutation, release-gate-secops. A hook is arbitrary shell that runs on every tool call; "I forgot that one was there" is the finding.
  4. settings.json — diff the live permissions.allow list against a known-good baseline and record any drift. A widened entry is one line in a diff and a permanent change to what runs without asking you.

Close the file with the one that matters most: which of the four did you not know was there before you looked? That answer is the audit's real output. The components were never the risk on their own — not knowing what you had installed was.
