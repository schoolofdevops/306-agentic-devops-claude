Agentic SecOps: the Agent as Security Analyst

Northstar ships Friday. Two scanners have already run against the platform — trivy against both services and the fault fixture, gitleaks against the whole repository, including its history — and between them they produced dozens of findings: dependency CVEs, a committed credential, an open network policy, a wildcard RBAC grant. Nobody has time to fix all of it before Friday. Somebody has to decide what actually blocks the release, and defend that decision with evidence.

That somebody is you, and the agent you point at this problem. By the end of this module you will have run a fleet of specialist roles against Northstar's real scan output, watched them disagree with a scanner's own severity ranking, synthesized their findings into one ship/no-ship verdict, and proven that a deterministic hook — not a person remembering to check — is what actually stops the deploy while a real finding stands.

A scanner finds everything and decides nothing​

This is the idea the whole module rests on, and it is worth stating once, plainly, before anything else:

Detection is deterministic and belongs in a gate. Prioritization is judgment and must be evidenced.

trivy and gitleaks are good at the first half. Run them against platform/secfixtures/vulnerable-service and you get a flat table: 1 CRITICAL, 7 HIGH, 8 MEDIUM — 16 findings, sorted by CVSS score, highest first. That table is complete and it is also useless for the actual question on the table, which is what do we fix before Friday. A scanner cannot tell you whether the CRITICAL finding at the top of its own list is code anything calls.

Think of it the way an emergency room triages patients. The nurse at the door does not treat people in the order they arrived loudest — she checks vitals, because volume and severity are not the same signal. A CVSS score is the volume. Reachability, exposure, and blast radius are the vitals. An agent that reads the scanner's table top to bottom and starts fixing from the top has skipped the vitals check.

The two numbers that make the point​

Northstar's fault fixture, platform/secfixtures/vulnerable-service/, pins two vulnerable packages on purpose, and they are deliberately picked to disagree with each other's CVSS score:

  • CVE-2020-14343, PyYAML 5.3.1, CVSS 9.8 CRITICAL. Grep the entire fixture for import yaml and you get zero matches. Nothing in this service imports or calls the yaml module. It is a pinned dependency nobody touches — dead weight on a code path that doesn't exist.
  • CVE-2023-32681, requests 2.19.1, CVSS 6.1 MEDIUM. app.py:8 imports requests; app.py:17 calls requests.get(url, timeout=5) inside the handler for GET /proxy/vendor-feed — a public, unauthenticated route where the storefront supplies url directly. The CVE (a Proxy-Authorization header leak on cross-host redirect) sits on a path an internet caller reaches directly.

Rank these by CVSS and PyYAML wins by 3.7 points. Rank them the way this module teaches and requests wins, because reachability comes first: a CRITICAL finding on a path nothing reaches is not a release blocker, and a MEDIUM finding on a path anyone on the internet can hit is. That reversal — not the scanner output itself — is the deliverable this module is built to produce.

A third finding sharpens the point further. gitleaks finds a committed AWS key, a database password and a GitHub token in fixtures/seed-data/prod-secrets.env, in a single commit that nothing since has touched. A scanner can tell you the string is in the repository. It cannot tell you whether the credential is still live — that is a fact only the issuing system can supply, and the honest finding says so rather than guessing in either direction.

And a fourth finding only shows up when you read two tools together. platform/policies/network-policies.yaml carries an allow-all-ingress NetworkPolicy — no source restriction at all. platform/rbac/agent-readonly.yaml grants get/list/watch on resources: ["*"], which includes Secrets, bound cluster-wide. Neither manifest alone is the finding: an open network with nothing valuable reachable through it is low value, and a Secret-readable identity nothing can reach is also low value. The finding is the correlation — any pod reachable across that open network can use that identity's token to enumerate every Secret in the namespace. It is the same lesson as a building with an unlocked front door and an office key that opens the safe: neither fact alone is dangerous, and together they are the whole story.

What you're handed, and what you own​

This is an operate project, not a build project. Unlike Module 11, you are not handing a brief to a harness and watching it design something from scratch. The kit — every role, every skill, the hook, the scanners — already exists in this repository, committed by the platform team before you open a session:

PieceWhat it isAuthority
dep-triageOwns dependency/image CVEs. Its real job is reachability — not severityRead-only
secret-triageOwns committed credentials — what they unlock, rotation evidenceRead-only
posture-auditorOwns cluster + IaC posture — correlates manifests a single scanner can'tRead-only
security-reviewerSynthesizes the three specialists into one ranked list + verdictRead-only
remediation-engineerThe only role that can Edit/Write — fixes what the reviewer approvesRead/Write
secfinding-style skillThe fixed finding schema and ranking rubric every role emits to—
reachability-check skillDeterministic grep for a real import + call site, with file:line evidence—
secops-triage skillOrchestrates the fan-out and the handoff to security-reviewer—
release-gate-secops.shPreToolUse hook: denies a deploy while agentops/secops/verdict.json records an unresolved critical—

What you own: the brief, the ranked findings with an exploitability rationale for each, the ship/no-ship decision, and a measurement of where the agent's reasoning missed something — never the kit itself.

The house standard: a schema, not a narrative​

Four independent reports — dependencies, secrets, posture, plus whatever security-reviewer finds on its own read — cannot be merged if each one is free-form prose. secfinding-style fixes every finding into the same nine fields:

finding · source_tool · component · reachable · exposure · compensating_control · rank · evidence · confidence

And it states the ranking rule as plainly as the rule at the top of this lesson: reachability, then exposure, then blast radius — never CVSS alone. reachable: no sinks a finding to the bottom regardless of severity. Among reachable findings, internet-facing outranks internal-only. Among findings tied on both, what the finding unlocks breaks the tie. CVSS rides along as metadata in the finding field's prose; it is never the sort key. If a role's ranked list matches the CVSS order, that is not confirmation — it is the sign the role skipped the rubric and needs to be sent back.

reachability-check is the piece of this that is not judgment at all — it is a deterministic grep for a real import and a real call site, with file:line as the evidence:

$ .claude/skills/reachability-check/scripts/reachability-check.sh \
    --lang py --import yaml --root platform/secfixtures/vulnerable-service
reachable=no
reason=no import of 'yaml' found under platform/secfixtures/vulnerable-service

$ .claude/skills/reachability-check/scripts/reachability-check.sh \
    --lang py --import requests --root platform/secfixtures/vulnerable-service
import: platform/secfixtures/vulnerable-service/app.py:8:import requests
call: platform/secfixtures/vulnerable-service/app.py:17:    resp = requests.get(url, timeout=5)
reachable=yes
reason=import and call site both found under platform/secfixtures/vulnerable-service

No model judgment went into either answer. That is on purpose — reachability is a fact you can check mechanically, and a role that "eyeballs" it from a CVE description instead of running this script is guessing, not triaging.

The composition: this is where M1–M10 add up to one capability​

No single scanner does the correlation above, and no pipeline does it either, because it needs a system that reads Go, Python, RBAC and a Terraform plan together and produces a judgment it can defend. That is only buildable because the first ten modules of this course already exist:

FoundationWhat this module does with it
M2 permissions/postureTriage runs read-only. The specialists can find a fix; only remediation-engineer can apply one
M3 context + evidenceA few hundred findings do not fit one context window. Bounded reads per finding class, evidence cited per claim
M4 model + costdep-triage/secret-triage/posture-auditor run Sonnet; security-reviewer's synthesis runs Opus — the step where a missed subtlety is most expensive gets the strongest model
M5 plan/execute/verifyThe brief goes in first; the ranking gets checked against ground-truth.md, not accepted from the summary
M6 skillssecfinding-style carries the fixed schema that turns four reports into one rankable list
M7 tool interfaceScanners as CLI (they're batch producers of bulk output — no round-trip benefit from a typed surface); the scan corpus as MCP where available (a capability that exposes no write verb cannot be misused); the house standard as a skill
M8 hooks/policyrelease-gate-secops.sh — deterministic detection, gating a judgment call it never makes itself
M9 rolesSeparation of duties: four read-only roles report; only remediation-engineer writes
M10 orchestrationFan out one specialist per finding class, then synthesize — because the classes are independent and the combined output does not fit one context

Strip any one of these out and the module degrades into "run a scanner and read the output." The composition is the actual lesson.

Fan out, then synthesize — and don't let synthesis agree with CVSS​

The three specialists triage independently, in parallel, each reading only its own finding class:

On a live run against Northstar's real fault set, dep-triage correctly ranked the reachable requests CVE first and the unreachable PyYAML CVE last. secret-triage correctly refused to guess whether the committed credentials were still live, and flagged that deleting a file does not rotate a key. posture-auditor correctly correlated the open NetworkPolicy with the wildcard RBAC grant into one finding.

But the specialists are not infallible, and this is where separate accountability earns its keep: security-reviewer, doing its own independent read while synthesizing, found a cluster-admin ClusterRoleBinding on the namespace's default ServiceAccount — a real finding none of the three specialist packets caught, because dependency, secret, and posture triage each stayed inside its own lane. Synthesis is not a rubber stamp on three reports; it is itself an audit. A security-reviewer that only merges what it's handed and never re-checks the system has skipped the job the role exists to do.

The failure mode to watch for is the opposite direction: a synthesis that quietly restores CVSS order because a specialist's report "looked" more severe. If security-reviewer's ranked list ever matches the raw scanner table, that is not agreement — it is the whole module's thesis failing at the last step.

Detection is a gate; the verdict is what it reads​

release-gate-secops.sh is a PreToolUse hook, registered alongside this repository's existing change-gate.sh and deny-cluster-mutation.sh hooks. It inspects a proposed kubectl apply / helm upgrade / terraform apply-pattern command, and only then reads agentops/secops/verdict.json. If that file records a finding at rank: 1 (or severity_class: "critical") whose status is not "resolved", it denies. Otherwise it allows.

One field in that verdict is worth reading closely: severity_class. It is not trivy's CVSS label — it is security-reviewer's own priority judgment, written down after applying the reachability rubric. On Northstar's fault set, the PyYAML finding carries severity_class: "informational" despite a CVSS of 9.8, and the reachable requests finding carries severity_class: "critical" despite a CVSS of 6.1. The hook only understands the reviewer's language. It never reads a raw scanner score. That is the module's thesis made mechanical: the gate is deterministic, and the only thing it is deterministic about is a judgment call a role already made and wrote down.

Proven directly, against a verdict recording an open, rank-1 finding:

$ echo '{"tool_name":"Bash","tool_input":{"command":"kubectl apply -f platform/helm/orders-api"}}' \
    | .claude/hooks/release-gate-secops.sh
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":
"verdict at agentops/secops/verdict.json records 2 unresolved critical finding(s) — release blocked
until security-reviewer marks them resolved"}}

Fail-closed matters here too: no verdict file at all denies, the same as an unresolved critical. A deploy attempted before any review has run is exactly the case a release gate must not wave through.

The fan-out that did not happen​

Everything above describes four specialists reading four finding classes independently. When this lab was first graded, zero subagents were dispatched. One session worked dependencies, then secrets, then posture, by itself, in sequence.

It produced a good ranked list, which is what makes this worth a section. Nothing in the output said the architecture had not run.

Two causes, neither of them the model's:

  • The reviewer had no dispatch tool. Its bundle was ["Read","Grep","Glob","Bash","Skill"]. A tool list is provisioning — an agent cannot delegate a capability it was never granted, and it does not announce the gap. It just does the work itself.
  • The specialists' own reporter was not allow-listed. reachability-check.sh prompted for approval on every call, so the honest path was blocked and the agent routed around it — the same failure the hooks module measures.

The fix is two lines: add Task to the reviewer's tools, and put the read-only reporters in permissions.allow. Re-run and three subagents dispatch — dep-triage, secret-triage, posture-auditor — in seven reviewer turns and twenty-two seconds, returning a no-ship verdict on three reasons, none of them CVSS-driven. Same roles, same prompt, same model. Only the provisioning changed.

Declared Task, invoked as Agent

You declare the dispatch tool as Task and system/init echoes Task — but the transcript shows the model calling it as Agent, with a subagent_type. The declared name and the invoked name differ, so a check that greps for Task in the transcript finds nothing and concludes, wrongly, that no fan-out occurred. Same class of surface-name drift as Grep and Glob.

What fan-out actually buys. Not savings — three lanes cost more tokens than one session doing three jobs. It buys wall-clock, and it buys independence: each subagent starts with its own context and tool list, so the secrets specialist cannot inherit the dependency specialist's conclusion, because it never saw it. One session carrying every lane forward is how a ranked list ends up agreeing with itself rather than with the evidence. If you cannot say which of those two you needed, you have not justified the architecture.

What you'll do in the lab​

  1. Confirm the scanners and the corpus. trivy and gitleaks, pinned versions, already run against both services and the fault fixture.
  2. Inspect the kit — every role's tool list, every skill, the hook's registration — the same discipline as every operate module: confirm what's actually here before trusting it.
  3. Write your brief to agentops/secops/SPEC.md: what "done" means for Friday's release review.
  4. Fan out: run dep-triage, secret-triage, and posture-auditor, each against its own finding class, and capture their schema'd handoffs.
  5. Synthesize: launch security-reviewer with all three packets and get one ranked list plus a ship/no-ship verdict.
  6. Save the verdict to agentops/secops/verdict.json and the ranked findings to agentops/secops/findings.md — security-reviewer has no Write tool on purpose, so this save is yours.
  7. Prove the gate: a deploy command against the real verdict, denied; the same command against a verdict with the criticals marked resolved, allowed.
  8. Check your findings against ground-truth.md, and record every miss — yours and the agent's.

The Deep Dive that follows turns the same question on your own tooling: what did you install, what does it actually do, and how would you know if it changed?
