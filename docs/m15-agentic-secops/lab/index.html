Lab — The Friday Release Review

Northstar ships Friday. trivy and gitleaks have already run against both services, the fault fixture, the cluster manifests, and the infrastructure plan. Between them they produced dozens of findings. Nobody has time to fix all of it before Friday. You are going to fan a specialist role out per finding class, synthesize their reports into one ranked list with a ship/no-ship verdict, and prove that a deterministic hook — not someone remembering to check — is what actually stops the deploy while a real finding stands.

This is an operate lab, not a build lab. Every role, every skill, the hook, and the scan corpus already exist in this repository, committed by the platform team before you open a session. Your job is to inspect the kit, run it, synthesize what it finds, and measure where it was wrong — never to author the kit itself.

By the end you will have four schema'd findings packets, one ranked list with a ship/no-ship verdict, a proven release gate, and a written record of what the specialists' fan-out missed and what synthesis caught.

Where you are working

Every command in this lab runs from the root of the agentic-ops-lab workspace you cloned in setup:

cd ~/agentic-ops-lab

Step 0 — The ticket, and the posture for this lab​

The ticket, as it would actually arrive: release review is Friday, the scanners already ran, and nobody has ranked the output yet. Every role you launch in this lab is read-only except the one you never launch — remediation-engineer stays out of scope here; this lab ends at the verdict, not the fix.

Because every specialist role you run is read-only by tool list (no Edit/Write declared at all), there is nothing here for a permission prompt to protect that RBAC or the tool list doesn't already protect. Run each specialist headless, with a bounded prompt, so the fan-out doesn't require four open terminals:

claude --agent dep-triage --model claude-sonnet-5 --dangerously-skip-permissions -p "..."

The flag is there because a headless run cannot answer a prompt, and these roles shell out to jq, grep and the reachability script on every finding. It is the right call here and it is worth being precise about why: the role carries no Edit or Write tool at all, so skipping the permission check removes a prompt that was never the control. On a role that could write, the same flag would be a different decision entirely — Module 8's hooks still refuse under it, and nothing else does.

You won't run that yet — Step 3 inspects the kit first. Read on.

Step 4 — Write your brief​

The brief is yours, and this is the one step nobody can do for you. The specialists decide which findings matter; you decide what the review is for, what it may not compromise on, and when it is finished. An agent that writes its own definition of done has not been given one.

Make the directory, then write agentops/secops/SPEC.md. What follows is the structure and the non-negotiables this lab depends on — type it, and change the wording where your judgment differs:

mkdir -p agentops/secops
# Friday release review — northstar

## Why
Two scanners have produced dozens of findings across both services, the fault fixture, the
cluster manifests and the infrastructure plan. Nobody has ranked them, and release is Friday.

## What's non-negotiable
- Every finding is ranked by reachability x exposure x blast radius — never by CVSS alone.
- Reachability is never eyeballed from a CVE description; the reachability-check skill
  produces the yes/no/unknown verdict with file:line evidence.
- Triage stays read-only. Only remediation-engineer may edit or write, and only against a
  verdict this review has already approved.
- The ranked list is checked against platform/secfixtures/ground-truth.md before it is trusted.

## Done means
- dep-triage, secret-triage and posture-auditor have each produced a schema'd findings packet.
- security-reviewer has synthesized all three into one ranked list and a ship/no-ship verdict,
  saved to agentops/secops/verdict.json and agentops/secops/findings.md.
- The release-gate-secops.sh hook has been proven to deny a deploy while the verdict records an
  unresolved critical, and to allow one once it doesn't.
- Every place the agent's ranking disagreed with ground-truth.md is recorded, not smoothed over.

Read the second bullet again before you move on. "Reachability is never eyeballed from a CVE description" is the constraint the whole module turns on, and you are writing it before you have watched an agent be tempted to break it.

Why this is SPEC.md and not a CLAUDE.md

A CLAUDE.md is injected into every turn of every future session in this directory, forever — right for a standing fact, wrong for a brief about this Friday's release. SPEC.md is a one-time input to one review; once the verdict ships, nothing keeps re-reading it.

Step 5 — Fan out: one specialist per finding class​

Three independent lanes, each reading only its own finding class. Run them one at a time or in separate terminals — they don't depend on each other:

This is exactly what the first graded run of this module did. Captured before the kit was fixed, security-reviewer carried ["Read","Grep","Glob","Bash","Skill"] — no dispatch tool — and the run dispatched zero subagents. One session worked dependencies, then secrets, then posture, itself, in sequence. It produced a good ranked list. The lab said four specialists, the run was one agent four times, and nothing in the transcript said so.

A tool list is provisioning. An agent cannot delegate a capability it was never granted, and it will not tell you it is missing — it will do the work itself and hand you a plausible answer.

A second piece of provisioning does the same job quietly, and you have met it already:

jq -r '.permissions.allow[]' .claude/settings.json | grep -E 'reachability-check|scan\.sh' \
  || echo "NO SECOPS REPORTER IS ALLOWED"
Expected output
Bash(.claude/skills/reachability-check/scripts/reachability-check.sh:*)
Bash(platform/secfixtures/scan.sh:*)

Both allow-listed. On the first graded run neither was, so the specialists' own deterministic reporter prompted for approval on every call — the honest path blocked, and a blocked agent substitutes something else. That is the same failure the hooks module measures.

The two lines that made the difference, for when you build this yourself:

python3 - <<'FIX'
import json, pathlib
a = pathlib.Path('.claude/agents/security-reviewer.md'); t = a.read_text()
a.write_text(t.replace('tools: ["Read", "Grep", "Glob", "Bash", "Skill"]',
                       'tools: ["Read", "Grep", "Glob", "Bash", "Skill", "Task"]'))
s = pathlib.Path('.claude/settings.json'); d = json.loads(s.read_text())
for e in ["Bash(.claude/skills/reachability-check/scripts/reachability-check.sh:*)",
          "Bash(platform/secfixtures/scan.sh:*)"]:
    if e not in d['permissions']['allow']: d['permissions']['allow'].append(e)
s.write_text(json.dumps(d, indent=2) + "\n")

Your figures will differ. What should not differ is the count: three dispatches, or the fan-out did not happen and the rest of this lab is one agent wearing four hats.

What fan-out buys, and what it costs

Three lanes cost more tokens than one session doing three jobs, not fewer. You are not buying savings. You are buying wall-clock and independence — each subagent starts with its own context and tool list, so the secrets specialist cannot inherit the dependency specialist's conclusion, because it never saw it. A single session carrying every lane forward is how a ranked list ends up agreeing with itself instead of with the evidence.

If you cannot say which of those two you needed, you have not justified the architecture.

Which model for this lab, and why​

Most of this lab is running scripts and reading JSON — trivy, gitleaks, reachability-check, jq. None of that needs a frontier model. The three specialist roles are pinned to Sonnet in their own role files: bounded, schema-constrained triage over one finding class at a time. security-reviewer is pinned to Opus deliberately — synthesizing four independent reports into one ship/no-ship call, and catching a finding the specialists missed, is exactly the step where a missed subtlety is most expensive.

Limits — what this triage does and does not give you​

  • A verdict is a judgment, and the gate enforces it without re-checking it. release-gate-secops.sh reads severity_class from verdict.json — security-reviewer's own priority call, never a scanner score. That is the design, and it means a wrong verdict blocks nothing. The gate makes a judgment stick; it does not make it right.
  • Reachability is a static answer to a dynamic question. The skill proves no code path imports yaml in this fixture today. It cannot see a plugin loaded by name, a dependency that imports it transitively at runtime, or the next commit. reachable: no has a shelf life.
  • "Is this credential still live?" is not answerable from here. secret-triage refused to guess, and that refusal is the correct output. Only the issuing system knows, and deleting the file does not rotate the key — a finding the packet must state rather than imply.
  • The fan-out has blind spots by construction. Each specialist stays in its lane, which is what makes the packets independent and is also why security-reviewer found a cluster-admin binding that none of the three caught. Synthesis has to be its own audit. If your reviewer only merges, nobody is looking across the lanes.
  • Ground truth exists here and will not at work. Step 8 checks your ranking against ground-truth.md. On a real release review there is no key, and the only available check is whether the evidence for each rank survives someone else reading it.
  • The scanners are pinned and the corpus is fixed. Two scanners, one fixture, one point in time. A finding class neither trivy nor gitleaks emits does not exist in this lab, and the ranking method is only as complete as the detection feeding it.

Step 9 — Take it to your own release review​

The transferable artifact is the rubric, not the roles. Most teams already have more findings than time; what they lack is a written, defensible order.

In a repository you ship from:

Take the most recent scanner output we have — dependency, secret or posture, whatever
exists. For the top five findings by the tool's own severity, tell me for each one:

1. Is the vulnerable code path reachable from anything we actually run? Name the file
   and line, or say you could not determine it.
2. Is that path exposed to anything outside our network?
3. What is the blast radius if it is exploited?

Then re-rank the five by those three answers instead of by severity, and show me
every place your order disagrees with the scanner's. Read only.

What you observe. The disagreements are the output. If your re-ranked list matches the scanner's order exactly, either the tool got lucky or the agent skipped step 1 and rationalised the original ranking — check the evidence fields before you believe it. And the findings where the honest answer to (1) is "could not determine" are the most useful of all: they are the ones where somebody has to go and look, and now you know which ones deserve the hour.

The second thing to port is the gate. A verdict file nothing reads is a document; the value appears the moment a deploy path refuses to run while a rank-1 finding is open.

Teardown​

Nothing here stood up a cluster or a container — every command in this lab reads files. There is nothing to tear down except the temporary verdict you used to prove the allow path:

rm -f /tmp/verdict-resolved.json /tmp/dep-triage-out.txt /tmp/secret-triage-out.txt \
  /tmp/posture-auditor-out.txt /tmp/security-reviewer-out.txt

Your agentops/secops/{SPEC.md,dep-triage.json,secret-triage.json,posture-auditor.json,verdict.json,findings.md,measurement.md} are the deliverable — leave them in place. ./scripts/grade.sh m15 checks all of it: that the kit holds the tool boundaries it claims, that your verdict and findings exist and are internally consistent, and that the hook denies and allows on exactly the conditions this lab proved.
