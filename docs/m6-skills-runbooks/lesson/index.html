Agent Skills

By Module 5 you could run one change end to end under a contract: intent agreed up front, plan reviewed before any edit, work isolated in a worktree, the repository deciding when it was done. That was a procedure. And you carried the whole thing in your head and your prompts, re-typing it each run. This module takes a procedure you run more than once and turns it into a named, versioned, testable artifact the agent can invoke: a skill. The team already has these procedures written down. They are called runbooks, and most of them are prose a human reads and executes by hand. A skill is that runbook rebuilt so an agent can execute it the same way every time, and so you can test that it does.

Here is the gap this closes. Your runbooks/ directory has a file called service-restart.md and another called db-connection-issues.md. They are institutional knowledge, and they rot. One of them, stale-runbook-wrong-endpoint.md, tells you to check http://localhost:8080/api/v1/status, an endpoint that does not exist; the service moved to /healthz and /readyz and nobody updated the doc. A prose runbook has no way to fail loudly when it drifts. A skill does: it is executed, so a wrong command errors, and it is tested, so drift shows up as a red check instead of a confused engineer during an incident. This module is about building the first five skills for Northstar Commerce, and, just as much, about choosing which procedures deserve to become skills at all.

The primitive question: skill, or something else?​

Before you build a skill, you have to know a skill is the right tool. Claude Code gives you five ways to steer an agent's behaviour, and reaching for the wrong one is the most common mistake in this whole area: people write a skill for something that should have been one line in CLAUDE.md, or paste a procedure into a prompt for the tenth time when it should have been a skill.

Analogy: think of how a kitchen encodes knowledge. A standing rule taped to the wall, "always wash hands before handling food", applies to everyone, always, and no one asks for it; that is a rule. A recipe card in a box, pulled out and followed step by step when you cook that dish; that is a skill. A verbal instruction to one cook for tonight only, "go easy on the salt, the customer asked", gone tomorrow; that is a prompt. A specialist you hand an entire station to, "you run the grill, I don't want to think about it", with their own tools and their own focus; that is a subagent. And the physical equipment, the oven, the mixer, a capability the kitchen simply has; that is a tool. You would not tape a recipe to the wall (rules are for what is always true), and you would not hire a grill specialist to pass one cook a note about the salt (that is a prompt). Matching the knowledge to the right encoding is the whole skill being taught here.

Here is the same distinction as a decision:

You need to encode…UseWhy this one
A convention that is always true in this repoCLAUDE.md ruleAlways loaded, no invocation: the agent should never not know it
A one-off instruction for this run onlyPromptEphemeral by design; persisting it would be noise
A procedure you run more than once, with stepsSkillNamed, versioned, testable: invoked when relevant
A whole task you want handled in isolationSubagentIts own context and role; keeps the main thread clean
A new external capability (an API, a system)MCP toolA typed boundary to something the agent otherwise cannot reach

The line that catches most people is the one between a rule and a skill. A rule is a fact the agent should always hold: "the inventory-api health endpoint is /healthz, never /health." A skill is a procedure the agent runs when asked: "check whether a service is healthy." The rule has no steps and no invocation; the skill has both. If you find yourself writing steps into CLAUDE.md, that is a skill trying to escape. If you find yourself writing a fact into a skill's frontmatter, that is a rule in the wrong place. The rest of this module is about the box in green: the procedures that genuinely are skills, and how to build them so they hold up.

What a skill actually is​

A skill is a directory under .claude/skills/ with a SKILL.md file inside it, optionally alongside scripts and templates the procedure needs. The SKILL.md has two parts: frontmatter that tells Claude Code when the skill applies, and a body that is the procedure itself.

---
name: service-health
description: Use when you need to check whether a Northstar service is healthy and report its status, before a deploy, during triage, or on a health complaint.
---

## Inputs
- service: which service to check (orders-api | inventory-api)

## Steps
1. Collect evidence (deterministic zone): run the health probes, capture raw output.
2. Analyze (reasoning zone): compare healthz vs readyz, name any dependency failure.

## Output schema
{ "service": "...", "healthy": true, "checks": {...}, "recommendation": "..." }

## Stop conditions
- If the service is unreachable, report that and stop. Do not attempt fixes.

The frontmatter matters more than it looks. name is how you invoke it: /service-health. description is how Claude Code decides automatically whether this skill is relevant to what you asked, so it is written as a trigger: "Use when…" followed by the situations that should pull it in. A vague description ("checks health") means the skill never gets auto-selected when it should; a precise one ("Use when… before a deploy, during triage, or on a health complaint") means the agent reaches for it at the right moment. You are writing the description for a reader who is deciding, in one glance, should I use this now?

Frontmatter is a contract, not decoration

The real Claude Code frontmatter has two required fields, name and description. Everything else in the body, Inputs, Steps, Output schema, Stop conditions, is structure you impose because it makes the skill testable and safe, not because Claude Code demands it. Treat those sections as the anatomy every good ops skill has, the way every good change ticket has the same fields. The lab builds all five skills to this same anatomy on purpose.

Progressive disclosure: the skill is a table of contents​

A skill you will actually maintain cannot dump everything into one wall of text. The terraform-plan-review skill, done fully, needs to know how to detect resource replacements, how to spot a stateful resource being destroyed, how to read a cost estimate, how to flag a wide-open security group: that is a lot, and most of it is not relevant to any single run. If all of it loads every time, the skill is expensive and the agent drowns in detail it does not need.

Analogy: progressive disclosure is how a good reference manual is built. The table of contents is short. You can hold it in your head. It does not reproduce chapter 7; it points to chapter 7, and you turn there only when the problem is a chapter-7 problem. A manual that inlined every chapter into the contents page would be useless: you could not find anything, and you would read a thousand pages to answer one question. A skill works the same way. The SKILL.md is the table of contents: short, always loaded, enough to route. The heavy detail lives in separate files and scripts the skill references, pulled in only when that step actually runs.

Concretely: the SKILL.md body stays short and names its steps. A step that needs a deterministic command references a script, scripts/detect-replace.sh, rather than embedding twenty lines of jq. A step that produces a document references a template. The agent reads the short SKILL.md every time and only loads detect-replace.sh when the run actually reaches the replacement-detection step. This is the same budgeting instinct from Module 3, applied one level up: keep the always-loaded surface small, and push detail behind pointers you follow on demand.

Two zones: separate collecting from reasoning​

This is the design idea that makes a skill testable, and it is the one most homemade skills get wrong. Every ops skill does two fundamentally different kinds of work, and mixing them makes the whole thing untestable.

The first kind is collecting evidence: run curl -s http://localhost:8080/readyz, run jq over a plan file, run kubectl get pods. These commands are deterministic: the same input produces the same output, every time, with no judgment involved. The second kind is reasoning about that evidence: "readyz is failing but healthz passes, and the failing check is the inventory dependency, so this is an upstream problem, not an orders-api problem." That is judgment: it is where the model earns its place, and it is not deterministic; two reasonable analyses can differ.

Analogy: this is the wall between the lab and the doctor. The lab draws blood and runs it through a machine: the same sample gives the same numbers no matter who runs it, and you can calibrate the machine against a known reference to prove it is accurate. The doctor reads those numbers and forms a diagnosis, that is expertise, and it varies with the case. A hospital keeps these separate on purpose: you can verify the lab mechanically (run a known sample, check the numbers come back right) precisely because the lab does no interpreting. If the doctor drew and interpreted blood in one inseparable act, you could never check the machine: every wrong number could be waved away as a judgment call. Skills work the same way. The deterministic collection zone is the lab; you can test it mechanically. The reasoning zone is the doctor; you evaluate it differently, on cases.

Why the separation is not optional: if collection and reasoning are tangled together, you cannot write a test for the skill. A test needs a fixed input and a checkable output. But if the command that produces the evidence is buried inside a paragraph of interpretation, there is no clean input to fix and no clean output to check. Pull the collection into its own zone (ideally its own script) and it becomes a function: feed it a known plan fixture, assert it detects the one replacement. The reasoning zone, sitting downstream of captured evidence, can then be exercised on that same fixed evidence without re-running the world. The two-zone structure is what lets the next section, testing, even exist.

Invocation: who can trigger this skill, and where it runs​

A skill can be invoked two ways, and the difference matters most for skills that change something.

Automatic invocation means Claude Code, reading your request and the skill's description, decides on its own that the skill is relevant and runs it. This is the point of a good "Use when…" description: it lets service-health fire the moment you say "is orders-api okay?" without you naming the skill. Auto-invocation is right for skills that only observe: collect evidence, report, recommend. If service-health runs when you did not strictly ask, the worst case is you get a health report you did not need.

Human-only invocation means the skill runs only when a person types /skill-name deliberately. This is the correct setting for any skill that has side effects: restarts a service, applies a manifest, scales a deployment. You do not want a skill that mutates production state to fire because the agent inferred it was relevant. The trigger for a state-changing action should be a human's explicit choice, not the model's relevance judgment. (This is the same instinct as Module 2's boundaries and Module 5's human-in-the-loop, now expressed at the skill level.)

context: fork is a third dimension. A forked skill runs in an isolated context: it does its work, and only its result comes back to your main conversation, not all the intermediate tool output. This is the Module 5 worktree idea applied to context instead of the filesystem: a skill that reads fifty log lines and twenty kubectl outputs to produce a three-line verdict should fork, so your main thread gets the verdict and not the fifty log lines. It keeps the reasoning context clean.

The invisible-side-effect trap

There is a subtle failure the Deep Dive is entirely about, so hold the thread now. A skill that should be human-only because it has side effects, but that you leave auto-invokable, is a hazard: the agent can fire a mutation you never asked for. And the fix is not what most people reach for. Making the skill human-only does keep the agent from auto-firing it, but it does not make the side effect safe: when a human does invoke it, the skill still runs under the same tool and permission boundaries from Module 2. A skill is not a way around your permissions. It runs inside them. The Deep Dive tests exactly this: the side-effecting skill that is invisible to automatic invocation, and that still cannot escape the environment's policy even when a human triggers it.

Testing a skill: positive, negative, ambiguous​

A skill you have not tested is a runbook you are hoping is still correct, which is exactly the stale-runbook-wrong-endpoint.md situation you are trying to escape. Because you separated the deterministic zone, you can test, and there are three cases every skill needs.

Analogy: this is how you test a smoke detector, and it is deliberately three tests, not one. You press the button and confirm it sounds. That is the positive test: given the thing it is for, does it fire? You also wave clean air at it and confirm it stays silent. That is the negative test: given a situation it should ignore, does it correctly do nothing? And a good detector handles the in-between, a wisp of steam from a shower, without either screaming or going dead; it signals uncertainty rather than committing to a false verdict. A detector that only ever passes the first test is worse than useless, because you have proven it can make noise but not that it can tell smoke from air. A skill is the same: proving it produces output on a good case tells you almost nothing until you also prove it catches the bad case and hesitates on the unclear one.

TestYou give the skill…It must…What it proves
PositiveA known-good scenario (healthy service, clean plan)Report healthy / no findingsIt recognizes "fine" and does not invent problems
NegativeA known-bad scenario (the replace fixture, a failing readyz)Catch the specific problemIt actually detects the thing it exists to detect
AmbiguousUnclear evidence (a service unreachable, partial data)Report uncertainty or ask, not guessIt fails safe instead of committing to a false verdict

The negative test is the one with teeth. It is easy to write a skill that says "looks healthy". A skill that always says that passes every positive test and is completely worthless. The negative test is what proves the skill can tell good from bad: you hand terraform-plan-review the plan-stateful-replace fixture, which destroys and recreates the production database, and if it does not flag that as a high-blast-radius replacement, the skill has failed no matter how good its prose is. The ambiguous test keeps the skill honest under uncertainty: you make the service unreachable and confirm the skill says so and stops, rather than confidently reporting a health status it could not actually measure. These three cases are why the two-zone design was worth the trouble: the deterministic zone gives you fixed inputs to build each case from.

What you'll do in the lab​

You will build the first five skills for Northstar Commerce, each to the two-zone, testable structure:

  1. service-health: probe /healthz and /readyz, report status and any dependency failure.
  2. terraform-plan-review: read a plan JSON from infra/fixtures/, flag replacements, blast radius, and cost.
  3. k8s-diagnose: check pod status, events, and logs for the common failure patterns.
  4. release-check: verify services healthy, tests pass, and no uncommitted changes before a release.
  5. incident-triage: read an incident ticket, collect bounded evidence, and produce an evidence packet.

For each you will write the SKILL.md with inputs, a deterministic collection zone, a reasoning zone, an output schema, and stop conditions, then test it with at least one positive and one negative case against the real spine: real fixtures, real endpoints, real incident tickets. You will make one skill auto-invokable and one human-only, and see the difference. And you will run grade.sh m6 to let the repository confirm the five skills exist and hold their structure. The Deep Dive then takes the invisible-side-effect thread from the warning above and tests it directly: a side-effecting skill that automatic invocation cannot see, and that, even when a human runs it, cannot step outside the tool and permission policy the environment enforces.
