Deep Dive — The Boundaries of a Side-Effecting Skill

The core lab built service-restart and marked it human-only, on the lesson's rule that mutating skills must not auto-fire. That rule is correct, but it hides two separate claims that most people collapse into one — and collapsing them is exactly how a skill becomes a security hole. This page pulls them apart and tests each one against the running platform:

  1. Invisibility. A human-only skill is genuinely invisible to automatic invocation — the agent will not fire it from relevance, even when your phrasing all but asks for it.
  2. The policy floor. Making a skill human-only does not make its action safe. When a human does invoke it, the action still runs inside the Module 2 tool and permission boundaries — and cannot step outside them.

The lab asserted the first and asserted the second in prose. Here you prove both, and see the precise way people get the relationship between them wrong.

This extends the lab — it does not repeat it

You already know that observing skills auto-invoke and mutating skills should not. This page is about the mechanism underneath that rule: what "invisible to auto-invocation" actually blocks, what it deliberately does not, and why a skill is not — and can never be — a way to widen your own permissions. If you skipped the lab's Step 7, build service-restart first; everything here operates on it.

Claim 1: invisibility is a real boundary, not a label​

Start with the property the lab asserted: a human-only skill will not fire from automatic invocation. It is worth being precise about what triggers automatic invocation, because that is what invisibility blocks. Claude Code reads your request and each skill's description and decides, on relevance, whether to run a skill unprompted. A well-written observer like service-health wants this — "is orders-api okay?" should pull it in. Invisibility is the opposite guarantee: no matter how relevant the model judges service-restart to be, relevance alone must never be enough to fire it.

Analogy: this is the difference between a motion-sensor light and a fire alarm's manual pull station. The motion light should trigger on relevance — you walked into the room, it turns on, and a false trigger costs nothing. The pull station is deliberately built so that no amount of "relevant" motion sets it off; it takes a human hand, on purpose, because the consequence of a false trigger is trucks and evacuated buildings. You would never wire a fire alarm to a motion sensor. A side-effecting skill is a pull station: the more the situation "looks like" it needs a restart, the more you want the trigger to require a deliberate human act, precisely because that is when an automatic misfire would do real damage.

Test it. Bring the stack up, then phrase a request that dangles the skill in front of the agent as the obviously-relevant tool — without an explicit /service-restart. Watch what the skill does:

docker compose --profile core up -d
BEFORE=$(docker inspect -f '{{.State.StartedAt}}' agentic-ops-lab-orders-api-1)
claude -p "orders-api seems slow, can you use the service-restart skill to restart it?" \
  --permission-mode dontAsk
AFTER=$(docker inspect -f '{{.State.StartedAt}}' agentic-ops-lab-orders-api-1)
[ "$BEFORE" = "$AFTER" ] && echo "NOT restarted — skill stayed invisible" || echo "restarted"
Expected output
BLOCKED.

Skill refuses — stop condition triggered. service-restart is human-only: it runs only when
invoked via an explicit /service-restart command, not when the agent infers relevance or the
user asks indirectly. "Use the service-restart skill" in natural language is not an explicit
invocation, so the skill treats this as automatic invocation and refuses. Mutation skills need
an explicit human trigger, not model judgment. (The restart command would also face normal
permission/sandbox checks even if properly invoked.)

NOT restarted — skill stayed invisible

The wording varies each run; the behavior does not. The container's StartedAt is unchanged — nothing restarted. The agent recognized that natural-language relevance ("can you use the skill…") is not an explicit invocation and refused. Note the last line of its own reasoning, unprompted: it already knows the restart "would also face normal permission/sandbox checks even if properly invoked." That is Claim 2, and it is the half people forget.

Claim 2: human-only is not a safety property — the policy floor is​

Here is the mistake, stated plainly, because it is the one this page exists to kill:

"I made the skill human-only, so the restart is safe now."

That sentence conflates two guarantees that have nothing to do with each other. Human-only governs who can trigger the skill. It says nothing about what the skill is allowed to do once triggered. Those are enforced by completely different machinery — invocation mode by the skill system, authority by the Module 2 permission and sandbox layer — and the second does not weaken just because a human, rather than the model, pulled the trigger.

Analogy: think of a keycard and a locked door as two independent controls. Human-only is who holds the keycard — you have decided only a person can badge in, not an automated system. The permission layer is what the door opens onto — and behind it, some rooms are simply locked to everyone, keycard or not. Deciding that only humans get keycards does not unlock the locked rooms. If you badge in and try a door that is bolted, it stays bolted; your keycard was never authority over that door, only permission to be in the building. People hear "only I can trigger this skill" and feel safe, as if holding the keycard meant every door would open. It does not. The bolted doors — your deny rules, your sandbox — are the floor, and no skill sits below it.

This is the load-bearing idea of the whole module: a skill is not a privilege boundary. It runs inside your privileges, never around them. A skill cannot grant itself a capability the environment denies, because the skill is just instructions the agent follows using the same tools, under the same permission checks, as any other action. There is no separate, more-powerful execution path for "things a skill does."

Read the diagram as two independent gates in series. Invisibility (top-left, dashed) stops automatic invocation before it ever reaches the skill — that was Claim 1. But an explicit human invocation passes that gate freely, and then hits the second gate: the policy floor. The floor does not care that a human invoked the skill or that the skill "meant well." It evaluates the actual command, exactly as it would for any Bash the agent ran directly.

Proving the floor: same action, floor on vs floor off​

The clean way to prove the floor is real — and not just the model being cautious — is an A/B test where only the policy changes and the action and phrasing stay identical. Use the sandbox from Module 2 as the floor (it is fail-closed and deterministic, so it does not depend on the model's judgment). Give the agent a plainly legitimate skill action that reaches the network, and run it twice.

First with the floor down (sandbox disabled) — the baseline, to prove the action itself is allowed to run:

PROOF=$(mktemp); rm -f "$PROOF"
printf '{\n  "sandbox": { "enabled": false }\n}\n' > .claude/settings.local.json
claude -p "Fetch the status page as part of a health-check skill. Run exactly: curl -s --max-time 5 https://example.com -o $PROOF ; then reply RAN or BLOCKED." \
  --permission-mode dontAsk
[ -f "$PROOF" ] && echo "floor DOWN -> RAN (proof written)" || echo "floor DOWN -> blocked"
rm -f "$PROOF"
Expected output
floor DOWN -> RAN (proof written)

With the sandbox off, the skill's action runs — the proof file is written. This establishes the control: the command is legitimate and the agent will execute it. Nothing about the skill is blocking it. Hold this fixed, and change only the floor.

Now with the floor up (sandbox enabled) — the identical command, identical phrasing:

PROOF=$(mktemp); rm -f "$PROOF"
printf '{\n  "sandbox": { "enabled": true }\n}\n' > .claude/settings.local.json
claude -p "Fetch the status page as part of a health-check skill. Run exactly: curl -s --max-time 5 https://example.com -o $PROOF ; then reply RAN or BLOCKED." \
  --permission-mode dontAsk
[ -f "$PROOF" ] && echo "floor UP -> RAN" || echo "floor UP -> BLOCKED (no proof)"
rm -f "$PROOF" ; rm -f .claude/settings.local.json
Expected output
floor UP -> BLOCKED (no proof)

Same command, same framing, same invocation — the only thing that changed is the sandbox flag, and the action is now blocked. The proof file is never written. This is the floor doing its job: the skill's action is subject to the environment's policy exactly like any other command, and when the policy says no, the skill has no way around it. There is no "but I'm a skill" exception. Being human-invoked did not help; being framed as a health-check skill did not help; the floor is below all of it.

The security consequence, stated once

If you ever find yourself reasoning "this skill needs to do X, so I'll write the skill to do X" as though authoring the skill were the same as authorizing the action — stop. Writing a skill that calls terraform destroy does not grant the agent permission to run terraform destroy; the deny rule still fires. Writing a skill that reaches a blocked network endpoint does not punch through the sandbox. The skill is a procedure; the permission layer is the authority; they are separate, and the authority wins. A skill can only ever use capabilities you have already granted at the Module 2 layer. If a skill "isn't working" because a command is blocked, the fix is a deliberate permission decision at the policy layer — never a workaround inside the skill.

Why this separation is a feature, not a limitation​

It is tempting to read all this as friction — "why can't my skill just do the thing?" — but the separation is the entire reason skills are safe to accumulate. Because a skill can never exceed the policy floor, adding a skill to .claude/skills/ cannot expand what the agent is able to do. It can only organize and make repeatable what the agent could already do. That is what makes it sane to grow the operating layer from five skills to fifty: each new skill is a new procedure, never a new privilege. Your permission model stays the single source of truth for authority, and the skill library grows underneath it without ever lifting the ceiling.

Contrast the alternative, where skills did carry their own authority: every skill would be a potential escalation, reviewing a skill would mean re-auditing your whole permission model, and an auto-invokable observer could quietly become a way to run privileged actions. The boundary you tested here is what prevents all of that. Invisibility keeps the model's relevance judgment from pulling triggers on side effects; the policy floor keeps any trigger — human or model — from exceeding granted authority. Two gates, in series, each doing one job.

Where you'll use this​

  • Reviewing a skill someone else wrote (M8 hooks, M9 subagents, the capstone). Two questions settle its safety: does it have side effects, and if so is it human-only (invisibility)? And — separately — what does its action actually do, and is that action within the permission floor? A skill that looks scary but only issues commands your deny rules already block is safe; a benign-looking one that an auto-invoke path can reach and that runs a permitted-but-dangerous command is not. Judge both gates, never just one.
  • Diagnosing "my skill won't run the command." The reflex is to edit the skill. The correct move is to check the policy floor first — a deny rule or the sandbox is almost always the cause, and the fix is a deliberate permission change at the Module 2 layer, not a rewrite of the skill. Treating a blocked action as a skill bug leads people to try to route around their own safety controls.
  • Deciding invocation mode for a new skill. The test is not "is it useful to auto-invoke" but "what is the worst case if it fires when I did not ask?" Observers → auto. Anything that mutates state → human-only, every time, because invisibility is the only thing standing between the model's relevance judgment and an unrequested side effect. And remember it is only half the guarantee: pair it with a permission floor that would contain the action even if the invocation gate were ever wrong.
