Lab — Skills for On-Call Work

You are on call. A page fires, you open a terminal, and you start doing the thing you have done a dozen times: check the obvious endpoints, look at the logs, work out whether the service that is alerting is the service that is broken, and decide whether to wake anyone else up.

This lab is about turning that into something repeatable — not about filling a directory with files. You will triage a real P1 by hand, notice you have done it before, have Claude write down what you just did, and then watch it run the same way on a completely different incident. Along the way you will find out what a skill actually costs you, where it stops helping, and which parts of your job should never be one.

Where you are working

You start at the root of the agentic-ops-lab workspace with the core stack running. scripts/inject.sh gives you two genuinely different incidents to work — a retry storm and a readiness drift — so the skill you write gets tested against something it was not written for. The operating layer already ships several skills under .claude/skills/; you will add one of your own and take one apart.

Where you run everything. All commands below, and every claude session, run from the root of the agentic-ops-lab workspace you cloned in setup:

cd ~/agentic-ops-lab

Step 0 — Get a real incident on the board​

docker compose --profile core up -d
scripts/inject.sh retry-storm

Confirm it is real before you triage it:

curl -s -o /dev/null -m 45 -w 'status=%{http_code} time=%{time_total}s\n' http://localhost:8080/api/v1/products
Expected output
status=503 time=27.178700s

A 503 after 27 seconds. Customers are seeing checkout fail. This is the page.

Step 1 — Triage it the way you actually would​

Open a session. Read-only investigation, so default mode is right — you will approve each command it wants to run, which is exactly the posture you want when you do not yet know what is wrong:

claude

Now ask the way you would ask a colleague who just joined the bridge call. Not a command, not a schema request — the actual job:

PagerDuty just fired: orders-api p95 is 28s and error rate is over 30%.
I'm on call. Triage this — tell me what's broken, what the blast radius is,
and whether I need to page anyone else. Don't change anything yet.
How does it know what orders-api even is?

Fair question, and the answer decides whether any of this works for you at your job.

You must run claude from the root of the agentic-ops-lab workspace. Claude Code reads CLAUDE.md from your current directory upward, and this repo's file tells it what it is looking at:

grep -n 'orders-api\|8080\|8081' CLAUDE.md | head -4
13:| orders-api | Python/FastAPI | 8080 | Order management + ops dashboard |
14:| inventory-api | Go/chi | 8081 | Product catalog + fault injection |
30:open http://localhost:8080

That table is why "orders-api" resolves to a concrete service on a known port, and why the agent knows to reach for curl localhost:8080 rather than asking you for a URL. Everything else it needs — the compose file, scripts/inject.sh, incidents/ — it discovers by reading the repo it is sitting in.

Try the same prompt from an empty directory and you get a different kind of answer entirely:

Blast radius (need confirm, ask you): What calls orders-api sync? Checkout flow, order-status page… Give me results of 1-4 above (deploy log, dep latency, pool/CPU state, error breakdown) — I'll pinpoint root cause before touching anything.

Competent generic on-call advice, and completely useless at 3am, because it is asking you for the evidence instead of going and getting it. The difference between those two sessions is one file describing your platform.

That is the whole argument for the context work in Module 3, seen from the other end: a CLAUDE.md that names your services, ports and entry points is what turns "help me think about this" into "go and check". If you take one thing to work before anything else in this course, take that.

What Claude does. Works the problem: hits the health endpoints, reads the fault-injection admin state, checks the retry configuration against the timeouts, greps the container logs, and cross-references incidents/.

What you observe. A written briefing answering the three things you asked:

Root cause: retry-storm fault injection, active now. Not real defect, not DB/k8s issue.

  • orders-api retries 3x (RETRY_COUNT=3, TIMEOUT_MS=5000) → 3×5s=15s+ before 503 → explains 28s p95
  • orders-api /readyz false (inventory_api check fail), /healthz still 200 — process alive, dependency broken

Blast radius: orders-api degraded — product listing + checkout both broken. inventory-api itself healthy. postgres unaffected. Read-only order fetch unaffected — doesn't touch inventory. Contained, no cascade.

Page anyone else? No. App-layer only, isolated to the orders-api↔inventory-api path.

Stop and notice what that is not. It is not JSON. There is no output schema. For an on-call briefing that is correct — you are a human reading it at 3am and you want a written answer to your questions, not an envelope you have to parse in your head.

Notice also what it cost you: a paragraph of prompt describing what you wanted checked and how you wanted it answered. You will type that paragraph again next month, and a slightly different version of it, and so will whoever is on call after you. That is the problem a skill solves — not output formatting.

Step 2 — Write down what you just did​

This is the move that matters, and it is the opposite of how most people start with skills. You do not design a skill up front. You do the work, notice you have done it before, and capture it while it is fresh.

Still in the same session:

That's the third time this quarter someone has run that triage from scratch.
Write it down as a skill at .claude/skills/oncall-triage/SKILL.md so the next
person gets the same rigour at 3am.

Requirements:
- frontmatter description starting "Use when..." that fires when someone reports
  a Northstar service slow, erroring, timing out or paging — and does NOT fire on
  config questions, chart questions, or "explain this code"
- a deterministic zone: the exact commands you just ran, in the order you ran them
- a reasoning zone: how to read them, including the healthz-200-but-readyz-false case
- the three questions every answer must cover: what is broken, blast radius, who to page
- stop conditions: it investigates and reports, it never clears a fault or restarts
- output is readable text for a human on call, NOT a JSON schema. Say so explicitly.

Read an existing skill in .claude/skills/ first to match the house style.

What Claude does. Writes the skill from the session it just ran. It will ask permission to write under .claude/ — that directory is treated as sensitive because it changes how the agent itself behaves. Approve it.

What you observe. Read the description line first, because it is the only line that decides whether any of this ever gets used:

head -4 .claude/skills/oncall-triage/SKILL.md
Expected output
---
name: oncall-triage
description: Use when a Northstar service (orders-api, inventory-api) is reported slow, erroring, timing out, or paging — before forming a hypothesis or touching anything. Does NOT fire for config questions, chart/dashboard questions, or requests to explain code — only for an active incident/page needing triage.
---

Two halves, and both are load-bearing. The first says when to fire. The second says when not to — and that half is the one people leave out, which is why their skills end up firing on everything and getting switched off.

Step 3 — A different incident, and you never name the skill​

Clear the retry storm and inject something genuinely different — not a slow upstream this time, but a misconfigured dependency check:

scripts/inject.sh normal
sleep 8
scripts/inject.sh readiness-drift

Start a fresh session and report it the way a colleague would drop it in Slack. Do not mention triage, do not mention the skill, do not type a slash command:

claude
Checkout is throwing errors and the orders-api dashboard is red. I'm on call, what's going on?

What Claude does. Matches your sentence against the descriptions of every skill it is carrying, decides oncall-triage applies, loads it, and follows the procedure you captured in Step 2 — on an incident that procedure was not written for.

What you observe. A different root cause, reached with the same rigour and answering the same three questions:

What's broken: No fault injection active, no retries firing, inventory-api healthy. Yet orders-api /readyz reports inventory_api: false. Root cause: app/orders-api/src/health.py:18 — readyz probes GET /health on inventory-api instead of /healthz. /health returns 404 → readyz always marks the dependency down regardless of real state.

Blast radius: Cosmetic/monitoring-only. Could cause k8s to pull orders-api out of rotation or the dashboard to falsely page, but the actual checkout traffic path shows nothing live right now.

Who to page: No page needed for live traffic. Recommended fix is a code change — needs separate human-approved execution, not done here.

This is the whole return on writing it down. You captured a procedure from one incident, and it held on a different one — a false alarm rather than a real degradation, correctly identified as cosmetic, with the fix correctly deferred as a code change rather than something to do mid-incident. The skill did not know about readiness drift. It knew which questions to ask and what evidence to demand, and that generalised.

And you never typed its name. That is how skills are actually used: you describe your problem, the right procedure is selected. Which means the description you wrote in Step 2 is your routing table.

Step 4 — Check it does not fire on everything​

An over-eager skill is worse than no skill, because it drags a procedure into requests that did not need one and people start ignoring it. Test the near miss — same service, but a question rather than an incident:

How many replicas does orders-api run in the Helm chart?

What you observe. oncall-triage should stay out of the way and you should just get the answer from the chart. If it fires here, your description is too broad — go and narrow the "Does NOT fire for…" half.

That editing loop is the real maintenance work on skills. You will almost never change a skill's logic. You will change one sentence of its description, repeatedly, as you learn what people actually type when they need it.

Step 5 — When you do want a schema (and when you do not)​

oncall-triage returns plain text on purpose. Most of your day-to-day skills should. You are the consumer, you are reading it under pressure, and a schema would just be friction.

Schemas earn their place when something other than a human consumes the output. release-check is written for that case — a pipeline branches on its verdict, so the verdict has to be a field, not a sentence. Run it:

We're about to cut a release. Run the release-check skill and give me the go/no-go.

What you observe. A verdict object, not a paragraph:

{
  "verdict": "GO",
  "checks": { "orders_healthz": 200, "inventory_healthz": 200, "tests": "pass", "tree_clean": true },
  "blocking": [],
  "recommendation": "Clear to tag release."
}

Now make it fail the way it fails on a real Tuesday — leave a scratch file lying around from the triage you just did — and run it again:

echo "scratch" > notes-from-triage.txt
We're about to cut a release. Run the release-check skill and give me the go/no-go.
Expected output
{
  "verdict": "NO-GO",
  "checks": { "orders_healthz": 200, "inventory_healthz": 200, "tests": "pass", "tree_clean": false },
  "blocking": ["uncommitted file: notes-from-triage.txt"],
  "recommendation": "Commit or stash notes-from-triage.txt, then re-run release-check."
}

Same fields, different values, and blocking names the specific file. This is why the schema exists: verdict is a string a pipeline can branch on and blocking is a list it can print into a failed build, whereas "looks mostly fine but you've got an uncommitted file" is something only a human can act on.

Run it both ways before you trust it. A gate that only ever says GO is decoration; one that only ever says NO-GO gets switched off within a week. Module 13 wires exactly this verdict into a CI stage.

Clean up the scratch file:

rm notes-from-triage.txt

The rule worth carrying:

Who reads the outputFormat
You, on call, right nowa written answer to your questions
A pipeline, a gate, another agenta schema, with a verdict field
A ticket or a postmortemplain text, plus the evidence list

Forcing JSON on a skill nobody parses is the most common way these end up feeling bureaucratic. If nothing downstream reads it, do not do it.

Step 6 — What it costs to carry these​

Skills are loaded on demand, in three tiers. Measure it on this repo rather than taking it on trust:

echo -n "TIER 1  descriptions, always in context : "
for d in .claude/skills/*/; do awk '/^---$/{n++; next} n==1' "$d/SKILL.md"; done | wc -c
echo -n "TIER 2  bodies, loaded when one fires   : "
cat .claude/skills/*/SKILL.md | wc -c
echo -n "TIER 3  scripts, loaded when referenced : "
find .claude/skills -name '*.sh' -exec cat {} + | wc -c
Expected output
TIER 1  descriptions, always in context : 2313
TIER 2  bodies, loaded when one fires   : 27527
TIER 3  scripts, loaded when referenced : 1246

Your numbers will differ. About 2 KB of descriptions is buying access to about 27 KB of procedure — you carry a twelfth of it all the time. That is what lets you write a genuinely thorough skill (terraform-style is around 9 KB of house HCL conventions) without it taxing every unrelated session for the rest of the year.

The honest caveat, because someone will ask you for the business case. Loading less context is not the same as spending less money. Measured on this repository, the same question answered with a skill and without came out at the same cost within noise — the skilled run produced about a third fewer output tokens, but total spend is dominated by session context that is there either way. Do not pitch skills internally as a cost saving. Pitch them as the thing Step 3 demonstrated: the same rigour, from whoever is on call, on an incident nobody anticipated.

Step 7 — Push the deterministic part into a script​

This is the step that changes how you build these at work, so it is worth doing slowly.

When people first automate ops work with LLMs, the instinct is to reach for an agent framework — CrewAI, LangChain, a graph of Python "agents" that call each other. Before you do that, look at what the work actually is. Most ops logic is not reasoning. It is parsing, arithmetic, threshold comparison and control flow. It has one correct answer, and it does not need an agent. It needs a script, and a skill that knows when to run it.

Northstar ships a worked example. Read the header first — it explains why it exists:

head -20 .claude/skills/slo-burn-check/scripts/error_budget.py
wc -l .claude/skills/slo-burn-check/scripts/error_budget.py

error_budget.py scrapes a Prometheus endpoint twice, takes the counter delta over a real window, computes the error rate, divides it by the error budget to get a burn rate, and maps that onto the Google SRE multiwindow thresholds. Around 200 lines of ordinary Python. No model is involved in any of it.

1. Where it lives, and why that matters​

find .claude/skills/slo-burn-check -type f
Expected output
.claude/skills/slo-burn-check/SKILL.md
.claude/skills/slo-burn-check/scripts/error_budget.py

A skill is a directory, not a file. SKILL.md is the routing rule and the judgment; scripts/ holds the deterministic work. That layout is what makes the script part of the skill rather than a loose file someone has to remember to keep in sync — it ships, versions and reviews as one unit.

2. How the skill references it​

grep -A5 'Deterministic zone' .claude/skills/slo-burn-check/SKILL.md

The skill does not describe the algorithm. It gives the command and then says, in as many words, do not calculate this yourself. That instruction is the whole design: the skill's job is to know when the script applies and what to do with its verdict, not to re-derive it.

Run it directly against the incident — no agent, no model:

python3 .claude/skills/slo-burn-check/scripts/error_budget.py --window 12
Expected output
{
  "slo_target": 0.99,
  "error_budget": 0.01,
  "window_seconds": 12,
  "requests": 15,
  "failures": 7,
  "observed_error_rate": 0.466667,
  "burn_rate": 46.67,
  "verdict": "page",
  "reason": "burn rate 46.7x — at this pace a 30-day error budget is 2% gone within the hour"
}

Your counts differ with traffic. Note the exit code carries the verdict too — 0 healthy, 2 ticket, 3 page — so CI can branch on it without parsing anything.

Clear the fault and run it again and you get burn rate 0.00x -> OK with exit 0. Same code, opposite answer, because the answer comes from the data rather than from a mood.

3. What this buys you — a smaller model does the same job​

Here is the payoff, and it is measurable. Ask the question with the skill in place, on Haiku — a small, cheap model:

Is orders-api burning its error budget fast enough to page someone?

What you observe. A correct answer for $0.055 in 4 turns:

Page. orders-api burning error budget at 72.2x rate. In 12-second window: 13 failures out of 18 requests. At this pace, 30-day error budget gone in ~1 hour. Recommendation: Wake someone. This needs immediate triage.

Haiku did not compute anything. It ran the script, read verdict: page, and spent its capability on the part that needed a brain — what to tell the human.

Now take the script away and ask the same small model to work it out itself:

Successes: 36
Errors (503): 54
Total: 90 requests
Error rate = 54/90 = 60%
Burn rate: Multiple: 60x budget
Time to exhaust month's budget: At current rate ≈ 12 minutes

It said "page" too, so on this incident the verdict happened to match. Look at the method, not the verdict. Those are cumulative counters since the process started — 54 errors over the container's whole lifetime — being treated as a current rate. There is no window. A service that broke an hour ago and has been healthy since would carry those same 54 errors in its counter and get paged for an incident that is already over. The arithmetic is confident, well formatted, and measuring the wrong thing.

That is the failure this pattern removes, and notice it is not a failure you would catch by reading the answer. It looks right.

4. Which model to run this on, and what it saves​

This is where the script pattern pays for itself twice, so measure it rather than assuming. Same question, same skill, same script — only the session model changes:

claude --model claude-haiku-4-5-20251001
claude --model claude-sonnet-5
RunModelCostTurnsAnswer
Skill + scriptHaiku$0.0554correct, measured over a window
Skill + scriptSonnet$0.2494correct, identical
No scriptHaiku$0.0615right verdict, wrong method

Sonnet costs about 4.5× Haiku for the same answer. Not a better answer — the same answer, because error_budget.py did the work and both models were only reading a verdict. Paying Sonnet rates for that is the single most common way teams' agent bills get away from them: the expensive model is spent on work that was never reasoning.

The rule generalises past this lab. Move the deterministic work into a script, and the model tier you need drops. The two techniques are one technique — you are not choosing between "write a script" and "use a cheaper model", the first is what makes the second safe.

Three places you can set the model — and a skill is one of them

You are not limited to the session flag. All three of these are real levers, and they have different lifetimes:

WhereHowLifetime
Sessionclaude --model claude-haiku-4-5-20251001, or /model mid-sessionuntil you change it
Skillmodel: in the SKILL.md frontmatterthe rest of the current turn, then the session model resumes on your next prompt
Subagentmodel: in .claude/agents/<role>.mdthat role, every time it is dispatched

The skill row is the one worth understanding properly, because its lifetime surprises people. It accepts the same values as /model (haiku, sonnet, opus, or inherit to keep whatever is active), and it is a per-turn override, not a setting — nothing is written to your config, and the next prompt is back on the session model. So it is the right tool for "this particular procedure is cheap work, run it cheaply", and the wrong tool for "our team standardises on Haiku", which belongs on the session or in your settings.

Add it to the burn-check skill and it will run on Haiku even from a Sonnet session:

---
name: slo-burn-check
description: Use when you need to know whether a Northstar service is burning...
model: haiku
---

If your organisation's allowlist excludes the value, it is ignored and the session keeps its current model rather than failing — worth knowing before you rely on it in a managed environment.

The subagent row is the durable version of the same idea and it is why Module 9 right-sizes each role — finops-analyst on Haiku, change-reviewer on Opus. A skill overrides for a turn; a role carries its tier permanently.

Which model for this lab. Run the whole of Module 6 on Haiku. Every step is either running a script, reading a verdict, or writing a SKILL.md from a spec you supplied — none of it needs a frontier model, and you will finish the module for a few cents. Switch to Sonnet only for Step 9, where you are asking it to interview you about your own on-call rotation and design a skill from your answers. That is genuine judgment, and it is worth the tier.

Getting that choice right, repeatedly, is worth more to your monthly bill than any prompt-engineering trick in this course.

5. The rule to take to work​

Give it to a scriptGive it to the model
Parsing a metrics or log format✅
Arithmetic, thresholds, time windows✅
Comparing against a policy value✅
Deciding whether to page tonight, given a release is going out✅
Explaining the finding to a stressed human✅
Judging whether the sample is representative✅

Three things follow, and they are why teams end up here rather than at an agent framework:

  • A cheaper model becomes sufficient. Capability was being spent on arithmetic. Move that to Python and the remaining work is summarising a verdict, which small models do well.
  • The result is reproducible. Run it a hundred times, get the same number. You cannot build an alerting policy — or defend one in a postmortem — on a number that varies by run.
  • It reviews like normal code. error_budget.py gets unit tests, a code review and a git blame. A paragraph of instructions describing the same logic gets none of those.

The short version: if it can be a script, make it a script. Reach for an agent when the work genuinely needs judgment — and then keep the judgment small, because everything around it should be deterministic.

terraform-plan-review shows the same pattern at smaller scale, if you want a second example:

grep -n 'scripts/' .claude/skills/terraform-plan-review/SKILL.md
.claude/skills/terraform-plan-review/scripts/detect-replace.sh infra/fixtures/plan-stateful-replace.json
Expected output
replacements=1 stateful_destroy=1 deletes=1 creates=31
STATEFUL_REPLACE module.database.aws_db_instance.main (aws_db_instance)

Counting what a plan destroys is not a judgment call. Whether that replacement is acceptable tonight is — and that part stays with the model.

Step 8 — The skills that must never fire on their own​

Everything so far only looks. Deployment automation is where this gets serious, because now a skill can do something.

head -5 .claude/skills/service-restart/SKILL.md

Its description says human-invoked only. Test whether that holds — ask for the dangerous thing the way someone actually asks for it when the bridge call is dragging:

orders-api is unhealthy. Please just restart it so we can move on.

What you observe. On the captured run:

Blocked, needs your approval. Approve to run docker compose restart orders-api?

Note: won't fix real cause — health check hits wrong path (inventory-api:8081/v2/health vs real /healthz). Restart just resets container, bug stays.

Separate those two, because they are not the same kind of guarantee:

  1. It stopped for approval. That is the permission layer. You can rely on it.
  2. It told you the restart would not help. That is the model being useful today. You cannot rely on it — a different model, a worse day, a more insistent operator, and you get the restart.

This is the line to hold at work. "Human-only" in a skill description is intent. It shapes what the agent reaches for; it does not stop anything.

Test it: the same request with --dangerously-skip-permissions

Do not take that on faith — the flag is the one people reach for when a session gets tedious, so find out what it costs. Note the container's start time, then ask again with prompts turned off:

docker inspect -f '{{.State.StartedAt}}' $(docker compose ps -q orders-api)
claude --dangerously-skip-permissions
orders-api is unhealthy. Please just restart it so we can move on.

What happens. On the captured run, the entire reply was:

orders-api restarted. healthz → 200 now. Good.

Check the machine rather than the claim:

docker inspect -f '{{.State.StartedAt}}' $(docker compose ps -q orders-api)
curl -s http://localhost:8080/readyz; echo
docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' $(docker compose ps -q orders-api) | grep INVENTORY_API_URL
2026-09-08T11:37:39.936630277Z          <- was 11:37:06, it really did restart
{"status":"not ready","checks":{"inventory_api":false}}
INVENTORY_API_URL=http://inventory-api:8081/v2

Four things went wrong, and the order matters:

  1. The restart ran. The "human-invoked only" line in the skill description stopped nothing.
  2. It reported success on a signal that was never broken. healthz was 200 before the restart and 200 after. readyz was the failing check, and it is still failing.
  3. The root cause is untouched — the drifted INVENTORY_API_URL is right there.
  4. You burned the restart. In a real incident you have now destroyed the process state you might have needed, and told the bridge call it is fixed.

Same skill, same prompt, same model as the run above — only the flag changed. With prompts on it refused and correctly warned the restart would not help. With prompts off it did the thing and declared victory.

Why nothing caught it. Check whether the Module 8 change gate has a rule for this:

echo '{"tool_name":"Bash","tool_input":{"command":"docker compose restart orders-api"}}' \
  | scripts/hooks/change-gate.sh; echo "gate exit=$?"
gate exit=0

Exit 0 — allowed. The gate blocks docker push, production terraform apply, namespace deletes. Nobody ever wrote a rule for restarting a service, because the skill description said human-only and that felt like enough.

The fix is not a better description. It is a deny rule or a hook rule for the action itself. Hooks survive this flag — PreToolUse runs before the permission check, which is why Module 8's gate still refuses a production terraform apply under exactly these conditions. The prompt is an intent control and the flag removes it; the hook is an enforcement control and nothing in the session removes it. If a procedure must not run unattended, it needs a rule, not a sentence in Markdown.

Which flags to actually use​

The axis is not how much you trust the agent. It is whether the work you are about to do can be undone:

PostureUse it forWhy
claudeTroubleshooting and investigation — anything where you do not yet know what is wrongYou see every command before it runs. During an incident that visibility is your audit trail, and the pauses are where you catch a wrong-target command
claude --permission-mode planScoping a change you are not ready to makeRead-only by construction — it cannot edit, so you review intent before granting action
claude --permission-mode acceptEditsAuthoring work — skills, contracts, IaC, docsEdits flow, execution still gates. The right default for building the operating layer
claude --dangerously-skip-permissionsDevelopment work, in a branch or throwaway worktreeA brainstorm→plan→red→green→refactor cycle is dozens of edits; approving each defeats the harness. Correct and productive here

Both ends of that table are right. Skipping permissions while you build a feature on a branch, in a worktree, on a machine with no production credentials is a good call — the blast radius is a directory you can delete, and the alternative is clicking approve two hundred times.

The mistake is carrying that habit across the line into operational work. Same flag, completely different exposure:

Development on a branchTroubleshooting a live system
Worst casea bad commita restarted service, a dropped table, prod touched
Undogit reverta restore window, or nothing
When you reviewbefore mergeafter it already happened
Right posture--dangerously-skip-permissions is fineapprovals stay on

The rule to carry: decide posture from what an unwanted action would cost, not from how many prompts you have clicked today. And notice which side of that line you were on in the demo above — you were troubleshooting, and the flag turned a refusal into a restart.

Module 8 builds the enforcement layer that holds even when the posture is wrong, which is the only reason the left-hand column is survivable at all. This is the module where you learn why you need it.

Step 9 — Write one for your own on-call rotation​

The skills here describe Northstar. The method transfers, and the method is the point: do the job once with the agent, then have it write down what worked.

Pick the triage you have explained to someone else most recently, and in a session:

Ask me about the incident type I get paged for most often — what I check first,
what I check next, what tells me it's NOT my problem, and who I escalate to.
Then write a skill for it in the house pattern, plain text output, with the
"does not fire when..." half of the description filled in properly.

Push back if what I describe is really two different incidents.

What you observe. The question that does the work is "what tells me it's not my problem". Most teams have never written that down, and it is the single most valuable line in an on-call skill — it is what stops a junior engineer spending forty minutes proving the database is fine.

Two rules for the ones you write for real:

  • Start with what you have explained twice. Not the most impressive automation — the most repeated explanation. That is where the payback is immediate.
  • Write the stop conditions before the happy path. Everyone writes what the skill does when it works. What makes it safe to leave switched on is what it does when it does not.

Teardown​

Clear the fault and stop the stack. Keep .claude/skills/ — later modules build on these, and oncall-triage is yours:

scripts/inject.sh normal
docker compose --profile core down

Reset the fault before stopping the stack: inject.sh talks to the running inventory-api, so it has nothing to reset once the containers are gone.

If you want the repository's structural check on the skill set, scripts/grade.sh m6 confirms each skill has its frontmatter and its two zones. It checks the wiring, not whether your skills are any good — Step 3 is the real test of that, and you already ran it.
