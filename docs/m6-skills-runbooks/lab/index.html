Lab — Build Five Skills

In the lesson you learned what a skill is (a runbook an agent can execute the same way every time), how to keep it testable (two zones — deterministic collection, then reasoning), and how to control who can trigger it (auto for observers, human-only for anything with side effects). This lab builds the first five skills for Northstar Commerce to that shape, tests each with a real positive and negative case against the running platform and the plan fixtures, and lets grade.sh m6 confirm the set holds together.

By the end you will have a populated .claude/skills/ directory — the beginning of Northstar's real operating layer — and you will have watched each skill catch the exact problem it exists to catch.

Where you are working

You start at the root of the agentic-ops-lab workspace. Two of the five skills (service-health, release-check, incident-triage) collect evidence from the running services, so you will bring the core stack up. Two others (terraform-plan-review, k8s-diagnose) work from fixtures and are grounded without a cluster. The stale runbook that motivates this whole module — runbooks/stale-runbook-wrong-endpoint.md — is already in the repo; you are building the skills that replace it.

You are not fixing it here; you are building a skill that correctly diagnoses it.) This asymmetry gives you a genuine healthy service and a genuine unhealthy one — your positive and negative cases, for free.

Step 2 — Build service-health (an observing skill, auto-invokable)​

The first skill probes a service and reports its status. It only observes, so it is safe to auto-invoke. Create it with the two-zone shape from the lesson: a deterministic collection zone, then a reasoning zone, plus an output schema and stop conditions.

mkdir -p .claude/skills/service-health
cat > .claude/skills/service-health/SKILL.md <<'EOF'
---
name: service-health
description: Use when you need to check whether a Northstar service (orders-api or inventory-api) is healthy — before a deploy, during triage, or when someone reports a service is misbehaving. Reports status only; never fixes.
---

# service-health

Check one Northstar service's health and report its status. Read-only.

## Inputs
- service: orders-api (port 8080) or inventory-api (port 8081)

## Deterministic zone — collect evidence
Run the probes and capture raw output. healthz = liveness; readyz = dependencies.
```bash
PORT=8080   # inventory-api is 8081
curl -s -o /dev/null -w 'healthz=%{http_code}\n' "http://localhost:${PORT}/healthz"
curl -s -w '\nreadyz_http=%{http_code}\n'        "http://localhost:${PORT}/readyz"
```
If healthz returns 000, the service is unreachable — go to stop conditions.

## Reasoning zone — analyze
- healthz=200 and readyz "ready" -> healthy.
- healthz=200 but readyz "not ready" -> process up, a DEPENDENCY is failing. Read the
  checks object and name which one (e.g. inventory_api:false). Upstream problem, not this service.
- healthz not 200 -> the process itself is unhealthy.

## Output schema
{ "service": "...", "healthy": true|false, "checks": {...}, "recommendation": "..." }

## Stop conditions
- If unreachable (healthz=000), report unreachable and STOP. Do not guess a status.
- Report only. No restart, no fix. Restarting is a separate, human-only skill.
EOF
echo "wrote service-health"
Expected output
wrote service-health

You now have a skill directory with a SKILL.md. The frontmatter's description starts with "Use when…" so Claude Code can decide, at a glance, whether to reach for it. The body separates collecting (curl) from reasoning (interpret) — the wall that makes it testable.

Now test it — negative case first, because the negative test is the one with teeth. Point the skill at orders-api, which you saw is live-but-not-ready. A worthless skill would say "healthy"; a good one names the failing dependency.

claude -p "/service-health check orders-api. Report using the skill's output schema." \
  --permission-mode dontAsk
Expected output
{
  "service": "orders-api",
  "healthy": false,
  "checks": { "healthz": 200, "readyz": "not ready", "inventory_api": false },
  "recommendation": "orders-api is live but not ready — its inventory-api dependency
   check is failing. Investigate the inventory dependency, not orders-api itself."
}

The exact wording varies each run. What matters is the shape of the verdict: healthy:false, and the recommendation correctly points at the dependency, not at orders-api crashing. The skill read healthz=200 + readyz not ready + inventory_api:false and reasoned to the right conclusion. That is the negative test passing — it caught the real problem instead of rubber-stamping the service.

Now the positive case: point it at inventory-api, which is genuinely healthy. A skill that only ever says "unhealthy" is as useless as one that only says "healthy" — you need it to recognize "fine" too.

claude -p "/service-health check inventory-api. Report using the skill's output schema." \
  --permission-mode dontAsk
Expected output
{
  "service": "inventory-api",
  "healthy": true,
  "checks": { "healthz": 200, "readyz": "ready" },
  "recommendation": "inventory-api is healthy — live and ready. No action needed."
}

healthy:true, no invented problems. Together with the negative case, you have now proven the skill can tell a healthy service from an unhealthy one — which is the entire job. One test would have proven nothing.

Step 3 — Build terraform-plan-review (progressive disclosure with a script)​

This skill reviews a terraform plan before apply. Its detection logic is non-trivial jq, so following the lesson's progressive-disclosure pattern, the logic lives in a script the skill references — not inline prose. Create the script first.

mkdir -p .claude/skills/terraform-plan-review/scripts
cat > .claude/skills/terraform-plan-review/scripts/detect-replace.sh <<'EOF'
#!/usr/bin/env bash
# Deterministic zone: emit machine-readable facts about a terraform plan. No interpretation.
set -euo pipefail
PLAN="${1:?usage: detect-replace.sh <plan.json>}"
jq -r '
  [ .resource_changes[] | select((.change.actions | sort) == ["create","delete"]) ] as $replaces
  | [ $replaces[] | select(.type | test("db_instance|rds|ebs_volume|efs|s3_bucket$|elasticache")) ] as $stateful
  | [ .resource_changes[] | select(.change.actions | index("delete")) ] as $deletes
  | [ .resource_changes[] | select(.change.actions | index("create")) ] as $creates
  | "replacements=\($replaces|length) stateful_destroy=\($stateful|length) deletes=\($deletes|length) creates=\($creates|length)"
' "$PLAN"
jq -r '
  .resource_changes[]
  | select((.change.actions | sort) == ["create","delete"])
  | select(.type | test("db_instance|rds|ebs_volume|efs|s3_bucket$|elasticache"))
  | "STATEFUL_REPLACE \(.address) (\(.type))"
' "$PLAN"
EOF
chmod +x .claude/skills/terraform-plan-review/scripts/detect-replace.sh
echo "wrote detect-replace.sh"
Expected output
wrote detect-replace.sh

The script is the deterministic zone made concrete: a fixed input (a plan JSON) produces a fixed facts line, with zero interpretation. That is exactly what makes it mechanically testable.

Prove the script's two-zone value directly, without the agent — run it on both fixtures. This is the positive and negative test of the deterministic zone:

echo "### NEGATIVE — plan-stateful-replace (destroys the prod DB) ###"
bash .claude/skills/terraform-plan-review/scripts/detect-replace.sh infra/fixtures/plan-stateful-replace.json
echo "### POSITIVE — plan-good (clean) ###"
bash .claude/skills/terraform-plan-review/scripts/detect-replace.sh infra/fixtures/plan-good.json
Expected output
### NEGATIVE — plan-stateful-replace (destroys the prod DB) ###
replacements=1 stateful_destroy=1 deletes=1 creates=31
STATEFUL_REPLACE module.database.aws_db_instance.main (aws_db_instance)
### POSITIVE — plan-good (clean) ###
replacements=0 stateful_destroy=0 deletes=0 creates=31

The counts will match on your machine — these are fixtures, so the deterministic zone is genuinely deterministic. The bad plan shows replacements=1 stateful_destroy=1 and names the database being destroyed and recreated; the good plan shows replacements=0. The zone tells them apart with no judgment involved — which is precisely why you can trust it as the input to the reasoning zone.

Now write the SKILL.md that references the script and adds the reasoning zone:

cat > .claude/skills/terraform-plan-review/SKILL.md <<'EOF'
---
name: terraform-plan-review
description: Use when reviewing a terraform plan (a plan JSON from terraform show -json) before apply — to catch resource replacements, high blast-radius stateful destroys, and cost jumps before they reach production. Reports findings; never applies.
---

# terraform-plan-review

Review a terraform plan JSON and report what it will do to the estate — before apply. Read-only.

## Inputs
- plan: path to a plan JSON (e.g. infra/fixtures/plan-good.json)
- estimate: optional cost estimate JSON

## Deterministic zone — collect facts
The detection logic lives in a script so it is testable, not re-derived in prose:
```bash
bash "$(dirname "$0")/scripts/detect-replace.sh" "${plan}"
```
If a cost estimate was given: `jq -r '"monthly_cost=" + .totalMonthlyCost' "${estimate}"`

## Reasoning zone — analyze
- replacements=0 -> only adds/updates. Low structural risk.
- replacements>0 AND stateful_destroy>0 -> HIGH blast radius. A STATEFUL_REPLACE on a
  db_instance means the production database is destroyed and recreated: data loss + downtime
  unless a snapshot/migration plan exists. This BLOCKS an apply.
- cost far above the ~$300/mo baseline -> flag the jump and name the driving resource.

## Output schema
{ "plan": "...", "replacements": N, "stateful_destroys": [...], "blast_radius": "low|high",
  "cost_monthly_usd": N, "recommendation": "..." }

## Stop conditions
- If the plan is missing or unparseable, report and stop.
- Never run terraform apply or any mutating terraform command. Review only.
EOF
echo "wrote terraform-plan-review"
Expected output
wrote terraform-plan-review

Test the whole skill through the agent on the negative fixture — the one that destroys the database:

claude -p "/terraform-plan-review with plan=infra/fixtures/plan-stateful-replace.json and estimate=infra/fixtures/cost-estimates/estimate-oversize.json. Use the output schema." \
  --permission-mode dontAsk
Expected output
{
  "plan": "infra/fixtures/plan-stateful-replace.json",
  "replacements": 1,
  "stateful_destroys": ["module.database.aws_db_instance.main"],
  "blast_radius": "high",
  "cost_monthly_usd": 3148.97,
  "recommendation": "BLOCK: this plan destroys and recreates the production database
   (module.database.aws_db_instance.main) — data loss and downtime without a verified
   snapshot and migration. Cost also jumps to ~$3149/mo, ~10x the ~$300 baseline."
}

Wording varies; the findings do not. The skill flagged the stateful replace as high blast radius, named the exact resource, and caught the cost jump. That is the negative test: it detected the thing it exists to detect. (Run the same command with plan-good.json + estimate-good.json for the positive case — you should get replacements:0, blast_radius:"low", ~301.97.)

Step 4 — Build k8s-diagnose (read-only, matches failure patterns)​

This skill diagnoses a struggling Kubernetes workload. The critical property is that it is read-only — it collects pod status, events, and logs but never mutates the cluster. Write it so its collection zone contains only reading verbs.

mkdir -p .claude/skills/k8s-diagnose
cat > .claude/skills/k8s-diagnose/SKILL.md <<'EOF'
---
name: k8s-diagnose
description: Use when a Kubernetes workload is unhealthy — pods CrashLooping, not Ready, pending, or an incident points at the cluster. Collects pod status, events, and logs and reports the likely cause. Read-only diagnosis; never mutates the cluster.
---

# k8s-diagnose

Diagnose a struggling workload from status, events, and logs. Read-only.

## Inputs
- namespace: e.g. northstar
- selector: label selector, e.g. app=orders-api

## Deterministic zone — collect evidence (all read-only)
```bash
kubectl get pods -n "${namespace}" -l "${selector}" -o wide
kubectl describe pod -n "${namespace}" -l "${selector}"
kubectl get events -n "${namespace}" --sort-by=.lastTimestamp | tail -20
kubectl logs -n "${namespace}" -l "${selector}" --tail=50 --all-containers --previous 2>/dev/null \
  || kubectl logs -n "${namespace}" -l "${selector}" --tail=50 --all-containers
```

## Reasoning zone — analyze (common patterns)
- CrashLoopBackOff + nonzero exit -> dies on start; read previous logs for why (bad config/env/migration).
- Running but 0/1 READY + "Readiness probe failed: statuscode 404" -> wrong probe path
  (this estate should probe /healthz, not /health). Process is fine; probe config is not.
- OOMKilled -> memory limit too low or a leak; note if no resources.limits are set.
- Pending -> nothing schedulable / unsatisfiable request.

## Output schema
{ "namespace": "...", "selector": "...", "pod_state": "...", "likely_cause": "...",
  "evidence": [...], "recommendation": "..." }

## Stop conditions
- If no pods match, report and stop.
- Report cause + recommendation only. This skill runs NO mutating cluster verbs — it never
  applies, deletes, scales, rolls out, or edits. Fixing is a separate, human-approved action.
EOF
echo "wrote k8s-diagnose"
Expected output
wrote k8s-diagnose

Prove the read-only property mechanically — the collection zone must contain reading verbs and no mutating ones. This is the negative test for a safety property rather than a detection property:

echo -n "has read verbs: "; grep -qi 'kubectl get' .claude/skills/k8s-diagnose/SKILL.md && echo yes || echo no
echo -n "has mutating verbs: "; grep -Eqi 'kubectl (apply|delete|scale|rollout|edit)' .claude/skills/k8s-diagnose/SKILL.md && echo "YES — UNSAFE" || echo "no — safe"
Expected output
has read verbs: yes
has mutating verbs: no — safe

The skill reads (kubectl get, describe, logs, events) and mutates nothing. A diagnosis skill that could kubectl delete a deployment while "investigating" is a landmine; this check is how you prove it cannot. (You have no live cluster in this lab — that comes in Module 12 — so you are validating the skill's shape now; the pattern-matching reasoning is exercised against a real cluster later.)

Step 5 — Build release-check (a go/no-go gate)​

This skill is the pre-release gate: services healthy, tests green, tree clean — every signal must be green for a GO. It observes only; it never tags or ships.

mkdir -p .claude/skills/release-check
cat > .claude/skills/release-check/SKILL.md <<'EOF'
---
name: release-check
description: Use before cutting a release or tagging a build — to confirm both services are healthy, the test suite passes, and the working tree is clean. A go/no-go gate; reports a verdict, never ships.
---

# release-check

Run the pre-release gate: services healthy, tests green, tree clean. Reports GO or NO-GO. Read-only.

## Inputs
- none — checks the whole workspace and both running services.

## Deterministic zone — collect evidence
```bash
curl -s -o /dev/null -w 'orders_healthz=%{http_code}\n'    http://localhost:8080/healthz
curl -s -o /dev/null -w 'inventory_healthz=%{http_code}\n' http://localhost:8081/healthz
( cd app/orders-api && .venv/bin/python -m pytest -q ) ; echo "pytest_exit=$?"
git status --short ; echo "tree_lines=$(git status --short | wc -l | tr -d ' ')"
```

## Reasoning zone — analyze
GO only if ALL hold: both *_healthz=200, AND pytest_exit=0, AND tree_lines=0.
Any single failure is NO-GO, and the report names which signal failed. A dirty tree is a
NO-GO even if all else is green — you do not tag a build you cannot reproduce from a commit.

## Output schema
{ "verdict": "GO|NO-GO", "checks": {...}, "blocking": [...], "recommendation": "..." }

## Stop conditions
- If a service is unreachable, verdict is NO-GO (cannot confirm health) — do not assume healthy.
- Report the verdict only. No tag, no push, no deploy. Shipping is a human decision after a GO.
EOF
echo "wrote release-check"
Expected output
wrote release-check

Test it now. In this workspace the verdict should be NO-GO for two honest reasons: orders-api is not ready (the M1 dependency defect), and your tree is dirty (you just created five untracked skills). A gate that returned GO here would be lying.

claude -p "/release-check. Report the go/no-go verdict using the output schema." \
  --permission-mode dontAsk
Expected output
{
  "verdict": "NO-GO",
  "checks": { "orders_healthz": 200, "inventory_healthz": 200, "tests": "pass", "tree_clean": false },
  "blocking": [
    "working tree is dirty (untracked .claude/skills/, labs/)",
    "orders-api readiness is degraded (inventory dependency failing)"
  ],
  "recommendation": "Do not tag. Commit the new skills and resolve the orders-api readiness
   defect before releasing."
}

Wording varies; the verdict does not. NO-GO, with the specific blocking reasons named. This is the gate doing its job — refusing a release the workspace is not actually ready for, and telling you exactly why. The negative test for a gate is that it says NO-GO when it should; a gate that always says GO is worse than no gate at all.

Step 6 — Build incident-triage (bounded evidence collection)​

The last observing skill turns an incident ticket into a filled evidence packet. The defining property is that its collection is bounded — it gathers exactly the evidence the ticket's scope points to, and it does not form a root cause or attempt a fix. Triage hands a clean packet to whoever forms the hypothesis.

mkdir -p .claude/skills/incident-triage
cat > .claude/skills/incident-triage/SKILL.md <<'EOF'
---
name: incident-triage
description: Use when an incident ticket lands (INC-00N) and you need a structured evidence packet before anyone forms a hypothesis — reads the ticket, collects the bounded evidence it points to, and fills the evidence-packet template. Collects evidence only; never fixes.
---

# incident-triage

Turn an incident ticket into a filled evidence packet. Read-only — triage collects, it does not remediate.

## Inputs
- incident: path to the ticket, e.g. incidents/INC-001-readiness-failure.md

## Deterministic zone — collect bounded evidence
Read the ticket for scope, then collect exactly the evidence it points to — no more.
```bash
cat "${incident}"
curl -s -o /dev/null -w 'orders_healthz=%{http_code}\n'    http://localhost:8080/healthz
curl -s -w 'orders_readyz=%{http_code} ' -o /tmp/rz http://localhost:8080/readyz; echo "body=$(cat /tmp/rz)"
curl -s -o /dev/null -w 'inventory_healthz=%{http_code}\n' http://localhost:8081/healthz
```
Run any additional READ-ONLY commands the ticket's "Investigation Commands" list — and only those.

## Reasoning zone — assemble the packet
Fill incidents/templates/evidence-packet.md from the evidence. Record gaps honestly (a field
you could not measure is "unknown", not guessed). Do NOT state a root cause — hand the packet on.

## Output schema
{ "incident": "...", "service": "...", "evidence": {...}, "gaps": [...],
  "packet": "path", "next_step": "hand to on-call for hypothesis" }

## Stop conditions
- Collect ONLY the evidence the ticket's scope points to. Do not expand into unrelated services
  or mutate anything to "see what happens." Triage is bounded by design.
- Report only. No fix, restart, or config change — that is a separate, human-approved action.
EOF
echo "wrote incident-triage"
Expected output
wrote incident-triage

Test it against the real INC-001 ticket. This ticket is about orders-api readiness — the exact defect live in your workspace — so the collected evidence will actually corroborate the ticket:

claude -p "/incident-triage with incident=incidents/INC-001-readiness-failure.md. Collect the bounded evidence and report using the output schema. Do not propose a root cause." \
  --permission-mode dontAsk
Expected output
{
  "incident": "INC-001",
  "service": "orders-api",
  "evidence": {
    "orders_healthz": 200,
    "orders_readyz": "not ready — {\"inventory_api\": false}",
    "inventory_healthz": 200
  },
  "gaps": ["no live cluster locally — kubectl pod/probe evidence from the ticket not collectable"],
  "packet": "incidents/templates/evidence-packet.md (filled)",
  "next_step": "Hand packet to on-call for hypothesis. Not fixing here."
}

Wording varies. Notice three things the skill did right: it collected the health evidence the ticket scopes to, it recorded the cluster evidence it could not gather as an honest gap rather than inventing it, and it stopped before a root cause — next_step hands off instead of diagnosing. That last restraint is the bounded property: a triage skill that jumped to "the readiness probe path is wrong" would be doing the on-call's job and, worse, might be confidently wrong. Collect, record gaps, hand off.

Step 7 — Build service-restart (a side-effecting, human-only skill)​

Every skill so far only observes. This one changes state — it restarts a service — which makes it categorically different. Per the lesson, a mutating skill must be human-only: it runs only when a person invokes it deliberately, never because the agent inferred it was relevant.

mkdir -p .claude/skills/service-restart
cat > .claude/skills/service-restart/SKILL.md <<'EOF'
---
name: service-restart
description: Use ONLY when a human has decided a Northstar service must be restarted and explicitly invokes this skill. This skill has side effects (it restarts a running service). It is human-only — it must never be auto-invoked by relevance.
auto-invoke: false
---

# service-restart

Restart a Northstar service. THIS SKILL CHANGES STATE. It is human-only: it runs only on an
explicit /service-restart, never because the agent thought it was relevant.

## Why human-only
An observing skill is safe to auto-invoke (worst case: an unneeded report). A mutating skill is
not (worst case: an unrequested restart of a live service). So the trigger is a human's explicit
choice, not the model's relevance judgment.

This does NOT make the restart safe by itself. Even when a human invokes it, the restart still
runs under the tool and permission boundaries from Module 2 — deny rules and sandbox still apply.
Human-only controls WHO can trigger; it grants no authority to step outside the environment's policy.

## Inputs
- service: orders-api or inventory-api
- reason: one line stating why (goes in the record)

## Deterministic zone — the side effect
```bash
docker compose restart "${service}"
```

## Stop conditions
- If invoked automatically (not by an explicit human /service-restart), refuse and report why.
- If the restart is blocked by a permission or sandbox policy, report the block. Do NOT try to
  work around it — the policy is the floor, and a skill does not override it.
EOF
echo "wrote service-restart"
Expected output
wrote service-restart

This skill deliberately carries auto-invoke: false in its frontmatter and states "human-only" in its body — both signal that automatic invocation must not reach it. The Deep Dive tests exactly this claim: that the skill is genuinely invisible to auto-invocation, and that even a human invoking it cannot use it to escape your Module 2 permissions.
