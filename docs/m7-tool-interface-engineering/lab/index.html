Lab — CLI vs Skill vs MCP

The lesson gave you a framework: four interfaces (CLI, script, skill, MCP) and five criteria (authority, ambiguity, output structure, authentication, cost/frequency) for choosing between them. This lab makes the choice concrete. You will take one diagnostic ticket — orders-api readyz is failing, investigate — and solve it three ways against the running Northstar platform: raw filtered CLI, the service-health skill from Module 6, and a typed read-only MCP observer you wire in here. You will record each run in an Agent Run Ledger, fill a comparison table, and then do the thing that separates an observer from a deny rule: try to make the observer write, and watch it fail because there is nothing to call.

By the end you will have a working read-only MCP server in platform/mcp-servers/, three recorded runs, and a defensible verdict on when each interface wins — the judgment the whole module exists to build.

Where you are working

You start at the root of the agentic-ops-lab workspace. The shootout diagnoses a live orders-api readiness defect, injected in Step 0 with scripts/inject.sh readiness-drift so all three approaches have a real problem to find. It reproduces the signature Module 1 taught — orders-api live but not ready against a healthy inventory-api — deliberately rather than by assuming Module 1's repair was never merged. The service-health skill you built in Module 6 is reused as-is for approach 2. The MCP observer for approach 3 is built fresh in this lab.

Step 0 — Prerequisites and the running stack​

Confirm your tools, then bring up the core services so all three approaches have a live orders-api to diagnose. The MCP observer is a Node script, so node matters here.

claude --version
node --version
jq --version
docker compose --profile core up -d
scripts/inject.sh readiness-drift
Expected output
2.1.197 (Claude Code)
v22.22.2
jq-1.7.1
 Container agentic-ops-lab-postgres-1       Healthy
 Container agentic-ops-lab-inventory-api-1  Healthy
 Container agentic-ops-lab-orders-api-1     Started

Your versions will differ. The three core containers come up. Give orders-api a few seconds to finish starting before the next step.

Confirm the defect is live — this is the problem all three approaches must diagnose:

curl -s -o /dev/null -w 'orders_healthz=%{http_code}\n' http://localhost:8080/healthz
curl -s http://localhost:8080/readyz
echo
curl -s -o /dev/null -w 'inventory_healthz=%{http_code}\n' http://localhost:8081/healthz
Expected output
orders_healthz=200
{"status":"not ready","checks":{"inventory_api":false}}
inventory_healthz=200

orders-api is live (healthz=200) but not ready — its readyz reports inventory_api:false, even though inventory-api is itself healthy (healthz=200). The correct diagnosis every approach must reach: orders-api's dependency check on inventory-api is failing — the process is fine, the readiness probe is misconfigured. That is the ground truth you will grade all three runs against.

Step 1 — Set up the Agent Run Ledger​

Every run gets recorded to one ledger so the comparison is apples-to-apples. The ledger and a probe helper already ship in labs/m7/. Make them executable and see what the ledger records.

chmod +x labs/m7/shootout-ledger.sh labs/m7/probe-observer.sh
./labs/m7/shootout-ledger.sh
Expected output
usage: labs/m7/shootout-ledger.sh record <approach> <correct> <cost_usd> <latency_s> <tool_attempts> <least_priv>
       labs/m7/shootout-ledger.sh table

The ledger records one row per approach with six fields: which interface, whether it reached the correct diagnosis, the run's cost, its wall-clock latency, how many tool attempts (turns) it took, and a one-line note on its least-privilege posture. You will call record three times, then table.

How you get the metrics

Every claude -p run below adds --output-format json, which returns a JSON envelope with total_cost_usd, duration_ms, and num_turns alongside the result. You will read those three numbers off each run and hand them to the ledger. Cost stands in for tokens here because it is what the run reports directly and it moves with token usage; num_turns stands in for tool attempts. Your exact numbers will differ from the ones shown — models and caching vary run to run — but the comparison itself holds.

Step 2 — Approach 1: Filtered CLI (raw Bash)​

Hand the agent Bash and let it diagnose with curl, grep, jq. This is the most flexible interface — the agent composes whatever commands it wants — and the least constrained: Bash can run anything, and you would rein it in only with the deny rules from Module 2.

claude -p "A ticket says orders-api readyz is failing. Use Bash with curl/jq only to diagnose against localhost:8080 and 8081. Report the root cause in 2 sentences." \
  --allowedTools "Bash" \
  --dangerously-skip-permissions \
  --output-format json | jq -r '"cost=$\(.total_cost_usd) dur_ms=\(.duration_ms) turns=\(.num_turns)\n---\n\(.result)"'
Expected output
cost=$0.224684 dur_ms=34934 turns=11
---
**Root cause:** orders-api `/readyz` fails because its dependency check on inventory-api
returns `"inventory_api": false`, even though inventory-api is healthy and its own `/readyz`
reports ready. orders-api is likely checking inventory-api at a wrong host/port internally
(misconfigured service URL or endpoint), so its readiness probe sees inventory as down
despite it being up.

Your numbers and wording will differ. Two things to notice. First, the diagnosis is correct — it found the dependency check failing. Second, look at turns=11: the agent composed and ran many separate commands — curl this, grep that, jq the other — exploring freely because Bash let it. That flexibility is the CLI's strength and its cost: it works on any problem with zero setup, but it sprawls, and every one of those 11 turns was a command that could have been anything, not just a read.

Record the run. Use your own three numbers; yes because the diagnosis was correct:

./labs/m7/shootout-ledger.sh record cli yes 0.2247 34.9 11 "Bash: can run anything"
Expected output
recorded: cli

Step 3 — Approach 2: The service-health skill​

Now use the skill you built in Module 6. It wraps the same probes in a bounded procedure with an output schema and stop conditions — the agent follows the recipe instead of improvising.

claude -p "A ticket says orders-api readyz is failing. Use the service-health skill to diagnose orders-api. Report the root cause using the skill's output schema." \
  --allowedTools "Bash" "Read" \
  --dangerously-skip-permissions \
  --output-format json | jq -r '"cost=$\(.total_cost_usd) dur_ms=\(.duration_ms) turns=\(.num_turns)\n---\n\(.result)"'
Expected output
cost=$0.173194 dur_ms=28574 turns=5
---
{
  "service": "orders-api",
  "healthy": false,
  "checks": { "healthz": 200, "readyz": "not ready", "inventory_api": false },
  "recommendation": "orders-api is live but not ready; its inventory-api dependency check
   is failing. Investigate inventory-api, not orders-api."
}

Wording varies; the result does not. Compare with approach 1: turns=5 instead of 11, and the output arrives structured — the skill's schema, not free-form prose the agent invented. The skill narrowed the sprawl (the procedure told it what to collect and how to report) and constrained the output. But the tool underneath is still Bash — the skill guided the agent's behaviour, it did not remove the agent's ability to run other commands. Authority control here is the skill's instructions plus your permission floor, not a smaller tool surface.

Record it:

./labs/m7/shootout-ledger.sh record skill yes 0.1732 28.6 5 "Bash+Read via skill scope"
Expected output
recorded: skill

Step 4 — Approach 3: Register the read-only MCP observer​

The third approach is different in kind. Instead of giving the agent a general tool and hoping it behaves, you give it a server that exposes only three typed read tools — and no write tool exists to call.

The observer itself ships in platform/mcp-servers/, already written. You are not building it here; you are reading its surface, proving the boundary at the protocol level, and wiring it in. That is the honest division — the interesting engineering in an MCP server is the surface you choose to expose, and that choice is what you are about to review.

cat platform/mcp-servers/northstar-observer.tools.json
Expected output
{
  "server": "northstar-observer",
  "description": "Read-only observer for Northstar services. Query tools only; no write/mutate tools exist.",
  "read_only": true,
  "tools": [
    { "name": "get_health", "kind": "read", "endpoint": "/healthz" },
    { "name": "get_readiness", "kind": "read", "endpoint": "/readyz" },
    { "name": "get_info", "kind": "read", "endpoint": "/api/v1/info" }
  ]
}

Three tools, every one kind: read. This manifest is the observer's whole surface — get_health, get_readiness, get_info, mapping to /healthz, /readyz, /api/v1/info. There is no restart, no scale, no apply. That absence is the entire point, and you will prove it is real in Step 6.

Before wiring it into Claude Code, smoke-test the server directly over stdio with the probe helper. This drives the raw MCP protocol — initialize, tools/list, one read call, and one write attempt — so you can see the boundary at the protocol level:

./labs/m7/probe-observer.sh orders-api | jq -c 'select(.id==2 or .id==3 or .id==9) | {id, tools: (.result.tools|length), error: (.error.message // null)}'
Expected output
{"id":2,"tools":3,"error":null}
{"id":9,"tools":null,"error":"unknown tool: restart"}
{"id":3,"tools":null,"error":null}

Read the three lines by id. id:2 is tools/list — the server offers exactly 3 tools. id:3 is a get_readiness read — it succeeds (no error). id:9 is a restart write attempt — it fails with unknown tool: restart. The write did not get denied; it got rejected as nonexistent. There is no restart in the interface to call. (Lines may arrive out of id order — the read does a live HTTP call, so it finishes after the synchronous write rejection.)

Now register the server with Claude Code. Project-scoped MCP servers live in a .mcp.json at the workspace root:

cat > .mcp.json <<'EOF'
{
  "mcpServers": {
    "northstar-observer": {
      "command": "node",
      "args": ["./platform/mcp-servers/northstar-observer.js"]
    }
  }
}
EOF
claude mcp list
Expected output
northstar-observer: node ./platform/mcp-servers/northstar-observer.js - ⏸ Pending approval (run `claude` to approve)

Claude Code found the server. A project-scoped server starts as pending approval — a supply-chain guardrail, since an MCP server is code Claude Code will execute. In interactive claude you would approve it once; in the headless run below you allow its tools explicitly by name (mcp__northstar-observer__*), which is the same scoping surface from Module 2 applied to MCP tool names.

Step 5 — Approach 3, continued: diagnose through the observer​

Run the same ticket, but this time the agent may use only the observer's typed tools. It has no Bash, no curl — its entire capability is three read tools.

claude -p "A ticket says orders-api readyz is failing. Use ONLY the northstar-observer MCP tools to diagnose. Report the root cause in 2 sentences." \
  --allowedTools "mcp__northstar-observer__get_health" "mcp__northstar-observer__get_readiness" "mcp__northstar-observer__get_info" \
  --dangerously-skip-permissions \
  --output-format json | jq -r '"cost=$\(.total_cost_usd) dur_ms=\(.duration_ms) turns=\(.num_turns)\n---\n\(.result)"'
Expected output
cost=$0.193300 dur_ms=26051 turns=7
---
**Root cause:** orders-api's readiness probe (`/readyz`) fails because its dependency check
on `inventory_api` returns `false`, even though inventory-api is actually healthy and ready.
This points to a connectivity or configuration issue in orders-api's readiness check —
likely orders-api using a wrong URL/endpoint to reach inventory-api internally, causing the
dependency check to fail despite inventory-api being fully operational.

Your numbers differ. The diagnosis is correct — same ground truth as the other two. But note what the agent could do here: nothing except call three read tools. It had no path to run an arbitrary command, because none existed in its tool surface. The result came back as typed JSON from each tool, not raw text the agent had to parse. This is least privilege by construction, not by policy.

Record the third run:

./labs/m7/shootout-ledger.sh record mcp yes 0.1933 26.1 7 "read tools only — no write exists"
Expected output
recorded: mcp

Step 6 — The observer boundary: try to make it write​

This is the step that proves the observer is more than "typed CLI." Ask the agent — through the observer — to restart orders-api. There is no restart tool. Watch what happens.

claude -p "orders-api is unhealthy. Restart it using the northstar-observer tools." \
  --allowedTools "mcp__northstar-observer__get_health" "mcp__northstar-observer__get_readiness" "mcp__northstar-observer__get_info" \
  --dangerously-skip-permissions \
  --output-format json | jq -r '.result'
Expected output
I can't restart orders-api with the northstar-observer tools — the server exposes only
read-only observability tools: get_health, get_readiness, and get_info. There is no
restart, scale, or any mutating tool available. To restart the service you'd need a
separate mechanism (e.g. docker compose restart, or a deployment tool) outside this
observer, which is intentionally read-only.

Wording varies. The point is what the agent cannot do and why. It did not refuse because a rule said no — it reported that there is no tool to call. Contrast this with the Module 6 service-restart skill, which relied on a stop condition and the permission floor to be safe. Here the safety is structural: restart is not in the tool set, so there is no attempt that could succeed. A capability that does not exist cannot be misused. (You can confirm nothing restarted — the orders-api container's start time is unchanged, because no restart was ever issued.)

Step 7 — Compare: fill the shootout table​

You have three recorded runs. Render the ledger as a table and read the verdict off it.

./labs/m7/shootout-ledger.sh table
Expected output
approach | correct | cost_usd  | latency_s | tool_attempts | least_privilege
---------|---------|-----------|-----------|---------------|-------------------
cli      | yes     | 0.2247    | 34.9      | 11            | Bash: can run anything
skill    | yes     | 0.1732    | 28.6      | 5             | Bash+Read via skill scope
mcp      | yes     | 0.1933    | 26.1      | 7             | read tools only — no write exists

Your numbers will differ, but the pattern is the lesson. All three reached the correct diagnosis — the ticket was well within reach of any interface. The differences are everywhere else:

  • CLI took the most turns (11) and cost the most — it explored freely because Bash let it, which is exactly why its least-privilege posture is the worst: it could run anything.
  • Skill was the tightest on this small task (fewest turns, lowest cost) because the procedure told the agent what to collect and how to report — but it still ran on Bash underneath.
  • MCP was competitive on cost and latency, and it is the only row where least privilege is structural: the agent had read tools and nothing else. On a one-off like this the token savings are modest (the tool definitions add some overhead); the win is the boundary, and that win compounds when the operation runs repeatedly against production.

Step 8 — Let the repository confirm the observer​

Run the module grader. It checks that the observer exists, that its manifest is genuinely read-only, that over stdio it lists exactly the three read tools and rejects a write, and that the ledger captured all three approaches.

./scripts/grade.sh m7
Expected output
Grading: Module m7
========================

Checking: Three-Way Tool Shootout — the read-only MCP observer

  ✓ read-only observer server + tool manifest present
  ✓ manifest is read-only — every exposed tool is a read tool
  ✓ server exposes exactly get_health, get_info, get_readiness (no write tool)
  ✓ a write attempt fails — no write tool exists to call (observer boundary)
  ✓ shootout ledger captured all three approaches (cli, skill, mcp)

RESULT: PASS (5 passed)

Five green. The grader ran the observer over its real stdio protocol to confirm the tool surface is exactly three reads and that a restart call is rejected as nonexistent — the same structural boundary you saw by hand in Step 6, now certified by the repository.

Step 9 — The verdict: when each interface wins​

You now have the evidence to state the rule the module has been building toward. Fill this in for yourself from your own table; here is the defensible version:

InterfaceWins whenBecause
Raw CLIOne-off exploration, ill-defined problem, low authorityZero setup, works on anything — accept the sprawl and the broad authority for the flexibility
SkillA repeated procedure you want bounded and structured, still on trusted CLIGuides behavior and output without server overhead; control and transparency
MCP observerHigh-authority or high-frequency reads, especially against productionLeast privilege is structural — no write tool exists — and output is typed; the boundary earns its build cost

The one-line rule from the lesson, now grounded in three real runs: CLI for exploration, MCP when the boundary earns its keep. The observer's read-only guarantee is not prose the agent might ignore — it is the absence of a tool. That is the property the Deep Dive dissects next, and the reason an observer is the right interface for a diagnostic you will run on production during an incident.

Step 10 — Teardown​

Bring the stack down. Keep the observer server and the lab scripts — they are module deliverables the Deep Dive builds on. Remove only the ephemeral ledger and the .mcp.json registration if you do not want the pending server lingering.

The readiness-drift injection needs no separate reset: it lives as an environment override on the orders-api container, so removing the container clears it. Your next docker compose up starts from the compose defaults with a healthy dependency check.

docker compose --profile core down
rm -f labs/m7/shootout.jsonl
git status --short platform/mcp-servers/ labs/m7/
Expected output
 Container agentic-ops-lab-orders-api-1      Removed
 Container agentic-ops-lab-inventory-api-1   Removed
 Container agentic-ops-lab-postgres-1        Removed
?? labs/m7/
?? platform/mcp-servers/

The stack is down; the observer server and lab scripts remain as untracked files. In real work your next move is to commit them — the observer is a reusable piece of Northstar's operating layer, the same way the M6 skills were. (Leave .mcp.json if you want the server registered for the Deep Dive; remove it with rm .mcp.json if you prefer a clean root.)

You solved one ticket three ways and let the evidence decide, not preference. You built a read-only MCP observer whose safety is structural — a write fails because no write tool exists, which you proved both by hand and through the grader. And you can now state, with a table to back it, when raw CLI, a skill, or a typed observer is the right interface. The Deep Dive presses on the observer's threat model — why the write attempt fails at the protocol level rather than the permission level — and adds ToolHive runtime isolation for the case the whole supply-chain thread points at: when the MCP server is code you did not write.
