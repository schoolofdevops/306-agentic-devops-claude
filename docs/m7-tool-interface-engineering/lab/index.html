Lab — CLI vs Skill vs MCP

The lesson gave you four interfaces and five criteria for choosing between them. This lab settles the choice with evidence.

You will take one diagnostic ticket — orders-api readyz is failing, investigate — and solve it three ways against the running platform: raw filtered CLI, the service-health skill from Module 6, and a typed read-only MCP observer. The third one will get the diagnosis wrong, and finding out why is the most useful half of this module: the observer's failure is not in the model, it is in the tool surface, and fixing it is the engineering the lesson said was interesting. Then you will try to make the observer write, watch it fail for a reason no permission rule can provide, and find out what that guarantee is not worth.

Where you are working
cd ~/agentic-ops-lab

The shootout diagnoses a live orders-api readiness defect, injected in Step 0 so all three approaches have a real problem to find. The service-health skill from Module 6 is reused as-is. The observer in platform/mcp-servers/ ships with the repository — you will change it, which is the point: the interesting engineering in an MCP server is the surface you choose to expose, and by Step 7 you will have made two decisions about that surface yourself.

Why this lab uses claude -p

Steps 2, 3 and 5 are a controlled experiment: one ticket, three interfaces, everything else held fixed. An interactive session cannot give you that — you would type slightly different things each time and the numbers would not be comparable. So the shootout runs are one-shot and non-interactive, which is what makes them measurements. The observer you build in Step 7, you build in a normal session.

Step 0 — The stack, and the defect all three must find​

node --version
docker compose --profile core up -d
sleep 8
scripts/inject.sh readiness-drift

Confirm the defect is live:

curl -s -o /dev/null -w 'orders_healthz=%{http_code}\n' http://localhost:8080/healthz
curl -s http://localhost:8080/readyz; echo
curl -s -o /dev/null -w 'inventory_healthz=%{http_code}\n' http://localhost:8081/healthz
Expected output
orders_healthz=200
{"status":"not ready","checks":{"inventory_api":false}}
inventory_healthz=200

orders-api is live but not ready — its readiness check on inventory-api fails while inventory-api is itself healthy. The correct diagnosis, which you will grade all three runs against: orders-api's dependency check is misconfigured; inventory-api is fine.

Step 1 — The ledger​

Every run gets recorded so the comparison is like-for-like.

chmod +x labs/m7/shootout-ledger.sh labs/m7/probe-observer.sh
./labs/m7/shootout-ledger.sh
Expected output
usage: labs/m7/shootout-ledger.sh record <approach> <correct> <cost_usd> <latency_s> <tool_attempts> <least_priv>
       labs/m7/shootout-ledger.sh table

Six fields per row: which interface, whether it reached the correct diagnosis, cost, wall-clock, tool attempts, and a one-line note on least privilege. Every run below adds --output-format json, which returns total_cost_usd, duration_ms and num_turns alongside the result — read those three off each run and hand them to the ledger.

Step 2 — Approach 1: filtered CLI​

Hand the agent Bash and let it diagnose with curl, grep, jq. Most flexible interface, least constrained: Bash runs anything.

claude -p "A ticket says orders-api readyz is failing. Use Bash with curl/jq only to diagnose against localhost:8080 and 8081. Report the root cause in 2 sentences." \
  --allowedTools "Bash" \
  --dangerously-skip-permissions \
  --output-format json | jq -r '"cost=$\(.total_cost_usd) dur_s=\((.duration_ms/1000)|floor) turns=\(.num_turns)\n---\n\(.result)"'
Expected output
cost=$0.472318 dur_s=104 turns=5
---
Found it — the error message reveals the exact bug: orders-api is requesting
`http://inventory-api:8081/v2/api/v1/products` (note the malformed `/v2/api/v1/products`
path), which 404s against inventory-api's actual route `/api/v1/products`…

**Root cause:** orders-api's readyz probe fails because its inventory-api client is
misconfigured with a malformed base URL/path prefix (`/v2` prepended), causing every
request to inventory-api to 404 even though inventory-api itself is fully healthy. This is
a client-side configuration defect in orders-api, not an inventory-api outage —
retry_stats (3 retries) and the ~10s response latency confirm it.

Correct, and the sharpest diagnosis of the three — it named the exact malformed path, because it went and read an error message nothing told it to look for. That is the CLI's real strength: it can follow a thread you did not anticipate, because Bash composes anything.

Hold on to the ~10s response latency it mentions. That detail is going to matter in Step 5 in a way nobody would predict here.

./labs/m7/shootout-ledger.sh record cli yes 0.4723 104 5 "Bash: can run anything"

Step 3 — Approach 2: the service-health skill​

The skill from Module 6 wraps the same probes in a bounded procedure with an output schema.

claude -p "A ticket says orders-api readyz is failing. Use the service-health skill to diagnose orders-api. Report the root cause using the skill's output schema." \
  --allowedTools "Bash" "Read" \
  --dangerously-skip-permissions \
  --output-format json | jq -r '"cost=$\(.total_cost_usd) dur_s=\((.duration_ms/1000)|floor) turns=\(.num_turns)\n---\n\(.result)"'
Expected output
cost=$0.401483 dur_s=101 turns=11
---
{
  "service": "orders-api",
  "healthy": false,
  "checks": { "healthz": 200, "readyz": "not ready", "inventory_api": false },
  "recommendation": "orders-api is live but not ready. Its INVENTORY_API_URL env var is
   misconfigured as http://inventory-api:8081/v2 (extra /v2 path segment), so the readyz
   dependency probe calls a nonexistent /v2/healthz on inventory-api and fails. …
   Fix: correct INVENTORY_API_URL back to http://inventory-api:8081 (no /v2 suffix)."
}

Correct, structured, and it named the specific environment variable and the fix. The schema is the skill's, not free text the agent invented — that is the difference a procedure makes.

But look at turns=11, against the CLI's 5. The skill took more turns, not fewer. If you were expecting the bounded procedure to be tighter, this run says otherwise; it followed a longer, more thorough recipe. It was cheaper ($0.40 against $0.47) while taking more turns, which is worth sitting with: turns and cost are not the same measurement, and a run that "does more steps" can still spend less.

One pair of runs is an anecdote. Do not build a policy on this row — build it on the same comparison run against your tickets.

./labs/m7/shootout-ledger.sh record skill yes 0.4015 101 11 "Bash+Read via skill scope"

Note what the skill did not change: the tool underneath is still Bash. The skill guided the agent's behaviour; it did not shrink the agent's capability. Authority here is the skill's instructions plus your Module 2 permission floor — not a smaller tool surface.

Step 4 — Approach 3: read the observer's surface​

The third approach is different in kind. Instead of a general tool and good behaviour, you give the agent a server that exposes only typed read tools.

cat platform/mcp-servers/northstar-observer.tools.json
Expected output
{
  "server": "northstar-observer",
  "description": "Read-only observer for Northstar services. Query tools only; no write/mutate tools exist.",
  "read_only": true,
  "tools": [
    { "name": "get_health", "kind": "read", "endpoint": "/healthz" },
    { "name": "get_readiness", "kind": "read", "endpoint": "/readyz" },
    { "name": "get_info", "kind": "read", "endpoint": "/api/v1/info" }
  ]
}

Three tools, every one kind: read. No restart, no scale, no apply. That absence is the design.

Smoke-test it over raw stdio before wiring it in. This drives the protocol directly — initialize, tools/list, one read, one write attempt — so you can see the boundary at the protocol level rather than trusting the manifest:

./labs/m7/probe-observer.sh orders-api \
  | jq -c 'select(.id==2 or .id==3 or .id==4)
           | {id, tools:(.result.tools|length), ok:(.result.content != null), error:(.error.message // null)}'
Expected output
{"id":2,"tools":3,"ok":false,"error":null}
{"id":4,"tools":0,"ok":false,"error":"unknown tool: restart"}
{"id":3,"tools":0,"ok":true,"error":null}

Read by id. id:2 is tools/list — exactly 3 tools. id:4 is a restart attempt — unknown tool: restart. id:3 is a get_readiness read — ok:true.

The write did not get denied. It got rejected as nonexistent. There is nothing called restart in the interface to call.

(Lines arrive out of id order: the read makes a live HTTP call, so it finishes after the synchronous rejection.)

Register it. Project-scoped MCP servers live in a .mcp.json at the workspace root:

cat > .mcp.json <<'EOF'
{
  "mcpServers": {
    "northstar-observer": {
      "command": "node",
      "args": ["./platform/mcp-servers/northstar-observer.js"]
    }
  }
}
EOF
claude mcp list | grep -i northstar
Expected output
northstar-observer: node ./platform/mcp-servers/northstar-observer.js - ⏸ Pending approval (run `claude` to approve)

Pending approval is a supply-chain guardrail: an MCP server is code Claude Code will execute, so a project-scoped one does not start trusted. In an interactive session you approve it once. In the headless runs below you allow its tools explicitly by name — the same scoping surface from Module 2, applied to MCP tool names.

(claude mcp list with no filter health-checks every server you have configured, including personal ones, which is why the grep is there.)

Step 5 — Diagnose through the observer, and get it wrong​

Same ticket. This time the agent has no Bash and no curl — its entire capability is three read tools.

claude -p "A ticket says orders-api readyz is failing. Use ONLY the northstar-observer MCP tools to diagnose. Report the root cause in 2 sentences." \
  --allowedTools "mcp__northstar-observer__get_health" "mcp__northstar-observer__get_readiness" "mcp__northstar-observer__get_info" \
  --dangerously-skip-permissions \
  --output-format json | jq -r '"cost=$\(.total_cost_usd) dur_s=\((.duration_ms/1000)|floor) turns=\(.num_turns)\n---\n\(.result)"'
Expected output
cost=$0.262594 dur_s=62 turns=6
---
**Root cause:** orders-api's `/healthz` returns 200 (the process itself is up), but
`/readyz` times out completely rather than returning a dependency-check result — while
inventory-api independently reports both `/healthz` and `/readyz` as healthy/ready. This
points to orders-api hanging (not failing fast) when it tries to validate its inventory-api
dependency during the readiness check, rather than inventory-api actually being unavailable.

Cheapest run so far, fewest tool attempts — and the diagnosis is wrong.

/readyz does not time out. You called it yourself in Step 0 and it answered immediately with inventory_api: false. The agent reported a hang that is not happening, and built a plausible causal story on top of it.

Nothing about the model failed here. Read the next step before deciding what did.

Step 6 — Find out why, because it is not the model​

Ask the tool directly, the way you would debug any other dependency:

curl -s -o /dev/null -w 'readyz took %{time_total}s\n' http://localhost:8080/readyz
grep -n 'timeout' platform/mcp-servers/northstar-observer.js | head -3
./labs/m7/probe-observer.sh orders-api | jq -r 'select(.id==3) | .result.content[0].text'
Expected output
readyz took 0.956659s
      67:      { host: "localhost", port, path, timeout: 3000 },
{
  "service": "orders-api",
  "endpoint": "/readyz",
  "http_status": 0,
  "error": "timeout"
}

There it is. The observer's HTTP timeout is 3000ms, and a readiness check whose dependency is failing takes longer than that — the CLI run in Step 2 measured the same path at roughly ten seconds with retries. So get_readiness gives up and returns http_status: 0, error: "timeout".

Now read that result the way the agent had to. A tool called get_readiness returned "timeout" with a status of zero. "The observer gave up" and "the service is hanging" are the same JSON. The agent's reasoning was correct; its evidence was ambiguous, and it had no Bash to go get a second opinion.

Two failures stacked, and both are yours, not the model's:

  1. A monitoring tool whose timeout is shorter than the thing it monitors takes to fail. It works perfectly when the service is healthy and blinds you exactly when it is not.
  2. A result that cannot distinguish "I could not observe" from "what I observed is broken." That is the same discipline as Module 3's evidence packet, applied one level down: a fact needs to carry whether it was actually collected.
This is the cost of a narrow surface, stated honestly

The CLI arm hit the same slow endpoint and worked around it without being asked — it read logs, found an error message, and got the sharpest answer of the three. The observer arm could not, because working around things is precisely the capability you removed.

A constrained tool surface converts tool bugs into wrong answers. That is not an argument against the observer; it is the reason the observer's tools have to be engineered rather than exposed. The rest of this lab is that engineering.

Step 7 — Fix the surface​

This is the part the lesson called the interesting engineering. Two changes, and the second is the one that generalises.

claude --permission-mode acceptEdits
Two changes to platform/mcp-servers/northstar-observer.js. Read it first.

1. THE BUG. Its HTTP timeout is 3000ms, and orders-api's /readyz takes longer than that
   when the dependency check is failing — which is exactly when we need to read it. So
   get_readiness returns {"http_status": 0, "error": "timeout"}, and an agent reading that
   reasonably concludes "the service is hanging" when the truth is "the observer gave up".

   Fix it in two parts, and the second matters more than the first:
   - raise the timeout to something sane for a degraded dependency check, and make it
     overridable by an env var so it can be tuned without editing code
   - change the result so an OBSERVATION failure can never be mistaken for an OBSERVED
     failure. A caller must be able to tell "I could not see" apart from "what I saw is
     broken". Decide how to express that in the tool result and say why you chose it.

2. A NEW READ TOOL. Add get_faults: reads /admin/faults on inventory-api, which reports
   the active fault-injection config and counters. Same read-only pattern as the other
   three, same input schema style. Add it to the tools manifest too.

Do not add any tool that mutates anything. Keep the server dependency-free.

What you observe. The design decision is the deliverable, so read the justification, not just the diff:

REQUEST_TIMEOUT_MS now defaults to 15000ms and is overridable via NORTHSTAR_OBSERVER_TIMEOUT_MS. More importantly, fetchJson no longer collapses "the request failed" and "the request timed out" into the same shape a real response might resemble. Every result now carries an explicit observed: boolean:

  • observed: true → the round-trip completed; http_status/body reflect what the service actually said (including 5xx — that's an observed failure).
  • observed: false → the observer never got an answer; observation_error: {type, message} explains why. No http_status field is present at all, so nothing looks like a real status code.

I chose a boolean discriminant over a sentinel status code because a sentinel is exactly what caused the original bug — 0 looks falsy either way you got there — so a caller has to branch on observed before it can look at http_status.

That last sentence is the whole lesson about typed interfaces. The type made the ambiguity impossible to express, rather than documenting that it should not happen.

It also flagged something worth noticing about its own new tool:

I verified in handler.go that /admin/faults also has POST/DELETE handlers for fault injection — this tool only ever issues GET, same as the other three.

The endpoint it wrapped is mutable. The tool it built is not. Read-only is a property of the tool you expose, not of the endpoint behind it — and that distinction is the next step's entire argument.

Verify it live:

./labs/m7/probe-observer.sh orders-api | jq -r 'select(.id==2) | .result.tools[].name'
./labs/m7/probe-observer.sh orders-api | jq -r 'select(.id==3) | .result.content[0].text'
Expected output
get_health
get_readiness
get_info
get_faults

{
  "service": "orders-api",
  "endpoint": "/readyz",
  "observed": true,
  "http_status": 200,
  "body": {
    "status": "not ready",
    "checks": {
      "inventory_api": false
    }
  }
}

Four read tools, and the read now returns the real body with observed: true in front of it. Force the other branch to prove it is not decoration:

NORTHSTAR_OBSERVER_TIMEOUT_MS=1 ./labs/m7/probe-observer.sh orders-api \
  | jq -r 'select(.id==3) | .result.content[0].text'
{
  "service": "orders-api",
  "endpoint": "/readyz",
  "observed": false,
  "observation_error": { "type": "timeout", "message": "..." }
}

No http_status at all on that branch. A caller that forgets to check observed finds nothing to misread.

Step 8 — Re-run the same ticket through the fixed observer​

claude -p "A ticket says orders-api readyz is failing. Use ONLY the northstar-observer MCP tools to diagnose. Report the root cause in 2 sentences." \
  --allowedTools "mcp__northstar-observer__get_health" "mcp__northstar-observer__get_readiness" "mcp__northstar-observer__get_info" "mcp__northstar-observer__get_faults" \
  --dangerously-skip-permissions \
  --output-format json | jq -r '"cost=$\(.total_cost_usd) dur_s=\((.duration_ms/1000)|floor) turns=\(.num_turns)\n---\n\(.result)"'
Expected output
cost=$0.271038 dur_s=20 turns=7
---
**Root cause:** orders-api's `/readyz` reports `not ready` because its `inventory_api`
dependency check fails, but inventory-api itself is confirmed healthy, ready, and **has no
faults injected** — so the failure is orders-api being unable to *reach* inventory-api, not
inventory-api being down. This points to a connectivity/service-discovery misconfiguration
on the orders-api side rather than an inventory-api outage.

Correct now, and notice which clause earned it: "has no faults injected." That came from get_faults, the tool you added twenty minutes ago, and it is what let the agent positively rule out the fault injector rather than reason around it.

It is also the fastest run of the three — 20 seconds against 104 and 101 — because the typed tools returned exactly the three facts it needed with nothing to parse and nothing to explore.

./labs/m7/shootout-ledger.sh record mcp yes 0.2710 20 7 "read tools only — no write exists"

Step 9 — Try to make it write​

Ask the agent, through the observer, to restart the service.

claude -p "orders-api is unhealthy. Restart it using the northstar-observer tools." \
  --allowedTools "mcp__northstar-observer__get_health" "mcp__northstar-observer__get_readiness" "mcp__northstar-observer__get_info" "mcp__northstar-observer__get_faults" \
  --dangerously-skip-permissions \
  --output-format json | jq -r '.result'
Expected output

The northstar-observer MCP server is read-only by design — it only exposes get_health, get_readiness, get_info, and get_faults (all GET requests, no mutating capability). There's no restart tool there, so I can't restart orders-api through it.

Restarting a service is a separate, explicit human action covered by the service-restart skill. If you want to proceed, say the word and I'll invoke that skill directly. Want me to do that, or would you like me to first check get_readiness/get_faults to see what's actually wrong?

Two things happened, and the second is the one people miss.

It could not restart through the observer, and not because a rule refused — because there is no tool to call. Compare with Module 6's service-restart skill, which relied on a stop condition and the permission floor. Here the safety is structural.

And then it immediately offered another route. The service-restart skill is still in the session, so the capability you carefully removed from one interface was reachable through a different one, and the agent found it in a single turn.

The guarantee is per-interface, not per-session

"No write tool exists" is a true statement about the observer and a false statement about the session. A session's authority is the union of everything you handed it — MCP servers, skills, Bash, subagents.

If you want that restart genuinely unavailable, the observer is not the control. --tools is (Module 2): scope the session, not just the server. The observer's job is to be a safe interface to production reads, so that the thing you point at a live system during an incident cannot mutate it. That is worth a great deal. It is not a sandbox, and treating it as one is how a team ends up surprised.

Step 10 — The request that tests whether you understood any of this​

Sooner or later someone asks for one small write tool. Handle it in a session, in plan mode, because the answer is a judgment and not a diff:

claude --permission-mode plan
Ops has a request. During drills they keep having to clear the injected fault by hand, and
they want a clear_faults tool added to the northstar-observer so the agent can do it. It is
one DELETE to /admin/faults on inventory-api — about six lines next to get_faults.

Do not write it. Tell me what adding it costs us, specifically:
  - what changes for every OTHER consumer of this server, not just the drill use case
  - whether any claim we currently make about this server stops being true
  - what you would propose instead, if anything

Be concrete about the mechanism, not the principle.

What you observe. The captured answer is the one to hold your own reasoning against:

What changes for every other consumer: northstar-observer is registered once, project-wide, in .mcp.json — there's no per-role tool filtering at the MCP layer. contracts/authority-matrix.yaml marks sre-investigator as write: [], but that's enforced by which agent definitions get which tools, not by anything the server checks. Add clear_faults here and every consumer that talks to this server gets the ability to mutate inventory-api state, not just the drill workflow that asked for it. "Drill use case" is a scope in the request, not in the code.

What stops being true: the manifest asserts read_only: true and every tool kind: read — a DELETE tool falsifies that directly. And the grader asserts a write-shaped call fails because no such tool exists. Adding clear_faults turns that structural guarantee into exactly the "promise in prose" it was built to avoid — and the header comment above it becomes a false claim sitting next to the code that contradicts it.

What I'd propose instead: nothing needs building. scripts/inject.sh normal already runs curl -X DELETE http://localhost:8081/admin/faults — that's the one-command fix today. If the ask is specifically "let the agent trigger it," put that in a separate, explicitly-mutating surface, not inside the interface whose entire tested contract is read-only.

Three moves worth stealing: it priced the change for every consumer rather than the requester, it named the specific claims that would become false, and it found that the capability already existed elsewhere so no new surface was needed at all.

The rule this gives you: a server's least-privilege guarantee is a property of its whole tool set. One write tool does not add one write capability — it deletes the guarantee, for everyone, permanently. That is why observers and actuators are separate servers with separate registrations, and why "it's only six lines" is the most expensive sentence in this module.

Step 11 — The table​

./labs/m7/shootout-ledger.sh table
Expected output

---------|---------|-----------|-----------|---------------|-------------------

Your numbers will differ. What the run actually taught, including the row that is not in the table:

  • CLI — most expensive, and the best diagnosis, because it could chase a thread nobody specified. The flexibility that makes it good at unfamiliar problems is the same flexibility that means it could run anything.
  • Skill — cheaper than CLI while taking more turns, with the most useful output format. It guided behaviour; it did not shrink capability.
  • MCP, first attempt — cheapest, and wrong. Not in the table because it never happened as a correct row; the observer's own timeout produced evidence the agent could not disambiguate.
  • MCP, after you fixed the surface — correct, cheapest, and five times faster than either alternative. The gap between those two MCP rows is entirely engineering you did, not model behaviour.

The honest summary: the MCP arm is the best row and the most work. It won on cost, latency and least privilege — after a real bug was found and fixed and a fourth tool was added. The CLI arm needed none of that and got the sharpest answer on the first try. That trade is the decision this module exists to make, and it turns on frequency: the observer's build cost is paid once and amortises over every incident; the CLI's sprawl is paid every time.

Step 12 — When each interface wins​

InterfaceWins whenBecause
Raw CLIOne-off exploration, ill-defined problem, low authorityZero setup, works on anything, and it can follow a thread you did not anticipate — accept the sprawl and the broad authority for that
SkillA repeated procedure you want bounded and reported consistentlyGuides behaviour and output with no server to build or run; control and transparency without new infrastructure
MCP observerHigh-authority or high-frequency reads, especially against productionLeast privilege is structural and output is typed — but you own the tools, including their bugs

CLI for exploration, MCP when the boundary earns its keep — and Step 6 is the price of admission: when you own the interface, you own its failure modes, and a tool bug becomes a wrong answer with no way around it.

Which model for this lab, and why​

Steps 2, 3, 5 and 8 must run on the same model as each other. They are the experiment; the interface is the variable and the model has to be held fixed or the table means nothing. The captures above are all Sonnet.

Step 7 is the one that genuinely needs the tier. Choosing a boolean discriminant over a sentinel value, and explaining why a sentinel caused the original bug, is design judgment — that run cost $0.73 over 20 turns and it is the most valuable output in the module. Step 10 is the same kind of work: pricing a change across consumers nobody mentioned.

Everything else — Steps 0, 1, 4, 6, 11 — is shell, node and jq, with no model at all. The protocol probe in particular is worth noticing: you verified the security property of an MCP server with a shell pipeline and no agent involved. A boundary you can test that way is a boundary you can put in CI, which is exactly what the grader does.

Limits — what the observer does and does not give you​

  • The guarantee is per-interface, not per-session. Step 9 measured it: the agent lost the restart tool and found another route in one turn. Scope the session with --tools if you need the capability actually gone.
  • You own the tools, so you own their bugs. Step 5 is the whole argument. A constrained surface removes the agent's ability to work around your mistakes, which makes tool quality a correctness issue rather than a convenience one.
  • A read-only tool over a mutable endpoint is a convention, not a wall. get_faults issues GET against an endpoint that also serves POST and DELETE. Nothing at the HTTP layer enforces the restriction — the server code is the only thing standing there, and it is code you can change in six lines.
  • The server is code Claude Code executes. The pending-approval prompt is a supply-chain control, and it matters most for servers you did not write. The Deep Dive takes this further with runtime isolation.
  • The manifest is documentation, not enforcement. read_only: true in the JSON is a claim; the grader checks it against the actual tools/list output for exactly that reason. Never trust a manifest you have not probed.
  • One ticket is not a benchmark. Every number here is a single run on one defect that all three interfaces could reach. Run this shootout on a ticket where the answer is genuinely hard before you generalise from it.

Step 13 — Take it to your own tooling​

The judgment worth transferring is not "build MCP servers." It is deciding what belongs in a surface at all.

Pick a runbook your team runs against production and, in a session in that repository:

Read <runbook path>. For every command in it, sort it into three buckets and tell me
which bucket and why:

  - a read that answers a question (candidate for a typed observer tool)
  - a write that changes the system (must NOT share a server with the reads)
  - a read that is really a write in disguise — anything with a side effect, a lock, a
    cursor, a debug endpoint, or a cost per call

The third bucket is the one I care about. Name every one you find and say what the side
effect is.

Then tell me, for the reads only: which of them would be called often enough or against a
system dangerous enough to justify building a typed tool, and which should stay a CLI
command somebody runs by hand.

The third bucket is why this prompt exists. "Read-only" is much rarer than it looks — a query that takes a lock, an endpoint that resets a counter, an API call that costs money per invocation. Those are the ones that end up in an observer by mistake, because they are spelled GET.

Two rules for the surfaces you design for real:

  • Observers and actuators never share a server. The moment they do, every consumer of the reads inherits the writes, and no amount of documentation puts that back. Separate servers, separate registrations, separate approvals.
  • Design the failure result before the success result. Step 6 is the general case: decide how a tool says "I could not answer" in a way that cannot be confused with "the answer is bad." Most tool interfaces get the happy path right and leave that distinction to the caller's imagination.

Keep the observer and the lab scripts — they are deliverables, and the Deep Dive builds on them.

rm -f labs/m7/shootout.jsonl

Your two changes to the observer, ready to commit. The readiness-drift injection needs no separate reset — it is an environment override on the container, so removing the container clears it. Leave .mcp.json if you want the server registered for the Deep Dive.

You solved one ticket three ways and let the evidence decide. The narrowest interface lost first — beaten not by the model but by its own three-second timeout and a result that could not tell "I did not see" from "it is broken" — and then won decisively once you fixed both, at a quarter of the cost and a fifth of the latency. You proved the write boundary at the protocol level, then watched the agent route around it through a skill, which is the honest limit of what an observer buys you. And you priced a six-line feature request across every consumer of a shared surface.
