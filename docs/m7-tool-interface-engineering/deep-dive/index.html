Deep Dive — The Observer Threat Model and Runtime Isolation

The core lab built a read-only observer and proved, by hand and through the grader, that a write attempt fails because no write tool exists. That is the right result, but "the write failed" is a symptom — this page is about the mechanism, because understanding exactly where and why the write fails is what lets you reason about the observer's real threat model, and where its guarantee stops. Two questions the lab left open: at what layer, precisely, does a write attempt die — and what threat does a read-only tool surface not cover? The answer to the second is the reason ToolHive and runtime isolation exist, and it is the supply-chain thread the whole module has been pointing at.

This extends the lab — it does not repeat it

You already know that the observer refuses to write. This page is about the layer underneath: the MCP protocol's tools/list contract, why "no write tool" is a stronger property than "write is denied," and — the part most people miss — that a read-only tool surface says nothing about whether the server process itself is trustworthy. If you skipped the lab's Step 4, build the observer first; everything here operates on it.

Where the write actually dies: the protocol, not the permission layer​

Trace a write attempt through the stack and you find it fails earlier than most people assume. In Module 2, a blocked command dies at the permission layer: the agent forms a valid Bash(kubectl delete ...) call, and a deny rule catches it before execution. The capability existed; a check stopped its use. A write attempt against the observer dies somewhere different and earlier.

When Claude Code connects to an MCP server, the very first thing it does after initialize is call tools/list. The server responds with the complete, exhaustive set of tools it offers — for the observer, exactly get_health, get_readiness, get_info. That list is the agent's entire universe of callable operations for that server. The agent cannot call a tool that was not in the list, because there is no protocol message that would name it — tools/call takes a tool name, and a name the server never advertised resolves to nothing.

Analogy: this is the difference between a restaurant that refuses to make a dish and a restaurant where the dish is not on the menu and the kitchen has no recipe for it. The first still has the capability — the ingredients are in the back, and whether you get the dish depends on the waiter enforcing a rule. The second has no path to the dish at all: you cannot order what the menu does not list, and even if you described it, the kitchen has nothing to make it from. A deny rule is the refusing waiter. The tools/list contract is the menu with no such item and a kitchen with no such recipe. You are not being told "no" — you are trying to reference something that does not exist in the interface.

Read the sequence carefully: the permission layer is never consulted for a write, because there is no valid write call to consult it about. In the lab's Step 6 the agent did not attempt a restart and get denied — it inspected its tool surface, found no restart tool, and reported the absence. This is why the observer's guarantee is stronger than a deny rule: a deny rule is a control you can get wrong (too narrow a pattern, an unanticipated command shape — the Module 2 failure modes), and it sits on top of a capability that is still there. The absence of a tool is not a control that can be misconfigured. There is nothing to configure.

You can see the two layers behave differently with a direct probe. Ask the server for a tool it never listed and watch it resolve to "unknown" — a nonexistence error, not a forbidden error:

docker compose --profile core up -d
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  '{"jsonrpc":"2.0","id":11,"method":"tools/call","params":{"name":"scale","arguments":{"replicas":0}}}' \
  '{"jsonrpc":"2.0","id":12,"method":"tools/call","params":{"name":"delete","arguments":{"service":"orders-api"}}}' \
  | node platform/mcp-servers/northstar-observer.js | jq -c 'select(.id>=11) | {id, error: .error.message}'
Expected output
{"id":11,"error":"unknown tool: scale"}
{"id":12,"error":"unknown tool: delete"}

Both write-shaped calls — scale, delete — come back as unknown tool, not "permission denied." The distinction is the whole point. A permission-denied response means the tool exists and a policy rejected the call; you would harden that by tightening the policy. An unknown tool response means there is nothing there — no policy is involved, and no policy needs to be, because the capability was never part of the surface. Naming the tool in --allowedTools on the client side would not help either: allowing a tool the server does not expose still leaves nothing to call.

What "read-only tool surface" does not protect against​

Here is the threat the observer pattern does not cover, and it is the one that matters most for production. The read-only guarantee is about what the agent can ask the server to do. It says nothing about what the server process itself does when it runs. And an MCP server is a program — the observer is node platform/mcp-servers/northstar-observer.js, a process Claude Code launches on your machine, with your user's privileges, your filesystem, your network.

Analogy: the tool surface is the set of buttons on a vending machine's front panel — you have designed it so the only buttons are "dispense water" and "dispense juice," and a customer cannot dispense anything else. But the machine's internal wiring is a separate concern entirely. If the machine's manufacturer wired it to also quietly phone home with everyone's purchase history, or to overheat, the limited front panel does nothing about that — the customer's restricted buttons never touched the machine's own behavior. A read-only tool surface constrains the customer (the agent). It does not vouch for the machine (the server code). For a server you wrote and can read — like the observer — that gap is small, because you know the wiring. For a server you npm install from a third party, the gap is the whole risk.

This is why the module kept returning to supply chain. Two separate trust questions live in every MCP server, and conflating them is the mistake:

  1. What can the agent make the server do? — answered by the tool surface. A read-only observer answers this well: nothing but reads.
  2. What does the server do on its own, with the privileges you launched it with? — answered by nothing in the tool surface. It is answered only by trusting the code, or by containing the process.

For the observer you built, question 2 is easy: you read the whole file, it makes outbound HTTP to two localhost ports and nothing else. For a third-party MCP server — a database server, a cloud-provider server, one of dozens on a public registry — you often cannot read all the code, and "it only exposes read tools" tells you nothing about what its process does with the credentials and filesystem access you handed it.

ToolHive: containing the server process itself​

This is the gap ToolHive fills. ToolHive (an open-source project from Stacklok) runs each MCP server inside its own locked-down container instead of as a bare process on your host, so the server's own behavior is constrained regardless of what tools it exposes. It answers question 2 the way the observer pattern answers question 1 — structurally, by removing capability rather than policing it.

Analogy: if a read-only tool surface is choosing which buttons the vending machine has, ToolHive is putting the whole machine inside a locked room with a single, metered pipe for exactly the one utility it legitimately needs. Even if the machine's internal wiring is malicious, it can only reach what the room's one pipe allows — it cannot touch the rest of the building. You have stopped trusting the machine's insides and started containing them.

Concretely, running an MCP server under ToolHive gives you:

  • Filesystem isolation — the server sees only the paths you mount into its container, not your whole home directory. A server that tried to read ~/.aws/credentials finds no such file, because it was never mounted.
  • Network isolation — the server reaches only the endpoints you allow. An observer that should talk to two localhost ports is given exactly those; an unexpected outbound connection has nowhere to go.
  • Least-privilege secrets — credentials are injected scoped and controlled, rather than the server inheriting your ambient environment.
  • A vetted registry — a curated set of known MCP servers, so the supply-chain question ("is this server code trustworthy at all?") has a better default answer than "whatever the internet published."

The two controls compose, and that is the point. A read-only tool surface constrains what the agent can ask; ToolHive constrains what the server can do. Together they close both trust questions: the agent cannot request a write (no write tool), and the server cannot exfiltrate or tamper on its own (no filesystem or network reach beyond what you granted). For the observer you built — code you wrote and can audit — the tool surface alone is a reasonable posture. The moment you reach for a server you did not write, runtime isolation stops being optional hardening and becomes the control that makes running someone else's code sane.

The trap: "it's read-only, so it's safe to install"

The most common supply-chain mistake with MCP is reading a third-party server's tool list, seeing only get_* tools, and concluding the server is safe. That reasoning answers question 1 and ignores question 2 entirely. A server can expose only read tools to the agent while its own process reads your credentials, opens outbound connections, and writes files — none of which the tool surface constrains, because they are the server's behavior, not the agent's requests. "Read-only tools" is not "safe process." Judge the server's code, or contain it (ToolHive), or both — never infer process safety from the tool surface.

Where you'll use this​

  • Vetting an MCP server before adding it to a project (the IaC/FinOps and Kubernetes modules bring real third-party servers into play). Ask the two questions separately: what can the agent make it do (its tool surface), and what can the process do on its own (its code and privileges). A read-only tool list answers only the first. If you cannot fully audit the code, run it under ToolHive so the second question is answered by containment, not trust.
  • Designing your own observer for production (the observability and capstone modules). Writing a read-only tool surface is the right first move, but pair it with a least-privilege credential for the server itself — the read-only KUBECONFIG from the lesson — so that even the server's own process cannot write, not just the agent through it. Two layers, each removing capability.
  • Explaining to a security reviewer why an agent with an observer is safe on production. The strong, defensible claim is structural: the agent has no write tool to call (protocol-level, not a deny rule that could be misconfigured), and the server runs contained with a read-scoped credential and no filesystem or network reach beyond the cluster read API. That pair — surface plus isolation — is a posture a reviewer can accept, in a way that "we told it not to write" never is.
