CLI and MCP Tools

By Module 6 you had built an operating layer of skills: runbooks the agent executes the same way every time. But a skill is only ever a procedure; underneath it, some actual tool does the work. service-health runs curl. k8s-diagnose runs kubectl. terraform-plan-review runs a jq script. Every one of those is a choice about how the agent reaches the outside world, and you made those choices implicitly, reaching for curl and kubectl because they were there. This module makes that choice explicit, because it is one of the highest-leverage decisions in agentic ops. The same diagnostic task can be handed to the agent through raw CLI, through a wrapper script, through a skill, or through a typed MCP server, and those four surfaces differ enormously in how much authority they hand the agent, how many tokens they burn, and how hard it is for the agent to do something you did not intend.

Here is the concrete situation this closes. A ticket lands: "orders-api readyz is failing, investigate." You could hand the agent Bash with curl, grep, and jq and let it work. Flexible, universal, and the agent can run anything Bash can run, including a docker compose down you never asked for. Or you could give it a typed tool called get_readiness that returns exactly one structured object and cannot do anything else, because no other operation exists in its interface. Both solve the ticket. They are not remotely equivalent in risk, cost, or evidence quality. Choosing between them, and knowing when the typed boundary is worth building and when it is over-engineering, is tool interface engineering, and it is the whole of this module.

Why this is a real decision, not a preference​

The reason this matters at work is that the wrong interface fails in two opposite, expensive ways. Reach for raw CLI everywhere and you get an agent that can do anything, which is exactly the problem when it misreads a ticket and runs a mutating command during an incident. Reach for a typed MCP server for everything and you spend a week building server implementations for one-off explorations that a single curl would have answered. Most teams pick one of these by habit and pay for it either in incidents or in wasted engineering. The skill here is picking the right surface per task, on evidence, using a small number of criteria you can apply in seconds.

Analogy: think about how a hospital hands out access to the pharmacy. A general key to the whole dispensary is fast and flexible, a nurse can grab anything, but it means every controlled substance is one wrong turn away, so you give it to almost no one. A requisition form narrows that: the nurse writes down what they need and a pharmacist fills it, so the process is scoped but still involves judgment. An automated dispensing cabinet is narrower still: it only opens the drawers this nurse is authorized for, for this patient, and physically cannot open the others; the restriction is built into the machine, not into a rule someone has to remember. And a vending machine in the lobby dispenses exactly one product line and nothing else, by construction. You do not give everyone the general key "to be safe," and you do not build a custom dispensing cabinet for a box of bandages. You match the delivery mechanism to how dangerous the contents are and how often you reach for them. The four tool interfaces are those four mechanisms, and this module is about matching them.

The four interfaces​

Every way the agent reaches the outside world in Claude Code is one of four surfaces. They form a spectrum from "maximum flexibility, maximum authority" to "minimum surface, least privilege by construction."

Raw CLI (Bash). You give the agent the Bash tool and it runs shell commands directly: curl, kubectl, jq, anything on the PATH. This is universal and needs zero setup: whatever a human can run at a terminal, the agent can run. The cost is twofold. First, authority: Bash is a general capability, the agent can run any command, and you constrain it only after the fact with deny rules and sandbox (the Module 2 machinery). Second, tokens: raw CLI output is unstructured text, a kubectl describe dumps hundreds of lines, and the agent pays to read all of it and parse the meaning out itself.

Wrapper script. You write a script, check-health.sh, that runs the CLI for the agent and returns only what matters. The agent runs one command (./check-health.sh orders-api) instead of composing five. The script controls the scope (it can only do what you wrote into it) and constrains the output (it returns three clean lines, not three hundred). This is the M6 progressive-disclosure idea applied to the tool boundary: the deterministic work lives in a script, so the agent's surface shrinks and its output tokens drop. But the agent still invokes the script through Bash, so Bash is still present, the script narrows what the agent typically does, not what it can do.

Skill. A skill (Module 6) wraps a procedure with instructions, an output schema, and stop conditions. It guides the agent: "collect this evidence, reason this way, report in this structure", and it can bundle wrapper scripts. A skill steers behavior and output structure strongly, but it does not, by itself, remove any capability: a skill still runs on top of whatever tools the agent has (usually Bash). Its authority control is the instructions and the permission floor beneath them, not a smaller tool surface.

MCP server. MCP, the Model Context Protocol, lets you give the agent a set of named, typed tools that are not shell commands at all. You write (or install) a server; it exposes tools like get_readiness with a typed input schema and a typed JSON output. The agent sees get_readiness as a first-class tool alongside Read and Bash, calls it with structured arguments, and gets back structured data. The defining property: the agent can only call the tools the server exposes. If the server has no delete tool, there is no delete. Not "delete is denied," but "delete does not exist in this interface." That is a different kind of guarantee than a deny rule, and the rest of the module turns on it.

Read the spectrum left to right as authority narrowing and structure increasing. On the left, the agent can do almost anything and you rein it in afterward. On the right, the agent can do almost nothing except the few typed things you deliberately exposed. Neither end is "correct". The left is right for open-ended exploration, the right is right for a repeated production operation you want locked down. The engineering is knowing which task sits where.

The decision framework: five criteria​

You do not choose an interface by taste. You run the task through five criteria, and the answers point you at a surface. Hold each criterion as a question you ask about this specific task.

Analogy: this is the same reasoning a bank uses to decide how a given transaction may happen. A large wire transfer, a routine balance check, and an ATM withdrawal are not offered the same way, the bank looks at how much authority the action carries, how much room there is to get it wrong, how the result needs to be recorded, who is allowed to do it, and how often it happens, then routes each to teller, app, or ATM accordingly. You are doing the same routing for agent tasks.

CriterionAsk about the taskPoints toward CLI/scriptPoints toward MCP
AuthorityHow much damage if the agent does the wrong thing?Low stakes, read-only explorationHigh stakes, or you must guarantee no writes
AmbiguityIs the output easy to misread?Output is simple, agent can parse itOutput is complex; a typed contract stops misreads
Output structureDo you need structured data downstream?A human reads it onceAnother tool/step consumes it; typed JSON matters
AuthenticationWho holds the credentials?Env vars / local config are fineA server should hold creds; the agent never sees them
Cost & frequencyHow often does this run, and how heavy is the output?One-off, or output is smallRepeated, or raw output is huge and typed output is far leaner

Two failure modes bracket the table. Over-privileging is choosing CLI when authority or ambiguity screamed for MCP: you gave the agent Bash for a production database operation and it now can run anything against prod. Over-engineering is choosing MCP when the task was a one-off read: you spent two days building a typed server to answer a question one curl would have answered. The criteria exist to keep you off both rocks.

The rule of thumb the whole framework compresses to: CLI for exploration, MCP when the boundary earns its keep. A boundary earns its keep when the task is high-authority (you need a guarantee, not a hope), or high-frequency (you run it enough that a typed contract pays back its build cost), or high-ambiguity (the output is complex enough that a typed schema prevents real misreads). If none of those hold, a typed server is weight you do not need. Reach for CLI or a script.

The read-only observer: a capability that does not exist cannot be misused​

This is the idea that makes MCP more than "typed CLI," and it is the design pattern the lab and Deep Dive are built around. When you build an MCP server that exposes only read operations, get_health, get_readiness, get_info, get_logs, and no write operations, the agent connected to that server cannot write. Not "is not allowed to write." Cannot. There is no restart tool, no scale tool, no apply tool to call. The write capability is not denied; it is absent.

Analogy: compare two ways to stop a machine from dispensing a dangerous item. The first is a sign on the machine: "do not dispense item X", plus a guard who checks each request against the rule. That is a permission check: the capability exists, and something has to catch every attempt to use it. If the guard is distracted, or the rule is worded loosely, or someone argues the request is really item Y, the item comes out. The second is a machine that was never built with a slot for item X: no drawer, no button, no mechanism. You cannot dispense what the machine has no way to dispense; there is nothing to catch, because there is no attempt that could succeed. A deny rule is the sign and the guard. A read-only tool surface is the machine with no slot. The second is stronger because it removes the capability rather than policing it.

This is why the observer pattern is worth the build cost for high-authority, repeated operations. A deny rule that blocks kubectl delete is a good control, but it lives on top of a Bash tool that can run kubectl delete, the safety depends on the rule being complete and correctly matched (and you saw in Module 2 how many ways a deny rule can be narrower than you think). An observer server that exposes only get_pods and get_events depends on nothing, there is no delete path to get the rule wrong about. For a diagnostic tool you will run on production during incidents, that difference is the whole point: during an incident is exactly when you least want your safety to rest on a pattern-match holding.

Read-only is a property of the tool set, not a promise in the prose

A skill's SKILL.md can say "read-only, never mutates," and a good one does. But that is an instruction the agent follows, sitting on top of a Bash tool that can still mutate if the instruction is ignored or misread. An observer MCP server makes read-only a property of what tools exist at all. The prose asks nicely; the tool surface makes it structural. The lab has you feel this difference directly, you will try to make an observer write, and watch it fail not because it refused but because there was nothing to call.

Configuring and scoping MCP in Claude Code​

Concretely, an MCP server is declared in .claude/settings.json under mcpServers. Each entry names a server, says how to launch it, and passes it environment:

{
  "mcpServers": {
    "k8s-observer": {
      "command": "node",
      "args": ["./mcp-servers/k8s-observer.js"],
      "env": { "KUBECONFIG": "./platform/kubeconfigs/readonly.yaml" }
    }
  }
}

Claude Code launches the server, discovers the tools it exposes, and presents them to the agent as mcp__k8s-observer__get_pods, mcp__k8s-observer__get_events, and so on. The mcp__<server>__<tool> naming is how you refer to them in allow/deny lists. Notice the env: the server is handed a read-only kubeconfig. That is the authentication criterion made concrete: the credential lives with the server, scoped to read, and the agent never holds it. Even the connection the observer uses is least-privilege, so it could not write even if you added a write tool by mistake.

Scoping to subagents. You rarely want every part of the agent to see every server. The controls are the same allow/deny surface from Module 2, now applied to MCP tool names:

  • --allowedTools "mcp__k8s-observer__*" auto-approves every tool from the observer server, right for a diagnostic subagent whose whole job is read-only investigation.
  • --disallowedTools "mcp__*__write*" denies any write tool across all servers, a belt-and-suspenders floor even when you believe a server is read-only.
  • A diagnosis subagent gets the observer server and nothing else; a remediation subagent (if you build one) gets a separate, deliberately narrow write server, gated human-only the way Module 6's service-restart was. Different roles, different tool sets, the subagent boundary from the modules ahead, expressed in which MCP servers each role can reach.

Managed allowlists are the enterprise version of this: an organization centrally defines which MCP servers are even available to Claude Code, so an engineer cannot point the agent at an arbitrary third-party server. That is a supply-chain control, and it is the thread the Deep Dive picks up, because an MCP server is code you run, and running someone else's server is running someone else's code.

Worked comparison: HashiCorp Agent Skills vs Terraform MCP​

To see the framework decide a real case, take Terraform operations, something the Northstar team does constantly. HashiCorp ships two ways to give an agent Terraform capability, and they sit at different points on the spectrum, so the choice is a clean application of the criteria.

HashiCorp Agent Skills package Terraform procedures as Claude Code skills, the M6 pattern, authored by HashiCorp. You get guided procedures ("here is how to review a plan, here is how to structure a module") that run on top of the Terraform CLI you already have. Authority control is the skill's instructions plus your permission floor; the surface is still Bash running terraform. This gives you control and transparency: you can read exactly what the skill does, and it uses tools you already understand, at the cost of the read-only guarantee being prose, not structure.

Terraform MCP server exposes Terraform operations as typed MCP tools, a get_plan or list_resources returns typed JSON, and the server defines exactly which operations exist. This gives you the typed contract and the capability boundary: if the server exposes only read/plan tools, the agent structurally cannot apply. The cost is that you run a server (more setup, and it is code you must trust), and you have less line-by-line visibility into each operation than reading a skill's prose gives you.

CriterionHashiCorp Agent SkillsTerraform MCP server
Authority controlSkill instructions + permission floor (Bash underneath)The exposed tool set, no apply tool means no apply
OutputWhatever the CLI prints, guided by the skillTyped JSON, contract-checked
TransparencyHigh, you read the skill's stepsLower, you trust the server implementation
Setup costLow, drop in a skillHigher, run and trust a server
Best whenYou want control, visibility, and CLI you already trustYou need a hard read-only boundary or typed output for a repeated prod op

Run it through the framework: for an engineer exploring Terraform interactively, low authority, one-off, the skill wins on control and zero server overhead. For an agent that runs terraform plan review on every PR in CI against production state, high frequency, high authority, the MCP server's structural read-only boundary earns its keep. Same tool, opposite answers, decided by the criteria rather than by preference. That is the entire skill this module teaches: the interface is a decision, and you now have the criteria to make it.

What you'll do in the lab​

You will run the Three-Way Tool Shootout: the same diagnostic ticket, orders-api readyz is failing, investigate, solved three ways against the running Northstar platform.

  1. Filtered CLI: hand the agent Bash with curl, grep, jq and let it diagnose. Capture correctness, tokens, latency, and how many tool attempts it took.
  2. Skill with wrappers: use the service-health skill you built in M6, which wraps the probes in a bounded procedure. Capture the same metrics.
  3. Read-only MCP observer: run a minimal MCP server that exposes exactly three typed tools (get_health, get_readiness, get_info) and no write tool, point the agent at it, and diagnose. Capture the same metrics, and then try to make it write, and watch it fail because there is nothing to call.

You will record all three runs in an Agent Run Ledger and fill a comparison table, correctness, evidence quality, tokens, latency, tool attempts, least privilege, then write the verdict: when each interface wins. grade.sh m7 confirms the observer exists, is genuinely read-only (no write tool in its manifest), and that the ledger captured all three runs. The Deep Dive then presses on the observer's threat model: why the write attempt fails at the protocol level, not the permission level, and adds ToolHive runtime isolation as optional hardening for when the server itself is code you did not write.
