Lab — Assemble the Specialist Team

The lesson drew the shift from one generalist to a team of specialists, each a Role Bundle: a system prompt, a tool set, a right-sized model, a turn budget, and a structured handoff — with the Module 8 enforcement layer underneath making the boundaries hold. This lab assembles that team and proves each boundary. You will read the four shipped roles as bundles, build the two missing ones, run the authority regression that asserts each read-only role cannot write and each authoring role can, validate a structured handoff and watch an unsourced one get rejected as contamination, and let the grader certify the whole team.

By the end you will have six specialist roles you can point a security reviewer at — not "we told the SRE not to edit," but "the SRE's bundle carries no write tool, here is the test that fails the build if that ever changes."

Where you are working

You start at the root of the agentic-ops-lab workspace. The four base agent files (sre-investigator, iac-engineer, platform-engineer, security-reviewer), the authority-regression script (scripts/role-authority-check.sh), and the handoff validator (scripts/evidence-validate.sh) ship in the repo — this lab is about understanding, completing, and proving the team, the same way Module 8 shipped the Change Gate and had you wire and test it. You do not need a live cluster; the authority checks operate on the agent files' declared tool sets and the handoff packets' contents, so they run anywhere.

Step 0 — Prerequisites​

Confirm your tools. The authority check and handoff validator use jq; the model-rationale check uses python3 with pyyaml.

claude --version
jq --version
python3 -c "import yaml; print('pyyaml', yaml.__version__)"
Expected output
2.1.197 (Claude Code)
jq-1.7.1
pyyaml 6.0.2

Your versions will differ. All three must resolve. If pyyaml is missing, pip3 install pyyaml.

Step 1 — See who is on the team, and who is missing​

Four of the six roles ship in the repo. Two — the FinOps analyst and the change-reviewer — are yours to build. List the agents directory:

ls .claude/agents/
Expected output
change-reviewer.md   finops-analyst.md    iac-engineer.md
platform-engineer.md security-reviewer.md sre-investigator.md

If you are starting from the base spine you will see only the four shipped roles — sre-investigator.md, iac-engineer.md, platform-engineer.md, security-reviewer.md. This lab has you add finops-analyst.md and change-reviewer.md; the listing above is the completed team you are working toward.

Step 2 — Read a role as a Role Bundle​

Before you build anything, read the SRE investigator the way the lesson framed it — not as a prompt, but as a bundle. Read its frontmatter and body:

cat .claude/agents/sre-investigator.md
Expected output (excerpt)
---
name: sre-investigator
description: Investigates Northstar incidents — reads health endpoints, logs, metrics, Kubernetes state, and events; forms an evidence-backed hypothesis. Read-only. Never modifies deployments, applies, or deletes. Hand off structured evidence for someone else to act on.
model: sonnet
tools: ["Read", "Grep", "Glob", "Bash"]
disallowedTools: ["Edit", "Write", "MultiEdit", "NotebookEdit"]
---

You are the **SRE Investigator** for Northstar Commerce. Your job is to find out
*what is wrong*, not to fix it.

Read it as five bundle parts: the model (sonnet — balanced reasoning under a budget), the tool set (Read/Grep/Glob/Bash and no write tool — plus an explicit disallowedTools belt-and-suspenders), the turn budget and handoff schema in the body, and the identity in the description. The tool set is the load-bearing line: this role is read-only because Edit/Write are absent, not because the prose asks it to behave.

Notice the two-layer boundary in the frontmatter. tools: lists what the role carries — no write tool. disallowedTools: also names the write tools explicitly. The tools allow-list is the real boundary; disallowedTools is a redundant, legible statement of intent that also survives if the allow-list is ever loosened. Belt and suspenders, exactly like fail-closed.

Step 3 — Build the FinOps analyst (haiku, read-only)​

The FinOps analyst reads Terraform plan fixtures and prices them against a budget, flagging any instance change over 2x. It is the model right-sizing case from the lesson: a bounded, mechanical task that runs on haiku on purpose. Create its bundle:

cat > .claude/agents/finops-analyst.md <<'EOF'
---
name: finops-analyst
description: Analyzes Northstar infrastructure cost — reads Terraform plan fixtures and environment configs, compares instance/storage sizing against budget thresholds, flags changes over 2x current size. Read-only. NEVER modifies infrastructure or runs terraform apply.
model: haiku
tools: ["Read", "Grep", "Glob", "Bash"]
disallowedTools: ["Edit", "Write", "MultiEdit", "NotebookEdit"]
---

You are the **FinOps Analyst** for Northstar Commerce. You read plans and price them. You change nothing.

## Authority

- **READ** `infra/fixtures/` (plan fixtures) and `infra/environments/`. Allowed.
- **ANALYZE** cost: compare proposed instance sizes and storage tiers against the current baseline and the budget threshold. Flag any instance change **> 2x** current size.
- **NEVER** edit files, and **NEVER** run `terraform apply` — you have no Edit/Write tool and applying is not your role. You produce a number and a flag, not a change.
- You may **APPROVE** instance-size and storage-tier changes as a verdict.

You run at **model: haiku** deliberately — reading a plan fixture and comparing numbers against a threshold is a bounded, mechanical task. Spending Opus on it would be paying for judgment the task does not need. Right-sizing the *model* to the role is itself a FinOps decision.

## Turn budget

Analyze in at most **6 turns** — this is a fast, narrow task.

## Handoff

The from_role/to_role/cost/flags/verdict/sources packet the change-reviewer consumes:
{ "from_role": "finops-analyst", "to_role": "change-reviewer", "cost": {...}, "flags": [...], "verdict": "block | approve", "sources": ["infra/fixtures/expensive-plan.json"] }
EOF
echo "finops-analyst created"
Expected output
finops-analyst created

The bundle encodes every lesson point: model: haiku (right-sized to a mechanical task), no write tool (read-only by capability), a 6-turn budget (fast and narrow), and a handoff packet whose sources field carries provenance. If the file already shipped in your workspace, this cat > overwrites it with equivalent content — the grader checks contents, not history. Your shipped copy may render the handoff as a fenced JSON block; either form satisfies the grader.

Step 4 — Build the change-reviewer (opus, read-only, independent)​

The change-reviewer is the last gate before production. It reads diffs, git log, and the authority matrix; it gives an independent verdict; and it never touches the candidate — the moment a reviewer edits what it reviews, the independence that makes the review worth anything is gone. It runs on opus because a missed problem here reaches customers. Create it:

cat > .claude/agents/change-reviewer.md <<'EOF'
---
name: change-reviewer
description: Reviews Northstar changes before production — reads diffs, git log, and the authority matrix; verifies blast radius, rollback viability, and authority-matrix compliance. Read-only, independent verdict. NEVER makes changes itself; the reviewer that edits the candidate has stopped being a reviewer.
model: opus
tools: ["Read", "Grep", "Glob", "Bash"]
disallowedTools: ["Edit", "Write", "MultiEdit", "NotebookEdit"]
---

You are the **Change Reviewer** for Northstar Commerce. You give an independent verdict on a proposed change. You do not touch the candidate.

## Authority

- **READ** everything — you need full context to judge a change.
- **EXECUTE** `git diff`, `git log` (read-only). Allowed.
- **NEVER** edit, write, or modify the candidate branch — you have no Edit/Write tool. The moment a reviewer edits the thing under review, there is no longer an independent review; there is one author with two hats. Your independence *is* the control.
- **APPROVE** production deployments, infrastructure changes, security changes — as a recorded verdict.

Before approving, verify: (1) the change matches its stated intent, (2) blast radius is acceptable, (3) a rollback plan exists, (4) no secrets in the diff, (5) the proposing role was allowed to make this change per authority-matrix.yaml.

You run at **model: opus** — the reviewer is the last gate before production, where a missed problem is most expensive.

## Turn budget

Review in at most **10 turns**, then produce the verdict.

## Handoff

The from_role/to_role/verdict/checks/sources packet the ops-lead consumes:
{ "from_role": "change-reviewer", "to_role": "ops-lead", "verdict": "approve | block | approve-with-conditions", "checks": {...}, "sources": ["git diff", "authority-matrix.yaml"] }
EOF
echo "change-reviewer created"
Expected output
change-reviewer created

The independence rule is the whole point: the reviewer has Read/Bash but no write tool, so it cannot edit the candidate — its verdict is trustworthy precisely because it had no way to author the thing it is judging. opus because this is the highest-stakes judgment on the team.

Step 5 — Run the authority regression: the forbidden-action matrix​

Now prove the boundaries. role-authority-check.sh reads a role's declared tool set and answers one question with a fixed rule and no model in the loop: is this role structurally capable of a write? Start with the SRE investigator — it must be blocked:

scripts/role-authority-check.sh sre-investigator write
echo "exit=$?"
Expected output
BLOCKED: role 'sre-investigator' has NO write tool in its bundle — it is structurally incapable of Edit/Write. Authority boundary holds.
exit=3

Exit 3 — blocked. Not "the SRE chose not to write." The SRE cannot write, because no write tool is in its bundle. This is the same shift as the Change Gate: a boundary you can test, not a behavior you hope for.

Now the inverse — the IaC engineer must be capable of writing, because authoring HCL is genuinely its job:

scripts/role-authority-check.sh iac-engineer write
echo "exit=$?"
Expected output
CAPABLE: role 'iac-engineer' carries write tool 'edit' — write is within its authority.
exit=0

Exit 0 — capable. An authority test is not "block everything"; it is "each role can do exactly what its job requires and no more." The IaC engineer writes; the SRE does not. Run the whole matrix at once:

for r in sre-investigator iac-engineer platform-engineer security-reviewer finops-analyst change-reviewer; do
  scripts/role-authority-check.sh "$r" write >/dev/null 2>&1
  case $? in 0) v="CAPABLE (exit 0)";; 3) v="BLOCKED (exit 3)";; *) v="exit $?";; esac
  printf '%-20s write -> %s\n' "$r" "$v"
done
Expected output
sre-investigator     write -> BLOCKED (exit 3)
iac-engineer         write -> CAPABLE (exit 0)
platform-engineer    write -> CAPABLE (exit 0)
security-reviewer    write -> BLOCKED (exit 3)
finops-analyst       write -> BLOCKED (exit 3)
change-reviewer      write -> BLOCKED (exit 3)

The full forbidden-action matrix in one pass: four read-only roles blocked (SRE, security-reviewer, FinOps, change-reviewer) and two authoring roles capable (IaC, platform). Every one of those verdicts is a fact about the bundle's declared tools, not a judgment. This is the table you put in CI.

Step 6 — Confirm the check fails closed​

The most important property of any safety check is what it does when it cannot decide. Ask it about a role that does not exist:

scripts/role-authority-check.sh nonesuch write
echo "exit=$?"
Expected output
role-authority-check: FAIL-CLOSED: no agent file for role 'nonesuch' at /path/to/agentic-ops-lab/.claude/agents/nonesuch.md
exit=1

Exit 1 — fail-closed. The check did not guess a capability for a role it could not find; it blocked. An authority check that returned "capable" (or even "blocked") for an unknown role would be reasoning about a role that does not exist. "I cannot evaluate this" and "deny" are the same outcome, exactly as in Module 8.

Step 7 — Validate a structured handoff​

A role's output is only useful if the next role can act on it without re-investigating. evidence-validate.sh enforces the handoff schema: the packet must be structurally complete and every claim must have provenance. Send it a well-formed, sourced evidence packet:

printf '{"from_role":"sre-investigator","to_role":"change-reviewer","evidence":{"service":"orders-api","status":"degraded","checks":{"healthz":true,"readyz":false},"hypothesis":"readiness probe points at the wrong inventory path","confidence":"high","sources":["curl /readyz","app/orders-api/src/health.py:25"]},"recommendations":["fix the readiness path"],"out_of_scope":["did not check the database"]}' \
  | scripts/evidence-validate.sh
echo "exit=$?"
Expected output
VALID: evidence packet from 'sre-investigator' -> 'change-reviewer'; hypothesis backed by 2 source(s), out_of_scope declared.
exit=0

Valid — the packet is complete and its hypothesis is backed by two sources. The next role can act on this without redoing the investigation, because every claim is traceable.

Now the contamination case — a confident hypothesis with no sources. This is the dangerous shape: an assertion dressed as evidence.

printf '{"from_role":"sre-investigator","to_role":"change-reviewer","evidence":{"service":"orders-api","status":"down","checks":{},"hypothesis":"it is definitely the database","confidence":"high","sources":[]},"recommendations":[],"out_of_scope":[]}' \
  | scripts/evidence-validate.sh
echo "exit=$?"
Expected output
INVALID: packet failed structure/provenance check — a confident claim with no sources, or a missing required field, is contamination, not evidence.
exit=4

Exit 4 — rejected. The hypothesis is confident ("definitely the database") but sources is empty, so the validator refuses it. This is the contamination control from the lesson made runnable: a claim with no provenance does not propagate to the next role. High confidence with zero sources is exactly the pattern that poisons a downstream handoff.

Confirm it fails closed on empty input, too:

printf '' | scripts/evidence-validate.sh
echo "exit=$?"
Expected output
evidence-validate: FAIL-CLOSED: empty input
exit=1

Exit 1 — an empty packet is not a valid empty handoff; it is nothing to validate, so it blocks.

Step 8 — Confirm the model right-sizing​

The model field is a per-role decision, not a global default. Verify the two ends of the spectrum — FinOps on the cheapest model, the two reviewers on the strongest:

for r in finops-analyst sre-investigator security-reviewer change-reviewer; do
  m=$(awk -F': ' '/^model:/{print $2; exit}' ".claude/agents/$r.md")
  printf '%-20s model=%s\n' "$r" "$m"
done
Expected output
finops-analyst       model=haiku
sre-investigator     model=sonnet
security-reviewer    model=opus
change-reviewer      model=opus

Read the reasoning off the table: FinOps runs haiku because pricing a plan is mechanical; the SRE runs sonnet for balanced reasoning under a budget; the security-reviewer and change-reviewer run opus because a missed subtlety in a review is the most expensive failure on the team — and both are read-only, so the spend buys judgment with zero blast-radius cost. Effort is a role decision.

Step 9 — Let the repository certify the team​

Run the module grader. It drives the full authority-and-handoff matrix — presence of all six bundles, tools + model on each, the read-only/authoring write split, model right-sizing, turn budgets, handoff schemas, and the evidence validator's accept/reject/fail-closed behavior.

./scripts/grade.sh m9
Expected output
Grading: Module m9
========================

Checking: The Specialist Team — role bundles, structured handoffs, and authority boundaries

  ✓ all six role agent files exist under .claude/agents/ with name + description frontmatter
  ✓ every role bundle declares both a tools list and a model (the two levers of a Role Bundle)
  ✓ the four read-only roles (sre, security-reviewer, finops, change-reviewer) declare NO write tool — the authority boundary is structural, not a promise
  ✓ the two authoring roles (iac-engineer, platform-engineer) DO carry a write tool — write is inside their authority
  ✓ FAIL-CLOSED: the authority check blocks (exit 1) on an unknown role rather than guessing capability
  ✓ model selection is right-sized per role: finops runs haiku (cheap/mechanical), security-reviewer and change-reviewer run opus (most expensive miss)
  ✓ every role file declares a turn budget — a runaway agent has no natural stopping point unless you give it one
  ✓ every role file declares a structured handoff (a JSON packet), so downstream roles act on structure, not prose
  ✓ a well-formed evidence packet with sources and out_of_scope validates (exit 0)
  ✓ a confident hypothesis with NO sources is rejected as contamination (exit 4) — provenance is required
  ✓ FAIL-CLOSED: the evidence validator blocks (exit 1) on empty input rather than passing an empty packet
  ✓ no role's agent file grants a write tool the authority-matrix does not: the tool grant is the tighter boundary (security-reviewer intentionally drops even the matrix's write path)

========================
RESULT: PASS (12 passed)

Twelve green. The grader ran the same authority regression you ran by hand — the write matrix, the fail-closed case, the handoff accept/reject — plus the presence, model, turn-budget, and schema checks across all six bundles. This is the payoff of authority-as-code: the team's boundaries are tested, not asserted.

Step 10 — Teardown​

The six agent files, the authority-regression script, and the handoff validator are module deliverables — leave them; the Deep Dive runs its full regression matrix against them. There is nothing ephemeral to clean up: the checks operate on files, not on a running cluster, so no services were started.

git status --short .claude/agents/
Expected output
 M .claude/agents/change-reviewer.md
 M .claude/agents/finops-analyst.md

If you built the two missing roles in a base workspace, git status shows them as added or modified. Leave them in place — they are now part of the workspace's specialist team, exactly as you would want in real work. If your workspace already shipped all six, the tree may be clean.

You assembled a team of six specialist roles, each a Role Bundle with a right-sized model, a bounded turn budget, and a structured handoff. You proved the authority boundaries hold with a deterministic regression: four roles structurally cannot write, two can, and the check fails closed on the unknown. You validated that a sourced handoff passes and an unsourced one is rejected as contamination. None of this depends on a role choosing to behave — which is the entire point. The Deep Dive now turns the authority regression into a full CI-grade matrix and shows the one boundary the tool-set check cannot see, and what you layer under it.
