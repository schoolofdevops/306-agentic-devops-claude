Lab — Assemble the Team

The lesson drew the shift from one generalist to a team of specialists, each a Role Bundle: a system prompt, a tool set, a right-sized model, a turn budget, and a structured handoff — with the Module 8 enforcement layer underneath making the boundaries hold. This lab assembles that team and proves each boundary. You will read the four shipped roles as bundles, build the two missing ones, run the authority regression that asserts each read-only role cannot write and each authoring role can, validate a structured handoff and watch an unsourced one get rejected as contamination, and let the grader certify the whole team.

By the end you will have six specialist roles you can point a security reviewer at — not "we told the SRE not to edit," but "the SRE's bundle carries no write tool, here is the test that fails the build if that ever changes."

Where you are working

You start at the root of the agentic-ops-lab workspace. Every command below — and every claude session — runs from there:

cd ~/agentic-ops-lab

The four base agent files (sre-investigator, iac-engineer, platform-engineer, security-reviewer), the authority-regression script (scripts/role-authority-check.sh), and the handoff validator (scripts/evidence-validate.sh) ship in the repo — this lab is about understanding, completing, and proving the team, the same way Module 8 shipped the Change Gate and had you wire and test it. You do not need a live cluster; the authority checks operate on the agent files' declared tool sets and the handoff packets' contents, so they run anywhere.

Step 0 — Prerequisites​

Confirm your tools. The authority check and handoff validator use jq; the model-rationale check uses python3 with pyyaml.

claude --version
jq --version
python3 -c "import yaml; print('pyyaml', yaml.__version__)"
Expected output
2.1.197 (Claude Code)
jq-1.7.1
pyyaml 6.0.2

Your versions will differ. All three must resolve. If pyyaml is missing, pip3 install pyyaml.

Step 1 — See who is on the team, and who is missing​

Four of the six roles ship in the repo. Two — the FinOps analyst and the change-reviewer — are yours to build. List the agents directory:

ls .claude/agents/
Expected output
change-reviewer.md   finops-analyst.md    iac-engineer.md
platform-engineer.md security-reviewer.md sre-investigator.md

All seven role files ship with this workspace, because later modules depend on them — Module 11's review chain dispatches the FinOps analyst, and Module 19's capstone routes through the change-reviewer. So this lab does not build the team from nothing. In Step 3 you take two of them away from yourself and rebuild them from a specification, which is a harder exercise than transcribing and a much better test of whether you can read a bundle.

Step 2 — Read a role as a Role Bundle​

Before you build anything, read the SRE investigator the way the lesson framed it — not as a prompt, but as a bundle. Read its frontmatter and body:

cat .claude/agents/sre-investigator.md
Expected output (excerpt)
---
name: sre-investigator
description: Investigates Northstar incidents — reads health endpoints, logs, metrics, Kubernetes state, and events; forms an evidence-backed hypothesis. Read-only. Never modifies deployments, applies, or deletes. Hand off structured evidence for someone else to act on.
model: sonnet
tools: ["Read", "Grep", "Glob", "Bash"]
disallowedTools: ["Edit", "Write", "MultiEdit", "NotebookEdit"]
---

You are the **SRE Investigator** for Northstar Commerce. Your job is to find out
*what is wrong*, not to fix it.

Read it as five bundle parts: the model (sonnet — balanced reasoning under a budget), the tool set (Read/Grep/Glob/Bash and no write tool — plus an explicit disallowedTools belt-and-suspenders), the turn budget and handoff schema in the body, and the identity in the description. The tool set is the load-bearing line: this role is read-only because Edit/Write are absent, not because the plain text asks it to behave.

Notice the two-layer boundary in the frontmatter. tools: lists what the role carries — no write tool. disallowedTools: also names the write tools explicitly. The tools allow-list is the real boundary; disallowedTools is a redundant, legible statement of intent that also survives if the allow-list is ever loosened. Belt and suspenders, exactly like fail-closed.

Step 3 — Take two roles away, then rebuild them​

Set the two you are about to author aside and confirm the grader notices:

mkdir -p /tmp/m9-reference
cp .claude/agents/finops-analyst.md .claude/agents/change-reviewer.md /tmp/m9-reference/
rm .claude/agents/finops-analyst.md .claude/agents/change-reviewer.md
./scripts/grade.sh m9
Expected output
  ✗ all six role agent files exist under .claude/agents/ with name + description frontmatter
  ✗ every role bundle declares both a tools list and a model (the two levers of a Role Bundle)
  ✗ the four read-only roles declare NO write tool — the authority boundary is structural, not a promise
  ✗ model selection is right-sized per role: finops runs haiku, security-reviewer and change-reviewer run opus
  ✗ every role file declares a turn budget
  ✗ every role file declares a structured handoff (a JSON packet)
  ✗ no role's agent file grants a write tool the authority-matrix does not

RESULT: FAIL (5 passed, 7 failed)

Seven red, and read what they are: every one names a property from the lesson — the tool bundle, the model right-sizing, the turn budget, the structured handoff, the authority boundary. That list is your specification. You do not need the original files; you need to satisfy those seven statements.

Now author the FinOps analyst. It reads Terraform plan JSON and prices it against a budget, flagging any instance change over 2x — the model right-sizing case from the lesson, a bounded mechanical task that runs on haiku on purpose.

Open a session and hand it the specification rather than the answer:

Write .claude/agents/finops-analyst.md.

It analyzes Northstar infrastructure cost: reads Terraform plan JSON and environment
configs, compares instance and storage sizing against budget thresholds, flags any
change over 2x current size. It produces a number and a verdict, never a change.

Match the house pattern in .claude/agents/sre-investigator.md. It must satisfy every
check in labs/m9/checks.json — read that file and hold yourself to it.

Choose the model deliberately and tell me why before you write it.

What you observe. The model choice is the one to argue about. If it reaches for opus or sonnet, push back: this role compares numbers against a threshold. Paying for the deepest judgment on a mechanical task is the FinOps failure the role itself exists to catch, which is the joke the lesson is making.

The reference bundle, once you have written yours
cat > .claude/agents/finops-analyst.md <<'EOF'
---
name: finops-analyst
description: Analyzes Northstar infrastructure cost — reads Terraform plan fixtures and environment configs, compares instance/storage sizing against budget thresholds, flags changes over 2x current size. Read-only. NEVER modifies infrastructure or runs terraform apply.
model: haiku
tools: ["Read", "Grep", "Glob", "Bash"]
disallowedTools: ["Edit", "Write", "MultiEdit", "NotebookEdit"]
---

You are the **FinOps Analyst** for Northstar Commerce. You read plans and price them. You change nothing.

## Authority

- **READ** `infra/fixtures/` (plan fixtures) and `infra/environments/`. Allowed.
- **ANALYZE** cost: compare proposed instance sizes and storage tiers against the current baseline and the budget threshold. Flag any instance change **> 2x** current size.
- **NEVER** edit files, and **NEVER** run `terraform apply` — you have no Edit/Write tool and applying is not your role. You produce a number and a flag, not a change.
- You may **APPROVE** instance-size and storage-tier changes as a verdict.

You run at **model: haiku** deliberately — reading a plan fixture and comparing numbers against a threshold is a bounded, mechanical task. Spending Opus on it would be paying for judgment the task does not need. Right-sizing the *model* to the role is itself a FinOps decision.

## Turn budget

Analyze in at most **6 turns** — this is a fast, narrow task.

## Handoff

The from_role/to_role/cost/flags/verdict/sources packet the change-reviewer consumes:
{ "from_role": "finops-analyst", "to_role": "change-reviewer", "cost": {...}, "flags": [...], "verdict": "block | approve", "sources": ["infra/fixtures/plan-oversize.json"] }
EOF
echo "finops-analyst created"
Expected output
finops-analyst created

The bundle encodes every lesson point: model: haiku (right-sized to a mechanical task), no write tool (read-only by capability), a 6-turn budget (fast and narrow), and a handoff packet whose sources field carries provenance. The grader checks contents, not history, so a bundle that satisfies the spec passes whether you typed it or generated it. Your reference copy may render the handoff as a fenced JSON block; either form is fine.

Diff yours against it — the differences are the interesting part, not the failures:

diff /tmp/m9-reference/finops-analyst.md .claude/agents/finops-analyst.md

Step 4 — Author the change-reviewer (opus, read-only, independent)​

The change-reviewer is the last gate before production. It reads diffs, git log, and the authority matrix; it gives an independent verdict; and it never touches the candidate — the moment a reviewer edits what it reviews, the independence that makes the review worth anything is gone. It runs on opus because a missed problem here reaches customers.

Author it the same way — specification, not transcription:

Write .claude/agents/change-reviewer.md.

It is the last gate before production: reads diffs, git log and the authority
matrix, and verifies blast radius, rollback viability and authority-matrix
compliance. Read-only, independent verdict, and it must NEVER edit the candidate
it is reviewing.

Same house pattern, same checks.json. Note the model choice differs from the
FinOps analyst — tell me why before you write it.

What you observe. Ask it to justify opus here after arguing for haiku in Step 3. The two answers together are the lesson: right-sizing is not "use the cheap one", it is matching spend to the cost of a miss. A wrong number in a cost report is embarrassing; a missed blast radius reaches customers.

The reference bundle
cat > .claude/agents/change-reviewer.md <<'EOF'
---
name: change-reviewer
description: Reviews Northstar changes before production — reads diffs, git log, and the authority matrix; verifies blast radius, rollback viability, and authority-matrix compliance. Read-only, independent verdict. NEVER makes changes itself; the reviewer that edits the candidate has stopped being a reviewer.
model: opus
tools: ["Read", "Grep", "Glob", "Bash"]
disallowedTools: ["Edit", "Write", "MultiEdit", "NotebookEdit"]
---

You are the **Change Reviewer** for Northstar Commerce. You give an independent verdict on a proposed change. You do not touch the candidate.

## Authority

- **READ** everything — you need full context to judge a change.
- **EXECUTE** `git diff`, `git log` (read-only). Allowed.
- **NEVER** edit, write, or modify the candidate branch — you have no Edit/Write tool. The moment a reviewer edits the thing under review, there is no longer an independent review; there is one author with two hats. Your independence *is* the control.
- **APPROVE** production deployments, infrastructure changes, security changes — as a recorded verdict.

Before approving, verify: (1) the change matches its stated intent, (2) blast radius is acceptable, (3) a rollback plan exists, (4) no secrets in the diff, (5) the proposing role was allowed to make this change per authority-matrix.yaml.

You run at **model: opus** — the reviewer is the last gate before production, where a missed problem is most expensive.

## Turn budget

Review in at most **10 turns**, then produce the verdict.

## Handoff

The from_role/to_role/verdict/checks/sources packet the ops-lead consumes:
{ "from_role": "change-reviewer", "to_role": "ops-lead", "verdict": "approve | block | approve-with-conditions", "checks": {...}, "sources": ["git diff", "authority-matrix.yaml"] }
EOF
echo "change-reviewer created"
Expected output
change-reviewer created

The independence rule is the whole point: the reviewer has Read/Bash but no write tool, so it cannot edit the candidate — its verdict is trustworthy precisely because it had no way to author the thing it is judging. opus because this is the highest-stakes judgment on the team.

Step 5 — Run the authority regression: the forbidden-action matrix​

Now prove the boundaries. role-authority-check.sh reads a role's declared tool set and answers one question with a fixed rule and no model in the loop: is this role structurally capable of a write? Start with the SRE investigator — it must be blocked:

scripts/role-authority-check.sh sre-investigator write
echo "exit=$?"
Expected output
BLOCKED: role 'sre-investigator' has NO write tool in its bundle — it is structurally incapable of Edit/Write. Authority boundary holds.
exit=3

Exit 3 — blocked. Not "the SRE chose not to write." The SRE cannot write, because no write tool is in its bundle. This is the same shift as the Change Gate: a boundary you can test, not a behavior you hope for.

Now the inverse — the IaC engineer must be capable of writing, because authoring HCL is genuinely its job:

scripts/role-authority-check.sh iac-engineer write
echo "exit=$?"
Expected output
CAPABLE: role 'iac-engineer' carries write tool 'edit' — write is within its authority.
exit=0

Exit 0 — capable. An authority test is not "block everything"; it is "each role can do exactly what its job requires and no more." The IaC engineer writes; the SRE does not. Run the whole matrix at once:

for r in sre-investigator iac-engineer platform-engineer security-reviewer finops-analyst change-reviewer; do
  scripts/role-authority-check.sh "$r" write >/dev/null 2>&1
  case $? in 0) v="CAPABLE (exit 0)";; 3) v="BLOCKED (exit 3)";; *) v="exit $?";; esac
  printf '%-20s write -> %s\n' "$r" "$v"
done
Expected output
sre-investigator     write -> BLOCKED (exit 3)
iac-engineer         write -> CAPABLE (exit 0)
platform-engineer    write -> CAPABLE (exit 0)
security-reviewer    write -> BLOCKED (exit 3)
finops-analyst       write -> BLOCKED (exit 3)
change-reviewer      write -> BLOCKED (exit 3)

The full forbidden-action matrix in one pass: four read-only roles blocked (SRE, security-reviewer, FinOps, change-reviewer) and two authoring roles capable (IaC, platform). Every one of those verdicts is a fact about the bundle's declared tools, not a judgment. This is the table you put in CI.

Step 6 — Confirm the check fails closed​

The most important property of any safety check is what it does when it cannot decide. Ask it about a role that does not exist:

scripts/role-authority-check.sh nonesuch write
echo "exit=$?"
Expected output
role-authority-check: FAIL-CLOSED: no agent file for role 'nonesuch' at /path/to/agentic-ops-lab/.claude/agents/nonesuch.md
exit=1

Exit 1 — fail-closed. The check did not guess a capability for a role it could not find; it blocked. An authority check that returned "capable" (or even "blocked") for an unknown role would be reasoning about a role that does not exist. "I cannot evaluate this" and "deny" are the same outcome, exactly as in Module 8.

Step 7 — Run a real handoff between two roles​

A role's output is only useful if the next role can act on it without re-investigating. So far you have read role files. Now run the chain and watch a packet cross between two identities.

Bring up the incident if it is not already running:

docker compose --profile core up -d
scripts/inject.sh readiness-drift

In a session, dispatch the investigator and have the Ops Lead persist what comes back:

claude --permission-mode acceptEdits
orders-api is degraded. Dispatch the sre-investigator subagent to investigate,
then write its findings to agentops/handoff.json as an evidence packet matching
the schema scripts/evidence-validate.sh enforces — read that script first to get
the fields right. The packet goes from sre-investigator to change-reviewer.

Do not fix anything.

What Claude does. It reads the validator to learn the contract, dispatches sre-investigator, and writes the packet. Note who writes it: the investigator is read-only (write: [] in the authority matrix), so the Ops Lead persists the finding. The worker produces, the orchestrator records.

What you observe. Look at the packet, and specifically at the two fields that make a handoff trustworthy:

jq '{from_role, to_role, hypothesis: .evidence.hypothesis, sources: (.evidence.sources | length), out_of_scope: (.out_of_scope | length)}' agentops/handoff.json
jq -r '.evidence.sources[0:3][]' agentops/handoff.json
Expected output
{
  "from_role": "sre-investigator",
  "to_role": "change-reviewer",
  "hypothesis": "orders-api's readiness check is misconfigured against inventory-api: an injected INVENTORY_API_URL env var appends '/v2' and the readyz handler queries '/health' instead of '/healthz', so it hits the non-existent http://inventory-api:8081/v2/health (404) even though inventory-api itself is fully healthy.",
  "sources": 9,
  "out_of_scope": 6
}
curl -sv http://localhost:8080/healthz -> 200 {"status":"ok"}
curl -sv http://localhost:8080/readyz -> 200 {"status":"not ready","checks":{"inventory_api":false}}
curl -sv http://localhost:8081/healthz -> 200 {"status":"ok"}

Yours will differ. Two things to read carefully.

sources are commands with their actual output, not descriptions of commands. Anyone can re-run line one and see the same 200. That is what makes the packet checkable rather than merely detailed.

out_of_scope has six entries — and this is the field engineers skip when they design handoffs. Read them:

jq -r '.out_of_scope[]' agentops/handoff.json

On the captured run they included "docker exec was blocked by sandbox permissions" and "did not take any corrective action — purely read-only investigation per role authority". The investigator declared the limits of its own authority as part of its finding. That is what stops the next role assuming coverage that never happened — the failure where a reviewer approves a change because "SRE looked at it", not knowing SRE never checked the database.

Validate it:

jq -c . agentops/handoff.json | scripts/evidence-validate.sh; echo "exit=$?"
Expected output
VALID: evidence packet from 'sre-investigator' -> 'change-reviewer'; hypothesis backed by 9 source(s), out_of_scope declared.
exit=0

Structurally complete, every claim traceable, scope declared. change-reviewer can now act on this without redoing the investigation — which is the entire economic argument for roles. Without the handoff contract, the second role re-derives what the first already knew, and you pay twice for one investigation.

Step 8 — The contamination case​

The validator earns its place on the packets it rejects. Send it the dangerous shape by hand — a confident hypothesis with no provenance:

Now the contamination case — a confident hypothesis with no sources. This is the dangerous case: an assertion dressed as evidence.

printf '{"from_role":"sre-investigator","to_role":"change-reviewer","evidence":{"service":"orders-api","status":"down","checks":{},"hypothesis":"it is definitely the database","confidence":"high","sources":[]},"recommendations":[],"out_of_scope":[]}' \
  | scripts/evidence-validate.sh
echo "exit=$?"
Expected output
INVALID: packet failed structure/provenance check — a confident claim with no sources, or a missing required field, is contamination, not evidence.
exit=4

Exit 4 — rejected. The hypothesis is confident ("definitely the database") but sources is empty, so the validator refuses it. This is the contamination control from the lesson made runnable: a claim with no provenance does not propagate to the next role. High confidence with zero sources is exactly the pattern that poisons a downstream handoff.

Confirm it fails closed on empty input, too:

printf '' | scripts/evidence-validate.sh
echo "exit=$?"
Expected output
evidence-validate: FAIL-CLOSED: empty input
exit=1

Exit 1 — an empty packet is not a valid empty handoff; it is nothing to validate, so it blocks.

Step 9 — Confirm the model right-sizing​

The model field is a per-role decision, not a global default. Verify the two ends of the spectrum — FinOps on the cheapest model, the two reviewers on the strongest:

for r in finops-analyst sre-investigator security-reviewer change-reviewer; do
  m=$(awk -F': ' '/^model:/{print $2; exit}' ".claude/agents/$r.md")
  printf '%-20s model=%s\n' "$r" "$m"
done
Expected output
finops-analyst       model=haiku
sre-investigator     model=sonnet
security-reviewer    model=opus
change-reviewer      model=opus

Read the reasoning off the table: FinOps runs haiku because pricing a plan is mechanical; the SRE runs sonnet for balanced reasoning under a budget; the security-reviewer and change-reviewer run opus because a missed subtlety in a review is the most expensive failure on the team — and both are read-only, so the spend buys judgment with zero blast-radius cost. Effort is a role decision.

Step 10 — Diff your rebuilt roles against the references​

You set finops-analyst and change-reviewer aside in Step 3 and rebuilt them from specifications. The originals are still in /tmp/m9-reference/. Compare them, because everything else in .claude/agents/ shipped with the workspace — this comparison is the only part of today that is yours.

diff -u /tmp/m9-reference/change-reviewer.md .claude/agents/change-reviewer.md

What you observe. Look past wording at the three things that carry authority: does your tools list actually exclude every write tool, or did you leave one in? Does your model line match the risk (opus for the last gate before production)? Does it declare a turn budget and a structured handoff, or does it trail off after the role description?

Record the comparison while it is fresh:

Write agentops/rebuild-notes-roles.md.

I rebuilt finops-analyst and change-reviewer from specifications and diffed them
against the references in /tmp/m9-reference/. For each, record:
  - what my version got right
  - what the reference had that mine was missing, and what would go wrong without it
  - one thing my version does better

Be specific about tools, model, turn budget and the handoff packet. Keep it short.

What you observe. The gap between "I can describe a role" and "I can specify one an authority regression will accept." A missing disallowedTools line reads like a formatting difference and is actually the whole boundary.

Step 11b — What roles do not give you, and what to build on Monday​

Before you take this pattern to work, be clear about what you just proved and what you did not.

A role is provisioning, not enforcement. The tools and disallowedTools lists decide what a subagent is equipped to reach for. They are a strong control — an agent with no Write tool cannot write — but the authority matrix is a YAML file describing intent, and nothing reconciles it against the agent files automatically. You saw this gap live in Step 7: the investigator's out_of_scope recorded that docker exec was blocked by sandbox permissions, not by its role definition. Two different systems, both doing work, and only one of them is in the file you edited.

Model right-sizing is a cost lever, not a safety one. Putting change-reviewer on opus makes it a better reviewer. It does not make it unable to approve something it should not — that is the tool bundle's job.

More roles is not better. Every role you add is another description competing to be selected, another file to keep true as the platform changes, and another thing that goes stale silently. Teams that start here usually build eight roles and use two.

So the honest starting point at your job is smaller than this repository:

Ask me about the review that is currently a bottleneck on my team — who does it,
what they check, and what they are NOT allowed to change while doing it. Then
draft a single role file for it in the house pattern: tools, disallowedTools,
model, turn budget, and a handoff packet the next person can act on.

Push back if what I describe is really two roles wearing one hat.

What you observe. The question that matters is the third one — what the reviewer may not change. That is the sentence that becomes disallowedTools, and it is the one most teams have never written down. If your answer is vague, the role will be too, and you have found the actual problem: the boundary was never explicit for the humans either.

Step 12 — Teardown​

The six agent files, the authority-regression script, and the handoff validator are module deliverables — leave them; the Deep Dive runs its full regression matrix against them. There is nothing ephemeral to clean up: the checks operate on files, not on a running cluster, so no services were started.

git status --short .claude/agents/
Expected output
 M .claude/agents/change-reviewer.md
 M .claude/agents/finops-analyst.md

If you built the two missing roles in a base workspace, git status shows them as added or modified. Leave them in place — they are now part of the workspace's specialist team, exactly as you would want in real work. If your workspace already shipped all six, the tree may be clean.

You assembled a team of six specialist roles, each a Role Bundle with a right-sized model, a bounded turn budget, and a structured handoff. You proved the authority boundaries hold with a deterministic regression: four roles structurally cannot write, two can, and the check fails closed on the unknown. You validated that a sourced handoff passes and an unsourced one is rejected as contamination. None of this depends on a role choosing to behave — which is the entire point. The Deep Dive now turns the authority regression into a full CI-grade matrix and shows the one boundary the tool-set check cannot see, and what you layer under it.
