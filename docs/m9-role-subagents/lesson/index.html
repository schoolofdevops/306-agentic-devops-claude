Role-Specific DevOps Subagents

Every module so far has shaped one agent — a single generalist you made better behaved with CLAUDE.md rules, permission settings, skills, typed tools, and in Module 8, hooks and read-only identities underneath all of it. That generalist works. But it carries a quiet problem that shows up the moment your work has more than one shape. The same agent that investigates an incident is the agent that writes Terraform, is the agent that reviews the change, is the agent that prices the plan. It has every tool, so it can do every job — which means it can do the wrong job at the wrong moment. The agent debugging a production outage has Edit and Write in its hand the entire time, and "please don't modify anything while you investigate" is a rule it is interpreting, not a capability it lacks.

Here is the situation this module closes. An incident is open — orders are erroring. You want the agent to investigate: read health endpoints, pull logs, form a hypothesis. What you do not want, under time pressure, is for that same investigation session to decide the fix is obvious and start editing a deployment. In Module 8 you learned the deep version of why: the destructive action should not depend on the agent choosing not to take it. This module applies that lesson to roles. Instead of one generalist you constantly have to fence in, you build a team of specialists, each provisioned with exactly the tools its job needs and nothing more — so the SRE investigator debugging your outage has no Edit tool to misuse, not because you asked it nicely, but because the capability was never in its bundle.

Why a team beats a generalist​

The reason this matters at work is the same reason real ops teams are not one person with every permission. On a real platform team, the person who investigates an incident, the person who writes infrastructure code, and the person who approves the change to production are different people with different access — and that separation is not bureaucracy, it is a safety property. The investigator cannot accidentally deploy because they do not have deploy access. The reviewer's approval means something because the reviewer did not write the change. When you collapse all of that into one generalist agent with every tool, you lose every one of those properties at once.

Analogy: think about onboarding a new specialist onto your team — say, a contractor brought in to review security posture. You do not just send an email that says "you're the security reviewer now." You provision them. You issue a badge that opens the rooms they need and not the ones they don't. You give them read access to the audit logs but not write access to the production database. You set their reporting line — who they hand findings to. You decide what systems they can even see. The job title is the last and least important part; the real onboarding is the bundle of access, tools, and boundaries that makes the title mean something. A "security reviewer" who has been given write access to everything they review is not really a security reviewer — they are an editor with a misleading title. A Role Bundle is exactly this provisioning act, applied to an agent: the role is not the system prompt that names the job, it is the whole bundle of tools, permissions, model, and handoff line that makes the job real.

That is the shift. You stop thinking "one agent I keep correcting" and start thinking "a team of specialists I provisioned correctly once."

What a Role Bundle actually is​

In Claude Code, the mechanism for a role-specific subagent is an agent file — a Markdown file in .claude/agents/ with YAML frontmatter. The frontmatter declares the role's identity and its provisioning; the body is the system prompt the subagent runs under. A minimal one looks like this:

---
name: sre-investigator
description: Investigates incidents — reads health, logs, metrics, k8s state. Read-only.
model: sonnet
tools: ["Read", "Grep", "Glob", "Bash"]
disallowedTools: ["Edit", "Write", "MultiEdit", "NotebookEdit"]
---

You are the SRE Investigator for Northstar Commerce. Your job is to find out
*what is wrong*, not to fix it.

But the agent file is only the visible tip. A Role Bundle is the agent file plus everything you provision around it to make the role coherent and safe:

  • The system prompt (the file body) — role identity and its boundaries, stated in prose the model reads on every turn.
  • The tool set (tools: / disallowedTools:) — which capabilities the role even carries. This is the load-bearing part: a role without Edit in its bundle cannot edit.
  • The model and effort (model:) — right-sized to the role. A mechanical plan-pricing role runs haiku; a security review where a missed subtlety is most expensive runs opus. Paying Opus rates for a threshold comparison is a FinOps mistake; running security review on the cheapest model is a safety mistake.
  • Scoped MCP + hooks (from Modules 7 and 8) — the read-only MCP observer and the Change Gate hook sit underneath the bundle, enforcing what the prose only requests.
  • The handoff line — the structured packet this role produces and who consumes it. A role that cannot hand its work to the next role in a form they can act on is not finished.

The agent file is the badge — it names the role and lists the tools. But a badge is only as good as the reader on the door. Which brings up the single most important thing to understand about agent files, and the reason Module 8 came first.

Why an agent file is not a security boundary​

Here is the trap, and it is the one most teams fall into: they write disallowedTools: ["Edit"] in an agent file, see the agent behave, and conclude the agent cannot edit. That conclusion is half right and dangerously overstated. An agent file is an intent control — the same category as a CLAUDE.md rule from Module 8. It shapes what the subagent is provisioned to reach for, and Claude Code respects the declared tool set when it launches the subagent. That is real and useful. But it is a control the harness applies by configuration, not a wall the target system enforces against the identity. It tells you what the agent is supposed to be able to do. It does not, by itself, make a destructive action against production physically impossible.

Analogy: an agent file is the job description you hand a new hire, and the tool set is the badge you issue them. Both matter. The job description says "you are read-only on production"; the badge is coded to open only the read-only doors. But neither the job description nor the badge is what actually stops someone from writing to the production database. What stops that is the database's own permission system — the account the badge maps to has no write grant. If you issued a badge but the database account behind it happened to have admin rights, the job description saying "read-only" would not save you. The agent file is the job description and the badge; the RBAC role, the read-only credential, the admission controller, and the Change Gate hook from Module 8 are the database's own permission system. You need both, and you must not mistake one for the other.

Concretely, for the Northstar roles: the SRE investigator's file lists no Edit tool, so the harness will not give the subagent an Edit tool — that closes the easy path. But the guarantee that the SRE cannot mutate production comes from the layers underneath: the read-only kubeconfig from Module 8 means even a Bash kubectl apply is rejected by the API server for lack of an RBAC verb, and the Change Gate hook denies the dangerous command shapes deterministically. The agent file expresses the intent of the role; the M8 enforcement layer makes the boundary hold. This is why the module order is what it is — you build the enforcement floor first, then bundle roles on top of it.

The two questions an agent file answers — and the one it doesn't

An agent file answers "what is this role's job?" and "what tools is it provisioned with?" It does not answer "what can this identity physically do against the target system?" That third question is answered by RBAC, read-only credentials, admission control, and hooks — the enforcement layer. A role's real authority is the intersection of what its bundle grants and what its identity is permitted at the target. Treat the agent file as intent; verify the boundary with a test against enforcement.

Right-sizing the model: effort as a role decision​

One field in the bundle deserves its own treatment because it is where most teams either overspend or under-protect: model. The instinct is to run everything on the strongest model "to be safe." That is wrong in both directions — it wastes money on roles that do not need judgment, and it hides the fact that some roles genuinely do.

The principle is to match the model to the hardest decision the role actually makes. Read the Northstar team's model choices as a table of that reasoning:

RoleModelWhy this model
finops-analysthaikuReading a plan fixture and comparing numbers to a threshold is bounded and mechanical. Opus here is paying for judgment the task does not need — itself a FinOps mistake.
sre-investigatorsonnetForming a hypothesis from logs and metrics needs real reasoning, but under a turn budget and against read-only tools. Sonnet is the balanced default.
iac-engineersonnetAuthoring correct HCL and reading a plan for blast radius is substantive but well-scoped work.
platform-engineersonnetEditing Helm values and validating renders — real, bounded engineering.
security-revieweropusA missed subtlety in a network policy or an IAM binding is the most expensive miss on the team. This role gets the strongest model even though it is read-only, because effort — not speed — is the right lever.
change-revieweropusThe last gate before production. A missed problem here reaches customers. Strongest model for the highest-stakes judgment.

Notice the two ends. FinOps runs the cheapest model on purpose — the task is mechanical, and right-sizing the model is a cost decision the FinOps role would itself endorse. Security review and change review run the most expensive model on purpose — they are read-only, so they cost you nothing in blast radius, but a subtle thing they miss is catastrophic, so you spend on judgment exactly where a miss is worst. Model selection is not a global setting; it is a per-role decision about where judgment is worth paying for.

Turn budgets and worktree isolation: bounding the runaway​

A generalist agent left alone can loop — gather more evidence, then more, then more, never quite concluding. A specialist with a job needs a stopping rule, and the bundle gives it one: a turn budget. The SRE investigator's file says "investigate in at most 8 turns, then checkpoint." That is not an arbitrary limit; it encodes a real operational truth — an incident needs a hypothesis fast, not a perfect one slowly. The budget forces the role to converge and hand off rather than spin.

Analogy: a turn budget is the time-box on a triage assessment. When a patient arrives in an emergency, the triage nurse does not run every test before deciding urgency — they have a bounded window to reach a working assessment and route the patient. The box is not about doing less; it is about the recognition that past a certain point, more assessment is worse than acting on a good-enough one. The SRE's 8-turn budget is that time-box: reach a hypothesis, checkpoint, hand off — do not spin gathering a tenth log line when eight already point at the answer.

The second bound is spatial rather than temporal: worktree isolation. When two roles work concurrently — say the IaC engineer edits Terraform while the platform engineer edits Helm values — you do not want them writing over each other in the same working tree. A git worktree gives each role its own checkout of the repo on its own branch, so their changes are physically isolated until each is proposed and reviewed. This matters most when you start orchestrating roles in parallel (Module 10), but the discipline starts here: a role that writes gets its own place to write, so "the IaC engineer's change" and "the platform engineer's change" never contaminate each other before review.

Structured handoffs: the interface between roles​

A team of specialists is only as good as how they hand work to each other. If the SRE investigator finishes and says, in prose, "I think it's probably the readiness probe, you should maybe fix the path," the next role has to re-derive everything — was that a guess or evidence-backed? which path? did they check the database? Prose handoffs force re-investigation, which defeats the entire point of having a specialist do the investigating.

The fix is a structured handoff schema: a role's output is a JSON packet with a fixed shape, and nothing downstream acts on prose — only on the packet. The SRE investigator produces an evidence packet:

{
  "from_role": "sre-investigator",
  "to_role": "change-reviewer",
  "evidence": {
    "service": "orders-api",
    "status": "degraded",
    "checks": { "healthz": true, "readyz": false },
    "hypothesis": "readiness probe points at the wrong inventory path",
    "confidence": "high",
    "sources": ["curl /readyz", "app/orders-api/src/health.py:25"]
  },
  "recommendations": ["fix the readiness path"],
  "out_of_scope": ["did not check the database connection pool"]
}

Two fields carry the weight. sources is provenance — every claim in evidence must trace to something the role actually ran or read. A hypothesis with no sources is not evidence; it is an assertion dressed up as one, and the next role must be able to reject it. out_of_scope is honest gap-declaration — the role names what it deliberately did not check, so the consumer knows the boundaries of the handoff instead of assuming it was exhaustive.

Analogy: a structured handoff is the lab report, not the hallway conversation. When one clinician hands a case to another, a scribbled "looks like an infection, probably" is worthless — the receiving clinician cannot act on it without redoing the work. A lab report is different: it states the finding, the test that produced it (provenance), the confidence, and explicitly what was not tested. The receiving clinician can act on a lab report precisely because every claim is traceable and the gaps are named. Your role handoffs are lab reports: structured, sourced, and honest about scope — so the next role acts instead of re-investigates.

This is enforceable, too. In the lab you will run evidence-validate.sh, a deterministic script that rejects a packet with a confident hypothesis and no sources — the same fail-closed discipline from Module 8, now applied to the contents of a handoff. A handoff that cannot show its provenance is treated as contamination, not evidence.

Memory, provenance, and contamination control​

Roles accumulate context as they work, and some of that context is worth carrying forward — a known-flaky endpoint, a previously-diagnosed root cause. But agent memory is a double-edged tool. Carried-forward context that is sourced speeds a role up; carried-forward context that is unsourced is contamination — the role starts treating a stale guess as a fact, and every downstream handoff inherits the error.

The control is the same provenance discipline, applied to memory: a claim a role carries forward must retain its source, or it does not get carried forward. "The orders-api readiness probe was misconfigured" is safe to remember if it carries app/orders-api/src/health.py:25 and the date it was verified. "The orders-api is probably fine" is not safe to remember at all — it is an unsourced impression that will mislead the next incident. The handoff schema's sources field is the memory discipline in miniature: it forces every retained claim to be traceable, so a role's memory is a set of verifiable facts rather than an accumulating pile of guesses.

The six roles, as a team​

Put it together and you have the Northstar specialist team — six roles, each a Role Bundle, each with a job it can do and boundaries it structurally cannot cross:

Read the shape off the diagram. Four roles are read-only — they investigate, audit, price, and review, and none of them carries a write tool, so none of them can mutate anything even by accident. Two roles author — they write HCL and Helm values, but only ever propose on a branch; the actual write to a live environment happens through the GitOps reconciler from Module 8, never from the role's own identity. And every arrow is a structured packet flowing to the change-reviewer, who gives an independent verdict precisely because they wrote none of the candidates.

Testing the roles: authority regression​

The last piece is how you know the boundaries hold — and this is where the Module 8 lesson pays off completely. Because a role's tool set is declared configuration, "can this role write?" is a question you can answer with a deterministic test, not a hope. You do not have to trust that the SRE investigator will decline to edit; you can assert that its bundle carries no write tool, so it is structurally incapable of editing. And you can assert the inverse: that the IaC engineer does carry a write tool, because authoring is genuinely its job.

That pair — assert a role can do what it should, and assert it cannot do what it must not — is an authority regression test. In the lab you will run role-authority-check.sh, which reads a role's declared tools and answers "is this role structurally capable of a write?" with a fixed rule and no model in the loop. The SRE, FinOps, change-reviewer, and security-reviewer all return "blocked" for write; the IaC and platform engineers return "capable." Run it in CI and a change that accidentally grants the SRE investigator an Edit tool fails the build — the boundary is a test, exactly like the Change Gate. The Deep Dive takes this all the way into a full forbidden-action matrix.

What you'll do in the lab​

You will assemble the Specialist Team and prove each role's boundaries hold:

  1. Read the four shipped agent files — sre-investigator, iac-engineer, platform-engineer, security-reviewer — and read each as a Role Bundle: prompt, tool set, model rationale, turn budget, handoff.
  2. Build the two missing roles — finops-analyst (haiku, read-only, prices plans) and change-reviewer (opus, read-only, independent verdict) — completing the team.
  3. Run the authority regression — role-authority-check.sh for every role, asserting the read-only roles cannot write and the authoring roles can, and confirming it fails closed on an unknown role.
  4. Validate a structured handoff — drive evidence-validate.sh with a well-sourced packet (passes) and a confident-but-unsourced one (rejected as contamination), and see it fail closed on empty input.
  5. Confirm the model right-sizing — verify finops runs haiku and the two reviewers run opus, and understand why.
  6. Let the repository certify the team — grade.sh m9 runs the whole authority-and-handoff matrix.

grade.sh m9 certifies all six bundles are present with tools and a model, the read-only roles carry no write tool while the authoring roles do, the model right-sizing holds, every role declares a turn budget and a handoff schema, and the evidence validator accepts sourced packets while rejecting unsourced ones. The Deep Dive then runs the full authority regression matrix — the SRE may query health but not edit deployments, FinOps may read plans but not apply, the reviewer may inspect but not modify the candidate — and shows why that matrix belongs in CI as a boundary you test, not a rule you hope about.
