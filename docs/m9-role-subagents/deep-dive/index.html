Deep Dive — The Authority Regression Matrix

The core lab proved each role's write boundary in isolation: the SRE is blocked, the IaC engineer is capable, the check fails closed on the unknown. That is the single-cell version of the idea. This page builds the full matrix — every role against every action it might attempt — and treats it the way you would treat any other regression suite: a thing that runs in CI, fails the build on drift, and encodes the specific authority claims your security reviewer will ask you to defend. Because the real question is not "can I check one boundary once." It is: "can I assert the entire team's authority contract, positively and negatively, as a test that runs on every change — so a role's power can never silently grow?" That is authority regression, and it is where role bundles become auditable instead of merely tidy.

This extends the lab — it does not repeat it

You already ran the write matrix by hand and saw it certified by grade.sh m9. This page is about the layer above that: why authority testing needs both directions (can-do and cannot-do), the precise thing the tool-set check can and cannot see, how the agent-file boundary can be tighter than the authority-matrix policy (and why that is correct), and where authority regression sits relative to the M8 enforcement layer. If you have not built the six roles and run the authority check (lab Steps 3–6), do that first; everything here runs against them.

Why one-sided testing is a false sense of safety​

The instinct when you hear "test the authority boundary" is to write the negative half: assert the SRE cannot write, the reviewer cannot edit, FinOps cannot apply. That half is necessary and it is where the danger lives, so it feels complete. It is not.

A suite that only asserts "these roles cannot write" passes just as green if you accidentally strip the write tool from the IaC engineer — the one role whose entire job is authoring HCL. Now your authoring workflow is silently broken: the role that is supposed to write can't, and nothing failed, because your tests only ever checked that roles couldn't do things. Over-restriction is a regression too. It does not cause a security incident; it causes a role to quietly stop being able to do its job, and you find out when someone asks why the IaC engineer keeps refusing to edit.

Analogy: authority regression is the fire-drill and the door test, not just one of them. A building safety audit checks two opposite things: that the emergency exits do open (people can get out) and that the secure doors stay locked (people can't get into the server room). An audit that only tested the locks would pass a building whose fire exits were welded shut — technically "secure," actually a death trap. An audit that only tested the exits would pass a building with a wide-open vault. You need both directions because a role's authority is a boundary, not a floor or a ceiling: exactly these capabilities, no fewer and no more. A test suite that checks only one edge of that boundary certifies a boundary you did not intend.

So the matrix is two-sided by construction. For every role it asserts the positive capabilities its job requires and the negative ones its job forbids. Run the full thing and read both columns:

for r in sre-investigator iac-engineer platform-engineer security-reviewer finops-analyst change-reviewer; do
  scripts/role-authority-check.sh "$r" read  >/dev/null 2>&1; rd=$?
  scripts/role-authority-check.sh "$r" write >/dev/null 2>&1; wr=$?
  rdv=$([ $rd -eq 0 ] && echo "read=YES" || echo "read=no ")
  wrv=$([ $wr -eq 0 ] && echo "write=YES" || echo "write=NO ")
  printf '%-20s %s  %s\n' "$r" "$rdv" "$wrv"
done
Expected output
sre-investigator     read=YES  write=NO 
iac-engineer         read=YES  write=YES
platform-engineer    read=YES  write=YES
security-reviewer    read=YES  write=NO 
finops-analyst       read=YES  write=NO 
change-reviewer      read=YES  write=NO

Both edges of every role's authority, in one table. Every role can read (they all need to see the world to do their job); only the two authoring roles can write. This is the authority contract of the entire team expressed as a grid of deterministic verdicts — the thing you commit and gate on. A change that flips any cell is a change to the team's authority, and the suite makes it visible.

The specific thing the tool-set check can see​

Be precise about what role-authority-check.sh actually proves, because a security reviewer will ask. It reads the role's declared tools array, checks whether a write tool (Edit/Write/MultiEdit/NotebookEdit) is present and not disallowed, and returns a verdict. That means it answers exactly one question with certainty:

Is this role provisioned with a write capability?

That is a real and valuable thing to know. If the answer is "no," the harness will not hand the subagent a write tool, so the easy, direct path to a file edit is closed — the role has no Edit to call. And because the verdict is a pure function of declared configuration, it is deterministic: run it three times, get the same answer three times.

a=$(scripts/role-authority-check.sh change-reviewer write >/dev/null 2>&1; echo $?)
b=$(scripts/role-authority-check.sh change-reviewer write >/dev/null 2>&1; echo $?)
c=$(scripts/role-authority-check.sh change-reviewer write >/dev/null 2>&1; echo $?)
echo "runs: $a $b $c"
Expected output
runs: 3 3 3

Three runs, three identical exit-3 verdicts. Determinism is what makes this a CI check rather than a judgment call — the same property that let you test the Change Gate in Module 8. A boundary you can assert identically on every run is a boundary you can put in a pipeline.

The specific thing it cannot see — and what you layer under it​

Here is the honest edge, and naming it is what separates a real implementation from a checkbox. The tool-set check proves the role is not provisioned with an Edit tool. It does not prove the role cannot cause a write by another path. A read-only role still has Bash. A Bash kubectl apply, a Bash terraform apply, a shell redirect that overwrites a file — none of those go through the Edit tool, so the tool-set check has nothing to say about them. The SRE investigator has no Edit tool, and it could still type a kubectl apply into Bash.

This is not a flaw in the check; it is the boundary of what a tool-set check can mean. And it is exactly why this module sits on top of Module 8 rather than replacing it. The write-by-Bash path is closed by the enforcement layer you already built:

scripts/role-authority-check.sh iac-engineer write >/dev/null 2>&1 && echo "role: write-capable"
printf '{"tool_name":"Bash","tool_input":{"command":"terraform apply -auto-approve infra/environments/production"}}' \
  | scripts/hooks/change-gate.sh >/dev/null 2>&1
echo "change-gate exit=$?"
Expected output
role: write-capable
change-gate exit=2

Read the two lines together. The IaC engineer is role-level write-capable — it can author HCL, which is its job. And yet a production terraform apply from that role is denied (exit 2) by the M8 Change Gate. The role bundle answers "may this role write files?"; the Change Gate answers "may this command run against prod?" They are different questions with different answers, and the dangerous action dies at the layer built to catch it. The tool-set check guards the provisioning; the hook and the read-only credential guard the action.

The authority regression is Layer 1 — and it is the layer you can test cheapest and earliest, at build time, before anything runs. That is its value: it catches the whole class of "a role got provisioned with more than it should have" at commit time, so the enforcement layers underneath only ever have to handle the residual. You do not lean on the gate to catch a misprovisioned role; you catch the misprovisioning in CI and let the gate do its narrower job.

When the agent file is tighter than the policy — and why that is correct​

There is a subtle case in the Northstar team worth dwelling on, because it teaches how these layers relate. The authority-matrix.yaml — the older, free text-level policy from earlier modules — grants the security-reviewer a write path (platform/policies/). But the security-reviewer's agent file carries no write tool at all. So the authority-matrix says "may write policies" while the bundle says "cannot write anything." Run the check:

scripts/role-authority-check.sh security-reviewer write
echo "exit=$?"
Expected output
BLOCKED: role 'security-reviewer' has NO write tool in its bundle — it is structurally incapable of Edit/Write. Authority boundary holds.
exit=3

The agent file is tighter than the policy, and that is the correct direction for a divergence to run. The security-reviewer's own plain text explains why: "a fix you write is a fix nobody reviewed." A reviewer that can patch what it audits has destroyed its independence — the same principle as the change-reviewer. So the role deliberately drops even the write path the older policy allowed. The tool grant is the tighter boundary, and when a tighter boundary and a looser policy disagree, the tighter one wins because it can only reduce authority, never expand it.

The safe direction for authority drift

When two layers disagree about a role's authority, the layer that grants less must win — never the one that grants more. The security-reviewer's bundle removing a write path the authority-matrix still lists is safe drift: the effective authority is the intersection, and the intersection here is "no write." The dangerous direction is the opposite — an agent file that grants more than the policy intends. That is exactly the case the authority regression must catch, which is why the M9 grader also asserts no read-only role's agent file grants a write tool: the tool grant may be tighter than the matrix, never looser.

This is a general rule for layered authority: effective authority is the intersection of every layer, and a safe change to any layer can only shrink the intersection. A test that asserts the read-only roles carry no write tool is checking that the tightest layer stays tight — so even if a looser policy drifts, the bundle holds the line.

The negative test as an incident rehearsal​

Read the negative half of the matrix one more way: each "cannot" cell is a rehearsal of an incident that did not happen. "SRE write -> BLOCKED" is the rehearsal of the SRE, mid-incident, deciding the fix is obvious and editing a deployment. "change-reviewer write -> BLOCKED" is the rehearsal of the reviewer editing the candidate it was supposed to judge. "finops-analyst write -> BLOCKED" is the rehearsal of the cost analyst deciding to just apply the cheaper plan itself. Each is a plausible, well-intentioned wrong move — the same pattern as Module 8's Destructive Shortcut, but at the level of who acts rather than what command runs.

for r in sre-investigator finops-analyst change-reviewer security-reviewer; do
  scripts/role-authority-check.sh "$r" write >/dev/null 2>&1
  [ $? -eq 3 ] && echo "$r: forbidden-action rehearsal PASSED (cannot write)" || echo "$r: FAILED — role can write!"
done
Expected output
sre-investigator: forbidden-action rehearsal PASSED (cannot write)
finops-analyst: forbidden-action rehearsal PASSED (cannot write)
change-reviewer: forbidden-action rehearsal PASSED (cannot write)
security-reviewer: forbidden-action rehearsal PASSED (cannot write)

Four incidents that cannot happen, certified. Each line is a specific "well-meaning agent does the wrong thing under pressure" scenario that the bundle forecloses structurally. This is what you show a security reviewer: not "we trust the roles to stay in their lane," but "here is the test that proves each read-only role structurally cannot leave it, and it runs on every commit."

Let the repository certify the full matrix​

Run the deep-dive grader. It drives the complete two-sided authority regression — every positive capability, every forbidden action, the determinism property, and the role-vs-enforcement layer distinction — as the CI-grade suite this page has been building.

./scripts/grade.sh m9-deep-dive
Expected output
Grading: Module m9-deep-dive
========================

Checking: Deep Dive — authority regression: each role can do what it should and CANNOT do what it must not

  ✓ POSITIVE: the SRE investigator CAN read — querying health and logs is its whole job
  ✓ FORBIDDEN: the SRE investigator CANNOT edit deployments — it carries no write tool, so the boundary is structural, not a request it might ignore
  ✓ POSITIVE: the FinOps analyst CAN read plan fixtures — pricing a plan requires reading it
  ✓ FORBIDDEN: the FinOps analyst CANNOT apply or edit infrastructure — it reads plans and returns a number, it never changes the estate
  ✓ POSITIVE: the change-reviewer CAN read — it needs full context to judge a change
  ✓ FORBIDDEN: the change-reviewer CANNOT modify the candidate branch — a reviewer that edits the thing under review has destroyed its own independence
  ✓ FORBIDDEN: the security-reviewer CANNOT patch what it audits — even though the authority-matrix lists a write path, the agent-file tool grant is the tighter boundary and drops it
  ✓ POSITIVE-AND-BOUNDED: the IaC engineer CAN write HCL (authoring is its role) but the M8 change gate still denies a production apply — authority and enforcement are two different layers
  ✓ REGRESSION: the full forbidden-action matrix holds in one pass — all four read-only roles blocked from write, both authoring roles permitted
  ✓ the authority check returns the SAME verdict on repeated runs — it is a deterministic script, so the boundary is a test you can put in CI, not a judgment that varies

========================
RESULT: PASS (10 passed)

Ten green. The suite certifies both directions of every role's authority boundary, the tighter-than-policy case for the security-reviewer, the role-vs-enforcement distinction for the IaC engineer, and the determinism that makes the whole thing CI-worthy. The team's authority contract is now a test, not a description.

Where you'll use this​

  • Adding a new role to the team (every module after this one that introduces a specialist). The moment you write a new agent file, add its row to the authority regression — both the positive capabilities it needs and the forbidden ones it must never have. A role without an authority test is a role whose power can grow silently; the test is how you keep the team's authority contract honest as it expands.
  • Reviewing a PR that touches .claude/agents/ (the GitOps and CI/CD modules). A change to a tool set is a change to a role's authority, and it deserves the same scrutiny as a change to an IAM policy. The authority regression turns "someone widened a role's tools" from an invisible diff into a red build — so the reviewer is looking at a failed test, not squinting at a YAML array hoping to notice.
  • Explaining role safety to a security reviewer. The defensible claim is two-sided and layered: each read-only role is provisioned without a write tool (a deterministic build-time test that fails on drift), and the write-by-Bash path is closed underneath by the Change Gate and read-only identities from Module 8, and — the part that shows you understand the boundary — the tool-set check proves provisioning, not runtime prevention, which is why the enforcement layer sits under it. A reviewer trusts the person who can name what their test proves and what it does not, then shows the layer that covers the gap.
