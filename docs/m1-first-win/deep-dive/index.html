Deep Dive — The Autonomy Ladder & the OOPAV Loop

The core lab gave you the loop as a checklist you ran by hand. This page takes it apart. You will see the loop as a named engineering discipline, learn where each autonomy level actually breaks, and pick up the one detail from the M1 grader that most people miss — a green check that is green for the wrong reason.

If the lab was "how to run the loop once," this is "how to decide who runs it, how far, and how to know when a guardrail is lying to you."

The OOPAV loop: the lab's checklist, named​

The diagnose → change → verify loop you ran is a compression of a five-phase control loop. Naming the phases matters because each one is a distinct place where autonomy can be granted or withheld — and where it can fail.

Analogy: it is the OODA loop that fighter pilots and incident commanders use — observe, orient, decide, act — with one addition that software makes possible and safety makes mandatory: a verify phase that closes the loop with evidence instead of belief.

Map it back to the lab:

OOPAV phaseWhat you did in M1
Observecurl /healthz and curl /readyz — collected the live symptom
OrientRead health.py, saw the probe hit /health while the service serves /healthz
ProposeHypothesis: fix the path; a one-word change
ActBranch fix/readyz-probe, edited the probe line
Verify./scripts/grade.sh m1 — red to green, reproducibly

The critical property is that verify feeds back into orient, never into act. When the grader is red, you re-orient — rebuild your model of the failure — you do not patch on top of the last patch. Stacking a second change on an unverified first is how a one-line fix becomes a three-file mystery. This is the single discipline that separates the technician from the tinkerer, expressed as a control-flow rule.

The autonomy ladder as a phase-by-phase grant​

The lab presented four levels as a table. The sharper model: autonomy is not one dial you turn up. It is a separate grant on each OOPAV phase. Who observes, who orients, who proposes, who acts, who verifies — each can be human or agent independently.

The move from Semi-Autonomous to Autonomous is not "the agent got smarter." It is that you removed the human approval gate between propose and act, and in exchange you demanded a much stronger verify — one trustworthy enough to trigger an automatic rollback with nobody watching. Autonomy is a trade: you spend human approval and buy it back with verification you can bet the system on.

This reframes the AIOps question. "Should this be autonomous?" becomes "is my verify phase strong enough to be the only thing standing between the agent and production?" If the answer is no, the human gate stays, and you are semi-autonomous, not autonomous — regardless of how good the model is.

The failure mode at each rung​

Each level fails in a characteristic way. Knowing the failure mode is how you choose the rung.

LevelIts characteristic failureThe tell
Manual / DeclarativeToo slow; the human is the bottleneck on toil that is safe to delegateYou are hand-editing the same class of trivial fix for the tenth time
AI AugmentedAutomation bias — you rubber-stamp the suggestion because reviewing feels like frictionYou approved a diff you did not actually read
Semi-AutonomousApproval-gate theatre — the human clicks "approve" without understanding the diffDiffs too large to review; approval becomes a formality
AutonomousThe guardrail is weaker than assumed; a bad change passes verify and shipsA green check that was green for the wrong reason

That last failure — a guardrail that passes when it should fail — is the most dangerous, because it fails silently. And M1's own grader contains a live example of it.

Under the hood: the M1 grader's honest weakness​

Here is the detail almost everyone misses. Look at what readyz() returns when the dependency check fails:

    all_ready = all(checks.values())
    return {
        "status": "ready" if all_ready else "not ready",
        "checks": checks,
    }

The function returns a dict, and it never sets a status code. FastAPI serializes any plain return as HTTP 200. So the broken endpoint — the one reporting inventory_api: false — still answers with a 200 status line. The body says "not ready"; the HTTP code says "fine."

Now re-read the grader's first check:

READYZ=$(curl -s -o /dev/null -w '%{http_code}' http://localhost:8080/readyz)
check "orders-api /readyz returns 200" "$([[ "$READYZ" == "200" ]] && echo true || echo false)"

Prove it against the unfixed endpoint — reset first so the bug is back:

./scripts/reset.sh m1 >/dev/null 2>&1; curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/readyz
Expected output
200

The broken endpoint returns 200. The grader's first check passes before you fix anything. A check meant to prove readiness is satisfied by an endpoint that is loudly declaring itself not ready.

So which grader checks actually discriminate the fix from the bug? Only the ones that inspect the code path and the Helm probe:

grep -c 'inventory_api_url}/healthz' app/orders-api/src/health.py
Expected output
0

On the unfixed code the count is 0 — the discriminating check is red. After your fix it becomes 1. This is the check that actually measures the repair; the HTTP-200 check is along for the ride.

The lesson is not "the grader is bad" — it is "read what your gate measures"

The M1 grader passes overall only because the code-path and Helm checks are strict, even though the HTTP-200 check is loose. But imagine an autonomous pipeline whose only gate was "does /readyz return 200?" It would greenlight the broken build every time and page nobody. Before you let a check gate an autonomous action, ask what it actually asserts — not what its name implies. A guardrail you have not audited is not a guardrail.

This is the deep reason verification has to be deterministic and audited, not just present. A check that always passes is worse than no check: it manufactures false confidence, which is exactly the fuel that makes automation bias and approval-gate theatre dangerous. The strength of your verify phase is the ceiling on how much autonomy you can safely grant.

A risk framework for choosing the rung​

Put it together into something you can apply to any task an agent might take. Score the task on three axes, then let the weakest axis cap the autonomy level.

  • Reversibility gates everything. If a mistake cannot be undone in the window before it does damage, no amount of verification quality earns autonomy — you keep a human on it. (The production credential rotation from the lab dies at this first gate.)
  • Verification quality is the second gate, and it is where most teams overestimate themselves. "We have tests" is not the same as "our tests would catch this failure." The M1 grader's HTTP-200 check is a miniature of that gap.
  • Blast radius × audited guardrail is the final gate that separates agentic from autonomous. A small blast radius with a guardrail you have personally read is autonomy-eligible; a small blast radius behind a check you have never inspected is not.

The M1 lab fix — a one-line probe path, on a branch, behind a grader whose discriminating checks you can read — clears all three gates. That is why it is a legitimate candidate for agentic autonomy, and it is the template for every "yes, let the agent do this" decision you will make in the rest of the course.

Where you'll use this​

  • Choosing a permission posture (M2). The autonomy ladder is the why behind the postures you configure next module — Manual, Accept Edits, Plan, Auto map directly onto these rungs.
  • Reviewing an agent's PR on call. When an agent opens a change during an incident, the phase-by-phase grant tells you exactly what to check: was the verify strong enough to trust the act?
  • Designing a CI gate for auto-merge. Before you let a pipeline merge without a human, you will audit whether the gate discriminates good from bad — the exact skill the M1 grader's HTTP-200 blind spot teaches.
  • Post-incident review. "The check was green" is the start of an investigation, not the end of one. This page is why you will always ask what did the green actually assert.
