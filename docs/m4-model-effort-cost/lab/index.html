Lab — The Agent Run Ledger

Every Claude Code run generates cost, token and behaviour data that evaporates the moment the session ends. Choosing a model and an effort level only pays off if you can see what the choice actually did, and almost nobody can.

This lab makes the run visible. You will stand up a local OpenTelemetry collector, export Claude Code's own telemetry to it, and build the Agent Run Ledger that rolls a run into one auditable record. Then you will audit that ledger and find that it is wrong by two orders of magnitude — not because you built it badly, but because the obvious way to count tokens stopped being correct and nothing told you. You will fix it, and only then compare models and effort levels on a real judgment task, because a cost comparison built on the wrong accounting will confidently rank the expensive run as the cheap one.

Where you are working

All commands run from the root of the agentic-ops-lab workspace. The collector config, the ledger and the budget check are committed artifacts under agentops/ — the instrumentation you would ship to a team, not throwaway scratch.

cd ~/agentic-ops-lab

You do not need the Northstar stack for this lab; the collector runs as a single container.

The one place claude -p belongs

Most of this course keeps you in interactive sessions, because that is how operational work is done. This lab is the exception, and the reason is the lab's subject. Steps 6 and 7 are controlled experiments: the same task, run repeatedly, with exactly one variable changed. An interactive session cannot give you that — you would type slightly different things, approve at different moments, and the numbers would not be comparable.

So the measurement runs use claude -p, which is one shot, non-interactive and identical every time. That is what makes them measurements rather than anecdotes. Everything you build here, you build in a normal session.

Step 0 — Prerequisites​

docker version --format '{{.Server.Version}}'

Expected output

Versions differ. Those two flags are the staffing dials from the lesson exposed on the CLI: --model picks who runs the task, --effort picks how hard they think about it. You will vary both and measure the difference.

Step 1 — Have Claude write the collector config​

Claude Code speaks OpenTelemetry. To capture that as something you can parse you run a collector: a small process that receives OTLP over the network and writes it to a file.

Do not type the config. Writing YAML from a spec is exactly the work you delegate — and the interesting part is whether the agent gets the two non-obvious details right without being told them.

claude --permission-mode acceptEdits
Write agentops/collector.yaml — an OpenTelemetry Collector config for capturing
Claude Code's own telemetry.

Requirements:
  - receive OTLP over HTTP on the standard OTLP/HTTP port, on 0.0.0.0
  - export everything to a file at /out/telemetry.jsonl
  - keep the collector's own logs quiet (error level only)
  - the pipelines must match what Claude Code actually exports -- check that
    before you choose them, and tell me which signal types you included and
    which you deliberately left out

Also create the directory agentops/otel-out.

What Claude does. Writes the config and creates the directory. The closing clause is doing the work: it forces the pipeline choice to be a stated decision rather than a plausible three-pipeline default.

What you observe — two details decide whether this works at all.

  1. The port is 4318. That is OTLP/HTTP. 4317 is OTLP/gRPC — a different protocol on a different receiver, and nothing will arrive.
  2. There is no traces pipeline. Claude Code exports metrics and log-record events, not spans. The events arrive on the logs pipeline and that is what the ledger is built from. A traces pipeline would sit there receiving nothing.
grep -E 'endpoint:' agentops/collector.yaml
yq '.service.pipelines | keys' agentops/collector.yaml
Expected output
        endpoint: 0.0.0.0:4318
[
  "logs",
  "metrics"
]

Key order varies. If traces appears, delete that pipeline — and note what just happened: the agent produced a confident, well-formed, wrong answer. Pricing that failure mode correctly is what this whole module is about, and you are going to meet it again in Step 5 in a form that is much harder to spot.

Step 2 — Start the collector​

docker run -d --name otel-ledger \

  -v "$PWD/agentops/collector.yaml:/etc/otelcol/config.yaml:ro" \
  -v "$PWD/agentops/otel-out:/out" \

The first run pulls the image. If the status is not Up, check docker logs otel-ledger — the usual cause is a wrong config path, which the collector reports on startup.

Step 4 — Have Claude build the Agent Run Ledger​

Raw telemetry is the timesheet; the ledger is the invoice. You need a script that reads a run's telemetry and rolls it into one record.

This is real tooling and exactly the kind you should not hand-type: the OTLP value-wrapping is fiddly and you will want to change it later.

Write agentops/ledger.py — the Agent Run Ledger.

Usage: python3 agentops/ledger.py <telemetry.jsonl> [label]
It prints ONE JSON row summarising the whole run.

Read agentops/otel-out/telemetry.jsonl first and work out the actual record structure
before you write any parsing. Two things will bite you:
  - OTLP wraps every attribute value as {"stringValue": ...} / {"intValue": ...}, so
    attributes need unwrapping before use
  - Claude Code's events arrive as log records, not spans

Claude Code's per-request event carries its name in the log record's body.stringValue —
the string `claude_code.api_request` — and the numbers live in that record's attributes
list: model, input_tokens, output_tokens, cost_usd, duration_ms.

The row must carry, accumulated in a single pass over the records, using exactly these
key names so downstream tooling can read it:
  model, effort, input_tokens, output_tokens, total_tokens, cost_usd, duration_ms
plus the number of tool calls and how many of them failed.

Numeric attributes must come out as numbers, not strings — OTLP encodes them as
{"intValue": "16000"} and {"doubleValue": 0.11}, so intValue needs an int cast.

Print nothing but the JSON row.

What Claude does. Reads the real telemetry before writing the parser — the instruction that matters, because the OTLP structure is not guessable and an agent that skips it writes a parser for an imagined format that returns zeros against the real one.

python3 agentops/ledger.py agentops/otel-out/telemetry.jsonl "read-claudemd"
Expected output
{"model": "claude-sonnet-5", "effort": "high", "input_tokens": 6, "output_tokens": 406, "total_tokens": 412, "cost_usd": 0.20794, "duration_ms": 8832, "tool_calls": 2, "tool_calls_failed": 0, "label": "read-claudemd"}

Your numbers differ. The script works, the JSON is well-formed, every field you asked for is present, and it will pass a code review.

It is also wrong, and the next step is the most important one in this module.

Step 5 — Audit your own ledger​

Look at those two numbers together: 412 tokens, and $0.208.

At any published price, 412 tokens costs a fraction of a cent. The row is internally inconsistent, and nothing in the tooling will ever tell you — a low token count reads as a cheap run, which is exactly the thing you would not investigate.

Hand it back:

Audit your own ledger before I trust it. The row it just printed says the run used 412
tokens and cost $0.208. Those two numbers cannot both be right — at any published price,
412 tokens is a fraction of a cent.

Go back to the raw claude_code.api_request event in agentops/otel-out/telemetry.jsonl and
list EVERY token-related attribute it carries, not just the two I named. Tell me what you
find before you change anything.

Then fix agentops/ledger.py so the row accounts for all of them. Keep input_tokens and
output_tokens as they are, add the ones you found under their own names, and make
total_tokens the honest total — the number that squares with cost_usd. Add a
billable_tokens field only if you can justify it from the data.

What you observe. On the captured run it found the gap and declined the extra field it could not justify:

claude_code.api_request carries six token/cost attributes: input_tokens, output_tokens, cache_read_tokens, cache_creation_tokens, cost_usd, and cost_usd_micros (a redundant micros-encoding, not a token count). The ledger was only summing input_tokens+output_tokens (→412), while cost_usd (→$0.208) was priced against 169,592 real tokens once cache reads (142,675) and cache writes (26,505) are included — that mismatch is exactly the bug.

No billable_tokens field — all four categories demonstrably feed cost_usd (just at different per-token rates), so a separate "billable" subset isn't justified by the data; it would only duplicate total_tokens.

python3 agentops/ledger.py agentops/otel-out/telemetry.jsonl "read-claudemd"
Expected output
{"model": "claude-sonnet-5", "effort": "high", "input_tokens": 6, "output_tokens": 406, "cache_read_tokens": 142675, "cache_creation_tokens": 26505, "total_tokens": 169592, "cost_usd": 0.20794, "duration_ms": 8832, "tool_calls": 2, "tool_calls_failed": 0, "label": "read-claudemd"}

412 became 169,592. The same run, the same telemetry file, the same script — off by a factor of 411 because two of the four counters were not in the sum.

Why this bug is the module, not a footnote

Nobody wrote a bad parser here. input_tokens + output_tokens was the right answer once, and prompt caching quietly moved almost all the volume into two counters that did not used to matter. The spec you were working from went stale and the code kept running.

That is how most cost-instrumentation failures look: not a crash, not an error, just a number that is confidently, quietly, enormously wrong — and wrong in the reassuring direction. You are about to see what it does to a decision.

One honest thing the agent said, worth reading

On the captured run it also reported that it could not run its own test:

I could not actually run pytest/python3 in this session — only cat, ls, find, grep… are pre-approved in .claude/settings.json, and this is a non-interactive session so I can't get a manual approval through. Instead I hand-simulated the exact aggregation logic with jq over the real telemetry.jsonl and got input=6, output=406, cache_read=142675, cache_creation=26505, cost_usd≈0.2079.

That is the Module 2 allow list doing its job, and the agent doing the right thing inside it: it verified with a tool it was allowed, and labelled the result as hand-simulated rather than claiming a test run. Compare it to what a less careful session would have said — "tests pass" — and you have the whole verification discipline in one paragraph.

Step 6 — Compare models on work that has a right answer​

Now the ledger is trustworthy, so a comparison means something.

Most cost comparisons are run on toy prompts, which measures nothing you care about: of course the cheap model summarises a sentence more cheaply. Use a task with a right answer and real consequences — reviewing a Terraform plan that destroys a production database — so you can grade the answer as well as the bill.

run_ledger () {   # run_ledger <label> <model> [effort]
  : > agentops/otel-out/telemetry.jsonl
  CLAUDE_CODE_ENABLE_TELEMETRY=1 \
  OTEL_METRICS_EXPORTER=otlp OTEL_LOGS_EXPORTER=otlp \
  OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf \
  OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 \
  OTEL_METRIC_EXPORT_INTERVAL=2000 OTEL_LOGS_EXPORT_INTERVAL=2000 \
  claude -p "Read infra/fixtures/plan-stateful-replace.json. We want to ship tonight. Tell me in two sentences whether this plan is safe to apply, and why." \
    --model "$2" ${3:+--effort "$3"} --permission-mode auto
  sleep 6
  python3 agentops/ledger.py agentops/otel-out/telemetry.jsonl "$1"
}

run_ledger "haiku"  haiku
run_ledger "sonnet" sonnet

What you observe. Both answers, then both rows. Grade the answers first:

Haiku: UNSAFE — do not apply. This plan destroys and recreates the production database (changing engine_version from 16.4 to 16.5) with skip_final_snapshot=true, causing complete data loss and downtime; you need either a verified backup strategy or to change skip_final_snapshot to false before proceeding.

Sonnet: No, this plan is not safe to apply tonight: it destroys and recreates module.database.aws_db_instance.main … since skip_final_snapshot is true, that replace happens with no final snapshot, meaning irreversible data loss plus downtime. Per infra/CLAUDE.md, this is a prod database change that requires change-reviewer approval regardless of size, and it should not go out without either a verified backup/migration plan or switching to a non-replacing upgrade path (e.g., minor-version in-place upgrade instead of triggering replace_paths).

Both are correct, and both found skip_final_snapshot. Sonnet additionally cited the governance rule from the context pack you wrote in Module 3 and named the non-destructive alternative. That is a real difference; whether it is worth paying for depends on whether the person reading it already knows the policy.

Now the bill:

Runnaive total (input+output)true totalcostwall
Haiku2,348238,715$0.10430.5s
Sonnet, high effort1,967419,730$0.42231.2s

Read the naive column on its own. It says Sonnet used fewer tokens than Haiku — 1,967 against 2,348 — so a ledger built on input + output would have reported the four-times-more-expensive run as the cheaper one.

That is what the Step 5 bug actually costs you. It does not merely under-report; it inverts the ranking you are making the staffing decision on. Every conclusion you would have drawn from that table would have been backwards, and the table would have looked fine.

With the true totals, the finding is the one the lesson argued for and now you can point at it: four times the money for a governance sentence. For a plan review feeding a human reviewer who knows the policy, Haiku is the right staffing. For one feeding an automated gate with nobody to supply the context, the extra is arguably worth it. That is now a decision with numbers under it.

Step 7 — Compare effort, and be prepared to be wrong​

Hold the model fixed and turn the effort dial.

run_ledger "sonnet-low"  sonnet low
run_ledger "sonnet-high" sonnet high
Expected output
Runtrue totalcostwallanswer
Sonnet, --effort low283,877$0.2458.8scorrect
Sonnet, --effort high169,592$0.2088.8scorrect

Low effort cost more than high effort. Not by much — 18% — but decisively in the wrong direction from the intuition, and the wall-clock times were identical.

The reason is visible in the ledger rows: the low-effort run did more cache reading (256k against 143k). It thought less and looked more, taking a different path through the repository to reach the same conclusion. Effort is a reasoning dial, not a spend dial, and on a bounded task with a clear answer the extra deliberation was not where the money was going.

What to actually take from Step 7

Not "low effort is more expensive" — that is one pair of runs on one task and it will not hold everywhere. Take the method: the dial you assume is a cost dial may not be, on your workload, and you now own the instrument that tells you.

The reason the lesson could not just give you this answer is that it depends on the task. Run this comparison on the three tasks your team actually repeats a thousand times a week, and the resulting table is worth more than any general advice about effort levels, including this course's.

A run that accomplished nothing still cost $0.40

While capturing these, one low-effort run was launched under acceptEdits and stopped at a permission gate before it read anything. It produced no answer at all — and the ledger recorded $0.397 for it, because the context was loaded and billed regardless.

Blocked runs, refused runs and runs you cancel are not free. If you are budgeting agent spend, count them, because your ledger already does.

Step 8 — Turn the ledger into a control​

A ledger you read afterwards is a post-mortem. Make it a gate.

Write agentops/budget-check.sh — a budget alert over a run's telemetry.

Usage: budget-check.sh <telemetry.jsonl> <max_tokens>

It sums the run's total tokens and compares them against the budget:
  - within budget -> print an OK line naming the totals, exit 0
  - over budget   -> print a line beginning "BUDGET ALERT" naming the totals and the
                     budget, and exit 1

Both arguments are required; refuse with a clear message if either is missing.
Make it executable.

Reuse the SAME token accounting as agentops/ledger.py — all four token categories, not
just input plus output. Two different answers to "how many tokens did that run cost" is
worse than having no answer at all, and you just fixed that exact bug in the ledger.

Now check it the way you would check anyone's gate — the exit codes, not the message text:

ls -l agentops/budget-check.sh | awk '{print $1}'
./agentops/budget-check.sh >/dev/null 2>&1;                        echo "no-args      exit=$?"
./agentops/budget-check.sh agentops/otel-out/telemetry.jsonl 1000 >/dev/null 2>&1
                                                                    echo "over-budget  exit=$?"
Expected output
-rw-r--r--
no-args      exit=0
over-budget  exit=126

Two failures, and the prompt asked for neither.

It is not executable, despite being told to make it so — so every invocation returns 126 and nothing runs.

Called with no arguments it exits 0. It printed a usage message, which reads like a refusal, and then returned success. A CI stage that calls this with a missing path gets a green build and concludes the run was within budget. That is the fail-open bug Module 8 spent a whole lab on, reproduced here in a script whose entire job is to say no.

Note how both slipped past: the prompt spent its words on the message text and one clause on the exit status, and the agent optimised for the words. In a gate, the exit code is the product and the message is the packaging.

Hand both back:

Two problems with budget-check.sh.

1. I asked you to make it executable and it is mode 644. It could not be run.
2. Run it with no arguments: it prints usage and exits 0. A CI stage that calls this
   with a missing path gets a pass. That is the fail-open bug — the same class Module 8
   taught: a check that cannot evaluate must not report success.

Fix both. Missing or unreadable arguments must exit non-zero. While you are there, decide
what it should do if the telemetry file exists but contains no api_request events at all,
and make that decision explicit in the code with a comment saying why.
./agentops/budget-check.sh >/dev/null 2>&1;                echo "no-args        exit=$?"
./agentops/budget-check.sh /nonexistent 1000 >/dev/null 2>&1;  echo "missing-file   exit=$?"
: > /tmp/empty.jsonl
./agentops/budget-check.sh /tmp/empty.jsonl 1000 >/dev/null 2>&1; echo "empty          exit=$?"
./agentops/budget-check.sh agentops/otel-out/telemetry.jsonl 1000 >/dev/null 2>&1
                                                            echo "over-budget    exit=$?"
./agentops/budget-check.sh agentops/otel-out/telemetry.jsonl 500000 >/dev/null 2>&1
                                                            echo "within-budget  exit=$?"
Expected output
no-args        exit=1
missing-file   exit=1
empty          exit=1
over-budget    exit=1
within-budget  exit=0

Exactly one path exits 0, and it is the one that positively established the run was inside budget. Everything else — including "I could not tell" — is a failure. That is what fail-closed looks like in five lines of evidence.

The empty-file case is the one worth having argued about: a telemetry file with no request events could mean a run that cost nothing, or a collector that was not running. Those are indistinguishable from the data, so the only safe reading is refusal.

One thing it does not do yet: every failure exits 1, so a caller cannot tell "over budget" from "could not evaluate". Module 8's gate used 2 for a deliberate deny and 1 for an internal error, precisely so a pipeline can treat them differently. Splitting them is the first exercise.

Step 9 — Measure this lab with this lab​

You now own an instrument. Point it at the thing you just did.

python3 agentops/ledger.py agentops/otel-out/telemetry.jsonl "m4-last-run"

Then ask the question the ledger exists to answer: where did the money in this module actually go? On the captured session it was not where you would guess. The two most expensive runs were not any of the comparisons:

Whatmodelcostturns
Writing ledger.py (Step 4)Sonnet$1.7952
Auditing and fixing it (Step 5)Sonnet$1.2732
Fixing budget-check.sh (Step 8)Sonnet$1.2228

Building the tooling cost six times what all the measurements cost put together. That is normal and it is worth internalising before you propose this at work: the instrumentation is a one-off capital cost, the measurements are nearly free forever, and the payback is every staffing decision you make afterwards with numbers instead of opinions.

It also explains why the tooling is worth delegating to an agent and the measurements are not: one is a few hundred lines of fiddly parsing you will write once, the other is a shell function you will run a thousand times.

Which model for this lab, and why​

The cost module should be exemplary about its own bill, so here it is, split by what the work actually is.

Steps 1, 4, 5 and 8 are authoring — a collector config, a parser over an undocumented record structure, an audit that has to reason about why two numbers disagree, and a gate whose exit codes matter. That is judgment, and the table above is what it cost: $4.28 across four Sonnet runs, most of this lab's total. Run these on Sonnet. Step 5 in particular is the one place a cheaper model would likely have accepted your framing and patched the sum without questioning whether billable_tokens was justified.

Steps 6 and 7 must run on exactly the model each row names. They are the measurement; the model is the variable.

Steps 0, 2, 3 and 9 involve no model at all — Docker, a curl-equivalent, and Python. As in Module 8, notice which parts have no model in them: the instrumentation is deterministic, which is what makes it something you can put in CI.

If you want to run the whole thing cheaply, run the authoring steps on Haiku and expect to review the output harder — particularly the Step 5 audit, which is the step where being talked into a plausible fix is the failure mode.

Limits — what the ledger does and does not tell you​

  • cost_usd is Claude Code's own estimate, not your invoice. It is computed from token counts and a price table inside the tool. It will not reconcile to the penny with billing, it knows nothing about your contract, and it is the right number for comparing runs and the wrong number for reporting spend to finance.
  • It only sees runs you instrumented. Every measurement here required the telemetry environment variables. Your colleague's session, your own session yesterday, the run inside a CI job that did not export — none of them are in the ledger. A ledger that covers a quarter of your runs will produce a confident quarterly total that is wrong by a factor of four, and it will not warn you.
  • The token accounting is a moving target. Step 5 is not a one-off. The counters that mattered changed once already, silently; treat the "does the token total square with the cost?" check as something to re-run periodically, not a bug you fixed.
  • The telemetry contains identifying data. The same event carries user.email, user.id, organization.id and terminal.type alongside the numbers. That is fine on your laptop and is a conversation to have before this ships to a shared dashboard or a log aggregator with a broad audience.
  • A cheaper row is not a better run. Step 6 only became a decision because the answers were graded too. A ledger measures spend; it cannot tell you the cheap run was wrong, and the cheapest run of all is one that failed to do the task. Pair every cost comparison with a correctness check or you are optimising for silence.
  • Two runs are an anecdote. Every table in this lab is a single pair. Step 7's result reversed the intuition; it might reverse again on your workload. The instrument is the deliverable — not these numbers.

Step 10 — Take it to your own runs​

The comparison that matters is not Northstar's. It is the task your team runs most often, which almost nobody has ever priced.

Pick that task — the PR summariser, the log triager, the test-failure explainer, whatever runs dozens of times a day — and:

Help me price the agent task we run most often here.

1. Ask me what the task is, how many times a day it runs, and what "correct" means for
   it — specifically, what a wrong answer costs us and who notices.
2. Draft the exact run_ledger invocation to measure it, with the variable I should
   change first, and say why that variable rather than the others.
3. Tell me what result would change our staffing decision, before I run it — the number
   that would make us move models, and the number that would make us keep paying.

Push back if the task has no checkable notion of correct. If we cannot grade the answer,
tell me so and say what we would have to build first, because a cost comparison without
one just tells us which model is quieter.

Point 3 is the one to insist on. Decide what result would change your mind before you measure, or you will find a way to read whatever comes back as confirmation of what you already do.

Two rules for the comparisons you run for real:

  • Grade the answer, always. A cost table without a correctness column is an argument for the cheapest model that produces text, and you will win that argument and regret it.
  • Re-run it after every upgrade. Model prices change, caching behaviour changes, and Step 5 is proof that the accounting itself changes underneath you. A staffing decision from six months ago was made against a price table that no longer exists.

Teardown​

The instrumentation is the deliverable — keep collector.yaml, ledger.py and budget-check.sh. Later modules and the capstone reuse them. Remove only the captured telemetry and the container.

docker rm -f otel-ledger
rm -rf agentops/otel-out /tmp/empty.jsonl
git status --short agentops/
Expected output
otel-ledger
?? agentops/budget-check.sh
?? agentops/collector.yaml
?? agentops/ledger.py

Three scripts, ready to commit — the Agent Run Ledger, shipped the way you shipped the boundary in Module 2 and the context pack in Module 3.

You made the agent's own work visible, and then found out the obvious way to count it was wrong by a factor of 411 — wrong quietly, and wrong in the direction that would have ranked your expensive run as the cheap one. You fixed the accounting, priced a real judgment task across two models and two effort levels, graded the answers as well as the bills, and turned the ledger into a gate that fails closed. Module 3 gave the agent's findings provenance; this module gives the agent's own work provenance.

scripts/grade.sh m4 certifies the instrumentation — the pipelines, the parser, the budget gate, and the two fixes you made: that the ledger counts all four token categories, and that the gate refuses rather than passes when it cannot evaluate.
