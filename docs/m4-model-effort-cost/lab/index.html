Lab — The Agent Run Ledger

In the lesson you learned that every Claude Code run generates cost, token, and behavior data that evaporates the moment the session ends — and that making model and effort deliberate choices only pays off if you can measure the result. This lab makes the run visible. You will stand up a local OpenTelemetry collector, export Claude Code's telemetry to it, build the Agent Run Ledger that rolls a run's raw telemetry into one auditable record, compare the same task across models and effort levels, and set a budget alert that flags a run for exceeding a token threshold.

Every step runs Claude Code non-interactively with claude -p, so each run's telemetry shows up as data you can read and grade.

Where you are working

All commands run from the root of the agentic-ops-lab workspace. The collector config, the ledger script, and the captured telemetry are committed artifacts under agentops/ — the same directory Module 3 used for checkpoints. You are building the instrumentation you would ship to a team, not throwaway scratch.

Where you run everything. All commands below, and every claude session, run from the root of the agentic-ops-lab workspace you cloned in setup:

cd ~/agentic-ops-lab

Step 0 — Prerequisites​

Confirm Claude Code and Docker are available. The collector runs as a single container; you do not need the full Northstar stack for this lab.

claude --version
docker version --format '{{.Server.Version}}'
Expected output
2.1.197 (Claude Code)
28.0.1

Your versions will differ — anything recent is fine. If claude is not found, revisit the Environment setup page.

Confirm Claude Code exposes the two flags this lab depends on — --model and --effort — both of which work with -p:

claude --help 2>&1 | grep -E '\-\-model|\-\-effort'
Expected output
  --effort <level>                      Effort level for the current session
  --model <model>                       Model for the current session. Provide

These are the two staffing dials from the lesson, exposed on the CLI: --model picks who runs the task, --effort picks how hard they think about it. You will vary both later and measure the difference.

Step 1 — Have Claude write the collector config​

Claude Code speaks OpenTelemetry (OTLP). To capture that telemetry as something you can parse, you run a collector — a small process that receives OTLP over the network and writes it to a file.

You are not going to type that config. Writing YAML from a spec is exactly the work you delegate, and the interesting part of this step is whether the agent gets the two non-obvious details right without being told them. Start a session:

claude --permission-mode acceptEdits

Give it the problem, not the file:

Write agentops/collector.yaml — an OpenTelemetry Collector config for capturing
Claude Code's own telemetry.

Requirements:
  - receive OTLP over HTTP on the standard OTLP/HTTP port, on 0.0.0.0
  - export everything to a file at /out/telemetry.jsonl
  - keep the collector's own logs quiet (error level only)
  - the pipelines must match what Claude Code actually exports -- check that
    before you choose them, and tell me which signal types you included and
    which you deliberately left out

Also create the directory agentops/otel-out.

What Claude does. It writes the config and creates the directory. The closing clause is the one doing the work: it forces the agent to state its pipeline choice as a decision rather than emit a plausible three-pipeline default.

What you observe — and what to check. Two details decide whether this config works at all:

  1. The port is 4318. That is OTLP/HTTP. If the agent wrote 4317, that is OTLP/gRPC — a different protocol on a different receiver, and nothing will arrive.
  2. There is no traces pipeline. Claude Code exports metrics and log-record events, not spans. The events (claude_code.api_request, claude_code.tool_result) arrive on the logs pipeline, and that is what the ledger is built from. An agent that adds traces has written a pipeline that will never receive anything — harmless here, but it means it guessed rather than checked.

Confirm both:

grep -E 'endpoint:' agentops/collector.yaml
yq '.service.pipelines | keys' agentops/collector.yaml
Expected output
        endpoint: 0.0.0.0:4318
[
  "logs",
  "metrics"
]

The receiver listens on 4318, and the pipelines are exactly logs and metrics — no traces. Key order will vary. If traces appears, delete that pipeline before continuing, and note what just happened: the agent produced a confident, well-formed, wrong answer. Pricing that failure mode correctly is what this whole module is about.

Step 2 — Start the collector​

Run the collector as a single container, mounting your config in and the output directory out:

docker run -d --name otel-ledger \
  -p 4318:4318 \
  -v "$PWD/agentops/collector.yaml:/etc/otelcol/config.yaml:ro" \
  -v "$PWD/agentops/otel-out:/out" \
  otel/opentelemetry-collector-contrib:latest \
  --config=/etc/otelcol/config.yaml
sleep 4
docker ps --filter name=otel-ledger --format '{{.Names}} {{.Status}}'
Expected output
otel-ledger Up 4 seconds

The first run pulls the collector image, which takes a moment; subsequent runs are instant. If the status is not Up, check docker logs otel-ledger — the most common cause is the config path being wrong, which the collector reports on startup.

Step 3 — Export a run's telemetry​

Now point Claude Code at the collector and run a real task. The environment variables do the wiring: enable telemetry, choose the OTLP exporters, set the protocol to HTTP, and aim at the collector's endpoint. The short export intervals just make the telemetry flush quickly so you are not waiting a full minute for data.

CLAUDE_CODE_ENABLE_TELEMETRY=1 \
OTEL_METRICS_EXPORTER=otlp \
OTEL_LOGS_EXPORTER=otlp \
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf \
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 \
OTEL_METRIC_EXPORT_INTERVAL=2000 \
OTEL_LOGS_EXPORT_INTERVAL=2000 \
claude -p "Read CLAUDE.md and name, in one sentence, the services Northstar runs." \
  --model sonnet --permission-mode acceptEdits
Expected output
Northstar runs three services: orders-api (Python/FastAPI, port 8080), inventory-api (Go/chi, port 8081), and PostgreSQL (port 5432).

The agent read the file and answered — and note that its answer is the only thing on stdout. The telemetry did not pollute the output; it flowed over the network to the collector instead. That separation is the point: the run's result goes to you, the run's instrumentation goes to the ledger.

Give the collector a few seconds to receive the final flush, then confirm telemetry landed:

sleep 5
wc -l < agentops/otel-out/telemetry.jsonl
Expected output
7

The exact line count will differ — each line is one OTLP batch of metrics or log records, and the number depends on timing. What matters is that it is non-zero: the collector received Claude Code's telemetry and wrote it as JSON lines. If it is 0, the run finished before the flush — re-run Step 3 and wait a little longer.

Peek at what the agent's API request recorded — this is the raw evidence the ledger will summarize:

python3 -c "
import json
for line in open('agentops/otel-out/telemetry.jsonl'):
    if not line.strip(): continue
    try: d=json.loads(line)
    except: continue
    for rl in d.get('resourceLogs',[]):
        for sl in rl.get('scopeLogs',[]):
            for rec in sl.get('logRecords',[]):
                if rec.get('body',{}).get('stringValue')=='claude_code.api_request':
                    a={x['key']:list(x['value'].values())[0] for x in rec['attributes']}
                    print({k:a.get(k) for k in ('model','input_tokens','output_tokens','cost_usd','duration_ms','effort')})
"
Expected output
{'model': 'claude-sonnet-5', 'input_tokens': '16695', 'output_tokens': '190', 'cost_usd': 0.1966, 'duration_ms': '2106', 'effort': 'high'}

Your token counts, cost, and duration will differ on every run — this is a point-in-time snapshot of one real execution. The pattern is the lesson: a single claude_code.api_request event carries the model, the input/output tokens, the estimated cost in USD, the wall-clock duration, and the effort level. Every field the ledger needs is already here, emitted by the agent about its own work. (effort: high is the default even though you did not pass --effort — you will change it in Step 6.)

Step 4 — Have Claude build the Agent Run Ledger​

Raw telemetry is the timesheet; the ledger is the invoice. You need a script that reads a run's telemetry file and rolls it into a single record — one row per run, in the terms you actually budget in.

This is a real piece of tooling, and it is the kind you should never hand-type from a listing: the parsing is fiddly, the OTLP value-wrapping is easy to get wrong, and you will want to change it later. Specify it and let the agent write it.

Write agentops/ledger.py — the Agent Run Ledger.

Usage: python3 agentops/ledger.py <telemetry.jsonl> [label]
It prints ONE JSON row summarising the whole run.

Read agentops/otel-out/telemetry.jsonl first and work out the actual record
shape before you write any parsing. Two things will bite you:
  - OTLP wraps every attribute value as {"stringValue": ...} / {"intValue": ...},
    so attributes need unwrapping before use
  - Claude Code's events arrive as log records, not spans

Claude Code's per-request event carries its name in the log record's
`body.stringValue` — the string `claude_code.api_request` — and the numbers live
in that record's `attributes` list: model, input_tokens, output_tokens, cost_usd,
duration_ms.

The row must carry, accumulated in a single pass over the records, using exactly
these key names so downstream tooling can read it:
  model, input_tokens, output_tokens, cost_usd, duration_ms
plus the number of tool calls, how many of them failed, and the number of
permission decisions.

Numeric attributes must come out as numbers, not strings — OTLP encodes them as
{"intValue": "16000"} and {"doubleValue": 0.11}, so intValue needs an int cast.

Print nothing but the JSON row.

What Claude does. It reads the real telemetry file before writing the parser — which is the instruction that matters, because the OTLP record structure is not guessable, and an agent that skips this step writes a parser for an imagined format that returns zeros against the real one.

What you observe. Have it run its own script against the telemetry you exported in Step 3. If the token counts come back as zero or fields are missing, the attribute unwrapping is wrong. That is the most likely bug here and it fails quietly — a row of zeros looks like a cheap run, not a broken parser.

Run the ledger against the telemetry you captured:

python3 agentops/ledger.py agentops/otel-out/telemetry.jsonl "read-claudemd" | python3 -m json.tool
Expected output
{
    "label": "read-claudemd",
    "session": "0fea62bf",
    "model": "claude-sonnet-5",
    "effort": "high",
    "input_tokens": 16695,
    "output_tokens": 190,
    "cost_usd": 0.1966,
    "wall_ms": 4116,
    "tool_calls": 1,
    "tool_failures": 0,
    "approved": 1,
    "denied": 0,
    "human_interventions": 0
}

Exact numbers vary per run. This is the invoice: one row that answers "what did this run cost and how did it behave." The agent made one tool call (reading CLAUDE.md), you approved one permission decision, it spent this many tokens for this many dollars. A shrug became a record.

The ledger is Module 3's evidence discipline, applied to the run

Every field in that row has provenance: it came from a specific telemetry event the agent emitted about its own execution, captured with its session ID and timestamp. You are not estimating what the run cost — you are reporting it from the run's own instrumentation. That is the same standard you held the agent's findings to in Module 3, now applied to the agent's work.

Step 5 — Compare models​

The ledger's real power shows up when you run the same task different ways and read the rows side by side. First, capture two runs of one simple task on two different models. A small helper keeps each run's telemetry in its own file:

run_ledger () {   # run_ledger <label> <model> [effort]
  : > agentops/otel-out/telemetry.jsonl
  CLAUDE_CODE_ENABLE_TELEMETRY=1 \
  OTEL_METRICS_EXPORTER=otlp OTEL_LOGS_EXPORTER=otlp \
  OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf \
  OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 \
  OTEL_METRIC_EXPORT_INTERVAL=2000 OTEL_LOGS_EXPORT_INTERVAL=2000 \
  claude -p "In one sentence, summarize what a readiness probe checks." \
    --model "$2" ${3:+--effort "$3"} >/dev/null 2>&1
  sleep 5
  python3 agentops/ledger.py agentops/otel-out/telemetry.jsonl "$1"
}

run_ledger "haiku" haiku
run_ledger "sonnet" sonnet
Expected output
{"label": "haiku", "session": "a1b2c3d4", "model": "claude-haiku-4-5", "effort": null, "input_tokens": 15980, "output_tokens": 34, "cost_usd": 0.0219, "wall_ms": 1740, "tool_calls": 0, "tool_failures": 0, "approved": 0, "denied": 0, "human_interventions": 0}
{"label": "sonnet", "session": "e5f6a7b8", "model": "claude-sonnet-5", "effort": "high", "input_tokens": 16112, "output_tokens": 41, "cost_usd": 0.1103, "wall_ms": 2210, "tool_calls": 0, "tool_failures": 0, "approved": 0, "denied": 0, "human_interventions": 0}

Your exact numbers will differ, and Haiku does not report an effort attribute (it does not expose the effort dial) — that is expected. The pattern is the lesson made measurable: the same one-sentence summarization task costs several times more on Sonnet than on Haiku. For a mechanical summary, that extra spend buys you nothing — this is the summarizer role from the lesson, and the ledger just showed you why it belongs on the cheap model.

This is the staffing decision, now backed by data

Before the ledger, "use the cheap model for summaries" was advice. Now it is a measured cost difference you can point at. Multiply that per-run gap across every summary your team runs a day, and the ledger has just made the business case for the staffing rule the lesson argued for.

Step 6 — Compare effort levels​

Now hold the model fixed and turn the effort dial. Run the same task at low and high effort on Sonnet:

run_ledger "sonnet-low"  sonnet low
run_ledger "sonnet-high" sonnet high
Expected output
{"label": "sonnet-low", "session": "11aa22bb", "model": "claude-sonnet-5", "effort": "low", "input_tokens": 16050, "output_tokens": 12, "cost_usd": 0.0421, "wall_ms": 1980, "tool_calls": 0, "tool_failures": 0, "approved": 0, "denied": 0, "human_interventions": 0}
{"label": "sonnet-high", "session": "33cc44dd", "model": "claude-sonnet-5", "effort": "high", "input_tokens": 16112, "output_tokens": 41, "cost_usd": 0.1103, "wall_ms": 2210, "tool_calls": 0, "tool_failures": 0, "approved": 0, "denied": 0, "human_interventions": 0}

Your numbers will vary — and on a task this trivial the gap is small and a little noisy, which is itself the point. Low effort produces fewer output tokens (less deliberation) and finishes faster; high effort spends more thinking to arrive at the same simple answer. For "summarize a readiness probe," the low-effort run got there for less. The effort dial earns its keep on hard tasks where the extra reasoning changes the answer — on easy ones, high effort is just spend you did not need.

Small tasks show a small, noisy delta — that is honest

On a one-sentence task the effort difference is modest and can jitter run to run, partly because cache reads and writes dominate the token count on tiny prompts. Do not read a single pair of rows as a law. The ledger's job is to let you measure the delta on your real tasks at your scale — where the effort choice, run thousands of times, compounds into real money.

Step 7 — Have Claude write the budget alert​

A ledger you only read after the fact is a post-mortem. Turn it into a control: a budget check that flags any run exceeding a token threshold. This is the cost SLO from the lesson — a stated expectation with an alarm when it is breached.

Write agentops/budget-check.sh — a budget alert over a run's telemetry.

Usage: budget-check.sh <telemetry.jsonl> <max_tokens>

It sums the run's total tokens (input + output, from the same
`claude_code.api_request` events the ledger reads) and compares them against the
budget:
  - within budget  -> print an OK line naming the totals, exit 0
  - over budget    -> print a line beginning "BUDGET ALERT" naming the totals and
                      the budget, and exit 1

Both arguments are required; refuse with a clear message if either is missing.
Make it executable.

Reuse the same token accounting as agentops/ledger.py rather than inventing a
second one — two different answers to "how many tokens did that run cost" is
worse than having no answer at all.

What Claude does. It writes the script and marks it executable.

What you observe — and the line worth checking. The exit codes. A budget check that prints ALERT and exits 0 is decoration: nothing in CI will ever notice it. Non-zero on breach is what makes this a control rather than a log line, and it is the detail agents most often drop when the prompt spends more words on the message text than on the exit status.

Run it with a deliberately low budget so you can see the alarm fire — a real run reads tens of thousands of tokens, so a 1,000-token budget will always breach:

./agentops/budget-check.sh agentops/otel-out/telemetry.jsonl 1000 || true
Expected output
BUDGET ALERT: run used 16153 tokens, over budget of 1000

The exact token count will differ. The alert fired and exited non-zero — which means you could put this check in front of every agent run, or in CI, and have it fail the pipeline when a run blows its budget. That non-zero exit is the whole point: it turns a number in a ledger into an alarm a system can act on.

Now run it with a realistic budget to see the pass path:

./agentops/budget-check.sh agentops/otel-out/telemetry.jsonl 100000
Expected output
within budget: 16153 tokens (budget 100000)

Same run, sensible budget, clean pass. This is your model regression check in miniature: pick the threshold from what the task should cost (measured from the ledger), and the day a run suddenly needs ten times that — because someone bumped the effort, bloated a prompt, or selected the wrong model — the alarm tells you before the bill does.

Step 8 — Run the grader​

Turn "the outputs looked right" into a deterministic pass. The grader checks that the ledger instrumentation is actually in place: the collector config defines the metrics and logs pipelines, the ledger script produces a valid record from real telemetry, and the budget check flags an over-budget run.

./scripts/grade.sh m4
Expected output
Grading: Module m4
========================

Checking: Agent Run Ledger

  ✓ collector config defines metrics + logs pipelines and a file exporter
  ✓ ledger.py present and emits a JSON row with model + cost + tokens
  ✓ budget-check.sh flags an over-budget run (non-zero exit)
  ✓ telemetry captured a claude_code.api_request event with cost + tokens

========================
RESULT: PASS (4 passed)

If the pipelines check is red, re-run Step 1. If the ledger check is red, re-run Step 4 and confirm agentops/otel-out/telemetry.jsonl has content from a real run (Step 3). If the telemetry check is red, the collector was not running or the export env vars were wrong — restart it with Step 2 and re-run Step 3.

Teardown​

The ledger instrumentation (agentops/collector.yaml, agentops/ledger.py, agentops/budget-check.sh) is a real deliverable — later modules and the capstone reuse it, so keep those. Remove only the captured telemetry and stop the collector.

docker rm -f otel-ledger
rm -rf agentops/otel-out
Expected output
otel-ledger

docker rm -f prints the container name it removed. The collector is gone and the captured telemetry is cleared; the scripts that produce and read it remain.

Confirm the instrumentation is still in place — these should show as new/untracked files ready to commit:

git status --short | grep agentops
Expected output
?? agentops/budget-check.sh
?? agentops/collector.yaml
?? agentops/ledger.py

The three scripts you wrote are present and untracked — this is the Agent Run Ledger, ready to ship to a teammate the way you shipped the boundary in Module 2 and the context pack in Module 3.

You made the agent's work visible and turned it into a ledger you can act on: a collector that captures Claude Code's own telemetry, a ledger script that rolls each run into one auditable record of model, effort, tokens, cost, and behavior, a side-by-side comparison that turned the lesson's staffing advice into measured cost deltas, and a budget alert that fires when a run exceeds expectation. Module 3 gave the agent's findings provenance; this module gave the agent's own work provenance. In the Deep Dive you will widen the lens to the two budgets every agentic ops team runs at once — what the infrastructure costs, and what running the agents costs — and why keeping them separate is the whole discipline.
