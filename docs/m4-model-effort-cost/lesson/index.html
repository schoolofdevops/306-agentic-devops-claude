Model and Cost Engineering

In Module 3 you gave the agent a durable operating contract and taught it to collect evidence with provenance. Every fact it produced could be traced back to where it came from. This module extends that same discipline to the agent's own work: the run itself is evidence, and right now you cannot see it.

▶ M4: Model and Cost EngineeringOpen fullscreen ↗

Here is the gap. When you ask Claude Code to diagnose the readiness bug, you get an answer, but you have no record of how much that answer cost. Which model ran it. What effort level. How many tokens went in and came back. How many tool calls it made, how many you had to approve, how many times you had to step in and correct it. On one task that opacity is fine. Across a platform team running the agent dozens of times a day, it is the difference between a tool you can budget for and a line item that surprises you at the end of the month. You already meter your infrastructure: CPU, memory, request rates. The agent is now part of your infrastructure, and it is unmetered.

This module closes that gap in two moves. First, you learn to make model and effort deliberate choices rather than defaults you never think about: staffing decisions, where you pick the right capability for the job instead of sending your most expensive reasoner to write a changelog. Second, you learn to turn every agent run into a measured, auditable record: the Agent Run Ledger, so that "how much did that cost" has an answer you can point to, the same way "is orders-api ready" had an answer in Module 1.

Why model choice is a staffing decision​

Think about how you staff a real team. You do not put your principal engineer on the task of renaming a variable across forty files, and you do not hand a critical production migration to the intern on their first week. You match the person to the job by four things: how capable they need to be, how fast you need it, what it costs to occupy their time, and how expensive a mistake would be. A rename is cheap to get wrong and cheap to fix, so you give it to whoever is free. A migration that could corrupt the orders database is expensive to get wrong, so you give it to someone whose judgment you trust and you have them double-check.

Analogy: choosing a model is hiring for a shift. Each model is a candidate with a different résumé, one is brilliant and expensive and deliberate, one is fast and cheap and good enough for routine work, one sits in the middle. You are not looking for "the best" in the abstract; you are looking for the right fit for this task, given what it costs you to be wrong. Sending Opus to summarize a log file is like flying in a staff engineer to reset someone's password. It works, and you overpaid for it.

Claude Code lets you choose the model per session, and the models sort roughly along the capability-versus-cost line:

ModelRelative strengthRelative costFits
OpusHighest capability, deepest judgmentHighestArchitecture, security review, complex multi-file changes, ambiguous debugging
SonnetStrong, balanced, the sensible defaultMiddleMost investigation, routine implementation, day-to-day ops work
HaikuFast, capable of mechanical workLowestSummaries, changelogs, formatting, high-volume simple classification

The pricing gap between the tiers is large. The most capable model costs several times the cheapest per token, so the choice is not cosmetic. It compounds. A task you run once a day at the wrong tier is a rounding error; the same task run by every engineer on every branch, all day, is a budget line.

The models change; the reasoning does not

Model names and prices move over time: new tiers ship, prices shift. Do not memorize a specific model ID as "the cheap one." Memorize the decision: capability, latency, price, failure cost. When the lineup changes, you re-run the same four-way judgment against the new options. The staffing logic outlives any particular roster.

Effort: how hard the same person works​

Model is who you assign. Effort is how hard you ask them to think about it. The same engineer can glance at a one-line fix or spend an afternoon reasoning through a subtle concurrency bug, and you would not want them spending the afternoon on the one-liner, or glancing at the concurrency bug. Effort is that dial, applied to the model you already chose.

Analogy: effort is the difference between "give me your gut read" and "go away and think about this properly." For "which of these three log lines is the error," the gut read is correct and instant, and asking for a deep analysis just burns time and money to arrive at the same place. For "why does this only fail under load after a deploy," the gut read is a guess, and you actually want the deliberate, show-your-working version. Turning the dial up buys you more reasoning, more tokens spent thinking before acting, which costs more and takes longer. Turning it down buys speed and thrift at the price of depth.

The two dials interact, and that is the whole art of it:

A cheap model at high effort and an expensive model at low effort are both real, sensible configurations, they just suit different tasks. The failure mode is running everything at the top-right corner because you never thought about it. That is not caution; it is paying for maximum reasoning on tasks that never needed it.

Mapping models and effort to roles​

The staffing analogy gets concrete when you stop thinking about individual tasks and start thinking about roles. In Module 5 you will split agent work into distinct jobs, and later modules give those jobs to separate subagents. Each role has a characteristic capability profile, and that profile tells you how to staff it:

  • Investigator: reads evidence and reasons toward a root cause. It needs genuine reasoning but rarely the deepest tier; a balanced model at medium effort finds the readiness bug without overpaying. Send Opus here only when the investigation is genuinely ambiguous.
  • Implementer: turns a decision into a code change. Routine changes (add a field, fix a path) are fine on a balanced model; a complex multi-file refactor with subtle interactions is where the top tier earns its price, because a wrong implementation is expensive to catch and fix.
  • Reviewer: the one role where you almost always pay for the best. A reviewer's whole job is judgment: catching the subtle bug, the security implication, the thing that looks fine and is not. This is your senior engineer signing off on the migration. Underpaying here is a false economy: the cost of the review is tiny next to the cost of the defect it should have caught.
  • Summarizer: mechanical restatement of work that already happened. Writing a changelog from a diff, a status line from a run. This is the cheapest model at the lowest effort, and paying more for it is pure waste.

The reviewer/summarizer split is the clearest illustration of the principle. Both are "read something and produce text," but one is a judgment call where mistakes are costly and the other is transcription where mistakes are cheap and obvious. Same kind of task, opposite staffing: the failure cost differs, not the surface activity.

The run is evidence you cannot yet see​

Now the second half of the module. You have learned to choose models and effort deliberately, but a choice you cannot measure is a choice you cannot defend or improve. If someone asks "why is our agent spend up 40% this month," or "did switching the reviewer to Opus actually catch more bugs, or just cost more," you need data about the runs themselves. Right now that data exists, it is generated on every run, but it evaporates the moment the session ends.

Analogy: a Claude Code session with no telemetry is a contractor who does good work and hands you no invoice, no timesheet, no materials list. You can see the finished wall. You cannot see that it took nine hours, used three trips to the supplier, and that they had to redo the wiring twice because the first plan was wrong. When the bill is a flat "trust me," you cannot budget, you cannot compare two contractors, and you cannot spot the job that quietly cost triple. The work being good is not the same as the work being accountable.

This connects directly to Module 3's evidence contracts. There, you insisted that any fact the agent produced come with provenance (source, time, uncertainty) so you could trust it. The agent's own execution deserves the same treatment. Every run produces facts: which model, what effort, how many tokens, what it cost, how many tools it called, how many permissions you approved or denied, how many times a human intervened. Those facts are operational evidence about the agent as a system, and like all evidence they are worthless if they evaporate. You need to capture them, with provenance, in a durable record.

OpenTelemetry: the agent's instrumentation​

The mechanism for capturing that evidence already exists and is a standard you likely use elsewhere in your stack: OpenTelemetry. Claude Code can emit telemetry about its own operation: metrics like token counts and cost, and events like each API request and tool decision, over the OpenTelemetry protocol (OTLP), to a collector you run.

Analogy: OpenTelemetry is the standardized diagnostic port on the agent. Modern vehicles all expose an OBD-II port: whatever the make, you plug in a standard reader and get standard readings: speed, fuel, error codes. You do not build a custom sensor rig per car. OpenTelemetry is that port for software: Claude Code emits its readings in the standard format, and any standard collector can receive them. Because it is the same protocol your services already speak, the agent's telemetry lands in the same kind of pipeline as everything else you operate, it is not a special snowflake tool, it is one more instrumented process.

You turn it on with environment variables (an enable flag and an exporter target) and Claude Code begins emitting. The readings flow to a collector: a small local process that receives OTLP data and writes it somewhere you can read. In the lab you run a lightweight collector that writes the telemetry to a file, and for the no-collector case Claude Code can print its telemetry straight to the console. Either way, the run stops being invisible.

The Agent Run Ledger​

Raw telemetry is necessary but not yet useful: it is a stream of data points and events, not an answer. The final step is to turn it into a ledger: one row per run, each row summarizing that run in the terms you actually care about.

Analogy: the ledger is the itemized invoice you build from the contractor's raw timesheet. The timesheet has every clock-in and clock-out and supply run; the invoice rolls it up into "job X: 9 hours, $340 materials, total $Y." You want the invoice, because that is the unit you budget and compare in. Raw telemetry is the timesheet. The Agent Run Ledger is the invoice, and because it is built from the real timesheet, not estimated, you can trust it.

Each ledger row captures a run as an auditable record:

FieldWhat it tells you
Session ID, timestamp, durationWhich run, when, how long on the wall clock
Model + effortHow it was staffed: the choice you now made deliberately
Input / output tokensThe size of the work in the unit you are billed in
Estimated costTokens turned into money, the number finance asks about
Tool calls (count, types, failures)How much the agent did, and where it stumbled
Permission decisions (approved / denied)How much the boundary from Module 2 was exercised
Human interventionsHow autonomous the run actually was

Read across a row and you can answer "what did this run cost and how did it behave." Read down a column across many rows and you can answer the questions that matter at team scale: which tasks cost the most, whether a model change paid off, whether a run that used to be cheap suddenly is not.

Budgets, alerts, and regression checks​

A ledger you only read after the fact is a post-mortem tool. Its real power is that it lets you set expectations in advance and get told when reality diverges, the same instinct that makes you alert on latency or error rate for your services.

Three controls fall straight out of having the data:

  • Per-role budgets. Once you know a summarizer run costs a fraction of a cent and a reviewer run costs meaningfully more, you can set a token or cost ceiling per role and flag any run that blows past it. A summarizer that suddenly costs like a reviewer is either misconfigured or being handed the wrong work.
  • Spend alerts. A simple threshold on a run ("flag any single run over N tokens") catches the runaway before it becomes a bill. This is the agent equivalent of an alert on a query that suddenly scans the whole table.
  • Model regression checks. The sharpest use of the ledger over time. If a task that reliably cost $0.10 last week now costs $1.00, something changed: a prompt got bloated, the effort got bumped, the wrong model got selected, the task got harder. You cannot notice that drift without a baseline, and the ledger is the baseline. This is exactly the Module 1 diagnose→change→verify loop applied to cost: you have a measured expectation, you detect the deviation, you investigate the cause.

Analogy: this is a cost SLO for the agent. You already run SLOs on the systems you operate (a latency budget, an error budget) and you alert when the service spends its budget faster than it should. A per-run token budget is the same contract applied to the agent: a stated expectation, and an alarm when it is breached. The agent is a system you operate now, so it gets operated on like one.

What you'll do in the lab​

You will make the agent's work visible and turn it into a ledger you can act on. You will stand up a local OpenTelemetry collector; configure Claude Code to export its telemetry to it; run a real diagnostic task against Northstar and capture the run's telemetry; build the Agent Run Ledger script that parses that telemetry into a structured per-run record; run the same task at different model and effort settings and compare the token, cost, and behavior differences side by side in the ledger; and finally set a per-run budget alert that flags a run for exceeding a token threshold, a regression check you could put in front of every agent run.

Module 3 gave the agent's findings provenance. This module gives the agent's own work provenance: a measured, auditable record of every run. By the end, "how much did that cost, and was it staffed right" is a question you can answer from data, not a shrug. The Deep Dive then widens the lens to the two separate budgets every agentic ops team runs at once: what the infrastructure costs, and what running the agents that manage it costs.
