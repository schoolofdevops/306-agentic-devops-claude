Lab — Triage a Degraded Cluster

You are on call. The northstar cluster is degraded — five workloads are unhealthy, nobody has said which faults are related, and you have fifteen minutes before someone asks what's broken. You are going to point an agent at that cluster and use it: triage all five faults, rank them by blast radius, remediate the one that matters, and then measure something the RBAC you're relying on does not protect.

This is an operate lab, not a build lab. Unlike Module 11, you are not handing a brief to a harness and watching it design and construct something. The operating kit — the k8s-operator role, both cluster identities, the bounded kubectl wrapper, the triage skill, and the deny hook — already exists in this repository, committed by the platform team before you ever open a session. Your job is to inspect it, prove it holds, and then use it on a real incident. What you own is the brief, the findings, the ranking, the remediation, and the measurement — never the kit itself.

By the end you will have triaged five faults into ranked, evidence-backed findings, fixed the one that mattered through an identity scoped for exactly that job, and measured — not assumed — what a "read-only" agent can still see.

Where you are working

Every command in this lab runs from the root of the agentic-ops-lab workspace you cloned in setup:

cd ~/agentic-ops-lab

The kit lives under platform/ (RBAC, kubeconfig generator, the bounded tool) and .claude/ (the role, the triage skill, the deny hook). Both platform/bin/kubectl-bounded and platform/kubeconfigs/make-agent-kubeconfig.sh resolve paths relative to your current directory, so stay at the workspace root for every command below unless a step says otherwise.

Step 0 — The ticket, and the posture for this lab​

The ticket, as it would actually arrive: northstar is degraded, five workloads are unhealthy, and you're the one who picked it up. Nothing here is a chart defect you're going to fix by editing a values file — it's a live cluster, and every read and write you make goes through a real identity with real, narrow authority.

This lab runs in acceptEdits. It is normal iterative work — you are reading cluster state, writing a handful of your own findings files, and applying one scoped patch — not a long autonomous build cycle, so there is no reason to turn permission prompts off entirely. The mechanical boundary in this module is RBAC and a deny hook, not the prompt, so leaving prompts on for Bash calls costs you nothing:

claude --agent k8s-operator --model claude-sonnet-5 --permission-mode acceptEdits

You won't launch that yet — Step 4 inspects the kit first, and Step 10 is where you actually launch as this role. Read on.

The script is idempotent — apply against objects that already exist reports unchanged or configured rather than erroring, so running it again on a cluster from an earlier session is safe. It also carries a node-capacity guard: it refuses to plant fault 03 (below) on a node with 10Gi or more allocatable memory, because on a bigger node that fault would schedule instead of staying Pending, and the guard would rather fail loudly than plant a fault that silently doesn't reproduce.

That's roughly 7.74Gi. Hold on to it — resource-limit-test requests 10Gi per replica, and that gap is why it stays Pending rather than a fluke.

Four things worth noting before you rely on any of them:

  • Skill is on k8s-operator's tools list. Without it, the role would still find k8s-triage's SKILL.md and read it as a plain file — no schema, no discipline, and nothing in the transcript would say so. That fact was measured in Module 9 and holds here unchanged.
  • There is no Write or Edit in that tools line. k8s-operator cannot save a file, on purpose — it is a read-only triage identity, and that constraint is why you, not the agent, will be the one saving findings to disk in Step 10.
  • Two RBAC files, two kubeconfigs (plus admin.yaml, which this lab never uses) — one identity to read, one identity to write, and neither is a general-purpose credential.
  • The hook file is executable. You'll prove what it actually does in Step 7.

Read the standing context every command in this directory operates under:

cat platform/CLAUDE.md
Expected output

- cluster: `northstar` (local kind)
- namespace: `northstar`
- kubeconfig: `platform/kubeconfigs/agent-readonly.yaml`

It is the right home for a standing fact and the wrong home for a one-time brief.

Step 5 — Write your triage brief​

Every module in this course puts the brief in the learner's hands, and this one is no exception — even though, unlike Module 11, you aren't handing this brief to a harness to design something from. Here it sets the terms of this on-call session: why it matters, what's non-negotiable, and what "done" looks like before you start reading cluster state.

Write platform/SPEC.md:

# On-call triage — northstar, INC pending

## Why
Five workloads in the northstar namespace are unhealthy. Nobody has said which faults
are related or which matters most, and the standup is in fifteen minutes.

## What's non-negotiable
- Triage stays read-only. Every cluster read goes through the agent-readonly identity
  and the bounded kubectl wrapper — never a direct kubectl call, never -A.
- Remediation, when it happens, goes through the agent-remediator identity, never the
  admin kubeconfig.
- Nothing gets patched before it has been ranked.

## Done means
- All five workloads have a fixed-schema finding: imagepull-test, crashloop-test,
  resource-limit-test, liveness-probe-test, configmap-mount-test.
- The five findings are ranked by blast radius, in agentops/k8s-triage/findings.md.
- The highest-priority fault that a Deployment patch can actually fix has been
  remediated through agent-remediator, recorded in agentops/k8s-triage/remediation.md.
- Whether the read-only identity can read a Secret has been measured, not assumed, in
  agentops/k8s-triage/secret-read-measurement.md.
Why this is SPEC.md and not a second CLAUDE.md

platform/CLAUDE.md, which you just read, is injected into every turn forever — right for "which cluster, which namespace," wrong for "what does done mean this afternoon." This file is a one-time brief for one incident. Once the incident's closed, it stops costing anyone anything, because nothing keeps re-reading it.

Step 6 — Prove the read-only identity's boundary​

Before you trust agent-readonly for anything, find out what it can actually do. Not what the RBAC document says it grants — what the API server says when asked:

KC=platform/kubeconfigs/agent-readonly.yaml
for v in get list watch create update patch delete; do
  for r in pods deployments configmaps secrets; do
    printf '%-8s %-12s ' "$v" "$r"
    kubectl --kubeconfig=$KC auth can-i $v $r -n northstar 2>/dev/null
  done
done

get      secrets      yes

list     deployments  yes
list     configmaps   yes
list     secrets      yes
watch    pods         yes

watch    secrets      yes

Every mutating verb is no, on every resource. And get secrets: yes is sitting right there in an otherwise clean read-only grant. Hold on to that line — Step 13 measures exactly what it means.

Now confirm the mutation refusal for real, not just as a can-i answer:

kubectl --kubeconfig=$KC delete deployment crashloop-test -n northstar
Expected output
Error from server (Forbidden): deployments.apps "crashloop-test" is forbidden: User "system:serviceaccount:northstar:agent-readonly" cannot delete resource "deployments" in API group "apps" in the namespace "northstar"

Read who is talking: the API server, not an agent, not a hook. It refused a command you typed yourself, with no model anywhere near the terminal, in the exact words it would use for anyone else bound to this identity. That is the boundary this whole module is built on — a lock, not a sign.

Step 7 — The thesis pair: the hook, and what it isn't​

.claude/hooks/deny-cluster-mutation.sh also refuses mutating kubectl verbs, and it's worth seeing it fire before you find out what it actually is:

echo '{"tool_input":{"command":"kubectl delete pod foo -n northstar"}}' \
  | .claude/hooks/deny-cluster-mutation.sh
Expected output
{"decision":"deny","reason":"Mutating kubectl verb. This role is read-only; remediation runs under the agent-remediator identity."}

A fast, loud no, before the command ever reaches a shell.

Now take the hook out of the picture entirely — not "ask the agent to skip it," physically bypass it by calling kubectl yourself, the way you did in Step 6:

kubectl --kubeconfig=$KC delete deployment crashloop-test -n northstar
Expected output
Error from server (Forbidden): deployments.apps "crashloop-test" is forbidden: User "system:serviceaccount:northstar:agent-readonly" cannot delete resource "deployments" in API group "apps" in the namespace "northstar"

Word for word, the same refusal as Step 6. The hook is ours, and the file it lives in could be deleted. The 403 is not ours, and there is no file to delete. That pairing — hook removed, boundary still holds — is the module's whole argument in two commands.

Step 8 — Prove the second identity's boundary​

agent-remediator exists for exactly one job: patching Deployments in northstar. Prove it is scoped to that, and nothing more:

KC=platform/kubeconfigs/agent-remediator.yaml
kubectl --kubeconfig=$KC auth can-i patch deployments -n northstar
kubectl --kubeconfig=$KC auth can-i delete deployments -n northstar
kubectl --kubeconfig=$KC auth can-i patch deployments -n kube-system
kubectl --kubeconfig=$KC auth can-i get secrets -n northstar
Expected output
yes
no
no
no

In order: it can patch Deployments in northstar — that's its job. It cannot delete them — deletion is a different authority it was never granted. It cannot patch anything in kube-system — a namespaced Role, not a ClusterRole, so the write scope stops at the namespace boundary. And it cannot read Secrets.

Put that last line next to Step 6's get secrets: yes under agent-readonly. The remediator can write, which the read-only identity cannot — but it cannot read Secrets, which the read-only identity can. Neither identity is a bigger version of the other; each is scoped to exactly the one job it does.

Step 9 — Wire the environment​

platform/CLAUDE.md, which you read in Step 4, already names the cluster, namespace, kubeconfig and context every command in this directory should use — that's why the can-i checks above didn't need you to set KUBECONFIG globally, and why k8s-operator never has to ask which cluster it's pointed at.

One thing to know before you launch: the kubeconfigs you've been using are generated, not committed — check that yourself:

git check-ignore -v platform/kubeconfigs/agent-readonly.yaml
Expected output
.gitignore:45:platform/kubeconfigs/agent-*.yaml	platform/kubeconfigs/agent-readonly.yaml

Ignored. The token inside each one is a real ServiceAccount token, generated with an 8-hour lifetime. If a command in this lab suddenly starts failing auth partway through, your token expired — regenerate it, you don't need to touch RBAC to do it:

platform/kubeconfigs/make-agent-kubeconfig.sh agent-readonly platform/kubeconfigs/agent-readonly.yaml

The same pattern regenerates the remediator's: make-agent-kubeconfig.sh agent-remediator platform/kubeconfigs/agent-remediator.yaml.

Step 10 — Launch as k8s-operator, triage all five, and write your findings​

Launch the role — not a general session:

claude --agent k8s-operator --model claude-sonnet-5 --permission-mode acceptEdits

--agent starts the session with k8s-operator's system prompt, model and tool list. Prompt it:

Triage all five unhealthy workloads in the northstar namespace: imagepull-test,
crashloop-test, resource-limit-test, liveness-probe-test, configmap-mount-test.

Use the k8s-triage skill for every one of them. Emit the fixed six-field finding for
each workload, then rank all five by blast radius, worst first, in a short closing
list.

Read only. Never propose or run a mutating command.

What Claude does. It invokes the k8s-triage skill once for all five workloads, then reads each one through platform/bin/kubectl-bounded — never a bare kubectl, never -A — and emits exactly one fixed-schema record per workload. On a validated run against this exact fault set (session graded in full — see planning/lab-tests/m12-agentic-k8s.md), one finding came back like this:

workload:      liveness-probe-test
signature:     RestartLoop
root_cause:    Liveness probe hits port 9999 (nothing listens); readiness probes 8080 while nginx
               serves 80 — both probe ports wrong.
evidence:      "Liveness probe failed: ... connect: connection refused" (port 9999)
blast_radius:  2 of 2, not serving
confidence:    high

What you observe. Your run's wording will differ from this and from run to run — this is a model, not a template — but the evidence behind every finding is real and reproducible on your cluster. liveness-probe-test is the one worth reading closely, because it carries two independent defects at once: the liveness probe targets a port nothing listens on, and — separately — the readiness probe targets a path the container never serves, so the pod restarts and never goes Ready between kills. Miss the second defect and a "fixed" pod still shows zero endpoints.

That second defect is exactly why the skill's fifth read matters. A naive glance at ENDPOINTS looks fine:

NAME                            ADDRESSTYPE   PORTS   ENDPOINTS                 AGE
liveness-probe-test-svc-rnlwc   IPv4          80      10.244.0.21,10.244.0.20   14h

Two addresses listed. But an EndpointSlice lists an address whether or not it's ready — read the condition, not the column:

kubectl --kubeconfig=platform/kubeconfigs/agent-readonly.yaml get endpointslices -n northstar \
  -l kubernetes.io/service-name=liveness-probe-test-svc \
  -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]}{" ready="}{.conditions.ready}{"\n"}{end}'
Expected output
10.244.0.21 ready=false
10.244.0.20 ready=false

Both addresses, both ready=false. The k8s-triage skill reads exactly this condition and never a bare kubectl get endpoints — that older view silently drops not-ready addresses, so an empty result and "no Service exists at all" would look identical.

Because k8s-operator carries no Write or Edit tool — you confirmed that in Step 4 — it cannot save its own output to disk. Copy what it actually printed, ranked, into agentops/k8s-triage/findings.md:

# Triage findings — northstar, [today's date]

## Ranking by blast radius

1. resource-limit-test — 3 of 3, not serving (also holds cluster capacity other pods need)
2. imagepull-test — 2 of 2, not serving
3. liveness-probe-test — 2 of 2, not serving
4. crashloop-test — 1 of 1, not serving
5. configmap-mount-test — 1 of 1, not serving

## Findings

workload:      liveness-probe-test
signature:     RestartLoop
root_cause:    ...
evidence:      ...
blast_radius:  2 of 2, not serving
confidence:    high

[... one block per workload, exactly as the agent emitted it ...]

The ranking is your judgment call, informed by the agent's blast_radius field on each finding — the schema gives you the numbers, it doesn't rank them for you. Every workload needs its own six-field block, and the file needs to actually say it's ranked by blast radius, not just carry the numbers.

Step 11 — Check the findings yourself​

The kit ships an answer key. Don't look at it before you've written your own findings — that would be grading yourself with the answers open — but once findings.md exists, self-check:

cat platform/troublesim/ground-truth.md

Compare, fault by fault: did you get the right signature, the right root cause, the right blast radius? Where you differ, go back to the evidence rather than the answer key — the point isn't matching a string, it's whether your read of the evidence was sound. Note any misses; a lab that claims a clean sweep without checking is exactly the failure mode this course keeps warning about.

Step 12 — Remediate through agent-remediator​

Pick the fault your ranking put near the top that a Deployment patch can actually fix. liveness-probe-test is the clean case: both probes are misconfigured against a container that's otherwise healthy — nginx, serving on port 80, path /. Patch both probes to match reality, through the remediator identity, never admin:

KC=platform/kubeconfigs/agent-remediator.yaml
kubectl --kubeconfig=$KC patch deployment liveness-probe-test -n northstar --type='json' -p='[
  {"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/httpGet/port","value":80},
  {"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/httpGet/path","value":"/"},
  {"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/port","value":80},
  {"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/"}
]'
Expected output
deployment.apps/liveness-probe-test patched

Wait for the rollout, then check:

kubectl get pods -n northstar -l app=liveness-probe-test
kubectl get endpointslices -n northstar -l kubernetes.io/service-name=liveness-probe-test-svc \
  -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]}{" ready="}{.conditions.ready}{"\n"}{end}'
NAME                                    READY   STATUS    RESTARTS   AGE
liveness-probe-test-85575df67d-gz28m    1/1     Running   0          17s
liveness-probe-test-85575df67d-khk95    1/1     Running   0          10s

10.244.0.17 ready=true
10.244.0.18 ready=true

Both pods 1/1 Running, both endpoints ready=true. The patch went through agent-remediator — a patch verb on deployments, the exact one thing that identity was granted in Step 8 — never the admin kubeconfig, never agent-readonly, which structurally cannot patch anything at all.

Record it:

mkdir -p agentops/k8s-triage
cat > agentops/k8s-triage/remediation.md <<'EOF'
# Remediation — liveness-probe-test

Fix: livenessProbe -> port 80, path /; readinessProbe -> port 80, path /
(container serves nginx on port 80; probes previously targeted 9999 and 8080/ready).

Applied via: kubectl --kubeconfig=platform/kubeconfigs/agent-remediator.yaml

If you're following along on a shared or already-graded cluster

This patch is a real mutation to a real Deployment. If you want the fault available to re-triage later, restore it afterward: kubectl delete deployment liveness-probe-test -n northstar && kubectl apply -n northstar -f platform/troublesim/set01/04-liveness-probe-error.yaml. On your own cluster, there's no reason to — leaving it fixed is the point.

Step 13 — Measure the honest limits​

Step 6 flagged one line and asked you to hold onto it: under agent-readonly, get secrets: yes. Find out what that actually means, rather than assuming a read-only agent is a harmless one:

KC=platform/kubeconfigs/agent-readonly.yaml
kubectl --kubeconfig=$KC auth can-i get secrets -n northstar
kubectl --kubeconfig=$KC get secret demo-app-credentials -n northstar -o jsonpath='{.data.api_key}{"\n"}'
kubectl --kubeconfig=$KC get secret demo-app-credentials -n northstar -o jsonpath='{.data.api_key}' | base64 -d; echo
Expected output
yes
c2stZGVtby1ub3QtcmVhbC0xMjM0NQ==
sk-demo-not-real-12345

The can-i check said yes. The read actually succeeded. And kubectl decoded it for free, because Kubernetes Secrets are base64-encoded, not encrypted — that gap is part of what this measurement is about. demo-app-credentials is a deliberately fake value planted by platform/troublesim/inject.sh specifically so this measurement reproduces on every cluster, not just the one it was first taken on.

A read-only agent, one that cannot delete, patch or create a single thing, is still a path for every Secret in this namespace to leave the cluster in its context window — because "read-only" was never a promise about what it reads, only about whether it can mutate. The ClusterRole behind agent-readonly grants get/list/watch on resources: ["*"], and that wildcard includes Secrets along with everything else, whether or not anyone decided it should.

Record the measurement — not the conclusion, the measurement:

cat > agentops/k8s-triage/secret-read-measurement.md <<'EOF'
# Honest limits — Secrets under the read-only identity

can-i get secrets -n northstar (agent-readonly): yes

kubectl get secret demo-app-credentials -n northstar -o yaml (agent-readonly): SUCCEEDED

data.api_key decodes to a real string: sk-demo-not-real-12345

Conclusion: read-only RBAC, as configured, does not exclude Secrets. A read-only
triage agent is still an exfiltration path for anything the resource wildcard covers.
EOF

Closing this hole — tightening the ClusterRole to an explicit resource list that excludes Secrets without breaking k8s-triage's own reads — is the subject of this module's Deep Dive.

Which model for this lab, and why​

Most of this lab is reading cluster state through a bounded wrapper and comparing it against a schema — can-i checks, kubectl get, a jsonpath query. None of that needs a frontier model; it doesn't involve a model at all. Step 10's triage is the one step that is genuine judgment — reading five sets of evidence, naming a root cause, and deciding what blast radius means for each — and that is where k8s-operator is pinned to Sonnet in its own role file, which is the correct tier for evidence-based diagnosis without needing Opus-level judgment on a bounded, schema-constrained task.

On a validated run, Step 10's full triage — all five workloads, six-field schema, ranked — cost $0.34 and took 53 seconds wall-clock (9 turns). All five findings matched the answer key, including both of fault 04's independent defects and fault 05's Secret-not-ConfigMap correction. That is the real bill for evidence-based triage on a bounded, five-workload incident.

If your team routinely summarizes an already-ranked finding into a one-line status update for a hand-off — "liveness-probe-test, two defects, patched, verify in five minutes" — that compression step is a good candidate for a cheaper model still: the hard part, deciding what the finding means, already happened on Sonnet in Step 10.

Limits — what a scoped cluster agent does and does not give you​

  • Read-only is not harmless, and you measured it. agent-readonly cannot mutate a single object and can still pull every Secret in the namespace into a context window. "Read-only" was a statement about verbs, never about data, and a wildcard on resources quietly makes it a statement about neither.
  • The hook and the kubeconfig cover different things. deny-cluster-mutation.sh inspects a proposed command; the identity decides what the API server will accept. Either alone leaves a path — a command the hook's patterns do not match, or a cluster reached through a kubeconfig nobody scoped. Both, and you have to defeat two independent controls.
  • A tool grant is a verb, not a path. platform-engineer carries a write tool, and the write: ["platform/helm/"] in the authority matrix is prose next to it. Nothing reconciles the two at runtime. This is the single most misread line in the whole operating layer.
  • Five planted faults are not an incident. They were injected together, they are independent, and the answer key exists. Real cluster incidents arrive one symptom at a time, with a cause that is upstream of everything you can see, and no key.
  • kind is not your cluster. One node, no admission controllers you did not install, no network policy enforcement unless you added a CNI that implements it, no quota pressure, no other tenants. Everything about blast radius changes on a shared cluster.
  • Remediation went through a second identity, and that was the design. Nothing in Kubernetes enforced that split — you built it, from two kubeconfigs and two role bundles. Delete either half and the agent that diagnoses is the agent that patches.

Step 14 — Take it to a cluster you actually operate​

Do not start by giving an agent a kubeconfig. Start by finding out what the one it would get can already do.

In a repository or directory where your cluster access lives:

Read the RBAC that my current kubectl context resolves to — the ClusterRoles and
Roles bound to this identity — and tell me, specifically:

1. Which resources carry a wildcard, and whether Secrets fall inside any of them.
2. Which verbs are mutating, and on which resources.
3. Which of those bindings are cluster-wide rather than namespaced.

Then propose the smallest read-only identity that could still triage a failing
workload here. Name what it would lose. Read only — do not apply anything.

What you observe. The third question is usually the surprise. Cluster-wide bindings accumulate because a namespaced one was inconvenient once, and nobody ever narrows them afterwards. The identity your agent would inherit is almost certainly your own, and your own is almost certainly wider than the job.

The deliverable is not the agent. It is the scoped kubeconfig, and it is worth having whether or not an agent ever uses it.

Teardown​

kind delete cluster --name northstar
Expected output
Deleting cluster "northstar" ...

This removes the cluster and everything on it — the faults, both identities' live tokens, and the demo Secret. Nothing under platform/ or .claude/ is touched; the operating kit is a file in this repository, not a live cluster object, and platform/kind/setup.sh plus platform/troublesim/inject.sh recreate the whole incident from scratch whenever you want to run this lab again.

You triaged five unrelated faults through a read-only identity you never had to build, ranked them by evidence rather than a hunch, fixed the one that mattered through an identity scoped to do exactly that and nothing more, and then measured the one thing "read-only" doesn't actually protect. ./scripts/grade.sh m12 checks all of it — both identities' RBAC, the kit's own pieces, and the four files you wrote yourself.
