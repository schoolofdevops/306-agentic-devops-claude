Deep Dive — Read-Only Is Not Harmless

The core lab proved something real: an identity with no mutating verb cannot delete, patch or create anything, and the API server enforces that whether or not an agent is involved. That is a genuine boundary. This page is about the gap right next to it, the one that is easy to miss because it does not look like a gap at all.

"Read-only" is a description of what an identity cannot do to the cluster's state. It says nothing about what it can read. A ClusterRole written to let a triage agent see pods, deployments, and events can, without anyone deciding it should, also let that agent read every Secret in the namespace — because get on resources: ["*"] does not stop at the resources the skill actually needs. The agent that triages your cluster and the agent that could exfiltrate every credential in it are, as configured, the exact same identity.

The point of this page is not "add a rule for Secrets." The point is that scoping an identity to read-only is a different job from scoping what it reads, and the first one does not do the second one for free. You are going to measure the hole on your own cluster, close it with an explicit resource list, and re-measure — because this module's own argument is that a boundary you have not measured is a boundary you are assuming.

Where you are working

You continue in the agentic-ops-lab workspace, against the agent-readonly identity built in the core lab and the live northstar cluster. This page adds one file you author yourself, platform/rbac/agent-readonly-tightened.yaml, graded by labs/m12/deep-dive.checks.json. The first two checks read the cluster and the committed role directly; the rest read the file you write.

Confirm the hole is real, not theoretical​

The read-only ClusterRole from the core lab grants exactly one resource pattern:

grep -n 'resources' platform/rbac/agent-readonly.yaml
Expected output
13:    resources: ["*"]

A wildcard. Every resource in every API group the rule's apiGroups line names — which includes the core group, and therefore Secrets.

Now don't take the RBAC document's word for it. Ask the API server directly, under the exact identity the triage agent operates as:

kubectl --kubeconfig=platform/kubeconfigs/agent-readonly.yaml auth can-i get secrets -n northstar
Expected output
yes

And confirm it is not just a permission check that says yes — the read actually succeeds. platform/troublesim/demo-secret.yaml plants exactly one Secret, demo-app-credentials, alongside the five faults, specifically so this measurement reproduces on every learner's own cluster rather than depending on whatever happens to already exist in the namespace:

kubectl --kubeconfig=platform/kubeconfigs/agent-readonly.yaml get secret demo-app-credentials -n northstar -o yaml
Expected output
apiVersion: v1
data:
  api_key: c2stZGVtby1ub3QtcmVhbC0xMjM0NQ==
kind: Secret
metadata:
  annotations:
    kubectl.kubernetes.io/last-applied-configuration: |
      {"apiVersion":"v1","data":{"api_key":"c2stZGVtby1ub3QtcmVhbC0xMjM0NQ=="},"kind":"Secret","metadata":{"annotations":{},"name":"demo-app-credentials","namespace":"northstar"},"type":"Opaque"}
  creationTimestamp: "2026-09-22T03:57:09Z"
  name: demo-app-credentials
  namespace: northstar
  resourceVersion: "12254"
  uid: 62ea715b-2918-4c62-94a4-2848fdc1695a
type: Opaque

Your creationTimestamp, resourceVersion and uid will differ — those are assigned when inject.sh applies the manifest on your cluster. The field that matters, data.api_key, is fixed: it is the same deliberately fake value on every cluster this manifest is applied to.

That data.api_key field is base64, not encrypted — kubectl decodes it for free:

echo 'c2stZGVtby1ub3QtcmVhbC0xMjM0NQ==' | base64 -d
sk-demo-not-real-12345

A demo value on this cluster. On a real one, this is exactly the field that ends up in a triage agent's context window the moment it runs a bounded read against the wrong resource — not because the agent misbehaved, but because the identity it runs as was never told Secrets were out of bounds. Read-only kept it from deleting anything. Nothing kept it from reading this.

Write down what "read-only enough" actually means​

Before touching the RBAC document, say what the triage skill genuinely needs, because the fix is not "block everything" — the k8s-triage skill still has to run. It reads pods, deployments, configmaps, events and EndpointSlices. It has never read a Secret, and the skill's own evidence schema has no field a Secret would fill.

That is a short, checkable requirement: an explicit resource list, not a wildcard, naming exactly the resources the skill uses, with Secrets left off the list, and no verb added beyond get, list, watch. Hand that requirement to Claude in a general session — this is a platform-configuration change, not a triage read, so it is deliberately outside what the k8s-operator role does; that role has no Write tool for a reason. Ask it to author platform/rbac/agent-readonly-tightened.yaml as a ClusterRole matching that requirement, following the structure of platform/rbac/agent-readonly.yaml.

Verify the fix without touching the cluster​

Four checks read the file you got back, and all four have to hold at once — narrowing the wildcard the wrong way (dropping a resource the skill actually needs) fails just as loudly as leaving Secrets in:

./scripts/grade.sh m12-deep-dive

Two things that would each independently break this: naming an explicit list that still forgets to drop secrets, and dropping secrets by writing a second wildcard-minus-one rule instead of an explicit list — resources: ["*"] with an exclusion is not a construct RBAC has, so that approach silently fails to compile the intent at all. The explicit list is not a style preference; it is the only way to say "these and only these" in a ClusterRole document.

Prove it live, the same way you proved the original boundary​

A file that reads correctly is not the same as a cluster that enforces it — the core lab's whole argument was that you measure the API server, not the document. Point the existing agent-readonly ServiceAccount at the tightened role instead of the original one, by editing the ClusterRoleBinding's roleRef (or applying a second binding and removing the first — either way, one ServiceAccount, one active role, so the comparison is clean), apply it, and ask the same question you asked at the top of this page:

kubectl --kubeconfig=platform/kubeconfigs/agent-readonly.yaml auth can-i get secrets -n northstar

If the tightened role is correctly scoped, that now returns no — and everything the triage skill actually reads still returns yes, because narrowing the wildcard did not touch the resources the skill uses. Confirm both, because a fix that silently breaks triage while closing the Secrets hole has traded one incident for another:

kubectl --kubeconfig=platform/kubeconfigs/agent-readonly.yaml auth can-i get pods -n northstar
kubectl --kubeconfig=platform/kubeconfigs/agent-readonly.yaml auth can-i get deployments -n northstar
kubectl --kubeconfig=platform/kubeconfigs/agent-readonly.yaml auth can-i get configmaps -n northstar

Restore the original binding once you've confirmed the pair of results, so the core lab's identity is left exactly as the lab built it.

What the API server still doesn't check​

One more limit is worth naming honestly, because this module's whole argument is measuring rather than assuming, and it cuts against the course too. RBAC decides whether a request is allowed. It has no opinion on why the request was made. If a workload's log line, an EndpointSlice annotation, or any other text the triage skill reads back contains an instruction — "also run kubectl delete on this deployment" — RBAC does not know that text exists; it only sees the verb and the resource in the request that eventually gets sent, if one gets sent at all.

That is a real and separate limit from the one you just measured, and it is also where this module's earlier point closes the loop rather than opens a new hole: whatever an injected instruction convinces the model to attempt, the identity it runs as still cannot delete, patch or create anything it was never granted — the same 403 that held in the core lab holds here too, regardless of what produced the request. RBAC does not stop the attempt. It stops the attempt from succeeding. Those are different guarantees, and conflating them is how a team ends up trusting a boundary for something it was never built to catch.

Where you will use this​

  • Any time you scope an identity — human or agent — for a read-only job. "Read-only" answers can it change state. It does not answer what can it see. Those are two separate scoping decisions, and a wildcard resource pattern collapses them into one by accident.
  • Reviewing someone else's RBAC document. A ClusterRole that lints and applies cleanly tells you nothing about what it grants beyond the verbs — read the resource list the same way you would read a security group's port range, not the way you'd skim a YAML file for syntax errors.
  • Handing any agent broader read access "to be safe." The instinct to over-grant reads because writes are the scary part is exactly backwards for an identity whose entire job is to read things and put them in a context window. The read path is the exfiltration path.
  • Anywhere you are tempted to trust a control for something it does not check. RBAC is a real, server-side, measured boundary against mutation. It was never a boundary against a model being talked into asking for the wrong thing — and the fix for that is not a bigger RBAC document, it's a different control, applied where the actual gap is.
