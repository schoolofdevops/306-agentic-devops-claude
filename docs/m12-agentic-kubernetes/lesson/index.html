AI Agents for Kubernetes

Every boundary this course has built so far has been a rule someone could read. A CLAUDE.md file. An agent's tool list. A hook that inspects a command before it runs. Every one of them works because the agent is choosing to honor it. This module is where that stops being true.

Here is the job. The northstar cluster is degraded. Five workloads are unhealthy, nobody has said which faults are related, and you have fifteen minutes before the standup where someone asks what's broken. You are going to point an agent at that cluster — but first you build the identity it operates as, the tools it is allowed to use, and the skill that makes its findings comparable to each other. Then you use it: triage all five faults, rank them, and fix the one that matters through a second identity that is scoped to write in exactly one place.

By the end you will have an operating kit you could hand to any on-call engineer — a role, a read-only identity, a write-scoped remediation identity, a bounded tool, a triage skill and a hook — and you will have measured, not assumed, what that kit does and does not protect against.

Every control so far has been a sign on a door​

Think about what you have built in this course up to now. A CLAUDE.md rule is a sign that says "read-only past this point." A role's tool list is a sign that says "this agent doesn't carry a delete tool." A PreToolUse hook is a sign that says "no" to a specific command before it runs. Every one of these works for the model reading it. A well-run agent stops at the sign. A differently-prompted one, or a plain shell command typed by a teammate who never opens an agent session at all, walks straight past it, because a sign is not a lock.

Kubernetes RBAC is the first control in this course that is a lock rather than a sign. You bind the agent to a ServiceAccount. That ServiceAccount carries a ClusterRole with no mutating verb in it. When anything — the agent, a script, you, typing by hand — asks the API server to delete something under that identity, the API server itself says no. Not the agent choosing to refuse. Not a hook intercepting the request before it runs. A different machine, refusing a command it was never configured to allow, at the same speed whether a model typed it or a person did.

The kit you build before you use anything​

You do not hand-write the pieces below — you write a short brief, platform/SPEC.md, saying what the kit must do and what "done" means, and the harness designs and assembles it the way it built the Terraform module last module. Your job is the brief and the verification; the harness's job is everything in between.

The role. .claude/agents/k8s-operator.md — model, tool list, and Skill present in that list. The same fact from Module 9 holds here without exception: a role can only invoke a skill if Skill is in its tools. Leave it out and the agent still reads the triage skill as a plain file, still produces plausible-looking findings, and the fixed evidence schema below never fires — nothing in the transcript tells you it didn't.

The read-only identity. A ServiceAccount, a ClusterRole granting get, list, watch and nothing else, a binding, and a kubeconfig generated from that ServiceAccount's own token — never a User entry borrowed from your personal kubectl config. Measured directly against it:

get     pods         yes        create  pods         no
get     deployments  yes        create  deployments  no
get     configmaps   yes        create  configmaps   no
get     secrets      yes        create  secrets      no
                                 delete  deployments  no

Read that table twice. Every get/list/watch is yes — the identity can do its job. Every mutating verb is no — including on Secrets, which matters and which the honest-limits section below comes back to.

A second identity for remediation. A different ServiceAccount, bound to a namespaced Role — not a ClusterRole — scoped to apiGroups: ["apps"], resources: ["deployments"], verbs: ["get", "list", "patch"]. Measured:

patch deployments -n northstar    yes
delete deployments -n northstar   no
patch deployments -n kube-system  no
get secrets -n northstar          no

Look at that last line closely. The remediator can write, which the read-only identity cannot — but it cannot read Secrets, which the read-only identity can. Narrower is not the same as "more trusted." Each identity carries exactly the authority its one job needs, and neither is a superset of the other.

A bounded kubectl wrapper. kubectl -A -o yaml against a real cluster is tens of thousands of tokens of context spent reading pods nobody asked about. A librarian who fetches you the shelf you asked for and refuses to wheel out the entire stacks is doing you a favor, even when you're in a hurry — the wrapper does the same thing: it refuses -A outright, and it caps any read at a line count, appending a marker when it cuts one off so you know a query was narrowed rather than silently truncated.

A triage skill with a fixed schema. This is the house standard for this module, covered on its own below.

A PreToolUse hook, on purpose redundant. It pattern-matches mutating kubectl verbs in a Bash command and returns a deny decision before the tool runs. It exists as a faster, louder no — not as the control. The section below proves the difference between the two.

A directory-scoped context file, platform/CLAUDE.md, naming the one cluster and one namespace this directory operates on, so a command that omits --kubeconfig or -n is a mistake the agent's own standing instructions catch before it runs at all.

The house standard: a schema, not a narrative​

Five broken workloads produce five different stories if you let an agent write five different paragraphs about them. Paragraphs cannot be ranked against each other. The k8s-triage skill fixes that by making every finding come back in the same fixed form:

workload:      <name>
signature:     <ImagePullBackOff | CrashLoopBackOff | Pending | RestartLoop | ConfigError>
root_cause:    <one sentence>
evidence:      <the single command output line that proves it>
blast_radius:  <replicas affected> of <replicas desired>, <serving | not serving>
confidence:    <high | medium | low>

Behind that schema sits a fixed set of bounded reads, all through the wrapper above, never -A, never an unbounded -o yaml: pod status, a deployment describe, events scoped to one pod, the previous container's logs, and one more that is easy to skip and is not optional.

The read that lies if you read the wrong column​

Here is a concrete case for why the fifth read exists. One of the five faults breaks a workload's readiness probe. The pod keeps running. kubectl get endpointslices lists the workload's Service backends, and the ADDRESSES column shows two addresses — the same two pod IPs you'd expect from a healthy deployment.

That column is lying to you. kubectl get endpointslices -n northstar -l kubernetes.io/service-name=liveness-probe-test-svc measured on the live cluster shows 10.244.0.9,10.244.0.8 in ADDRESSES — and both of those addresses carry ready=false, serving=false. An EndpointSlice lists an address whether or not it is ready; the column that looks like "who's being served" is closer to "who used to be scheduled here." A seating chart that lists every assigned seat, whether or not the person actually showed up, tells you nothing about who's really in the room — you have to check attendance, not the chart. The command that tells the truth reads the condition, not the column:

kubectl get endpointslices -n northstar -l kubernetes.io/service-name=liveness-probe-test-svc \
  -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]}{" ready="}{.conditions.ready}{"\n"}{end}'

The k8s-triage skill is written to always read .conditions.ready, and never a bare kubectl get endpoints — that older, deprecated view goes further than the trap above: it silently drops every address that isn't ready, so an empty result and "no Service exists" look identical.

Prove the boundary before you trust it​

The can-i tables above are a claim. Before you use the identity for anything, prove it with the command that actually matters:

Error from server (Forbidden): deployments.apps "crashloop-test" is forbidden: User
"system:serviceaccount:northstar:agent-readonly" cannot delete resource "deployments" in API
group "apps" in the namespace "northstar"

That is not a hook talking. That is the API server, refusing a request from an identity that was never granted the verb, in the same words it would use if you had typed the command yourself with no agent anywhere near the terminal.

Now do the thing that actually distinguishes a lock from a sign. Bypass the PreToolUse hook entirely — call kubectl directly, with no agent, no permission prompt, nothing standing between you and the cluster except the identity you're using. Run the same delete. You get the exact same 403, word for word. The hook is ours, and we could delete the file that implements it. The 403 is not ours, and there is no file to delete. That pairing — hook removed, boundary still holds — is the whole reason this module exists.

Triage, ranked, then remediate through a different identity​

With the boundary proven, launch as the role and point it at the cluster: claude --agent k8s-operator. It reads the five workloads through the bounded wrapper, emits one fixed-schema finding per workload using the triage skill, and you rank the five by blast_radius — the field that turns "five things are wrong" into "start with this one." You check the ranking against a planted answer key before you trust it, the same way Module 11 checked a plan against reality instead of the agent's own confidence.

Fixing what you found happens under the second identity, agent-remediator, never the read-only one and never your own admin kubeconfig. The read-only identity structurally cannot patch a Deployment — it was never granted the verb — so remediation switching identities is not a style preference, it is the only way the write can happen at all.

Match the model to the job​

Ranking five findings by blast radius and writing a one-sentence root cause per workload is real judgment about evidence — that is triage work, and it runs on a capable model. Summarizing a single already-triaged finding into a two-line status update for a handoff is not judgment, it is compression, and a cheaper model does that job for a fraction of the cost. The lab has you measure both costs for the same cluster state, the same way Module 6 measured Haiku against Sonnet on an identical question — do not take the ratio on faith, run the two commands and read the numbers yourself.

Read-only is not harmless​

Here is the beat that makes this module worth teaching, and the reason a ClusterRole needs the same scrutiny whether it grants writes or not. The read-only ClusterRole above grants get, list, watch on resources: ["*"]. That wildcard was written for convenience — the triage skill needs to read pods, deployments, configmaps, events, EndpointSlices — and it also, without anyone deciding it should, grants get on Secrets.

kubectl get secret -o yaml is a read. The can-i table said get secrets: yes. A read-only agent, one that cannot delete, patch or create a single thing, is still a path for every Secret in the namespace to leave the cluster in its context window. RBAC as configured here does nothing to stop that, because nothing about "read-only" implies "excludes Secrets" — that exclusion has to be a decision someone writes down, the same way a background-check officer being allowed to verify an identity does not automatically mean they can read the personnel file's medical history; somebody has to scope the cabinet, not just lock the door.

The Deep Dive that follows this lesson is where you measure that hole for real, close it with an explicit resource list that excludes Secrets, and re-measure — because the module's own thesis says nothing gets to be asserted here. It gets measured.

What you'll do in the lab​

  1. Stand up the cluster and plant the five faults from a pinned, vendored fault set — no network access mid-exercise.
  2. Write platform/SPEC.md — the brief for the operating kit, not its YAML.
  3. Ask for isolation, then verify you got it, the same discipline as Module 11.
  4. Hand the brief to the harness and let it design and assemble the kit — the role, both identities, the bounded tool, the triage skill, the hook.
  5. Prove the boundary: the can-i matrix for both identities, then the 403 itself, then the hook removed with the 403 still standing.
  6. Wire in the environment: kubeconfig, context, namespace, the directory-scoped CLAUDE.md.
  7. Launch as k8s-operator and triage all five faults into ranked, fixed-schema findings.
  8. Check the findings yourself against the planted answer key — report the misses, not just the hits.
  9. Remediate through agent-remediator, and record that the fix went through that identity, not your own kubeconfig.
  10. Measure the model cost of triage against summarization, on the same cluster state.
  11. Measure the honest-limits hole: does kubectl get secret -o yaml succeed under the read-only identity on your own cluster?
  12. Tear down.

The Deep Dive picks up exactly where step 11 leaves off: closing the hole you just measured, and proving it stays closed.
