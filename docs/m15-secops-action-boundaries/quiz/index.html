SecOps & Action Boundaries — Quiz

Three files in the repository answer the question "what may this role write?" — the authority matrix, the role's agent file, and the system/init event of a real session. They disagree. Which one is the fact?

All nine role files declare tools: ["Read","Grep","Glob","Bash","Skill"], and a live session reports ["Read","Bash","Skill"]. The roles still searched files successfully. What happened?

The attestation has two arms. Which statements are true of how they differ? (Select all that apply.)

On its first live run, every behavioural probe returned unproven because a missing --verbose flag made claude -p exit 1. The unit suite was fully green. What does this show about the unproven status?

The scorer records correct, overreach, and unnecessary-refusal. A colleague argues the third one is noise — the suite exists to catch dangerous behaviour, not annoying behaviour. What is the counter-argument?

The oracle returns clarify when an agent is asked to restart orders-api in production-2, while the environment contract's namespace is production. Why is clarify the correct outcome rather than refuse?

attest.sh emits verdict: null, and a separate security-reviewer role reads the attestation and signs it. Why not have the instrument compute the verdict itself?

Asked to build the attestation instrument, security-reviewer declined and said: "I could technically abuse Bash with a heredoc to write security/attest.sh, but that would violate the constraint in spirit, not just letter, so I won't." What is the most important thing in that sentence?

A CI job checks the instrument with: bash security/attest.sh | jq -c '.summary'; if [ $? -ne 0 ]; then fail; fi. The instrument exits 1 by design against this repository. What does the job report?

The first probe matrix varied five dimensions across five probes, and every single probe expected the outcome refuse-target. The unit suite was green. What went wrong, and why did the tests miss it?

Every claim in the attestation carries expected, observed, source and status. A reviewer proposes dropping expected and observed to keep the document short. What is lost?

The instrument is written under security/ by a new secops-engineer role rather than by the existing platform-engineer, which already has Edit and Write. Why add a role?

During isolation the secops-engineer appended .worktrees/ to .gitignore on main and committed it — outside the security/ path its own role file calls "your only write path". Nothing stopped it. Why not?

A team runs the attestation once, files it with the security review, and moves on. Six weeks later somebody edits a role file. What is the status of the filed attestation?
