Deep Dive — Concurrency, Routines, Channels & Monitor

The core lab closed the sequential duplicate: the same event delivered twice, one after the other, deduplicated on its correlation ID. That is the common case and the dedup ledger handles it. This deep dive goes after two things the core lab left open — the concurrent duplicate (two triggers firing at the same instant, which sequential dedup cannot catch) and the question of what actually fires these triggers in Claude Code today, weighed honestly for production maturity.

Neither of these is a repeat of the lab. Concurrency is a genuinely harder problem than deduplication, and the trigger-maturity question is the one that decides whether you can run any of this unattended in production yet.

The gap sequential deduplication cannot close​

Look closely at how the dedup ledger works. The loop greps the ledger for the correlation ID, and if it is absent, it does the work and then writes the ledger. That sequence — check, then work, then record — has a window in it. Between the check and the record, the correlation ID is not yet in the ledger. If a second trigger for the same incident arrives during that window, it also checks the ledger, also finds nothing, and also starts working. Both runs pass the dedup check because neither has recorded yet.

Analogy: deduplication is the guest list at the door — the bouncer checks your name, crosses it off, and lets you in. That works when guests arrive one at a time. But if two people holding the same invitation walk up to two different doors at the same instant, both bouncers check their lists, both see the name un-crossed, and both let a copy in. The guest list is not wrong; it just cannot handle simultaneity. For that you need something stronger: a single turnstile that only one person can pass through at a time, no matter how many doors there are.

That turnstile is a lock. And this is not a theoretical race. In practice, an incident often trips several triggers at once — a scheduled routine and an inbound webhook both wake on INC-002, or two Monitor conditions cross their thresholds in the same tick. Without a lock you get two control loops racing, and the damage from that is worse than a double read: two loops can open two pull requests for the same fix, or propose two conflicting remediations, and now a human has to untangle which one to keep.

An atomic lock keyed by correlation ID​

The concurrency guard, scripts/triage-lock.sh, locks on the same correlation ID the rest of the contract uses — so the unit of mutual exclusion is "one incident," which is exactly right. Two triggers for the same incident contend; two triggers for different incidents do not block each other.

The primitive matters. The guard uses mkdir as its atomic operation, and the reason is worth understanding: mkdir either creates the directory (you won) or fails because it already exists (someone else holds it), and that decision is atomic on every POSIX filesystem — the kernel guarantees exactly one caller can create a given directory even if a thousand call at once. No flock, no lock server, no database row; it works identically on macOS and Linux. A check-then-create written in two steps (test if the dir exists, then create it) would have the same race as the ledger. mkdir collapses check-and-claim into one indivisible operation, which is the whole point.

Acquire, contend, release:

scripts/triage-run.sh --reset >/dev/null
CID="INC-002-2024-11-18T14:07:00Z"
scripts/triage-lock.sh --acquire --cid "$CID"; echo "first=$?"
scripts/triage-lock.sh --acquire --cid "$CID"; echo "second=$?"
scripts/triage-lock.sh --release --cid "$CID"; echo "release=$?"
Expected output
acquired: INC-002-2024-11-18T14:07:00Z
first=0
held: another run owns the lock for INC-002-2024-11-18T14:07:00Z — concurrent contender rejected
second=9
released: INC-002-2024-11-18T14:07:00Z
release=0

The first acquire wins (first=0). The second, while the lock is held, is rejected — the "held" message goes to stderr and the process exits 9 (second=9). The contender is rejected immediately, not queued: a second remediation for an incident already being handled is never the right move, so blocking-and-waiting would be wrong here. Release frees the lock so a later, non-overlapping run can proceed — the guard rejects overlap, it does not permanently blacklist the correlation ID.

Now prove it holds under a real race — five acquirers launched simultaneously, contending for one correlation ID:

scripts/triage-run.sh --reset >/dev/null
WINS=$(mktemp)
for i in 1 2 3 4 5; do
  ( scripts/triage-lock.sh --acquire --cid race >/dev/null 2>&1 && echo win >> "$WINS" ) &
done
wait
echo "winners: $(wc -l < "$WINS" | tr -d ' ')"
rm -f "$WINS"; scripts/triage-lock.sh --release --cid race >/dev/null 2>&1
Expected output
winners: 1

Exactly one winner out of five simultaneous contenders. This is the property sequential deduplication cannot give you: no matter how many loops wake for the same incident at the same instant, the atomic lock guarantees exactly one does the work. In a real deployment the winner triages and the four losers exit cleanly, and you get one packet and one PR instead of five.

Where deduplication ends and locking begins

Keep the two mechanisms straight, because you need both. Deduplication (the ledger) handles the duplicate that arrives after the first was recorded — the common redelivery, cheap to check. Locking (the turnstile) handles the duplicate that arrives before the first was recorded — the simultaneous trigger, which dedup structurally cannot see. A production loop acquires the lock first, then checks the ledger, does the work, records, and releases. The lock covers the window; the ledger covers everything after it.

What actually fires the trigger: Claude Code's automation surface​

Everything above assumes something delivers the event. In Claude Code today, four features can play that role, and they sit at very different maturity levels. Being honest about which are production-ready is the difference between a design that works and one that pages you at 3am because a preview feature changed under it.

Analogy: think of these as the difference between a wall clock, a kitchen timer, a smoke detector, and a butler you are still training. Each can "trigger" something, but you would trust them with very different jobs. You do not wire your production incident response to the butler who started last week.

FeatureWhat it isTrigger modelMaturity for unattended prod
Headless mode (claude -p)One-shot non-interactive run, prints and exitsYou invoke it — from cron, CI, a webhook handlerProduction-ready. The stable foundation; you already used it in M13. Everything reliable is built on this.
Routines (/cron)Scheduled recurring runs on Anthropic's infrastructureTime-based (a schedule)Preview. Great for periodic sweeps; verify the schedule semantics and failure behavior before depending on them.
ChannelsNamed streams that carry events/messages between agents and triggersEvent/message-basedPreview / evolving. Promising for event fan-in, but the delivery guarantees (at-least-once? ordering?) are exactly what your contract must not assume.
MonitorWatches a condition and wakes an agent when it crosses a thresholdCondition-basedPreview. The most "always-on" of the set; treat its wake-ups as untrusted triggers like any other.

The load-bearing point is not which feature is newest — it is that your reliability contract must not trust any of them to be exactly-once. Every one of these can, under the wrong conditions, deliver an event twice, out of order, or late. That is not a defect to wait out; it is the nature of distributed delivery. A routine can fire twice if a run is retried. A channel can redeliver on reconnect. Monitor can re-trip on a flapping condition. This is why the contract exists: you build deduplication, idempotency, and locking so that the trigger's delivery guarantees stop mattering. A loop that honors the contract is correct whether the event arrives once, twice, or five times at once — which means you can adopt a preview trigger without betting production on its maturity.

Adopting preview features safely

The safe adoption pattern is a seam. Put a stable, production-ready boundary — a claude -p invocation of your contract-honoring loop — between the preview trigger and any real action. The preview feature's only job is to deliver an event; your loop's job is to make delivery safe. If the preview feature misbehaves (double-fires, drops, reorders), the contract absorbs it and nothing downstream double-acts. When the feature graduates to GA, nothing in your loop has to change. Never let a preview trigger reach into a write path directly.

Architecture comparison: control loop versus a persistent agent (Hermes)​

There are two shapes for always-on automation, and they trade off differently. The first is the event-driven control loop you built: dormant until an event arrives, wakes, runs the contract, produces a structured result, exits. The second is a persistent agent — a long-lived process that stays resident, holds context across events, and reacts continuously. The Hermes Agent pattern (a persistent operator that watches, remembers, and acts over long horizons) is the reference for this second shape.

Analogy: the control loop is a temp you call in for one job — they show up, do the task by the book, hand you the result, and leave, carrying nothing between calls. The persistent agent is a resident night-shift operator — always there, remembers last Tuesday's incident, notices patterns across events. The temp is trivial to reason about and impossible to leave in a bad state (they are gone the moment the job ends). The resident is more capable but must be managed — their accumulated memory can drift, their long-running process can wedge, and "restart them clean" is a real operational task.

DimensionEvent-driven control loop (this module)Persistent agent (Hermes pattern)
LifetimePer-event: wake, run, exitLong-lived, resident
StateStateless between runs; state lives in the ledger/packets on diskHolds context in-process across events
Cross-event memoryNone by default — each run is independentRich — can correlate events over time
Failure blast radiusBounded — a bad run exits and leaves no process behindWider — a wedged or drifted process persists until restarted
Reliability contractNaturally enforced — a fresh process per event makes idempotency and clean termination easyHarder — must add contract plus memory hygiene, health checks, and restart policy
Best forWell-scoped, repeatable reactions (triage, checks, gated changes)Long-horizon operation needing memory and pattern detection across many events

The honest recommendation for production DevOps automation today: start with the stateless control loop. It gives you the reliability contract almost for free, because a fresh process per event is inherently idempotent and inherently clean on exit — there is no accumulated state to corrupt and no resident process to wedge. Reach for the persistent-agent shape only when you genuinely need cross-event memory (correlating a slow-burn pattern across many incidents), and when you do, budget for the extra operational surface: the process needs health checks, a restart policy, and memory hygiene, on top of the same contract the loop already gave you. Persistence buys capability at the cost of operability; do not pay that cost until the capability is the thing you actually need.

Where you will use this​

The concurrency lock is the piece you will reach for the first time an automated triage opens two pull requests for one incident and someone asks why — the answer is a missing turnstile, and mkdir-atomic locking keyed on the correlation ID is the fix. The maturity table is the conversation you will have when a teammate wants to wire a preview routine straight into a deploy; the answer is the seam — let the preview feature deliver events, let a contract-honoring claude -p loop make delivery safe, and never let the two collapse into one. And the control-loop-versus-persistent-agent comparison is the design decision at the top of any always-on project: default to stateless loops, and earn the right to a persistent agent only when cross-event memory is the requirement, not the temptation.

Grade this deep dive's concurrency guarantees:

scripts/grade.sh m17-deep-dive
Expected output
Grading: Module m17-deep-dive
========================

Checking: Deep Dive — routines, channels and Monitor as automation triggers, and concurrency control against duplicate PRs / conflicting remediations

  ✓ the correlation-scoped concurrency guard exists and is executable — dedup handles the sequential duplicate, the lock handles the concurrent one
  ✓ CONCURRENCY: the first contender for a correlation_id acquires the lock (exit 0) — exactly one holder does the work
  ✓ CONCURRENCY: a second contender for a correlation_id already locked is rejected at exit 9 — two triggers for one incident never open two PRs
  ✓ CONCURRENCY: releasing the lock frees it so a later, non-overlapping run can proceed — the guard rejects OVERLAP, it does not permanently block the correlation_id
  ✓ CONCURRENCY (true race): under five simultaneous acquirers for one correlation_id, EXACTLY ONE wins — the mkdir primitive is atomic, so no two loops ever run together
  ✓ CONCURRENCY: two DIFFERENT correlation_ids lock independently — the guard is per-incident, so unrelated incidents triage in parallel without blocking each other

========================
RESULT: PASS (6 passed)

Six checks, all concurrency: the lock exists, one contender wins and the next is rejected, release frees it, a real five-way race yields exactly one winner, and distinct incidents lock independently. These are the guarantees that turn "two triggers fired at once" from a double-PR incident into a non-event.

Teardown​

scripts/triage-run.sh --reset
Expected output
triage-state cleared

--reset also removes the lock directory tree under agentops/triage-state/locks/. Nothing in this deep dive started a persistent process — every lock was acquired and released within a single command — so a clean slate is one reset away.
