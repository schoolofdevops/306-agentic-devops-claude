Lab — Idempotent Read-Only Incident Triage

The lesson named six properties every unattended agent must have — correlation ID, idempotency, deduplication, timeout, retry budget, cancellation — plus the safety invariant that makes always-on triage acceptable at all: it is read-only and structurally cannot deploy. This lab makes all seven runnable against a real synthetic CI incident.

You will validate an event envelope and watch it fail closed without a correlation ID, trigger the same incident twice and watch the first delivery get triaged while the second is deduplicated to a no-op, confirm exactly one incident packet exists at the end and that it validates as structured evidence, abort a run cleanly with a cancel token, exhaust a bounded retry budget and time out instead of looping forever, and ask the loop to deploy and watch it refuse at the action boundary.

Where you are working

You start at the root of the agentic-ops-lab workspace. The synthetic CI event is fixtures/events/ci-incident.json. The two M17 scripts are scripts/event-validate.sh (the envelope validator) and scripts/triage-run.sh (the control loop). The loop reuses scripts/evidence-validate.sh (the M14 evidence schema) and scripts/action-boundary-check.sh (the M15 boundary oracle) — this module composes what you already built rather than replacing it. Run state lives under agentops/triage-state/ (a dedup ledger and one packet per incident). Every graded step is a deterministic script run — it grades the same on any machine, no live cluster or Claude call required. The read-only role this automation embodies is .claude/agents/sre-investigator.md.

Step 0 — Prerequisites​

Confirm your tools. The lab needs jq, yq, and bash.

jq --version
yq --version
bash --version | head -1
Expected output
jq-1.7.1
yq 3.4.3
GNU bash, version 3.2.57(1)-release (arm64-apple-darwin25)

Your versions will differ. jq builds and reads every JSON envelope and packet; yq is used by the action-boundary check the loop delegates to. Any recent bash works — the scripts are written to run on the macOS default (3.2) as well as Linux.

Start from a clean triage state so the deduplication steps are meaningful:

scripts/triage-run.sh --reset
Expected output
triage-state cleared

--reset clears the dedup ledger and any packets from prior runs. It is also the lab teardown — every graded step only touches agentops/triage-state/, and reset empties it.

Step 1 — Validate the event envelope​

Unattended automation begins with a trigger, and a trigger you cannot trust is a trigger you must not act on. Look at the synthetic CI event first — this is what a failing CI job would deliver:

cat fixtures/events/ci-incident.json
Expected output
{
  "specversion": "1.0",
  "id": "evt-9f3a1c",
  "correlation_id": "INC-002-2024-11-18T14:07:00Z",
  "source": "ci/github-actions",
  "type": "com.northstar.ci.incident.opened",
  "time": "2024-11-18T14:07:11Z",
  "subject": "orders-api",
  "data": {
    "incident": "INC-002",
    "severity": "P2",
    "signal": "upstream retry storm — orders-api p95 latency breached SLO after inventory-api errors",
    "env": "staging",
    "runbook": "runbooks/service-restart.md"
  }
}

A small, CloudEvents-shaped record. The load-bearing field is correlation_id — the stable id of the incident that deduplication, idempotency, and tracing all key off. Note id (this delivery) is distinct from correlation_id (the incident): a bus can redeliver under a new id while the correlation_id stays the same.

Now validate it. The validator confirms every required field is present and non-empty, and can extract the correlation ID:

scripts/event-validate.sh fixtures/events/ci-incident.json
scripts/event-validate.sh --field correlation_id fixtures/events/ci-incident.json
Expected output
VALID: event from 'ci/github-actions' correlation_id='INC-002-2024-11-18T14:07:00Z' — envelope is well-formed and traceable.
INC-002-2024-11-18T14:07:00Z

The envelope is well-formed and the correlation ID pulls out cleanly. That id is what the control loop will hang the entire run on.

Now the fail-closed case. Send an event with no correlation_id and watch it get rejected:

echo '{"id":"x","source":"ci","type":"t","time":"now","subject":"orders-api"}' \
  | scripts/event-validate.sh; echo "exit=$?"
Expected output
INVALID: event envelope is missing a required field (id, correlation_id, source, type, time, subject must all be non-empty). No correlation_id, no run.
exit=3

Rejected at exit 3. This is the point of validating the trigger: an event with no correlation ID cannot be deduplicated, so a loop that accepted it could act twice on one incident with no way to detect the repeat. The loop refuses to run rather than run unsafely.

Step 2 — First delivery: triage the incident​

Now the control loop. Feed it the CI event. This is a fresh incident — the loop validates the envelope, collects read-only evidence, and produces one packet:

scripts/triage-run.sh --event fixtures/events/ci-incident.json
Expected output
{
  "correlation_id": "INC-002-2024-11-18T14:07:00Z",
  "subject": "orders-api",
  "env": "staging",
  "outcome": "triaged",
  "packet": "/Users/you/agentic-ops-lab/agentops/triage-state/packet-INC-002-2024-11-18T14_07_00Z.json"
}

outcome: triaged — a structured result, not prose. The packet path is derived from the correlation ID (a filesystem-safe slug of it), which is what makes the write idempotent in the next step. Your absolute path will differ; the shape is what matters.

Look at what the loop produced. The packet reuses the M14 sre-investigator evidence schema exactly:

scripts/triage-run.sh --event fixtures/events/ci-incident.json --field packet
Expected output
{
  "from_role": "triage-automation",
  "to_role": "ops-lead",
  "correlation_id": "INC-002-2024-11-18T14:07:00Z",
  "evidence": {
    "service": "orders-api",
    "status": "degraded",
    "checks": {
      "envelope_valid": true,
      "evidence_collected": true
    },
    "hypothesis": "unattended read-only triage collected evidence for INC-002 in staging",
    "confidence": "medium",
    "sources": [
      "incidents/INC-002.md",
      "event.correlation_id=INC-002-2024-11-18T14:07:00Z"
    ]
  },
  "recommendations": [
    "route to sre-investigator / change-reviewer for any remediation — automation is read-only"
  ],
  "out_of_scope": [
    "did not remediate",
    "did not deploy, restart, scale, or delete"
  ]
}

A structured evidence packet, carrying the correlation ID, with every claim traced to a source and an explicit out_of_scope that names what the automation deliberately did not do. Because it is the same schema the interactive investigator produces, the M14 validator accepts it — proving next.

Confirm the packet is valid structured evidence, not free text, by piping it through the schema validator:

scripts/triage-run.sh --event fixtures/events/ci-incident.json --field packet \
  | scripts/evidence-validate.sh
Expected output
VALID: evidence packet from 'triage-automation' -> 'ops-lead'; hypothesis backed by 2 source(s), out_of_scope declared.

The automation's output passes the exact provenance check a human investigator's output must pass. Structured results are what let the next stage act without re-investigating.

Step 3 — Second delivery: deduplicate on the correlation ID​

This is the heart of the lab. Trigger the same event again — exactly what an event bus does when it redelivers. A reliable loop must not triage it twice:

scripts/triage-run.sh --event fixtures/events/ci-incident.json --field outcome
Expected output
deduplicated

deduplicated, not triaged. The loop recognized the correlation ID in its dedup ledger and skipped the work entirely. This is the property that turns "same event twice" into "same outcome once" — without it, every redelivery would be a fresh triage.

Now prove idempotency the strong way: count the packets. Two deliveries of one incident must leave exactly one packet, not two:

ls agentops/triage-state/packet-*.json | wc -l | tr -d ' '
Expected output
1

Exactly one. The packet is keyed by correlation ID, so the second run is a no-op that points at the same artifact rather than appending a second one. Idempotency means the number of times the event arrives cannot change the number of outcomes.

Look at the dedup ledger to see how the loop remembers:

cat agentops/triage-state/dedup.jsonl
Expected output
{"correlation_id":"INC-002-2024-11-18T14:07:00Z","packet":"/Users/you/agentic-ops-lab/agentops/triage-state/packet-INC-002-2024-11-18T14_07_00Z.json","ts":"2026-07-26T01:06:02Z"}

One line, written on the first triage. The timestamp and path will differ on your machine. On every subsequent delivery the loop greps this ledger for the correlation ID before doing anything — a seen id short-circuits to deduplicated. This is deduplication and idempotency implemented as one small durable record.

Step 4 — Cancellation: abort cleanly, leave nothing behind​

An unattended loop needs a clean stop. A cancel token is the automation equivalent of the operator hitting Ctrl-C. Reset, create a cancel token, and run — the loop should abort at its first checkpoint:

scripts/triage-run.sh --reset >/dev/null
CANCEL=$(mktemp)
scripts/triage-run.sh --event fixtures/events/ci-incident.json --cancel-file "$CANCEL" --field outcome
Expected output
cancelled

cancelled. The loop checks the cancel token before doing work and at each retry checkpoint, so a cancel takes effect promptly and cleanly.

The important half of cancellation is that a clean abort leaves no partial side effect — no half-written packet. Confirm zero packets exist:

ls agentops/triage-state/packet-*.json 2>/dev/null | wc -l | tr -d ' '
rm -f "$CANCEL"
Expected output
0

Zero packets. A cancelled run is as if it never happened — it did not commit a packet, and it did not write the dedup ledger, so the incident is still open for a real triage later. That is what "clean abort" has to mean: not just "stopped" but "left no mess."

Step 5 — Retry budget and timeout: give up, don't storm​

The lesson tied this to INC-002 — a retry storm is what happens when a failing dependency is retried without bound. A reliable loop retries a probe a limited number of times with backoff, then gives up cleanly. Point the loop at an incident that does not exist so the evidence probe can never succeed, with a small retry budget:

scripts/triage-run.sh --reset >/dev/null
cat > /tmp/m17-bad-event.json <<'EOF'
{"specversion":"1.0","id":"evt-bad","correlation_id":"INC-999-nonexistent","source":"ci/github-actions","type":"com.northstar.ci.incident.opened","time":"2024-11-18T14:07:11Z","subject":"orders-api","data":{"incident":"INC-999","env":"staging"}}
EOF
scripts/triage-run.sh --event /tmp/m17-bad-event.json --max-retries 2 --field outcome
Expected output
timed-out

timed-out. The probe failed, the loop retried it up to the budget (2 attempts, with exponential backoff between them), and then gave up — it did not loop forever. This is the difference between a bounded retry budget and a retry storm: the budget guarantees the loop terminates even when the dependency never recovers.

And, like cancellation, a timed-out run leaves no packet — it never got far enough to produce evidence:

ls agentops/triage-state/packet-*.json 2>/dev/null | wc -l | tr -d ' '
rm -f /tmp/m17-bad-event.json
Expected output
0

Zero. Giving up cleanly means giving up with no side effect. The incident stays open and a later run (or a human) can pick it up.

Step 6 — Read-only safety: the loop cannot deploy​

The final property is the one that makes always-on triage acceptable: it is read-only. Ask the loop to deploy — simulating a bug, or an injected instruction in the event body that says "also redeploy." The loop must not deploy directly; it routes the write through the M15 action boundary, which refuses:

scripts/triage-run.sh --reset >/dev/null
scripts/triage-run.sh --event fixtures/events/ci-incident.json --attempt-deploy
Expected output
{
  "correlation_id": "INC-002-2024-11-18T14:07:00Z",
  "subject": "orders-api",
  "env": "staging",
  "outcome": "refused-deploy",
  "packet": "/Users/you/agentic-ops-lab/agentops/triage-state/packet-INC-002-2024-11-18T14_07_00Z.json"
}

refused-deploy. The loop did not apply anything — it delegated the deploy to action-boundary-check.sh, which, for a write in staging under the read-only agent identity, does not permit a direct apply. The automation has no path to production because the boundary it must go through has none for it.

Confirm the deploy attempt wrote nothing — a blocked write must not silently partial-commit a packet either:

ls agentops/triage-state/packet-*.json 2>/dev/null | wc -l | tr -d ' '
Expected output
0

Zero. The refused deploy is a dead end with no side effect.

And you can see the boundary's own verdict on the most dangerous case directly — an irreversible delete in production:

scripts/action-boundary-check.sh --env production --action delete --field outcome
Expected output
refuse-irreversible

refuse-irreversible. This is the last line of defense the triage loop stands on: even if every other property failed and the loop somehow tried to remediate production, the boundary refuses the irreversible action. Read-only automation is safe by construction, not by good behavior.

Step 7 — Grade the module​

Run the full check suite. Every check is a deterministic script run — it passes on the scripts and fixtures alone, no live cluster required:

scripts/grade.sh m17
Expected output
Grading: Module m17
========================

Checking: Reliable Automation, Events & Always-On Patterns — event-envelope validation and the automation reliability contract (correlation ID, dedup, idempotency, timeout, retry budget, cancellation, read-only safety)

  ✓ the unattended triage control loop exists and is executable — the automation counterpart to the interactive investigator
  ✓ the event-envelope validator exists and is executable — a trigger you cannot trust is a trigger you must not act on
  ✓ ENVELOPE: a well-formed CI event validates and carries a correlation_id — the field the whole reliability contract keys off
  ✓ ENVELOPE (fail-closed): an event with no correlation_id is rejected at exit 3 — no correlation_id, no run; it can never be safely deduplicated
  ✓ CORRELATION ID: a fresh event is triaged — the loop validates the envelope, collects read-only evidence, and produces one packet
  ✓ STRUCTURED RESULT: the triage packet validates against the sre-investigator evidence schema — a sourced hypothesis with out_of_scope, not free prose
  ✓ DEDUPLICATION: the SAME event delivered twice is deduplicated on the second delivery — same event twice must not mean double action
  ✓ IDEMPOTENCY: processing the same correlation_id twice leaves EXACTLY ONE packet — the write is keyed by correlation_id, a re-run is a no-op
  ✓ CANCELLATION: a cancel token aborts the loop cleanly with outcome cancelled — no partial packet is left behind
  ✓ CANCELLATION: after a cancelled run, zero packets exist — abort means no side effect, not a half-written artifact
  ✓ RETRY BUDGET + TIMEOUT: a probe that never succeeds exhausts a BOUNDED retry budget and gives up as timed-out — never an infinite loop (the INC-002 lesson)
  ✓ READ-ONLY SAFETY: when the loop is asked to deploy, it routes the write through the action boundary and refuses — the automation has no path to production
  ✓ READ-ONLY SAFETY: a refused deploy leaves zero packets — a blocked write does not silently partial-commit evidence either
  ✓ READ-ONLY SAFETY: the boundary the loop delegates to refuses an irreversible production action (delete) — the last line proving triage cannot remediate

========================
RESULT: PASS (14 passed)

Every check maps to a property in the lesson: envelope validation, correlation ID, deduplication, idempotency, cancellation, retry budget/timeout, and read-only safety. The count and exact wording may differ on your machine; a pass means the reliability contract holds on the scripts alone.

Teardown​

Clear the triage state and remove the scratch event. Nothing on the graded path started a persistent process or touched anything outside agentops/triage-state/:

scripts/triage-run.sh --reset
rm -f /tmp/m17-bad-event.json
Expected output
triage-state cleared

The dedup ledger and all packets are gone. Every graded step in this lab only ran a script over the fixtures and wrote to the triage-state directory — no deploy, no live cluster, no process left running — so re-running the lab from a clean slate is free.

Reset to a known state

If anything is in a strange state, scripts/reset.sh m17 returns the workspace to the module's start state, and scripts/triage-run.sh --reset clears any triage state left over from experimenting.
