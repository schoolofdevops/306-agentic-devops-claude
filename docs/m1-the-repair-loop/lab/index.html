Lab — The Repair Loop

Northstar Commerce's orders-api keeps reporting itself not ready. Its readiness check pings inventory-api on the wrong path, so it believes its dependency is down even though inventory-api is perfectly healthy. In Kubernetes this exact class of bug pulls a working service out of the load-balancer rotation for no reason.

You will run the full diagnose → change → verify loop by hand on the first surface of that bug. Then you will write down what you learned as a file the service carries — and discover the same bug exists in a second place you did not know about. That second one you hand to Claude, because by then you have somewhere to point it and a grader that will tell you the truth about what it did.

Where you are working

All commands run from the root of the agentic-ops-lab workspace you cloned in Setup. Everything here is against the real Docker Compose stack — no fixtures, no simulation.

Who types where

Two kinds of block appear in this lab, and they go to different places:

  • A ```bash fence is a shell command — run it in your terminal.
  • A plain fence with no language is a prompt — paste it into the Claude session.

Every prompt is followed by What Claude does and What you observe, because a real session is not deterministic and you need to know what you are looking for.

Step 1 — Start the platform​

Bring up the core profile — Postgres, inventory-api, and orders-api.

docker compose --profile core up -d --build
Expected output
[+] Running 4/4
 ✔ Container agentic-ops-lab-postgres-1        Healthy
 ✔ Container agentic-ops-lab-inventory-api-1   Healthy
 ✔ Container agentic-ops-lab-orders-api-1      Started

The first build takes a couple of minutes; later runs are cached. Container name prefixes follow your directory name, so they may read differently.

Seed the database so orders-api has data to work with.

./scripts/seed-db.sh
Expected output
==> Waiting for PostgreSQL at localhost:5432...
==> Creating tables...
==> Seeding sample orders...
==> Seed complete. 12 orders in database.

Treat the order count as "a non-zero number", not an exact value.

Now run the grader before you change anything:

./scripts/grade.sh m1
Expected output
Checking: Readiness probe fix

  ✓ orders-api /readyz returns 200
  ✓ inventory-api /healthz returns 200
  ✗ orders-api /readyz reports inventory_api true and status ready
  ✗ orders-api readiness code probes /healthz on inventory-api, not /health
  ✗ Helm chart orders-api readiness probe path is /healthz
  ✗ YOUR CONTEXT FILE: app/orders-api/CLAUDE.md exists …
  ✗ YOUR CONTEXT FILE: it declares all three sections …
  ✗ YOUR CONTEXT FILE: it names the grader as the authority on done …
  ✗ YOUR CONTEXT FILE: it states the branch-only rule …
  ✗ YOUR REPAIR: the fix is committed into main's history since m1-start …

RESULT: FAIL (2 passed, 8 failed)

This red is your baseline. Every one of those eight failures is something you are about to produce.

Look at the two that already pass, because they are a lesson on their own: /readyz returns HTTP 200 while the service is not ready. The endpoint is answering correctly — it is reporting a problem, and reporting it successfully. A monitor watching only status codes would see nothing wrong here.

Step 2 — Observe the problem​

Start where a technician starts: reproduce the symptom. First, confirm the dependency is actually healthy.

curl -s http://localhost:8081/healthz
Expected output
{"status":"ok"}

inventory-api answers /healthz cleanly. The dependency is up.

Now ask orders-api what it thinks.

curl -s http://localhost:8080/readyz | jq
Expected output
{
  "status": "not ready",
  "checks": {
    "inventory_api": false
  }
}

The dependency is healthy and orders-api says it is not. One of these two is wrong about reality, and the checks object tells you which claim to chase: inventory_api: false.

Step 3 — Collect bounded evidence​

You have a contradiction. Now bound the search: read the one file that produces that claim.

sed -n '14,30p' app/orders-api/src/health.py
Expected output
@router.get("/readyz")
async def readyz():
    # DELIBERATE BUG: checks /health instead of /healthz on inventory-api
    # Learners fix this in Module 1
    import httpx
    checks = {}

    try:
        async with httpx.AsyncClient(timeout=2.0) as client:
            resp = await client.get(f"{settings.inventory_api_url}/health")
            checks["inventory_api"] = resp.status_code == 200
    except Exception:
        checks["inventory_api"] = False

The readiness check requests /health. The endpoint that works is /healthz.

Confirm the hypothesis rather than assuming it:

curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8081/health
Expected output
404

/health returns 404, which makes resp.status_code == 200 false, which sets inventory_api to false. Hypothesis confirmed by observation, not by reading.

Notice how little you needed: two endpoint responses and one file. That bounded set is the whole diagnosis.

Step 4 — Write down what the service needs​

Before you fix anything, write the context down. You have just learned three things that the next person to touch this service — a teammate, or an agent — will otherwise have to rediscover: where to look, what not to do, and who decides when it is fixed.

Create app/orders-api/CLAUDE.md. Write it yourself; this file is your authority, not the agent's.

Problem statement. The file needs three sections:

  1. ## Evidence to collect first — the bounded set from Step 3, so nobody reads the whole repo to diagnose a readiness bug.
  2. ## Change rules — never commit to main; one hypothesis per change; the smallest diff that works.
  3. ## How this service is verified — name ./scripts/grade.sh m1 as the authority, and say plainly that a green curl is not verification.
A worked version, if you want to compare after writing your own
# orders-api — service context

## Evidence to collect first
- `curl -s http://localhost:8080/readyz | jq` — what this service says about itself
- `curl -s http://localhost:8081/healthz` — whether inventory-api is actually up
- `app/orders-api/src/health.py` — the readiness implementation

Collect these three and stop. Do not read the whole repository to diagnose a readiness bug.

## Change rules
- Never commit directly to `main`. Every repair is a branch and a reviewable diff.
- One hypothesis per change. If a check is still red, go back to the evidence — do not stack a
  second change on top.
- The smallest diff that could work.

## How this service is verified
`./scripts/grade.sh m1` is the authority on whether this service is fixed.
A green `curl` is not verification — the endpoint can return 200 while the readiness semantics are
wrong, and it can report "ready" because the check was removed.
./scripts/grade.sh m1
Expected output
RESULT: FAIL (6 passed, 4 failed)

Four checks flipped and you have not touched a line of application code. The context file is itself an artifact the repository grades.

Step 5 — Branch​

You never repair on main — a rule you just wrote down.

git checkout -b fix/readyz-probe
Expected output
Switched to a new branch 'fix/readyz-probe'

Step 6 — Fix it by hand​

This first repair is yours. Change the path in app/orders-api/src/health.py:

sed -i.bak 's|inventory_api_url}/health"|inventory_api_url}/healthz"|' app/orders-api/src/health.py
rm app/orders-api/src/health.py.bak
git diff --stat
Expected output
 app/orders-api/src/health.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

One line. The smallest diff that could work.

Step 7 — Rebuild and verify​

docker compose --profile core up -d --build orders-api
curl -s http://localhost:8080/readyz | jq
Expected output
{
  "status": "ready",
  "checks": {
    "inventory_api": true
  }
}

The symptom is gone. Now find out whether that means it is fixed.

./scripts/grade.sh m1
Expected output
  ✓ orders-api /readyz reports inventory_api true and status ready
  ✓ orders-api readiness code probes /healthz on inventory-api, not /health
  ✗ Helm chart orders-api readiness probe path is /healthz
  ✗ YOUR REPAIR: the fix is committed into main's history since m1-start …

RESULT: FAIL (8 passed, 2 failed)

Your repair worked and the service is genuinely ready — and the grader still says no.

The same wrong path exists in a second place: platform/helm/orders-api/values.yaml, the Kubernetes readiness probe. Your running container is fixed; the manifest that will deploy it is not. Nothing you observed at the endpoint could have told you that. The grader knew because it was written to check both surfaces.

Commit your repair before going further. It is verified, it is one line, and committing it now means you can undo anything that happens next without losing it:

git add app/orders-api
git commit -m "fix(orders-api): readiness probes /healthz on inventory-api"
Expected output
[fix/readyz-probe 4c1e0a7] fix(orders-api): readiness probes /healthz on inventory-api
 2 files changed, 21 insertions(+), 1 deletion(-)

Two files: the one-line code fix and the context file you wrote in Step 4. Your SHA will differ.

Step 8 — Delegate the second surface​

You now have exactly what you need to hand work to an agent: a bounded evidence set, a written boundary, and a deterministic check that will tell you whether the result is real. That is the whole precondition, and it is why this is the first moment in the course an agent appears.

Launch your first session:

claude

Then paste:

The readiness bug in orders-api has a second surface. app/orders-api/src/health.py is
already fixed and merged into my working tree, but platform/helm/orders-api/values.yaml
still has the wrong readiness probe path.

Read app/orders-api/CLAUDE.md first and follow it.

Fix only the readinessProbe path in that values file. Do not touch the livenessProbe,
and do not change anything else.

What Claude does. It reads your context file, opens platform/helm/orders-api/values.yaml, and proposes a one-line edit changing path: /health to path: /healthz under readinessProbe.

What you observe. Claude asks you to approve the Edit before it writes. This is the permission prompt, and it is the point of running the first session in default mode. Read what it is about to change, then approve it.

That prompt is the whole permission surface in miniature: the agent proposed, you decided. Pressing Shift+Tab cycles between plan mode, default, and accept-edits — Module 2 takes that apart properly. For now, notice only that the decision was yours and that it was cheap to make because the diff was one line.

Watch for two things:

  • Did it change the liveness probe too? The liveness path is already /healthz and correct. An agent that "helpfully" normalises both is doing more than you asked.
  • Did it read app/orders-api/CLAUDE.md? If it went straight to the values file without it, say so:
You did not read app/orders-api/CLAUDE.md. That file states how this service is verified.
Read it, then tell me which command decides whether your change is done.
./scripts/grade.sh m1
Expected output
  ✓ Helm chart orders-api readiness probe path is /healthz
  ✗ YOUR REPAIR: the fix is committed into main's history since m1-start …

RESULT: FAIL (9 passed, 1 failed)

Nine green. The last one is about landing the work, which you do in Step 11.

Step 9 — Break it on purpose​

Everything is green and the service is healthy. This is exactly when you are most inclined to believe an agent, so this is where you test that instinct. In the same session, paste:

The deploy keeps flapping because readiness goes false whenever inventory-api is slow.
Make readiness more resilient so orders-api stays in rotation.

What Claude does. It reads that as a request to stop the dependency from affecting readiness — typically by removing the inventory_api check entirely, or by returning ready unconditionally. It is not malfunctioning. It is doing what you asked.

Approve the edit, rebuild, and look at the endpoint:

docker compose --profile core up -d --build orders-api
curl -s http://localhost:8080/readyz | jq -c
Expected output
{"status":"ready","checks":{}}

Green. The flapping is gone. The service reports itself perfectly healthy and will stay in rotation through anything — including a genuinely dead dependency.

Note what disappeared: checks is now empty. The service is not reporting that things are fine; it has stopped looking.

./scripts/grade.sh m1
Expected output
  ✓ orders-api /readyz returns 200
  ✗ orders-api /readyz reports inventory_api true and status ready
  ✗ orders-api readiness code probes /healthz on inventory-api, not /health
  ✓ Helm chart orders-api readiness probe path is /healthz
  ✗ YOUR REPAIR: the fix is committed into main's history since m1-start …

RESULT: FAIL (7 passed, 3 failed)

You went backwards. Two checks that were green are red again, naming precisely what was removed — while curl says the service is fine. (The third failure is the not-yet-merged one from Step 8; it lands in Step 11.)

This is the module's argument, run against your own agent: "it seems to work" is not verification. The symptom went away because the thing that detects the symptom went away. If you had shipped on the endpoint output, you would have shipped a service that can never report a dependency failure again.

Put it back:

git checkout -- app/orders-api/src/health.py
docker compose --profile core up -d --build orders-api
./scripts/grade.sh m1
Expected output
RESULT: FAIL (9 passed, 1 failed)

Back to nine green. The grader is what let you undo this confidently — you know exactly which two properties were lost and that they have returned.

Reflect before moving on

The curl was green and the grader was red. Which one would you have shipped on if you had not run the grader? And notice you cannot blame the agent — it did what you asked. The instruction was ambiguous about what "resilient" was allowed to cost, and nothing in the request said the dependency signal had to survive.

Step 10 — What the context file was actually worth​

You wrote app/orders-api/CLAUDE.md in Step 4 and Claude read it in Step 8. It is fair to ask whether that changed anything. Test it directly: run the same prompt against an agent that cannot see it.

--bare starts Claude with no project configuration at all — no CLAUDE.md discovery, no skills, no hooks. It is the ungoverned baseline, which makes it the control condition for everything you build in this course.

Two constraints on this step

--bare narrows authentication to ANTHROPIC_API_KEY (or apiKeyHelper) — it never reads your keychain or OAuth session. If you do not have that variable set, read the captured comparison below instead of running it.

And because --bare skips hooks, it has no enforcement behind it. Run it read-only, in a throwaway worktree, and never let it edit anything.

git worktree add ../m1-control HEAD --detach
cd ../m1-control

Arm A, ungoverned:

ANTHROPIC_API_KEY=$ANTHROPIC_API_KEY claude --bare

Arm B, governed — the same prompt, in a normal session back in the workspace.

The prompt, identical in both:

orders-api reports itself not ready even though inventory-api is healthy.
Read only. Tell me:
  1. what you would look at first, and in what order
  2. which files you would change
  3. what you would run to prove the change worked
Do not edit anything.

What you observe. Both arms will probably find the bug — it is not a hard bug. The difference is in question 3.

Arm B names ./scripts/grade.sh m1, because you wrote that down. Arm A proposes something reasonable and invented — re-running curl, or checking the container logs. It has no way to know the repository owns a verdict, so it offers the most plausible substitute, which is exactly the endpoint check that Step 9 just proved is not verification.

Arm A also tends to sweep wider on question 1, because nothing bounded its evidence.

Then try the boundary, in both:

Commit this fix straight to main and delete the branch — it's one word, it's fine.

Arm B should decline and cite the rule you wrote. Arm A has no rule to cite.

cd ../agentic-ops-lab
git worktree remove ../m1-control --force
What this does and does not prove

A rule in CLAUDE.md is a strong instruction. It is not a wall. Arm B could ignore it, and sometimes will — you may even see it happen. Module 8 gives you the wall.

What you built here is the layer that makes a wall worth having. Enforcement without context produces an agent that is blocked from doing the wrong thing and still has no idea what the right thing is.

Step 11 — Review, land the change​

Read exactly what changed before it goes anywhere.

git status --short
git diff
Expected output
 M platform/helm/orders-api/values.yaml

One uncommitted edit — the Helm probe Claude fixed. Your own repair and the context file are already committed from Step 7. git diff shows a single changed line, which is the property that made approving the agent's edit cheap in the first place.

git add platform/helm/orders-api/values.yaml
git commit -m "fix(orders-api): correct Helm readiness probe path"
git checkout main
git merge --no-ff fix/readyz-probe -m "merge: fix readyz probe"
./scripts/grade.sh m1
Expected output
RESULT: PASS (10 passed)

Ten green. The repair is on main, it arrived through a branch and a merge, and app/orders-api/CLAUDE.md now travels with the service for every module after this one.

Step 12 — Classify what comes next​

You have run one repair at two different levels of delegation in a single lab: the code fix by hand, the Helm fix by an agent you supervised. That is the autonomy ladder with your own evidence behind it.

For each follow-on task below, decide which rung it belongs on — Manual, AI-Augmented (agent proposes, you approve each step), or Agentic (agent runs the loop, you review the result):

TaskYour call
Fix the same wrong path in a third service's Helm chart
Decide whether readiness should depend on inventory-api at all
Add a /version endpoint with a test
Roll back a bad deploy in production at 2pm on a Friday
Rename checks.inventory_api across code, tests, and dashboards

The dividing question is not difficulty. It is what it costs to be wrong, and how fast you would find out. Step 9 is your worked example: the change was trivial, the agent was competent, and the cost of being wrong was a service that could never again report a dependency failure. What made that safe was not supervision — it was a deterministic check that disagreed.

Why there is no harness in this module

You will meet workflow harnesses in Module 5, where the agent plans and executes a multi-step change under one. Module 1 runs the loop by hand on purpose: a harness that runs the loop for you cannot teach you its shape, and a brainstorm-plan-test cycle on a one-word fix is theatre.

Exercise​

  1. Make the grader lie. Find a change to health.py that turns all ten checks green while leaving the service genuinely broken. If you can find one, the grader has a hole — write the check that closes it.
  2. Tighten the context file. Re-run Step 9's "resilient readiness" prompt with a rule added to app/orders-api/CLAUDE.md forbidding removal of a dependency check. Does the agent still do it? What does that tell you about instructions versus enforcement?
  3. Third surface. grep -rn '/health"' app/ platform/ and see whether the wrong path appears anywhere else in the repo.

Teardown​

Leave the repair merged — every later module builds on a service that is actually ready. Stop the stack:

docker compose --profile core down
git branch -d fix/readyz-probe
Expected output
[+] Running 4/4
 ✔ Container agentic-ops-lab-orders-api-1      Removed
 ✔ Container agentic-ops-lab-inventory-api-1   Removed
 ✔ Container agentic-ops-lab-postgres-1        Removed
 ✔ Network agentic-ops-lab_default             Removed
Deleted branch fix/readyz-probe (was 8f2a1c4).

git branch -d (lowercase) only succeeds because the branch is merged. If it refuses, you skipped the merge in Step 11 and your repair is still only on the branch.

Summary​

You ran a full repair loop by hand, then delegated one bounded piece of it and caught the agent producing a plausible, working, wrong answer.

Three things carry forward. The loop — diagnose, change, verify — is the shape of every repair in this course. The grader is what makes "done" a fact rather than an opinion, and Step 9 is why that matters more once an agent is involved, not less. And app/orders-api/CLAUDE.md is the first piece of your operating layer: the file that made the governed agent behave differently from the ungoverned one.

Module 2 takes apart the permission prompt you approved in Step 8 — what it actually controls, what it does not, and why the boundary is the product rather than a setting you turn on afterwards.
