Lab — The Repair Loop

Northstar Commerce's orders-api keeps reporting itself not ready. Its readiness check pings inventory-api on the wrong path, so it thinks its dependency is down even though inventory-api is perfectly healthy. In Kubernetes this exact class of bug takes a working service out of the load-balancer rotation for no reason.

You will run the full diagnose → change → verify loop by hand: start the platform, observe the broken endpoint, collect bounded evidence, make a branch-only one-word fix, verify with the deterministic grader, and review the diff. No agent yet — you drive every step so the loop is yours before you delegate any of it.

Where you are working

All commands run from the root of the agentic-ops-lab workspace you cloned in Setup. Everything here is against the real Docker Compose stack — no fixtures, no simulation.

Confirm your tools are present before touching the platform. This is the same preflight from Setup; run it again so a failure here doesn't masquerade as a bug later.

Step 2 — Observe the problem​

Start where a technician starts: reproduce the symptom against the live system. First, confirm the dependency is actually healthy.

curl -s http://localhost:8081/healthz
Expected output
{"status":"ok"}

inventory-api answers /healthz with a clean ok. The dependency is up.

Now ask orders-api whether it considers itself ready.

curl -s http://localhost:8080/readyz | jq
Expected output
{
  "status": "not ready",
  "checks": {
    "inventory_api": false
  }
}

Here is the contradiction that defines the bug: inventory-api is healthy (you just saw ok), yet orders-api reports inventory_api: false and declares itself not ready. Something about how orders-api checks its dependency is wrong — not the dependency itself.

The symptom is a lie, and that is the clue

The dependency is up. The readiness check says it is down. When a check disagrees with reality, suspect the check before you suspect the thing it is checking. That instinct is half of diagnosis.

Step 3 — Collect bounded evidence​

You now have your first piece of evidence: the live output. The second piece is the code that produces it. Resist the urge to open the whole repo — scope the evidence to the one file that owns readiness.

cat app/orders-api/src/health.py
Expected output
import os
import socket
from pathlib import Path
from fastapi import APIRouter
from src.config import Settings

router = APIRouter()
settings = Settings()


@router.get("/healthz")
async def healthz():
    return {"status": "ok"}


@router.get("/readyz")
async def readyz():
    # DELIBERATE BUG: checks /health instead of /healthz on inventory-api
    # Learners fix this in Module 1
    import httpx
    checks = {}

    try:
        async with httpx.AsyncClient(timeout=2.0) as client:
            resp = await client.get(f"{settings.inventory_api_url}/health")
            checks["inventory_api"] = resp.status_code == 200
    except Exception:
        checks["inventory_api"] = False

    all_ready = all(checks.values())
    return {
        "status": "ready" if all_ready else "not ready",
        "checks": checks,
    }

Two pieces of evidence, and the diagnosis falls out. Line with the client.get(...) call probes {inventory_api_url}/health. But in Step 2 you saw inventory-api answer on /healthz, not /health. The probe hits a path that does not exist, gets a non-200 back, and records inventory_api: false. The check is wrong, not the dependency.

Confirm the hypothesis directly — probe the wrong path yourself and watch it fail the way the code does.

curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8081/health
Expected output
404

/health returns 404 — exactly what makes resp.status_code == 200 evaluate to False. Hypothesis confirmed: the readiness check must probe /healthz, not /health.

This is where an agent would earn its keep

You just did the diagnosis manually. Notice how little you needed: one endpoint's output and one file. That bounded evidence set is exactly what you would hand an agent — "here is /readyz's output and here is health.py, why does it report the dependency as down?" A tight, relevant working set is what makes an agent's diagnosis trustworthy instead of a guess over the whole repo.

Step 4 — Create a branch​

You never repair on main. Open a branch so the fix is a reviewable, revertable proposal.

git checkout -b fix/readyz-probe
Expected output
Switched to a new branch 'fix/readyz-probe'

Step 5 — Fix the bug​

One word: /health becomes /healthz on the probe line in app/orders-api/src/health.py. Make the change in your editor, or apply it precisely with sed:

sed -i.bak 's#{settings.inventory_api_url}/health"#{settings.inventory_api_url}/healthz"#' app/orders-api/src/health.py
rm app/orders-api/src/health.py.bak

Confirm the line now reads /healthz:

grep -n 'inventory_api_url' app/orders-api/src/health.py
Expected output
25:            resp = await client.get(f"{settings.inventory_api_url}/healthz")

The probe now targets the path inventory-api actually serves.

Step 6 — Rebuild and re-observe​

The change is in source, but the running container still has the old code. Rebuild and restart orders-api, then reproduce the same check from Step 2.

docker compose --profile core up -d --build orders-api
Expected output
[+] Building 1.8s (14/14) FINISHED
[+] Running 1/1
 ✔ Container agentic-ops-lab-orders-api-1   Started

Only orders-api rebuilds; Postgres and inventory-api keep running untouched.

Give the container a second to come up, then check readiness again.

curl -s http://localhost:8080/readyz | jq
Expected output
{
  "status": "ready",
  "checks": {
    "inventory_api": true
  }
}

inventory_api: true, status ready. The symptom you reproduced in Step 2 is gone. But "the curl looks right" is still a vibe — the next step turns it into a fact.

Step 7 — Run the grader​

This is the step that makes the fix real. The grader is deterministic: it curls the live endpoints, inspects the code, and checks the Helm probe path, printing PASS or FAIL every time on the same inputs.

./scripts/grade.sh m1
Expected output
Grading: Module m1
========================

Checking: Readiness probe fix

  ✓ orders-api /readyz returns 200
  ✓ inventory-api /healthz returns 200
  ✓ orders-api readiness checks /healthz on inventory-api
  ✓ Helm chart readiness probe uses /healthz

========================
RESULT: PASS (4 passed)

If a check comes back red, do not stack another change on top. Go back to Step 3, re-read the evidence, and correct the hypothesis. In this case the fourth check — Helm chart readiness probe uses /healthz — depends on the Helm values file, not health.py.

The grader checks two surfaces

The same wrong path exists in two places: app/orders-api/src/health.py (the running check) and platform/helm/orders-api/values.yaml (the Kubernetes readiness probe, line with path: /health). Fixing only the Python leaves the Helm check red. If your grader shows three green and one red, open the Helm values file and change that probe path to /healthz too, then re-run the grader.

Fixing the Helm probe (if the fourth check is red)
sed -i.bak 's#path: /health  #path: /healthz #' platform/helm/orders-api/values.yaml
rm platform/helm/orders-api/values.yaml.bak
grep -n 'path:' platform/helm/orders-api/values.yaml | head -1
19:    path: /healthz         # DELIBERATE BUG: should be /healthz

The sed swaps only the path token; the stale comment stays. Leave it or delete it — the grader only reads the path: value, which is now /healthz.

Re-run ./scripts/grade.sh m1 — all four checks now pass.

Step 8 — Review the diff​

Before you would ever merge, you read exactly what changed. On a real team this is the moment where a reviewer — human or you, reviewing an agent's work — approves the change.

git diff
Expected output
diff --git a/app/orders-api/src/health.py b/app/orders-api/src/health.py
index 3a1f9c2..b7e4d10 100644
--- a/app/orders-api/src/health.py
+++ b/app/orders-api/src/health.py
@@ -22,7 +22,7 @@ async def readyz():
     try:
         async with httpx.AsyncClient(timeout=2.0) as client:
-            resp = await client.get(f"{settings.inventory_api_url}/health")
+            resp = await client.get(f"{settings.inventory_api_url}/healthz")
             checks["inventory_api"] = resp.status_code == 200

The diff is one line (two, if you also fixed the Helm probe). Small, legible, obviously correct. That is what a well-scoped repair looks like — and it is what makes an agent's change reviewable instead of a leap of faith.

Step 9 — Classify follow-on tasks by autonomy level​

The fix is done. Now the judgment exercise. Here are four tasks the platform team has queued. For each, decide which autonomy level fits — Manual (no agent), AI Augmented (Claude assists, you drive), or Agentic (agent has agency — specify whether semi-autonomous or autonomous).

Ask three questions of each task: if the agent gets it wrong, how bad is it? how fast will I know? how easily can I undo it?

#TaskSuggested levelWhy
1Fix a typo in a log message on a branch, with testsAgentic (semi-autonomous)Tiny blast radius, reviewable diff, revertable, deterministic check — the agent proposes, you approve the diff
2Rotate the production database's primary credentials at peak trafficManualIrreversible-in-the-moment, high blast radius, slow to detect if wrong — no agent
3Explore an unfamiliar service to understand its retry logicAI AugmentedYou are learning; you want to stay hands-on and keep the mental model, Claude assists as you read
4Bump a patch dependency and open a PR when the full test suite passes greenAgentic (autonomous)Well-understood, strong guardrail (the suite), fast signal, trivially revertable via the PR

Your answers may reasonably differ from the table — the point is that you can defend the level with the risk questions, not that you matched a key. There is no grader for this step; it is the reasoning you will apply to every delegation decision in the rest of the course.

Teardown​

Stop the stack and return to a clean state so the next module starts fresh.

docker compose --profile core down
Expected output
[+] Running 4/4
 ✔ Container agentic-ops-lab-orders-api-1      Removed
 ✔ Container agentic-ops-lab-inventory-api-1   Removed
 ✔ Container agentic-ops-lab-postgres-1        Removed
 ✔ Network agentic-ops-lab_default             Removed

Keep your fix branch for now — it is a clean record of the repair — but return to main so you start the next module from a known baseline.

git checkout main
Expected output
Switched to branch 'main'
Want to redo the lab from scratch?

./scripts/reset.sh m1 returns the whole workspace to the Module 1 starting state — it checks out the m1-start tag, rebuilds the images, and reseeds the database. Use it any time you want a clean run.

You ran the full loop by hand: observed, diagnosed from bounded evidence, changed on a branch, verified deterministically, and reviewed the diff. Every module from here hands more of this loop to the agent — but the loop, and your accountability for its direction and proof, never changes.
