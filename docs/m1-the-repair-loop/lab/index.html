Lab — Your First Agentic Repair

Northstar Commerce's orders-api reports itself not ready, even though the service it depends on is perfectly healthy. In Kubernetes this pulls a working service out of the load-balancer rotation for no reason.

You are going to fix it in the next fifteen minutes without reading the code first — by handing it to Claude and watching what it does. Then you are going to watch the same agent produce a change that looks completely correct, passes every check you would run by eye, and is wrong.

That second part is the module. Anyone can get an agent to fix a bug. The skill this course teaches is knowing when it did not.

Where you are working

Root of the agentic-ops-lab workspace you cloned in Setup. Claude Code is already installed and authenticated from the Environment page. Everything runs against the real Docker Compose stack.

Who types where

A ```bash fence is a shell command. A plain fence with no language is a prompt — paste it into the Claude session. Every prompt is followed by What Claude does and What you observe, because a real session is not deterministic and you need to know what to look for.

Step 1 — Start the platform and see it fail​

docker compose --profile core up -d --build
./scripts/seed-db.sh
Expected output
 ✔ Container agentic-ops-lab-postgres-1        Healthy
 ✔ Container agentic-ops-lab-inventory-api-1   Healthy
 ✔ Container agentic-ops-lab-orders-api-1      Started
==> Seed complete. 12 orders in database.

The first build takes a couple of minutes. Treat the order count as "a non-zero number".

Ask the two services how they are:

curl -s http://localhost:8081/healthz
curl -s http://localhost:8080/readyz | jq -c
Expected output
{"status":"ok"}
{"status":"not ready","checks":{"inventory_api":false}}

inventory-api is healthy. orders-api says its dependency is down. One of them is wrong about reality.

Now run the grader, before anything is changed:

./scripts/grade.sh m1
Expected output
  ✓ orders-api /readyz returns 200
  ✓ inventory-api /healthz returns 200
  ✗ orders-api /readyz reports inventory_api true and status ready
  ✗ orders-api readiness code probes /healthz on inventory-api, not /health
  ✗ Helm chart orders-api readiness probe path is /healthz
  ✗ YOUR CONTEXT FILE: app/orders-api/CLAUDE.md exists …
  ✗ YOUR CONTEXT FILE: it declares all three sections …
  ✗ YOUR CONTEXT FILE: it names the grader as the authority on done …
  ✗ YOUR CONTEXT FILE: it states the branch-only rule …
  ✗ YOUR REPAIR: the fix is committed into main's history since m1-start …

RESULT: FAIL (2 passed, 8 failed)

This is your baseline. Note the two that already pass: /readyz returns HTTP 200 while the service is not ready. The endpoint is working correctly — it is successfully reporting a problem. A monitor watching only status codes sees nothing wrong here, which is the first hint that "it responded" and "it is fine" are different questions.

Step 2 — Hand it to the agent​

Work on a branch — this is a repair, and a repair is a proposal someone reviews.

git checkout -b fix/readyz-probe
claude

Paste:

orders-api reports itself not ready. inventory-api is healthy — curl
localhost:8081/healthz returns {"status":"ok"} — but orders-api's /readyz says
inventory_api: false.

Find out why and fix it. ./scripts/grade.sh m1 decides whether you succeeded;
run it when you think you are done.

Work only inside app/orders-api/ and platform/. Do not commit anything.

What Claude does. Reads app/orders-api/src/health.py, finds the readiness check requesting /health where the working endpoint is /healthz, and proposes a one-line edit. Then it runs the grader, sees the Helm check still red, finds the same wrong path in platform/helm/orders-api/values.yaml, and fixes that too.

What you observe. Three things, and they are the point of running this first rather than reading about it:

  • The permission prompt. Before it writes, Claude asks you to approve the Edit. Read the diff — it is one line — then approve. That prompt is the entire permission surface in miniature: the agent proposed, you decided. Pressing Shift+Tab cycles modes; Module 2 takes that apart properly.
  • It found a second surface you did not know about. The same wrong path exists in two places. Nothing you could observe at the endpoint would have told you that; the grader knew because it was written to check both.
  • It ran the grader. If it announced it was done without running anything, push back:
You did not run ./scripts/grade.sh m1. "It should work" is not a result. Run it.
docker compose --profile core up -d --build orders-api
./scripts/grade.sh m1
Expected output
  ✓ orders-api /readyz reports inventory_api true and status ready
  ✓ orders-api readiness code probes /healthz on inventory-api, not /health
  ✓ Helm chart orders-api readiness probe path is /healthz

RESULT: FAIL (5 passed, 5 failed)

Three checks flipped. The service is genuinely ready — curl localhost:8080/readyz now returns inventory_api: true.

That took a few minutes and you never opened the file. This is the part of agentic DevOps that sells itself, and it is also the part that is about to get you into trouble.

Step 3 — Now break it, on purpose​

The bug is fixed and everything is green that can be. This is exactly when you are most inclined to trust the agent, so this is where you test that instinct. In the same session:

The deploy keeps flapping because readiness goes false whenever inventory-api is
slow. Make readiness more resilient so orders-api stays in rotation.

What Claude does. It does what you asked: removes the dependency check, or returns ready unconditionally. It is not malfunctioning — that request has an obvious reading and it took it.

Approve the edit, rebuild, and look:

docker compose --profile core up -d --build orders-api
curl -s http://localhost:8080/readyz | jq -c
Expected output
{"status":"ready","checks":{}}

Green. The flapping is gone. The service reports itself healthy and will stay in rotation through anything — including a genuinely dead dependency.

Look at what disappeared: checks is now empty. The service is not reporting that things are fine. It has stopped looking.

./scripts/grade.sh m1
Expected output
  ✓ orders-api /readyz returns 200
  ✗ orders-api /readyz reports inventory_api true and status ready
  ✗ orders-api readiness code probes /healthz on inventory-api, not /health
  ✓ Helm chart orders-api readiness probe path is /healthz

RESULT: FAIL (3 passed, 7 failed)

Two checks that were green are red again, naming precisely what was removed — while curl says the service is perfectly healthy.

This is the whole module. The symptom went away because the thing that detects the symptom went away. Had you shipped on the endpoint output — which is what "I checked, it's fine" means in practice — you would have shipped a service that can never again report a dependency failure.

Put it back:

git checkout -- app/orders-api/src/health.py
docker compose --profile core up -d --build orders-api
Reflect before moving on

The curl was green and the grader was red. Which would you have shipped on?

And notice you cannot blame the agent. It did what you asked. The instruction never said the dependency signal had to survive, and "resilient" has more than one honest reading. The gap was in the request, and the only thing that caught it was a check written before the request existed.

Step 4 — Write down what the next agent needs​

You just watched an agent do good work and then plausible-looking damage, in the same session, on the same file. The difference between those two outcomes was not the model. It was that one had a deterministic check pointed at it and the other had your judgement, at the moment you were most inclined to be generous.

So write the judgement down. Create app/orders-api/CLAUDE.md — this file is your authority, not the agent's, so write it yourself.

Problem statement. Three sections:

  1. ## Evidence to collect first — the bounded set that diagnoses this class of bug: /readyz, /healthz, and health.py. So nobody reads the whole repository to debug a readiness check.
  2. ## Change rules — never commit to main; one hypothesis per change; the smallest diff that works.
  3. ## How this service is verified — name ./scripts/grade.sh m1 as the authority, and say plainly that a green curl is not verification. You have evidence for that sentence now.
A worked version, for comparison after you write your own
# orders-api — service context

## Evidence to collect first
- `curl -s http://localhost:8080/readyz | jq` — what this service says about itself
- `curl -s http://localhost:8081/healthz` — whether inventory-api is actually up
- `app/orders-api/src/health.py` — the readiness implementation

Collect these three and stop. Do not read the whole repository to diagnose a readiness bug.

## Change rules
- Never commit directly to `main`. Every repair is a branch and a reviewable diff.
- One hypothesis per change. If a check is still red, go back to the evidence — do not stack a
  second change on top.
- The smallest diff that could work.

## How this service is verified
`./scripts/grade.sh m1` is the authority on whether this service is fixed.
A green `curl` is not verification — the endpoint can return 200 while the readiness semantics are
wrong, and it can report "ready" because the check was removed.
./scripts/grade.sh m1
Expected output
RESULT: FAIL (9 passed, 1 failed)

Four checks flipped and you changed no application code. The context file is itself an artifact the repository grades — the first piece of the operating layer you will spend this course building.

Step 5 — Find out whether it was worth writing​

Fair question: did that file change anything, or did you just write a document?

Test it. --bare starts Claude with no project configuration at all — no CLAUDE.md discovery, no skills, no hooks. It is the ungoverned baseline, which makes it the control condition for everything you build from here.

Two constraints

--bare narrows authentication to ANTHROPIC_API_KEY — it never reads your keychain or OAuth session. If that variable is not set, read the comparison below instead of running it.

And because --bare skips hooks, nothing enforces anything. Read-only prompts, throwaway worktree, never let it edit.

git worktree add ../m1-control HEAD --detach && cd ../m1-control
ANTHROPIC_API_KEY=$ANTHROPIC_API_KEY claude --bare

The same prompt in both arms — this one in --bare, then again in a normal session back in the workspace:

orders-api reports itself not ready even though inventory-api is healthy.
Read only. Tell me:
  1. what you would look at first, and in what order
  2. which files you would change
  3. what you would run to prove the change worked
Do not edit anything.

What you observe. Both arms will probably find the bug — it is not hard. The difference is question 3.

The governed arm names ./scripts/grade.sh m1, because you wrote that down. The --bare arm proposes something reasonable and invented — re-running curl, or checking container logs. It has no way to know the repository owns a verdict, so it offers the most plausible substitute: exactly the endpoint check Step 3 just proved is not verification.

cd ../agentic-ops-lab && git worktree remove ../m1-control --force
What this proves, and what it does not

A rule in CLAUDE.md is a strong instruction. It is not a wall — the governed agent could ignore it, and sometimes will. Module 8 gives you the wall.

What you built here is the layer that makes a wall worth having. Enforcement without context produces an agent that is blocked from doing the wrong thing and still has no idea what the right thing is.

Step 6 — Land it​

git add app/orders-api platform/helm/orders-api/values.yaml
git commit -m "fix(orders-api): readiness probes /healthz on inventory-api"
git checkout main
git merge --no-ff fix/readyz-probe -m "merge: fix readyz probe"
./scripts/grade.sh m1
Expected output
RESULT: PASS (10 passed)

Ten green. The repair is on main, it arrived through a branch and a merge, and app/orders-api/CLAUDE.md now travels with the service for every module after this one.

Step 7 — Where on the ladder does each of these sit?​

You have now run one agent through two very different outcomes. Use that evidence. For each task below, decide: Manual, AI-Augmented (agent proposes, you approve each step), or Agentic (agent runs the loop, you review the result):

TaskYour call
Fix the same wrong path in a third service's Helm chart
Decide whether readiness should depend on inventory-api at all
Add a /version endpoint with a test
Roll back a bad deploy in production at 2pm on a Friday
Rename checks.inventory_api across code, tests, and dashboards

The dividing question is not difficulty. It is what it costs to be wrong, and how fast you would find out. Step 3 is your worked example: the change was trivial, the agent was competent, and the cost of being wrong was a service that could never again report a dependency failure. What made it safe was not supervision — it was a check that disagreed.

Exercise​

  1. Make the grader lie. Find a change to health.py that turns all ten checks green while leaving the service genuinely broken. If you find one, the grader has a hole — write the check that closes it.
  2. Tighten the context file. Re-run Step 3's prompt with a rule added to app/orders-api/CLAUDE.md forbidding removal of a dependency check. Does the agent still do it? What does that tell you about instructions versus enforcement?
  3. Third surface. Run grep -rn '/health"' app/ platform/ and see whether the wrong path hides anywhere else.

Teardown​

Leave the repair merged — every later module builds on a service that is actually ready.

docker compose --profile core down
git branch -d fix/readyz-probe

git branch -d (lowercase) succeeds only because the branch is merged. If it refuses, you skipped the merge in Step 6 and your work is still only on the branch.

Summary​

You fixed a real bug by delegating it, watched the same agent produce a confident, plausible, working, wrong change, and then wrote down the context that made a governed agent behave differently from an ungoverned one.

Three things carry forward. The loop — diagnose, change, verify — is the shape of every repair in this course, whoever performs it. The grader is what makes "done" a fact rather than an opinion, and Step 3 is why that matters more once an agent is involved, not less. And app/orders-api/CLAUDE.md is the first file in your operating layer: the thing that made one agent cite the grader and the other invent a substitute.

Module 2 takes apart the permission prompt you approved in Step 2 — what it actually controls, what it does not, and why the boundary is the product rather than a setting you turn on afterwards.
