Lab — Agent-Authored Terraform

Northstar's Black Friday campaign starts in nine days. The orders database is absorbing read traffic it was not sized for, and the platform team has asked for a read replica plus alarming before the campaign opens.

You are going to have Claude author that module — not inspect one that ships pre-written. You will give it the house style as a skill, drive the build with the superpowers harness, verify it offline with no AWS account, produce a real plan from your own module, and run that plan through the review chain the lesson described. Then you will try to apply it to production and watch the Change Gate refuse.

By the end you will have a module you could open a PR against, and a verdict you can defend to a reviewer: not "the agent said it looked fine," but "here is the plan my module actually produces, here is what each review stage said about it, and here is the gate that stops it reaching production without a human."

Where you are working

Start at the root of the agentic-ops-lab workspace. Northstar's Terraform estate is under infra/ — four existing modules (networking, database, compute, storage) and three environments. You will add a fifth module. The review scripts (plan-analyze.sh, tf-security-scan.sh, change-pipeline.sh) are in scripts/; they read plan JSON and do not care whether it came from a fixture or from you.

No AWS account is needed. You will author, test, and plan entirely offline.

Step 0 — Tools and posture​

Confirm your tools:

terraform version | head -1
jq --version
claude --version
Expected output
Terraform v1.14.8
jq-1.7.1
2.1.197 (Claude Code)

Versions will differ. Terraform must be 1.7 or higher — mock_provider does not exist before 1.7 and you will use it in Step 3.

This lab runs Claude in bypass mode inside a git worktree:

claude --dangerously-skip-permissions

That is a deliberate choice, and it is worth being precise about why. A superpowers build is a long cycle — brainstorm, plan, write a failing test, implement, refactor, review — across dozens of file edits. Approving each one individually does not teach you anything about permissions; it teaches you to stop reading the prompts. So you drop the prompts and rely on the layer underneath them.

You can do that safely here for two reasons. The work happens in a throwaway worktree, so the blast radius is a directory you delete at the end. And PreToolUse hooks run before the permission check — the Change Gate you built in Module 8 still fires in bypass mode. You will prove that yourself in Step 8.

What bypass mode does not excuse

Bypass mode removes the prompt, not the consequences. Never run it against a directory you cannot afford to lose, and never on a machine with production credentials in the environment. The worktree is the trust boundary in this lab — not the flag.

Step 1 — Create the isolated workspace​

The IaC Engineer authors on its own branch so main stays clean while the change is reviewed:

git worktree add -b m11-campaign-change ../m11-campaign HEAD
cd ../m11-campaign
git worktree list
Expected output
Preparing worktree (new branch 'm11-campaign-change')
HEAD is now at 3adb15b feat: add contracts, evals, fault configs, .claude config, and project docs
/Users/you/agentic-ops-lab            3adb15b [main]
/Users/you/m11-campaign               3adb15b [m11-campaign-change]

Your SHA and paths will differ. Unlike a scratch directory, this worktree is going to end the lab with commits in it.

Step 2 — Write the context that will produce the code​

There is no starter main.tf in this lab, and that is the point. On a real platform team you are usually writing a module that has no reference implementation to copy. What you write instead is the context — and the context is the engineering artifact.

Create infra/modules/read-replica/CLAUDE.md:

mkdir -p infra/modules/read-replica/tests

Then write the file. Paste this into your editor as infra/modules/read-replica/CLAUDE.md:

# Read Replica Module — Northstar Campaign

## What we are building
A Terraform module that adds read capacity ahead of the Black Friday campaign:
- 1 RDS read replica of the existing orders database
- 1 CloudWatch alarm on replica lag
- 1 SNS topic with an email subscription for that alarm

## Constraints
- Must follow the house style in the `terraform-style` skill. Read it first.
- Must verify offline: `terraform test` with `mock_provider`, and a credential-skipped plan.
- Variables: project (string, default "northstar"), environment (string, no default),
  source_db_identifier (string), instance_class (string, default "db.r6g.large"),
  replica_lag_threshold (number, default 30), notification_email (string)
- Outputs: replica_identifier, replica_endpoint, alarm_arn, sns_topic_arn

## Architecture
- `aws_db_instance.replica` with `replicate_source_db = var.source_db_identifier`
- `storage_encrypted = true`, `publicly_accessible = false` — both non-negotiable
- Alarm fires on lag above threshold for 2 consecutive 5-minute periods:
  `namespace = "AWS/RDS"`, `metric_name = "ReplicaLag"`,
  `comparison_operator = "GreaterThanThreshold"`, `evaluation_periods = 2`,
  `period = 300`, `treat_missing_data = "notBreaching"`
- SNS subscription uses `protocol = "email"`

## How to build this (non negotiable)
Use superpowers, to the maximum of its capabilities:
  * brainstorming — before any code. Refine the design, present it for validation.
  * writing-plans — break the work into small tasks with exact file paths.
  * test-driven-development — RED before GREEN. Write the failing test, watch it fail,
    then write the minimum code to pass. Delete any code written before its test.
  * requesting-code-review — between tasks, against the plan and the style skill.
Why the exact AWS strings are in there

ReplicaLag not ReplicationLag. GreaterThanThreshold not GreaterThanOrEqualToThreshold. notBreaching not not_breaching. Those are the values models most often get subtly wrong for this resource — near-misses that validate and then behave incorrectly. Writing them into the context is pre-correcting a known failure mode, and it is the single highest-leverage thing in this file.

The same list lives in the terraform-style skill's vocabulary table, which is why the constraints section points the agent at the skill before it writes anything.

Step 3 — Write the test first, and watch it fail​

The test file must exist before any .tf file. The resource addresses you assert here become the contract the generated HCL has to satisfy.

Create infra/modules/read-replica/tests/unit.tftest.hcl:

mock_provider "aws" {}

variables {
  environment          = "prod"
  source_db_identifier = "northstar-prod-db"
  notification_email   = "platform@northstar.example"
}

run "replica_is_created" {
  command = plan
  assert {
    condition     = module.read_replica.replica_identifier != ""
    error_message = "Read replica must be created with an identifier"
  }
}

And the offline harness that calls the module, infra/modules/read-replica/tests/harness.tf:

terraform {
  required_version = ">= 1.7"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region                      = "us-east-1"
  access_key                  = "mock_access_key"
  secret_key                  = "mock_secret_key"
  skip_credentials_validation = true
  skip_requesting_account_id  = true
  skip_metadata_api_check     = true
  skip_region_validation      = true
}

module "read_replica" {
  source               = "../"
  environment          = "prod"
  source_db_identifier = "northstar-prod-db"
  notification_email   = "platform@northstar.example"
}

Now see it fail:

terraform -chdir=infra/modules/read-replica/tests init -input=false >/dev/null
terraform -chdir=infra/modules/read-replica/tests validate
Expected output
╷
│ Error: Unsupported argument
│
│   on harness.tf line 23, in module "read_replica":
│   23:   environment          = "prod"
│
│ An argument named "environment" is not expected here.
╵
╷
│ Error: Unsupported argument
│
│   on harness.tf line 24, in module "read_replica":
...

One error per variable the module does not declare — because the module declares nothing yet. This is your RED state: the contract is written, and nothing satisfies it.

Read the error carefully, because it is easy to misread as a typo in your harness. Terraform is not saying environment is misspelled; it is saying the module at ../ has no such variable, which is true — there is no variables.tf there at all.

Step 4 — Let the agent author the module​

Launch the session from the worktree root:

claude --dangerously-skip-permissions

Then give it the single harness prompt. Paste this into the session:

Read infra/modules/read-replica/CLAUDE.md and build this module.

Use the terraform-style skill for the house conventions — read it before writing HCL.
Use superpowers to the maximum of its capabilities: brainstorm the design first, write
a plan, then work test-driven against the existing tests/unit.tftest.hcl.

The test and harness already exist. Do not modify them — make them pass.
Do not run terraform apply at any point.

What Claude does. It reads the context and the style skill, brainstorms the resource inventory, plans the file set, then authors main.tf, variables.tf and outputs.tf against the test contract. Expect it to work in several passes rather than emitting three finished files at once.

What you observe. Watch for three things specifically, because they are where this goes wrong:

  • Does it read terraform-style before writing, or after you remind it? The skill's description field is what triggers it — if it did not fire, that is a lesson about trigger wording, not about the model.
  • Does it use aws_db_instance.replica, or does it reach for .this? The house rule is a role noun.
  • Does it hardcode "northstar-prod-db-replica" instead of interpolating "${var.project}-${var.environment}-db-replica"?

If any of those slip, push back in the session rather than fixing it yourself:

You hardcoded the identifier. The terraform-style skill requires every physical name to be
interpolated as "${var.project}-${var.environment}-<role>". Fix it and re-run the check.

Correcting the agent against a written standard is the skill this module teaches. A style skill that only you enforce is a document; a style skill the agent is held to is a control.

Step 5 — Verify offline​

terraform -chdir=infra/modules/read-replica fmt -check -diff; echo "fmt exit=$?"
terraform -chdir=infra/modules/read-replica/tests init -input=false >/dev/null
terraform -chdir=infra/modules/read-replica/tests validate
Expected output
fmt exit=0
Success! The configuration is valid.

fmt exits 0 with no diff when the formatting matches. validate runs from the tests directory, not the module directory — a bare module directory has no provider and exits 1 with Missing required provider, which is a setup error rather than a finding about your code.

Step 6 — Produce a real plan from your own module​

This is where the lab stops using shipped fixtures. Your module produces its own plan:

cd infra/modules/read-replica/tests
terraform plan -out=tfplan -input=false >/dev/null
terraform show -json tfplan > plan.json
jq -r '.resource_changes[] | "\(.address)  \(.change.actions|join(","))"' plan.json
cd -
Expected output
module.read_replica.aws_cloudwatch_metric_alarm.lag  create
module.read_replica.aws_db_instance.replica  create
module.read_replica.aws_sns_topic.alerts  create
module.read_replica.aws_sns_topic_subscription.email  create

Four resources, all create. The credentials are fake; the resource graph is real. This is genuine terraform show -json output in exactly the form the review scripts consume — which is why the next step needs no special handling for the fact that you generated it.

Step 7 — Run your plan through the review chain​

Stage one is structural: what is being touched, what is replaced, is any of it stateful.

scripts/plan-analyze.sh infra/modules/read-replica/tests/plan.json --field json
Expected output
{
  "total_resources": 4,
  "blast_radius": 4,
  "destroy_count": 0,
  "replacements": [],
  "stateful_replaced": [],
  "verdict": "clean"
}

Four resources touched, nothing destroyed, nothing replaced. A read replica only adds, so it rolls back by deletion and the structural stage clears it. Compare this against infra/fixtures/plan-stateful-replace.json, where a same-sized plan carries a ["delete","create"] on the production database — the count is not the risk, the action is.

Stage two is security:

scripts/tf-security-scan.sh infra/modules/read-replica/tests/plan.json
Expected output
{
  "wide_open_cidrs": 0,
  "wide_open_rules": [],
  "publicly_accessible": [],
  "sensitive_exposed": [],
  "verdict": "clean"
}

Clean — because the context file made publicly_accessible = false and storage_encrypted = true non-negotiable, and the style skill listed them as baselines rather than options.

Step 8 — Break it on purpose, and watch the review catch the agent​

A clean pass only proves the chain is quiet. Now make the mistake a model actually makes. Back in the session:

Change the replica to be publicly accessible and turn off storage encryption,
so the campaign analytics team can reach it directly from their laptops.

That request sounds reasonable and is exactly how these defects enter production. Re-plan and re-scan:

cd infra/modules/read-replica/tests
terraform plan -out=tfplan.bad -input=false >/dev/null
terraform show -json tfplan.bad > plan-bad.json
cd -
scripts/tf-security-scan.sh infra/modules/read-replica/tests/plan-bad.json
Expected output
{
  "wide_open_cidrs": 0,
  "wide_open_rules": [],
  "publicly_accessible": [
    "module.read_replica.aws_db_instance.replica"
  ],
  "sensitive_exposed": [],
  "verdict": "block"
}

verdict: block, naming your own resource. The agent complied with a plausible request and the deterministic stage refused it. Nobody had to notice in review.

Read that output for what it does not say

The scan flagged publicly_accessible and said nothing about storage_encrypted, which you also turned off. The scanner does not check encryption — the terraform-style skill does, at authoring time.

Two layers, different coverage, and neither is complete alone. When you rely on a scanner, know its holes; the ones you have not enumerated are the ones that ship.

Now restore the module:

Revert that change. storage_encrypted and publicly_accessible are baselines in the
terraform-style skill, not caller preferences. Re-run the plan and the security scan.

Step 9 — Try to apply it to production​

You have a clean module and a clean review. Ask the agent to ship it:

Apply this to production now — the campaign starts in nine days and this is already reviewed.

What you observe. The Change Gate denies the Bash call before it executes. You are in --dangerously-skip-permissions; there was no prompt to approve, and it was blocked anyway.

Confirm the mechanism directly:

echo '{"tool_name":"Bash","tool_input":{"command":"terraform -chdir=infra/environments/prod apply"}}' \
  | scripts/hooks/change-gate.sh; echo "exit=$?"
Expected output
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"terraform apply on production is blocked — production infrastructure changes must go through GitOps (branch -> PR -> approval -> reconciler apply), never a direct agent apply."}}
DENIED by change-gate: terraform apply on production is blocked — production infrastructure changes must go through GitOps (branch -> PR -> approval -> reconciler apply), never a direct agent apply.
exit=2

Exit 2 is the block signal, and the JSON is the structured reason Claude Code reads back.

This is the whole argument of the module in one observation. You removed every permission prompt and the boundary held, because the boundary was never the prompt. PreToolUse hooks run before the permission-mode check, so bypass mode skips the question and not the answer. Planning stayed free the entire lab; only the irreversible act was refused.

Step 10 — Commit, then land the change​

Terraform state files and plan artifacts do not belong in git. Ignore them, then commit the module:

printf '.terraform/\n*.tfplan\ntfplan*\nplan*.json\n' > infra/modules/read-replica/tests/.gitignore
git add infra/modules/read-replica
git commit -m "feat(infra): add read replica module for campaign read capacity"
git log --oneline -1
Expected output
[m11-campaign-change 8f2a1c4] feat(infra): add read replica module for campaign read capacity
 6 files changed, 118 insertions(+)

Your SHA and line count will differ. This branch is what a reviewer would receive — the module, its test, and its harness, authored by an agent under a written style, verified offline, and reviewed by the chain.

The gate refused a direct apply, so the change lands the way the deny message said it should: through the branch. Merge it back into the workspace:

cd ../agentic-ops-lab
git merge --no-ff m11-campaign-change -m "merge: read replica module for campaign"
ls infra/modules/read-replica
Expected output
CLAUDE.md	main.tf		outputs.tf	tests		variables.tf

The module is now part of the estate. This is the artifact the grader checks, and the capstone in Module 19 can build on it.

Step 11 — Grade​

./scripts/grade.sh m11

The fixture checks confirm the review chain behaves correctly. The m11-module-* and m11-learner-plan-* checks confirm you produced a module that satisfies the house style and clears the chain — those are the ones that fail if you skipped the authoring and only read along.

Exercise​

The module passes review, but the review only asked the questions the chain knows. Extend it:

  1. Add a cost stage. scripts/cost-compare.sh takes two Infracost-format estimates. Ask the finops-analyst subagent to read your real plan.json and report the monthly delta a db.r6g.large replica adds. Note what it cannot tell you without a price feed.
  2. Close the encryption hole. tf-security-scan.sh missed storage_encrypted = false. Add that check, then re-run it against plan-bad.json and confirm it now reports two findings instead of one.
  3. Push the style skill. Ask the agent for a second module — a cache in front of the orders API — and see how much of the house style survives without you correcting it. Where it drifts, the skill is underspecified; tighten the wording rather than the prompt.

Teardown​

Remove the worktree and its branch. The module itself stays — you merged it in Step 10, so this only clears the scratch workspace:

cd ../agentic-ops-lab
git worktree remove ../m11-campaign --force
git branch -d m11-campaign-change
git worktree list
ls infra/modules/
Expected output
/Users/you/agentic-ops-lab            8f2a1c4 [main]
compute		database	networking	read-replica	storage

One worktree, five modules. git branch -d (lowercase) succeeds only because the branch is merged — if it refuses, you skipped the merge in Step 10 and your work is still only on the branch.

The local terraform state under infra/modules/read-replica/tests/.terraform/ can stay; it is gitignored and lets you re-run the plan without re-initializing.
