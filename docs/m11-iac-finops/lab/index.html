Lab — AI-Augmented IaC & FinOps

The lesson drew the line between planning (safe, read-only) and applying (irreversible, gated), and named the four questions a plan review answers — replacements, blast radius, drift, and cost — each run by a specialist in the IaC → Security → FinOps → Change Reviewer chain. This lab makes all of it runnable against Northstar's real Terraform estate. You will prove the Change Gate keeps mutation a separate authority, analyze real plan JSON for stateful replacements and blast radius, scan for the 0.0.0.0/0 rule that opens Postgres to the internet, price the oversize database at its true +$2,847/month, review rollback viability, and run the full handoff chain end to end — plus the agent-run cost receipt that proves right-sizing the model per role is itself a FinOps decision.

By the end you will have a change verdict you can defend to a reviewer: not "the agent said it looked fine," but "here is the deterministic gate that blocks a data-loss replacement, a datastore exposure, and a budget blowout — and passes a clean change."

Where you are working

You start at the root of the agentic-ops-lab workspace. Northstar's Terraform estate lives under infra/ — four modules (networking, database, compute, storage), three environments, and a set of plan fixtures under infra/fixtures/ that stand in for terraform show -json output. The review scripts (plan-analyze.sh, tf-security-scan.sh, cost-compare.sh, plan-drift.sh, rollback-review.sh, agent-cost-receipt.sh, change-pipeline.sh) ship in scripts/. They encode the specialist checks from the lesson with no model in the loop, so the review is reproducible and gradeable and this lab runs anywhere — you do not need a live AWS account or a running cluster. In production each check would be the corresponding subagent from Module 9; here they are deterministic reads of the plan JSON, so the review shape is identical but the run is repeatable.

Step 0 — Prerequisites​

Confirm your tools. Every review script uses jq; the plan fixtures are real terraform show -json shape, so terraform is only needed if you regenerate them.

terraform version | head -1
jq --version
claude --version
Expected output
Terraform v1.14.8
jq-1.7.1
2.1.197 (Claude Code)

Your versions will differ. jq must resolve (every check parses plan JSON with it); terraform should be ≥ 1.5; claude is used where the lab points out where a real subagent would run.

Step 1 — Prove state safety: mutation is a separate authority​

Before you review a single plan, prove the boundary the whole module rests on. The Change Gate you built in Module 8 denies a production terraform apply from an agent identity — planning is free, mutation is gated. Simulate the hook call the agent's Bash tool would trigger for an apply on production:

echo '{"tool_name":"Bash","tool_input":{"command":"terraform -chdir=infra/environments/prod apply"}}' \
  | scripts/hooks/change-gate.sh; echo "exit=$?"
Expected output
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"terraform apply on production is blocked — production infrastructure changes must go through GitOps (branch -> PR -> approval -> reconciler apply), never a direct agent apply."}}
DENIED by change-gate: terraform apply on production is blocked — production infrastructure changes must go through GitOps (branch -> PR -> approval -> reconciler apply), never a direct agent apply.
exit=2

Exit 2 is the block signal Claude Code reads, and the JSON is the structured deny. The agent cannot apply to production — not because it chose not to, but because the gate refuses it.

Now confirm the safe operation is untouched — planning on the same production environment is allowed:

echo '{"tool_name":"Bash","tool_input":{"command":"terraform -chdir=infra/environments/prod plan"}}' \
  | scripts/hooks/change-gate.sh; echo "exit=$?"
Expected output
exit=0

Exit 0, no deny. terraform plan is read-only, so the gate lets it through. This is the split from the lesson made concrete: the agent plans freely and is stopped only at the irreversible act.

Step 2 — Author the campaign change in an isolated worktree​

The IaC Engineer authors the campaign change on its own branch, in a git worktree, so the main branch stays clean while the change is reviewed. Create the isolated workspace:

git worktree add -b m11-campaign-change ../m11-campaign HEAD
git worktree list
Expected output
Preparing worktree (new branch 'm11-campaign-change')
HEAD is now at 3adb15b feat: add contracts, evals, fault configs, .claude config, and project docs
/Users/you/agentic-ops-lab            3adb15b [main]
/Users/you/m11-campaign               3adb15b [m11-campaign-change]

Your commit SHA and paths will differ. You now have a sealed room: the IaC Engineer authors HCL and generates plans in ../m11-campaign on the m11-campaign-change branch, and main is untouched until the change clears the review chain. In this lab the review runs against shipped plan fixtures so it is reproducible, but the worktree is the real isolation control from Module 9's role bundles (worktree: true for iac-engineer).

Where the agent fits

In a real run you would launch the IaC Engineer subagent here: claude with the iac-engineer role, pointed at the worktree, told to author the change and run terraform plan -out=tfplan then terraform show -json tfplan > plan.json. It authors and plans; it never applies. The rest of this lab is the review of the plan.json it would hand off — which is exactly what the shipped fixtures represent.

Step 3 — Analyze the plan JSON: blast radius and replacements​

The first review stage is structural. plan-analyze.sh reads the plan JSON and answers "what is being touched, what is being replaced, and is any of it stateful." Start with the known-good plan — the shape a clean campaign change should have:

scripts/plan-analyze.sh infra/fixtures/plan-good.json --field json
Expected output
{
  "total_resources": 31,
  "blast_radius": 31,
  "destroy_count": 0,
  "replacements": [],
  "stateful_replaced": [],
  "verdict": "clean"
}

Thirty-one resources touched, zero destroyed, nothing replaced — verdict: clean. A large plan is not a dangerous plan; blast radius is about destruction, not diff size. This one only creates, so it rolls back cleanly and the structural stage clears it.

Step 4 — Catch the stateful replacement​

Now the dangerous case. A plan that recreates the orders database looks almost identical to the good one — same resource count — but one resource's action is ["delete","create"] on a aws_db_instance. Analyze it:

scripts/plan-analyze.sh infra/fixtures/plan-stateful-replace.json --field json
Expected output
{
  "total_resources": 31,
  "blast_radius": 31,
  "destroy_count": 0,
  "replacements": [
    "module.database.aws_db_instance.main"
  ],
  "stateful_replaced": [
    "module.database.aws_db_instance.main"
  ],
  "verdict": "block"
}

Same 31 resources as the good plan — but verdict: block, and the analyzer names the resource: module.database.aws_db_instance.main is being replaced, and it is stateful, so the replacement destroys the orders data. This is the finding a human eyeballing a 31-resource plan would miss. The rule is exact and unforgiving: any stateful replacement blocks, regardless of how routine the rest of the plan looks.

Step 5 — Run the security scan​

The second stage is exposure. tf-security-scan.sh reads the same plan JSON for the two findings that page a security team: any 0.0.0.0/0 ingress, and any resource going publicly accessible — with sensitive datastore ports escalated. Scan the plan that adds a debug rule:

scripts/tf-security-scan.sh infra/fixtures/plan-wide-network.json --field json
Expected output
{
  "wide_open_cidrs": 1,
  "wide_open_rules": [
    "module.networking.aws_security_group_rule.db_public_debug"
  ],
  "publicly_accessible": [],
  "sensitive_exposed": [
    {
      "address": "module.networking.aws_security_group_rule.db_public_debug",
      "port": 5432
    }
  ],
  "verdict": "block"
}

verdict: block. The scan pinpoints db_public_debug — a rule opening port 5432 (Postgres) to 0.0.0.0/0, the whole internet. Open the fixture and you will see its own description: "Temporary debug access for on-call — REMOVE AFTER INCIDENT." This is how datastore exposures reach production: a genuinely-meant-to-be-temporary debug rule that nobody removed. The scan escalates it because the port is a datastore, not a web tier — exposing the database is the finding that ends careers.

Confirm the scan does not cry wolf. Run it on the good plan:

scripts/tf-security-scan.sh infra/fixtures/plan-good.json --field verdict
Expected output
clean

A scanner that flags everything is a scanner nobody reads. The good plan has no wide-open ingress and nothing public, so it clears — the block on the wide-network plan means something precisely because the clean plan passes.

Step 6 — Detect environment drift​

A candidate change is authored against one environment; drift analysis asks "what does this introduce that the known-good baseline does not have?" plan-drift.sh diffs the candidate against the baseline and surfaces exactly what drifted in — most importantly, a new 0.0.0.0/0 rule:

scripts/plan-drift.sh infra/fixtures/plan-good.json infra/fixtures/plan-wide-network.json --field json
Expected output
{
  "new_addresses": [
    "module.networking.aws_security_group_rule.db_public_debug"
  ],
  "new_wide_open": [
    "module.networking.aws_security_group_rule.db_public_debug"
  ],
  "drift_count": 2,
  "verdict": "block"
}

The diff isolates the one thing the candidate adds that the baseline lacks: the db_public_debug rule, appearing as both a new resource address and a new wide-open rule (hence drift_count: 2). Drift analysis is how you catch an exposure that slipped in under cover of an otherwise-legitimate change — you are not reviewing 1,400 lines of JSON, you are reviewing the two-line delta from a plan you already trust.

Step 7 — Run the cost comparison​

terraform plan says nothing about money. The FinOps stage prices the plan by comparing two cost estimates — the baseline and the proposed — and reduces it to a delta, a multiple, and the specific resources driving the change:

scripts/cost-compare.sh \
  infra/fixtures/cost-estimates/estimate-good.json \
  infra/fixtures/cost-estimates/estimate-oversize.json --field json
Expected output
{
  "baseline_monthly": 301.97,
  "proposed_monthly": 3148.97,
  "delta_monthly": 2847,
  "multiple": 10.43,
  "threshold": 2,
  "drivers": [
    {
      "resource": "module.database.aws_db_instance.main",
      "from": 189.80,
      "to": 3036.80,
      "multiple": 16
    }
  ],
  "verdict": "block"
}

verdict: block, and the number that makes the case: +$2,847/month. The estate goes from ~$302 to ~$3,149 a month — and drivers attributes it to one resource, the database, growing 16x (a db.r6g.large resized to a db.r6g.4xlarge). This is a one-line diff in HCL. Without the cost stage it sails through as "changed the instance class"; with it, it is a $34,000/year decision that needs a human to sign off.

Step 8 — Review rollback viability​

Blast radius and cost are not the whole risk. The Change Reviewer asks a different question: if this goes wrong, can we get back? rollback-review.sh judges reversibility — and a stateful replacement is the case where the answer is no:

scripts/rollback-review.sh infra/fixtures/plan-stateful-replace.json --field json
Expected output
{
  "irreversible_resources": [
    "module.database.aws_db_instance.main"
  ],
  "reversible": false,
  "reason": "replaces/destroys stateful resource(s): module.database.aws_db_instance.main — data cannot be recovered by re-apply",
  "verdict": "requires-restore-plan"
}

reversible: false. The point is subtle and it matters: this is not the same as blast radius. A one-resource plan that replaces the database has a tiny blast radius but zero rollback — re-applying the Terraform builds an empty instance, it does not un-delete the data. So the verdict is requires-restore-plan: the change is not forbidden, but it cannot be approved without an explicit restore-from-backup plan recorded. A pure-create plan, by contrast, rolls back by destroying what you made — run it against plan-good.json and you get verdict: approve.

Step 9 — Run the full handoff chain​

Now join the stages. change-pipeline.sh runs IaC → Security → FinOps → Change Reviewer over a plan and produces one verdict, fail-closed on the strongest objection. Run it on the good plan with a matching cost pair — every stage should clear:

scripts/change-pipeline.sh infra/fixtures/plan-good.json \
  infra/fixtures/cost-estimates/estimate-good.json \
  infra/fixtures/cost-estimates/estimate-good.json --field json
Expected output
{
  "stages": {
    "iac_engineer": {
      "verdict": "clean",
      "blast_radius": 31,
      "stateful_replaced": []
    },
    "security_reviewer": {
      "verdict": "clean",
      "wide_open_cidrs": 0,
      "sensitive_exposed": []
    },
    "finops_analyst": {
      "verdict": "clean",
      "delta_monthly": 0
    },
    "change_reviewer": {
      "reversible": true,
      "verdict": "approve"
    }
  },
  "blockers": [],
  "verdict": "approve"
}

Four stages, all clear, blockers: [], verdict: approve. This is a change that ships. Each stage's evidence is in the packet, so the approval is auditable — you can see why each specialist cleared it, not just that the chain said yes.

Now prove one dissent stops the line. Run the chain on the stateful-replace plan and print just the blockers:

scripts/change-pipeline.sh infra/fixtures/plan-stateful-replace.json --field blockers
Expected output
iac: module.database.aws_db_instance.main
rollback: replaces/destroys stateful resource(s): module.database.aws_db_instance.main — data cannot be recovered by re-apply

Two stages object — the IaC structural analysis and the Change Reviewer's rollback check — and either one alone blocks the change. The syntax was valid; the plan applied cleanly in a sandbox; and the chain still refuses it, because "it works" is not "it is safe." That gap is the whole reason the chain exists.

Step 10 — Produce the agent-run cost receipt​

The last stage is FinOps turned on the reviewers themselves. agent-cost-receipt.sh prices the review chain — each role on the model right-sized for it in the authority matrix — against the counterfactual of running every role on Opus:

scripts/agent-cost-receipt.sh --field json
Expected output
{
  "chain": [
    { "role": "iac-engineer",      "model": "sonnet", "tokens": 40000, "cost_usd": 0.12 },
    { "role": "security-reviewer", "model": "opus",   "tokens": 60000, "cost_usd": 0.9 },
    { "role": "finops-analyst",    "model": "haiku",  "tokens": 15000, "cost_usd": 0.012 },
    { "role": "change-reviewer",   "model": "opus",   "tokens": 50000, "cost_usd": 0.75 }
  ],
  "total_usd": 1.782,
  "all_opus_total_usd": 2.475,
  "savings_usd": 0.693,
  "verdict": "mixed-model-cheaper"
}

The mixed-model chain costs $1.78 per review; the same token spend on all-Opus would be $2.48. The FinOps analyst on Haiku costs $0.012 — a fortieth of what it would cost on Opus — because reading a plan and comparing numbers to a threshold does not need a frontier model. Right-sizing the model per role saves $0.69 per review, and the receipt proves it. Change the model in contracts/authority-matrix.yaml and the receipt re-prices automatically, because the matrix is the source of truth for both the role bundle and its cost.

Confirm the authority boundary the receipt depends on — the reviewers cannot write:

scripts/role-authority-check.sh iac-engineer write; echo "exit=$?"
scripts/role-authority-check.sh finops-analyst write; echo "exit=$?"
Expected output
CAPABLE: role 'iac-engineer' carries write tool 'edit' — write is within its authority.
exit=0
BLOCKED: role 'finops-analyst' has NO write tool in its bundle — it is structurally incapable of Edit/Write. Authority boundary holds.
exit=3

The IaC Engineer writes — authoring HCL is its job. The FinOps Analyst is structurally incapable of writing: no Edit or Write tool in its bundle. Its review is trustworthy because it cannot modify the change it is pricing, exactly the read-only independence from Module 9.

Step 11 — Let the repository certify the review​

Run the whole matrix. grade.sh m11 runs every check — state safety, plan analysis, security scan, drift, cost, rollback, authority, the handoff chain, and the agent-run cost receipt:

./scripts/grade.sh m11
Expected output

========================

Checking: AI-Augmented IaC & FinOps — plan-JSON analysis, state safety, security scan, cost compare, specialist handoff chain

  ✓ STATE SAFETY: terraform plan on production is ALLOWED — planning is read-only, only apply is gated
  ✓ PLAN ANALYSIS: a plan of pure creates (the known-good plan) analyzes to verdict 'clean' — nothing destroyed, nothing replaced
  ✓ BLAST RADIUS: the good plan touches all 31 resources — the analyzer reports the count a reviewer would gate on
  ✓ STATEFUL REPLACE: the plan that recreates the RDS instance analyzes to 'block' — a stateful replacement is a data-loss risk, not a routine change
  ✓ STATEFUL REPLACE: the analyzer names the exact resource being destroyed and recreated — the database, so the finding is actionable
  ✓ SECURITY SCAN: the plan adding a 0.0.0.0/0 rule scans to 'block' — an internet-open ingress on a datastore port is a page-the-team finding
  ✓ SENSITIVE EXPOSURE: the scan pinpoints the rule opening Postgres (5432) to the whole internet — the datastore, not a web tier
  ✓ SECURITY SCAN: the good plan has no wide-open or public exposure — verdict 'clean', so the scan does not cry wolf
  ✓ COST ESTIMATION: the oversize change is a +$2847/mo delta over baseline — the number that turns a sizing choice into a budget decision
  ✓ FINOPS THRESHOLD: a per-resource cost jump past 2x (the RDS instance grows 16x) blocks — the FinOps role's 'flag changes > 2x' rule, enforced
  ✓ ENVIRONMENT DRIFT: diffing the candidate against the known-good baseline surfaces the NEW 0.0.0.0/0 rule that drifted in — verdict 'block'
  ✓ ROLLBACK REVIEW: the stateful-replace plan is judged irreversible — its approval REQUIRES a restore-from-backup plan, it is not a clean roll back
  ✓ ROLLBACK REVIEW: a pure-create plan is reversible (destroy what you made) — verdict 'approve', no restore plan needed
  ✓ AUTHORITY: the IaC engineer STRUCTURALLY carries a write tool — authoring HCL is in its role (exit 0)
  ✓ AUTHORITY: the FinOps analyst CANNOT write — it reads plans and prices them, it does not mutate infrastructure (exit 3)
  ✓ AGENT-RUN COST RECEIPT: the mixed-model handoff chain is cheaper than running every role on opus — right-sizing the model per role is itself a FinOps decision
  ✓ HANDOFF CHAIN: the good plan clears all four stages (IaC -> Security -> FinOps -> Change Reviewer) and the pipeline verdict is 'approve'
  ✓ HANDOFF CHAIN: one stage's block stops the line — the stateful-replace plan is blocked by the pipeline even though its syntax is valid

RESULT: PASS (20 passed)

Twenty checks, all green. The review is not "we were careful" — it is a gate that fails the build if any control breaks.

Step 12 — Teardown​

The review scripts are module deliverables — leave them; the Deep Dive uses them to catch a three-defect change in one plan. The only ephemeral thing you started is the worktree; remove it and its branch:

git worktree remove ../m11-campaign --force
git branch -D m11-campaign-change
git worktree list
Expected output
/Users/you/agentic-ops-lab            3adb15b [main]

Your SHA and path will differ. The worktree and its branch are gone; only main remains. Nothing else needs stopping — the review operates on the repo's plan fixtures, not on a running cluster or a real cloud account, so there are no services to bring down.

You proved the boundary the module rests on — the agent plans freely and is stopped only at the irreversible apply. You analyzed real plan JSON for stateful replacements and blast radius, caught a datastore exposure and traced it to a "temporary" debug rule, priced an oversize database at its true $2,847/month, judged a replacement irreversible, and ran the full IaC → Security → FinOps → Change Reviewer chain to one auditable verdict — then priced the reviewers themselves and proved the mixed-model chain is the cheaper, correct choice. Every control is a property of the review, tested in CI, not a behavior you hoped the agent would exhibit. The Deep Dive now takes the case that defeats any single reviewer: one agent-generated plan that passes syntax but replaces the database, oversizes it, and opens it to the internet — and shows the chain catching all three where no one specialist could.
