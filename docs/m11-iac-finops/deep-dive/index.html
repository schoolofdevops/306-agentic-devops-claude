Deep Dive — Composing Independent Reviewers to Catch a Multi-Defect Terraform Change

The core lab reviewed one defect at a time: a plan that replaces a database, a different plan that opens a port, a third plan that oversizes an instance. Each was caught cleanly, and each was caught by exactly the stage you would expect. That is the tidy case. This Deep Dive is the case that actually shows up in production — the one where a single, plausible-sounding prompt produces a single change that carries all three defects at once, passes terraform validate, applies without error in a sandbox, and would quietly destroy the orders database, triple the monthly bill, and expose Postgres to the internet if it reached production.

The point here is not "run three checks." You already did that. The point is why no single reviewer catches all three, and why the chain — four independent specialists, one dissent stops the line — is the smallest structure that does. If you take one thing from this module beyond the mechanics, take this: a competent-looking, syntactically valid infrastructure change is not a safe one, and the gap between those two claims is not covered by any one reviewer's expertise. It is covered by the composition of reviewers.

Where you are working

You continue in the agentic-ops-lab workspace with the review scripts from the core lab. This Deep Dive adds one fixture, infra/fixtures/plan-cheap-prompt.json, that carries all three defects in a single plan, and grades against labs/m11/deep-dive.checks.json. Everything is a deterministic read of the plan JSON — no model in the loop for the checks — so the review is reproducible.

The prompt that produced it​

Picture the prompt that generated this change. It is not malicious and it is not obviously wrong:

"The orders database is slow under campaign load. Resize it to handle the traffic, make sure on-call can reach it directly to debug, and get it deployed."

Every clause is reasonable on its face, and each one, taken literally by an agent optimizing for "make the campaign work," produces one of the three defects:

  • "Resize it to handle the traffic" → the agent jumps the instance class from db.r6g.large to db.r6g.4xlarge. Reasonable-sounding, 16x the cost.
  • "Make sure on-call can reach it directly to debug" → the agent adds a security-group rule opening port 5432 to 0.0.0.0/0, with the honest description "Temporary debug access for on-call — REMOVE AFTER INCIDENT." Reasonable-sounding, the whole internet can now reach your database.
  • The resize itself, combined with a parameter change, forces replacement of the RDS instance → ["delete","create"]. Reasonable-looking in the plan, destroys every order in the database.

Analogy: this is the difference between a code review that checks "does it compile" and one that checks "should this ship." A junior reviewer who confirms the build is green has verified something real and useful — and has told you nothing about whether the change is correct, affordable, or safe. The cheap prompt produced cheap correctness: it satisfies the literal request and the compiler. The expensive part — the data loss, the bill, the exposure — lives entirely outside what syntax and "it applied" can see. This is why "the agent's change passed" is a claim you must interrogate, not accept.

First, confirm the trap: it passes syntax​

Start where a careless pipeline would stop. The generated plan is structurally valid JSON — it is a well-formed terraform plan:

jq -e '.resource_changes | type == "array"' infra/fixtures/plan-cheap-prompt.json \
  >/dev/null 2>&1 && echo valid || echo invalid
Expected output
valid

Valid. If your gate were "does the plan parse" or even "does terraform validate pass," this change sails through. Syntax is table stakes; it is not the review. The three defects are all in the semantics of the plan — what it does to real state, cost, and exposure — which no syntactic check reaches.

Watch each specialist catch its own defect — and miss the others​

Now the instructive part. Run each single reviewer against the combined plan and watch it catch the defect in its lane while being structurally blind to the other two.

The IaC structural stage catches the replacement:

scripts/plan-analyze.sh infra/fixtures/plan-cheap-prompt.json --field stateful_replaced
scripts/plan-analyze.sh infra/fixtures/plan-cheap-prompt.json --field verdict
Expected output
module.database.aws_db_instance.main
block

It names the database replacement and blocks. But plan-analyze.sh looks at structure — actions and resource types. It has no notion of cost, so the 16x oversize is invisible to it, and no notion of network exposure, so the 0.0.0.0/0 rule is invisible to it. It caught one of three.

The security scan catches the exposure:

scripts/tf-security-scan.sh infra/fixtures/plan-cheap-prompt.json --field sensitive_exposed
scripts/tf-security-scan.sh infra/fixtures/plan-cheap-prompt.json --field verdict
Expected output
module.networking.aws_security_group_rule.db_public_debug:5432
block

It pinpoints Postgres exposed on 5432 and blocks. But the security scanner looks at CIDRs and public flags. The database being replaced is not a security finding to it, and the instance class being 4xlarge is not either. It caught a different one of three.

The FinOps stage catches the cost:

jq -r '.resource_changes[] | select(.address=="module.database.aws_db_instance.main") | .change.after.instance_class' \
  infra/fixtures/plan-cheap-prompt.json
scripts/cost-compare.sh infra/fixtures/cost-estimates/estimate-good.json \
  infra/fixtures/cost-estimates/estimate-oversize.json --field verdict
Expected output
db.r6g.4xlarge
block

The plan sizes the database at db.r6g.4xlarge, and priced against the baseline it blocks on the 2x threshold. But FinOps looks at money. A resource being replaced is not a cost signal (a replacement can even cost the same), and a public CIDR has no price. It caught the third defect — and would have waved the other two through.

Line these up and the lesson is stark. Three reviewers, three catches, and not one of them saw more than a single defect. The security scan, run alone on this plan, would block it — for the wrong and incomplete reason, missing the data loss and the cost entirely. Had the exposure not been there, the security scan would have returned clean and a security-only gate would have approved a change that destroys the database. Run the security scan on the stateful-replace-only plan to see exactly that blind spot:

scripts/tf-security-scan.sh infra/fixtures/plan-stateful-replace.json --field verdict
Expected output
clean

A plan that destroys the orders database is clean to the security reviewer, because destroying a database is not a security finding. A single-reviewer gate is a gate with holes exactly the shape of everything outside that reviewer's expertise.

The chain: composition closes every hole​

Now run the full pipeline over the combined plan. This is the composition — IaC → Security → FinOps → Change Reviewer — joined into one verdict, fail-closed on any objection:

scripts/change-pipeline.sh infra/fixtures/plan-cheap-prompt.json \
  infra/fixtures/cost-estimates/estimate-good.json \
  infra/fixtures/cost-estimates/estimate-oversize.json --field blockers
Expected output
iac: module.database.aws_db_instance.main
security: sensitive/public exposure
finops: cost > threshold (module.database.aws_db_instance.main)
rollback: replaces/destroys stateful resource(s): module.database.aws_db_instance.main — data cannot be recovered by re-apply

Four blockers, from four independent stages, on the one plan. The IaC stage caught the replacement; Security caught the exposure; FinOps caught the cost; and the Change Reviewer's rollback check caught that the replacement is irreversible. Each stage contributes a finding no other stage could see. The verdict is block, and it is block for all the right reasons — which is what you need, because a change blocked for one reason and silently carrying two others is a change someone will "fix" the one reason and re-submit.

Analogy: the chain is the Swiss-cheese model of accident prevention. Every single reviewer is a slice of cheese with holes — gaps exactly the shape of the risks outside its expertise. The security scanner's holes are cost and data loss; the FinOps analyst's holes are exposure and replacement. No slice is complete, and no slice can be made complete by trying harder — a security reviewer will never be a cost model. Safety comes from stacking the slices so that no hole lines up all the way through: a defect that slips past one reviewer's holes hits the solid part of the next. The cheap-prompt plan had three defects; it needed three different slices to be stopped, and the fourth (rollback) to make the data-loss consequence explicit for the human who will decide what to do next.

Why the join must be fail-closed on the strongest objection​

One design choice in the pipeline is worth dwelling on, because it is the difference between a real gate and a checkbox. The join does not average the stages, take a vote, or approve-with-conditions when three of four are happy. It blocks if any stage blocks — fail-closed on the strongest objection.

Consider the alternative. Suppose the join were a majority vote: three stages say "well, apart from my one finding it's fine" and the change is 75% approved. That number is meaningless. The 25% that objected is the part that destroys the database. Risk does not average — a change that is "mostly safe" and "definitely destroys production data" is not 75% safe, it is unsafe, and the one dissent is the entire signal. This is the same fail-closed discipline from Module 8's Change Gate and Module 10's synthesis (which refused to average a disagreement into a majority vote): when the downside is irreversible, a single credible objection outweighs any number of clearances.

The rollback stage makes this concrete in a way blast radius alone does not. Confirm the reviewer's verdict on reversibility:

scripts/rollback-review.sh infra/fixtures/plan-cheap-prompt.json --field reversible
Expected output
false

reversible: false. Even if you somehow accepted the cost and the exposure, this change cannot be approved without a restore-from-backup plan, because the moment it applies, the orders data is gone and re-applying the Terraform builds an empty instance. The rollback stage is the one that translates "a stateful resource is being replaced" into the sentence a human decision-maker actually needs: if this goes wrong, we cannot get the data back — so what is the restore plan? That question is the difference between an approval and a catastrophe with a paper trail.

Run the Deep Dive's grade to confirm every claim above holds as a test, not a story:

Eleven checks, all green. The scenario is not a cautionary tale you have to trust — it is a fixture and a set of assertions that fail the build if the chain ever stops catching all three.

Where you will use this​

The cheap-prompt-expensive-plan pattern is not a Terraform curiosity; it is the general failure mode of putting an agent on any high-consequence change surface, and you will meet it repeatedly:

  • Reviewing any agent-authored infrastructure PR. The moment an agent proposes IaC, Helm values, or a Kubernetes manifest, the question is never "did it apply cleanly" — it is "what does this do to state, cost, and exposure that a clean apply hides." Compose the specialists; do not trust a single pass.
  • Setting up CI gates for IaC. When you wire plan review into a pipeline, wire the chain, not one linter. A cost check without a security check approves an exposed-but-affordable change; a security check without a rollback check approves a locked-down database deletion. Each gate you add closes one shape of hole.
  • Any prompt that sounds reasonable. The defects here came from a prompt with no bad intent. Whenever you delegate a change to an agent, assume the literal-but-unsafe interpretation is on the table, and let independent reviewers — not the authoring agent's own judgment — decide whether it ships.
  • Deciding what to model-size. The chain that caught all three defects cost $1.78 to run (from the core lab's receipt). That is the price of not destroying a production database. Right-sizing the reviewers is a real FinOps decision, but under-provisioning the review itself — collapsing four specialists into one over-trusted generalist to save tokens — is the false economy this whole module argues against.

The next module takes this same compose-independent-reviewers discipline onto the Kubernetes and GitOps surface, where "the manifest applied" hides an even wider set of consequences than "the plan applied" — and the same lesson holds: syntax is not safety, and safety is a property of composition.
