Deep Dive — One Plan, Three Defects, Four Reviewers

You just wrote a module the right way: a clear spec, a failing test first, the house style skill checked, and it came out clean. This Deep Dive asks the question that comes right after: what happens when a change is not written that carefully?

The core lab reviewed one defect at a time — a plan that replaces a database, a different plan that opens a port, a third plan that oversizes an instance. Each was caught cleanly, by exactly the check you would expect. That is the easy case. This is the case that actually shows up at work: a single, reasonable-sounding request produces one change that carries all three defects at once. It passes terraform validate. It would apply without an error. And if it reached production, it would quietly destroy the orders database, triple the monthly bill, and open Postgres to the internet.

The point of this page is not "run three checks" — the lab already did that. The point is that no single reviewer catches all three, and that a chain of four independent reviewers — where any one of them can stop the change — is the smallest setup that does. Keep one thing from this page above everything else: a change that looks fine and passes validate is not the same as a change that is safe to apply. Closing that gap is not one reviewer's job. It takes all of them, checking different things, at the same time.

Where you are working

You are still in the agentic-ops-lab workspace, using the same review scripts from the lab. This page adds one new fixture, infra/fixtures/plan-cheap-prompt.json, which carries all three defects in a single plan, and it is graded by labs/m11/deep-dive.checks.json. Every check here is a deterministic read of the plan JSON — no model involved — so you get the same result every time you run it.

The prompt that produced it​

Picture the prompt that generated this change. It is not malicious and it is not obviously wrong:

"The orders database is slow under campaign load. Resize it to handle the traffic, make sure on-call can reach it directly to debug, and get it deployed."

Every clause is reasonable on its face, and each one, taken literally by an agent optimizing for "make the campaign work," produces one of the three defects:

  • "Resize it to handle the traffic" → the agent jumps the instance class from db.r6g.large to db.r6g.4xlarge. Reasonable-sounding, 16x the cost.
  • "Make sure on-call can reach it directly to debug" → the agent adds a security-group rule opening port 5432 to 0.0.0.0/0, with the honest description "Temporary debug access for on-call — REMOVE AFTER INCIDENT." Reasonable-sounding, the whole internet can now reach your database.
  • The resize itself, combined with a parameter change, forces replacement of the RDS instance → ["delete","create"]. Reasonable-looking in the plan, destroys every order in the database.

This is the same gap as a code review that only checks "does it build" instead of "should this ship." Confirming the build is green is real and useful — and it tells you nothing about whether the change is correct, affordable, or safe. The cheap prompt above produces exactly that: code that satisfies the literal request and passes the compiler. The expensive part — the data loss, the bigger bill, the open port — sits entirely outside what "it built" or "it applied" can see. So "the agent's change passed" is a claim you should check, not one you should accept on its own.

First, confirm the trap: it looks fine​

Start where a careless pipeline would stop looking. The generated plan is valid, well-formed JSON — a real Terraform plan:

jq -e '.resource_changes | type == "array"' infra/fixtures/plan-cheap-prompt.json \
  >/dev/null 2>&1 && echo valid || echo invalid
Expected output
valid

Valid. If your only gate were "does the plan parse" or even "does terraform validate pass," this change gets through with no problem. Parsing correctly is the minimum bar, not the review. All three defects live in what the plan actually does — to real state, real cost, real exposure — and no check that only reads syntax will ever see that.

Watch each reviewer catch its own defect — and miss the other two​

Now the useful part. Run each reviewer on its own against the combined plan, and watch it catch the one defect it was built to look for, while being completely blind to the other two.

The IaC structural stage catches the replacement:

scripts/plan-analyze.sh infra/fixtures/plan-cheap-prompt.json --field stateful_replaced
scripts/plan-analyze.sh infra/fixtures/plan-cheap-prompt.json --field verdict
Expected output
module.database.aws_db_instance.main
block

It names the database replacement and blocks. But plan-analyze.sh only looks at structure — what type each resource is, and what action is happening to it. It has no idea what anything costs, so the 16x oversize is invisible to it. It has no idea about network rules, so the open port is invisible to it too. It caught one defect out of three, because that is the only one it was built to look for.

The security scan catches the exposure:

scripts/tf-security-scan.sh infra/fixtures/plan-cheap-prompt.json --field sensitive_exposed
scripts/tf-security-scan.sh infra/fixtures/plan-cheap-prompt.json --field verdict
Expected output
module.networking.aws_security_group_rule.db_public_debug:5432
block

It finds Postgres exposed on port 5432 and blocks. But the security scanner only looks at network rules and public-access flags. A database being replaced is not something it checks for, and neither is the instance size. It caught a different one of the three defects — and nothing else.

The FinOps stage catches the cost:

jq -r '.resource_changes[] | select(.address=="module.database.aws_db_instance.main") | .change.after.instance_class' \
  infra/fixtures/plan-cheap-prompt.json
scripts/cost-compare.sh infra/fixtures/cost-estimates/estimate-good.json \
  infra/fixtures/cost-estimates/estimate-oversize.json --field verdict
Expected output
db.r6g.4xlarge
block

The plan sizes the database at db.r6g.4xlarge, and priced against the baseline it blocks on the 2x rule. But FinOps only looks at money. A resource being replaced does not, by itself, cost anything extra, so that is not a signal to it. An open port has no price tag either. It caught the third defect, and it would have let the other two through without a second look.

Put those three results side by side and the lesson is clear. Three reviewers, three catches, and not one of them saw more than one defect. The security scan alone would still block this plan — but for an incomplete reason, missing the data loss and the cost entirely. And if the open port had not been there, the security scan would have returned clean, and a security-only gate would have approved a change that destroys the database. Run the security scan on a plan with the replacement but no open port, and you can see that blind spot directly:

scripts/tf-security-scan.sh infra/fixtures/plan-stateful-replace.json --field verdict
Expected output
clean

A plan that destroys the orders database comes back clean from the security reviewer, because destroying a database is not something a security scanner checks for. A gate built from one reviewer has a hole exactly the size of everything that reviewer was never built to look for.

The chain: four reviewers, no gaps left​

Now run the full pipeline over the combined plan. This chains all four reviewers together — IaC → Security → FinOps → Change Reviewer — joined into one verdict, and any one of them can block it:

scripts/change-pipeline.sh infra/fixtures/plan-cheap-prompt.json \
  infra/fixtures/cost-estimates/estimate-good.json \
  infra/fixtures/cost-estimates/estimate-oversize.json --field blockers
Expected output
iac: module.database.aws_db_instance.main
security: sensitive/public exposure
finops: cost > threshold (module.database.aws_db_instance.main)
rollback: replaces/destroys stateful resource(s): module.database.aws_db_instance.main — data cannot be recovered by re-apply

Four blockers, from four independent reviewers, on the one plan. The IaC check caught the replacement. Security caught the open port. FinOps caught the cost. And the Change Reviewer's rollback check confirmed the replacement cannot be undone. Each reviewer found something none of the others could see. The verdict is block, and it is block for all four real reasons at once — which matters, because a change blocked for one reason while quietly carrying two more is a change someone will "fix" the one reason on and resubmit, still broken.

No single reviewer here is incomplete because it was built badly. Each one is doing exactly its job, and each job only covers part of the risk — the security scanner will never price a plan, and the FinOps analyst will never check for an open port. The safety comes from running all four together: whatever slips past one reviewer's blind spot still has to get past the other three. This plan had three real defects. It took three different reviewers to catch them, and a fourth (the rollback check) to spell out for the human what "irreversible" actually means here.

Why one block always wins​

One design choice here is worth looking at closely, because it is the difference between a real gate and a formality. The four reviewers are never averaged, never voted, and never approved "on balance" when three of four are happy. Any single block stops the change, no matter what the other three say.

Think about what the alternative would mean. If this were a majority vote, three reviewers saying "fine, apart from my one finding" would make the change "75% approved." That number means nothing. The missing 25% is the part that destroys the database. Risk does not average out — a change that is mostly safe and also destroys production data is not 75% safe. It is unsafe, full stop, and the one objection is the only thing that matters. This is the same rule you already know from Module 8's Change Gate and Module 10's review chain: when the downside cannot be undone, one real objection outweighs any number of approvals.

The rollback check makes this real in a way "how many resources are touched" does not. Check what it says about this plan:

scripts/rollback-review.sh infra/fixtures/plan-cheap-prompt.json --field reversible
Expected output
false

reversible: false. Even if you were willing to accept the cost and the open port, this change still cannot be approved without a plan to restore from backup — because the moment it applies, the orders data is gone, and running Terraform again just builds a new, empty database. The rollback check turns "a stateful resource is being replaced" into the exact question a human decision-maker needs answered: if this goes wrong, we cannot get the data back — so what is the restore plan? Asking that question before approval is the difference between a real decision and a disaster nobody planned for.

Where you will use this​

This is not a Terraform-only problem. It is what happens any time you put an agent on a high-stakes change, and you will run into it again:

  • Reviewing any agent-written infrastructure change. Whether it is Terraform, a Helm values file, or a Kubernetes manifest, "did it apply cleanly" is never the real question. The real question is what it does to state, cost, and exposure that a clean apply does not show you. Run it past more than one reviewer; do not trust a single pass.
  • Setting up checks in a CI pipeline. When you wire plan review into a pipeline, wire in the whole chain, not one linter. A cost check with no security check approves an exposed-but-affordable change. A security check with no rollback check approves a database deletion that just happens to be locked down. Every check you add closes one specific gap, and only that one.
  • Any request that sounds reasonable. Nobody here asked for anything malicious. Whenever you hand a change to an agent, assume it might take a request literally in a way that is unsafe, and let independent reviewers — not the same agent's own judgment — decide whether it ships.
  • Deciding what model each check should run on. The full chain that caught all three defects cost about $1.78 to run. That is a small price for not destroying a production database. Picking the right model size for each reviewer is a real cost decision — but cutting the review itself down to one over-trusted generalist to save a few cents is the mistake this whole module argues against.

The next module carries this same idea — check with more than one independent reviewer, never trust a single pass — onto Kubernetes and GitOps, where "the manifest applied" can hide an even wider set of problems than "the plan applied" does here.
