Agentic IaC and FinOps

Module 9 gave you a team of specialist agents. Module 10 gave you ways to run them together. This module points that team at the highest-stakes work you do: writing the Terraform that builds real infrastructure.

Here is the job. Northstar's campaign starts in nine days. The orders database is under more read load than it was sized for, and the platform team needs a read replica plus an alarm, added before the campaign opens. You are going to have Claude write that Terraform module for you — the same way you would ask a new engineer to build it: give it a clear spec, hold it to your team's house style, make it prove the module works before you trust it, and only then let the change move toward production.

By the end, you will have a real module you could open a pull request with. Not "the agent said it looked fine" — but a module built to a written spec, checked against your team's own conventions, tested without touching a real cloud account, and priced before anyone ships it.

Write the spec first, then let the agent build​

The habit that makes this work has nothing to do with Terraform. It is the same habit that makes any agent-written code good: you write down what you want before you ask for it.

For this module, that means writing a short SPEC.md inside the new module folder: why the change is needed, what it must do, what is not negotiable, and what "done" means. Eleven lines is enough. You write this file yourself. It is not busywork — it is the real engineering decision, put in words the agent can act on.

Notice what the brief does not contain. It does not list the resources, because choosing them is design work and the agent is about to do that properly. It does not repeat the exact AWS strings either — ReplicaLag, GreaterThanThreshold and the rest already live in the house style skill, and a second copy is just something to keep in sync.

It also is not a CLAUDE.md. That distinction matters more than it looks: a CLAUDE.md is injected into every turn of every session that runs in its directory, so it is the right home for rules that are always true and the wrong home for a build brief. Put the brief there and, long after the module ships, every future session in that folder is still paying to be told about work that finished months ago.

A spec like this earns you something specific. When you hand it to Claude, the first thing a well-run session does is tell you whether your spec was clear enough. A bounded task is one where every real decision was already made in the spec, so there is nothing left to discuss — just build it. If Claude comes back with a list of open questions instead, that is not the agent being slow. That is your spec telling you it was too thin, and it is far cheaper to learn that now than three files into the build.

The house style is a skill, not a suggestion​

Every team has conventions: how you name a resource, which fields you always set, which settings are never left to the caller. If those conventions live only in a senior engineer's head, an agent cannot follow them, and neither can a new hire. So you write them down once, as a skill, and both the agent and your reviewers read the same file.

Northstar's terraform-style skill is a real example. A few of its rules, stated exactly as the skill states them:

  • The main resource in a module is labelled main — never this, never default.
  • Every physical name is built from a pattern, "${var.project}-${var.environment}-<role>", never typed out by hand. A hardcoded name works today and breaks the moment the module runs in a second environment.
  • storage_encrypted = true and publicly_accessible = false are hardcoded on every database, not offered as a variable. Turning a guarantee into a variable is itself the mistake — it lets someone switch it off later without anyone noticing.
  • Every variable has a plain-English description. An output with no description is an undocumented API.

This is what "best practices" means in a way you can actually check: not a paragraph of advice, but a short list a script or a human reviewer can test a module against. The agent reads this skill before it writes a line of HCL, and checks its own output against it before handing the module back to you.

Build it test-first, in a worktree​

Once the spec exists, you do not just ask Claude to "write the module." You run the same discipline you would use for any serious change:

  1. Launch Claude as the role, not as a general session: claude --agent iac-engineer. That flag starts the session with the role you built in Module 9 — its system prompt, its model, its tool list. It can write under infra/, it can run plan, validate and fmt, and it has no way to run apply at all. The boundary is real from the first keystroke, rather than depending on a general agent choosing to delegate.
  2. Hand it the brief and let the harness work. The harness here is superpowers — the same skills library this course was built with, installed once with claude plugin install superpowers@claude-plugins-official back in the Plan-Execute-Verify module. You never call its skills by name. You ask for the workflow in plain words — brainstorm the design, write a plan, work test-driven — and it selects and runs them in order. Brainstorming fires before any code and stops to put the design in front of you. Then a plan. Then the test-driven cycle: the failing test first, watched failing, then just enough code to pass it.
  3. The agent writes the test. This is the part worth pausing on, because it is the opposite of what most people expect. Given eleven lines of requirements and a written house style, it produced a far stronger test than a hand-written one: four separate scenarios, every value from the vocabulary table pinned, and — the assertion almost nobody writes by hand — a re-run of the whole module under a different environment to prove the names really do interpolate rather than merely happening to look right.
  4. The agent checks its own work against the style skill before handing it back. You still verify this yourself — the self-check is a first pass, not the final word.

One detail decides whether any of that actually happens: a role can only invoke a skill if Skill is in its tools list. Leave it out and the agent will still find the style file and read it, and still produce a module that works — but the brainstorm, the plan and the test-first discipline never run. You get the output without the method. What a role is allowed to use is as load-bearing as what it is told to do.

All of this happens inside a git worktree — a second copy of the repository, on its own branch, created just for this change. The agent authors there, not on your main branch, so nothing it does can touch the code everyone else works from until you decide to merge. If the whole thing goes wrong, you delete the worktree and nothing was ever at risk.

You do not create that worktree yourself. Isolation is one of the things the harness already owns: ask for it, and the using-git-worktrees skill checks whether you are already isolated, creates one if not, and carries any uncommitted work across with a stash so nothing is stranded behind you. Doing it by hand would work, and you would never find out the harness does it better.

But check that you got it, because this is the least predictable step in the module. Across repeated runs it usually creates the worktree and occasionally announces the intent and stops. One git worktree list tells you which happened. Asking for an outcome and then verifying you actually got it is the same discipline as reading the plan instead of trusting "it looked fine" — it just applies to the harness too.

Because a build like this touches many files over many small steps, you run this session with prompts turned off (--dangerously-skip-permissions), inside that same worktree. Approving twenty small edits one at a time teaches you nothing except how to stop reading them. The worktree is what makes turning the prompts off safe here — the blast radius is a folder you can delete, not your real codebase. Later in this module you will see that turning prompts off does not remove every safeguard — a separate, mechanical check still runs underneath and still blocks the one action that actually matters.

Plan is safe. Apply is not.​

There is one property of infrastructure code that application code does not have: a large share of what it does cannot be undone. Recreating a stateless web server is nothing. Recreating a database destroys the data inside it, and running Terraform again does not bring that data back.

That is why Terraform splits the work into two separate commands, and why this module treats them completely differently. terraform plan only computes what would change — it touches nothing, so you can run it as often as you like, and so can the agent. terraform apply is the one that actually changes real infrastructure, and it is the one step the agent is never allowed to run against production on its own.

The rule that enforces this is the Change Gate you built in Module 8: a check that runs before every command the agent tries to execute, and denies any apply or destroy aimed at production. It does not touch plan, validate, or fmt — those stay completely free, because a rule that stopped the agent from even investigating would get switched off within a week. And because this check runs before the normal permission prompts, it still holds even in the worktree session above, where you turned those prompts off. Turning off the question does not turn off the answer.

So a change like the one you are building always moves the same way: the agent authors and plans freely in its worktree, and the moment anything would actually touch production, a human — or a pipeline a human set up — has to be the one who runs it.

Match the model to the job​

Not every part of this work needs the same model, and paying for more than a task needs is one of the most common, most invisible mistakes in this kind of work.

Writing the module is real judgment — reading a spec, deciding how to structure the HCL, matching an existing house style — so that step runs on Sonnet, and it is genuinely most of what this lab costs. Pricing a plan against a threshold, on the other hand, is arithmetic: read two numbers, compare them, say whether the second is more than twice the first. That does not need a frontier model, so the FinOps check in this module runs on Haiku, and costs a fraction of a cent to do the same job correctly.

The same idea you already use for choosing an EC2 instance size applies here: pick the smallest model that does the job right, not the strongest one by default. Later in the lab you will see the actual numbers — a full four-role review, run with each role on the model it needs, costs about $1.78; the same review with every role on the most expensive model costs about $2.48 and gets the same answer. Recognizing that difference, and choosing not to pay it, is itself the FinOps decision.

Once the module is written, a review chain checks the plan​

Writing a good module and testing it offline gets you most of the way there. It does not tell you what the module actually does to the infrastructure once it is planned. For that, you generate a real plan from your own module and run it through four checks, each looking for something different:

  1. Is anything stateful being replaced? Replacing a database means the old one is destroyed and a new, empty one takes its place. This check blocks on that, no matter how small the rest of the plan looks.
  2. How many resources does this touch, and how many does it destroy? A plan that only creates things is low-risk even if it is large. A plan that destroys even one resource is higher-risk, because destruction cannot be undone.
  3. Does it introduce something the known-good baseline does not have — most importantly, a new rule that opens a port to the whole internet?
  4. What does it cost? terraform plan says nothing about money on its own, so a separate check prices the plan and flags any single resource that grew past twice its previous size.

These four checks map to the specialist roles from Module 9 and 10: an IaC engineer who authors the change, a security reviewer who checks for exposure, a FinOps analyst who checks cost, and a change reviewer who makes the final call, including whether the change can be rolled back if it goes wrong. Only the IaC engineer can write — every reviewer after it is read-only, on purpose. A reviewer that could edit the change it is judging would stop being independent.

Any one of the four can block the change on its own — passing three of four checks does not rescue a change that fails the fourth. The Deep Dive later in this module walks through exactly why that matters: a single plan can fail all four ways at once, and no single reviewer, working alone, would catch more than its own piece of it.

The change reviewer also checks something the scripts never look at: was every change in this branch something its author was allowed to make? That question matters because a pull request is a bundle. In the lab you will put a one-line edit into a role file — giving a read-only reviewer a write tool — and watch the change reviewer find it inside a branch that is otherwise pure Terraform. It reports the obvious problem, that a read-only role now grants and denies Write at the same time. Then it makes the sharper point: no role has authority over the agent files at all, so whoever made that edit was out of bounds regardless of whether the change was a good idea.

That is how permission changes actually reach production — not announced, but riding along inside a change about something else, reviewed by someone looking at the infrastructure and with no reason to open a configuration file.

Refactoring safely: what "the tests still pass" does not tell you​

Once the module works, the next real job is making it reusable. The alarm-and-notification pattern in it is one other modules would want too, and copying it a third time is how an infrastructure rots. So you ask the agent to pull it into its own child module.

This is where two things go wrong in ways worth seeing once.

First: what your tests can see depends entirely on what they assert. When the agent extracts the child module, the assertions move with it — the alarm checks leave the parent's test and reappear in the child's own, while the parent keeps one test proving it is actually wired to the child. That last test is the one that matters. In the lab you orphan the child yourself, by commenting out the call, and the parent's suite fails immediately.

Now imagine the parent had only asserted on an output, which is the obvious and easy test to write. The child module would sit there fully written and fully tested, nothing would reference it, the suite would stay green, and the plan would be byte-identical. Nothing would have told you the refactor never happened. A green suite is not evidence a refactor landed; it is evidence that whatever you asserted on still holds.

Second: the same resources can move. After the refactor is real, compare the plan against the one you saved before. The set of resources is unchanged — same count, same types, all still creates. But three addresses changed, because they now sit inside the child module.

That distinction is the whole lesson, and it is invisible to every check in this module:

  • Terraform tracks a resource by its address, not by what it is in AWS.
  • Change the address and Terraform sees the old one as gone and a new one as needing creation.
  • Against real state, that means destroy and recreate — a new SNS topic ARN, and an email subscription your teammates have to re-confirm before alerts reach anyone again.
  • The plan still looks perfect: all creates, nothing destroyed, security clean, cost unchanged.

The fix is a moved block, written by the person doing the refactor, telling Terraform that the old address and the new address are the same thing. No scanner can infer it for you. A plan full of creates is only safe if the addresses it creates were not already something else.

A good refusal is not the same as a control​

There is one more thing worth testing before you trust any of this, because it is easy to get backwards.

If you ask the agent, mid-session, to turn off encryption or open the database to the public, a well-built agent refuses — often citing your own spec file back at you, and correctly. That is a good answer. It is also not something you should rely on. The same model, asked slightly differently, on a different day, with a thinner spec file in context, can give you a different answer. A refusal is something the model chose to do. It is not a rule that always fires.

Here is why that distinction matters in practice: the agent is not the only way infrastructure gets changed. A teammate's pull request, an old branch someone merges by mistake, a value someone edits by hand to unblock a demo — none of those go through a model at all. So the real test is to make the exact same change yourself, by hand, with a plain text edit, and see whether anything still catches it. In this lab, it does: the same security check that scanned the agent's plan also scans yours, finds the same problem, and blocks it — without caring who made the change or how reasonable the request sounded. That is the actual control. The refusal was a nice extra.

It is also worth checking what a scanner like this does not say. If you turn off two separate safety settings and the scanner only reports one, that is not the scanner being lenient — it means nobody wrote a rule for the second one yet, even though the information needed to catch it was sitting right there in the plan. A scanner only checks what someone told it to check. Trusting one you have not read the rules for is trusting a list you have never seen.

What you'll do in the lab​

You are going to build Northstar's read replica module end to end, the way the sections above describe it:

  1. Look at what you are extending — the current database size and the infrastructure's monthly cost, so the change is a decision, not just a ticket.
  2. Set up an isolated worktree and write the module's CLAUDE.md spec yourself.
  3. Launch Claude as the iac-engineer role and hand it the brief — the harness brainstorms, plans, and writes the failing test before any code exists.
  4. Verify it yourself — fmt, validate and test from the module root — and push back if it drifts from the brief or the house style.
  5. Wire it into an environment and plan from there, because a module on its own builds nothing — no AWS account involved.
  6. Run your own plan through the review chain, then get an independent verdict from the change reviewer — with a planted permission change in the branch, so you see the authority check do real work.
  7. Price it, including asking where the price actually came from.
  8. Refactor it for reuse, then orphan the child module on purpose to find out whether your tests would notice — and find the three resource addresses that moved.
  9. Test the difference between a good refusal and a real control, by making the same risky change yourself and watching what catches it.
  10. Try to apply straight to production, and watch the Change Gate stop it even with every prompt turned off.
  11. Commit the module and merge it, the way a change is actually supposed to land.

The Deep Dive takes this further: one plan, carrying three real defects at once, and why it takes all four reviewers working together — not one clever one — to catch every one of them.
