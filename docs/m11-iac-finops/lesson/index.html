Agentic IaC and FinOps

Module 9 gave you a team of specialists and Module 10 gave you the topologies to run them in. This module points that machinery at the highest-consequence surface in your estate: the Terraform that provisions real infrastructure. When an agent edits application code and gets it wrong, a test fails and you fix it. When an agent edits infrastructure code and gets it wrong, the failure mode is a database recreated from empty, a service oversized into a five-figure monthly bill, or a datastore opened to the public internet: and you find out after the change reached production, not before.

Here is the situation this module closes. Northstar's marketing team is running a campaign next week and the platform needs one bounded infrastructure change to support it, a small capability added to the estate. You want to hand that authoring to an agent, because it is exactly the kind of mechanical Terraform work an agent is good at. But "an agent authored a Terraform change" and "that change is safe to apply to production" are two very different claims, and the gap between them is everything this module is about. The change has to pass module standards, a plan review, policy, a security scan, a cost comparison, and a rollback review before anyone approves it, and you want each of those checks run by the specialist provisioned for it, not by one over-trusted generalist.

Why planning is safe and applying is not​

The reason this matters at work is that infrastructure code has a property application code does not: a large fraction of its operations are irreversible. Recreating a stateless web server is a non-event. Recreating a database destroys the data inside it, and no amount of "re-apply the Terraform" brings that data back. So the single most important distinction in this whole module is the one between planning a change and applying it.

Analogy: think about the difference between a surgeon reviewing a scan and a surgeon making an incision. Reading the scan (studying it, measuring the tumor, arguing about the approach in a case conference) is completely safe. You can do it a hundred times, from a hundred angles, and the patient is untouched. The incision is the irreversible act; it happens once, deliberately, with the whole team having signed off, and never as an improvisation mid-discussion. terraform plan is reading the scan. It computes exactly what would change and touches nothing: you can run it freely, let an agent run it freely, run it in CI on every branch. terraform apply is the incision. It mutates real infrastructure, and it is the one operation the agent must never perform on production on its own.

This is why mutation is a separate authority. In Module 8 you built the Change Gate: a hook that denies a production terraform apply from an agent identity. That gate is the enforcement behind this whole module. The agent can plan all day; the moment it reaches for apply on production, the gate denies it, and the change is routed the only safe way: branch, plan, review, approval, and then a reconciler or CI pipeline applies it. The agent proposes; a human (or a pipeline a human configured) disposes.

Read the colors: the green box is the safe operation the agent runs itself, the red box is the irreversible one it never touches, and everything between them is the review this module builds. The plan is free; the apply is gated; the review is what earns the crossing.

The gate's discrimination is worth understanding, because it is what lets the agent stay productive instead of being blocked from everything. The Change Gate does not deny "Terraform commands": that would stop the agent from doing its job. It denies precisely terraform apply (and destroy) when the target is production, and lets terraform plan, terraform validate, and terraform fmt through untouched. The agent can plan against production all day to see what a change would do; it simply cannot pull the trigger. That is the mark of a good boundary: maximally permissive on the safe operations, absolute on the irreversible one. A gate that blocked planning too would be security theater that makes the agent useless; a gate that allowed apply would be no gate at all. In the lab you will watch the same gate deny the apply and allow the plan on the same production environment, which is the whole discrimination in two commands.

The plan JSON is the artifact you review​

Here is the shift that makes agentic IaC review possible at all: you do not review the HCL the agent wrote, and you do not review the human-readable terraform plan output. You review the plan JSON.

terraform show -json tfplan takes a saved plan and emits a structured JSON document: every resource that will change, the exact action on it (create, update, delete, or the ["delete","create"] pair that means replace), and the full before-and-after of every attribute. It is the plan as data, not as plain text.

Analogy: the difference between the plan JSON and the plan's text output is the difference between a blood panel and the patient saying "I feel a bit off." The patient's report is a narrative: useful, but you cannot compute on it, you cannot set a threshold against it, you cannot diff this week's against last week's. The blood panel is structured: every marker has a name and a number, so a rule can say "flag any value above this line" and a machine can run that rule the same way every time. The plan JSON is the blood panel of an infrastructure change. Because it is structured, every review this module runs (is a stateful resource being replaced, how many resources are touched, is a CIDR opening to the world, how much will this cost) becomes a fixed query against the same document, not a judgment call over plain text.

That is what makes the review CI-able and gradeable. In the lab, every specialist check is a deterministic read of the plan JSON: plan-analyze.sh for structure, tf-security-scan.sh for exposure, cost-compare.sh for spend. No model is in the loop for the check: the model authored the change; deterministic tools review it. That separation is deliberate, and it is the same principle as Module 9's read-only reviewers: the thing that writes the change is not the thing that decides it is safe.

This is also where an agent earns its keep on the authoring side, not just the review. Three Terraform tasks are tedious for a human and well-suited to an agent that can read the whole estate at once:

  • Authoring and refactoring HCL. Extracting a repeated block into a module, threading a new variable through three environments, renaming a resource consistently: mechanical edits across many files where the agent's advantage is that it holds the entire module tree in context. It writes the HCL; terraform validate and terraform fmt check it; the plan proves the effect.
  • Import planning. When a resource already exists in the cloud but not in state (a bucket someone created by hand, a security group clicked into being during an incident), it has to be imported so Terraform manages it going forward. The agent's job is to read the live resource, write the matching HCL, and produce the import block or terraform import command, then plan to confirm the import is a no-op (state now matches reality) rather than a surprise change. A bad import plan is one that shows a diff (meaning the HCL does not match what is actually deployed), and the plan JSON is exactly where you catch that.
  • Design-alternative analysis. Asked to "make the database handle more load," an agent can lay out the options, a larger instance class, a read replica, connection pooling, caching, with the cost and blast-radius trade-off of each, so the human chooses from a priced menu instead of rubber-stamping the first idea. The value is not the agent picking; it is the agent surfacing the alternatives with their consequences attached, which is the analysis a rushed engineer skips and later regrets.

The four questions a plan review answers​

A plan review is not one question, it is four, and each maps to a specialist and a control you can run:

1. What is being replaced, and is it stateful? A replacement is ["delete","create"]: Terraform will destroy the resource and build a new one. For a load balancer or a launch template, that is a brief blip. For a database, an EBS volume, an S3 bucket (a stateful resource), it is data loss. The analyzer's rule is exact: any replacement of a stateful resource type (aws_db_instance, aws_rds_cluster, aws_ebs_volume, and their kin) is a block, regardless of how small the plan looks. A one-line plan that replaces the orders database is more dangerous than a fifty-resource plan of pure creates.

2. What is the blast radius? Not "is the diff big" but "how many real resources does this touch, and how many does it destroy." A plan that creates thirty resources and destroys none is low blast radius even though it is large. A plan that destroys one is higher, because destruction is the irreversible direction. The reviewer gates on the destroy count and the touched count together.

3. Is there environment drift? The change was authored against one environment; does it introduce something a known-good baseline does not have? Diffing the candidate plan against the baseline plan surfaces exactly what drifted in: a new resource, and most importantly a new 0.0.0.0/0 rule that was not there before. Drift analysis is how you catch the exposure that slipped in under cover of a legitimate change.

4. What does it cost? terraform plan says nothing about money. A cost estimate (from a tool like Infracost) prices the plan, and the FinOps comparison comes down to a delta and a multiple: this change is +$X/month, and this specific resource grew Y times its current size. The FinOps rule flags any single resource that grows past a threshold, 2x by default, because a database quietly resized from large to 4xlarge is a legitimate-looking one-line diff that carries a $2,800/month price tag.

No single question is the review. A change can pass structure and cost and still open a datastore to the internet; it can pass security and still destroy a database. The review is all four, and the verdict is fail-closed on the strongest objection.

The specialist handoff chain​

You met these four specialists in Module 9 and learned in Module 10 that a dependent, staged job is a pipeline topology. The plan review is exactly that pipeline: IaC Engineer → Security Reviewer → FinOps Analyst → Change Reviewer, each producing a structured evidence packet the next consumes, joined into one verdict.

Analogy: this is the approval chain on a mortgage, not a single loan officer's gut call. When you apply for a mortgage, the file does not get one person's yes-or-no. It passes through an underwriter who checks the numbers add up, an appraiser who independently values the property, a title officer who checks nobody else has a claim, and a closer who verifies every prior sign-off is present before funding. Each looks at a different risk, each is independent, and any one of them can stop the file. The closer does not re-appraise the house; the appraiser does not check the title. The strength of the chain is that four different kinds of risk get four specialists, and one dissent stops the deal. The plan review is built the same way: four reviewers, four kinds of infrastructure risk, one verdict, and any block stops the change.

Two properties make this chain trustworthy, and both come straight from Module 9. First, the reviewers are read-only. The IaC Engineer carries a write tool because authoring HCL is its job. Every reviewer after it (Security, FinOps, Change Reviewer) has no Edit or Write tool at all. A reviewer that could patch the change it is reviewing has stopped being a reviewer; its independence is the control, and that independence is structural, not a promise. Second, each role runs a right-sized model. Security and Change review run on Opus because a missed subtlety there is most expensive. FinOps runs on Haiku because comparing two numbers against a threshold is a bounded, mechanical task that does not need a frontier model. IaC runs on Sonnet: capable authoring without paying for judgment the task does not require.

FinOps applies to the agents, too​

That last point deserves its own beat, because it is the FinOps idea turned back on the thing doing the reviewing. You are used to FinOps as a discipline about cloud spend: right-size the instance, don't pay for capacity you don't use. The same discipline applies to the agents: right-size the model to the role, don't pay for judgment the task doesn't need.

Analogy: you would not send a cardiac surgeon to take a blood-pressure reading. The reading needs doing correctly, but it is a bounded task a nurse does perfectly well, and putting the surgeon on it wastes the one resource, surgeon-hours, that is genuinely scarce and expensive. Running the FinOps analyst on Opus is sending the surgeon to take the blood pressure. It reads a plan and compares numbers to a threshold; Haiku does that correctly and costs a fraction. Spending Opus on it is waste, and recognizing that waste is itself a FinOps decision.

In the lab you produce the agent-run cost receipt: the actual token cost of running the four-role chain with each role on its right-sized model, compared against the counterfactual of running every role on Opus. The mixed-model chain comes out cheaper, and the receipt proves it: a FinOps analysis of your FinOps analysts. The point is not the exact dollar figure; it is that "which model does this role need" is a cost decision you can measure and defend, exactly like "which instance size does this service need."

Worktree isolation: the change stays quarantined until it clears​

One more structural piece. The agent authors the campaign change in a git worktree, a separate working directory on its own branch, so the main branch stays clean the entire time the change is being reviewed.

Analogy: a worktree is the biosafety lab, not the open bench. You do not study a novel pathogen on the counter where everything else lives; you study it in a sealed, negative-pressure room, and nothing leaves that room until it has been cleared. The worktree is that sealed room for a risky change. The IaC Engineer authors in it, the plan is generated in it, the whole review chain runs against it: and the change only merges to main after every stage in the chain has approved. If the review blocks, the change never touched the trunk; you throw the worktree away and nothing was contaminated. This is the isolation control from Module 9's role bundles (worktree: true for the IaC Engineer and Change Reviewer), applied to the highest-stakes work you do.

What you'll do in the lab​

You will take Northstar's campaign infrastructure change through the full gate: author it in isolation, plan it, and prove every specialist control holds:

  1. Prove state safety: watch the Change Gate deny terraform apply on production and allow terraform plan, confirming mutation is a separate authority.
  2. Analyze the plan JSON: run structural analysis for replacements, stateful-replace detection, and blast radius against the real Northstar plans.
  3. Catch the stateful replacement: see a plan that recreates the orders database get blocked, and named, on structure alone.
  4. Run the security scan: flag the 0.0.0.0/0 rule opening Postgres to the internet, and prove a clean plan does not cry wolf.
  5. Detect environment drift: diff a candidate against the known-good baseline and surface the exposure that drifted in.
  6. Run the cost comparison: get the +$2,847/month delta and the 16x resource multiple that turn a one-line diff into a budget decision.
  7. Review rollback viability: see the stateful-replace change judged irreversible, so its approval requires a restore-from-backup plan.
  8. Run the full handoff chain: IaC → Security → FinOps → Change Reviewer over a plan, joined into one verdict, and produce the agent-run cost receipt proving the mixed-model chain is cheaper than all-Opus.
  9. Let the repository certify it: grade.sh m11 runs the whole matrix.

The Deep Dive then takes the hardest case: a single agent-generated change that passes syntax but carries all three defects at once, it replaces the database, oversizes it, and opens it to the internet, and shows why no single reviewer catches all three, but the chain does.
