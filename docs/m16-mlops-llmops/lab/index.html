Lab — Diagnosing the LLM Gateway Regression

The lesson laid out five disciplines: the gateway config is a reviewed artifact, the four dials are golden signals, provider latency is not application latency, prompts live in Git, and a regression suite is a CI gate. This lab makes all five runnable against Northstar's real gateway configuration, provider map, and request traces — and walks you through the support incident from symptom to fix.

The story you are dropping into: the support-drafting assistant slowed to a crawl this afternoon and the model bill spiked. Nothing Northstar wrote is down. A routing change moved the entire support workload onto the wrong model. Your job is to prove that from the artifacts, quantify the damage, prove the latency is the provider's and not your code's, and deliver the revert through the review gate.

Where you are working

You start at the root of the agentic-ops-lab workspace. The gateway config lives under platform/gateway/ — routing.yaml (which model serves which traffic), providers.yaml (tier → provider, price, latency), and prompts/ (the versioned prompt). The last-known-good routing is fixtures/gateway/routing-baseline.yaml; request traces are under fixtures/gateway/traces/. The four M16 tools are gateway-diff.sh, llm-dials.sh, and promptfoo-gate.sh, all under scripts/. Every graded step is a deterministic read or script run — it grades the same on any machine, with no live model provider required. The role you meet in the deep dive is .claude/agents/mlops-engineer.md.

Step 0 — Prerequisites​

Confirm your tools. This lab needs jq, yq, and bash. Note that yq here is the Python kislyuk/yq build (a jq wrapper), the same one the earlier modules use.

jq --version
yq --version
Expected output
jq-1.7.1
yq 3.4.3

Your versions will differ. jq drives every JSON check; yq reads the YAML gateway config inside the scripts. If yq is missing, install it (brew install python-yq on macOS, or pip install yq) — every gateway tool fails closed without it.

Step 1 — Read the reviewed artifact​

Before diagnosing anything, look at the config that broke. The routing file is the switchboard: which model tier serves which traffic class.

cat platform/gateway/routing.yaml
Expected output (abridged)
version: 3

defaults:
  fallback: fast
  timeout_ms: 8000

routes:
    # DELIBERATE BUG (M16): support was 'fast' in v2. This route flip sends the
    # entire high-volume support workload to 'deep' — slower and costlier.
  support:
    model: deep           # <- REGRESSED. Baseline (v2) had 'fast'.
    max_tokens: 512
    rate_limit:
      rpm: 600
      tpm: 300000

The support class points at deep. Hold that thought — the comment tells you it used to be fast, but in a real incident nobody leaves you a comment. You are going to prove the regression mechanically, not by reading a hint.

Now look at what the tiers actually cost and how fast they are. The provider map carries the two numbers every dial depends on:

yq -r '.models | to_entries[] | "\(.key)\tprice=$\(.value.price_per_1m_usd)/1M\tp95=\(.value.latency_ms.p95)ms\ttpm_ceiling=\(.value.tpm_limit)"' platform/gateway/providers.yaml
Expected output
fast	price=$0.8/1M	p95=900ms	tpm_ceiling=500000
mid	price=$3.0/1M	p95=2600ms	tpm_ceiling=300000
deep	price=$15.0/1M	p95=9500ms	tpm_ceiling=120000

deep is roughly 19× the price of fast and 10× the p95 latency, and its provider rate-limit ceiling is lower (120k tpm vs 500k). Every one of those three facts is about to hurt, because the support class was just pointed at deep.

Step 2 — Flag the regression by diffing against the baseline​

You could eyeball the diff. You would also skip that when the queue is on fire. gateway-diff.sh is the reviewed-artifact gate made mechanical: it compares the current routing against the last-known-good baseline, and for every route whose tier changed it prices the move and renders a verdict.

scripts/gateway-diff.sh
Expected output
{
  "changed": [
    {
      "route": "support",
      "from": "fast",
      "to": "deep",
      "price_per_1m_usd": {
        "from": 0.8,
        "to": 15.0
      },
      "provider_p95_ms": {
        "from": 900,
        "to": 9500
      },
      "support_cost_delta_per_day_usd": 8946
    }
  ],
  "support_cost_delta_per_day_usd": 8946,
  "verdict": "review-required"
}

There it is, proven mechanically: the support route moved fast → deep, price jumped 0.8 → 15.0, p95 jumped 900 → 9500ms, and the modeled workload cost delta is +$8,946/day. The verdict is review-required — not because a route changed, but because it moved to a tier that is both costlier and slower. That is the gate refusing to wave the change through.

The verdict is what CI or a review gate keys on. Read it alone:

scripts/gateway-diff.sh --field verdict
Expected output
review-required

A one-line edit to routing.yaml produced a review-required verdict with an $8,946/day number attached. This is the whole first discipline in one command: a route change is priced as a cost-and-SLO decision, not read as a config typo.

Step 3 — Read the four dials​

The diff told you what changed. The dials tell you how bad it is across all four axes at once. Read the support route's dials:

scripts/llm-dials.sh dials support
Expected output
{
  "route": "support",
  "model": "deep",
  "latency": {
    "p50_ms": 4200,
    "p95_ms": 9500
  },
  "token_cost": {
    "price_per_1m_usd": 15.0,
    "day_cost_usd": 9450
  },
  "rate_limits": {
    "route_rpm": 600,
    "route_tpm": 300000,
    "provider_tpm": 120000,
    "tpm_headroom_pct": -150
  },
  "quality": {
    "last_gate_verdict": "unknown"
  }
}

Read all four together, the way the lesson said. Latency: p95 of 9.5 seconds for a feature where a human is waiting on a draft. Token cost: $9,450/day for a class that cost a fraction of that yesterday. Rate limits: the killer detail — the route is configured for 300,000 tpm, but the deep tier's provider ceiling is only 120,000, so the headroom is −150%. The flip did not just make support slow and expensive; it configured it to exceed the provider's rate limit, which means throttling and dropped requests on top of everything else. Quality: unknown, because no regression gate has run yet — you fix that in Step 5.

The negative-headroom trap

tpm_headroom_pct: -150 is the finding an eyeball review misses every time. The routing file's tpm: 300000 looked fine when support ran on fast (500k ceiling). The moment the tier flipped to deep (120k ceiling), the same unchanged rate-limit line became a violation. This is why routing and provider facts are reviewed together: a number that was safe under one tier is a breach under another, and only pricing the change against the provider map surfaces it.

Step 4 — Prove it is the provider, not your code​

Support is slow. Before anyone "optimizes the application," settle the argument the lesson set up: is the latency the provider's (fix the route) or the application's (fix the code)? Split a real request trace from after the regression:

scripts/llm-dials.sh split fixtures/gateway/traces/support-regressed.json
Expected output
{
  "trace_id": "req-support-9f2a",
  "route": "support",
  "model": "deep",
  "total_ms": 8730,
  "provider_ms": 8390,
  "application_ms": 340,
  "dominant": "provider",
  "provider_share_pct": 96.1
}

The verdict is unambiguous: of 8,730ms total, 8,390ms is provider time and only 340ms is application time. dominant: provider, 96.1% of the wait is the model's own kitchen. This is a routing problem, full stop — no amount of application optimization touches the 96% that is the provider generating tokens on a deep model.

Now falsify the "our code got slower" hypothesis directly by splitting the baseline trace — a request from before the regression — and comparing the application half:

scripts/llm-dials.sh split fixtures/gateway/traces/support-baseline.json --field application_ms
scripts/llm-dials.sh split fixtures/gateway/traces/support-regressed.json --field application_ms
Expected output
220
340

Application time went from 220ms to 340ms — essentially flat, a rounding error next to the multi-second provider swing. Your code did not get slower. If you had spent the incident profiling the application, you would have been optimizing the 340ms and ignoring the 8,390ms. The split is what keeps you from chasing the wrong half.

Why this step comes before the fix

It is tempting to skip straight to reverting the route — you already know it is wrong. But an incident write-up that says "we reverted the route" without the provider-vs-application split leaves the next responder no way to tell a routing regression from an application slowdown. The split is the evidence that makes the fix defensible: this class of latency (provider-dominant) has this fix (routing), and here is the number that proves the category.

Step 5 — Run the quality gate on the versioned prompt​

The support prompt is a file in Git, not a string in application code. Confirm it exists and carries the behaviors that matter:

sed -n '1,12p' platform/gateway/prompts/support-summarize.txt
Expected output
You are Northstar Commerce's support-drafting assistant. Given a customer
support ticket, produce a concise draft reply.

Rules:
- Open with the customer's name if present, otherwise "Hi there,".
- State the resolution or next step in the FIRST sentence.
- If the ticket is about an order, always include the order ID verbatim.
- Never promise a refund, credit, or delivery date the ticket does not
  already confirm. If unconfirmed, say a human will follow up.
- Keep it under 90 words. Plain, direct, no marketing language.

Each of those rules is a behavior a regression could break. The regression suite pins the important ones as assertions. Run the gate against a good set of recorded outputs:

scripts/promptfoo-gate.sh evals/promptfoo/support-summarize.yaml --set good --field json
Expected output (abridged)
{
  "set": "good",
  "passed": 8,
  "failed": 0,
  "failed_required": 0,
  "results": [
    {
      "test": "order-ticket-keeps-id",
      "assert": "contains",
      "value": "NS-48213",
      "required": true,
      "pass": true
    }
  ],
  "verdict": "pass"
}

Eight assertions, zero failures, verdict: pass, exit code 0. Every required behavior holds — the draft keeps the order ID, avoids the word "refund," stays under the word limit, greets by name. This is the green CI check a prompt change must earn.

Now see the gate do its actual job — catch a regression. The regressed set is what the drafts looked like when quality slipped: inventing refunds, dropping order IDs, guaranteeing delivery dates.

scripts/promptfoo-gate.sh evals/promptfoo/support-summarize.yaml --set regressed --field verdict
echo "exit code: $?"
Expected output
fail
exit code: 2

verdict: fail, exit code 2. Five required assertions broke, and the gate exits non-zero — which in a CI pipeline means the check is red and the change does not merge. The same suite that passed the good outputs blocks the regressed ones. That is quality turned from a vibe into a gate: a prompt or model change that quietly makes the drafts worse is stopped before a customer ever sees it.

Why the gate writes a state file

promptfoo-gate.sh records its last verdict to agentops/gateway/last-gate.json, which is why llm-dials.sh can show the quality dial alongside the other three. Run the good gate, then re-read the dials, and the quality.last_gate_verdict flips from unknown to pass — all four dials finally reading together. This is the wiring the deep dive builds on.

Step 6 — Deliver the fix through the gate​

You have the diagnosis, the cost, the latency proof, and a green quality gate. Now deliver the fix the way every change in this course is delivered: make the edit, then let the gate confirm it. Revert the support route to fast:

sed -i.bak 's/^    model: deep           # <- REGRESSED.*/    model: fast           # reverted to v2 baseline (M16)/' platform/gateway/routing.yaml
scripts/gateway-diff.sh --field verdict
Expected output
clean

The verdict flips from review-required to clean. No route now sits on a costlier-and-slower tier than the baseline — support is back on fast. The same gate that blocked the regression now certifies the fix. Confirm the dials agree:

scripts/llm-dials.sh dials support --field latency_p95
scripts/llm-dials.sh dials support --field tpm_headroom
Expected output
900
40

p95 back to 900ms, and tpm headroom back to a healthy positive 40% — the fast tier's 500k ceiling comfortably above the route's 300k. Latency fixed, cost fixed, rate-limit breach cleared, all from reverting one line and confirming it through the gate rather than trusting the edit.

Teardown​

Restore the workspace to the state a fresh clone starts in — the regression in place (so the lab is repeatable) and the generated gate-state file removed.

# Restore the deliberate regression so the lab can be re-run from the start.
mv platform/gateway/routing.yaml.bak platform/gateway/routing.yaml 2>/dev/null || \
  sed -i 's/^    model: fast           # reverted to v2 baseline (M16)/    model: deep           # <- REGRESSED. Baseline (v2) had '"'"'fast'"'"'./' platform/gateway/routing.yaml

# Remove the runtime gate-state file (regenerated on demand; gitignored).
rm -f agentops/gateway/last-gate.json
rmdir agentops/gateway 2>/dev/null || true

# Confirm the workspace is back to the inherited (regressed) state.
scripts/gateway-diff.sh --field verdict
Expected output
review-required

review-required confirms the regression is back in place and the lab is ready to run again from Step 1. If you kept the .bak file, the mv restored the original verbatim; the sed fallback covers the case where it was already cleaned up.

You have run the full LLMOps loop against a real gateway config: flagged a routing regression mechanically, priced it at $8,946/day, proved the latency was the provider's with a trace split, gated the prompt on a regression suite, and delivered the revert through the same gate. The deep dive turns this from a set of commands into a role — the mlops-engineer that owns the gateway the way the finops-analyst owns the cloud bill — and adds the two-layer cost view that prices both the workload and the review itself.
