MLOps and LLMOps

Northstar trains no models. What it operates is the layer over hosted providers: which model serves which traffic, what it costs, how fast it is, whether it is inside its rate limits, and whether the output still passes the quality bar. That is LLMOps, and it is an SRE job with a different set of gauges.

Somebody changed one line of the routing file. Support drafting went from fast to deep. To a git diff it is one word. This module is the diagnosis that follows, and the thing you hand a reviewer at the end.

The gateway is the reviewed artifact​

Analogy: the gateway is the call-routing switchboard in a support centre. A switchboard does not answer calls; it decides which desk each call goes to. Priority customers to the senior team, routine questions to the general queue. Flipping one rule — "send all Tier-1 calls to the premium desk" — is a single switch, and it looks trivial. That one switch floods an expensive team with routine traffic, blows the staffing budget, and makes everyone wait longer. The switch is small. The decision it encodes is not.

Northstar splits the decision from the facts. platform/gateway/routing.yaml says support runs on fast — that is the reviewable decision. platform/gateway/providers.yaml says fast costs $0.80/1M and runs at 900 ms p95 — those are the facts. Split that way, a reviewer can price a routing change immediately, because the facts are one lookup away.

So the first discipline: a route change is a cost-and-SLO decision, not a config typo, and it gets priced before it merges rather than after finance notices.

The four dials​

An LLM feature can go wrong in a hundred ways and the temptation, exactly as in a service incident, is to look at everything. There is a small fixed set of signals that tells you whether it is in trouble and why.

DialThe questionTool
latencyhow long until the user has their answer?llm-dials.sh dials <route>
token costwhat does a day of this traffic cost?llm-dials.sh dials <route>
rate limitshow close is this route to being throttled?llm-dials.sh dials <route>
qualityis the output still good enough for its job?promptfoo-gate.sh <suite>

They trade off against each other, and that is the whole art. A deeper model buys quality and costs you latency and cost and rate-limit headroom. There is no setting that wins on all four — only the right setting for this traffic class. Support wants the fast corner because a human is waiting and the bar is "draftable". The incident path wants the deep corner because being right matters more than being quick. The regression put support in the incident corner.

A recommendation that moves one dial without saying what it cost the other three is not a recommendation. It is a preference.

Provider latency and application latency​

Analogy: a dish is taking too long to reach the table. Either the kitchen is slow, or the waiter is. Same symptom, opposite fix. Shout at the chef when the problem was the waiter and you have achieved nothing except an annoyed chef.

An LLM request splits the same way. Provider latency is the model's own server-side time — the kitchen, a property of the tier you routed to. Application latency is everything your code adds around the call: queueing, prompt assembly, retries, your own network hops — the waiter, and you own it completely.

Measured on the regressed trace: 8,390 ms provider against 340 ms application — 96.1 % provider. On the pre-change trace: 560 against 220. So the slowdown is in the model call, and the fix belongs in the routing file, not the application code.

Never state a cause before the split has run. And note what it does not tell you: the split proves which half is slow, not that the route was wrong. That argument comes from the traffic class.

Every number names its command​

Here is the discipline that separates this module from "run three scripts."

A number that cannot name the command that produced it is not a dial reading. It is a guess wearing a dial's clothes.

So every dial in a recommendation is recorded with its source:

{"dial": "token_cost", "value": 9450, "unit": "usd_per_day",
 "source": "scripts/llm-dials.sh dials support --field json", "measured": true}

source is the exact command, not a file path and not a description. "From the provider map" is not a source. And measured: false is allowed and honest; measured: false beside a confident value is not.

This is not a style rule. Given the real incident and told to work it out, the mlops-engineer role produced a perfectly formatted handoff packet — p95_ms: 9500, day_cost_delta_usd: 8946, tpm_headroom_pct: -150, quality_gate: "pass" — with none of the tools having run. It had called them with positional arguments, they fail-closed on unknown arg, and it computed the numbers by hand instead, noting that they "match exactly" the figures in its brief.

They matched because they came from the brief. +$8,946/day and −150 % are the illustrative examples written into the role file. Checking your answer against your own instructions is not checking. The packet's format was no evidence at all that its numbers were measured.

The dial it could not copy is the one it got wrong

Three of its four numbers were right, and all three were printed in its own role file. The fourth — quality, the one it had to actually measure — it reported as pass while the dial said fail, and it pre-emptively dismissed the contradicting fixture as "not evidence". A well-formatted answer with one invented field is more dangerous than an obviously broken one.

The dial that cannot name what it measured​

Then it turns out the quality dial has no fixed answer either.

llm-dials.sh reports quality.last_gate_verdict by reading a state file and taking .verdict — whatever promptfoo-gate.sh wrote last. Run the gate against the good output set and the dial says pass. Run it against the regressed set and the same dial says fail. No route changed, no model changed, nothing in the config moved.

The state file is honest — it records "set": "regressed" alongside the verdict. The dial reads .verdict and throws the set away.

So a module whose thesis is read all four dials together ships three dials and a rumour. The correct reading of that dial is not pass and not fail. It is unknown, with the sets stated separately — and unknown is never pass.

The house standard, measured​

Every project module in this course hands the agent a written standard: terraform-style, helm-style, gate-style. This one had none, so the role's method lived only in its own prose, and across a full 23-turn diagnosis no skill fired at all — not because Skill was missing from the tool list, but because there was nothing for it to invoke.

Adding gateway-dials-style changed the behaviour on an identical prompt:

no standardstandard, tools deniedstandard, tools allowed
first tool callBashSkill: gateway-dials-styleSkill: gateway-dials-style
dialshand-computedrefused, listed the commands it neededall measured, all sourced
quality dialpass (wrong)unknownunknown, both sets run
cost$0.4506$0.3779$0.3966

The run that guessed was the most expensive of the three. Being made to stop and ask cost 16 % less than being left to invent an answer.

There is a second cause in that table worth naming. The three gateway scripts were not in permissions.allow, so the honest path was blocked. Denying a read-only reporter does not make an agent safe — it makes it guess.

What a recommendation must carry​

The deliverable is not a diagnosis. It is something a change-reviewer can act on without redoing your work:

  • what changed, named — route, from, to, and the command that showed it.
  • the four dials, each with its source, and unknown where a dial cannot name its input.
  • the split, run before any blame is assigned.
  • a number attached to the recommendation. "Revert support to fast" is an opinion. "Revert support to fast: +$8,946/day and 9.5 s p95 against 0.9 s" is a decision.
  • unknowns, never omitted and never silently empty. If you believe there are none, say so — an absent list reads as full coverage.
  • decision_owner, which is never you. The role reads, prices and recommends. The route flip goes through the change gate and a reviewer.

Cost​

StageModelCost
Diagnosis that guessedSonnet$0.4506
Diagnosis that refused and askedSonnet$0.3779
Diagnosis that measuredSonnet$0.3966
Every deterministic tool—$0

mlops-engineer is pinned to Sonnet deliberately. Pricing a diff and reading four dials is not work that needs your strongest reasoner; the scripts do the arithmetic, and the model composes and explains.

What this does not cover​

  • The headline figure is modelled, not billed. +$8,946/day comes from requests_per_day: 900000 and tokens_per_request: 700 in providers.yaml, which the file's own comments call an estimate. It is the right number to recommend on — deterministic, re-checkable, and it moves correctly with the route — but there are two assumptions inside it.
  • The split says which half, not why. Provider-dominant means the model is the slow part. It does not prove the route was wrong; that argument comes from the traffic class.
  • Neither recorded output set is tied to the live route. The gate proves the suite can catch a break. It does not measure what deep is producing for customers today.
  • The tools are deterministic and the agent is not. It will produce a well-formed packet whether or not they ran. The format is not the evidence.

In the lab​

  1. Read the routing change and price it.
  2. Write the brief — what a recommendation must contain.
  3. Run the diagnosis and watch the dials get hand-computed.
  4. Find out why, and fix the cause rather than scolding the agent.
  5. Re-run against the standard and check every number yourself.
  6. Catch the dial that cannot name its input, and repair it.
  7. Hand the recommendation to a reviewer.

The Deep Dive takes the role apart: how it is right-sized, what a cost receipt for the diagnosis itself looks like, and where the rate-limit dial goes negative before anybody notices.
