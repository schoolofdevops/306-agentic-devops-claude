Lab — The Release Gate

Last month a release candidate reached staging with a readiness probe pointing at a path the application does not serve, and a rollout that takes every pod down at once. Both defects were sitting in the candidate, readable, before it shipped. Nothing caught them — because catching them depended on somebody remembering to look.

You are going to build the thing that remembers. Not by writing a script yourself: you write the brief, launch the release-engineer role under the superpowers harness, and it designs, plans and writes the failing tests before any gate exists. Then you wire that gate into CI three different ways — as a shell step, as a headless Claude stage, and as the Claude GitHub Action on a pull request — and you find out which of the three is allowed to decide anything.

By the end you will have a gate that answers may this release proceed with three distinct outcomes, a test suite that has demonstrated all three, and a clear-eyed view of where a model belongs in a release pipeline and where it does not.

Where you are working

Start at the root of the agentic-ops-lab workspace. From Step 2 you move into a worktree the harness creates.

cd ~/agentic-ops-lab

The analysers you will compose are scripts/pipeline-analyze.sh and scripts/canary-verify.sh. The release candidate under judgement is fixtures/release/candidate-values.yaml — a values overlay cut from a long-lived branch, carrying both defects. No cluster is needed for this module: everything is rendered and analysed offline.

Step 0 — Look at the candidate that shipped​

grep -nE 'path:|maxUnavailable' fixtures/release/candidate-values.yaml
Expected output
17:#   2. rollingUpdate.maxUnavailable -> "100%"   (no serving floor during a deploy)
21:    path: /health
30:    maxUnavailable: "100%"

Line 17 is the fixture's own comment describing itself; the two that matter are 21 and 30. The first names a route the application does not serve — the app answers on /healthz, so every pod fails readiness and the rollout stalls with the service looking healthy from the inside. The second permits the rollout to remove every serving pod at once.

Both are plain text in a file somebody reviewed. That is the thing to sit with: this is not a subtle defect that needs a clever tool. It needs any tool at all, running automatically, every time.

Now run the analyser that already knows about both:

scripts/pipeline-analyze.sh --values fixtures/release/candidate-values.yaml --field json | jq -c '{verdict, blockers}'
Expected output
{"verdict":"block","blockers":["readiness: probe path /health is not a route the app serves (/healthz, /readyz, /api/v1/info)","rollout: maxUnavailable 100% leaves no serving floor"]}

The knowledge was already in the repository. What is missing is a gate: one command CI runs that composes the analysers, judges a named candidate, and is trusted when it says no. That is what you are about to build.

Why a new role rather than an existing one. The gate lives under release/ and .github/workflows/, and no role in contracts/authority-matrix.yaml has authority over either. Stretching platform-engineer to cover it would be precisely the finding the change reviewer raised in the previous module: a writable path is not an approvable change class. When the work does not fit an existing authority, the honest move is a new role with its own declared one — not a wider interpretation of somebody else's.

Read what this role may not do, because it is unusual:

grep -A4 '^## Authority' .claude/agents/release-engineer.md | head -8

- **READ / WRITE** under `release/` and `.github/workflows/`. Allowed.
- **EXECUTE** the read-only analysis scripts — `scripts/pipeline-analyze.sh`, `scripts/canary-verify.sh`,
  `helm template`, `helm lint`. Allowed.

It builds the machinery that decides whether a release proceeds, and it may never perform a release or approve one. The proposer is never the approver — and here that separation is enforced by the role's tool list and authority, not by a sentence in a runbook.

Step 3 — Write the requirements, not the design​

Write release/SPEC.md. Notice what is absent: no exit codes, no JSON schema, no mention of which analyser to call. Those are the house standard's job and the agent's job respectively.

# Release Gate — Requirements

## Why
Last month a release candidate reached staging with a readiness probe pointing at a
path the application does not serve, and a rollout strategy that takes every pod
down at once. Both were visible in the candidate before it shipped. Nothing caught
them, because catching them depended on somebody remembering to look.

## What we need
- One command CI can run that decides whether a release candidate may proceed.
- It judges a named candidate, and its answer says which candidate it judged.
- When it blocks, it says what failed and where that finding came from.
- When it cannot do its job — missing input, an analyser that fails — it must not
  approve.

## Constraints
- Follow the `gate-style` skill. It is the house standard and it carries the
  exit-code protocol and the verdict schema.
- Compose the analysers that already exist under `scripts/`. Do not re-implement
  their rules inside the gate.
- The gate reports. It never tags, pushes, deploys, or edits the candidate to make
  itself pass.
- No credentials. If it needs a secret to run, it is doing someone else's job.

## Done means
- The gate's own tests pass from a single command, and each was watched failing
  against the current behaviour before it passed.
- All three outcomes are demonstrated by tests: approve, block, and cannot-evaluate.
- The change is proposed on a branch. Nothing is released.
The one requirement people leave out

"When it cannot do its job, it must not approve."

Everybody specifies the happy path and the blocking path. The third outcome — the gate could not read its input, or an analyser it depends on fell over — is the one that gets written as an afterthought, and it is the one that costs you. A gate that returns "approve" because it never examined anything is worse than no gate, because now there is a green check mark next to it.

Step 4 — Read the standard the agent will be held to​

sed -n '/## The exit-code protocol/,/^## Exact shell traps/p' .claude/skills/gate-style/SKILL.md | head -20
Expected output
## The exit-code protocol — the whole contract

Three outcomes, three codes, and the third one is the one people forget:

| Exit | Meaning | When |
|---|---|---|
| `0` | **approve** | The gate examined the candidate and found nothing blocking |
| `2` | **block** | The gate examined the candidate and found at least one blocker |
| `1` | **cannot evaluate** | The gate could not do its job — missing input, unreadable file, an analyser that failed, a dependency absent |

2 for block is not arbitrary: it is the same code the PreToolUse change gate returns, so every gate in this repository speaks one language. A caller that understands one understands them all.

The section after it is the one worth reading twice — a table of shell constructs that silently turn a block into an approval. set -e with grep -q. $? after a pipeline. An unset variable that makes the gate analyse the default instead of the candidate. You will hit one of these yourself in Step 6.

Step 5 — Hand it over and watch seven tests fail​

claude --agent release-engineer --dangerously-skip-permissions --model claude-sonnet-5
Read release/SPEC.md and build this.

Use superpowers to the maximum of its capabilities: brainstorm the design first and
present it for validation, then write a plan, then work test-driven - write the failing
tests first, watch them fail, then write the gate that makes them pass.

Read the gate-style skill before writing any gate code.

Do not tag, push or deploy anything.

What Claude does. It reads the standard, then runs the existing analysers to see their real output rather than assuming what they return, then writes tests, then the gate.

What you observe. Seven tests, and they run before the gate exists:

FAIL: expected exit 0 (approve), got 127
FAIL: expected exit 2 (block), got 127
FAIL: expected exit 1 (cannot-evaluate), got 127
…
PASS 0 / FAIL 7
This RED is weaker than it looks, and it is worth naming

127 is "command not found". These failures prove the tests execute and the gate is absent. They do not prove the assertions can detect wrong behaviour — a test asserting rc == 2 would also report got 127 if it were checking nothing at all.

A greenfield artifact can only start here. But do not bank it as your red-green evidence: in Step 6 you make a test fail on behaviour, which is the failure that actually tells you the assertion works.

Then GREEN. Verify it yourself rather than reading the summary:

./release/tests/run.sh; echo "suite exit=$?"
Expected output
PASS: approves the fixed candidate (exit 0, candidate=release/tests/fixtures/good-candidate-values.yaml)
PASS: approves with a healthy canary, canary check recorded
PASS: blocks the bad candidate (exit 2, 2 blockers, candidate=fixtures/release/candidate-values.yaml)
PASS: blocks on unhealthy canary, attributed to canary-verify.sh
PASS: cannot-evaluate on missing canary snapshot (exit 1, no stdout)
PASS: cannot-evaluate on nonexistent candidate file (exit 1, no stdout)
PASS: cannot-evaluate on missing --values (exit 1, no stdout)
PASS 7 / FAIL 0
suite exit=0

Read the coverage rather than the count: two approve paths, two block paths, three cannot-evaluate paths. The third outcome has the most tests, which is the right balance for a gate — it is the outcome nobody exercises by accident.

Read one of the fail-closed tests:

cat release/tests/cannot-evaluate-missing-values.test.sh
Expected output
#!/usr/bin/env bash
# cannot-evaluate-missing-values.test.sh — no --values named at all: the gate
# must not silently analyse some default. Fail-closed, exit 1, no stdout JSON.
set -uo pipefail
ROOT="$(cd "$(dirname "$0")/../.." && pwd)"

out=$("$ROOT/release/ci-release-gate.sh" 2>/tmp/ci-release-gate.stderr)
rc=$?

[[ "$rc" -eq 1 ]] || { echo "FAIL: expected exit 1 (cannot-evaluate), got $rc"; exit 1; }
[[ -z "$out" ]] || { echo "FAIL: expected no stdout JSON on cannot-evaluate, got: $out"; exit 1; }
grep -qi 'values' /tmp/ci-release-gate.stderr || { echo "FAIL: stderr does not explain the missing --values input"; exit 1; }

echo "PASS: cannot-evaluate on missing --values (exit 1, no stdout)"

Three assertions, and the middle one is the one a human would skip: no stdout JSON. A gate that fails closed and still prints a verdict object gives a downstream parser something to misread. Silence on stdout is part of the contract.

Note the test captures out=$(…) and then rc=$? on its own line. It does not pipe. That matters in about thirty seconds.

Step 6 — Verify the verdicts yourself, and fall into the trap​

Run the gate directly against the bad candidate:

./release/ci-release-gate.sh --values fixtures/release/candidate-values.yaml | jq -c '.verdict'; echo "block exit=$?"
Expected output
"block"
block exit=0

Exit 0 from a gate that just blocked. Nothing is broken — $? after a pipeline reports jq's status, not the gate's, and jq parsed the JSON perfectly well.

This is row two of the trap table you read in Step 4, and it was written by the same person who then typed this command while validating this lab. It matters because this is exactly how a reviewer "confirms" a gate works: run it, eyeball the output, check the exit code. Do that through a pipe and a blocking gate reports success.

Now do it correctly:

out=$(./release/ci-release-gate.sh --values fixtures/release/candidate-values.yaml 2>/dev/null); rc=$?
echo "rc=$rc"
echo "$out" | jq -c '{candidate, verdict, blockers: [.blockers[] | {detail, source}]}'
Expected output
rc=2
{"candidate":"fixtures/release/candidate-values.yaml","verdict":"block","blockers":[{"detail":"readiness: probe path /health is not a route the app serves (/healthz, /readyz, /api/v1/info)","source":"scripts/pipeline-analyze.sh"},{"detail":"rollout: maxUnavailable 100% leaves no serving floor","source":"scripts/pipeline-analyze.sh"}]}

rc=2, the candidate is named in its own verdict, and every blocker carries the analyser it came from. Six weeks later, that candidate field is what tells you the gate judged the release rather than the default.

And the other two outcomes:

./release/ci-release-gate.sh --values release/tests/fixtures/good-candidate-values.yaml >/dev/null 2>&1; echo "approve rc=$?"
./release/ci-release-gate.sh --values fixtures/release/nope.yaml >/tmp/out 2>/tmp/err; echo "missing rc=$? stdout_bytes=$(wc -c </tmp/out)"
cat /tmp/err
Expected output
approve rc=0
missing rc=1 stdout_bytes=       0
ci-release-gate: FAIL-CLOSED: no such candidate file: fixtures/release/nope.yaml

Three codes, three behaviours, and the third one prints nothing on stdout.

Now make a test fail on behaviour​

The 127 failures in Step 5 proved the tests run. Prove they can catch a wrong answer — break the fail-closed path the way a tired engineer would, by making the gate "helpful":

cp release/ci-release-gate.sh /tmp/gate-good.sh
sed -i '' 's|^fail_closed() { echo "ci-release-gate: FAIL-CLOSED: $1" >&2; exit 1; }|fail_closed() { echo "ci-release-gate: WARN: $1" >\&2; exit 0; }|' release/ci-release-gate.sh
./release/tests/run.sh | tail -5
Expected output
FAIL: expected exit 1 (cannot-evaluate), got 0
--- cannot-evaluate-missing-canary-file.test.sh failed ---
FAIL: expected exit 1 (cannot-evaluate), got 0
--- cannot-evaluate-missing-file.test.sh failed ---
FAIL: expected exit 1 (cannot-evaluate), got 0
--- cannot-evaluate-missing-values.test.sh failed ---
PASS 4 / FAIL 3

On Linux use sed -i without the ''.

That is a behavioural RED. One edit — downgrading a fail-closed to a warning, which reads like a kindness in a pull request — and the gate now approves every release it could not evaluate. Three tests catch it and name the exact expectation they held.

This is the failure mode the whole module exists for. Nobody merges a change titled "make the gate approve broken releases". They merge one titled "don't fail the build on a missing file".

cp /tmp/gate-good.sh release/ci-release-gate.sh
./release/tests/run.sh | tail -2
Expected output
PASS 7 / FAIL 0

Step 7 — Surface one: the gate as a plain CI step​

The gate is a shell script with no model in it. That is a design decision, not a limitation — so the first way to run it in CI has no model either. Ask the role to wire it:

Now wire the gate into CI, in .github/workflows/.

release-gate.yml runs release/tests/run.sh and then the gate against
fixtures/release/candidate-values.yaml on every pull_request. Pure shell. No model,
no secrets, no network. It must fail the job when the gate blocks, and it must
distinguish exit 2 from exit 1 in what it reports.

What you observe. The interesting part is how it keeps the two failure codes apart:

grep -nE "if: steps.gate.outputs.rc|continue-on-error|rc=\\\$\?" .github/workflows/release-gate.yml
Expected output
33:      # explicitly (continue-on-error, not `set -e`) so exit 2 (block) and
38:        continue-on-error: true
42:          rc=$?
54:        if: steps.gate.outputs.rc == '0'
59:        if: steps.gate.outputs.rc == '2'
72:        if: steps.gate.outputs.rc == '1'

continue-on-error on the gate step, the code captured into $GITHUB_OUTPUT, and then three branches. Both 2 and 1 fail the job — a caller must not merge on either — but the log and the job summary never say the same thing for both.

That distinction is the whole reason the third exit code exists. "The gate blocked your candidate" sends a developer to their values file. "The gate could not evaluate" sends somebody to the gate. Collapsing them sends everybody to the wrong place.

Confirm what this workflow is allowed to do:

grep -c 'secrets\.' .github/workflows/release-gate.yml
grep -A2 '^    permissions:' .github/workflows/release-gate.yml
Expected output
0
    permissions:
      contents: read
    steps:

Zero secrets, read-only on the repository. A gate that needs a credential is doing someone else's job — and a gate with write permission is no longer only a gate.

Step 8 — Surface two: headless Claude as a pipeline stage​

The gate decides. It does not explain well — its output is JSON aimed at a machine. So the second surface is a model, doing the job a model is actually good at: turning a verdict into something a developer can act on.

VERDICT=$(./release/ci-release-gate.sh --values fixtures/release/candidate-values.yaml 2>/dev/null)

claude -p "This release gate verdict blocked a candidate. Write the PR comment a reviewer
should see: one line saying what was blocked, then one bullet per blocker naming the fix.
No preamble, under 80 words. Do not suggest overriding the gate.

$VERDICT" --model claude-haiku-4-5-20251001 \
  --strict-mcp-config --mcp-config /tmp/empty-mcp.json \
  --output-format json < /dev/null > /tmp/stage.json

jq -r '"cost=$\(.total_cost_usd)  turns=\(.num_turns)  ms=\(.duration_ms)"' /tmp/stage.json
jq -r '.result' /tmp/stage.json

Create the empty MCP config first, because a pipeline stage should carry nothing ambient:

echo '{"mcpServers":{}}' > /tmp/empty-mcp.json
Expected output
cost=$0.0435861  turns=1  ms=12300
fixtures/release/candidate-values.yaml blocked.
• Readiness probe /health doesn't exist — use /healthz, /readyz, or /api/v1/info
• maxUnavailable 100% — set to ≤75% for serving floor

Four and a half cents, one turn, twelve seconds, on the cheapest model — because the hard part was already done by a script.

Three details in that command are the difference between a demo and a pipeline stage:

  • --output-format json makes the run machine-readable, and the wrapper carries the cost and turn count, which is how you put a price on a stage that runs on every pull request.
  • --strict-mcp-config --mcp-config gives the run no MCP servers. On the machine this was captured from, a local MCP server wrote a line to stdout and corrupted the JSON for jq. In CI you want nothing ambient: no MCP, no plugins, no local settings.
  • < /dev/null because without a stdin redirect the CLI waits and warns "no stdin data received in 3s".
Read the second bullet again

maxUnavailable 100% — set to ≤75% for serving floor.

That is not the house standard. The rule is that a rolling update always leaves a floor, which is a relationship between maxUnavailable and the replica count — 75% of one replica is still zero pods serving. The explanation is useful; the recommendation is wrong.

Run it twice and this gets sharper. The same command on a second run produced Rollout maxUnavailable: 100% violates serving floor — reduce to maintain availability at cost=$0.0417721: vaguer, not wrong, and still not the rule. The wording varies per run; what does not vary is that the explainer is reconstructing guidance it was never given. The gate cited scripts/pipeline-analyze.sh for its finding. The model cited nothing for its fix.

This is the division of labour in one observation. The deterministic gate decided, correctly and reproducibly. The model explained, helpfully and imprecisely. Nobody should take release advice from the explainer — and a pipeline that let the model decide would have shipped a fix that does not fix anything.

Step 9 — Surface three: the Claude GitHub Action on a pull request​

The third surface is the one that runs where the conversation is. Ask for it:

Now add claude-release-review.yml. Use anthropics/claude-code-action@v1 to explain a
blocked verdict on the pull request. Authenticate with claude_code_oauth_token from
secrets.CLAUDE_CODE_OAUTH_TOKEN so a subscription works without an API key. Least
privilege on permissions. Cap the run with claude_args. The model explains; it must not
be able to change the verdict or the code.

Read https://code.claude.com/docs/en/github-actions if you need the exact input names -
do not guess them. Then tell me which inputs you used and why.

What you observe. It fetches the documentation rather than guessing input names, and then makes an argument about privilege:

claude_args: --max-turns 3 and --allowedTools "Read,Grep,Glob,Bash(gh pr comment:*)" … the tool allow-list has no Edit, Write, or general Bash. It can read the repo to explain a source […]

— and the single command pattern it may run is posting a pull request comment.

Deliberately not used — id-token: write: that is required for the action's default GitHub App auth path or for federation. I am using neither, so omitting it is the least-privilege call.

Check it:

grep -nE "uses:|claude_code_oauth_token|claude_args|--max-turns|--allowedTools|if: steps" .github/workflows/claude-release-review.yml
grep -A3 '^    permissions:' .github/workflows/claude-release-review.yml
Expected output
28:      - uses: actions/checkout@v6
54:        if: steps.gate.outputs.rc == '2'
55:        uses: anthropics/claude-code-action@v1
63:          claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
87:          claude_args: |
88:            --max-turns 3
89:            --allowedTools "Read,Grep,Glob,Bash(gh pr comment:*)"
    permissions:
      contents: read # read the repo to explain a finding's source; never write
      pull-requests: write # only granted permission that lets Claude act: post a comment
    steps:

Four boundaries, and each one is doing separate work:

BoundaryWhat it stops
if: steps.gate.outputs.rc == '2'The model never runs unless a deterministic gate already blocked. No verdict, no model.
--allowedTools with no Edit/WriteIt can read the repository to explain a finding. It cannot change the candidate, the gate, or the tests.
--max-turns 3A bounded run. An agent in CI with no turn cap is an unbounded bill and an unbounded runtime.
permissions: contents: readEven if something went wrong, the job's token cannot push.

The claude_code_oauth_token input is the one that matters for you specifically: generate it with claude setup-token and the action runs on your Pro or Max subscription. The alternative input is anthropic_api_key, which bills a separate API account.

This workflow is authored and validated here, not executed

The YAML parses, the input names match the documented schema, and the permissions are minimal. It has not been run on GitHub in this lab, because that needs the Claude GitHub App installed on a repository and Actions minutes spent.

To run it for real on your own fork: claude in your repository, then /install-github-app, which installs the app, stores your token as a repository secret and opens a pull request with the workflow files. Then push a branch containing fixtures/release/candidate-values.yaml as the live values and watch the gate block and the comment appear.

Step 10 — Which surface is allowed to decide?​

Three invocation surfaces, and exactly one authority between them:

grep -c 'ci-release-gate.sh' .github/workflows/release-gate.yml .github/workflows/claude-release-review.yml
grep -n 'exit 0' .github/workflows/claude-release-review.yml | tail -2
Expected output
.github/workflows/release-gate.yml:1
.github/workflows/claude-release-review.yml:2
35:      # explicit exit 0 keep this workflow from ever gating the merge itself;
51:          exit 0

Both workflows run the same gate. Only one of them can fail the merge: in claude-release-review.yml the gate step carries continue-on-error and ends with an explicit exit 0, so that job always succeeds regardless of the verdict. It reruns the gate purely to read rc and decide whether there is a block worth explaining — it never decides whether the merge may proceed. Its own comment says so:

This job never decides pass/fail for CI — it only decides whether there is a block worth explaining … that job belongs to release-gate.yml alone.

That is the division worth carrying to work. The deterministic thing decides; the model explains the decision to a human. Reverse those two and you have built a system whose release criteria change from run to run.

Which model for this lab, and why​

The build is the bill, and it is small. The captured runs: isolation and the worktree, $0.28; the design-plan-TDD build, $0.73; the CI wiring with the documentation fetched, $0.73. All on Sonnet, as the role file pins it. Writing a gate against a written standard is judgment work — it is deciding what "cannot evaluate" means for this pipeline — so it gets a capable model once.

The stage that runs forever is the cheap one. The headless explain-the-block stage costs $0.0436 a run on Haiku, because a script already decided and all that is left is writing three sentences. On a repository with fifty pull requests a week that is about two dollars a month.

That inversion is the lesson. The expensive model is used once, at authoring time, to produce a deterministic artifact. The cheap model runs every time, doing work that cannot affect the outcome. A pipeline that puts an expensive model in the decision path pays repeatedly for a decision it cannot reproduce.

Limits — what this lab does not give you​

  • The gate judges what the analysers know. It composes pipeline-analyze.sh and canary-verify.sh; anything neither of them checks is not checked. A clean verdict means "none of the rules somebody wrote fired".
  • The GitHub Action was not executed here. It is authored, parsed and checked against the documented inputs. Its behaviour on a real pull request is yours to confirm on your own fork.
  • --max-turns 3 bounds the run, not the blast radius. The allow-list does that. A turn cap on an agent that could write files would just be a smaller accident.
  • The model in the pipeline is not reviewed. Its comment is generated fresh each run. It was measurably imprecise in Step 8 — treat its output as a prompt to go and read the standard, never as the standard.
  • A subscription token is a personal credential. CLAUDE_CODE_OAUTH_TOKEN is tied to the person who ran claude setup-token. For a shared repository, an organisation API key or workload identity federation is the right answer, and both are named in the documentation linked in Step 9.
  • Nothing here tested the release itself. The gate reads a candidate. Whether the release works is a question for the canary, and for the module after this one.

Step 12 — Take it to your own pipeline​

Read the three checks our CI runs today that most often block a release, and the
runbook we follow when one of them fires.

Write me a gate-style skill for this repository: the exit-code protocol we should use,
the verdict schema, and the shell traps that would silently turn one of our blocks into
an approval. Use the checks we actually run, not the ones you would recommend.

Then tell me which of our current checks cannot report a cannot-evaluate outcome at
all, and what each one does today when its input is missing.

That last question is the one that finds things. Most CI checks have two outcomes because the shell gives you two for free, and the third outcome is the one that decides whether a green pipeline means anything.

Exercise​

  1. Add a check the analysers do not have. Pick something your team cares about — an image tag that is not latest, a required label — and add it to the gate, test-first. Watch your new test fail against the current gate before you make it pass.
  2. Break a different trap. Take any row from the gate-style trap table that the gate does not currently exhibit, introduce it deliberately, and find out whether the existing seven tests notice. Where they do not, that is a test you are missing.
  3. Price your own stage. Run the Step 8 headless call against a verdict with five blockers instead of two, and compare total_cost_usd. Then decide what your monthly bill would be at your real pull request volume.

Teardown​

cd ~/agentic-ops-lab
git worktree list | awk 'NR>1 {print $1}' | xargs -I{} git worktree remove {} --force
git branch -D release-gate/ci-gate 2>/dev/null
ls release/ 2>/dev/null || echo "release/ is only on the branch"
Expected output
release/ is only on the branch

If you merged the branch first, you will see the release/ tree instead — either is fine. The worktree was scratch space; the commit is the artifact.

You built a gate that answers three questions instead of two, watched it approve every unevaluable release after a one-line "kindness", and then ran it three ways: as a shell step that can fail a merge, as a four-cent model stage that can only explain, and as a GitHub Action bounded by an allow-list. The thing that decides is a script anyone can read. That is the point.

scripts/grade.sh m13 checks all of it — the gate's three outcomes, the tests that demonstrate them, and that neither workflow gives the model a way to change a verdict.
