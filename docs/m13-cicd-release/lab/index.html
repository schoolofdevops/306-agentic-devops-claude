Lab — The Release Gate

The lesson drew the release chain: an inspector agent produces a structured verdict, a supervisor gates it, the reconciler drives the deploy, and a canary check receives it. This lab makes every role runnable against Northstar's real orders-api. You will invoke Claude headless and read the JSON envelope a pipeline parses; run the deterministic release-gate analyzer the model's verdict is reconciled against, and watch it block the current candidate on executable evidence; enforce separation of duties by proving the proposer identity can write and the reviewer identity structurally cannot; confirm the approval boundary the change gate holds; and verify a canary into a promote or rollback decision.

By the end you will have a release pipeline where the agent analyzes and the pipeline gates — and no single identity can move a change from candidate to production alone. The Deep Dive then hands that same pipeline a plausible, stale runbook and watches a doc-anchored repair fail.

Where you are working

You start at the root of the agentic-ops-lab workspace. The release-gate analyzer (scripts/pipeline-analyze.sh), the canary checker (scripts/canary-verify.sh), and the role-authority regression (scripts/role-authority-check.sh) live under scripts/. The output contract for the hermetic verdict is contracts/release-verdict.schema.json; canary fixtures are under fixtures/canary/. The Helm chart under review is platform/helm/orders-api/ (it still carries the Module 12 defects, on purpose). The Module 8 change gate is scripts/hooks/change-gate.sh. Every graded step is a deterministic read of the repo — no live cluster is required. Step 1 makes one real headless call so you can read an actual envelope; the grade does not depend on it.

Step 0 — Prerequisites​

Confirm the tools this lab uses: claude (for the headless flags), helm (the analyzer renders the chart), and jq.

claude --version
helm version --short
jq --version
Expected output
2.1.197 (Claude Code)
v4.2.1+gd591a19
jq-1.7.1

Your versions will differ. Any Claude Code with -p, --output-format and --json-schema is fine (all three are checked in Step 1). helm ≥ 3.12 and any jq ≥ 1.6 work.

Step 1 — Confirm the headless surface a pipeline depends on​

Before building the pipeline, confirm Claude Code exposes the three flags that make it a CI stage: non-interactive print, JSON output, and a schema constraint. These are the mechanics from the lesson — a form request, not a conversation.

claude --help 2>/dev/null | grep -E '\-p, --print|output-format|json-schema'
Expected output
  --bare                                Minimal mode: skip hooks, LSP, plugin
  --json-schema <schema>                JSON Schema for structured output
  --output-format <format>              Output format (only works with --print):
  -p, --print                           Print response and exit (useful for

All three present. -p runs headless, --output-format json returns a parseable envelope, and --json-schema constrains the result to your contract. These are the flags every CI invocation of the agent is built from.

Note what is not here: --bare. It strips hooks, skills and CLAUDE.md discovery, which sounds like the right thing for a hermetic CI run and is exactly wrong for a gate — a run with no operating layer is a run with no enforcement behind it. --bare is a control condition for comparing against, not a way to run production checks.

Now run one for real and look at the envelope the pipeline reads. Constrain it to the release-verdict contract so the answer is an object your gate can branch on rather than prose it has to parse:

SCHEMA="$(jq -c 'del(.["$schema"])' contracts/release-verdict.schema.json)"
claude -p "Release verdict for orders-api v1.2.0: check the Helm values and the app routes." \
  --json-schema "$SCHEMA" \
  --output-format json \
  --model claude-haiku-4-5-20251001 \
  | jq '{subtype, is_error, num_turns, total_cost_usd, structured_output}'
Expected output
{
  "subtype": "success",
  "is_error": false,
  "num_turns": 17,
  "total_cost_usd": 0.1599491,
  "structured_output": {
    "verdict": "block",
    "blockers": [
      "Readiness probe path /health does not match any actual endpoint (app serves /healthz) — pods will fail health checks, hanging deployment",
      "maxUnavailable 100% violates SLA: causes full outage during rolling update with only 1 replica in values.yaml"
    ],
    "evidence": {
      "readiness_probe_path": "/health",
      "max_unavailable": "100%"
    }
  }
}

Point-in-time output — your blockers, turn count and cost will differ.

Read what it actually did. It took seventeen turns, went and read the Helm chart and the application routes, and came back with verdict: block naming two defects that are genuinely in this repository. Nobody told it what to look for.

The envelope is the reason this is CI-usable. A pipeline reads is_error to know whether to trust the run at all, num_turns and total_cost_usd to see what it cost, and structured_output for an object with a verdict field that is approve or block and nothing else. Free text could carry none of that.

The fail-closed rule follows directly: if is_error is true, or structured_output is absent, the stage treats the release as block. A gate that cannot read a verdict has not received an approval.

Two things that will bite you here

--json-schema takes the schema inline, not a path — and it rejects a schema carrying a $schema: "https://json-schema.org/draft/2020-12/schema" key with no schema with key or ref. That is why the command above pipes through jq -c 'del(.["$schema"])' rather than passing the file.

And pin --model. This call cost $0.16 on a small model; the default is several times that, on a stage that runs on every push.

Step 2 — Read the output contract the hermetic verdict must satisfy​

A headless verdict the pipeline can gate on is not just any JSON — it is your JSON, constrained to a schema. Read the release-verdict contract:

jq '{required, verdict_enum: .properties.verdict.enum, evidence_fields: (.properties.evidence.properties | keys)}' \
  contracts/release-verdict.schema.json
Expected output
{
  "required": [
    "verdict",
    "blockers",
    "evidence"
  ],
  "verdict_enum": [
    "approve",
    "block"
  ],
  "evidence_fields": [
    "app_routes",
    "max_unavailable",
    "readiness_probe_path"
  ]
}

The contract says a valid verdict is an object with exactly verdict (only approve or block), a blockers list, and an evidence object carrying the readiness probe path, the app's real routes, and the rollout max_unavailable. Passing this schema inline (via jq -c 'del(.["$schema"])', as in Step 1) forces the agent's answer into this shape — an off-contract answer fails validation instead of quietly misleading the gate. The evidence fields are deliberate: the verdict must show its work, so a reviewer can check the probe path against the routes the app actually serves.

Step 3 — Run the release-gate analysis and watch it BLOCK​

pipeline-analyze.sh is the deterministic reference for what the in-CI agent analysis produces — the same schema, the same fields, fully reproducible, so the pipeline is gradeable and a live hermetic verdict has something to be checked against. Run it over the current release candidate:

scripts/pipeline-analyze.sh --field json
Expected output
{
  "gates": {
    "readiness": {
      "ok": false,
      "probe_path": "/health",
      "app_routes": [
        "/healthz",
        "/readyz",
        "/api/v1/info"
      ]
    },
    "render": {
      "ok": true,
      "max_unavailable": "100%"
    },
    "terraform": {
      "verdict": "skipped"
    }
  },
  "blockers": [
    "readiness: probe path /health is not a route the app serves (/healthz, /readyz, /api/v1/info)",
    "rollout: maxUnavailable 100% leaves no serving floor"
  ],
  "verdict": "block"
}

The verdict is block, and the reasons are grounded in executable evidence, not opinion. The readiness gate rendered the probe path (/health) from the Helm values and checked it against the routes the app actually serves — read straight from the source — and /health is not among them. The render gate found maxUnavailable: 100%, a rollout with no serving floor. This is the inspector signing a report the pipeline can act on: two blockers, both traceable to a fact you can re-derive on any machine.

The analyzer's job is analysis only — it never mutates. Prove it carries no write command:

grep -Eq '(kubectl[[:space:]]+(apply|delete|scale|patch)|helm[[:space:]]+(upgrade|install)|terraform[[:space:]]+apply|docker[[:space:]]+push)' scripts/pipeline-analyze.sh \
  && echo "FOUND a write command (bad)" || echo "no write command — analysis only"
Expected output
no write command — analysis only

The analyzer reads, renders, and reports. It holds no path to a cluster, to infrastructure, or to a registry — least privilege for the agent's identity in CI, expressed as the absence of the capability rather than a promise not to use it.

Now feed it a Terraform plan too, and watch the chain fail-close on the strongest objection. The plan-stateful-replace.json fixture replaces a database — no clean rollback:

scripts/pipeline-analyze.sh --plan infra/fixtures/plan-stateful-replace.json --field blockers
Expected output
readiness: probe path /health is not a route the app serves (/healthz, /readyz, /api/v1/info)
rollout: maxUnavailable 100% leaves no serving floor
terraform: stateful replacement (no clean rollback)

Three blockers now — the Terraform gate reused plan-analyze.sh from Module 11 and added its objection. The join rule is fail-closed on the strongest: any single blocker makes the whole release block. A release ships only when every gate clears. One dissent stops the line, exactly like a review chain.

Step 4 — Enforce separation of duties by identity, not instruction​

The lesson's rule: the agent that proposes must not be the agent that approves. Northstar enforces this by giving the two roles different tool bundles. Prove it with the authority regression — it reads a role's declared tools and answers whether the role is structurally capable of a write.

The proposer (platform-engineer) can write desired state:

scripts/role-authority-check.sh platform-engineer write; echo "exit=$?"
Expected output
CAPABLE: role 'platform-engineer' carries write tool 'edit' — write is within its authority.
exit=0

The proposer holds an Edit tool, so it can author changes to Helm values and manifests. That is its job — propose. Exit 0 means the capability is present.

The reviewer (change-reviewer) cannot:

scripts/role-authority-check.sh change-reviewer write; echo "exit=$?"
Expected output
BLOCKED: role 'change-reviewer' has NO write tool in its bundle — it is structurally incapable of Edit/Write. Authority boundary holds.
exit=3

The reviewer has no write tool. It is not asked to refrain from editing the candidate — it cannot, because the capability is absent from its bundle. That structural absence is the separation of duties: the approver physically cannot become the author. Exit 3 is the "not capable" signal, and it is a fact you can test, not a behavior you hope for.

The security-reviewer is the same shape — read-only by construction, so its verdict is independent:

scripts/role-authority-check.sh security-reviewer write; echo "exit=$?"
Expected output
BLOCKED: role 'security-reviewer' has NO write tool in its bundle — it is structurally incapable of Edit/Write. Authority boundary holds.
exit=3

Every reviewer role in the chain is read-only. A fix a reviewer wrote would be a fix nobody reviewed, so the reviewers cannot write — the independence that makes the review worth anything is enforced by the tool bundle, not by the prompt.

Step 5 — Confirm the approval boundary the pipeline cannot cross​

Separation of duties handles who reviews; the change gate handles what the agent identity can never do in the pipeline. The two production-affecting actions a CI agent must never take directly are applying to production and pushing an image. Confirm both are denied.

A terraform apply that targets production is blocked:

echo '{"tool_name":"Bash","tool_input":{"command":"terraform apply -auto-approve -var env=production"}}' \
  | scripts/hooks/change-gate.sh; echo "exit=$?"
Expected output
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"terraform apply on production is blocked — production infrastructure changes must go through GitOps (branch -> PR -> approval -> reconciler apply), never a direct agent apply."}}
DENIED by change-gate: terraform apply on production is blocked — production infrastructure changes must go through GitOps (branch -> PR -> approval -> reconciler apply), never a direct agent apply.
exit=2

Exit 2 is the block signal. A production apply from an agent identity in CI has no safe form — production changes route through GitOps, approved and reconciled, never applied directly by the pipeline's agent.

A docker push is blocked — images are built and published by a separate, purpose-scoped CI step, not by the agent:

echo '{"tool_name":"Bash","tool_input":{"command":"docker push orders-api:1.4.0"}}' \
  | scripts/hooks/change-gate.sh >/dev/null 2>&1; echo "exit=$?"
Expected output
exit=2

Blocked. This is the least-privilege split from the lesson made concrete: the agent's identity holds no registry-write path. Publishing an image is a different step with a different, narrowly-scoped credential — the agent analyzes the build, it does not ship it.

Step 6 — Verify the canary and produce a promote/rollback decision​

The reconciler has deployed a canary; now the receiver reads its signals. canary-verify.sh applies fixed SLO thresholds (error rate ≤ 1%, p95 ≤ 300 ms, all replicas Ready) to a metrics snapshot. Start with a healthy canary:

scripts/canary-verify.sh fixtures/canary/canary-healthy.json --field json
Expected output
{
  "slo": {
    "max_error_rate": 0.01,
    "max_p95_ms": 300
  },
  "observed": {
    "error_rate": 0.004,
    "p95_latency_ms": 210,
    "ready_replicas": 2,
    "desired_replicas": 2
  },
  "reasons": [],
  "verdict": "promote"
}

Error rate 0.4% (under the 1% SLO), p95 210 ms (under 300), both canary replicas Ready. No reasons to hold, so the verdict is promote. The agent turned a pile of metrics into one decision the pipeline can act on — but note it only recommends; promoting is a gated action a human or the reconciler takes.

Now an unhealthy canary — an SLO breach and a replica that never became Ready:

scripts/canary-verify.sh fixtures/canary/canary-unhealthy.json --field json
Expected output
{
  "slo": {
    "max_error_rate": 0.01,
    "max_p95_ms": 300
  },
  "observed": {
    "error_rate": 0.037,
    "p95_latency_ms": 640,
    "ready_replicas": 1,
    "desired_replicas": 2
  },
  "reasons": [
    "error_rate 0.037 exceeds SLO 0.01",
    "p95_latency_ms 640 exceeds SLO 300",
    "only 1/2 canary replicas Ready"
  ],
  "verdict": "rollback"
}

Three reasons, any one of which is enough: error rate 3.7% (nearly 4× the SLO), p95 640 ms (more than double), and one of two replicas never came Ready. The verdict is rollback — the food taster showed trouble, so the meal does not reach the table. Catching this on a canary slice is cheap; catching it after promoting to all traffic is an incident.

Run the machine checks for M13:

scripts/grade.sh m13

  ✓ HEADLESS: claude exposes --output-format json — the pipeline gets a machine-parseable result to gate on, not free text
  ✓ HEADLESS: claude exposes --json-schema — structured output can be constrained to a release-verdict contract the pipeline validates
  ✓ HERMETIC: claude exposes --bare (skip hooks/LSP/plugins) — the analysis runs without project context for a reproducible, hermetic verdict
  ✓ SCHEMA: the release-verdict JSON schema exists — the output contract the hermetic analysis is bound to (verdict + blockers + evidence)
  ✓ PIPELINE: pipeline-analyze.sh exists and is executable — the deterministic reference for what the in-CI agent analysis produces

  ✓ GATE: pipeline-analyze BLOCKS the current release candidate — the chart's readiness probe (/health) is not a route the app serves, caught from executable evidence

  ✓ CANARY: canary-verify.sh exists and is executable — the post-deploy health verdict the agent reads before a promote decision
  ✓ CANARY: a healthy canary (error rate + p95 within SLO, all replicas Ready) yields verdict=promote

RESULT: PASS (16 passed)

Sixteen green. Every check maps to a claim in the lesson, and every one is a deterministic read of the repo — the headless flags, the schema, the analyzer's block verdict, the role tool bundles, the change gate, and the canary decisions all hold on the files alone, no live cluster and no authenticated Claude call required.

Teardown​

This lab created no cluster, no containers, and no Git state — every step read the repo or ran a deterministic analyzer. There is nothing to tear down. If you fed the analyzer a plan fixture and want to be sure the workspace is pristine:

git status --short scripts/ labs/m13/ contracts/ fixtures/canary/
Expected output

Empty output means the M13 assets are unmodified — the analyzer, the canary checker, the schema, and the fixtures are read-only inputs, and the lab left them exactly as it found them.

Reset to a known state

If anything is in a strange state, scripts/reset.sh m13 returns the workspace to the module's start state. The M13 lab is pure analysis, so a reset is rarely needed — but it is there.
