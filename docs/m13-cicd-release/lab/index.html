Lab — Agent-Assisted Release Pipeline

You are going to wire Claude into a release the way a platform team runs one: it reviews the change on the pull request, emits a typed release verdict that the pipeline branches on, and never holds deploy authority. The deterministic gate you build first is what that verdict is derived from.

Three invocation surfaces, one authority. By the end you will have a pipeline where the model's output is a schema-validated object rather than prose, where the run is reproducible on any runner, and where a job fails if your own skills or roles did not load.

Where you are working
cd ~/agentic-ops-lab

The analysers are scripts/pipeline-analyze.sh and scripts/canary-verify.sh. The release candidate is fixtures/release/candidate-values.yaml. No cluster is needed — everything is analysed offline.

Step 0 — The candidate, and what the repo already knows​

grep -nE 'path:|maxUnavailable' fixtures/release/candidate-values.yaml
scripts/pipeline-analyze.sh --values fixtures/release/candidate-values.yaml --field json | jq -c '{verdict, blockers}'
Expected output
17:#   2. rollingUpdate.maxUnavailable -> "100%"   (no serving floor during a deploy)
21:    path: /health
30:    maxUnavailable: "100%"
{"verdict":"block","blockers":["readiness: probe path /health is not a route the app serves (/healthz, /readyz, /api/v1/info)","rollout: maxUnavailable 100% leaves no serving floor"]}

Line 21 names a route the application does not serve; line 30 lets a rollout remove every serving pod at once. The analyser already reports both. What is missing is a pipeline that runs it on every change and a decision a job can act on.

This is feature work and it must not happen on the main branch. Use superpowers
to set up an isolated workspace for it first.

Tell me where you put it and how I get there.
git worktree list

Expected output
/Users/you/agentic-ops-lab                                     b2d1caa [main]
/Users/you/agentic-ops-lab/.worktrees/release-gate-ci-gate     b2d1caa [release-gate/ci-gate]

The directory name is the agent's choice. Read it off the command. One line means isolation did not happen — say so and let it finish.

Step 3 — The brief​

Write release/SPEC.md:

# Release Pipeline — Requirements

## Why
A candidate reached staging with a readiness probe pointing at a path the app does
not serve and a rollout that takes every pod down at once. Both were detectable
before it shipped. Nothing ran the check, and nothing turned the answer into a
decision the pipeline could act on.

## What we need
- One command CI runs that decides whether a named candidate may proceed.
- A machine-readable decision: a job must branch on it without parsing prose.
- When the decision cannot be made, the pipeline must not proceed.
- Claude may review and decide. It may not deploy.

## Constraints
- Follow the `gate-style` skill: the exit-code protocol and the verdict schema.
- Compose the analysers under scripts/. Do not re-implement their rules.
- No credentials in the gate. No deploy command in any workflow.

## Done means
- The gate's tests pass from one command, each watched failing first.
- The verdict is schema-validated, and a verdict missing a rollback is rejected.
- CI fails when a skill or role did not load.

Step 4 — Build the gate, test-first​

claude --agent release-engineer --dangerously-skip-permissions --model claude-sonnet-5
Read release/SPEC.md and build this.

Use superpowers to the maximum of its capabilities: brainstorm the design first and
present it for validation, then write a plan, then work test-driven - write the failing
tests first, watch them fail, then write the gate that makes them pass.

Read the gate-style skill before writing any gate code.

Do not tag, push or deploy anything.

What you observe. Seven tests, run before the gate exists:

FAIL: expected exit 0 (approve), got 127
FAIL: expected exit 2 (block), got 127
FAIL: expected exit 1 (cannot-evaluate), got 127
…
PASS 0 / FAIL 7

127 is command-not-found: it proves the tests execute and the gate is absent, not that the assertions can detect a wrong answer. You produce a behavioural failure yourself in Step 6.

Verify the result rather than reading the summary:

./release/tests/run.sh; echo "suite exit=$?"
Expected output
PASS: approves the fixed candidate (exit 0, candidate=release/tests/fixtures/good-candidate-values.yaml)
PASS: blocks the bad candidate (exit 2, 2 blockers, candidate=fixtures/release/candidate-values.yaml)
PASS: cannot-evaluate on nonexistent candidate file (exit 1, no stdout)
PASS: cannot-evaluate on missing --values (exit 1, no stdout)
…
PASS 7 / FAIL 0
suite exit=0

Three outcomes: 0 approve, 2 block, 1 cannot-evaluate. The third has the most tests, which is the right balance — it is the one nobody exercises by accident.

Step 5 — Check the verdicts by hand​

out=$(./release/ci-release-gate.sh --values fixtures/release/candidate-values.yaml 2>/dev/null); rc=$?
echo "rc=$rc"
echo "$out" | jq -c '{candidate, verdict, blockers: [.blockers[] | {detail, source}]}'
Expected output
rc=2
{"candidate":"fixtures/release/candidate-values.yaml","verdict":"block","blockers":[{"detail":"readiness: probe path /health is not a route the app serves (/healthz, /readyz, /api/v1/info)","source":"scripts/pipeline-analyze.sh"},{"detail":"rollout: maxUnavailable 100% leaves no serving floor","source":"scripts/pipeline-analyze.sh"}]}

Capture the output, then read $?. Run the gate through a pipe — ./gate … | jq '.verdict'; echo $? — and you read jq's exit code, so a blocking gate reports 0. That is the single most common way a gate is wrongly declared working.

Step 6 — Break the fail-closed path​

cp release/ci-release-gate.sh /tmp/gate-good.sh
sed -i '' 's|^fail_closed() { echo "ci-release-gate: FAIL-CLOSED: $1" >&2; exit 1; }|fail_closed() { echo "ci-release-gate: WARN: $1" >\&2; exit 0; }|' release/ci-release-gate.sh
./release/tests/run.sh | tail -7
cp /tmp/gate-good.sh release/ci-release-gate.sh
Expected output
FAIL: expected exit 1 (cannot-evaluate), got 0
--- cannot-evaluate-missing-canary-file.test.sh failed ---
FAIL: expected exit 1 (cannot-evaluate), got 0
--- cannot-evaluate-missing-file.test.sh failed ---
FAIL: expected exit 1 (cannot-evaluate), got 0
--- cannot-evaluate-missing-values.test.sh failed ---
PASS 4 / FAIL 3

On Linux use sed -i without ''. One line — a fail-closed downgraded to a warning — and the gate now approves every release it could not evaluate. Three tests catch it. Nobody merges a change titled "approve broken releases"; they merge one titled "don't fail the build on a missing file".

Step 7 — A typed verdict​

An exit code tells a job whether to stop. It does not tell a release note, a risk level or a rollback plan. Ask the harness for the contract:

Extend the release tooling so a pipeline can branch on a typed verdict.

1. release/verdict.schema.json - a JSON Schema for a release verdict: verdict
   (ship|hold|block), risk (low|medium|high), blast_radius, rollback,
   release_notes[], blockers[] with detail and source.

2. .claude/agents/release-decider.md - a role that decides ship/hold/block from the
   gate's exit code and JSON ONLY. It must not edit files, deploy, or tag. If the
   gate exits 1 the verdict is hold, never ship. Give it Skill in tools.

Add tests that assert the schema rejects a verdict missing rollback, rejects an
out-of-enum verdict value, and accepts the structure the gate produces. Watch them fail
first.
Expected output
PASS: schema accepts the block verdict the gate produces
PASS: schema rejects an out-of-enum verdict value (invalid: 'maybe' is not one of ['ship', 'hold', 'block'] (path: ['verdict']))
PASS: schema rejects a verdict missing rollback (invalid: 'rollback' is a required property (path: []))
PASS 10 / FAIL 0
jq -c '.required, .properties.verdict.enum' release/verdict.schema.json
grep -E '^(name|tools|disallowedTools):' .claude/agents/release-decider.md
["verdict","risk","blast_radius","rollback","release_notes","blockers"]
["ship","hold","block"]
name: release-decider
tools: ["Bash", "Skill"]
disallowedTools: ["Edit", "Write", "MultiEdit", "NotebookEdit"]

rollback is required, so a verdict that cannot say how to undo the release is rejected by the schema rather than by a reviewer's attention. The decider has Bash and Skill and no file tools at all — it runs the gate and reads its output; it cannot read around it for a second opinion.

Now produce a verdict with the schema enforced:

claude -p "You are deciding whether this release may ship. The candidate is
fixtures/release/candidate-values.yaml. Run: bash release/ci-release-gate.sh --values
fixtures/release/candidate-values.yaml (exit 0 approve, 2 block, 1 cannot-evaluate)
and base your verdict on its JSON. Do not edit anything." \
  --model claude-sonnet-5 \
  --allowedTools "Read,Bash(bash release/ci-release-gate.sh *)" \
  --strict-mcp-config --mcp-config /tmp/empty-mcp.json \
  --output-format json --json-schema "$(cat release/verdict.schema.json)" < /dev/null \
  | jq '{cost: .total_cost_usd, verdict: .structured_output.verdict, risk: .structured_output.risk, notes: .structured_output.release_notes}'

Create the empty MCP config first: echo '{"mcpServers":{}}' > /tmp/empty-mcp.json

Expected output
{
  "cost": 0.3749688,
  "verdict": "block",
  "risk": "high",
  "notes": [
    "BLOCKED by ci-release-gate.sh (exit 2)",
    "readiness: probe path /health not served by app — use /healthz, /readyz, or /api/v1/info",
    "rollout: maxUnavailable 100% leaves no serving floor during update"
  ]
}

--json-schema validates the model's output before you see it, and it arrives under .structured_output. A job branches on .structured_output.verdict — no prose parsing, no regex over an English sentence that changes wording between runs.

Note where the content came from: the gate decided block and the model turned that into a verdict with release notes. It did not re-judge the chart.

Step 8 — What a CI run actually loads​

A pipeline stage has to behave the same on every runner. Check what a plain -p run pulls in:

claude -p "reply OK" --model claude-haiku-4-5-20251001 --output-format stream-json --verbose < /dev/null 2>/dev/null \
  | jq -c 'select(.type=="system" and .subtype=="init") | {agents:(.agents|length), plugin_errors:((.plugin_errors//[])|length), mcp_errors:((.mcp_server_errors//[])|length)}'
Expected output
{"agents":51,"plugin_errors":2,"mcp_errors":0}

Your numbers will differ, and that is the point. This run declared nothing, and fifty-one agents were available to it — everything installed on the machine. On a CI runner that is whatever the image happens to carry, and it is not the same between two runners.

plugin_errors is non-empty on the machine this was captured from: two skill folders with invalid manifests that silently did not load. Nobody knew.

Turn that into a gate:

claude -p "reply OK" --model claude-haiku-4-5-20251001 --output-format stream-json --verbose < /dev/null 2>/dev/null > /tmp/init.jsonl
n=$(jq -r 'select(.subtype=="init") | ((.plugin_errors//[]) + (.mcp_server_errors//[])) | length' /tmp/init.jsonl)
echo "load errors: $n"
[ "$n" -eq 0 ] && echo "load-check PASS" || { echo "load-check FAIL — offenders:"; jq -r 'select(.subtype=="init") | (.plugin_errors//[])[] | "  \(.plugin): \(.message|split("\n")[0])"' /tmp/init.jsonl; }
Expected output
load errors: 2
load-check FAIL — offenders:
  gourav-voice@skills-dir: Failed to load skill folder as plugin: Plugin gourav-voice has an invalid manifest file at /Users/you/.claude/skills/gourav-voice/.claude-plugin/plugin.json.
  gourav-labs@skills-dir: Failed to load skill folder as plugin: Plugin gourav-labs has an invalid manifest file at /Users/you/.claude/skills/gourav-labs/.claude-plugin/plugin.json.

A run whose skill did not load still answers, confidently, with none of the procedure behind it. This check is how that becomes a red build instead of a quiet one.

Step 9 — Pin the run without an API key​

Step 8 showed a run inheriting fifty-one agents. The documented fix is --bare, which loads no hooks, plugins, MCP servers, auto-memory or CLAUDE.md. It has one property that decides this project's design:

--bare cannot use your subscription

Bare mode never reads OAuth credentials or the keychain, and it does not read CLAUDE_CODE_OAUTH_TOKEN either. A --bare run authenticates only with ANTHROPIC_API_KEY or an apiKeyHelper.

Captured while writing this lab, on a subscription login with no API key set:

$ claude --bare -p "reply OK" --allowedTools "Read" --output-format json
{"is_error":true,"num_turns":1,"total_cost_usd":0,…}
Not logged in · Please run /login

So this project does not use --bare anywhere. Nothing in this lab or its pipeline requires an Anthropic API key — every Claude invocation runs on your Pro or Max subscription.

What you pin instead, and it costs nothing:

echo '{"mcpServers":{}}' > /tmp/empty-mcp.json
cat > /tmp/agents.json <<'EOF'
{"release-decider":{"description":"Decides ship/hold/block from the gate's verdict only.",
 "prompt":"You decide ship/hold/block for a release candidate. You run the release gate and read its JSON. You never edit files, never deploy, never tag. If the gate cannot evaluate, the verdict is hold.",
 "tools":["Read","Bash"],"model":"sonnet"}}
EOF
claude -p "Decide the release for fixtures/release/candidate-values.yaml using the gate." \
  --agents "$(cat /tmp/agents.json)" --strict-mcp-config --mcp-config /tmp/empty-mcp.json \
  --allowedTools "Read,Bash(bash release/ci-release-gate.sh *)" \
  --output-format stream-json --verbose < /dev/null 2>/dev/null \
  | jq -r 'select(.subtype=="init") | "agents=\(.agents|length) has_decider=\((.agents|index("release-decider")) != null)"'
Expected output
agents=51 has_decider=true

--strict-mcp-config removes MCP servers; --agents pins the role definition to this file rather than whatever .claude/agents/ happens to contain. The agent count is still high, because hooks and plugins from the host are still loaded — that is the part only --bare removes, and the price of removing it is an API key.

This is the real trade-off, and it is worth stating plainly: full isolation costs you subscription auth. So you pin what you can for free, and you catch the rest with the load check from Step 8 — which is why that job exists.

For CI, the same token works: claude setup-token mints a long-lived OAuth token, and the workflow reads it from CLAUDE_CODE_OAUTH_TOKEN. Pro, Max, Team and Enterprise plans all support it.

Step 10 — The three workflows​

Now the CI wiring. Three workflows:

1. release-verdict.yml - on pull_request. Runs the gate, then a headless Claude stage
   that emits the typed verdict with an inline --agents release-decider and
   --json-schema, pinned with --strict-mcp-config. Authenticate with
   CLAUDE_CODE_OAUTH_TOKEN so the whole project runs on a subscription - do NOT use
   --bare, it cannot read that token. Parse .structured_output with jq, write verdict
   and risk to GITHUB_OUTPUT, and fail the job unless verdict is ship.

2. claude-pr-review.yml - anthropics/claude-code-action@v1 reviewing the diff against
   our release standard. Subscription auth via claude_code_oauth_token. Least
   privilege, bounded with claude_args.

3. agent-load-check.yml - fails the job if system/init reports a non-empty
   plugin_errors or mcp_server_errors.

Deploy stays a pipeline step: no workflow may give Claude a deploy command. Read
https://code.claude.com/docs/en/headless if you need exact flag names - do not guess.

Verify what was produced:

python3 - <<'PY'
import pathlib, yaml
for f in sorted(pathlib.Path('.github/workflows').glob('*.yml')):
    d = yaml.safe_load(f.read_text())
    for job, spec in d['jobs'].items():
        print(f"{f.name}  job={job}  perms={spec.get('permissions')}")
PY
grep -lE 'kubectl (apply|delete)|helm (upgrade|install)|docker push|git tag' .github/workflows/*.yml || echo "no deploy command in any workflow"
Expected output
agent-load-check.yml  job=load-check  perms={'contents': 'read'}
claude-pr-review.yml  job=review  perms={'contents': 'read', 'pull-requests': 'write'}
release-gate.yml  job=gate  perms={'contents': 'read'}
release-verdict.yml  job=decide  perms={'contents': 'read'}
no deploy command in any workflow

Four jobs, none with contents: write. The review job holds pull-requests: write because posting a comment is the one thing it does. The verdict job is read-only — it decides, and a later pipeline step deploys.

Read how the verdict job handles authentication, because it is the one place the rule differs:

grep -rn 'ANTHROPIC_API_KEY' .github/workflows/ || echo "no API key in any workflow"
grep -n 'CLAUDE_CODE_OAUTH_TOKEN' .github/workflows/*.yml | head -3
Expected output
no API key in any workflow
.github/workflows/agent-load-check.yml:38:          CLAUDE_CODE_OAUTH_TOKEN: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
.github/workflows/claude-pr-review.yml:42:          claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
.github/workflows/release-verdict.yml:92:          CLAUDE_CODE_OAUTH_TOKEN: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}

One secret, three jobs, and it is a subscription token rather than an API key. The Action takes it as the claude_code_oauth_token input; the two CLI jobs read it from the environment.

These workflows are authored and validated here, not executed

The YAML parses, the action inputs match the documented schema, and the permissions are minimal. Running them needs the Claude GitHub App installed on a repository and Actions minutes. To do it on your own fork: claude, then /install-github-app, then open a PR carrying the candidate values.

Step 11 — Commit​

git add release .github .claude/agents/release-decider.md
git commit -m "feat(release): gate, typed verdict schema, decider role, CI wiring"
git log --oneline -1 --stat | head -12

Which model for this lab, and why​

StepModelCost
Isolation and worktreeSonnet$0.28
Gate, test-firstSonnet$0.73
Schema + decider role, test-firstSonnet$0.74
CI wiring, docs fetchedSonnet$1.47
Typed verdict per pull requestSonnet$0.37
Load check per runHaiku~$0.01

Authoring is a handful of dollars, once. The two stages that run forever are the verdict and the load check. The verdict is worth Sonnet because it summarises a decision for humans; the load check is a Haiku call whose only job is to emit an init event you can read.

Limits​

  • The verdict is only as good as the gate. The model summarises the gate's output; it does not re-derive the rules. A gate that misses something produces a confident verdict that also misses it.
  • --json-schema validates structure, not truth. A schema-valid verdict can still be wrong about risk or rollback.
  • No GitHub Actions run was executed here. The workflows are authored and checked against the documented inputs.
  • --bare is not used anywhere in this project. It is the only way to drop host hooks and plugins, and it cannot read a subscription token — so the project trades that isolation for not requiring an API key, and covers the gap with the load check.
  • The load check catches load failures, not bad skills. A skill that loads and is wrong passes it.
  • Nothing here deployed anything. Deploy authority belongs to a pipeline step, and that step is out of scope for this module.

Exercise​

  1. Make the decider prove hold. Point it at a missing candidate file so the gate exits 1, and confirm the verdict is hold rather than block or ship.
  2. Add a required field. Put owner in the schema, re-run Step 7, and see whether the model fills it or the validation rejects the run.
  3. Fail the load check on purpose. Add a broken plugin manifest and confirm the Step 8 gate turns red, then fix it and watch it go green.

cd ~/agentic-ops-lab
