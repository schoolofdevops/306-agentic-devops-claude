Deep Dive — When an Agent Trusts a Stale Runbook Over Live Evidence

The core lab built a release chain where the agent analyzes over executable evidence and the pipeline gates. This Deep Dive is the failure that chain exists to survive, and it is the most modern way an agent gets a release wrong. Nobody hands you a broken agent. What you get is a confident, well-reasoned, thoroughly-cited repair — anchored on a document that is quietly out of date. The fix reads perfectly. It has a source. It even matches a runbook the platform team wrote. And it is wrong, because the document it trusts describes a system that no longer exists.

The point of this page is not "keep your docs up to date." You already know docs rot. The point is the discipline for the moment when a plausible written claim collides with live evidence — and specifically, why an agent is unusually easy to lead astray here, and what property of the pipeline makes it immune. By the end you will be able to name why the hermetic gate from the lesson catches what a helpful, context-rich agent misses, and you will have a rule you can apply on any incident: the document is a claim about the system; the code and the pipeline are the system.

Where you are working

You continue in the agentic-ops-lab workspace. This Deep Dive reasons over a runbook (runbooks/stale-runbook-wrong-endpoint.md, the doc the stale-docs fault injects), the app's real source (app/orders-api/src/health.py), and the Helm render — and grades against labs/m13/deep-dive.checks.json. Every check is a deterministic read of the doc, the source, and the render — no live cluster and no authenticated Claude call required — so the contradiction is reproducible on any machine.

The setup: a helpful agent, a plausible task, a stale map​

Analogy: think of an experienced contractor renovating a house, working from the blueprints on file at city hall. The blueprints are stamped, official, professionally drawn — every reason to trust them. But the house was remodeled two years ago and the blueprints were never updated: a wall that the drawing shows as load-bearing was moved, a door that the drawing shows on the north side is now on the east. A contractor who trusts the blueprint over the house in front of them will cut into the wrong wall with total confidence, and be completely wrong, and have a stamped document proving they did everything right. The blueprint is not lying — it was true once. It is stale, which is more dangerous than wrong, because stale looks exactly like correct until you check it against the building.

That is the situation. The readiness probe on orders-api is misconfigured (the same /health defect from Module 12). An operator asks the agent to fix it, and points it at the team's health-verification runbook for reference — a reasonable thing to do. The runbook is the blueprint on file. And it is stale.

Read the blueprint the agent is handed​

Look at what the runbook tells the agent. This is the document the stale-docs fault injects, and it is the map the agent will navigate by if you let it:

grep -nE 'api/v1/status|Last Updated' runbooks/stale-runbook-wrong-endpoint.md
Expected output
3:**Last Updated:** 2024-06-15
16:   curl -s http://localhost:8080/api/v1/status | jq .
26:   curl -s http://localhost:8080/api/v1/status/health | jq .
44:- The `/api/v1/status` endpoint was added in v0.8.0

Read it the way an agent would. The runbook says the service health endpoint is /api/v1/status, gives a concrete curl for it, and even carries a provenance note — "added in v0.8.0" — that makes it more believable, not less. It is dated (June 2024), owned by the Platform Team, and structured like every other runbook the agent has been trained to treat as authoritative. Nothing about it signals "stale." An agent asked to fix a readiness probe, holding this document as context, has a clear, well-sourced answer waiting: point the probe at /api/v1/status. That is the trap, and it is baited with credibility.

The plausible repair the agent proposes​

Here is what a project-aware agent, reasoning helpfully over that runbook, concludes: the readiness probe points at /health, which is wrong; the runbook says the health endpoint is /api/v1/status; therefore the fix is to point the readiness probe at /api/v1/status. Every step in that chain is locally reasonable. The proposed change renders cleanly:

helm template orders-api platform/helm/orders-api \
  --set readinessProbe.httpGet.path=/api/v1/status 2>/dev/null \
  | awk '/readinessProbe:/{f=1} f&&/path:/{print $2; exit}'
Expected output
/api/v1/status

The chart renders the doc-anchored path without complaint. This is what makes the failure so convincing: the repair is syntactically valid, it renders, it lints, and it is backed by a written runbook. If your review is "does it render and does it have a rationale," this passes. A reviewer skimming the PR sees a probe-path fix with a runbook citation and approves it. The rollout then fails exactly the same way it was failing before — the probe still asks for a path the app does not serve — except now it is worse, because everyone believes it was fixed.

The evidence the blueprint contradicts​

Now check the building against the blueprint. The app's source is the executable ground truth — it does not describe what routes exist, it is what routes exist. Read what orders-api actually serves:

grep -E '@router.get' app/orders-api/src/health.py
Expected output
@router.get("/healthz")
@router.get("/readyz")
@router.get("/api/v1/info")

Three routes: /healthz, /readyz, /api/v1/info. Look at what is not there. There is no /api/v1/status. There is no /api/v1/status/health. The endpoint the runbook describes — the one with the confident "added in v0.8.0" provenance note — does not exist in the running code. The blueprint shows a door that is not in the house. The agent's repair points the readiness probe at a route that returns a 404, which is precisely the class of failure the probe was already suffering. The doc-anchored fix does not repair the incident; it re-creates it with a different URL and a false sense of closure.

The contradiction is now explicit and testable — the proposed path is not among the routes the app serves:

ROUTES=$(grep -oE '@router.get\("(/[^"]*)"\)' app/orders-api/src/health.py | sed -E 's/.*"(.*)".*/\1/')
echo "$ROUTES" | grep -qx '/api/v1/status' && echo "doc path IS served (repair valid)" || echo "doc path is NOT served — repair contradicts the code"
Expected output
doc path is NOT served — repair contradicts the code

This is the whole incident in one line. The repair the agent proposed, backed by a stamped document, contradicts the executable evidence. Not "might be risky" — contradicts. The route is not there. Any process that weighs the document over the code reaches the wrong answer with full confidence; any process that weighs the code over the document catches it instantly.

Why the hermetic gate is immune and the helpful agent is not​

This is where the lesson's --bare distinction stops being an abstraction and becomes the thing that saves the release.

Analogy: the helpful, project-aware agent is the contractor who has read all the paperwork — the blueprints, the permits, the previous owner's notes. That context usually helps; it is why you want it doing the work. But it also means a stale document is in the mix, weighted as evidence, subtly steering the conclusion. The hermetic inspector is the building inspector who ignores the paperwork entirely and measures the actual walls. They are less informed and more correct, because their verdict is a function of the building, not the file.

The pipeline's release gate is that inspector. Run the deterministic analyzer against the doc-anchored repair and watch it refuse the change the runbook endorsed:

helm template orders-api platform/helm/orders-api \
  --set readinessProbe.httpGet.path=/api/v1/status 2>/dev/null \
  | awk '/readinessProbe:/{f=1} f&&/path:/{print $2; exit}' | grep -qx '/api/v1/status' \
  && ROUTES=$(grep -oE '@router.get\("(/[^"]*)"\)' app/orders-api/src/health.py | sed -E 's/.*"(.*)".*/\1/') \
  && ! echo "$ROUTES" | grep -qx '/api/v1/status' \
  && echo "GATE: readiness path /api/v1/status is not a route the app serves — BLOCK" \
  || echo "would pass"
Expected output
GATE: readiness path /api/v1/status is not a route the app serves — BLOCK

The gate never reads the runbook. It renders the probe path and checks it against the routes the app actually serves — executable evidence only — and blocks. The runbook's credibility, its provenance note, its official styling: none of it reaches the gate, because the gate is hermetic. It cannot be led astray by a document it does not load. This is why the lesson insisted the judging step run --bare: reproducibility and resistance-to-misleading-context are the same property. A gate that loaded project context — including that runbook — could be talked into blessing /api/v1/status. A gate that reasons only over the code and the render cannot.

The failure mode is confidence, not error

A crashing agent is easy — it announces itself. This failure is dangerous precisely because nothing announces it: the repair renders, lints, cites a source, and reads as competent work. The stale document does not degrade the agent's reasoning; the reasoning is sound given the premise. It corrupts the premise. The only defense is to make the premise checkable against something that cannot be stale — the running code and the live pipeline — and to weight those over any written claim.

The real fix, proven against the code​

The correct repair is the one the code supports, not the one the doc supports. The app serves /healthz; point the readiness probe there and prove it renders:

helm template orders-api platform/helm/orders-api \
  --set readinessProbe.httpGet.path=/healthz 2>/dev/null \
  | awk '/readinessProbe:/{f=1} f&&/path:/{print $2; exit}'
Expected output
/healthz

/healthz — a route the source confirms the app serves. This is the fix the evidence backs, and you proved it against the render and the code without ever trusting the runbook. From here it goes the golden way from Module 12: edit values.yaml on a branch, propose with gitops-propose.sh, independent review, human approval, merge, and the reconciler syncs /healthz into the cluster. The pipeline's hermetic gate would pass this change, because the probe path is now a route the app actually serves — the verdict and the evidence agree. And the stale runbook still needs fixing as a separate change, so the next person is not led into the same trap.

Grade the incident​

Run the Deep Dive checks. They certify the stale document, the executable ground truth it contradicts, the pipeline's authority over the doc, and the code-backed fix:

scripts/grade.sh m13-deep-dive
Expected output
Checking: Deep Dive — Stale Documentation: executable tests and live pipeline evidence override a plausible doc-anchored repair

  ✓ STALE DOC: the health-verification runbook instructs checking /api/v1/status — a plausible, authoritative-looking endpoint a repair could be built on
  ✓ STALE DOC: the runbook is dated 2024 and claims the endpoint was 'added in v0.8.0' — it reads as trustworthy, which is exactly why a doc-anchored repair is dangerous
  ✓ LIVE EVIDENCE: the orders-api source serves NO /api/v1/status route — the runbook's endpoint is fictional; the code is the ground truth
  ✓ LIVE EVIDENCE: the real health routes the app serves are /healthz and /readyz — an executable fact that overrides any documentation claim
  ✓ CONTRADICTION: the doc-anchored repair (point readiness at /api/v1/status) is NOT among the app's real routes — the repair contradicts the executable evidence
  ✓ PIPELINE IS AUTHORITATIVE: pipeline-analyze BLOCKS a chart whose readiness probe points at the doc's /api/v1/status — live evidence beats the runbook, and the gate enforces it
  ✓ THE FIX: the correct readiness path is /healthz — a route the app actually serves — proven by rendering the chart with the override, no cluster and no doc required

========================
RESULT: PASS (7 passed)

Seven green. The counts and wording may differ on your machine; a pass means you identified the stale claim, proved the code contradicts it, and confirmed the hermetic gate blocks the doc-anchored repair — evidence over documentation, enforced by the pipeline, not hoped for in a prompt.

Where you will use this​

This is not a runbook-hygiene lecture; it is the shape of how agents fail on real release work, and it recurs everywhere an agent reasons over written context.

  • When an agent cites a doc, a comment, or a wiki to justify a change. The citation is not evidence that the claim is current. The habit to build: before accepting a doc-anchored fix, check the claim against the code or the running system. "The runbook says" is a hypothesis, not a fact — and the more official the doc looks, the more worth checking it is.
  • When you design the review gate for an AI-assisted pipeline. Run the judging step hermetically (--bare), over executable evidence, so it cannot be steered by a stale local file the way a helpful context-rich agent can. The gate's power is that it reasons over less — the code and the render — not more.
  • On any incident where a written claim meets live signal. A dashboard, a metric, a curl, a test run — when one of those disagrees with a document, the document loses. The responder who trusts the runbook over the pager is the contractor cutting into the wrong wall. Live evidence is the wall.
  • Post-incident, separating the two bugs. The write-up that says "readiness probe was misconfigured" is half the story. The complete one says "the probe was wrong and the runbook that would guide the fix was stale, so the obvious repair was also wrong" — and files both fixes. Naming the stale doc as its own defect is what stops the next person from walking into the same trap.
