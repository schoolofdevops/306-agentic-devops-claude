CI/CD and Release

Module 12 built the golden path for a single change: an agent proposes desired state in Git, a human approves, and Argo CD reconciles the cluster. That path is correct, but it is manual: a person drives every step. This module automates the middle of it. The pipeline becomes the thing that runs the checks, invokes the agent for analysis, enforces the approval, deploys, and verifies the canary, while keeping the one property that made the golden path safe: the agent proposes and analyzes, it never deploys.

Here is the situation this module closes. Northstar's platform team merges dozens of changes a week (app code, Terraform, Helm values) and each one needs the same battery of checks before it reaches production: does it build, do the tests pass, is the Terraform plan safe, does the Helm chart render, and is there an independent judgment that the change is sound? Doing that by hand is slow and inconsistent; the reviewer who is tired on a Friday afternoon misses what the reviewer on Monday would catch. You want the pipeline to run the analysis every time, identically, with an agent doing the reading-and-judging that a human is good at but cannot do at 2 p.m. on the fifth review of the day. What you do not want is to hand that same pipeline a write path to production. The whole design of this module is: put the agent in CI for its judgment, and structurally deny it the ability to act on that judgment.

The pipeline is a bonded courier chain, and the agent is the inspector, never the driver​

Before any of the mechanics, hold the shape of the thing you are building.

Analogy: think of how a high-value shipment moves through a bonded courier chain: cash, say, or medical samples. No single person carries the package from origin to destination. An inspector opens it, checks it against a manifest, and signs a report: contents match, seal intact, nothing contraband. A supervisor, a different person, reads that report and either releases the shipment or holds it. A driver, a third person, moves it. And at the destination a receiver confirms it arrived intact before it is accepted into the vault. The reason the chain has four roles and not one is not bureaucracy. It is that the person who inspects must not be the person who decides, and neither may drive, so that no single point of failure or dishonesty can move the package unchecked. Each hands the next a signed artifact, and every hand-off is recorded.

Your release pipeline is that chain. The agent is the inspector: it opens the release candidate, reads the diff, the Terraform plan, the rendered Helm manifest, and signs a structured report: approve or block, with reasons. It does not decide and it does not drive. A separate control (a human, or an independent reviewer agent) is the supervisor who reads the report and gates. The reconciler (Argo CD, from Module 12) is the only driver. And the canary check is the receiver, confirming the shipment arrived healthy before it is fully accepted. Four roles, each producing a signed artifact the next consumes, no single identity able to move a release from candidate to production alone.

Everything else in this module is the mechanics of making each of those four roles real, runnable, and impossible for one identity to collapse into the others.

The CI environment is untrusted, so the agent gets least privilege​

Start with the threat, because it dictates every design choice after it. A CI runner is one of the most exposed places in your whole system, and the reasons are worth naming precisely: the same discipline you used on the container's packing list in Module 12, one layer out.

Analogy: a CI runner is a rental car, not your own garage. It is ephemeral, spun up for one job, destroyed after, so anything you leave in it is either gone or, worse, available to the next renter if the platform leaks state. It holds keys that are not really "yours": the shared secrets (registry credentials, cloud tokens, a kubeconfig) that let the job do its work, sitting in environment variables any step can read. And it runs code you did not fully write: every dependency the build pulls, every action in the workflow, is code executing with those keys in reach. You would not leave your house keys and bank card in a rental car's glovebox; the CI runner's secret store is exactly that glovebox.

That threat model has three consequences for an agent running in CI:

  • The runner is ephemeral and shared. Whatever the agent can do, it does with credentials that outlive the run and are shared across jobs. A compromised step (a poisoned dependency, a malicious PR that alters the workflow) inherits every permission the job holds. So the job should hold as little as possible.
  • Secrets are in blast radius. The agent's transcript, its logs, and its tool output all pass through the runner. A command that prints a decoded secret, or an agent that reads a credentials file "to check something," writes that secret into logs that may be retained and readable. This is why the Module 8 change gate blocks secret-printing commands, and it matters more in CI than on a laptop, because CI logs persist and fan out.
  • The dependency supply chain is an input. The agent reasons over code and configs that were themselves pulled from registries. Treat everything the pipeline ingests as untrusted input, including what the agent reads.

The design answer is least privilege, defaulting to read-only. The agent in CI gets exactly the permissions its analysis job needs: read the repo, run helm template, run read-only terraform and kubectl, invoke the deterministic analyzers, and nothing that writes. Write authority (push an image, apply Terraform, sync the cluster) belongs to specific, separately-credentialed steps, not to the agent's identity. This is the same split as Module 12's reconciler-only model, expressed as pipeline permissions: the analysis step and the deploy step are different identities with different scopes, and the agent lives in the analysis one.

OIDC: short-lived, scoped credentials instead of a stored key​

The concrete mechanism modern pipelines use to shrink the rental-car glovebox is OIDC federation. Instead of storing a long-lived cloud key as a CI secret (a key that, if it leaks, works until someone remembers to rotate it), the CI provider vouches for the specific job to the cloud, which mints a short-lived, narrowly-scoped credential on the spot.

Analogy: a stored long-lived key is a copied house key that opens the door forever, no matter who ends up holding the copy. OIDC is a hotel keycard: the front desk (the cloud's identity provider) issues it to this guest for this room for this stay, and it stops working at checkout. If someone finds it in the parking lot next week, it opens nothing. The credential is bound to the exact repository, branch, and job that requested it, and it expires in minutes.

For an agent in CI the payoff is direct: even if a step is compromised while the agent runs, the credential it could steal is scoped to one job and already expiring, not a master key to the estate. Least privilege over time (short-lived) and scope (this repo, this environment) is what makes it safe to run automation, agentic or not, in an untrusted runner.

Headless Claude Code: the agent as a pipeline stage​

An interactive Claude session is a conversation. A pipeline stage is not: it takes an input, produces an output, and exits with a status code the next stage reads. To put the agent in CI you run it headless: no REPL, no human turn-taking, one prompt in, one structured result out.

Analogy: interactive Claude is a colleague you chat with at their desk; headless Claude is the same colleague filling out a standardized form and dropping it in the tray. The pipeline does not want a conversation. It wants a filled form it can file, sort, and act on mechanically. The form has fields the machine reads: a verdict, a list of blockers, the evidence. Free-flowing prose is the wrong output for a stage that has to parse the result and decide whether to fail the build.

The mechanics, all real Claude Code flags:

  • claude -p "<prompt>" (--print) runs non-interactively: send the prompt, print the response, exit. This is the base of every CI invocation.
  • --output-format json returns a structured envelope instead of plain text: a JSON object with the result, the number of turns taken, token usage, cost, and an is_error flag. The pipeline parses that envelope with jq and gates on it. (stream-json is the same data delivered incrementally, for long runs you want to watch.)
  • --json-schema <file> constrains the result itself to a schema you define, so the agent's answer is not just JSON, it is your JSON: a release-verdict object with exactly the verdict, blockers, and evidence fields your pipeline expects. A malformed or off-contract answer fails validation instead of silently misleading the gate.
  • Turn and time limits. A pipeline stage cannot run forever. You bound the agent two ways: a wall-clock limit with the shell's own timeout around the call (the CI-native way: if the analysis has not produced a verdict in N seconds, the stage fails closed), and a turn limit via the Agent SDK's maxTurns option when you drive Claude programmatically rather than from the CLI. The --output-format json envelope reports num_turns so you can see how many the run actually used.
  • Exit handling. The stage's exit status is what CI branches on. A clean run exits 0; the pipeline then reads the verdict field and decides. The discipline is fail-closed: if the invocation errors, times out, or returns something that does not validate against the schema, the stage treats it as block, never approve. An analysis you could not trust is not a pass.

Hermetic --bare analysis vs project-aware execution​

There is a choice buried in that invocation that decides whether the verdict is reproducible or context-rich, and you have to make it deliberately: does the headless agent load the project's context (its CLAUDE.md, hooks, skills, plugins) or run stripped of all of it?

Analogy: think of an auditor examining a company's books. A hermetic audit is the auditor who walks in knowing nothing about the company, reads only the ledgers in front of them, and applies standard accounting rules: the same rules, the same way, regardless of which company it is. Its verdict is reproducible: two hermetic auditors on the same books reach the same conclusion, because neither is influenced by the company's internal culture or the last audit's assumptions. A project-aware audit is the auditor who has worked with this company for years. They know its quirks, its history, the context behind unusual entries. That richness helps them catch things a stranger would miss, but it also means their judgment is entangled with context that another auditor does not share, so it is harder to reproduce and easier to lead astray by a misleading internal document.

In Claude Code, --bare is the hermetic auditor:

  • claude -p --bare runs in minimal mode: it skips hooks, LSP, plugins, and the project's operating layer. The agent sees the prompt and the files you point it at, nothing else. No CLAUDE.md shaping its priorities, no skills nudging its approach, no hooks intercepting its tools.
  • The trade-off is reproducibility versus context. A --bare analysis is hermetic: given the same inputs it produces the same verdict, on any machine, uninfluenced by whatever local configuration a particular developer has. That is exactly what you want for a release gate: the verdict must not depend on whose laptop or which runner it ran on. A project-aware run (the default) loads the full context and can reason with more nuance, which is what you want for doing the work (writing the fix, navigating the repo), but is the wrong choice for a gate whose job is to be identical every time.

The rule to carry: hermetic for judging, project-aware for building. The pipeline's analysis gate runs --bare so its verdict is reproducible and cannot be quietly steered by a local file. The agent that implements a change runs project-aware, because it needs the context to do the work well. Mixing them up (a gate that loads project context) is how a release verdict becomes non-reproducible and, as the Deep Dive shows, how a misleading local document can lead the agent to bless a change the evidence says is broken.

Why the gate must be hermetic

The Deep Dive turns on exactly this. A project-aware agent handed a plausible-but-stale runbook will weight that document as context and can propose a "fix" that the doc endorses and the live pipeline evidence contradicts. A hermetic gate that reasons only over executable evidence (the app's real routes, the rendered manifest, the test results) cannot be led there. Reproducibility and resistance-to-misleading-context are the same property.

Separation of duties: the proposer is never the approver​

The bonded-courier chain had a rule underneath it: the inspector must not be the supervisor. In pipeline terms, the agent that proposes a change must not be the agent that approves it. This is not a style preference; it is the control that makes the review mean anything.

Analogy: it is the two-signature rule on a large cheque, or the reason the person who writes the expense report is not the person who approves it. If one identity both authors and blesses a change, there is no review. There is one actor wearing two hats, and the second hat is decorative. The independence is the control. The moment the reviewer can edit the thing under review, you no longer have a reviewer; you have a second author.

Northstar encodes this as distinct identities with distinct tool bundles, which you met as roles in Module 9:

  • The proposer (platform-engineer) can Edit desired state and run gitops-propose.sh, but it is Git-only: its own definition forbids applying to the cluster, deleting namespaces, or scaling prod. It proposes; it cannot deploy.
  • The reviewer (change-reviewer) has no Edit or Write tool at all: it is read-only by construction. It reads the diff, the git log, and the authority matrix and produces a verdict. It physically cannot modify the candidate, so its independence is structural, not promised.
  • The human approval gate sits after the reviewer for anything that touches production. The change contract says a standard deployment requires approval; a major one requires two approvers plus security and FinOps sign-off.

The key insight is that separation of duties here is enforced by the shape of the identities, not by instructions. Telling a single agent "propose, then review your own work objectively" is asking one actor to be its own check: the exact thing the two-signature rule exists to prevent. Giving the reviewer no write tool means it cannot become the author no matter what it decides. Enforcement over intent, the through-line of the whole course, applied to the release chain: the reviewer's read-only tool bundle is the enforcement; a prompt saying "please stay objective" would be mere intent.

Canary verification: confirm the shipment arrived healthy​

The reconciler deploys, and you are not done. A deploy that applied cleanly is not the same as a deploy that is healthy. The pods came up, but are they serving? Before you promote a release to all traffic, you run a canary: route a slice of traffic to the new version and watch it against your SLOs.

Analogy: a canary release is the food taster before the banquet is served. A small, sacrificial portion goes first, and you watch it: is the error rate acceptable, is latency within budget, are the new pods actually Ready? Only if the taster is fine does the meal go to the whole table. If the taster shows trouble, you do not serve it; you roll back. The taster's job is to fail cheaply and early, on a slice, instead of expensively and late, on everyone.

The agent's role at this stage is the receiver in the courier chain: it reads the canary's signals and produces a structured verdict, promote or rollback, with the reasons. It does not promote and it does not roll back itself; those are gated, human-or-reconciler actions. What it does is turn a pile of metrics into a decision the pipeline can act on:

  • Error rate within SLO? The fraction of failing requests over the canary window, checked against a threshold.
  • Latency within budget? p95 (or p99) latency against the SLO.
  • Replicas actually Ready? The new pods reporting Ready: the same readiness signal from Module 12, now as a release gate. A canary where one of two replicas never becomes Ready is not healthy even if the served requests look fine.

Any one breached → rollback. All within budget and all replicas Ready → promote. The verdict is fail-closed the same way the analysis gate is: incomplete or missing signals mean "do not promote," because a canary you could not fully verify is not a canary that passed.

What you will carry out of this module​

You will have built the four-role release chain and run it against Northstar's real orders-api: modelled the CI threat surface and the least-privilege, OIDC-scoped identity an agent gets in a runner; invoked Claude headless with -p, a JSON output format, a schema-constrained verdict, and fail-closed exit handling; run the analysis --bare so the release verdict is hermetic and reproducible; enforced separation of duties through distinct proposer and read-only reviewer identities plus a human approval gate; and verified a canary into a promote/rollback decision before any release is fully accepted.

The Deep Dive then breaks it in the most modern way an agent fails. Handed a plausible, authoritative-looking runbook that is quietly stale, Claude proposes a repair the document fully supports, and that the live pipeline evidence flatly contradicts. You will watch a confident, well-reasoned, doc-anchored fix point the readiness probe at an endpoint the application does not serve, and you will learn the discipline that catches it: executable tests and live evidence outrank documentation, always. The runbook is a claim about the system; the code and the pipeline are the system. When they disagree, the words lose.
