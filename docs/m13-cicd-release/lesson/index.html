CI/CD and Release

This module wires Claude into a release pipeline. It reviews the change on the pull request, it produces a release decision the pipeline can act on, and it never deploys anything.

The artifacts are a deterministic gate, a typed verdict derived from that gate, and three workflows that invoke Claude three different ways. What makes it a module rather than a demo is the last constraint: none of those workflows can ship.

The pipeline​

Four jobs. The gate decides, a headless run turns that decision into a typed object, and a pipeline step consumes it. The review job comments. The load check guards the other three.

The order of the middle two matters. The gate runs first and the model reads its output — the model is not asked to look at a chart and form an opinion about whether it is safe. That answer would vary between runs and could not be reproduced six weeks later. The rules live in a script; the model turns the script's answer into something a human can read and a job can branch on.

Exit codes​

A gate has three outcomes, not two:

ExitMeaning
0approve — examined the candidate, nothing blocking
2block — examined the candidate, found a blocker
1cannot evaluate — missing input, unreadable file, failed analyser

Most checks have two, because a shell gives you two for free. The third has to be designed in, and it is fail-closed: exit 1 must never be read as approval.

The distinction has an owner attached. Exit 2 sends a developer to the candidate; exit 1 sends an engineer to the gate. Collapse them and every failure looks like the candidate's fault, which is how a gate that has stopped examining anything goes unnoticed — it looks exactly like a strict one.

In the lab you cause that failure with a one-line edit: exit 1 becomes exit 0 and the message gains the word WARN. The pull request title is "don't fail the build on a missing file". Three tests catch it, because they assert on the exit code rather than on whether the command completed.

The verdict is typed​

An exit code tells a job whether to stop. It carries no risk level, no rollback plan, no release notes. So the decision is defined as a schema:

{
  "verdict": "ship | hold | block",
  "risk": "low | medium | high",
  "blast_radius": "…",
  "rollback": "…",
  "release_notes": ["…"],
  "blockers": [{"detail": "…", "source": "scripts/pipeline-analyze.sh"}]
}

Three properties of that contract do real work:

  • rollback is required. A release decision that cannot say how to undo itself is rejected by the schema, not by whether a reviewer noticed.
  • Every blocker carries a source. A blocked release tells you which analyser produced the finding, so somebody can go and read it.
  • verdict is an enum. --json-schema validates the model's output before your pipeline sees it, so a job reads a field instead of pattern-matching an English sentence that will be worded differently on the next run.

On the real candidate this returned verdict: block, risk: high and three release notes, for $0.375 in three turns. The model did not re-judge the chart — it read the gate's JSON and filled the contract.

Three invocation surfaces​

SurfaceCommandAuth
Interactiveclaude --agent release-engineersubscription login
Headless in CIclaude -p --agents … --json-schema … --strict-mcp-configCLAUDE_CODE_OAUTH_TOKEN
Pull requestanthropics/claude-code-action@v1claude_code_oauth_token

The Action detects its mode from one input: with a prompt it runs automatically on whatever event you choose; without one it waits for @claude in an issue or pull request comment.

The whole project runs on a subscription. claude setup-token mints a long-lived OAuth token; the Action takes it as claude_code_oauth_token, and the two CLI jobs read it from CLAUDE_CODE_OAUTH_TOKEN. No Anthropic API key is required anywhere.

That constraint is what rules out --bare. Bare mode is the only way to drop the host's hooks and plugins, but it reads neither OAuth credentials nor CLAUDE_CODE_OAUTH_TOKEN — a bare run authenticates only with an API key. Measured on a subscription login: claude --bare -p … returns Not logged in · Please run /login and exits 1.

Reproducible runs​

A pipeline stage has to behave the same on every runner. Three measurements from the lab explain why that takes effort:

  • A plain claude -p run reported 51 agents available to it — everything installed on the host machine. On a CI runner that is whatever the image happens to carry, and it differs between runners.
  • On the same run, plugin_errors was not empty: two skill folders with invalid manifests that silently did not load. Nobody knew until the event was read.
  • --bare, which fixes both by loading nothing implicitly, refused a subscription login — Not logged in, exit 1.

So the project pins what it can without a key: --strict-mcp-config with an empty MCP config removes MCP servers, and --agents pins the decider role to a definition in the workflow rather than to whatever .claude/agents/ contains. Hooks and plugins from the host still load — that is the part only --bare removes, and the price of removing it is an API key.

That is also where the fourth job comes from. Every run emits a system/init event carrying plugin_errors and mcp_server_errors; the load check reads it with jq and fails the build when either list is non-empty. The failure it catches is specific: a run whose skill did not load still answers, confidently, with none of the procedure behind it, and nothing in the output says so.

Deploy authority​

JobPermissionsWhat it may do
release-gate.ymlcontents: readfail the build on exit 2 or 1
release-verdict.ymlcontents: reademit the typed verdict
claude-pr-review.ymlcontents: read, pull-requests: writepost one comment
agent-load-check.ymlcontents: readfail the build on load errors

No job holds contents: write, and no workflow contains kubectl apply, helm upgrade, docker push or git tag. The deploy is a pipeline step that consumes the verdict — the model decides and explains; the pipeline ships.

That boundary is enforced three ways at once: the decider role's tool list has no file-write tool, the workflow's permissions: block cannot push, and the PreToolUse change gate denies the dangerous commands even under --dangerously-skip-permissions.

Cost​

StageModelCost
Gate, test-firstSonnet$0.73
Schema + decider role, test-firstSonnet$0.74

Authoring is a handful of dollars, once. The two stages that run forever are the verdict and the load check, and the load check is a Haiku call whose only job is to emit an event you can read.

What this does not cover​

  • The verdict is only as good as the gate. The model summarises; it does not re-derive the rules.
  • A schema-valid verdict can still be wrong about risk or rollback. --json-schema validates structure, not truth.
  • The load check catches load failures. A skill that loads and is wrong passes it — and it is doing double duty here, covering the host hooks and plugins that only --bare could have excluded.
  • Nothing here deploys. Deploy authority belongs to a pipeline step, and that step is out of scope.

In the lab​

  1. Read the candidate and the analyser that already reports both of its defects.
  2. Write the brief.
  3. Build the gate test-first, with three exit codes.
  4. Break the fail-closed path and watch the suite catch it.
  5. Add the verdict schema and the decider role.
  6. Emit a typed verdict from the gate's output.
  7. Measure what a CI run loads, and turn it into a load check.
  8. Wire three workflows, none of which can deploy.
