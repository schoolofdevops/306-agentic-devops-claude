CI/CD and Release

Last month a release candidate reached staging with a readiness probe pointing at a path the application does not serve, and a rollout that takes every pod down at once. Both defects were plain text in a file somebody reviewed. Nothing caught them, because catching them depended on a person remembering to look.

This module builds the thing that remembers — a release gate: one command CI runs that decides whether a candidate may proceed. You write the brief; the release-engineer role builds it test-first under the harness. Then you run that gate three different ways, and work out which of the three is allowed to decide anything.

A gate answers three questions, not two​

Most checks in a pipeline have two outcomes, because a shell gives you two for free: it worked, or it did not. A gate needs three.

ExitMeaning
0approve — it examined the candidate and found nothing blocking
2block — it examined the candidate and found at least one blocker
1cannot evaluate — it could not do its job: missing input, unreadable file, an analyser that failed

The third one is the whole module. A gate that cannot tell "I checked and it is fine" apart from "I could not check" will eventually approve a release it never examined, and there will be a green check mark next to it.

The distinction is not academic — it sends different people to different places. The gate blocked your candidate sends a developer to their values file. The gate could not evaluate sends somebody to the gate. Collapse the two and everybody goes to the wrong place, slowly.

In the lab you break this on purpose, with a one-line edit that looks like a kindness in a pull request: turning a fail-closed exit into a warning. Three tests catch it. Nobody merges a change titled "make the gate approve broken releases"; they merge one titled "don't fail the build on a missing file".

The shell is where gates quietly lie​

A gate is usually a script, and the ways a script silently turns a block into an approval are specific enough to write down. Northstar keeps them in a gate-style skill, because they all survive review by eye:

  • set -e with grep -q — grep exits 1 when it matches nothing, killing the script mid-check.
  • $? after a pipeline — that is the last command's status, not the gate's.
  • [[ -f "$f" ]] || echo "missing" — prints a message and carries on to approve.
  • An unset $CANDIDATE — analyses the default instead of the release and approves it.

The second one is worth dwelling on, because it is how a reviewer "confirms" a gate works: run it, pipe it to something readable, check the exit code.

./release/ci-release-gate.sh --values candidate.yaml | jq '.verdict'; echo "exit=$?"

That prints "block" and then exit=0. The author of this course typed exactly that while validating the lab, an hour after writing the rule against it. If you take one habit from this module, take this one: capture first, then check — out=$(cmd); rc=$?.

Compose analysers; do not re-implement them​

The repository already knows what is wrong with that candidate. pipeline-analyze.sh reports the probe path and the rollout floor; canary-verify.sh judges a canary snapshot. The gate's job is not to re-derive those rules — it is to call them, collect their verdicts, and be trusted about the result.

That matters for a reason beyond tidiness. The moment a gate contains its own copy of a rule, you have two places where "what blocks a release" is defined, and they drift. The gate becomes the thing that must be updated whenever a standard changes, which is how gates end up out of date and then switched off.

So a verdict is an aggregation, and it carries its sources:

{
  "gate": "ci-release-gate",
  "candidate": "fixtures/release/candidate-values.yaml",
  "verdict": "block",
  "blockers": [
    {"check": "pipeline-analyze",
     "detail": "readiness: probe path /health is not a route the app serves",
     "source": "scripts/pipeline-analyze.sh"}
  ]
}

Two fields there do work people skip. candidate is what tells you, six weeks later, that the gate judged the release rather than the default. And source on every blocker is what makes a finding actionable — "failed policy check" is a mood, not a finding.

Three ways to invoke Claude, and only one authority​

The interesting question in agentic CI/CD is not can an agent run in a pipeline. It is which invocation is allowed to decide anything. This module uses three, deliberately different:

One — interactive, on your machine. claude --agent release-engineer with the harness: brainstorm, plan, failing tests, then the gate. This is where judgment is spent, once, to produce something deterministic.

Two — headless, as a pipeline stage. claude -p --output-format json turning a verdict into a comment a developer can act on. Three flags make it a stage rather than a demo: --output-format json so the run is machine-readable and carries its own cost, --strict-mcp-config so it runs with nothing ambient, and < /dev/null so it does not sit waiting on stdin.

Three — the GitHub Action. anthropics/claude-code-action@v1 runs Claude Code inside a workflow. Two modes, and the difference is one input: with no prompt, it waits for @claude in an issue or pull request comment; with a prompt, it runs automatically on whatever event you choose. Authentication is either anthropic_api_key or claude_code_oauth_token — and the second one, generated with claude setup-token, means a Pro or Max subscription works without a separate API account.

The authority sits in exactly one of the three. The shell workflow can fail the merge. The Action's workflow carries continue-on-error and ends in exit 0, so it can never pass or fail anything — it runs after a decision, about a decision. That is the arrangement to carry to work: the deterministic thing decides; the model explains the decision to a human. Reverse them and your release criteria change from run to run.

Bounding an agent that runs in CI​

An agent in a pipeline has no human watching it, so its limits have to be structural:

  • --allowedTools "Read,Grep,Glob,Bash(gh pr comment:*)" — it can read the repository to explain a finding, and run exactly one kind of shell command. No Edit, no Write, no general Bash.
  • --max-turns 3 — a bounded run. An uncapped agent in CI is an unbounded bill and an unbounded runtime.
  • permissions: contents: read — even if something went wrong, the job's token cannot push.
  • if: steps.gate.outputs.rc == '2' — the model does not run at all unless a deterministic gate already blocked.

Note which of those is load-bearing. A turn cap on an agent that could write files would just be a smaller accident; the allow-list is the boundary, and the turn cap is a budget.

What a model in a pipeline is actually good at​

In the lab you run the headless stage and get back a clean, useful PR comment — for four cents, in twelve seconds, on the cheapest model, because a script had already done the deciding.

Then you read its second bullet, and it recommends maxUnavailable ≤ 75%. That is not the house standard: the rule is that a rollout always leaves a floor, which depends on the replica count too, and 75% of one replica is still zero pods serving. Run it again and the wording changes to something vaguer and still not the rule.

The gate cited scripts/pipeline-analyze.sh for its finding. The model cited nothing for its fix. Treat the explainer's output as a prompt to go and read the standard, never as the standard — and never let it be the thing that decides.

Cost, inverted​

The expensive model runs once, at authoring time, and produces a script. The cheap model runs every time, and cannot affect the outcome.

WhatModelCost
Isolation and the role auditSonnet$0.28
Design, plan, test-first buildSonnet$0.73
The CI wiring, with docs fetchedSonnet$0.73
Explain-the-block stage, per pull requestHaiku$0.04

A pipeline that puts an expensive model in the decision path pays repeatedly for a decision it cannot reproduce. One that puts a cheap model in the explanation path pays pennies for something no script writes well.

Where this goes next​

Claude Code has surfaces beyond the three here, and they are worth knowing by name so you can judge when they fit:

  • Cloud sessions — claude --cloud starts a session on Anthropic-managed infrastructure that keeps running after you close your laptop; --teleport pulls one back into your terminal. Useful for a long migration you want to check on from your phone.
  • Auto-fix pull requests — /autofix-pr has Claude watch a PR and respond to CI failures and review comments. Read the warning in the docs before enabling it on a repository where a PR comment can deploy infrastructure: Claude replies under your GitHub account, which can trigger comment-driven automation.
  • Routines — scheduled or event-triggered cloud runs. That is the subject of the automation module later in this course, not this one.

All three need the Claude GitHub App installed on a real repository, which is why this lab stops at authoring and validating the workflow rather than running it.

What you will do in the lab​

  1. Look at the candidate that shipped, and confirm the repository already knew what was wrong with it.
  2. Check the role can invoke skills at all, and read why this module needed a new role rather than a wider reading of an existing one.
  3. Write the brief — including the requirement everybody leaves out.
  4. Hand it to the harness and watch seven tests fail before the gate exists.
  5. Verify the three outcomes yourself, and fall into the $?-after-a-pipe trap on the way.
  6. Make a test fail on behaviour by downgrading the fail-closed path to a warning.
  7. Wire it three ways — shell step, headless stage, GitHub Action — and check which one can fail a merge.
  8. Price the stage that will run on every pull request for the rest of the repository's life.

The Deep Dive takes the other half: what a release gate cannot see, and how a canary verdict closes that gap after the merge.
