Deep Dive — The Operating Layer as a Product

The core lab treated the .claude/ operating layer as a thing you use: seven agents, a change gate, contracts, an observer MCP, all driving one incident. This deep dive treats it as a thing you ship and maintain — an internal product with a version number, an owner, a security cadence, a rollback story, and a deprecation policy. The shift matters because the moment more than one team depends on your operating layer, "it works on my repo" stops being good enough. A product has to survive being upgraded, being adopted by people who did not build it, and being wrong.

This page assumes you have run the capstone and packaged the starter. It goes past that: how you version the layer without breaking downstream teams, how you decide which changes need a security review, what happens when a new hook version breaks the workflow, how you retire a role no one should use anymore, and which metrics actually tell you the whole thing is worth running.

Why "product," not "config"​

Analogy: think about the difference between a script someone keeps in their home directory and a package on an internal registry. The home-directory script works — for its author, on their machine, until they leave. The package has a version, a changelog, an owner, and a deprecation path, so a hundred people can depend on it and upgrade on their own schedule without reading its source. Your operating layer is currently a home-directory script that happens to be shared. Turning it into a product is what lets it outlive the person who wrote it.

The concrete difference is a set of promises the layer makes to its consumers:

  • A version they can pin. A team on 1.4.0 is not forced onto 2.0.0 the day it ships.
  • A changelog they can read instead of diffing agent files to guess what changed.
  • A boundary between what is standard (ships in the starter) and what is theirs (their incidents, their fixtures, their answer keys).
  • A deprecation path so a role or hook they depend on is never removed from under them without warning.

The lab already asserted the first three. This page is about the machinery behind them.

Semver for an operating layer​

Semantic versioning is well understood for libraries: MAJOR breaks the API, MINOR adds compatibly, PATCH fixes. The subtlety for an operating layer is deciding what counts as a breaking change, because the "API" here is not function signatures — it is authority and decisions.

The rule the starter uses:

  • MAJOR — a change to any agent's authority (a reader gains write), a hook decision reversal (the gate now allows what it used to deny), or a contract schema break. These change what the layer permits, so a consumer must re-review before upgrading.
  • MINOR — a new role, a new skill, a new check, a new deny rule that only tightens. Additive; safe to adopt.
  • PATCH — a fix that does not change any decision (a typo in a message, a faster implementation of the same verdict).

The load-bearing insight: widening authority is always at least a MAJOR concern, even if the code change is one line. A one-character edit that gives the sre-investigator a write tool is a MAJOR version bump and a security review, because the blast radius of the layer just changed. Lines of code are the wrong unit; what the layer is now allowed to do is the right one.

The starter enforces that its changelog cannot silently drift from its version:

V=$(jq -r '.version' starter/.claude-plugin/plugin.json)
grep -c "\[$V\]" starter/CHANGELOG.md
Expected output
1

There is exactly one changelog entry for the shipped version. A starter whose plugin.json says 1.0.0 but whose changelog stops at 0.9.0 is one nobody can safely upgrade — they cannot tell what changed. This check is cheap to run in CI and closes that gap.

Ownership and the security-review cadence​

Not every change to the layer deserves the same scrutiny. Renaming a skill and widening the change gate's allow-list are not the same risk, and treating them the same either slows everything down or reviews nothing carefully.

Analogy: it is how a building treats changes. Repainting a wall needs no permit; moving a load-bearing wall needs an engineer's sign-off. The trick is knowing which walls are load-bearing. In the operating layer, the load-bearing walls are the pieces that can widen blast radius: the authority matrix and the hook decisions. Everything else is paint.

The cadence the MANIFEST commits to:

  • Owner: the platform team owns the starter as a product — one team accountable, not a free-for-all.
  • Always reviewed before merge: any edit to authority-matrix.yaml or a hook's deny logic. These are the load-bearing walls; a change here can hand an agent authority it should not have.
  • Reviewed on cadence, not per-change: skills and role prompts, monthly, because a prompt that quietly under-investigates is a slower-burning risk (M18's regression gate is the automated half of this).
  • No review needed: message text, docs, formatting.

The point is to spend review budget where blast radius lives. A team that reviews every typo as carefully as an authority change will, in practice, review neither carefully.

Rollback: what happens when a new version breaks the workflow​

A new hook version ships. It has a bug — it now denies a command the workflow depends on, and every incident run stalls at Phase 3. You need to get back to a known-good state fast, and "revert the commit and wait for CI" is too slow when incidents are queuing.

Analogy: this is a database migration with a down-migration, not a one-way door. You do not fix a bad migration by hand-editing production rows; you roll back to the previous schema, which you know works, and fix forward calmly. The operating layer needs the same: the previous version is always a known-good target.

Because the layer is versioned and its decisions live in files, rollback is a pin, not a scramble:

Two properties make this safe. First, the previous version is a complete known-good layer — the gate rules, the contracts, and the agent bundles all revert together, so you are never in a half-upgraded state. Second, the fix-forward carries a regression test for the exact over-deny, so 2.1.1 cannot reintroduce it. Rollback buys you calm; the test buys you not repeating the bug.

Deprecation: retiring a role or a hook​

Suppose the mlops-engineer role is being replaced by a more general platform-engineer capability, and you want it gone. Deleting it in one release breaks every team that referenced it. Leaving it forever means dead code that new users will find and misuse.

Analogy: it is how an API deprecates an endpoint. You do not delete /v1/orders the day /v2/orders ships. You mark v1 deprecated, point callers at v2, give them a window, and only then remove it — with the removal announced, not discovered. A role is retired the same way.

The starter's policy retires a piece over two MINOR releases:

  1. First MINOR: mark it deprecated in the CHANGELOG, name its replacement, keep it working.
  2. Following MINOR: remove it, recorded under a ### Removed heading.

Nothing is removed silently. The CHANGELOG check earlier and the deprecation-policy check below are the machine-readable half of that promise:

grep -qi 'deprecation policy' starter/CHANGELOG.md && echo present || echo missing
Expected output
present

The policy is stated in the changelog, not just in someone's memory. A starter that removes a role with no deprecation window is one whose consumers learn about breaking changes from their incidents failing — the worst possible place to find out.

The regression gates that guard every change​

The adoption ladder promotes an agent one rung at a time, but nothing about a new plugin version or a new model is safe just because the ladder placed the agent at stage 3 last month. Every plugin or model change re-opens the question: does this version still diagnose correctly, and does it still respect the authority boundaries? Two gates answer those, and they are the same ones the capstone used.

The quality gate re-scores a run and fails the build if it regressed:

scripts/regression-gate.sh fixtures/capstone/run-capstone.json >/dev/null 2>&1 && \
  ! scripts/regression-gate.sh fixtures/runs/generalist.json >/dev/null 2>&1 && \
  echo guarded || echo open
Expected output
guarded

The gate passes the good run (the capstone, exit 0) and fails the degraded one (the generalist, exit 2). Wired into CI on a plugin bump or a model swap, it turns the build red when the new version's diagnosis quality drops below the bar — before that version ever touches an incident. This is why a model change is not a config edit: it can regress diagnosis quality in a way that still compiles, and only an eval against a known-good rubric sees it.

The authority regression gate checks that no role silently gained power:

scripts/role-authority-check.sh sre-investigator write >/dev/null 2>&1; A=$?
scripts/role-authority-check.sh iac-engineer write >/dev/null 2>&1; B=$?
[ "$A" = "3" ] && [ "$B" = "0" ] && echo held || echo breached
Expected output
held

The read-only investigator is still refused write (exit 3) and the writer still allowed (exit 0), so the boundary held. If a plugin edit had quietly added a write tool to a reader's bundle, this flips to breached and fails the gate — catching an authority MAJOR change that a human diffing YAML might miss. Quality and authority are independent regressions, so they need independent gates.

Metrics that actually tell you it is working​

A dashboard full of green does not tell you whether the operating layer is helping. Three comparisons do:

  • Adoption rate per ladder stage. How many teams are at read-only pilot vs bounded closed loop, and are they moving up? A layer where everyone is stuck at stage 1 after six months is a layer nobody trusts — that is a signal about your gates or your agents, not your teams.
  • Incidents-with-agent-assist vs without. Compare resolution quality (eval-score composite) and time on incidents the governed team handled against those it did not. If the assisted incidents do not score higher, the layer is ceremony.
  • Eval-score trend over versions. Plot the composite the regression gate records across plugin versions. A flat-or-rising trend means upgrades are safe; a dip on a specific version is a regression the gate should have caught — and if it did not, your answer key has a gap.

Analogy: these are the layer's own vital signs, the way M18 gave the agent a harness-telemetry plane separate from the target-system plane. The target system's dashboards tell you the services are healthy. These metrics tell you the operating layer is healthy — a completely different question, and one no service dashboard can answer.

The honest failure mode to watch for: a layer that scores well on its own eval but that teams route around because it is too slow or too strict. Adoption rate is the check on that — a governance layer nobody uses governs nothing.

Where you will use this​

You reach for this the moment your .claude/ layer stops being yours alone:

  • A second team wants your agents. That is when you package the starter, cut a 1.0.0, and write the MANIFEST boundary — because "clone my repo and delete the parts you don't need" does not scale to ten teams.
  • You are about to bump a model or a plugin version. Run both regression gates in CI first. A model swap that quietly degrades diagnosis is exactly the failure the quality gate exists to catch, and an edit that widens a role's authority is exactly what the authority gate catches.
  • A new hook version breaks an incident run. Pin back to the last known-good version, restore flow, then fix forward with a regression test — do not hand-patch under pressure.
  • You want to retire a role. Deprecate it over two releases with the replacement named, never delete it in one — your consumers should read about the change in a changelog, not discover it when their workflow fails.

Check the packaging discipline end to end — semver, a matching changelog, the four-rung ladder with a rollback trigger on every stage, the deprecation policy, and both regression gates holding:

scripts/grade.sh m19-deep-dive
Expected output
========================
RESULT: PASS (11 passed)

Eleven green checks mean the operating layer is not just runnable but shippable: versioned, documented, bounded, and guarded. That is the difference between a workbench you built and a product a team can adopt.
