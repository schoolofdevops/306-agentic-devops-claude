Lab — Capstone Incident

Two halves, and the second one is the point.

Part I is the checkride: INC-006 is live, and you run it end to end through the five phase gates using the operating layer you have spent eighteen modules building. The difference from every previous run is that the evidence each gate consumes is produced by your agents, not read from a fixture.

Part II is the Nano Project. You build one agent that is yours, ship it in the starter, place it on the adoption ladder, and defend it. There is no walkthrough for that section.

Where you are working

Root of agentic-ops-lab, with core running. Part II's reference option also needs Postgres, which core already provides.

Step 0 — What the grader says now​

./scripts/grade.sh m19
Expected output
RESULT: FAIL (24 passed, 12 failed)

Twenty-four green before you have typed anything. Those check the estate: the orchestrator script, the incident ticket, the contracts, the shipped fixtures. They were true when you cloned the repo and they prove the platform is intact, not that you can operate it.

The twelve red are the capstone. Four are Part I's evidence; eight are an agent that does not exist yet.

Part I — the checkride​

Phase 1 — Triage, with four real investigators​

./scripts/capstone-triage.sh phase1
cat incidents/INC-006-campaign-capstone.md | head -30

The lock is real concurrency control and belongs to the script. The investigation does not — you dispatch it.

Open a session in acceptEdits — the investigators write packets, and the change gate and deny rules stay in force underneath:

claude --permission-mode acceptEdits

Dispatch four subagents, one per track, each writing to agentops/capstone/tracks/. Run them one at a time or in parallel, but give each one this structure:

Investigate ONLY the application-retry track of INC-006. Use the alert-correlate
skill from Module 14.

Do NOT read agentops/capstone/tracks/ — the other tracks are running in parallel and
reading their conclusions is how three investigations become one guess with three
signatures.

Write your hypothesis packet to agentops/capstone/tracks/application-retry.json,
conforming to contracts/hypothesis-packet.schema.json — read it first. root_cause
is an enum, not prose, and derived_from must be null.

Repeat for platform-resource, recent-change, and data-integrity.

What you observe. This is the phase most likely to go red on your first attempt, and that is the most valuable thing that can happen here. Two failure modes:

  • A track read a peer's file and emits a non-null derived_from. The synthesizer refuses at exit 4.
  • Three tracks name three different causes. No refusal, but no corroboration either — verdict comes back no-supported-hypothesis or need-more-evidence.
mkdir -p agentops/capstone
jq -s '.' agentops/capstone/tracks/*.json > agentops/capstone/hypotheses.json
./scripts/synthesize-hypotheses.sh agentops/capstone/hypotheses.json
What you are looking for
verdict=corroborated
root_cause=<the cause two independent tracks reached separately>
detail=2 independent dimension(s) converged on the same root cause from their OWN evidence — real corroboration, not an echo.

If you get INVALID: consensus theater, one of your agents read another's packet. Do not edit the derived_from field to make it pass — re-run that track with the constraint enforced. Editing the field is exactly the thing the check exists to catch.

Phases 2–5 — run the gates​

./scripts/capstone-triage.sh phase2
./scripts/capstone-triage.sh phase3
./scripts/capstone-triage.sh phase4
./scripts/capstone-triage.sh phase5

Phase 3 puts the dangerous plan through change-pipeline.sh and it blocks — that plan is a fixture and should be, because it is the estate's condition rather than your work. Phase 5 scores the run.

Why your score may be lower than the fixture's

eval-score.sh now reads a run record built from your tracks. A run where one track anchored on another scores lower on evidence coverage than the shipped fixture does.

That is correct. It was a worse run. A capstone that always returns the fixture's score is measuring the fixture.

Part II — Nano Project: ship one agent​

You have spent nineteen modules building an operating layer for someone else's repository. Build one piece of it that is yours.

Pick one agent below, or propose your own. Build it end to end and defend it. There is no walkthrough for this section.

Requirements — all six​

  1. It reads a real signal from this workspace. Not a fixture you wrote. Live Postgres, live Prometheus, real git history, real plan JSON, real Helm values.
  2. It ships as a skill plus a scoped role. .claude/skills/<name>/SKILL.md with a deterministic zone and a reasoning zone whose branches each end in a named finding, and .claude/agents/<name>.md whose tool bundle makes the dangerous action structurally impossible.
  3. The role is wired into contracts/authority-matrix.yaml, and scripts/role-authority-check.sh <name> write returns the answer you intended.
  4. Its output is validated by a script that already exists. Reuse contracts/evidence-packet.schema.json and scripts/evidence-validate.sh unless you have a reason not to — and if you do, write the reason down.
  5. It ships in the starter: a row in starter/MANIFEST.md, an entry in starter/adoption-ladder.yaml with its own trust gate and rollback trigger, and a matching starter/CHANGELOG.md entry.
  6. You broke it on purpose and it caught the thing you broke, by name, and you kept the output.

Declare which one you built so the grader can find it:

mkdir -p agentops/capstone
echo "pii-scan" > agentops/capstone/nano-project.txt   # your agent's slug

A is recommended because it is the only option that touches a live datastore you have been running since Module 1, it produces a finding nothing in this repo has pre-computed, and its break-it step is unambiguous.

Option A — what makes it hard, without giving you the answer​

Look at what is actually in the database before you design anything:

docker compose exec -T postgres psql -U orders -d orders -At -F'|' -c \
  "SELECT table_name, column_name, data_type FROM information_schema.columns
   WHERE table_schema='public' AND table_name NOT LIKE 'pg_%' ORDER BY 1,2;"
Expected output
orders|created_at|timestamp without time zone
orders|id|integer
orders|product_id|character varying
orders|quantity|integer
orders|status|character varying
orders|updated_at|timestamp without time zone

There is no PII in this database today. Your scanner's correct first answer is CLEAR, and a scanner that reports a finding here is worse than no scanner.

That is what makes the break-it step real: you will add the column the campaign migration would have added, and find out whether your agent notices.

Three design decisions the requirements do not make for you:

  • Name-based or pattern-based detection? A column called customer_email is easy. A column called notes that contains addresses is the one that matters at audit. What does your reasoning zone do about each, and what does it name them?
  • How do you sample without leaking? The scanner must look at values to judge format, and must never put a value in the report, the transcript, or a log. md5() on read is one answer. There are others. Whatever you choose goes in the NEVER DO list.
  • What is the scoped role actually preventing? Postgres access is not read-only by default. What in the bundle stops an UPDATE, and would it stop one issued through Bash?

The break-it step​

Add the column the campaign would have added, run your agent, and keep the output:

docker compose exec -T postgres psql -U orders -d orders -c \
  "ALTER TABLE orders ADD COLUMN customer_email varchar(255);"
docker compose exec -T postgres psql -U orders -d orders -c \
  "UPDATE orders SET customer_email = 'user' || id || '@example.com';"

Run your agent. It must name the finding — the table, the column, and why — not report "possible issue". Save what it said to agentops/capstone/break-it.md.

Then put the database back:

docker compose exec -T postgres psql -U orders -d orders -c \
  "ALTER TABLE orders DROP COLUMN customer_email;"
If your agent said CLEAR on the modified schema

That is a finding about your agent, and it is worth more than a pass. Record what it missed and why in break-it.md before you fix it. An agent that fails silently on the case it was built for is the exact failure this course has been about since Module 1.

Defend it​

Write agentops/capstone/defense.md with a ## heading per question and an honest answer:

## What signal does it read, and how do you know it is real?
## What is the dangerous action, and what structurally prevents it?
## What did you break, and what exactly did it say?
## What can it NOT do? Name the question it will be trusted for and cannot answer.
## Why rung 1 and not rung 2? What would have to be true to promote it?
## What would make you turn it off?

The fourth and sixth are the ones that matter. An agent whose author cannot name its blind spot will be trusted for it, and an agent with no defined off-switch condition is one nobody is willing to own.

./scripts/grade.sh m19
Expected output
RESULT: PASS (36 passed)

Teardown​

Nothing to remove. The starter now carries an agent you built, at a version you bumped, on a ladder rung you chose.

docker compose --profile core down

Summary​

You ran a live incident through five gates on evidence your own agents produced — including, most likely, watching the synthesizer refuse a round because one investigator read another's homework.

Then you built something that is yours: a real signal, a scoped role that cannot mutate what it inspects, output an existing validator accepts, a place in a versioned starter, a rung on the ladder, and a written defense including the question it cannot answer.

That last item is the course. Every module has been one form of the same argument — that an agent's usefulness is bounded by what you can prove about it, and that the proof has to exist before you need it. You now have an operating layer that makes those proofs cheap, and one agent in it that you can defend line by line to somebody who did not build it.
