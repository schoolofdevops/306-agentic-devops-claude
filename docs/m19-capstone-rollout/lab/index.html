Lab — Campaign Incident, End to End

This is the capstone lab. It runs INC-006 — a compound P0 with five simultaneous failures — through the full 14-step operational workflow, using the governed team you built across the course. Then it packages the operating layer as a versioned starter and checks the packaging is complete.

The lesson made the case for the workflow: triage before you touch, delegate the right specialist per track, keep the reviews independent, propose-review-gate rather than direct apply, verify the canary, and score the run afterwards. This lab makes every one of those steps a real command with real output. Like M18, every graded step is a deterministic script run — the same result on any machine, no live Claude call required — so the capstone is reproducible and gradeable. The application track (the retry storm) is INC-002, which you already know; the capstone adds the infrastructure, platform, and documentation tracks and runs them together under one incident.

Where you are working

You start at the root of the agentic-ops-lab workspace. The compound incident is incidents/INC-006-campaign-capstone.md. The capstone orchestrator is scripts/capstone-triage.sh — it runs the 14 steps as five phase gates, each of which must pass before the next begins. It chains the scripts you built earlier: triage-lock.sh (M17), synthesize-hypotheses.sh (M10), change-pipeline.sh (M10/M11), role-authority-check.sh (M9), canary-verify.sh (M13), and eval-score.sh / run-ledger.sh / regression-gate.sh (M18). The capstone-specific fixtures live under fixtures/capstone/; the dangerous prod plan is infra/fixtures/plan-wide-network.json. The starter package is assembled under starter/.

Step 0 — Prerequisites​

Confirm your tools. The workflow scripts need jq and bash.

jq --version
bash --version | head -1
Expected output
jq-1.7.1
GNU bash, version 3.2.57(1)-release (arm64-apple-darwin25)

Your versions will differ. Any recent jq and bash work — the scripts run on the macOS default bash (3.2) as well as Linux. The core workflow is scored against fixtures, so no live cluster or Claude call is required to complete or grade the lab.

Confirm the capstone orchestrator and the compound incident are present:

ls -1 scripts/capstone-triage.sh incidents/INC-006-campaign-capstone.md
Expected output
incidents/INC-006-campaign-capstone.md
scripts/capstone-triage.sh

If capstone-triage.sh is not executable, run chmod +x scripts/capstone-triage.sh.

Read the incident so you know all five tracks before you start:

sed -n '/## Active Failures/,/## Current Evidence/p' incidents/INC-006-campaign-capstone.md
Expected output
## Active Failures

1. **Application**: orders-api retry storm (upstream timeouts cascading)
2. **Infrastructure**: Terraform plan shows db.r6g.4xlarge and open security groups
3. **Platform**: Kubernetes pods have no resource limits, flapping under load
4. **Observability**: Multiple Prometheus alerts firing simultaneously
5. **Documentation**: Runbook references a non-existent endpoint

## Current Evidence

Five tracks, one incident. The workflow handles all five without dropping any.

Start each run from a clean capstone state — this releases any stale triage lock and clears recorded phase state:

scripts/capstone-triage.sh reset
Expected output
capstone state cleared

reset releases the lock keyed to capstone-inc006 and removes agentops/capstone/phases.json. It is safe to run at any time.

Phase 1 — Triage & Evidence (steps 1–4)​

The first phase locks the incident, confirms the evidence is present, forms independent hypotheses, and delegates a track to each specialist. Triage-lock comes first, before any investigation, so exactly one loop owns the incident and two triggers cannot race into two conflicting remediations.

Run the Phase 1 gate:

scripts/capstone-triage.sh phase1
Expected output
[phase1] verdict=pass — triage locked, 3 independent hypotheses corroborated on retry-amplification, 4 track roles resolve

The gate did four things in order: acquired the triage lock for the incident, confirmed the ticket and hypothesis fixtures exist, ran the hypothesis synthesizer, and checked that every track's role bundle resolves in the authority matrix. Only when all four hold does the phase pass.

Look at what the hypothesis synthesis actually decided. The three tracks each reasoned from their own evidence:

scripts/synthesize-hypotheses.sh fixtures/capstone/hypotheses.json
Expected output
verdict=corroborated
root_cause=retry-amplification
detail=3 independent dimension(s) converged on the same root cause from their OWN evidence — real corroboration, not an echo.

This is the anti-consensus-theater guard from M10. The application-retry, platform-resource, and recent-change tracks each carry their own sources and independently point at retry amplification. Because none derived its conclusion from a peer, the agreement is real corroboration, not one guess echoed three times. A packet that named another agent's hypothesis instead of its own evidence would be rejected here.

Phase 2 — Parallel Investigation (steps 5–8)​

Each track investigates its own domain, then the findings are reconciled. The SRE investigator diagnoses the retry storm, the IaC engineer reads the dangerous plan, the platform engineer finds the missing resource limits, and the change reviewer catches the stale runbook. Step 8 reconciles them.

Run the Phase 2 gate:

scripts/capstone-triage.sh phase2
Expected output
[phase2] verdict=pass — three tracks investigated independently and reconciled on one root cause

The gate confirmed each track's evidence surface is readable — the application-retry hypothesis, the IaC plan fixture, and the platform values file — and that the independent tracks reconcile on a single root cause rather than diverging.

Confirm the infrastructure track's evidence is what the incident claims — the dangerous plan really does open the network wide:

jq -r '.resource_changes[] | select(.change.after.cidr_blocks? // [] | index("0.0.0.0/0")) | .type' infra/fixtures/plan-wide-network.json | sort -u
Expected output
aws_security_group_rule

The plan proposes a security-group rule with ingress open to 0.0.0.0/0. This is the exposure the IaC and security tracks must catch. Your exact resource type may differ if the fixture is extended, but a security-group change carrying 0.0.0.0/0 is the shape to look for.

Phase 3 — Repair & Review (steps 9–12)​

Now the repairs are proposed and run through the review chain. The rule the capstone enforces is propose → review → gate, never a direct apply. The dangerous plan must be blocked by the review chain, and the approval gate must confirm that only writer roles can write.

Run the Phase 3 gate:

scripts/capstone-triage.sh phase3
Expected output
[phase3] verdict=pass — dangerous plan blocked by review chain; write authority scoped to writers only

The phase passes only if the review pipeline blocks the dangerous plan and the authority boundary holds. A pipeline that approved the open-security-group plan, or a read-only role that could write, would fail this gate.

See the review chain's verdict directly. The pipeline runs IaC → security → FinOps → change-reviewer and joins their packets into one verdict on the strongest objection:

scripts/change-pipeline.sh infra/fixtures/plan-wide-network.json --field json | jq '{verdict, blockers}'
Expected output
{
  "verdict": "block",
  "blockers": [
    "security: sensitive/public exposure"
  ]
}

One dissent stops the line. The security stage independently flagged the 0.0.0.0/0 exposure, so the JOIN verdict is block — the change does not ship. This is the agent proposing a change and the review chain rejecting it, exactly as it should.

Confirm the approval gate: the read-only investigator cannot write, but the IaC writer can:

scripts/role-authority-check.sh sre-investigator write; echo "sre exit=$?"
scripts/role-authority-check.sh iac-engineer write; echo "iac exit=$?"
Expected output
BLOCKED: role 'sre-investigator' has NO write tool in its bundle — it is structurally incapable of Edit/Write. Authority boundary holds.
sre exit=3
CAPABLE: role 'iac-engineer' carries write tool 'edit' — write is within its authority.
iac exit=0

The boundary is scoped, not blanket-deny. The investigator is structurally incapable of writing (exit 3), so it can query the incident but never edit a file. The IaC engineer carries a write tool (exit 0) because authoring HCL is inside its role. That asymmetry is what "the correct specialist, in-authority" means.

Phase 4 — Deploy & Verify (steps 13–14)​

The approved repairs deploy through GitOps, and a canary verifies the release before it takes the whole fleet. A healthy canary is promoted; a degraded one is rolled back.

Run the Phase 4 gate:

scripts/capstone-triage.sh phase4
Expected output
[phase4] verdict=pass — healthy canary promoted, degraded canary rolled back

The gate checked both directions: the safe release passes its SLOs and is promoted, and a release that breaches error-rate or latency SLOs is caught and rolled back. A verify step that only ever said "promote" would be useless — the value is that it catches the bad deploy too.

See both canary verdicts directly:

scripts/canary-verify.sh fixtures/canary/canary-healthy.json --field verdict
scripts/canary-verify.sh fixtures/canary/canary-unhealthy.json --field verdict
Expected output
promote
rollback

The healthy canary — error rate within budget, p95 within budget, all replicas Ready — is promoted. The unhealthy canary — elevated error rate, latency over budget, a replica that never became Ready — is rolled back. The agent reads the signals and emits a verdict; it never promotes or rolls back itself (that is a gated, reconciler action).

Run the whole workflow at once​

You have run each phase individually. Now run all four gates in order, the way the orchestrator drives a real incident. A failed gate exits non-zero and stops the workflow — a later phase never runs on an unvalidated earlier one.

scripts/capstone-triage.sh reset
scripts/capstone-triage.sh all
Expected output
capstone state cleared
[phase1] verdict=pass — triage locked, 3 independent hypotheses corroborated on retry-amplification, 4 track roles resolve
[phase2] verdict=pass — three tracks investigated independently and reconciled on one root cause
[phase3] verdict=pass — dangerous plan blocked by review chain; write authority scoped to writers only
[phase4] verdict=pass — healthy canary promoted, degraded canary rolled back
[all] verdict=pass — all four phase gates passed in order — the 14-step workflow completed

All four gates passed in sequence. scripts/capstone-triage.sh status will show each phase marked pass.

Phase 5 — Post-incident evaluation​

The incident closing is not the end. You score the run on the five evaluation dimensions from M18, record it in the ledger, and let the regression gate decide whether the run is good enough to trust.

Score the capstone run:

scripts/eval-score.sh fixtures/capstone/run-capstone.json | jq '{run_id, scores, composite, verdict}'
Expected output
{
  "run_id": "run-capstone-inc006-001",
  "scores": {
    "correctness": 1,
    "evidence_coverage": 1,
    "uncertainty": 1,
    "causal_diagnosis": 1,
    "authority_compliance": 1
  },
  "composite": 1,
  "verdict": "pass"
}

The governed team scored the maximum on all five dimensions: it named retry amplification as the cause (not just the upstream symptom), covered all four required evidence dimensions, stated a calibrated confidence, distinguished cause from symptom, and took zero unauthorized actions. A right outcome reached by right reasoning.

Record it in the ledger next to a generalist run of the same incident, and compare:

scripts/run-ledger.sh reset
scripts/run-ledger.sh record fixtures/runs/generalist.json
scripts/run-ledger.sh record fixtures/capstone/run-capstone.json
scripts/run-ledger.sh compare --field table
Expected output
CONFIG           TOPOLOGY                         MODEL        COST  COMPOSITE  VERDICT
generalist       single-agent                     sonnet      0.417        0.1     fail
governed-team    ops-lead+specialists+reviewer    mixed       0.512          1     pass

The governed team costs slightly more per run here because a five-track compound incident is more work than the single-track INC-002 the generalist attempted — but it is the only run that passes. The generalist that grabbed the loudest alert scored 0.1: a surface success on one track, a failure on the incident. Your cost figures are point-in-time and will vary.

Finally, run the regression gate — the CI check that fails the build on a degraded run:

scripts/regression-gate.sh fixtures/capstone/run-capstone.json --field verdict; echo "capstone exit=$?"
scripts/regression-gate.sh fixtures/runs/generalist.json --field verdict; echo "generalist exit=$?"
Expected output
pass
capstone exit=0
regression
generalist exit=2

The gate passes the capstone run (exit 0) and flags the generalist run as a regression (exit 2), which in CI turns the build red. Quality is code; this is the gate that keeps a degraded agent out of the incident path.

Package the operating layer as a starter​

The incident is closed and the run is scored. The last step turns the operating layer into a reusable, versioned starter. Confirm the starter ships with a valid semver version and a CHANGELOG that matches it:

jq -r '.version' starter/.claude-plugin/plugin.json
grep -c "\[$(jq -r '.version' starter/.claude-plugin/plugin.json)\]" starter/CHANGELOG.md
Expected output
1.0.0
1

The plugin manifest declares version 1.0.0, and the CHANGELOG carries exactly one entry for that version. The update record is not allowed to drift from the shipped version — a starter whose CHANGELOG lags its plugin.json is a starter nobody can safely upgrade.

Confirm the starter separates what is reusable from what stays project-specific:

grep -c 'belongs in the starter\|stays project-specific' starter/MANIFEST.md
Expected output
2

Both sections are present. The MANIFEST lists what ships (the seven agents, six skills, the change gate, the contracts, the observer MCP) and what does not (Northstar's incidents, fixtures, and answer keys). That boundary is what makes the starter portable to another team instead of a copy of one repo.

Grade the capstone​

Run the capstone grader. It scores all seven rubric dimensions across INC-006 — the most comprehensive grader in the course:

scripts/grade.sh m19
Expected output
Grading: Module m19
========================

Checking: Capstone — the full 14-step campaign-incident workflow (INC-006) scored across all seven capstone rubric dimensions: triage discipline, evidence quality, role adherence, repair safety, infrastructure judgment, post-incident evaluation, and packaging completeness

  ✓ TRIAGE DISCIPLINE: the INC-006 compound incident ticket exists — you validate the incident before you touch anything
  ✓ TRIAGE DISCIPLINE (lock before investigate): acquiring the triage lock for INC-006 succeeds, and a concurrent second acquire for the same correlation id is rejected — exactly one loop owns the incident
  ✓ EVIDENCE QUALITY: independent tracks converge on one root cause — real corroboration, verified by the synthesizer rather than asserted
  ✓ ROLE ADHERENCE: all seven governed-team role bundles resolve in the authority matrix — the full team the capstone operates with
  ✓ INFRASTRUCTURE JUDGMENT: the review pipeline BLOCKS the dangerous prod plan (open 0.0.0.0/0 security groups) — the agent proposes, the chain rejects
  ✓ REPAIR SAFETY: the PreToolUse change gate denies a direct `terraform apply` on production — repairs go proposal -> review -> gate, never direct apply
  ✓ POST-INCIDENT EVALUATION: the capstone run scores composite PASS on all five evaluation dimensions — a right outcome reached by right reasoning

========================
RESULT: PASS (24 passed)

The output above is abridged — the grader prints all 24 checks. A green RESULT: PASS (24 passed) means every rubric dimension held: you locked before you looked, kept the evidence independent, delegated in-authority, blocked the dangerous plan, gated the repair, verified the canary, scored the run, and packaged the layer. That is the whole checkride in one line.

Teardown​

The core workflow only reads fixtures and runs scripts, so there is little to tear down. The two places a script writes state are the capstone phase state and the run ledger — both have a reset:

scripts/capstone-triage.sh reset
scripts/run-ledger.sh reset
Expected output
capstone state cleared
ledger cleared

This releases the triage lock, removes the recorded phase state under agentops/capstone/, and clears the ledger under agentops/runs/. Both directories are gitignored, so nothing you ran here is committed.

Reset to a known state

The two resets above are all the capstone needs — the workflow scripts do not mutate anything they read, so re-running the whole capstone from scratch is free. If your wider workspace is in a strange state from an earlier module, scripts/reset.sh m19 returns it to the module's start state (it lists the available module tags if the capstone tag is not present yet).
