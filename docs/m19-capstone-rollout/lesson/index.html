Capstone: Campaign Incident, Packaging & Rollout

Every module before this one taught one instrument in isolation. You learned to earn a first diagnosis, to build evidence packets, to set permission boundaries, to write hooks and gates, to give a subagent a scoped role, to fan an investigation across parallel tracks, to reject a dangerous Terraform plan, to reconcile a Kubernetes deploy through GitOps, to run a change through CI, to triage an incident from telemetry, to draw an action boundary, to run an always-on loop, and to score an agent run against a rubric. Each of those was a single procedure practised on a single, clean problem.

This module is the checkride. One incident, five simultaneous failures, and the same governed team you built across the course — operated end to end, under time pressure, with a business campaign launching in two hours.

The analogy: the final checkride​

Analogy: think about how a pilot earns a type rating. Along the way they practised every manoeuvre on its own — stalls, engine-out drills, crosswind landings, instrument approaches — each in a calm session with an instructor talking them through it. The type rating is not another one of those sessions. It is a single flight where the examiner loads several things at once: an engine fails on climb-out while the weather closes in and a warning light comes on. The examiner is not looking for a perfect flight. They are looking for one thing: can the crew reach for the right procedure for each failure without freezing, and run them in the right order, without letting one emergency make them forget another.

The capstone is exactly that. INC-006 is a compound P0 — five failures firing together — and the skill being tested is not any single fix. It is whether you can triage before you touch, delegate the right specialist to each track, keep the reviews independent, and never let the pressure of a launch push you into a direct apply. The procedures are all ones you already know. The exam is running them together, correctly, when it matters.

INC-006: five failures at once​

Here is the incident you will operate. During a campaign launch load test, the following fire simultaneously:

TrackFailureThe module that taught the fix
Applicationorders-api retry storm — aggressive retries amplify a brief upstream blip into a self-sustaining stormM14 (SRE / observability)
Infrastructurea prod Terraform plan proposes db.r6g.4xlarge and opens 0.0.0.0/0 security groupsM11 (IaC / FinOps)
PlatformKubernetes pods have no resource requests, so the HPA cannot scale and pods flap under loadM12 (K8s / GitOps)
Observabilitymultiple Prometheus alerts fire at once — HighErrorRate, LatencyBreach, UpstreamTimeoutSpikeM14 (alert triage)
Documentationthe on-call runbook step 3 curls /api/v1/status, an endpoint that does not existM13 (change review)

The failure mode a novice falls into here is to grab the loudest alert and start fixing. The retry storm is the loudest, so they restart orders-api, the metric recovers, and they close the ticket — leaving the dangerous plan un-reviewed, the missing limits in place, and the stale runbook to mislead the next on-call. A right outcome on one track is not success when four other tracks were never touched. The discipline the capstone tests is handling all five without dropping any.

The 14-step operational workflow​

The whole point of a workflow is that it does not depend on which failure is loudest. You run the same fourteen steps in the same order every time, and the order is what keeps you from skipping a track or applying a repair before it was reviewed.

Analogy: it is the difference between a checklist and improvisation. A surgeon does not decide mid-operation whether to count the instruments — the count is a fixed step that runs every time, precisely so a busy, high-pressure moment cannot make it optional. The fourteen steps are that checklist for an incident.

The steps group into five phases, each ending in a gate that must pass before the next phase begins:

Read the sequence for what each step guarantees the next one:

  • Triage-lock first (step 1). Before anyone investigates, one loop claims the incident. This is not bureaucracy — it stops two triggers for the same incident (a routine and a webhook both waking on INC-006) from racing to open two conflicting remediations. The lock is keyed by the incident's correlation id; exactly one holder wins, every concurrent contender is rejected. You lock before you look, because an investigation that forks into two uncoordinated repairs is worse than a slow one.
  • Evidence before hypothesis (steps 2–3). You collect structured, multi-source evidence, then form hypotheses from it — not the other way round. Each track's hypothesis carries its own sources.
  • Delegate to the right specialist (step 4). The retry storm goes to the sre-investigator, the plan to the iac-engineer, the limits to the platform-engineer, the runbook to the change-reviewer. Each is a scoped role with its own authority bundle.
  • Reconcile, don't average (step 8). The parallel tracks reasoned independently. If they converge on one root cause from their own evidence, that is real corroboration. If they diverge, the reconcile step surfaces the disagreement instead of hiding it. Independence is the whole value of fanning out — three agents that anchored on each other's answer are one guess echoed three times.
  • Propose, review, gate — never direct apply (steps 9–12). A repair is proposed as a change, run through the review chain (IaC → security → FinOps → change-reviewer), and only ships if every stage clears it. One dissent stops the line. The approval gate confirms that only writer roles can write.
  • Deploy through GitOps, then verify the canary (steps 13–14). The change reconciles; a canary takes a slice of traffic; you promote only a healthy canary and roll back an unhealthy one.
  • Score the run afterwards (phase 5). The incident closing is not the end. You score the run on five dimensions, record it in the ledger, and let the regression gate decide whether this run is good enough to trust the workflow that produced it.
Why the order is the point

The steps are not independent tasks you can do in any sequence. Each gate is a precondition for the next phase: you cannot reconcile hypotheses you never formed, cannot review a repair that was never proposed, cannot verify a canary for a deploy that skipped the gate. Running them out of order is how a compound incident turns into a compound mistake.

Packaging the operating layer as a starter​

Once the incident is closed, you have something worth keeping: a governed operating layer that just handled a five-track P0 correctly. The mistake is to leave it as loose files in one repo. The next team — or the next project — has to rebuild it from scratch.

Analogy: think of the difference between a house someone wired by hand and an electrical code. The hand-wired house works, but nobody can safely extend it without reverse-engineering every choice. A code is the same knowledge, packaged: versioned, documented, with a clear boundary between what is standard and what is site-specific. Packaging the operating layer turns your hand-wired workbench into something a new team can install and extend safely.

A reusable starter ships as a versioned plugin. What goes in:

  • Role agents — the seven authority-scoped specialists. These are reusable because they encode authority boundaries, not Northstar's business logic.
  • Skills — the runbook procedures (incident-triage, k8s-diagnose, release-check), parameterised by service rather than hard-coded.
  • Hooks — the change gate that denies production apply, protected-namespace deletes, and wildcard blast radius.
  • Contracts — the authority matrix, environment contract, and change contract: the governance schema.
  • The observer MCP — the read-only telemetry lens.
  • Versioning — a plugin.json with a semver version, a CHANGELOG.md that carries an entry for that version, and a deprecation policy so a role or hook is retired over releases, never removed silently.

What stays out of the starter is just as important: the incident tickets, fault fixtures, and answer keys are Northstar-specific. The line between "reusable governance" and "one project's data" is what makes the starter portable instead of a copy of one repo. The deep dive treats this packaging as a product with an owner, a security-review cadence, and a rollback strategy.

The adoption ladder​

You do not hand a new agent the keys on day one. Authority is earned one rung at a time, and each rung carries an explicit trust gate to enter, a rollback trigger that drops you back, and graduation criteria to move up.

Analogy: it is how a hospital grants a resident privileges. A first-year does not walk in with authority to operate unsupervised. They observe, then assist, then act under direct supervision, then act within a defined scope with a review afterwards. Each expansion of what they may do is earned by evidence at the current level — and any serious mistake drops them back a step. Nobody sensible grants full authority up front and hopes.

The invariant across all four rungs: authority only widens after the evidence at the current rung says it is safe to widen it. Stage 1 is read-only precisely so the first thing you verify is that the agent diagnoses well before it can ever write. Stage 4 is a bounded loop — the agent acts within fail-closed guardrails it cannot disable, and a human audits afterwards — not an unbounded free hand. You never skip a rung, and every rung is reversible.

What the capstone actually scores​

The grader is the most comprehensive in the course because it scores all seven rubric dimensions at once. Each maps to a phase of the workflow:

DimensionWhat it measuresWhere it is tested
1. Triage disciplinedid you lock the incident before investigating?Phase 1, step 1
2. Evidence qualitystructured, multi-source, independent — no consensus theaterPhase 1–2, steps 3, 8
3. Role adherencethe correct specialist on each track, each in-authorityPhase 2, step 4
4. Repair safetyproposal → review → gate, never a direct applyPhase 3, steps 9–12
5. Infrastructure judgmentreject the dangerous plan, propose a safe alternativePhase 3, steps 10–11
6. Post-incident evaluationeval-score, run-ledger, regression-gatePhase 5
7. Packaging completenessthe starter ships with every piecepackaging

A run that closes the incident but skipped the lock, or applied a repair without review, or shipped a starter missing its change gate, fails the dimension it skipped — even though the metric recovered. The rubric grades the reasoning and the process, not just the outcome, which is the same lesson M18 taught about a single run, now applied to the whole workflow.

The lab runs this end to end against INC-006, using the governed team you built. The deep dive then treats the operating layer as a versioned internal product — ownership, security cadence, update lifecycle, rollback, deprecation, and the metrics that tell you whether the whole thing is actually helping.
