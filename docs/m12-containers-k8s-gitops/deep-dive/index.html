Deep Dive — The Failed Rollout

The core lab put orders-api on the golden path and everything came up green. This Deep Dive is the shift you get paged for at 9 a.m. on a launch day: a rollout that stalls, with symptoms that point at the wrong thing. The dashboard says the service is down. The pods say they are alive. curl against the container works. And the deployment sits at "1 old, 1 new, 0 available" and will not move. Every instinct you have — restart the pods, roll back the app, check the database — is aimed at a cause that is not the cause.

The point of this page is not "readiness probes matter." You know that. The point is the diagnostic discipline for a class of Kubernetes failure where five completely different faults all present as the same symptom — "the service is broken" — and each is fixed a different way. Confusing them is what turns a five-minute fix into a three-hour incident. By the end you will be able to name which of the five you are looking at from the evidence, and you will repair the real one through Git, on the golden path, without ever reaching for kubectl edit.

Where you are working

You continue in the agentic-ops-lab workspace with the orders-api Helm chart. This Deep Dive reasons over the rendered manifest and the app's real source, and grades against labs/m12/deep-dive.checks.json. Every check is a deterministic read of the chart render and the source — no live cluster required — so the diagnosis is reproducible on any machine. If you have a cluster from the core lab, the symptoms described are exactly what you will see live; if you do not, the render and source evidence prove the same root cause.

The five things that all look like "the service is broken"​

Analogy: think of a car that will not start. The symptom is identical — you turn the key, nothing happens — but the cause is one of a handful of completely different systems: a dead battery, an empty tank, a bad starter motor, a blown fuse, a kill switch left on. A mechanic who "just replaces the battery" every time is right often enough to feel competent and wrong often enough to waste your afternoon. The skill is not knowing that cars need batteries; it is the ordered set of checks that tells you which system failed before you touch anything. A stalled Kubernetes rollout is the same: one symptom, five candidate systems, and a diagnosis order that saves you from fixing the wrong one.

Here are the five, and the crucial fact that they are distinguishable from evidence:

  1. Application health — the process itself is crashing or erroring. Evidence: the container exits, logs show a stack trace, restart count climbs.
  2. Probe configuration — the app is fine, but the probe asks it the wrong question (wrong path, wrong port, too-short timeout). Evidence: the container runs, but Kubernetes marks the pod not-ready or kills it on a liveness failure.
  3. Rollout state — the strategy is misconfigured, so a deploy that would otherwise be survivable takes down availability. Evidence: old and new pods coexist wrong, maxUnavailable/maxSurge let too many go down at once.
  4. Routing — the pods are healthy and ready, but the Service selector, port mapping, or network policy sends traffic to the wrong place or nowhere. Evidence: pods Ready, but requests still fail.
  5. Resource pressure — the pod cannot schedule or gets OOM-killed because requests/limits do not fit the node. Evidence: Pending pods, OOMKilled, FailedScheduling events.

The incident you are handed touches two of these at once — probe configuration and rollout state — and the reason it is so misleading is that the other three are innocent, and their innocence looks like reassurance pointing you away from the fix.

The symptom: a rollout that will not complete​

Picture the deploy. A change merged, Argo CD synced, and the new ReplicaSet is stuck. If you have a live cluster, this is what you see; if not, the render evidence below proves why:

NAME                          READY   STATUS    RESTARTS   AGE
orders-api-7d9c8b6f4-xk2lp    0/1     Running   0          4m

Read it carefully, because every field is a clue. STATUS: Running — the container started and has not crashed. RESTARTS: 0 — the kubelet has not killed and restarted it, so liveness is passing. READY: 0/1 — but Kubernetes will not put it in service. A pod that is Running, not restarting, and not Ready is the signature of exactly one of the five: probe configuration. The app is alive (liveness green, zero restarts) but readiness is failing. It is not application health — a crashing app restarts. It is not resource pressure — that pod would be Pending or OOMKilled, not Running.

Rule out application health first​

Discipline says: prove the app is healthy before you blame the probe, because if the app really is broken, fixing the probe just makes a broken app receive traffic. The app serves its own health endpoint; check what it actually exposes:

grep -E '@router.get' app/orders-api/src/health.py
Expected output
@router.get("/healthz")
@router.get("/readyz")
@router.get("/api/v1/info")

The app serves /healthz (liveness) and /readyz (readiness), plus an info route. It works — those handlers return 200. Note what is not there: there is no /health route at all. Hold that fact; it is the whole incident.

Confirm the process answers when you ask it the right question. In the cluster this is a kubectl exec curl; the deterministic proof is that the handler exists and returns a static 200:

grep -A3 '@router.get("/healthz")' app/orders-api/src/health.py
Expected output
@router.get("/healthz")
async def healthz():
    return {"status": "ok"}

The app is healthy. /healthz returns {"status": "ok"} unconditionally — no database call, no dependency. Application health is ruled out. This is the moment most incidents go wrong: the responder sees "0/1 Ready," assumes the app is broken, and starts rolling back a perfectly good application. You have proof it is fine. Move to the probe.

Find the probe mismatch in the render​

The probe config lives in the rendered manifest — never in the template alone, as the lesson insisted. Render the chart and read what Kubernetes is actually asking the pod:

helm template orders-api platform/helm/orders-api | grep -A2 'readinessProbe'
helm template orders-api platform/helm/orders-api | grep -A2 'livenessProbe'
Expected output
          readinessProbe:
            httpGet:
              path: /health
            httpGet:
              path: /healthz

There it is, and this is the misleading part made precise. The liveness probe asks /healthz — a path the app serves — so liveness passes, the container is never killed, RESTARTS stays 0, and every signal says "the app is alive." The readiness probe asks /health — a path the app does not serve — so it gets a 404 on every check, the pod never reports Ready, and no traffic is routed to it. One character of divergence between two probes produces a pod that is simultaneously "healthy" and "unusable," which is exactly why the responder who trusts the green liveness signal chases the wrong cause.

This is the fault, and notice where it lives. It is not in the app (the app is correct), not in the cluster (the cluster is doing exactly what the manifest told it), and not in Argo CD (it synced faithfully). It is in desired state, in Git — a wrong string in values.yaml. That single location is the whole reason the fix routes through the golden path and not through kubectl.

The second fault: the rollout strategy amplifies it​

A wrong readiness path alone would leave you with a stuck new pod and, on a sane rollout strategy, the old pod still serving traffic — degraded, not down. But this chart has a second defect that turns "degraded" into "outage." Read the rollout strategy from the render:

helm template orders-api platform/helm/orders-api | grep -A3 'strategy:'
Expected output
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 100%

maxUnavailable: 100% tells the rollout it may take every existing pod out of service before a replacement is Ready. Combine that with a new pod that will never become Ready (the probe fault), and the sequence is: old pod terminated → new pod comes up unready → stays unready forever → zero pods in service. The strategy did not cause the failure, but it removed the safety margin that would have kept the old pod serving while you noticed. This is the difference between "the deploy is stuck" (probe fault alone) and "the site is down" (probe fault plus a strategy with no floor).

Why two faults, not one

An incident with a single cause is a tutorial. Real rollouts fail because a latent misconfiguration (the 100% maxUnavailable, harmless for months) meets a triggering defect (the probe path) and the combination is worse than either alone. The diagnostic lesson: when the symptom is severe, ask whether two of the five systems are involved. Fixing only the probe here leaves the outage-amplifying strategy in place for the next deploy.

Confirm routing and resources are innocent​

Before you fix, close the loop on the remaining three systems, so you are certain you have the whole picture and not a coincidence. Routing: the Service selector must match the pod labels, and it does (the chart's Service and Deployment share selectorLabels) — but it does not matter yet, because an unready pod is removed from the Service endpoints regardless of the selector. Routing cannot be the cause when readiness is already failing: the pod is not in rotation because it is unready, not because of a selector bug. Resource pressure: the pod is Running, not Pending or OOMKilled, so it scheduled and has not been memory-killed. Both are ruled out by the evidence you already have.

That is the full diagnosis: probe configuration (readiness → /health, a 404) is the root cause, rollout state (maxUnavailable: 100%) is the amplifier, and application health, routing, and resource pressure are all innocent. Five systems, two implicated, three cleared — from evidence, before a single change.

Repair through Git and the reconciler — never kubectl edit​

Here is where the discipline of the whole module pays off. You have found a defect in a live, customer-facing deployment during an incident. The tempting move — the one a stressed responder makes — is kubectl edit deployment orders-api and fix the path right in the cluster. That is the wrong-target class of mistake, and the change gate refuses it from an agent identity:

echo '{"tool_name":"Bash","tool_input":{"command":"kubectl edit deployment orders-api -A"}}' \
  | scripts/hooks/change-gate.sh >/dev/null 2>&1; echo "exit=$?"
Expected output
exit=2

Blocked. And it should be — a hand-edit to the live cluster would be immediately reverted by Argo CD's selfHeal, because the cluster is a projection of Git and Git still says /health. Fixing the cluster without fixing Git is not a fix; it is a change that lasts until the next reconcile loop, seconds later. The only durable repair is to correct desired state.

The root cause is one line in values.yaml. Confirm the defect is there:

grep -n 'path: /health' platform/helm/orders-api/values.yaml
Expected output
19:    path: /health          # DELIBERATE BUG: should be /healthz

The readiness probe path in desired state. This is the candidate change: path: /health → path: /healthz, so the probe asks the app a question it can answer. (A complete incident fix would also lower maxUnavailable from 100% to something like 25% so the next rollout keeps a floor of serving pods — the same one-line-in-Git discipline.)

Prove the fix renders correctly before proposing it — plan before apply, one layer up. Render with the corrected readiness path and confirm the probe now matches the app:

cat > /tmp/fix-readiness.yaml <<'EOF'
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  initialDelaySeconds: 5
  periodSeconds: 10
EOF
helm template orders-api platform/helm/orders-api -f /tmp/fix-readiness.yaml | grep -A2 'readinessProbe'
Expected output
          readinessProbe:
            httpGet:
              path: /healthz

The rendered readiness probe now points at /healthz — the path the app actually serves. You have proven the fix works against the render without touching the cluster, exactly as you would prove a Terraform change against the plan JSON before apply. From here the change goes the golden way: edit values.yaml on a branch, scripts/gitops-propose.sh fix-readiness-probe "readiness probe /health -> /healthz; rollout was stuck at 0/1 Ready", human approval, merge, and Argo CD reconciles the corrected state into the cluster. The pod passes readiness, the Service adds it to endpoints, traffic flows, the rollout completes. Incident closed — through Git, by the reconciler, with a diff someone approved.

Grade the incident​

Run the Deep Dive checks. They certify the diagnosis (app healthy, readiness mismatched, liveness correct, strategy dangerous), the fix location (Git, not the cluster), and the governance (the repair routes through the golden path):

scripts/grade.sh m12-deep-dive
Expected output
Checking: Deep Dive — The Failed Rollout: separating app health, probe config, rollout state, routing, and resource pressure

  ✓ APP HEALTH: the orders-api process serves /healthz (and /readyz) but has NO /health route — so a probe pointed at /health gets a 404, not because the app is down
  ✓ PROBE CONFIG: the RENDERED readiness probe points at /health — the path the app does not serve — so the pod will never report Ready
  ✓ PROBE CONFIG: the liveness probe correctly points at /healthz — this is the misleading part, the container is NOT killed, it just stays perpetually unready
  ✓ ROLLOUT STATE: maxUnavailable is rendered as 100% — a rolling update may take every old pod down before a new one is Ready, turning an unready rollout into a full outage
  ✓ THE FIX: the defect lives in Helm values (desired state in Git), not in the app or the cluster — so the repair is a one-line values change routed through the reconciler, not a kubectl edit
  ✓ THE FIX VERIFIED: overriding the readiness path to /healthz renders a probe that matches the app's real endpoint (proven with helm template and a values override, no cluster touched)
  ✓ GOVERNANCE: the repair path is the golden path — a direct kubectl edit of the live deployment from an agent identity is exactly the wrong-target class the gate blocks; the fix is proposed in Git

========================
RESULT: PASS (7 passed)

Seven green. The counts and exact wording may differ on your machine; a pass means you diagnosed the right two systems out of five and proved the fix renders correctly, all without a hand-edit to the cluster.

Where you will use this​

This is not a Kubernetes-quirk drill; it is the shape of most rollout incidents you will actually run.

  • Any stuck rollout on call. The Running + 0/1 Ready + RESTARTS: 0 signature means "probe, not app" every time. Recognizing it in the first minute is the difference between fixing the probe and needlessly rolling back a healthy release.
  • When an agent proposes a deployment change. The readiness path, the port, and maxUnavailable are exactly the fields an agent can get subtly wrong in a plausible-looking diff. Reviewing the rendered probe and strategy — not the template — is how you catch it before merge, at the approval stop on the golden path.
  • When someone reaches for kubectl edit during an incident. The reflex to fix the live cluster directly is strongest under pressure and most dangerous then — the edit is reverted by selfHeal and now Git and cluster disagree. The muscle memory to fix desired state in Git instead is the single habit that keeps GitOps honest when it matters most.
  • Post-incident, distinguishing the trigger from the amplifier. The write-up that says "readiness probe was misconfigured" is incomplete; the one that says "readiness fault plus maxUnavailable: 100% removed the serving floor" prevents the next outage. Naming both systems is what a real postmortem does.
