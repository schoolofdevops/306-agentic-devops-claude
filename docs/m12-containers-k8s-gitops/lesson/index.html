Kubernetes and GitOps

Module 11 pointed the specialist machinery at Terraform: the code that provisions the estate. This module points it one layer up, at the code that runs on that estate: the Dockerfile that packages a service, the Helm chart that describes how it should live in Kubernetes, and the reconciler that turns a merged Git commit into running pods. It is the same governing idea you have carried since Module 8: the agent proposes, a reconciler disposes, but now the surface is the thing your customers actually talk to. When an agent gets a Terraform change wrong, you might recreate a database. When an agent gets a deployment change wrong, every pod behind the load balancer can go unready at once, and the first anyone hears of it is the checkout page timing out.

Here is the situation this module closes. Northstar's orders-api runs fine in Docker Compose on a laptop, but production is Kubernetes, and the platform team needs the service containerized cleanly, deployed to a real cluster, and, this is the part that matters, set up so that every subsequent change to how it runs in that cluster flows through one auditable path. Not "the agent has kubectl and we trust it." A path where the agent edits desired state in Git, a human approves, and a reconciler is the single identity that writes to the cluster. You are going to build that path, put orders-api on it, and then live inside it for every change after.

The container is a shipping container, and the review is the packing list​

Before Kubernetes, before Helm, before any of it, there is one artifact: the container image. Everything downstream inherits its properties, so the review starts here.

Analogy: a container image is a literal shipping container. The whole point of the intermodal shipping container (the steel box that revolutionized global trade) is that it is sealed, standardized, and identical whether it sits on a truck, a train, or a ship. Nobody at the destination port opens it to check the packing; they trust that what was sealed at origin is what arrives. That trust is exactly what makes it fast, and exactly what makes a bad packing job dangerous. If you sealed a leaking drum of something toxic inside, it travels the whole supply chain unopened and arrives just as toxic. A container image is the same bargain: seal it once, run it identically everywhere, which means every flaw you sealed in (a secret baked into a layer, a root user, a 1.2 GB image full of build tools) ships to every environment, unopened, and runs in production exactly as you built it.

So the container review an agent runs is a packing-list review, and it has five questions, each of which maps to a property that will haunt you later if it is wrong:

  • Is it reproducible? Does the base image pin a version (python:3.12-slim), or does it float on latest: so that the image you tested and the image that ships are silently different builds? A floating base is a change you did not make, applied at a time you did not choose.
  • Is it small? A multi-stage build compiles in a fat builder stage and copies only the artifact into a slim runtime stage. The difference is not vanity: a 1.2 GB image pulls slowly on every node, holds a larger attack surface, and carries every build tool an attacker would love to find already installed.
  • Does it run as non-root? A container that runs as root runs as root on the node if it escapes its namespace. The packing-list question is: is there a USER directive dropping to an unprivileged account, or does this box arrive with the keys still in it?
  • Does it declare health? The image and its manifest have to tell the orchestrator how to know the process is alive (liveness) and ready for traffic (readiness). Get this wrong and Kubernetes cannot tell a warming-up pod from a wedged one: which is the exact failure the Deep Dive dissects.
  • Are there secrets in the layers? A COPY . . that sweeps a .env file into a layer, or an ARG that bakes a token into image history, ships that credential to every environment inside the sealed box. Image layers are not scratch space; they are permanent and inspectable.

This is work an agent is genuinely good at, because it is pattern-matching against a checklist over files it can read in full: the Dockerfile, the .dockerignore, the compose file. The agent's advantage is that it holds all of them in context at once and never gets bored on the fifth review of the day. What it does not get is the authority to push the image; that ships through CI, and the Change Gate from Module 8 denies docker push from an agent identity for exactly that reason.

Kind is the flight simulator for your cluster​

Once the image is packed, it has to run somewhere you can break safely. That somewhere is kind, Kubernetes IN Docker, a full, real Kubernetes cluster that runs as containers on your laptop.

Analogy: kind is a flight simulator. It is not a toy, it runs the same API server, the same scheduler, the same kubelet as the cluster in production, the way a flight simulator runs the same avionics and flight model as the real aircraft. What it gives you is the freedom to crash. You can stall the plane, lose an engine, deploy a broken readiness probe and watch every pod go unready, and nobody is hurt, nothing costs money, and you reset and try again. The reason this matters for agentic work specifically is that an agent's proposed change needs somewhere to prove itself before it touches anything real, and a laptop cluster you can create and delete in ninety seconds is that somewhere.

The catch a real team hits is memory. A full kind cluster with a control plane and a worker node, plus Argo CD, plus your services, wants headroom an 8 GB laptop does not have. Northstar ships two kind profiles for exactly this:

The setup.sh script auto-detects your RAM and warns you to pass --lean below 12 GB. The lesson the agent has to internalize is that the profile changes the topology, and a change validated on one profile is not automatically valid on the other. A pod that schedules fine on a single-node lean cluster might be unschedulable on a two-node standard cluster if it has a node selector; conversely a resource request that fits the standard cluster's worker might not fit when control plane and workload share one node. Adapting to the profile is part of the agent's job, not an afterthought.

Helm renders; you review what it rendered, not what you wrote​

A Helm chart is not manifests. It is a template for manifests plus a values.yaml of the knobs, and the manifests only exist after Helm combines the two. This is the single most important mechanical fact in this module, and it is the direct analog of Module 11's "review the plan JSON, not the HCL."

Analogy: a Helm chart is a form letter with fill-in-the-blank fields, and values.yaml is the mail-merge spreadsheet. "Dear ⟨name⟩, your ⟨plan⟩ renews on ⟨date⟩" is not the letter anyone receives: it is the template. The letter that actually lands in a mailbox exists only after the merge fills every blank. If you proofread the template you catch typos in the fixed text, but you will never catch that row 400 of the spreadsheet has an empty plan field that renders "your renews on", because that defect only appears in the merged output, not the template. Reviewing a Helm chart by reading its templates has the same blind spot. The defect that takes down a service (a probe pointing at a path the app does not serve, a maxUnavailable set to 100%) lives in the rendered manifest, which is template and values combined.

So the agent's Kubernetes review is built on one command: helm template. It runs the chart through the templating engine with a given values file and emits the exact YAML that would be applied: the rendered manifest, as data. From there every review is a query against that output:

  • Does it render at all? A chart with a template error fails helm template, and catching that on a laptop is infinitely cheaper than catching it when Argo CD refuses to sync.
  • What does the probe actually point at? After rendering, the readinessProbe.httpGet.path is a concrete string. The Deep Dive turns on exactly this: the template is fine, but a release candidate renders a probe pointing at /health when the app serves /healthz.
  • What is the rollout strategy? maxUnavailable and maxSurge are rendered numbers. maxUnavailable: "100%" means a rolling update may take every old pod down before a new one is ready: a self-inflicted outage that is invisible until the deploy runs.
  • Rendered-vs-running diff. The highest-value review compares what the chart renders against what is currently running in the cluster (helm template output diffed against kubectl get ... -o yaml). That diff is the blast radius of a sync, the exact set of changes the reconciler will make, and it is the thing a reviewer approves.

The chart and values are the intent; the rendered manifest is the computed effect; the diff against running state is the consequence. You review the effect and the consequence, never just the intent: the same discipline as the plan JSON, one layer up the stack.

There is a subtler review the render also enables: catching what is absent. A missing field is invisible when you read a template (you cannot see a block that was never written), but in the rendered manifest its absence has consequences you can name. Northstar's orders-api chart, for instance, renders a pod with no resources block: no CPU/memory requests, no limits. Read as intent, that is just a gap in a values file. Read as effect, it is a scheduling and stability decision made by omission: a pod with no requests can be scheduled onto a node with no room to actually run it, and a pod with no memory limit can grow until it starves its neighbors and gets OOM-killed under load, exactly the "resource pressure" failure the Deep Dive lists as one of its five look-alikes. The agent's job is to notice the absence and propose the requests and limits the workload needs, because "the chart never set them" is not the same as "the workload does not need them." Reviewing the render is as much about the fields that are missing as the ones that are wrong.

RBAC and policy are the enforcement under the intent​

Module 8 drew a line you have used ever since: intent is what a policy says should happen; enforcement is what the system physically prevents regardless of intent. In Kubernetes, that line has names, and the agent needs to read them the way it reads Helm values: as facts about what is and is not possible, not aspirations.

  • Service accounts and RBAC. Every pod runs as a service account, and that account's Role/ClusterRole bindings define what it can touch through the API. Northstar's read-only kubeconfig (platform/kubeconfigs/readonly.yaml) binds a ClusterRole whose verbs are exactly get, list, watch: no create, update, delete. That is not a promise the agent will only read; it is an identity that cannot write, checked by the API server on every call. The agent-facing lesson: read the RBAC to know what an identity can actually do, and never assume a "read-only" label without confirming the verbs.
  • Network policy. By default, every pod in a namespace can talk to every other pod: a flat network. A NetworkPolicy narrows that. Northstar ships an intentionally permissive allow-all-ingress policy today (hardened later in the SecOps module), and the honest thing is to read the policy and report what it actually allows, not what its name suggests.
  • Admission checks (Pod Security). The northstar namespace carries Pod Security Standard labels, enforce: baseline, warn: restricted, audit: restricted. Those are admission-time gates: a pod that violates the baseline standard is rejected at creation by the API server, before it ever schedules. This is enforcement in its purest form, the cluster refuses the object, no matter who submitted it.

The reason all three matter to an agent is the same reason the Change Gate matters: an agent operating in a cluster should be bounded by the cluster's own controls, so that even a confused or misdirected agent cannot exceed them. The read-only kubeconfig is the agent's default identity for a reason: it lets the agent investigate freely and prevents it from writing at all.

The golden path: the reconciler is the only writer​

Everything above converges on one model, and it is the whole point of the module. The agent has no direct cluster-write path. It edits desired state in Git; a human reviews and merges; Argo CD, the reconciler, is the single identity that turns merged Git state into cluster state.

Analogy: think of the cluster as a bank vault with exactly one key, and that key is held by an automated system, not a person and not an agent. You do not walk up to the vault and move money. You submit a signed transfer request, an officer approves it, and the automated system (the only holder of the key) executes it and logs every move. The agent is the customer filling out the transfer slip. It can propose any change it likes, in perfect detail, and it physically cannot open the vault. Argo CD is the automated system with the key: it watches the merged Git branch and reconciles the cluster to match, continuously, and it is the only identity with write access. If the live cluster drifts from Git (someone hand-edits a deployment), the reconciler pulls it back. Git is the source of truth; the cluster is a projection of it.

This is why the golden path has five stops, and why the agent's authority ends at the second:

  • Candidate. The platform-engineer agent edits values.yaml (or a manifest) on a branch and validates it renders with helm template and helm lint. It runs scripts/gitops-propose.sh, which stages the desired-state change, shows the diff, and stops: printing the human's next steps. That script refuses to touch a cluster; it is the agent's structural stopping point.
  • Approval. A human (or the read-only change-reviewer agent) reviews the rendered diff, the blast radius of the sync, against the change contract.
  • Merge. The approved change lands on main in the Git remote Argo CD watches.
  • Sync. Argo CD detects the new commit and reconciles the cluster to match. This is the only write to the cluster, and it comes from the reconciler's identity, never the agent's.
  • Verify. The rollout completes, pods pass readiness, and the change is confirmed live: or the rollout stalls and you have an incident, which is the Deep Dive.

The reason this path is worth the ceremony is that it makes "the agent did something to production" impossible to do by accident. There is no kubectl apply for the agent to fat-finger, no helm upgrade for a runaway loop to execute against the wrong context. The agent's most dangerous possible action is proposing a bad change in Git: which a human reads before it ever syncs. The blast radius of an agent mistake is bounded to "a pull request someone rejects."

Where this connects

The pieces you assemble here were built in earlier modules: Module 1 fixed the /health vs /healthz readiness bug in the app and the chart (the Deep Dive watches a stale release candidate reintroduce it); Module 8 built the candidate → approval → merge → sync change path and the Environment Contract; Module 9 built the platform-engineer role you use for Kubernetes work; Module 11 used git worktree isolation for infrastructure changes, and the same pattern applies to desired-state changes here.

What you will carry out of this module​

You will have containerized orders-api and reviewed the Dockerfile against the five packing-list questions; stood up a real Kubernetes cluster on kind and adapted to its memory profile; rendered a Helm chart and reviewed the output, not the template; read the RBAC, network policy, and admission labels that bound what any identity, including the agent, can do; and put orders-api on the golden path, where every change from here flows candidate → approval → merge → sync → verify with the reconciler as the only writer.

The Deep Dive then breaks it on purpose. A misconfigured readiness probe produces a rollout that fails with misleading symptoms, the application is healthy, but the pods are not ready, and the difference between "the app is down" and "the probe is wrong" is the difference between a thirty-minute incident and a three-hour one. You will learn to separate application health from probe configuration from rollout state from routing from resource pressure, five things that all look like "the service is broken" and each of which is fixed a completely different way. And you will fix it the only way this module allows: through Git, through the reconciler, on the golden path.
