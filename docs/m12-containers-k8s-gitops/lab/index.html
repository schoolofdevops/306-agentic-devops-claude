Lab — Containers, Kubernetes & GitOps

The lesson drew the arc: review the container as a packing list, run it on kind as a flight simulator, review the rendered Helm manifest and not the template, read the RBAC and policy that bound every identity, and put the service on the golden path where the reconciler is the only writer. This lab makes all of it runnable against Northstar's real orders-api chart and kind configs. You will review the Dockerfile against the five packing-list questions, stand up a real Kubernetes cluster (standard or lean depending on your RAM), render the Helm chart and read the two defects hiding in the output, confirm what the read-only identity and the change gate physically prevent, and then route one change through the full candidate → approval → merge → sync → verify path with Argo CD as the reconciler.

By the end you will have orders-api running in Kubernetes and a change path where the agent proposes in Git and never touches the cluster — the state the Deep Dive then breaks on purpose.

Where you are working

You start at the root of the agentic-ops-lab workspace. The container assets live under app/orders-api/ (the Dockerfile) and docker-compose.yaml. The Kubernetes assets live under platform/: Helm charts in platform/helm/, kind configs and setup.sh in platform/kind/, the minimal Argo CD install in platform/argocd/, kubeconfigs in platform/kubeconfigs/, and policies in platform/policies/. The GitOps scripts (local-git-remote.sh, gitops-propose.sh) and the Module 8 change gate (scripts/hooks/change-gate.sh) ship in scripts/. The container-review and Helm-render steps run anywhere with Docker + Helm; the cluster steps need kind (they create and delete a local cluster you own).

Step 0 — Prerequisites​

Confirm your tools. The cluster steps need kind, kubectl, and Docker running; the render steps need helm.

docker version --format '{{.Client.Version}}'
kind version | head -1
kubectl version --client -o json | jq -r '.clientVersion.gitVersion'
helm version --short
Expected output
29.5.3-rd
kind v0.27.0 go1.23.6 darwin/arm64
v1.35.0
v4.2.1+gd591a19

Your versions will differ. Docker must be running (the cluster runs as containers); kind ≥ 0.20, kubectl and helm ≥ 3.12 (or v4) are fine. If docker version errors on the client line, Docker Desktop is not running — start it before continuing.

Step 1 — Review the container as a packing list​

Before the service runs anywhere, review the image it will run as. Read the Dockerfile against the five packing-list questions from the lesson.

cat app/orders-api/Dockerfile
Expected output
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /install /usr/local
COPY src/ src/
COPY static/ static/
ENV PORT=8080
ENV PYTHONPATH=/app
EXPOSE 8080
CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8080"]

Now score it against the checklist. This is the review an agent produces — mechanical, checklist-driven, over a file it reads in full:

echo "1. Reproducible base?  "; grep '^FROM' app/orders-api/Dockerfile
echo "2. Multi-stage (small)?"; grep -c '^FROM' app/orders-api/Dockerfile
echo "3. Non-root USER?      "; grep -c '^USER ' app/orders-api/Dockerfile
echo "4. .dockerignore?      "; ls app/orders-api/.dockerignore 2>/dev/null || echo "MISSING"
Expected output
1. Reproducible base?  
FROM python:3.12-slim AS builder
FROM python:3.12-slim
2. Multi-stage (small)?
2
3. Non-root USER?      
0
4. .dockerignore?      
MISSING

Read the findings. Good: the base image is pinned (python:3.12-slim, not latest) so the build is reproducible, and there are two FROM lines — a multi-stage build that leaves the compiler behind and copies only the installed packages into a slim runtime. Findings: there is no USER directive (the container runs as root — finding), and there is no .dockerignore (a COPY src/ is scoped, but the absence means a careless COPY . . later would sweep in anything, and there is nothing stopping a local .env from entering a layer — finding). A real review would propose adding a non-root USER and a .dockerignore; note them and move on — the point is that the agent produces the findings, a human decides.

Step 2 — Stand up a real Kubernetes cluster on kind​

Pick your profile by RAM. The setup.sh script auto-detects and warns, but you choose explicitly:

  • 16 GB or more: standard profile (control-plane + worker), the default.
  • 8 GB: lean profile (single node), pass --lean.
# 16 GB path (default):
platform/kind/setup.sh
# 8 GB path — run THIS instead if you have 8 GB:
# platform/kind/setup.sh --lean
Expected output
[INFO] Using standard config (1 control-plane + 1 worker)
[INFO] Creating Kind cluster 'northstar'...
Creating cluster "northstar" ...
 ✓ Ensuring node image (kindest/node:v1.29.2) 🖼
 ✓ Preparing nodes 📦 📦
 ✓ Writing configuration 📜
 ✓ Starting control-plane 🕹️
 ✓ Installing CNI 🔌
 ✓ Installing StorageClass 💾
 ✓ Joining worker nodes 🚜
 ✓ Waiting ≤ 1m0s for control-plane = Ready ⏳
[INFO] Waiting for nodes to be ready...
node/northstar-control-plane condition met
node/northstar-worker condition met
[INFO] Creating 'northstar' namespace...
namespace/northstar created
[WARN] Image orders-api:latest not found locally. Build with: docker compose build
[INFO] Cluster 'northstar' is ready!

This is point-in-time output — the node image tag, emoji, and timing will differ. The [WARN] about orders-api:latest is expected; you build and load the image in Step 3. On the lean profile you would see one node (northstar-control-plane) instead of two.

Confirm the cluster shape:

kubectl get nodes
Expected output
NAME                       STATUS   ROLES           AGE   VERSION
northstar-control-plane    Ready    control-plane   45s   v1.29.2
northstar-worker           Ready    <none>          30s   v1.29.2

Two nodes on the standard profile, one on lean. This is a real cluster — same API server, scheduler, and kubelet as production.

Step 3 — Build the image and load it into the cluster​

kind runs its own containerd; an image built on your host Docker is not visible to the cluster until you load it. Build orders-api and load it:

docker build -t orders-api:latest app/orders-api
kind load docker-image orders-api:latest --name northstar
Expected output
[+] Building 12.4s (14/14) FINISHED
 => => naming to docker.io/library/orders-api:latest
Image: "orders-api:latest" with ID "sha256:..." found to be already present on all nodes.

Build time and the image ID will differ. The kind load line confirms the image is now available to every node in the cluster — without this, pods would sit in ErrImageNeverPull, because the chart sets pullPolicy: IfNotPresent and there is no registry to pull from.

Step 4 — Render the Helm chart and review the OUTPUT​

Do not read the templates to decide if the chart is safe. Render it and read what Helm actually produces. Render orders-api with its default values:

helm template orders-api platform/helm/orders-api | grep -A4 'readinessProbe'
Expected output
          readinessProbe:
            httpGet:
              path: /health
              port: http
            initialDelaySeconds: 5

Read the rendered path: /health. Hold that — the orders-api process serves its readiness endpoint at /healthz, not /health. This is the defect that only appears in the rendered output (it lives in values.yaml, merged into the template), and it is what the Deep Dive turns into a failed rollout. For now, note it as a finding.

Now render the rollout strategy — the other defect hiding in the values:

helm template orders-api platform/helm/orders-api | grep -A4 'strategy:'
Expected output
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 100%
    type: RollingUpdate

maxUnavailable: 100% means a rolling update is allowed to take every existing pod down at once before a replacement is ready. On a single-replica deployment that is a guaranteed gap in availability on every deploy. Two findings, both invisible in the template, both plain in the render — this is exactly why you review the output.

Confirm the chart is at least structurally valid (lint checks template correctness, not your findings):

helm lint platform/helm/orders-api
Expected output
==> Linting platform/helm/orders-api
[INFO] Chart.yaml: icon is recommended

1 chart(s) linted, 0 chart(s) failed

Lint passes — the chart renders and is well-formed. That is the trap the lesson warned about: a chart that lints clean can still carry a probe pointed at the wrong path and a rollout strategy that guarantees an outage. Lint checks the form letter; your review checks the merged result.

Step 5 — Read the enforcement: RBAC, network policy, admission​

Before you deploy, read what the cluster physically prevents — the enforcement under the intent. First the read-only identity the agent uses by default:

grep -A2 'name: northstar-readonly' platform/kubeconfigs/readonly.yaml | head; echo "---verbs---"; grep 'verbs:' platform/kubeconfigs/readonly.yaml
Expected output
  name: northstar-readonly
rules:
  - apiGroups: ["", "apps", "batch", "networking.k8s.io"]
---verbs---
    verbs: ["get", "list", "watch"]

The read-only ClusterRole grants exactly get, list, watch — no create, update, or delete. This is not a promise the agent will only read; it is an identity the API server will not let write. Bind the agent's kubectl to this and a mutating call is refused at the server, regardless of the agent's intent.

Now the admission-time gate on the namespace:

grep 'pod-security.kubernetes.io/enforce:' platform/policies/pod-security.yaml
Expected output
    pod-security.kubernetes.io/enforce: baseline

The northstar namespace enforces the baseline Pod Security Standard: a pod that violates it is rejected at creation by the API server, before it ever schedules. That is enforcement in its purest form — the object is refused no matter who submits it.

Step 6 — Deploy through GitOps: the local Git remote and Argo CD​

Now put orders-api on the golden path. The reconciler needs a Git remote to watch. Create the local bare remote and install Argo CD into the cluster:

scripts/local-git-remote.sh
kubectl apply -f platform/argocd/install.yaml
kubectl -n argocd rollout status deploy/argocd-application-controller --timeout=120s
Expected output
==> Creating bare Git remote at /tmp/northstar-remote.git...
Initialized empty Git repository in /tmp/northstar-remote.git/
==> Adding as remote 'local' and pushing...
==> Local Git remote ready.
   Path: /tmp/northstar-remote.git
namespace/argocd created
serviceaccount/argocd-server created
deployment.apps/argocd-application-controller created
service/argocd-server created
deployment "argocd-application-controller" successfully rolled out

The remote at /tmp/northstar-remote.git is what Argo CD watches — the orders-api Application points its repoURL at exactly this path. Argo CD is now running; the application controller is the identity that will write to the cluster.

Register the orders-api Application so Argo CD begins reconciling it from Git:

kubectl apply -f platform/argocd/applications/orders-api.yaml
kubectl -n argocd get application orders-api
Expected output
application.argoproj.io/orders-api created
NAME         SYNC STATUS   HEALTH STATUS
orders-api   Synced        Progressing

SYNC STATUS: Synced means the cluster now matches Git; HEALTH STATUS climbs from Progressing toward Healthy as pods come up. Argo CD did the write — you applied the Application definition, and the reconciler applied the rendered chart from the Git remote. That is the split the whole module rests on.

Step 7 — Confirm the agent cannot write to the cluster​

Prove the boundary directly. The agent's most dangerous cluster commands are denied by the Module 8 change gate. Simulate the hook calls the agent's Bash tool would trigger.

Deleting a namespace is blocked:

echo '{"tool_name":"Bash","tool_input":{"command":"kubectl delete namespace northstar"}}' \
  | scripts/hooks/change-gate.sh >/dev/null 2>&1; echo "exit=$?"
Expected output
exit=2

Exit 2 is the block signal. The agent cannot delete a namespace — the blast radius is unbounded and the gate refuses it.

A wildcard mutation across all namespaces is blocked:

echo '{"tool_name":"Bash","tool_input":{"command":"kubectl delete pods -A"}}' \
  | scripts/hooks/change-gate.sh >/dev/null 2>&1; echo "exit=$?"
Expected output
exit=2

Blocked. A mutating kubectl targeting every namespace has no safe blast radius, so the gate denies it.

And docker push from an agent identity is blocked — images ship through CI, not the agent:

echo '{"tool_name":"Bash","tool_input":{"command":"docker push orders-api:latest"}}' \
  | scripts/hooks/change-gate.sh; echo "exit=$?"
Expected output
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"docker push is blocked — images are built and published by the CI pipeline, not from an agent identity. Push code to a branch and let CI build and publish the image."}}
DENIED by change-gate: docker push is blocked — images are built and published by the CI pipeline, not from an agent identity. Push code to a branch and let CI build and publish the image.
exit=2

The structured deny and exit 2 together are what Claude Code reads to refuse the tool call. The agent proposes changes in Git; images and cluster writes are somebody else's authority.

Step 8 — Route a change the golden way: candidate → propose → stop​

Now make a real change the correct way. Say the review in Step 1 said replicaCount should be 2 for availability. The platform-engineer edits desired state in Git and proposes — it does not helm upgrade anything.

Where the agent fits

In a real run you would launch the platform-engineer subagent (from Module 9) to make this edit. Its tool bundle is Git-only — it can Edit files under platform/, run helm template/helm lint and read-only kubectl, and propose on a branch, but it has no cluster-write path. Here you do the edit by hand so the mechanics are visible; the authority boundary is identical either way — edit desired state, validate the render, propose, stop.

Make the desired-state edit and validate it renders:

sed -i.bak 's/^replicaCount: 1/replicaCount: 2/' platform/helm/orders-api/values.yaml && rm -f platform/helm/orders-api/values.yaml.bak
helm template orders-api platform/helm/orders-api | grep 'replicas:'
Expected output
  replicas: 2

The render confirms the change takes effect in the output. You validated the candidate before proposing it — the same discipline as running terraform plan before proposing an infra change.

Run the proposal script — the agent's structural stopping point:

scripts/gitops-propose.sh bump-orders-replicas "Set orders-api replicaCount to 2 for availability"
Expected output
==> Preparing GitOps proposal on branch 'propose/bump-orders-replicas'
Proposed desired-state change:
 platform/helm/orders-api/values.yaml | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

==> This is the agent's stopping point.
The agent has proposed a change in Git. It has NOT touched any cluster.

Next steps (human / reconciler — NOT the agent):
  1. git commit -m "Set orders-api replicaCount to 2 for availability"
  2. git push local HEAD:propose/bump-orders-replicas
  3. Open a PR, get change-reviewer approval, merge to main
  4. Argo CD (the reconciler) syncs merged state to the cluster

The reconciler is the only identity that writes to the cluster.

This is the whole model in one command. The agent staged the desired-state change, showed the diff (the blast radius a reviewer approves), and stopped. It printed the human steps and touched no cluster. Everything past the stop line — commit, push, PR, approval, merge, sync — is a human or the reconciler, never the agent.

Step 9 — Complete the golden path: merge and let the reconciler sync​

Play the human role. Commit and push the approved change to the branch the remote tracks, then merge to main (the branch Argo CD watches):

git checkout main 2>/dev/null || git checkout -b main
git add platform/helm/orders-api/values.yaml
git commit -m "Set orders-api replicaCount to 2 for availability"
git push local HEAD:main
Expected output
[main 1a2b3c4] Set orders-api replicaCount to 2 for availability
 1 file changed, 1 insertion(+), 1 deletion(-)
To file:///tmp/northstar-remote.git
   3adb15b..1a2b3c4  HEAD -> main

The approved change is now on main in the remote. You did the write to Git; you never touched the cluster. Argo CD (with syncPolicy.automated) detects the new commit and reconciles — verify the sync picked it up:

kubectl -n argocd get application orders-api -o jsonpath='{.status.sync.status}{"\n"}'
kubectl -n northstar get deploy orders-api -o jsonpath='{.spec.replicas}{"\n"}'
Synced
2

The deployment now runs 2 replicas — and the reconciler made that change, from merged Git, not you. That is candidate → approval → merge → sync → verify, end to end, with the agent's authority ending at "propose."

Step 10 — Grade the module​

Run the machine checks for M12:

scripts/grade.sh m12
Expected output
Grading: Module m12
========================

Checking: Containers, Kubernetes & GitOps — container review, rendered-manifest review, cluster enforcement, and the reconciler-only change path

  ✓ CONTAINER REVIEW: the orders-api Dockerfile pins a versioned base image (python:3.12-slim), not :latest — the build is reproducible
  ✓ CONTAINER REVIEW: the orders-api Dockerfile is multi-stage (two FROM lines) — the compiler stays in the builder, only the artifact ships in the slim runtime
  ✓ RENDER REVIEW: helm template surfaces the readiness probe path as a concrete string in the rendered manifest (review the output, not the template)
  ✓ RENDER REVIEW: the rollout strategy is readable as data in the render — maxUnavailable is a concrete value a reviewer can gate on
  ✓ RENDER REVIEW: the chart lints clean (0 failed) — a well-formed chart can still carry the two defects, which is why lint is not the review
  ✓ ENFORCEMENT: the read-only kubeconfig's ClusterRole grants exactly get/list/watch and no write verb — the agent's default identity cannot mutate the cluster
  ✓ ENFORCEMENT: the northstar namespace enforces the baseline Pod Security Standard at admission — violating pods are rejected at creation
  ✓ GITOPS: the change gate denies deleting the northstar namespace from an agent identity (exit 2) — an unbounded blast radius is refused
  ✓ GITOPS: the change gate denies a mutating kubectl across all namespaces (-A) from an agent identity (exit 2)
  ✓ GITOPS: the change gate denies docker push from an agent identity (exit 2) — images ship through CI, not the agent
  ✓ GITOPS: the proposal script exists and is executable — the agent's structural stopping point (edit desired state, propose on a branch, stop)
  ✓ GITOPS: gitops-propose contains no cluster-write command (no kubectl apply / helm upgrade) — it writes to Git and stops, never to a cluster

========================
RESULT: PASS (12 passed)

Every check maps to a claim in the lesson. Notice these grade checks are all deterministic reads of the repo (Dockerfile, chart render, kubeconfig, policy, change gate) — none of them require a live cluster, so grade.sh m12 passes whether or not you completed Steps 2–3 and 6. The container review, the render review, the enforcement reads, and the reconciler-only change path all hold on the files alone.

Teardown​

Delete the cluster, remove the local Git remote, and reset the chart change so the next module starts clean:

kind delete cluster --name northstar
scripts/local-git-remote.sh --clean
git checkout platform/helm/orders-api/values.yaml
Expected output
Deleting cluster "northstar" ...
Deleted nodes: ["northstar-control-plane" "northstar-worker"]
==> Removing existing remote at /tmp/northstar-remote.git...
Updated 1 path from the index

The cluster and its containers are gone (kind clusters cost nothing when deleted), the local remote is removed, and values.yaml is back to its committed state. Nothing about this lab persists — you can re-run it from a clean slate any time.

Reset to a known state

If anything is in a strange state, scripts/reset.sh m12 returns the whole workspace to the module's start state, and kind get clusters confirms no stray cluster is left running.
