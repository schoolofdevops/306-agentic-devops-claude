Lab — Harden and Ship an Image

The lesson drew the arc: review the container as a packing list, run it on kind as a flight simulator, review the rendered Helm manifest and not the template, read the RBAC and policy that bound every identity, and put the service on the golden path where the reconciler is the only writer. This lab makes all of it runnable against Northstar's real orders-api chart and kind configs.

You will have Claude review the Dockerfile against the five packing-list questions and then repair what it finds, stand up a real Kubernetes cluster, review the rendered chart and hand its one remaining defect to the platform-engineer subagent, confirm what the read-only identity and the change gate physically prevent, and route the whole repair through the two change paths — desired state through GitOps, application code through CI — to a merge the reconciler syncs.

By the end you will have an orders-api that runs as a non-root user, ships a scoped build context, and rolls out with a serving floor — all of it merged on main through a path where the agent proposes and never writes to a cluster.

Where you are working

You start at the root of the agentic-ops-lab workspace. The container assets live under app/orders-api/ (the Dockerfile) and docker-compose.yaml. The Kubernetes assets live under platform/: Helm charts in platform/helm/, kind configs and setup.sh in platform/kind/, the minimal Argo CD install in platform/argocd/, kubeconfigs in platform/kubeconfigs/, and policies in platform/policies/. The GitOps scripts (local-git-remote.sh, gitops-propose.sh) and the Module 8 change gate (scripts/hooks/change-gate.sh) ship in scripts/. The container-review and Helm-render steps run anywhere with Docker + Helm; the cluster steps need kind (they create and delete a local cluster you own).

This lab assumes Module 1 is merged

Module 1 repaired the readiness probe in platform/helm/orders-api/values.yaml and merged it to main. This lab reviews the chart after that repair, so the rendered probe you see below is /healthz. If you skipped Module 1 or discarded its merge, go back and finish it — the render review here reads as a false finding otherwise.

Step 0 — Prerequisites and launch posture​

Confirm your tools. The cluster steps need kind, kubectl, and Docker running; the render steps need helm.

docker version --format '{{.Client.Version}}'
kind version | head -1
kubectl version --client -o json | jq -r '.clientVersion.gitVersion'
helm version --short
Expected output
29.5.3-rd
kind v0.32.0 go1.26.3 darwin/arm64
v1.32.2
v4.2.1+gd591a19

Your versions will differ. Docker must be running (the cluster runs as containers); kind ≥ 0.20, kubectl and helm ≥ 3.12 (or v4) are fine. If docker version errors on the client line, Docker Desktop is not running — start it before continuing.

Now start Claude. This module is normal iterative work — the agent edits a Dockerfile and a values file, and the hooks and deny rules from Module 8 stay in force underneath — so run it in acceptEdits:

claude --permission-mode acceptEdits

You will approve individual Bash calls (the build, the render) as they come up; file edits go through without a prompt. That is the trade this posture makes: low friction on edits, an explicit decision on anything that runs.

Step 1 — Review the container as a packing list​

Before the service runs anywhere, review the image it will run as. Hand Claude the five packing-list questions from the lesson and hold it to evidence — a review that does not cite the line it read is an opinion.

Review app/orders-api/Dockerfile as a release reviewer, against these five questions:
1. Is the base image pinned to a version, or does it float on :latest?
2. Is the build multi-stage, so build tools stay out of the runtime image?
3. Does the image run as a non-root USER?
4. Is there a .dockerignore, so build context and secrets do not leak into layers?
5. Is the runtime port declared, and does the CMD match it?

Answer each question with the line of evidence you read.
Read only — do not edit anything yet.

What Claude does. It reads the Dockerfile in full, then goes looking for a .dockerignore that the Dockerfile itself never mentions — a file whose absence is the finding, which is why question 4 is asked as a question and not as a grep.

What you observe. Two clear passes, two clear findings, and — on the run this was captured from — a third observation nobody asked for:

  1. Base pinned? No. Line 1/6: FROM python:3.12-slim — tag floats on minor/patch, no digest pin. Not :latest literally, but not fully pinned either.
  2. Multi-stage? Yes. Line 1 AS builder builds deps, line 6 fresh FROM python:3.12-slim runtime, only --from=builder /install /usr/local copied over.
  3. Non-root USER? No. No USER instruction anywhere. Runs as root.
  4. .dockerignore present? No. Build context + COPY src/ static/ risk leaking stray files (.env, .git, __pycache__).
  5. Port declared + CMD match? Yes. EXPOSE 8080, ENV PORT=8080, CMD binds --port 8080. Consistent.

Your wording will differ. Read finding 1 carefully, because it is the one you should push back on: python:3.12-slim is pinned enough for this course's purposes, and Claude has quietly widened the question from "is it pinned" to "is it digest-pinned." That is a real practice, and it is also a change nobody asked for. Deciding which findings you act on is the review; the agent produces the list, you own the disposition.

Step 2 — Repair the two findings that matter​

A review that ends in a list is half a review. Have Claude fix the two findings you accepted:

Fix the two findings from your review, in the repository:

1. Add a non-root USER to app/orders-api/Dockerfile. Create an unprivileged user
   in the runtime stage and switch to it before CMD.
2. Create app/orders-api/.dockerignore covering VCS metadata, Python caches,
   local env files, and test artifacts.

Do not change the base image, the stage layout, or the CMD.
Then run: docker build -t orders-api:latest app/orders-api
and tell me whether the image builds.

What Claude does. It edits the runtime stage of the Dockerfile, writes a new .dockerignore, and then asks your approval for the docker build — the one Bash call in the step. Approve it.

What you observe. It adds a system user and group rather than a bare USER 1000, and it chowns /app so the unprivileged process can still read what it needs — the detail that separates a USER line that works from one that breaks the container on start. Confirm the repair:

cat app/orders-api/Dockerfile
Expected output
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /install /usr/local
COPY src/ src/
COPY static/ static/
RUN groupadd --system app && useradd --system --gid app --no-create-home app \
    && chown -R app:app /app
ENV PORT=8080
ENV PYTHONPATH=/app
EXPOSE 8080
USER app
CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8080"]

The USER app sits after the chown and before CMD — the order matters. A USER placed before the COPY lines would leave the copied files owned by root and unreadable to the new user.

Now score the Dockerfile against the same checklist you gave Claude, mechanically. This is the review as the grader will run it:

echo "1. Reproducible base?  "; grep '^FROM' app/orders-api/Dockerfile
echo "2. Multi-stage (small)?"; grep -c '^FROM' app/orders-api/Dockerfile
echo "3. Non-root USER?      "; grep -c '^USER ' app/orders-api/Dockerfile
echo "4. .dockerignore?      "; ls app/orders-api/.dockerignore 2>/dev/null || echo "MISSING"
Expected output
1. Reproducible base?  
FROM python:3.12-slim AS builder
FROM python:3.12-slim
2. Multi-stage (small)?
2
3. Non-root USER?      
1
4. .dockerignore?      
app/orders-api/.dockerignore

Four for four. Question 3 went from 0 to 1 and question 4 from MISSING to a real path — those are the two repairs, visible as data rather than as a claim in a report.

A USER line in a Dockerfile is desired state, not proof. Ask the running image who it is:

docker run --rm --entrypoint sh orders-api:latest -c 'id'
Expected output
uid=999(app) gid=999(app) groups=999(app)

uid=999, not uid=0. The process inside the container is now unprivileged, which is what the baseline Pod Security Standard in Step 7 is going to care about. Note the difference between the two checks: the grep proved the instruction exists, and this proved the image behaves that way. Reviewing the first and assuming the second is how a USER line that never took effect ships to production.

Step 4 — Build the image and load it into the cluster​

kind runs its own containerd; an image built on your host Docker is not visible to the cluster until you load it. Load the hardened orders-api you built in Step 2:

kind load docker-image orders-api:latest --name northstar
Expected output
Image: "orders-api:latest" with ID "sha256:..." found to be already present on all nodes.

The image ID will differ. This line confirms the image is now available to every node in the cluster — without it, pods would sit in ErrImageNeverPull, because the chart sets pullPolicy: IfNotPresent and there is no registry to pull from. Note what you just loaded: the non-root image from Step 2, not the root one you started the lab with.

Step 5 — Render the Helm chart and review the output​

Do not read the templates to decide if the chart is safe. Render it and read what Helm actually produces. Start with the readiness probe:

helm template orders-api platform/helm/orders-api | grep -A4 'readinessProbe'
Expected output
          readinessProbe:
            httpGet:
              path: /healthz
              port: http
            initialDelaySeconds: 5

/healthz — a path the orders-api process actually serves. This is Module 1's repair, seen from the other end. In Module 1 you fixed a string in values.yaml and trusted a grader; here you are reading the merged result Kubernetes will act on, which is the only artifact that ever mattered. A probe path is correct in the render or it is not correct at all.

Now render the rollout strategy — the defect still hiding in the values:

helm template orders-api platform/helm/orders-api | grep -A4 'strategy:'
Expected output
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 100%
    type: RollingUpdate

maxUnavailable: 100% means a rolling update is allowed to take every existing pod down at once before a replacement is ready. On a single-replica deployment that is a guaranteed gap in availability on every deploy. Invisible in the template, plain in the render — which is exactly why you review the output.

Confirm the chart is at least structurally valid. Lint checks template correctness, not your findings:

helm lint platform/helm/orders-api
Expected output
==> Linting platform/helm/orders-api
[INFO] Chart.yaml: icon is recommended

1 chart(s) linted, 0 chart(s) failed

Lint passes — the chart renders and is well-formed. That is the trap the lesson warned about: a chart that lints clean can still carry a rollout strategy that guarantees an outage. Lint checks the form letter; your review checks the merged result.

Step 6 — Hand the chart repair to the platform-engineer​

You could fix maxUnavailable yourself in two keystrokes. Do not — hand it to the role whose authority actually covers it. platform-engineer (from Module 9) owns platform/helm/, runs helm template/lint and read-only kubectl, and has no cluster-write path at all. The Dockerfile you edited in Step 2 is outside its authority; the chart is squarely inside it.

Hand this to the platform-engineer subagent — the chart is its authority, not mine.

The rendered rollout strategy for orders-api sets maxUnavailable to 100%, which lets
a rolling update take every serving pod out before a replacement is Ready. On a
single-replica deployment that is a guaranteed outage on every deploy.

Ask it to:
1. Set maxUnavailable to "25%" in platform/helm/orders-api/values.yaml.
2. Set replicaCount to 2, so a 25% floor actually leaves a pod serving.
3. Re-render with helm template and report the strategy and replicas blocks.

Nothing else in the file changes, and nothing is applied to the cluster.

What Claude does. It delegates to platform-engineer, which edits values.yaml and asks approval to run helm template — a read-only command that still counts as a Bash call under this posture.

What you observe. Two lines changed, and the second one is the point. maxUnavailable: 25% on a single replica still rounds down to taking the only pod out; the floor is meaningless without the replica count to back it. A repair that changes the number without changing what the number applies to would have graded green and fixed nothing.

Verify the render, not the file:

helm template orders-api platform/helm/orders-api | grep -A4 'strategy:'
helm template orders-api platform/helm/orders-api | grep 'replicas:'
Expected output
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 25%
    type: RollingUpdate
  replicas: 2

Two replicas with a 25% ceiling on unavailability means at least one pod stays in service through any rolling update. The deployment now has a serving floor.

Step 7 — Read the enforcement: RBAC, network policy, admission​

Before you deploy, read what the cluster physically prevents — the enforcement under the intent. First the read-only identity the agent uses by default:

grep -A2 'name: northstar-readonly' platform/kubeconfigs/readonly.yaml | head; echo "---verbs---"; grep 'verbs:' platform/kubeconfigs/readonly.yaml
Expected output
  name: northstar-readonly
rules:
  - apiGroups: ["", "apps", "batch", "networking.k8s.io"]
---verbs---
    verbs: ["get", "list", "watch"]

The read-only ClusterRole grants exactly get, list, watch — no create, update, or delete. This is not a promise the agent will only read; it is an identity the API server will not let write. Bind the agent's kubectl to this and a mutating call is refused at the server, regardless of the agent's intent.

Now the admission-time gate on the namespace:

grep 'pod-security.kubernetes.io/enforce:' platform/policies/pod-security.yaml
Expected output
    pod-security.kubernetes.io/enforce: baseline

The northstar namespace enforces the baseline Pod Security Standard: a pod that violates it is rejected at creation by the API server, before it ever schedules. That is enforcement in its purest form — the object is refused no matter who submits it. Notice how this connects back to Step 2: the non-root image you built is not just tidier, it is the thing that keeps you on the right side of an admission controller as these standards tighten.

Argo CD did the write — you applied the Application definition, and the reconciler applied the rendered chart from the Git remote. That is the split the whole module rests on.

Step 9 — Confirm the agent cannot write to the cluster​

Prove the boundary directly. The agent's most dangerous cluster commands are denied by the Module 8 change gate. Simulate the hook calls the agent's Bash tool would trigger.

Deleting a namespace is blocked:

echo '{"tool_name":"Bash","tool_input":{"command":"kubectl delete namespace northstar"}}' \
  | scripts/hooks/change-gate.sh >/dev/null 2>&1; echo "exit=$?"
Expected output
exit=2

Exit 2 is the block signal. The agent cannot delete a namespace — the blast radius is unbounded and the gate refuses it.

A wildcard mutation across all namespaces is blocked:

echo '{"tool_name":"Bash","tool_input":{"command":"kubectl delete pods -A"}}' \
  | scripts/hooks/change-gate.sh >/dev/null 2>&1; echo "exit=$?"
Expected output
exit=2

Blocked. A mutating kubectl targeting every namespace has no safe blast radius, so the gate denies it.

And docker push from an agent identity is blocked — images ship through CI, not the agent:

echo '{"tool_name":"Bash","tool_input":{"command":"docker push orders-api:latest"}}' \
  | scripts/hooks/change-gate.sh; echo "exit=$?"
Expected output
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"docker push is blocked — images are built and published by the CI pipeline, not from an agent identity. Push code to a branch and let CI build and publish the image."}}
DENIED by change-gate: docker push is blocked — images are built and published by the CI pipeline, not from an agent identity. Push code to a branch and let CI build and publish the image.
exit=2

The structured deny and exit 2 together are what Claude Code reads to refuse the tool call. Read the deny reason closely, because it decides the next step: your Dockerfile repair cannot reach a registry from here. It reaches production the way every application change does — as code on a branch that CI builds.

Step 10 — Propose the repairs on the two change paths​

You are holding two repairs of genuinely different kinds, and the system treats them differently.

gitops-propose.sh is the desired-state path. It stages platform/helm and platform/argocd — the files that describe the intended cluster — and stops. Run it:

scripts/gitops-propose.sh harden-orders-container "Non-root USER + .dockerignore for orders-api; rollout floor maxUnavailable 25% at 2 replicas"
Expected output
==> Preparing GitOps proposal on branch 'propose/harden-orders-container'

Proposed desired-state change:
 platform/helm/orders-api/values.yaml | 4 ++--
 1 file changed, 2 insertions(+), 2 deletions(-)

==> This is the agent's stopping point.
The agent has proposed a change in Git. It has NOT touched any cluster.

Next steps (human / reconciler — NOT the agent):
  1. git commit -m "Non-root USER + .dockerignore for orders-api; rollout floor maxUnavailable 25% at 2 replicas"
  2. git push local HEAD:propose/harden-orders-container      # push proposal to the remote
  3. Open a PR, get change-reviewer approval, merge to main
  4. Argo CD (the reconciler) syncs merged state to the cluster

The reconciler is the only identity that writes to the cluster.

Observe what it staged. One file — values.yaml. Your Dockerfile and .dockerignore are not in that diffstat, and that is not a bug. gitops-propose.sh proposes desired state, and a Dockerfile is not desired state; it is application source that CI turns into an image, exactly as the deny reason in Step 9 said. Two repairs, two paths, one script that knows the difference.

Commit the application change onto the same branch, so one review covers the whole repair:

git add app/orders-api/Dockerfile app/orders-api/.dockerignore
git commit -m "harden orders-api: non-root USER, .dockerignore, rollout floor 25% at 2 replicas"
git push local HEAD:propose/harden-orders-container
Expected output
[propose/harden-orders-container 8095502] harden orders-api: non-root USER, .dockerignore, rollout floor 25% at 2 replicas
 3 files changed, 30 insertions(+), 2 deletions(-)
 create mode 100644 app/orders-api/.dockerignore
To file:///tmp/northstar-remote.git
 * [new branch]      HEAD -> propose/harden-orders-container

Your commit SHA will differ. Three files on one branch: the two application files you just added, plus the values.yaml the propose script had already staged. The proposal is complete and the agent's authority has ended — everything past this line is a human or the reconciler.

Step 11 — Merge and let the reconciler sync​

Play the reviewer and merge. --no-ff keeps the proposal visible as a unit in history, which is what you want a reviewer to be able to point at later:

git checkout main
git merge --no-ff propose/harden-orders-container -m "merge: harden orders-api container and rollout"
git push local HEAD:main
Expected output
Merge made by the 'ort' strategy.

 create mode 100644 app/orders-api/.dockerignore
To file:///tmp/northstar-remote.git
   cfad07b..41619f4  HEAD -> main

Your SHAs will differ. The approved change is now on main in the remote. You did the write to Git; you never touched the cluster.

Argo CD (with syncPolicy.automated) detects the new commit and reconciles. Verify the sync picked it up:

kubectl -n argocd get application orders-api -o jsonpath='{.status.sync.status}{"\n"}'
kubectl -n northstar get deploy orders-api -o jsonpath='{.spec.replicas}{"\n"}'

The deployment now runs 2 replicas — and the reconciler made that change, from merged Git, not you. That is candidate → approval → merge → sync → verify, end to end, with the agent's authority ending at "propose."

What you have now, and what breaks next​

orders-api runs unprivileged, builds from a scoped context, and rolls out with a serving floor — merged on main through a path where the agent proposed and the reconciler wrote. That is the golden path working exactly as designed.

The Deep Dive is what happens when something comes at that path: a release candidate from a long-lived branch, plausible on its face, that would quietly undo two of the repairs you just made. You will diagnose a stalled rollout from evidence alone, tell the trigger from the amplifier, and reject the candidate before it merges rather than repairing the cluster after it does.

Teardown​

Delete the cluster and remove the local Git remote:

kind delete cluster --name northstar
scripts/local-git-remote.sh --clean
Expected output
Deleting cluster "northstar" ...
Deleted nodes: ["northstar-control-plane" "northstar-worker"]
==> Removing existing remote at /tmp/northstar-remote.git...

The cluster and its containers are gone (kind clusters cost nothing when deleted) and the local remote is removed.

Leave the three repairs merged. They are not lab scaffolding — every later module builds on an orders-api that runs unprivileged and rolls out with a floor, and Module 13's release gate compares an incoming candidate against this repaired main. Do not git checkout values.yaml or the Dockerfile to "clean up"; that would undo the work the grader just certified.

Reset to a known state

If anything is in a strange state, scripts/reset.sh m12 returns the workspace to the module's start state, and kind get clusters confirms no stray cluster is left running. Re-running the lab from there is safe.
