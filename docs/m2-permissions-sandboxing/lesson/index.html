Install, Permission Postures & Sandboxing

In Module 1 you ran the diagnose → change → verify loop by hand and decided, task by task, how much of it to hand to the agent. That was the autonomy ladder as judgment. This module turns that judgment into configuration: the actual install, rules, flags, and sandbox that decide what Claude Code is allowed to do on your machine before it does anything at all.

Here is the shift. On the platform team you do not get to supervise every keystroke the agent makes — that defeats the point. Instead you set boundaries once, and the agent operates inside them. Get the boundaries right and the agent is a fast, safe teammate. Get them wrong and you have either a nagging assistant that asks permission for ls, or an unsupervised process holding a shell on your production credentials. This module is how you get them right — starting with getting the tool installed and authenticated the way a team actually runs it.

Install and authenticate: the part you do once​

The Environment setup page already had you install the full toolchain, Claude Code included. This section is the focused version for the one tool this whole course is about, so you understand what you installed and how it knows who you are — not just that a command exists.

Analogy: installing Claude Code is like installing kubectl; authenticating it is like giving it a kubeconfig. The binary is inert until it has credentials, and which credentials you give it decides what it can reach and who pays. You would never confuse "kubectl is installed" with "kubectl is pointed at the right cluster." Same discipline here.

There are three install paths, and which one you pick is an operational decision, not a matter of taste:

  • Native installer — a self-contained binary that manages its own updates. Best for a developer laptop where you want it to stay current on its own.
  • npm global — npm install -g @anthropic-ai/claude-code. Natural if your team already standardizes on Node tooling and manages versions that way.
  • Pinned in an image — for CI runners and containers, you install an exact version in the image build, never a floating "latest." A tool that auto-updates itself inside a pipeline is a supply-chain surprise waiting to happen; pin it like any other build dependency.

Verify the install the same way you verify any CLI, and use the built-in doctor to catch a broken or shadowed binary before it wastes an hour:

claude --version
claude doctor

Authentication is the credential you attach, and it is a governance decision, not just a login:

MethodWhat it usesWhere it fits
Subscription loginYour Claude Pro/Max plan, via interactive /login in the REPLIndividual engineers doing daily work
API keyAn Anthropic Console key (usage-billed)Automation, CI, or when usage must land on a specific billing account
Enterprise (Bedrock / Vertex)Your cloud provider's model endpoint and IAMOrgs that require model traffic to stay inside their AWS/GCP boundary and audit trail

The reason this matters for this module: authentication decides whose account and whose policy the agent runs under, and enterprise auth is exactly where the managed policy at the top of the permission hierarchy comes from. When your org puts Claude Code on Bedrock with a managed settings file, the boundaries you are about to learn stop being suggestions a developer can edit and become policy a developer cannot override. Auth and permissions are the same governance story seen from two ends.

You do not re-authenticate per project

Authentication is machine-level, set once. Permissions, which you configure next, are per-project and per-invocation. Keep the two separate in your head: auth is who the agent is; permissions are what that identity is allowed to do here.

With the tool installed and authenticated, the rest of this module is the three boundaries that decide what it can do.

Why the boundary is the product​

Think about how you already onboard a new engineer. You do not read every command over their shoulder. You give them a role: read access to production, write access to staging, no access to the billing database, and a rule that schema changes go through review. The role is a boundary you set once so you can stop watching and start trusting.

An AI agent needs the exact same thing, for a sharper reason: it acts at machine speed and it does not get tired, bored, or cautious near the end of a long task. A human who is unsure will usually pause. An agent that is unsure will confidently run the command. So the boundary is not a nice-to-have you add later — it is the safety model. Everything else in this course (skills, hooks, subagents, autonomous incident response) sits on top of the permission layer you configure here.

There are three separate boundaries, and confusing them is the single most common way people get this wrong:

  1. What tools the agent even has — availability.
  2. What it can do without asking you — auto-approval, governed by permission rules.
  3. What the shell it runs is physically prevented from touching — the sandbox.

The rest of this lesson is those three boundaries, one at a time, and how they compose.

The permission hierarchy: whose rule wins​

Analogy: think about firewall or IAM policy evaluation. You do not have one flat list of rules; you have layers — an org-wide policy, a team policy, a per-service policy — and a precedence order that decides which one wins when they disagree. A deny at the org level beats an allow at the service level, every time, because the whole point of the org policy is that a service owner cannot punch a hole in it.

Claude Code's permissions work the same way. Rules come from several places, and they stack in a fixed precedence:

Higher in the diagram wins. Enterprise managed settings sit at the top precisely so that no project file and no CLI flag a developer types can override a boundary the organization set — the same reason an org SCP in AWS beats an account admin.

Within any one settings file, permissions are three arrays — allow, ask, and deny — and they have their own precedence that you must commit to memory:

{
  "permissions": {
    "allow": ["Read", "Bash(git status:*)", "Bash(git diff:*)"],
    "ask":   ["Bash(git push:*)"],
    "deny":  ["Bash(rm -rf:*)", "Read(./.env)", "WebFetch"]
  }
}

deny beats ask beats allow. If a command matches a deny rule, it is refused — even if it also matches an allow rule. This ordering is what makes deny trustworthy: you can hand out a broad allow for convenience and still be certain a deny on rm -rf or on reading .env can never be overridden by it. A boundary you can poke a hole in is not a boundary.

Why deny-wins is the whole game

When you write allow: ["Bash(git:*)"] for convenience and deny: ["Bash(git push:*)"] for safety, you are trusting that the narrow deny wins over the broad allow. It does. Every safe broad-allow you will write in this course depends on that guarantee — internalize it now.

How a rule matches a command​

The rule Bash(git status:*) is not a regex — it is a prefix pattern. The part before the : is matched literally against the start of the command; the :* means "and any arguments after that." So:

  • Bash(git status:*) matches git status, git status -s, git status --short — but not git push.
  • Bash(npm run test:*) matches npm run test and npm run test -- --watch.
  • Bash(git status) with no :* matches only the exact command git status, nothing with arguments.

For file tools, the specifier is a path glob: Read(./secrets/**) matches any read under secrets/, and putting it in deny walls that directory off from the agent entirely, no matter what else it is allowed to read.

The important habit: write deny rules against the capability, not the phrasing. deny: ["Bash(curl:*)"] stops curl, but an agent that wants network access can reach for wget, nc, or a Python one-liner. Deny lists catch the obvious; they are a backstop, not the primary control. The primary control for "no network" is the sandbox, which we get to below — because it stops the capability, not a spelling of it.

Permission postures: matching the ask to the task​

The permission rules say what is allowed. The posture — Claude Code calls it the permission mode — says how eagerly the agent proceeds through the things that would otherwise prompt you. Same rules, different amount of interrupting.

Analogy: this is the driver-assistance ladder from Module 1, made concrete. Cruise control still obeys the speed limit (the rules) — what changes between assistance levels is how much it does before it asks you to take over. You pick the level by how much can go wrong on this stretch of road, not by how capable the car is.

You select the posture with --permission-mode <mode>, and the mode names are exact: default, acceptEdits, plan, auto, dontAsk, bypassPermissions. They form a ladder from "asks about almost everything" to "asks about nothing."

PostureWhat it auto-approvesWhat it still gatesGood fit
planNothing — it cannot edit or runThe whole point: it produces a plan and touches nothingScoping an unfamiliar change before you let it act — the safest way to "ask the agent what it would do"
defaultOnly what your allow rules already coverEverything else prompts youThe daily driver — agentic work where you review each new kind of action
acceptEditsFile edits (Write/Edit)Bash and anything with side effects still promptRefactors and doc edits where the risk is in running things, not writing them
auto / dontAskEvery action except what deny blocksOnly deny rules stop it — nothing promptsBounded, well-understood loops where your deny list is the whole safety net
bypassPermissionsEvery action not on the deny list — including the destructive ones you never thought to denyOnly deny still holds; allow, ask, and all prompts are goneAlmost never. Ephemeral throwaway sandboxes only — never a repo with real credentials

Map these straight back to Module 1's ladder: plan and default are agentic (you stay in the loop on each new action), acceptEdits is a calibrated grant for a low-risk class of action, and auto/dontAsk/bypassPermissions are all autonomous — the agent acts without asking. The difference among the autonomous modes is subtle and worth pinning down precisely: all of them still honor deny (in current Claude Code, a deny on rm holds even under bypassPermissions — you will verify this). What bypassPermissions removes is every other check — the allow gate, the ask gate, and the trust prompts — so the agent will run anything you did not explicitly deny.

Why bypassPermissions is still dangerous even though deny holds

It is tempting to conclude "deny still works, so bypass is fine." It is not. deny only protects the commands you anticipated. Under default or auto, an unanticipated destructive action still hits a prompt or an allow-check; under bypassPermissions, the only thing standing between the agent and a command is whether you happened to list it in deny ahead of time. You cannot enumerate every dangerous command in advance — that is precisely why you keep the allow/ask gates. Use auto behind a deliberate deny when a loop is genuinely repetitive; reach for bypassPermissions only in a disposable sandbox where "it runs anything not denied" cannot hurt you.

Availability vs. auto-approval: the misconception that bites​

This is the distinction that catches nearly everyone, so it gets its own section.

There are two independent questions about any tool:

  1. Is the tool available at all? — can the agent use it if it wants to?
  2. Is the tool auto-approved? — can it use it without asking you?

These are controlled by different mechanisms, and the flag names actively invite the confusion:

  • --allowedTools Read,Edit answers question 2. It says "auto-approve Read and Edit." It does not say "and remove every other tool." Bash is still available — it will simply prompt before each use instead of running silently.
  • To answer question 1 — to actually take a tool away so the agent cannot use it even with your approval — you use --disallowedTools, or a deny rule in settings. That is removal. That is a boundary.

Analogy: --allowedTools is a fast-pass lane at the airport — it lets certain people skip the line. It does not close the other lanes. Everyone else still gets through; they just wait for a check. If your goal is that a tool can never be used, a fast-pass for two other tools does nothing — you need to close the lane (--disallowedTools / deny), not speed up a different one.

The trap in one sentence: --allowedTools is a convenience (fewer prompts), not a restriction (fewer capabilities). If you hand someone a config with --allowedTools Read,Edit believing you have built them a read-and-edit-only agent, you have built no such thing — you have built an agent that can still run any shell command, and merely pauses to ask first. On a bypassPermissions posture, it would not even pause. You will prove this to yourself in the lab, because reading it is not the same as watching Bash still be there after you thought you removed it.

The sandbox: stopping the capability, not the spelling​

Permission rules gate tools. But a single tool — Bash — is a universal escape hatch: it can reach the network, write outside the project, read your SSH keys. You cannot enumerate every dangerous command as a deny rule, because the agent can always phrase the same capability a new way. deny curl does not stop wget.

So the last boundary is not a rule about commands — it is a wall around capabilities. Claude Code can run Bash commands inside a sandbox ("sandbox": { "enabled": true } in settings) that restricts them at the operating-system level: the process cannot reach the network, and cannot write outside the project directory, no matter what command produced the attempt. Network egress is cut off by routing all outbound traffic through a proxy that refuses it — so a curl inside the sandbox does not get a socket error, it gets a proxy refusal (curl: (56) CONNECT tunnel failed, response 403), which is the sandbox talking.

Analogy: this is the airlock on a biosafety lab, not the sign on the door. A sign that says "do not remove samples" (a deny rule) depends on everyone reading and obeying it. An airlock physically prevents anything from leaving. When you are dealing with a fast, literal agent that treats your deny list as a puzzle to route around, you want the airlock.

Two properties make the sandbox trustworthy rather than decorative:

  • Filesystem + network isolation. The sandboxed shell can read and write inside the working directory but is blocked from writing elsewhere and from reaching the network — and "the network" includes localhost, so even a curl to a service on your own machine is refused. That strictness is the point: it is precisely the blast radius you want around an agent doing local code work, which cannot exfiltrate a secret or phone home. (When a sandboxed step does need a specific host, you grant it explicitly rather than dropping the wall — covered in the Deep Dive.)
  • Fail-closed. This is the property that separates a real security control from a comforting one. If the sandbox cannot be applied — an unsupported platform, a misconfiguration, a missing dependency — the command is denied, not quietly run unsandboxed. A fail-open sandbox is worse than none, because it gives you confidence exactly when the protection has silently vanished. Northstar's posture, and yours, is fail-closed: no sandbox, no command.
Sandbox and permissions are layers, not alternatives

The sandbox does not replace permission rules; it backs them. Permissions decide which tools and commands the agent may attempt; the sandbox decides what those commands can physically reach when they run. A command can be allowed by your rules and still be stopped by the sandbox the moment it tries to reach the network. Defense in depth: the rule is the policy, the sandbox is the enforcement floor.

Putting the three boundaries together​

You now have the full picture. Every action the agent attempts passes through three gates in order, and any one of them can stop it:

The three gates are independent on purpose. Availability decides the toolbox. Permissions decide the paperwork. The sandbox decides the physics. A safe agent configuration sets all three deliberately — and the failure you will study in the Deep Dive is what happens when someone sets one and assumes it covered the other two.

What you'll do in the lab​

You will make these boundaries real against the Northstar Commerce workspace. You will inspect and extend the project's .claude/settings.json; run the same read-only diagnostic task under three postures and watch the prompting change; add a deny rule and prove it overrides a matching allow; hand yourself the classic --allowedTools misconception and watch Bash still be there; and turn on the Bash sandbox and watch a network attempt get refused fail-closed. Finally you will take the follow-on tasks from Module 1's autonomy ladder and choose the posture each one earns — turning last module's judgment into this module's configuration.

The boundary is the product. By the end of the lab you will have configured it, not just read about it.
