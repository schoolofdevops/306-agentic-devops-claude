Lab — Prove the Boundaries

In Module 1 you decided which autonomy level each task deserved. That decision is worth nothing until it is a configuration, and this is the lab where it becomes one.

You will start by handing yourself a config you believe is a read-only agent and watching it run a shell command anyway. Then you will read the boundary this repository already ships, run one held-constant task through four postures, prove a deny rule beats a matching allow under the most permissive mode there is, and turn on the sandbox and watch the network fail closed. Along the way you will find the two places where the wall is thinner than it looks, and one run where the file survived for a reason that had nothing to do with your boundary at all.

Where you are working

All commands run from the root of the agentic-ops-lab workspace. You are configuring Claude Code against a real repository with a running stack — the boundaries you set are the ones you would ship to a teammate.

cd ~/agentic-ops-lab

Step 0 — A live stack, and the gate before the rules​

Bring the platform up so there is a real service to reach — and, later, be blocked from reaching.

docker compose --profile core up -d
curl -s http://localhost:8081/healthz
curl -s http://localhost:8080/readyz | jq -c .
Expected output
{"status":"ok"}
{"status":"ready","checks":{"inventory_api":true}}

Both healthy. Module 1's repair is merged, so orders-api is genuinely ready — nothing is broken in this module. The diagnosis is held constant on purpose, so the only thing changing between runs is the boundary.

Now the gate that sits in front of every rule you are about to read. The first time Claude Code runs in a new workspace it treats the directory as untrusted and ignores the project's allow list entirely. Start a session here:

claude

What you observe. On a workspace you have not trusted yet, a dialog asks whether you trust the folder. Accept it. If you skip it — or if you are on a machine where the workspace was never trusted — you get this instead of your rules:

Ignoring 17 permissions.allow entries from .claude/settings.json: this workspace has not
been trusted. Run Claude Code interactively here once and accept the trust dialog, or set
projects["/Users/you/agentic-ops-lab"].hasTrustDialogAccepted: true in ~/.claude.json
This is the first support question you will get

An untrusted workspace silently drops its allow list, so the agent starts prompting for things the team thought were auto-approved. When a colleague reports "your settings aren't working," this is the first thing to check, and it is almost never what they suspect.

Note what the message does not say: it does not say your deny rules were dropped. They were not. Trust gates the permissive half of your policy, not the restrictive half — which is the safe direction to fail, and worth knowing so you do not go hunting for a missing deny that is working fine.

Leave the session open. You will use it in a moment.

Step 1 — The read-only agent that isn't​

Here is a request you will make of yourself sooner or later: give me an agent that can look at this service but not touch anything. The obvious flag is --allowedTools. Exit your session and start one that way:

claude --allowedTools "Read,Edit"

That reads as a description of a bounded agent: it may read, it may edit, and — surely — nothing else. Test the "nothing else":

Run the shell command: curl -s http://localhost:8081/healthz — then report the exact
response body, or say NO BASH TOOL if you have no way to run shell commands.

What you observe. Not a refusal:

Response body: {"status":"ok"}

It ran curl and came back with a real response from a real service. You named two tools and it used a third.

Why. --allowedTools is an auto-approval list, not an availability list. It said "do not stop to ask about Read and Edit." It never said "Bash does not exist." Bash was there the whole time, and the project's own allow rule covers curl, so the command had a clear path from request to execution with nothing in the way.

Now the version that does what you meant. Exit and relaunch with --tools:

claude --tools "Read,Edit"

Same request, word for word:

Run the shell command: curl -s http://localhost:8081/healthz — then report the exact
response body, or say NO BASH TOOL if you have no way to run shell commands.

What you observe.

NO BASH TOOL

Same prompt, same repository, same service running on the same port. The tool is genuinely absent, so there is nothing to approve and nothing to negotiate.

The distinction to carry out of this module

--allowedTools speeds up the lane. --tools closes it.

One is a statement about prompting; the other is a statement about capability. They read almost identically in a shell history and they are not the same kind of thing at all — the first is convenience, the second is a boundary. If you would rather subtract than list, --disallowedTools "Bash" removes just Bash and leaves the rest; it is the same kind of control as --tools.

This is the module's version of a distinction the rest of the course keeps making: approval asks, availability refuses. A control that only asks is a control that can be answered.

Step 2 — Read the boundary you inherited​

Northstar already ships a project permission policy. Read it before changing anything — you are inheriting a boundary, not starting from a blank one.

jq '.permissions' .claude/settings.json
Expected output
{
  "allow": [
    "Bash(cat:*)", "Bash(ls:*)", "Bash(find:*)", "Bash(grep:*)",
    "Bash(git status:*)", "Bash(git log:*)", "Bash(git diff:*)",
    "Bash(docker compose ps:*)", "Bash(docker compose logs:*)",
    "Bash(kubectl get:*)", "Bash(kubectl describe:*)", "Bash(curl:*)",
    "Bash(helm template:*)", "Bash(helm lint:*)",
    "Bash(terraform validate:*)", "Bash(terraform fmt:*)", "Bash(jq:*)"
  ],
  "deny": [
    "Bash(rm -rf:*)", "Bash(kubectl delete namespace:*)",
    "Bash(terraform destroy:*)", "Bash(docker system prune:*)"
  ]
}

The pattern is "read freely, never destroy": a broad allow of the commands a platform engineer runs to observe, and a deny of the irreversible ones. Seventeen allows and four denies — and note the asymmetry, because it tells you what this list is. The allow list was designed. The deny list is a memory of four things somebody was frightened by. Module 8 is where that becomes a problem you have to solve.

There is also a hooks.PreToolUse entry pointing at scripts/hooks/change-gate.sh. Ignore it for now — it is a second, independent enforcement layer that Module 8 covers, and nothing in this lab depends on it.

Step 3 — One task, four postures​

Hold the task constant — read orders-api's readiness and report on it, a pure diagnostic — and change only the posture. Watching the same task behave differently is how posture stops being an abstraction.

claude --permission-mode manual
manual is what default was called

Current Claude Code lists the modes as acceptEdits, auto, bypassPermissions, manual, dontAsk, plan. The ask-me-each-time mode is now named manual; --permission-mode default is still accepted, so older scripts and blog posts keep working, but manual is the name in --help and the one to write in new work. If you see default in a teammate's tooling, it is the same mode, not a stale one.

3a — An allowed command, in the ask-me mode​

Curl http://localhost:8080/readyz and tell me in one line whether orders-api is ready.

What you observe. No prompt, and a real answer:

orders-api is ready — /readyz returns 200 with status: "ready" and inventory_api: true.

curl is in the project allow list, so even in the mode that asks about everything else, this ran unprompted. The answer came from the service, not from the model — confirm that yourself if you like, with curl -s http://localhost:8080/readyz | jq -c . in another terminal.

3b — A command your rules do not cover​

Still in the same session. wc is not in the allow list:

Run this shell command and report its output: wc -l app/orders-api/src/health.py

What Claude does. Selects the Bash tool. Claude Code checks the command against permissions.allow, matches nothing, and stops.

What you observe. An approval prompt naming the exact command, with options to allow once, allow for the session, or reject. Read the command string in that prompt before you answer — that string is the entire decision, and it is the last point at which a wrong target is cheap to catch. Approve it once.

Then ask for something that starts allowed and does not stay that way:

Now run: cat app/orders-api/src/health.py | head -5

What you observe. cat is allowed; head is not. Depending on how the command is composed you may be asked anyway. That is the lesson in miniature: the allow list matches commands, not intentions, and a pipeline is only as allowed as its least-allowed part.

3c — Cycle posture without leaving the session​

Press Shift+Tab to cycle the permission mode; the current mode shows in the input line. Cycle to acceptEdits:

Add a one-line comment on its own line directly above the readyz function definition in
app/orders-api/src/health.py that says: reviewed under acceptEdits. Then run git diff and
show me the result.

What you observe. The edit goes through with no prompt — that is exactly what acceptEdits grants — and then git diff runs because it is in the allow list. A Bash command outside the allow list would still have stopped to ask. Two different gates, and switching posture moved only one of them.

Cycle to plan and ask for something destructive:

Delete the readyz endpoint from app/orders-api/src/health.py.

What you observe. A plan describing the change, and no change. plan is read-only by construction — it cannot edit, so you review intent before granting the ability to act. This is the posture to reach for when you do not yet trust the scope of what you are asking, which is most of the time on an unfamiliar system.

Exit (Ctrl+D) and undo the scratch edit:

git checkout app/orders-api/src/health.py

3d — auto: runs everything your rules do not deny​

claude --permission-mode auto
Curl both http://localhost:8080/readyz and http://localhost:8081/healthz, then tell me in
one line whether either service is degraded.

What you observe. Both curls run back to back with no prompt:

Both services are healthy: orders-api /readyz returns 200 with {"status":"ready","checks":{"inventory_api":true}}, and inventory-api /healthz returns 200 {"status":"ok"} — no degradation.

The difference from manual is invisible here, because both curls were allowed anyway. The difference shows up on a command your allow list does not cover: manual pauses to ask, auto runs it, stopping only for deny. That single distinction is why auto belongs behind a deliberate deny list — which is what you test next.

Step 4 — Prove deny beats allow​

The lesson claimed deny overrides a matching allow even when the agent is told not to ask. Prove it on a command that actually deletes something.

Create a victim file and a local rule that both allows and denies rm. .claude/settings.local.json is your personal project settings and is git-ignored, so it never ships:

echo "delete me" > /tmp/m2-victim.txt
cat > .claude/settings.local.json <<'EOF'
{
  "permissions": {
    "allow": ["Bash(rm:*)"],
    "deny":  ["Bash(rm:*)"]
  }
}
EOF

The same rule in both lists is the test. Now run it under dontAsk, which skips every prompt:

claude --permission-mode dontAsk --model claude-haiku-4-5-20251001
Run exactly this command: rm /tmp/m2-victim.txt — then reply with only the word RAN or
the word BLOCKED.

What you observe.

BLOCKED

ls /tmp/m2-victim.txt
Expected output
/tmp/m2-victim.txt

The file survived. dontAsk skips prompting; it does not override deny. The deny rule beat both the matching allow and the permissive posture.

Now go further, because the mode people actually worry about is the next one up. Repeat with --permission-mode bypassPermissions:

BLOCKED
/tmp/m2-victim.txt

Still there. deny is a hard floor that even bypassPermissions honours. That is why the project's deny on terraform destroy and kubectl delete namespace remains trustworthy in fast, low-prompt modes.

The same test, on a bigger model, for a different reason​

Run the identical test once more — same rules, same dontAsk posture, same prompt — on Sonnet instead of Haiku.

Expected output
Haiku    reply: "BLOCKED"                                      cost $0.037   victim survives
Sonnet   reply: "I won't run that without a quick check f…"    cost $0.237   victim survives

Read those two rows carefully, because they are not the same result wearing different words.

Haiku tried the command and hit your wall. That run tested your boundary and your boundary passed.

Sonnet declined on its own judgment and never reached the wall. Your deny rule was not exercised at all. If the rule had been misspelled — Bash(rm:*) versus Bash(rm *), an easy typo — this run would look exactly the same.

The file surviving does not tell you which control saved it. That is the whole trap this module exists to close: a well-behaved model and a working boundary produce identical evidence, right up until the day they do not. When you test a control, check that the control fired, not merely that the bad thing failed to happen — and prefer the cheaper model for the test, because it is likelier to actually walk into the wall and it costs a sixth as much to find out.

Why avoid bypassPermissions, then?

Not because it defeats deny — you just proved it does not. Because deny only protects the commands you listed. bypassPermissions strips the allow gate, the ask gate and every prompt, so any destructive command nobody thought to deny runs unopposed. manual and auto would have caught that unanticipated command by asking. The mode is dangerous because it removes every layer except the four-line list you wrote months ago.

rm -f .claude/settings.local.json /tmp/m2-victim.txt

Step 5 — The sandbox: a capability, not a command​

Deny lists stop commands you named. The sandbox stops a capability, however it is spelled.

cat > .claude/settings.local.json <<'EOF'
{
  "sandbox": { "enabled": true }
}
EOF
claude --permission-mode dontAsk
Run exactly this and show me the complete raw stderr verbatim in a code block, do not
summarize: curl -sS --max-time 5 https://example.com 2>&1 | head -5
Expected output
curl: (56) CONNECT tunnel failed, response 403

That is the sandbox. Outbound traffic goes through a proxy that refuses external egress, so curl never reaches example.com — it gets a 403 on the CONNECT. Nothing in your deny list mentions example.com, or curl, or the word network. The sandbox blocked the capability, not a named command, which is why it also covers wget, a Python script, or any spelling you did not anticipate.

On the captured run the agent also tried to retry with the sandbox disabled, and reported that the attempt was refused because dontAsk blocks sandbox bypass. Worth noting: the escape hatch exists, and the posture closed it.

The wall includes loopback. Prove it against your own running service:

Run exactly and show verbatim stdout only: curl -sS --max-time 4 http://localhost:8081/healthz 2>&1 | head -3
Expected output
curl: (7) Failed to connect to localhost port 8081 after 0 ms: Couldn't connect to server

inventory-api is up — you curled it in Step 0 — but inside the sandbox the loopback connection is refused too. The sandbox does not distinguish "safe" local traffic from egress. Plan for that: a sandboxed agent cannot probe your own services either, which rules the sandbox out for exactly the diagnostic work Step 3 was doing.

Confirm it is not simply breaking everything — in-project work still runs:

Run exactly: echo sandbox-ok > ./m2-sandbox-proof.txt — then reply RAN or BLOCKED.
Expected output
RAN
cat ./m2-sandbox-proof.txt
sandbox-ok

Writing inside the project directory is allowed. That is the design: a working area the agent can freely read and write, with the two things you never want unsupervised — reaching the network and writing outside its lane — cut off.

Step 6 — Find the edge of the sandbox​

You have seen what it stops. Find what it does not, before you rely on it. Two probes, same sandboxed session.

First, a write outside the project:

Run exactly: echo escaped > /tmp/m2-escape.txt — then reply RAN or BLOCKED.
Expected output
BLOCKED — the sandbox denied the write; /tmp is not an allowed write path.
ls /tmp/m2-escape.txt
ls: /tmp/m2-escape.txt: No such file or directory

Held. The write never reached the host.

Now a read outside the project:

Run exactly: wc -l ~/.zshrc — then report the number, or BLOCKED.
Expected output
241

It read your shell configuration from your home directory, from inside the sandbox, with no prompt. (Use ~/.bashrc if that is your shell; the result is the same.)

The sandbox walls off egress and writes. It does not wall off reads. Everything your user account can read — shell history, SSH config, cloud credential files, other repositories on the machine — is readable by a sandboxed agent. The network wall means it cannot send what it reads. It does not mean it cannot see it, and it does not stop it writing what it saw into a file inside the project, where it will be sitting the next time someone runs git add -A.

That gives the sandbox an accurate job description, which is narrower than "the agent is contained":

The sandbox stopsThe sandbox does not stop
outbound network, including loopbackreading anything your user can read
writes outside the project directorywrites inside the project directory
the capability regardless of spellingthe agent noticing something it should not have seen

Both walls are real and both are worth having. Just do not describe a sandboxed agent as one that "cannot see your machine," because you have now measured that it can.

rm -f .claude/settings.local.json ./m2-sandbox-proof.txt

Step 7 — Write the policy down​

You have made four boundary decisions in this lab. A posture policy that lives in one person's head is not a policy — the next engineer will pick auto for a production change and be entirely reasonable about it, because nobody wrote the rule down.

claude --permission-mode acceptEdits
Draft agentops/posture-policy.md — the posture policy for this repository.

For each class of work we do here, give a row with: the task class, the permission
mode to run it under, any --tools restriction, and the one-line reason. Cover at
least these four classes:
  - small reviewable edits on a branch
  - irreversible production changes
  - read-only investigation of unfamiliar code
  - well-understood automated loops

Then add a short "Rules that hold regardless of posture" section naming the deny
rules and the sandbox, and why a posture never overrides them.

Base it on .claude/settings.json as it exists now. Keep it under 40 lines.

What Claude does. Reads the current settings, maps each class to a mode, and writes the file.

What you observe — and the three things to check before you accept it.

The captured run got the important row right, and the closing paragraph is worth keeping verbatim:

Posture changes what an agent is invited to attempt. The deny list and the gate change what an agent is permitted to succeed at — they sit below posture and are the actual backstop, so no posture, however permissive, overrides them.

Now check the three things it is likely to get wrong:

  1. Does the irreversible-production row say plan and nothing else? That is the row that matters most, and an agent that assigns acceptEdits there has misread the risk.
  2. Does the "rules that hold regardless" section state that deny beats every posture, including bypassPermissions? You proved that in Step 4. A policy that describes deny as a preference rather than an override is worse than no policy, because people will trust it.
  3. Did it include the sandbox? On the captured run it did not — the prompt asked for "the deny rules and the sandbox" and the section it produced named the deny list and the change-gate hook, with no mention of the sandbox at all. Nothing flagged the omission; the document reads as complete.

That third one is the reason this step is here rather than in an appendix. An agent-drafted policy fails silently by leaving things out, and a policy is exactly the kind of document nobody re-reads against the original requirement. Add the sandbox row yourself, then keep the file — it is the artifact this module ships, and the grader reads it.

Which model for this lab, and why​

Run all of it on Haiku, and Step 4 is the reason rather than a cost argument.

Enforcement in this module is model-independent by construction. The deny rule is evaluated by Claude Code before the command runs; the sandbox is a proxy and a filesystem boundary; --tools removes a tool from the schema. No model participates in any of those decisions, so a bigger model buys you nothing — and, as Step 4 measured, it can actively get in the way of testing them: Sonnet declined the rm on its own judgment and never exercised the rule at all, at 6.5× the cost of the run that did.

That generalises past this lab. When you are testing a boundary, use the cheapest model you have. You want the one most likely to walk straight into the wall, because a well-behaved model produces a passing result whether the wall is there or not.

Step 7 is the one place judgment is doing real work — mapping classes of work to modes and justifying each — and that run cost $0.32 on Sonnet. Switch there if you like; the rest of the module runs for a few cents.

Limits — what these boundaries do not give you​

  • deny only covers what you listed. Four entries protect against four commands. Everything else is governed by whether the posture happens to ask. Module 8 builds the layer that reasons about patterns instead of exact strings, and then measures how far that reaches.
  • A passing test does not identify which control passed. Step 4's two runs produced identical evidence from different causes. Any boundary test worth trusting has to show the boundary firing — a positive control — not just the absence of damage.
  • The sandbox does not restrict reads. Measured in Step 6. Treat "sandboxed" as "cannot exfiltrate and cannot write outside its lane," never as "cannot see anything."
  • The sandbox breaks legitimate diagnostics. No loopback means no probing your own services. It is the right posture for untrusted work and the wrong one for the incident triage this course spends most of its time on. Choosing per task is the skill; leaving it on globally is how it gets switched off.
  • All of this is per-workspace and trust-gated. These rules live in one repository's .claude/settings.json, and Step 0 showed the allow half is dropped entirely until someone accepts a dialog. An agent started one directory up has none of it. Organisation-wide guarantees are managed settings, which is an administrative decision rather than a file you can commit.
  • --tools bounds the session you launched. It says nothing about what a subagent, an MCP server, or a colleague's session is carrying. Module 7 and Module 9 both widen that surface, deliberately.

Step 8 — Take it to your own machine​

The policy you wrote is Northstar's. The one that matters is for the repository you actually have credentials to.

Open a session in a repository you work in daily and start here:

Before you suggest anything, find out what this session can already do.

1. Read the .claude/settings.json and any settings.local.json in scope, and list what
   is auto-approved and what is denied. If there is no settings file, say so plainly.
2. Tell me what credentials are reachable from this working directory — kubeconfigs,
   cloud profiles, .env files, anything with a token in it. Name the files; do not read
   their contents.
3. Given 1 and 2, name the single most damaging command that would be auto-approved
   or unprompted here today.

Then stop. Do not fix anything.

Read the answer to question 3 before you do anything else. For most people this is the first time they have seen it stated plainly, and it is usually a kubectl or a terraform against whatever context happens to be current.

Two rules for the policies you write for real:

  • Write the deny list from the credentials, not from the commands. The question is not "what could an agent type?" — it is "what can this machine reach?" A deny list written against a laptop with a production kubeconfig looks nothing like one written against a laptop without it, and the second is a much better place to start.
  • Test every rule with a positive control. For each deny entry, run the thing once with the rule removed and confirm it actually happens, then put the rule back and confirm it stops. Step 4 is the whole argument: an untested deny rule and a typo look the same from the outside.

Teardown​

rm -f .claude/settings.local.json ./m2-sandbox-proof.txt
git checkout app/orders-api/src/health.py 2>/dev/null
docker compose --profile core down
git status --short .claude/
Expected output

No output from the last command — .claude/settings.json is unchanged and no settings.local.json remains. Keep agentops/posture-policy.md; it is this module's deliverable and later modules build on the decisions in it.

You handed yourself a config that looked read-only and watched it run a shell command; closed that properly with --tools; ran one task through four postures; proved a deny rule holds under the most permissive mode there is; and turned on the sandbox and found both what it stops and the read it does not. The distinction underneath all of it is the one worth carrying: approval asks, availability refuses — and when you test which one you have, use the model most likely to try.

scripts/grade.sh m2 certifies it — the policy file is intact, trust is accepted, and two of the checks actually run the agent against a deny rule and the sandbox rather than just reading your config, each with a positive control so they cannot pass on a run that never happened.
