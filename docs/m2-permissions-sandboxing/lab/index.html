Lab — Prove the Boundaries

In Module 1 you ran the loop by hand and classified which autonomy level each task deserved. This lab makes that classification enforceable. You will run the same read-only diagnostic task under different permission postures, watch a deny rule override a matching allow, catch the --allowedTools misconception in the act, and stand up the Bash sandbox and watch it refuse network access fail-closed.

Most steps here run Claude Code non-interactively with claude -p ("print" mode: it runs the prompt to completion and exits), so enforcement shows up as plain terminal output you can read and grade. Step 2 breaks that on purpose and runs interactively, because -p has nobody to ask — an un-allowed command comes back as a refusal, and the approval prompt itself, the thing this module is actually about, never appears on screen. You need to see it once.

Where you are working

All commands run from the root of the agentic-ops-lab workspace. You are configuring Claude Code against a real repository with a running stack — the boundaries you set are the same ones you would ship to a teammate.

Step 0 — Prerequisites and trust​

Confirm Claude Code is installed and authenticated, then bring up the core stack so there is a live service for the agent to reach (and, later, be blocked from reaching).

claude --version
Expected output
2.1.197 (Claude Code)

Your version will differ — anything recent is fine. If claude is not found, revisit the Environment setup page. claude doctor gives a fuller install/auth health view if you want to double-check authentication.

Start the platform so inventory-api answers on 8081:

docker compose --profile core up -d
curl -s http://localhost:8081/healthz
Expected output
{"status":"ok"}

A clean ok means the dependency the agent will probe is live. If the port is not answering, give the containers a few seconds and re-run the curl.

The first time Claude Code runs in a new workspace, it treats the directory as untrusted and ignores the allow rules in the project's .claude/settings.json until you accept the trust dialog. Trigger and accept it once so the project's permission rules actually take effect:

claude -p "Reply with the single word: trusted" --permission-mode default
Expected output

The first run prompts you to trust the folder — accept it. After that, the command returns:

trusted

If you instead see a line beginning Ignoring 17 permissions.allow entries from .claude/settings.json: this workspace has not been trusted, the trust dialog was not accepted. Run claude interactively in this directory once, accept the trust prompt, then re-run the command.

Trust is the gate before rules even load

This is a real behavior worth internalizing: an untrusted workspace silently drops its allow list, so the agent prompts for things you thought you had auto-approved. If a teammate reports "your settings aren't working," the first thing to check is whether they accepted trust for that folder.

Step 1 — Read the boundary you inherited​

Northstar already ships a project permission policy. Read it before you change anything — you are inheriting a boundary, not starting from a blank one.

cat .claude/settings.json
Expected output
{
  "permissions": {
    "allow": [
      "Bash(cat:*)",
      "Bash(ls:*)",
      "Bash(find:*)",
      "Bash(grep:*)",
      "Bash(git status:*)",
      "Bash(git log:*)",
      "Bash(git diff:*)",
      "Bash(docker compose ps:*)",
      "Bash(docker compose logs:*)",
      "Bash(kubectl get:*)",
      "Bash(kubectl describe:*)",
      "Bash(curl:*)",
      "Bash(helm template:*)",
      "Bash(helm lint:*)",
      "Bash(terraform validate:*)",
      "Bash(terraform fmt:*)",
      "Bash(jq:*)"
    ],
    "deny": [
      "Bash(rm -rf:*)",
      "Bash(kubectl delete namespace:*)",
      "Bash(terraform destroy:*)",
      "Bash(docker system prune:*)"
    ]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "$CLAUDE_PROJECT_DIR/scripts/hooks/change-gate.sh"
          }
        ]
      }
    ]
  }
}

Notice the pattern: a broad allow of read-only and diagnostic commands (the things a platform engineer runs to observe), and a deny of the irreversible ones (rm -rf, kubectl delete namespace, terraform destroy). This is the "read freely, never destroy" posture — auto-approve observation, hard-stop demolition.

There is also a hooks.PreToolUse entry wired to scripts/hooks/change-gate.sh — ignore it for now. It is a second, independent enforcement layer (a hook that runs its own logic before every Bash call, on top of the allow/deny rules above) that Module 8 covers in depth. Nothing in this lab depends on it.

This is exactly the boundary Module 1's autonomy ladder implies: diagnostic work is agentic (auto-approved), destructive work is manual (blocked outright). Now you will watch it behave.

Step 2 — The same task, four postures​

Here is the task you will hold constant: read orders-api's readiness and report on it — a pure diagnostic. What changes is the posture. Watching the same task behave differently under different modes is how the posture concept stops being abstract.

Module 1's repair is merged, so orders-api is genuinely ready here and every honest readiness answer below says so. You are not hunting a bug in this module — the diagnosis is held constant on purpose, so that the only thing changing between runs is the posture.

2a — default mode: allowed commands run, the rest would ask​

claude -p "Curl http://localhost:8080/readyz and tell me in one line whether orders-api is ready." --permission-mode default
Expected output
orders-api ready — 200, deps ok.

curl is in the project allow list, so under default it ran without prompting and the agent answered from real output. Wording varies run to run; what is fixed is that the allowed curl ran unprompted and the answer came from the service rather than from the model's guess.

Confirm the agent is not inventing that answer — ask the service yourself:

curl -s http://localhost:8080/readyz | jq -c .
{"status":"ready","checks":{"inventory_api":true}}

Same verdict, from the same source. Had the agent reached for a command not in the allow list, default would have stopped to ask — and in -p mode there is nobody to ask, so it declines instead of hanging. That limitation is the whole reason the next part of this step runs interactively.

2b — Watch a real approval prompt (interactive)​

Everything so far ran headless, and headless can never show you the thing this module is about. -p has nobody to ask, so an un-allowed command comes back as a refusal — you see the outcome of the boundary but never the boundary itself. Start an interactive session:

claude --permission-mode default

Now ask for something the project allow list does not cover. wc is not in it:

Run this shell command and report its output: wc -l app/orders-api/src/health.py

What Claude does. It selects the Bash tool, and Claude Code checks the command against permissions.allow before running it. wc matches nothing, so instead of executing, it stops and asks you.

What you observe. An approval prompt naming the exact command it wants to run, with options to allow it once, allow it for the rest of the session, or reject it. Read the command in the prompt before answering — that string is the entire decision. Approve it once and the command runs; the agent reports the line count.

Ask again, this time for something in the allow list:

Now run: cat app/orders-api/src/health.py | head -5

What you observe. cat is allowed and runs with no prompt — but head is not, so depending on how Claude composes the command you may be asked anyway. That is the lesson in miniature: the allow list matches commands, not intentions, and a pipeline is only as allowed as its least-allowed part.

2c — Cycle the posture without leaving the session​

Press Shift+Tab to cycle the permission mode. The current mode shows in the input line.

Cycle to acceptEdits and ask for an edit:

Add a one-line comment on its own line directly above the readyz function
definition in app/orders-api/src/health.py that says: reviewed under acceptEdits.
Then run git diff and show me the result.

What Claude does. It writes the edit and asks nothing. Then it runs git diff, which is in the allow list, and shows you the hunk.

What you observe. The edit went through with no prompt — that is exactly what acceptEdits grants — while a Bash command outside the allow list would still have stopped to ask. Edits are auto-approved; execution is not. Two different gates, and switching posture moved only one of them.

Cycle to plan and ask for something destructive-sounding:

Delete the readyz endpoint from app/orders-api/src/health.py.

What you observe. A plan describing the change, and no change. plan is read-only by construction — it cannot edit, so you get to review intent before granting the ability to act. This is the posture worth reaching for when you do not yet trust the scope of what you are asking.

Exit the session (Ctrl+D) and undo the scratch edit so the rest of the lab starts clean:

git checkout app/orders-api/src/health.py
Expected output
Updated 1 path from the index

The file is restored to its committed state.

2d — auto mode: runs everything your rules don't deny​

Back to headless for the last posture, because what matters here is what it does not stop for:

claude -p "Curl both http://localhost:8080/readyz and http://localhost:8081/healthz, then tell me in one line whether either service is degraded." --permission-mode auto

What you observe. Both curls run back to back with no prompt, and the agent reports both services healthy. The difference from default is not visible in this answer — both curls were allowed anyway. The difference is what happens on a command your allow list does not cover: default pauses to ask, auto runs it regardless, stopping only for deny rules. That single distinction is why auto belongs behind a deliberate deny list, which you test next.

Posture is per-invocation, and that is a feature

You just ran the same class of task at three postures without changing a single settings file. Posture is a decision you make per task, matched to that task's risk — exactly the Module 1 ladder, now as a flag you set each time you invoke the agent.

Step 3 — Prove deny beats allow​

The lesson claimed deny overrides a matching allow, even when the agent is told not to ask. Now you prove it on a command that actually matters: a destructive rm. You will add a deny for it in your personal project settings (.claude/settings.local.json, git-ignored so it never ships), then try to make the agent delete a file under the most permissive posture short of bypass.

Create a throwaway victim file and a local rule that both allows and denies rm:

echo "delete me" > /tmp/m2-victim.txt

cat > .claude/settings.local.json <<'EOF'
{
  "permissions": {
    "allow": ["Bash(rm:*)"],
    "deny":  ["Bash(rm:*)"]
  }
}
EOF

The same rule appears in both lists on purpose — that is the test. Now ask the agent to delete the file under dontAsk, the posture that skips every prompt:

claude -p "Run exactly this command: rm /tmp/m2-victim.txt — then reply with only the word RAN or the word BLOCKED." --permission-mode dontAsk
Expected output
BLOCKED.

The agent tried and was refused. dontAsk skips prompting, but it does not override deny — the deny rule wins over both the matching allow and the permissive posture.

Prove it with evidence rather than the agent's word — the victim file should still exist:

ls /tmp/m2-victim.txt
Expected output
/tmp/m2-victim.txt

The file survived. deny is not advisory; it is a hard stop that a permissive posture cannot talk past. This is why the project's deny on terraform destroy and kubectl delete namespace is trustworthy even when you run the agent in a fast, low-prompt mode like auto or dontAsk.

bypassPermissions would not have deleted this file either — but do not rely on that

You might assume bypassPermissions (the "skip all permissions" mode) would have deleted the file. In current Claude Code it would not: deny is a hard floor that even bypassPermissions honors. So why avoid it? Because deny only protects commands you listed. bypassPermissions strips away the allow gate, the ask gate, and every prompt — so any destructive command you did not think to deny runs unopposed. default and auto would have caught that unanticipated command; bypassPermissions will not. The mode is dangerous not because it defeats deny, but because it removes every layer except deny.

Clean up the local rule before the next step:

rm -f .claude/settings.local.json /tmp/m2-victim.txt

Step 4 — Catch the --allowedTools misconception​

This is the trap from the lesson. You will hand yourself a config that looks like a read-and-edit-only agent — --allowedTools "Read,Edit" — and prove Bash is still there. Then you will do it the right way with --tools and watch Bash actually disappear.

First, the misconception. --allowedTools "Read,Edit" auto-approves Read and Edit — and, people assume, removes everything else. Ask the agent to run a shell command anyway. (curl is in the project allow list from Step 1, so if Bash is still available, the command has a clear path to run — which is exactly what we are testing.)

claude -p "Run the shell command: curl -s http://localhost:8081/healthz — then report the exact response body, or say NO BASH TOOL if you have no way to run shell commands." --permission-mode dontAsk --allowedTools "Read,Edit"
Expected output
Response body:

{"status":"ok"}

Read that carefully. You listed only Read,Edit in --allowedTools, yet the agent ran curl and got a real response. Bash was never removed — --allowedTools added Read and Edit to what gets auto-approved; it did not subtract Bash from what exists. (The curl ran because Bash is still available and the project's own allow rule covers curl. Under default mode a Bash command your rules did not cover would prompt; the point is that the tool is present either way.) --allowedTools is a convenience, not a restriction — a config you believed was read-only still has a live shell.

Now the correct way. --tools sets which tools are available at all. Give it only Read,Edit and the same request has nothing to run with:

claude -p "Run the shell command: curl -s http://localhost:8081/healthz — then report the exact response body, or say NO BASH TOOL if you have no way to run shell commands." --permission-mode dontAsk --tools "Read,Edit"
Expected output
NO BASH TOOL — there is no shell/bash tool available in this session.

Same prompt, same posture — but this time Bash was genuinely absent, so the agent could not run curl at all. The difference between the two runs is the entire lesson: --allowedTools speeds up the lane; --tools closes it.

--disallowedTools "Bash" is the other way to close the lane

--tools "Read,Edit" is a positive allowlist of availability. If you would rather subtract, --disallowedTools "Bash" removes just Bash and leaves the rest. Both make the tool unavailable — the agent cannot use it even if it wanted to and even if you approved. That is the boundary --allowedTools never was.

Step 5 — Turn on the sandbox and watch network fail-closed​

Deny lists stop commands you named. The sandbox stops a capability no matter how it is spelled. You will enable the Bash sandbox, then watch an outbound network call get refused — the fail-closed wall from the lesson.

Enable the sandbox in your local project settings:

cat > .claude/settings.local.json <<'EOF'
{
  "sandbox": { "enabled": true }
}
EOF

Now ask the agent to reach an external host and show you curl's raw error:

claude -p "Run exactly this and show me the complete raw stderr verbatim in a code block, do not summarize: curl -sS --max-time 5 https://example.com 2>&1 | head -5" --permission-mode dontAsk
Expected output
curl: (56) CONNECT tunnel failed, response 403

That is the sandbox talking. Outbound traffic is routed through a proxy that refuses external egress, so curl never reaches example.com — it gets a 403 on the CONNECT. Nothing in your deny list mentions example.com or even curl; the sandbox blocked the capability (network egress), not a named command.

The wall is strict — it includes localhost. Prove that even a call to your own running service is refused inside the sandbox:

claude -p "Run exactly and show verbatim stdout only: curl -sS --max-time 4 http://localhost:8081/healthz 2>&1 | head -3" --permission-mode dontAsk
Expected output
curl: (7) Failed to connect to localhost port 8081 after 0 ms: Couldn't connect to server

inventory-api is up — you curled it successfully in Step 0 — but inside the sandbox the loopback connection is refused too. The sandbox does not distinguish "safe" local traffic from egress; it walls off the network entirely.

Now confirm the sandbox is not just breaking everything — legitimate in-project work still runs. Ask it to write a file inside the workspace:

claude -p "Run exactly: echo sandbox-ok > ./m2-sandbox-proof.txt — then reply RAN or BLOCKED." --permission-mode dontAsk
cat ./m2-sandbox-proof.txt
Expected output
RAN
sandbox-ok

Writing inside the project directory is allowed — that is the whole design. The sandbox gives the agent a working area it can freely read and write, while cutting off the two things you never want a local code agent to do unsupervised: reach the network and write outside its lane.

Fail-closed is the property that makes this trustworthy

The reason this is a real control and not a comfort blanket: if the sandbox could not be applied on your platform, the command would be denied, not silently run unsandboxed. A protection that quietly disappears when it can't engage is worse than none — you would trust a wall that isn't there. Fail-closed means the absence of the wall is the absence of the command.

Tear down the sandbox setting and the proof file so later modules start from the plain project policy:

rm -f .claude/settings.local.json ./m2-sandbox-proof.txt

Step 6 — Run the grader​

Turn the whole lab from "the outputs looked right" into a deterministic pass. The grader checks that the project policy is intact, that trust is set, and that the boundary actually behaves — deny-wins and sandbox-blocks — the same way every time.

./scripts/grade.sh m2
Expected output
Grading: Module m2
========================

Checking: Permission boundary & sandbox

  ✓ project settings.json has a permissions.allow list
  ✓ project settings.json denies destructive commands (rm -rf, terraform destroy)
  ✓ workspace trust accepted (allow rules load)
  ✓ deny overrides allow: rm blocked under dontAsk
  ✓ sandbox blocks outbound network (fail-closed)

========================
RESULT: PASS (5 passed)

If the trust check is red, re-run Step 0's trust command. If the deny or sandbox checks are red, you likely left a .claude/settings.local.json from an earlier step in place — remove it and re-run. The last two checks each take a few seconds because they actually invoke the agent.

What the grader is really asserting

Two of these checks execute the boundary, not just read the config: they ask the agent to rm a file behind a deny and to curl an external host inside the sandbox, and pass only if both are refused. Reading a settings file proves the rule is written; running the agent against it proves the rule is enforced. After Module 1's lesson about graders that pass for the wrong reason, this one insists on the second kind of evidence.

Step 7 — Assign a posture to each Module 1 task​

Module 1 left you with four follow-on tasks and asked which autonomy level each deserved. Now close the loop: translate each into the concrete Claude Code configuration — the posture plus any rules — you would actually run it under.

#TaskPosture + rulesWhy
1Fix a typo in a log message on a branch, with testsdefault (or acceptEdits), project allow for the test commandSmall, reviewable; auto-approve the edit and the test run, still see each new action
2Rotate the production database's primary credentials at peak trafficplan only — no execution posture at allIrreversible, high blast radius; the most autonomy it earns is "show me the plan," a human runs it
3Explore an unfamiliar service to understand its retry logicdefault with --tools "Read,Bash" (no Edit)Pure investigation; remove the ability to change anything so exploration cannot drift into editing
4Bump a patch dependency and open a PR when the full suite passes greenauto behind a strict deny (no terraform destroy, no kubectl delete), sandbox onWell-understood loop with a strong guardrail; auto skips prompts, the deny + sandbox stay as the safety net

Your choices may reasonably differ — but you should now be able to express the choice as configuration, not just name a level. That translation, from "how much do I trust this task" to "which flags and rules do I run it under," is the skill this module exists to build.

Now write it down as something your team can actually use. A posture policy that lives in one person's head is not a policy. Start Claude interactively and have it draft one:

Draft agentops/posture-policy.md — the posture policy for this repository.

For each class of work we do here, give a row with: the task class, the
permission mode to run it under, any --tools restriction, and the one-line
reason. Cover at least these four classes:
  - small reviewable edits on a branch
  - irreversible production changes
  - read-only investigation of unfamiliar code
  - well-understood automated loops

Then add a short "Rules that hold regardless of posture" section naming the
deny rules and the sandbox, and why a posture never overrides them.

Base it on .claude/settings.json as it exists now. Keep it under 40 lines.

What Claude does. It reads the current settings.json, maps each task class to a mode, and writes the file.

What you observe — and what you should push back on. Check two things before you accept it. First, does the irreversible-production row say plan and nothing else? An agent that assigns default there has misread the risk, and that is the row that matters most. Second, does the "rules that hold regardless" section actually state that deny beats every posture, including auto and dontAsk? You proved that in Step 3 — if the draft hedges it, correct it. A policy that describes deny as a preference rather than an override is worse than no policy, because people will trust it.

Fix what is wrong and keep the file. It is the artifact this module ships, and the grader reads it.

Teardown​

Stop the stack and remove any lab-local settings so the next module starts from the clean project policy.

rm -f .claude/settings.local.json ./m2-sandbox-proof.txt
git checkout app/orders-api/src/health.py 2>/dev/null
docker compose --profile core down
Expected output
[+] Running 4/4
 ✔ Container agentic-ops-lab-orders-api-1      Removed
 ✔ Container agentic-ops-lab-inventory-api-1   Removed
 ✔ Container agentic-ops-lab-postgres-1        Removed
 ✔ Network agentic-ops-lab_default             Removed

Confirm you are back to the committed project policy with no local override lingering:

git status --short .claude/
Expected output

No output — .claude/settings.json is unchanged and no settings.local.json remains. (If you see an untracked settings.local.json, delete it.)

You configured the three boundaries and watched each one hold: availability removed a tool, a deny overrode an allow under the most permissive posture, and the sandbox refused the network fail-closed. From here on, every time you hand the agent more of the loop, you will set these boundaries first — because the boundary, not the model, is what makes the delegation safe.
