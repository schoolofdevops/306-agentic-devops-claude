Lab — The Change Gate

The lesson drew the line between intent controls (rules the agent chooses to follow) and enforcement controls (things that hold regardless of what the agent decides). This lab builds the enforcement layer and proves it holds. You will wire a deterministic PreToolUse hook — the Change Gate — that blocks the five dangerous command shapes with clear reasons and fails closed on error. Then you will build the Environment Contract: canonical dev/staging/production bundles with explicit target metadata, read-only identities for non-dev, and a fail-closed mismatch check that kills the wrong-target class of incident. Finally you will stand up the GitOps path where the reconciler is the only cluster writer and the agent merely proposes.

By the end you will have a tested safety control you can point a security reviewer at — not "we told the agent not to," but "the destructive command produces exit code 2, here is the test."

Where you are working

You start at the root of the agentic-ops-lab workspace. The Change Gate hook (scripts/hooks/change-gate.sh), the environment bundles (in contracts/environment-contract.yaml), the mismatch check (scripts/env-check.sh), and the GitOps proposal helper (scripts/gitops-propose.sh) ship in the repo — this lab is about understanding, wiring, and proving them, the same way Module 7 shipped the observer and had you register and test it. You do not need a live Kubernetes cluster for the enforcement checks; the gate and the contract check operate on command text and declared metadata, so they run anywhere.

Step 0 — Prerequisites​

Confirm your tools. The gate uses jq to parse the hook event; the contract check uses python3 (with pyyaml) to read the bundles.

claude --version
jq --version
python3 -c "import yaml; print('pyyaml', yaml.__version__)"
git --version
Expected output
2.1.197 (Claude Code)
jq-1.7.1
pyyaml 6.0.2
git version 2.50.1 (Apple Git-155)

Your versions will differ. All four must resolve. If pyyaml is missing, pip3 install pyyaml.

Step 1 — Read the Change Gate before you trust it​

The gate is a safety control, so read it before wiring it in — you do not run a checkpoint you have not inspected. Look at what it denies and, just as important, how it fails closed.

sed -n '1,40p' scripts/hooks/change-gate.sh
Expected output
#!/usr/bin/env bash
# change-gate.sh — deterministic PreToolUse gate for Bash commands.
#
# Claude Code invokes this before a Bash tool call, passing the hook event as
# JSON on stdin. The gate inspects the proposed command and DENIES the ones the
# environment contract says must never run from an agent identity:
#
#   1. terraform apply on production   -> route through GitOps, never apply
#   2. kubectl delete namespace <prot> -> protected namespace, never delete
#   3. kubectl ... --all-namespaces/-A -> wildcard target, blast radius too wide
#   4. commands that print secrets      -> data-leakage risk
#   5. docker push                      -> images ship through CI, not the agent
...

Read the header, then scan the body: each rule is a grep against the normalized command, and each deny prints a JSON permissionDecision:"deny" plus a reason. The fail_closed() function at the top is the key design point — if jq is missing or stdin is empty, the gate exits non-zero (blocks) rather than allowing. A gate that cannot evaluate a command must not pass it.

Make it executable:

chmod +x scripts/hooks/change-gate.sh
echo "gate ready"
Expected output
gate ready

Step 2 — Drive the gate by hand: the five denials​

The gate reads a hook event on stdin — a JSON object with tool_name and tool_input.command. Send it a real production apply and watch it deny. This is exactly the payload Claude Code sends; you are simulating it directly so you can see the verdict.

printf '{"tool_name":"Bash","tool_input":{"command":"terraform apply -auto-approve infra/environments/production"}}' \
  | scripts/hooks/change-gate.sh
echo "exit=$?"
Expected output
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"terraform apply on production is blocked — production infrastructure changes must go through GitOps (branch -> PR -> approval -> reconciler apply), never a direct agent apply."}}
DENIED by change-gate: terraform apply on production is blocked — production infrastructure changes must go through GitOps (branch -> PR -> approval -> reconciler apply), never a direct agent apply.
exit=2

Two things. The stdout line is the structured decision Claude Code reads — permissionDecision:"deny" with a reason. The stderr line and exit=2 are the belt-and-suspenders block signal. The reason is written for the agent: it does not just say "no," it says why and what to do instead (route through GitOps), so the agent can correct course.

Now run the whole deny set at once. Each should exit 2:

for c in \
  'terraform apply -auto-approve infra/environments/production' \
  'kubectl delete namespace production' \
  'kubectl delete pods -A' \
  'kubectl get secret db-creds -o yaml' \
  'docker push northstar/orders-api:latest'
do
  printf '{"tool_name":"Bash","tool_input":{"command":"%s"}}' "$c" \
    | scripts/hooks/change-gate.sh >/dev/null 2>&1
  echo "exit=$?  <-  $c"
done
Expected output
exit=2  <-  terraform apply -auto-approve infra/environments/production
exit=2  <-  kubectl delete namespace production
exit=2  <-  kubectl delete pods -A
exit=2  <-  kubectl get secret db-creds -o yaml
exit=2  <-  docker push northstar/orders-api:latest

All five dangerous shapes from the threat table — irreversible prod apply, protected-namespace delete, wildcard blast radius, secret output, and an image push that belongs in CI — are denied deterministically. Not "usually." Every time, because it is a script, not a judgment.

Step 3 — Prove the gate is narrow: safe commands pass​

A gate that blocks investigation along with destruction is broken. Confirm the agent can still do its job — terraform plan, a dev apply, read-only kubectl -A, a Secret referenced by name, a health curl — all exit 0.

for c in \
  'terraform plan -out=plan.tfplan' \
  'terraform apply infra/environments/dev' \
  'kubectl get pods -A' \
  'kubectl get secret db-creds' \
  'curl -s http://localhost:8080/readyz'
do
  printf '{"tool_name":"Bash","tool_input":{"command":"%s"}}' "$c" \
    | scripts/hooks/change-gate.sh >/dev/null 2>&1
  echo "exit=$?  <-  $c"
done
Expected output
exit=0  <-  terraform plan -out=plan.tfplan
exit=0  <-  terraform apply infra/environments/dev
exit=0  <-  kubectl get pods -A
exit=0  <-  kubectl get secret db-creds
exit=0  <-  curl -s http://localhost:8080/readyz

Every safe command passes. Note the precision: terraform apply is denied only when production is in the command — the dev apply sails through. A read-only kubectl get -A passes because the wildcard rule only fires on mutating verbs. kubectl get secret db-creds passes because it references the secret by name and never renders its value; only -o yaml/jsonpath/base64 -d trip the leak rule. The gate stops the four dangerous shapes and nothing else.

Step 4 — Prove it fails closed​

The most important property of a safety control is what it does when it cannot decide. Send the gate empty input — no command to evaluate — and confirm it blocks rather than allows.

printf '' | scripts/hooks/change-gate.sh
echo "exit=$?"
Expected output
change-gate: internal error: empty hook input on stdin
exit=1

exit=1 — blocked. The gate received nothing to evaluate and refused rather than defaulting to allow. This is the fail-closed contract: "I could not decide" is the same outcome as "deny." A control that opened the door whenever it was confused would not be a control at all.

Step 5 — Wire the gate into Claude Code​

Now make the gate real: register it as a PreToolUse hook on Bash in .claude/settings.json, so every Bash command the agent proposes passes through it before running. Inspect the wiring that ships in the repo:

jq '.hooks' .claude/settings.json
Expected output
{
  "PreToolUse": [
    {
      "matcher": "Bash",
      "hooks": [
        {
          "type": "command",
          "command": "$CLAUDE_PROJECT_DIR/scripts/hooks/change-gate.sh"
        }
      ]
    }
  ]
}

The matcher: "Bash" means the hook fires before any Bash tool call. $CLAUDE_PROJECT_DIR resolves to the workspace root, so the path works regardless of where the agent's cwd is. This one block is what turns the script from a thing you tested by hand into a floor under every command the agent runs.

The hook is now live for this workspace

With this wired, an agent session in this workspace has the Change Gate in front of its Bash tool. That is the point — but it means if you later add a legitimate command shape the gate does not anticipate, you will see a denial. The fix is to widen the gate's rules deliberately and re-test, never to disable the hook to "unblock" the agent. An enforcement control you switch off under pressure is an intent control wearing a costume.

Step 6 — Read the Environment Contract bundles​

The gate is the command layer. The Environment Contract is the target layer — it declares, per environment, exactly what is permitted. Look at the bundles that were added to the contract:

python3 -c "
import yaml
b = yaml.safe_load(open('contracts/environment-contract.yaml'))['bundles']
for env, cfg in b.items():
    print(f\"{env:12} identity={cfg['identity']:9} apply={cfg['allow_apply']!s:5} delete={cfg['allow_delete']!s:5} approval={cfg.get('require_approval')}\")"
Expected output
dev          identity=admin     apply=True  delete=True  approval=False
staging      identity=readonly  apply=False delete=False approval=False
production   identity=readonly  apply=False delete=False approval=True

Read the invariant off the table: dev is the only bundle whose identity can write. Staging and production are pinned to the readonly identity with allow_apply: false and allow_delete: false — the agent is read-only against them by credential, not by promise. Production additionally requires approval. The environment you are in is now a row in a file with hard booleans, not a memory you might have wrong.

Step 7 — The fail-closed mismatch check​

env-check.sh is the pilot's checklist: it confirms the environment you declared matches the one actually in effect, and that the action you intend is permitted. It reads the effective kube-context from $KUBE_CONTEXT (so you can run it without a cluster) or from kubectl config current-context. First, the wrong-target incident — you think you are in staging but you are pointed at production's opposite:

KUBE_CONTEXT=dev-cluster scripts/env-check.sh production read
echo "exit=$?"
Expected output
BLOCKED (env-check): environment MISMATCH — you declared 'production' (expects context 'prod-cluster') but the effective context is 'dev-cluster'. This is the wrong-target class of incident; the operation is blocked before it runs.
exit=1

The declared environment (production) and the effective context (dev-cluster) do not match, so the check blocks. This is the wrong-target threat killed at the source: you cannot run "the production operation" while pointed somewhere else, because the mismatch is a hard block, not a warning you might skim past.

Now the action-policy check — even when the context matches, an apply to staging is forbidden because staging is GitOps-only:

KUBE_CONTEXT=staging-cluster scripts/env-check.sh staging apply
echo "exit=$?"
Expected output
BLOCKED (env-check): action 'apply' is NOT permitted in 'staging' (allow_apply: false). Changes to this environment flow through GitOps — branch, PR, approval, reconciler. Blocked.
exit=1

The context is right, but the bundle says allow_apply: false, so the apply is blocked and pointed at GitOps. The check enforces the contract's booleans, not just context identity.

Confirm the happy path — a read in dev, where the declared environment matches and the action is allowed — passes:

KUBE_CONTEXT=dev-cluster scripts/env-check.sh dev read
echo "exit=$?"
Expected output
OK (env-check): declared 'dev' matches effective context 'dev-cluster'; action 'read' permitted.
exit=0

Match plus permitted action equals pass. And like the gate, the check is fail-closed: try scripts/env-check.sh qa read (unknown environment) or run it with no $KUBE_CONTEXT and no cluster — both block, because an environment it cannot positively verify is treated as the wrong one.

Step 8 — The GitOps path: the reconciler is the only writer​

The contract makes staging and production read-only to the agent. So how do changes reach them? Through GitOps — the agent proposes on a branch and stops; the reconciler applies from merged Git state. Look at how the Argo CD Applications declare the reconciler as the sole writer:

python3 -c "
import glob, yaml
for f in sorted(glob.glob('platform/argocd/applications/*.yaml')):
    a = yaml.safe_load(open(f))
    s = a['spec']
    auto = s['syncPolicy'].get('automated', {})
    print(f\"{a['metadata']['name']:14} repo={s['source']['repoURL'].split('/')[-1]:20} selfHeal={auto.get('selfHeal')} prune={auto.get('prune')}\")"
Expected output
inventory-api  repo=northstar-remote.git selfHeal=True prune=True
orders-api     repo=northstar-remote.git selfHeal=True prune=True

Each Application syncs from the Git remote with selfHeal: true and prune: true. selfHeal means the reconciler continuously reverts any change made outside Git — a manual kubectl edit gets undone. prune means resources removed from Git are removed from the cluster. Together they make Git the single source of truth: the only durable way to change the cluster is to change Git, and the only identity that writes is the reconciler.

Now walk the agent's side of the path. The gitops-propose.sh helper is the runnable "route through GitOps" action — it stages desired-state changes, creates a proposal branch, and stops at the human handoff. It never touches a cluster.

scripts/gitops-propose.sh
Expected output
gitops-propose: usage: gitops-propose.sh <change-slug> "<summary>"

Called with no arguments it prints usage — it requires an explicit change slug and a one-line summary the reviewer will read. The full path is: the agent edits the Helm values that describe desired state, runs gitops-propose.sh scale-orders "bump orders-api replicas to 3", which creates a propose/scale-orders branch and prints the next (human) steps — commit, push to the remote, open a PR, get approval, merge. At merge, the reconciler detects the drift and applies it. The agent's involvement ends at "propose." It has no write path to the cluster, by identity and by design.

Step 9 — Let the repository certify the whole gate​

Run the module grader. It drives the Change Gate with real deny and allow inputs, confirms it fails closed, checks the hook is wired in settings, verifies the bundles declare read-only non-prod identities, and confirms the mismatch check blocks a wrong-target and permits a match.

./scripts/grade.sh m8
Expected output
Grading: Module m8
========================

Checking: Change Gate + Environment Contract — deterministic hook denials and fail-closed target checks

  ✓ the change-gate PreToolUse hook exists and is executable
  ✓ DENY: terraform apply against production is blocked (exit 2) and routed to GitOps
  ✓ DENY: deleting the protected 'production' namespace is blocked (exit 2)
  ✓ DENY: a mutating kubectl targeting all namespaces (-A) is blocked (exit 2)
  ✓ DENY: rendering a Secret's decoded value is blocked (exit 2) to keep credentials out of the transcript
  ✓ DENY: docker push is blocked (exit 2) — images ship through CI, not an agent identity
  ✓ ALLOW: terraform plan, dev apply, read-only kubectl -A, and a secret referenced by name all pass the gate (exit 0)
  ✓ FAIL-CLOSED: the gate blocks (nonzero exit) when it receives no input to evaluate
  ✓ the change-gate hook is wired as a PreToolUse Bash matcher in .claude/settings.json
  ✓ the environment contract declares dev/staging/production bundles, each with kubeconfig, allow_apply, allow_delete
  ✓ staging and production bundles are pinned to the read-only identity and forbid apply/delete (agent cannot write them)
  ✓ FAIL-CLOSED: env-check blocks when the declared environment does not match the effective context (declared production, pointed at dev)
  ✓ env-check blocks an apply to staging even when the context matches (allow_apply:false — GitOps only)
  ✓ env-check permits a read in dev when the declared environment matches the effective context

========================
RESULT: PASS (14 passed)

Fourteen green. The grader ran the same gate you tested by hand — the denials, the allows, the fail-closed case — plus the contract's read-only invariant and the mismatch check, and certified them all. This is the payoff of enforcement-as-code: the safety control is tested, not asserted.

Step 10 — Teardown​

The gate, the bundles, the mismatch check, and the GitOps helper are module deliverables — leave them; the Deep Dive runs its incident against them. Clean up only the ephemeral proposal branch if you created one while exploring Step 8.

git checkout main 2>/dev/null || git checkout master 2>/dev/null || true
git branch -D propose/scale-orders 2>/dev/null || echo "no proposal branch to remove"
git status --short scripts/hooks/ contracts/ .claude/settings.json
Expected output
no proposal branch to remove

If you never ran a real gitops-propose.sh with a slug, there is no branch to remove and git status shows the deliverables as tracked/modified in place. Leave the Change Gate wired — it is now part of this workspace's safety floor, exactly as you would want it in real work.

You built a deterministic safety control and proved it holds: five dangerous command shapes denied every time, safe commands untouched, fail-closed on error, wired in front of every Bash call. You made the environment a machine-checkable fact with read-only identities for everything but dev, and a mismatch check that kills the wrong-target incident before it runs. And you established the GitOps path where the agent only ever proposes and the reconciler is the only writer. None of this depends on the agent choosing correctly — which is the entire point. The Deep Dive now takes the most dangerous instruction in the course — "clean up old resources and fix production" — and runs it straight into everything you just built.
