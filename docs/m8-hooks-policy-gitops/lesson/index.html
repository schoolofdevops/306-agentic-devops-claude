Hooks and Guardrails

Every module so far has made the agent better behaved. You wrote CLAUDE.md rules it reads, permission settings it respects, skills that steer how it works, and typed tools that narrow what it reaches for. All of those share one property: they work by getting the model to choose the right action. Module 7's read-only observer was the first crack in that pattern: a control that did not ask the agent to behave, but removed the capability entirely. This module is about that shift, made general. Because there is a category of action where "the agent chose correctly" is not good enough, where you need a control that holds even if the model misreads the ticket, ignores the rule, or is talked into the wrong thing. A terraform apply on production. A kubectl delete namespace. A command that prints your database password into the transcript. For those, hope is not a control. This module builds the layer that does not depend on the agent's judgment at all.

Here is the concrete situation it closes. A ticket lands during an incident: "clean up the old resources and fix production." Your agent has CLAUDE.md rules saying "never apply to production directly" and "route changes through GitOps." Those rules are real and the agent usually follows them. But usually is doing a lot of work in that sentence. Under time pressure, with an ambiguous instruction, the model might read "fix production" as "run the apply", and every intent control you have is a rule it is interpreting, which means a rule it can misinterpret. What you want is a control that makes the destructive apply fail, deterministically, regardless of what the model decided. That control is a hook, and it is the center of this module.

Why this is a different kind of control​

The reason this matters at work is that the failure modes of intent controls and enforcement controls are completely different, and you need both because each covers the other's gap. An intent control (a CLAUDE.md rule, a skill instruction, a permission preference) steers what the agent tries to do. It fails when the model misinterprets: the rule was there, the agent read it, and it still did the wrong thing because it understood the situation differently than you did. An enforcement control (a hook, an IAM policy, an RBAC role, an admission webhook) physically prevents the action regardless of intent. It fails only when it is misconfigured: the rule was too narrow, the pattern did not match, you forgot a case.

The distinction is not academic. Intent controls fail silently and plausibly: the agent does something reasonable-looking that happens to be wrong, and you find out later. Enforcement controls fail loudly and structurally: either the action was blocked or it was not, and you can test exactly which. You want the destructive operations behind enforcement, so that "did the safety hold?" is a question you can answer with a test instead of a hope.

Analogy: think about how a building keeps people out of the server room. There is a sign on the door that says "Authorized personnel only." That is an intent control: it works on people who read it and choose to comply, and it fails the moment someone decides the sign does not apply to them, or does not notice it, or is in a hurry. Then there is the badge reader that will not open the door without an authorized badge. That is an enforcement control: it does not care whether you read the sign or how urgent your reason is; the door does not open. You do not remove the sign, it sets expectations and handles the honest majority cheaply. But for the room that actually matters, you do not rely on the sign alone. You put a badge reader on it, because the sign fails exactly when you most need it to hold: when someone is motivated to ignore it. Intent controls are the sign. Enforcement controls are the badge reader. This module is about putting badge readers on the doors that matter.

Read the two columns as layers, not alternatives. You keep every intent control you built, they are cheap, they handle the common case, and they make the agent pleasant to work with. Enforcement controls sit underneath them as the floor: the thing that catches what intent missed. The rest of this module builds that floor at three depths: the command layer (hooks), the target layer (identities, RBAC, admission), and the change path (GitOps), and then ties them together with the Environment Contract.

Model the threat surface first​

Before building controls, name what you are defending against. The threat surface for an agent doing ops is not "the model is evil". It is far more mundane and far more likely: the model does something reasonable given how it read the situation that turns out to be destructive. Four patterns cover most of it, and every control in this module maps to one.

Threat patternWhat it looks likeThe reasonable-but-wrong reading
Wrong targetA correct command against the wrong environment"Fix the deployment", agent is pointed at prod, thought it was staging
Excess blast radiusA command whose scope is wider than intended"Restart the pods" becomes --all-namespaces
Irreversible destructionA delete/apply with no undo"Clean up old resources" deletes a live namespace
Data leakageSecrets pulled into the transcript"Check the DB config" dumps a Secret's decoded value

None of these require a malicious model. Each is a plausible misreading of an ambiguous instruction, which is exactly why an intent control ("don't do that") is a weak defense: the agent is not trying to violate the rule, it genuinely believes it is doing the right thing. Enforcement is the answer precisely because it does not depend on the agent's belief being correct.

The command layer: deterministic hooks​

A hook in Claude Code is a shell command that runs around a tool call: before it (PreToolUse), after it (PostToolUse), or at other lifecycle points. The defining property, and the reason this module exists: a hook is a deterministic shell script, not an LLM. It does not reason, interpret, or get talked out of its decision. It runs the same code on the same input every time and returns the same verdict. When you gate the agent's Bash calls through a hook, you have inserted a piece of ordinary, testable software between the model's intent and the command's execution.

A PreToolUse hook receives the proposed tool call as JSON on stdin, the tool name and its input, and gets to decide before anything runs. It blocks by exiting non-zero (and, in current Claude Code, by emitting a JSON decision of permissionDecision: "deny"). The critical design choice is fail-closed: if the hook script itself errors (jq missing, malformed input, an unhandled case) it must block, not allow. A gate that cannot evaluate a command has no business letting it through. "I could not decide" and "deny" must be the same outcome, because the alternative is a safety control that opens the door whenever it is confused.

Analogy: a hook is the airport security checkpoint, and fail-closed is its operating rule. The checkpoint runs the same procedure on every passenger: it does not decide who looks trustworthy, it applies fixed rules to what the scanner sees. And when the scanner malfunctions or the operator cannot tell what an object is, the rule is not "wave them through to keep the line moving". It is "stop, do not pass, resolve it." The default on uncertainty is closed, not open. A checkpoint that let people through whenever its equipment glitched would not be a security control at all. Your hook is the same: deterministic procedure, and closed on doubt.

The Change Gate you build in the lab is one such hook, and it encodes the threat table directly. It denies, deterministically: a terraform apply on production (irreversible + wrong-layer, route it through GitOps), a delete of a protected namespace (irreversible destruction), a mutating kubectl with an all-namespaces target (excess blast radius), a command that would render a Secret's decoded value (data leakage), and a docker push (images ship through CI, not an agent identity). Each denial returns a reason the agent sees, so it can correct course rather than just hitting a wall. And crucially, the gate is narrow: terraform plan passes, a dev apply passes, a read-only kubectl get -A passes, a Secret referenced by name passes. A gate that blocks investigation along with destruction is a broken gate, the whole point is to stop the four dangerous command patterns while leaving the agent free to do its job.

A hook is code, so you test it like code

Because the gate is a deterministic script, its correctness is testable in a way an intent control never is. You cannot write a unit test for "the model will interpret this rule correctly." You absolutely can write one for "this exact command produces exit code 2." The lab has you drive the gate with real deny inputs and real allow inputs and assert the verdicts, the same positive/negative/boundary testing you applied to skills in Module 6, now applied to a safety control. An enforcement control you have tested is worth more than an intent control you are hoping about.

The target layer: least privilege at the identity​

The hook is the command layer, it inspects what the agent is about to run. Underneath it sits a second, stronger layer: what the agent's identity is even allowed to do, enforced by the target system rather than by your script. This is the Module 7 observer idea generalized from tools to credentials. If the kubeconfig the agent holds is bound to a role that has only get, list, watch verbs, then the agent cannot write to the cluster. Not because a hook caught the command, but because the API server rejects the identity. The write capability is absent from the credential itself.

This is why the target layer is stronger than the command layer, and why you want both. A hook is your code checking the command text, it can be too narrow (a command pattern you did not anticipate slips through). RBAC is the cluster checking the identity, it does not care how the command is spelled; an identity with no write verb cannot write, full stop. The controls compose: the hook catches the obvious destructive commands early and gives a helpful reason; the read-only identity is the backstop that holds even if the hook has a gap.

The target-layer controls you will meet, from your own machine outward:

  • Read-only identities. The agent session runs with readonly.yaml, a kubeconfig bound to a role with only read verbs. The admin.yaml writer identity exists but is used by humans and the reconciler, not the agent's default session.
  • IAM / RBAC. Cloud IAM policies and Kubernetes RBAC define what each identity may do at the target. This is where "the agent is read-only in staging and prod" becomes a fact about the credential, not a promise in prose.
  • Admission controllers. The cluster's own gate: a webhook that inspects every write the API server receives and can reject it: deny privileged pods, require resource limits, forbid deletes of protected namespaces. This is enforcement the cluster applies to everyone, agent or human.
  • OPA / Conftest (optional). Policy-as-code you run against manifests and Terraform plans before they are applied, the same deterministic-rule idea as the hook, expressed as reusable policy bundles. Optional for this module, but the natural next step when your deny rules outgrow a single shell script.

Analogy: the command layer and the target layer are the difference between the bouncer at the door and the vault behind the counter. The bouncer (your hook) checks each person against a list as they try to enter, fast, helpful, and only as good as the list. The vault (the read-only identity, RBAC, admission) does not check anyone against a list; it simply cannot be opened without the right key, no matter who walks up or what they say. You want the bouncer for the fast, friendly first pass, and the vault for the guarantee that holds when the bouncer's list has a gap. Defense in depth is not redundancy for its own sake; it is putting the friendly, fallible control and the structural, unarguable control on the same door.

The change path: GitOps and the reconciler-only writer​

The target layer says the agent cannot write to staging or production. That raises an obvious question: then how do changes to those environments ever happen? The answer is the third layer, and it is the one that turns "the agent can't write prod" from a limitation into an operating model: GitOps.

In GitOps, the desired state of the cluster lives in Git: Helm values, manifests, Argo CD Application definitions. A reconciler (Argo CD, in this course) continuously compares the cluster's actual state to Git's declared state and drives the cluster to match. The reconciler is the only identity with write access to the cluster. Not the agent. Not the human running the agent. Only the reconciler, and only from merged Git state. That single constraint reshapes every change into one path:

agent edits manifests → opens a change on a branch → human reviews the PR
  → approval → merge to main → reconciler detects the drift → reconciler applies

The agent's job ends at "propose." It writes to a branch and stops. Everything after (review, approval, merge, apply) happens through identities and systems the agent does not control. This is the strongest enforcement in the module because it does not just constrain what the agent can do to the cluster; it removes the agent from the write path entirely. The agent literally has no route to the cluster's state except through a human-reviewed, reconciler-applied Git merge.

Analogy: GitOps is the difference between letting a contractor renovate your house with their own key, versus a system where the contractor can only submit drawings. In the first, the contractor has direct write access to your house, you are trusting their judgment on every cut. In the second, the contractor draws up the change, an inspector reviews it against code, and only then does an authorized crew, working from the approved drawings, do the physical work. The contractor never touches the structure directly. The value is not that the contractor is untrusted; it is that every change goes through the same reviewed, recorded, reversible path, so a mistake is caught at the drawing stage and the house's actual state always matches an approved plan. The agent is the contractor who submits drawings. The reconciler is the only crew with a key.

Notice how the reconciler's selfHeal closes the loop: if anything changes the cluster outside of Git, a manual kubectl edit, a stray write, the reconciler detects the drift and reverts it to match the declared state. Git is not just the change path; it is the source of truth, and the reconciler enforces it continuously. There is no durable way to change the cluster except by changing Git.

The Environment Contract: making the target explicit​

The three layers are strongest when the agent, and your scripts, can know which environment they are operating against, with no ambiguity. That is the job of the Environment Contract: a single declarative file that names each environment as a bundle of explicit target metadata. For dev, staging, and production, it declares the kube-context, the kubeconfig identity, the Terraform backend, and three hard booleans: allow_apply, allow_delete, require_approval.

The contract is what turns "be careful about production" into a machine-checkable fact. Its central invariant: dev is the only bundle whose identity can write. Staging and production are pinned to the read-only identity, with allow_apply: false and allow_delete: false. So the environment you are in is not a vibe or a memory, it is a row in a file, and that row says, in booleans, exactly what is permitted.

bundles:
  dev:
    kubeconfig: platform/kubeconfigs/admin.yaml    # writer identity
    allow_apply: true
    allow_delete: true
    require_approval: false
  staging:
    kubeconfig: platform/kubeconfigs/readonly.yaml # read-only to the agent
    allow_apply: false                              # writes flow through GitOps
    allow_delete: false
  production:
    kubeconfig: platform/kubeconfigs/readonly.yaml # read-only to the agent
    allow_apply: false
    allow_delete: false
    require_approval: true

The contract does its real work through a fail-closed mismatch check: env-check.sh in the lab. Before an operation, the check reads the declared environment and compares it to the effective one: does the kube-context in effect match the bundle you named? Does the identity match? Is the action you are about to take permitted by that bundle's booleans? If any answer is "no", or if the check cannot determine the answer, it blocks. This directly kills the wrong-target threat from the table: you cannot run "the staging fix" while accidentally pointed at production, because the declared environment and the effective context will not match, and the mismatch is a block, not a warning. And it is fail-closed for the same reason the hook is: an environment you cannot positively verify is treated as the wrong one.

Analogy: the Environment Contract is the pre-flight checklist a pilot runs before takeoff. The checklist does not trust the pilot's memory of which runway they are cleared for or whether the flaps are set. It forces an explicit, item-by-item confirmation that the declared plan matches the actual aircraft state. And a checklist item that cannot be confirmed is not skipped to save time; it halts the takeoff. The contract is that checklist for an ops operation: declare the environment, confirm the effective state matches, confirm the action is permitted, and halt if any item cannot be confirmed. Pilots do not run checklists because they are careless; they run them because the cost of a wrong-target action is catastrophic and human memory is exactly the thing that fails under pressure. Same reasoning, same discipline.

How the layers compose​

Put the four pieces together and you have defense in depth where each layer covers the layer above it's failure mode:

  1. Intent controls (CLAUDE.md, skills) handle the honest common case cheaply.
  2. The Change Gate hook deterministically blocks the dangerous command patterns, with reasons.
  3. The Environment Contract check blocks wrong-target and forbidden actions before they run.
  4. Read-only identities + GitOps are the structural backstop: even if every control above had a gap, the agent's credential cannot write staging or production, and the only write path is a reviewed Git merge applied by the reconciler.

The lesson of the whole module compresses to this: do not make the destructive action depend on the agent choosing not to do it. Make it depend on a deterministic script, a read-only credential, and a reconciler that is the only writer, controls that hold when the model's judgment does not, because they are not judgment at all.

What you'll do in the lab​

You will build the Change Gate + Environment Contract and prove every control holds:

  1. Build the Change Gate hook: a deterministic PreToolUse script that denies production apply, protected-namespace deletion, wildcard mutations, secret output, and docker push, each with a reason, fail-closed on error.
  2. Wire it into settings.json: a PreToolUse matcher on Bash, so every command the agent proposes passes through the gate.
  3. Test each denial: drive the gate with real dangerous commands and watch them fail with clear messages; drive it with safe commands and watch them pass. Confirm it fails closed on bad input.
  4. Build the environment bundles: extend the Environment Contract with dev/staging/production target metadata, read-only identities for non-dev, and the allow_apply/allow_delete booleans.
  5. Implement the fail-closed mismatch check: env-check.sh that blocks when the declared environment does not match the effective context, or when the action is forbidden by the bundle.
  6. Set up the GitOps path: use the local Git remote and the Argo CD Applications to show the reconciler as the only cluster writer; the agent proposes on a branch and stops.

grade.sh m8 certifies the gate blocks what it must and allows what it must, the bundles are declared with read-only non-prod identities, and the mismatch check is genuinely fail-closed. The Deep Dive then runs the Destructive Shortcut incident, "clean up old resources and fix production", against everything you built, and you will see the enforcement layer turn a dangerous, ambiguous instruction into a safe, evidence-first, GitOps-routed response, with no direct production write anywhere in it.
