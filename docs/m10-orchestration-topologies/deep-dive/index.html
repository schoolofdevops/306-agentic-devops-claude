Deep Dive — The Audit as an Agent SDK Fan-Out

The core lab ran the estate audit as a shell workflow — a fan-out expressed with & and wait, with the partition, the concurrency cap, and the join all implied by how the script was written. That is the right first tool: it is reproducible, it grades green, and it needs nothing but bash and jq. But the shell hides the orchestration inside shell mechanics. The concurrency cap is a batch barrier you have to read carefully to see; the "partition" is a for loop over a string; the join is a jq -s. When the orchestration gets more complex — per-worker models, measured token cost, a real semaphore, dynamic worker counts — the shell stops being the clearest way to express it. This page rebuilds the same audit with the Claude Agent SDK, where every control from the lesson becomes an explicit line of code you wrote, and then compares the two on the axes that actually decide which to reach for: behavior, tokens, and latency.

This extends the lab — it does not repeat it

You already ran the shell workflow and saw it certified by grade.sh m10. This page is about the layer above that: the same orchestration shape expressed programmatically, why the SDK's explicitness is worth its cost only past a certain complexity, how a real semaphore differs from a batch barrier, and how the SDK worker inherits the M9 role-bundle boundaries (read-only tools, a turn budget). If you have not run the audit workflow (lab Steps 7–9), do that first; the SDK script here is validated against the shell version's exact output.

Why reach for the SDK at all​

The instinct after the shell workflow is "it works and it grades — why write it again in Node?" The honest answer is: for the four-module audit exactly as it stands, you probably would not. The shell version is simpler and has zero dependencies. The SDK earns its place when the orchestration needs things the shell expresses badly.

Analogy: the shell workflow is a checklist taped to the wall; the SDK script is the workflow engine. For a four-item checklist done the same way every day, the taped list is perfect — everyone can read it, nothing to install, no moving parts. But the moment the process needs conditionals ("if the security scan flags something, route it to a second reviewer"), measured throughput ("how many token-seconds did each station cost"), or a genuine work queue with a fixed number of stations pulling from it, the taped checklist stops scaling and you reach for the engine. The engine costs more to stand up and is more to maintain — but it makes explicit exactly the things the checklist left implicit. Neither is "better"; they fit different complexity. The skill is knowing where the crossover is, and not paying for the engine before you need it.

Concretely, the SDK gives you three things the shell makes awkward:

  1. Per-worker agent provisioning in code — each module's worker is a query() call with its own system prompt, model, tool set, and turn budget. This is the M9 Role Bundle, instantiated per fan-out branch, in a language that can compute the provisioning rather than hardcode it.
  2. A real semaphore, not a batch barrier — the shell's --max-parallel drains a whole batch before starting the next; the SDK holds exactly N workers in flight and starts a new one the instant one finishes. For uneven work (one module slow, three fast), the semaphore keeps all N lanes busy where the batch barrier idles them waiting for the slow one.
  3. Measured cost and latency — the SDK's result stream carries per-worker usage and total_cost_usd, so the token cost of the fan-out is a number you can sum, not something you infer. This is the Agent Run Ledger from Module 4, now per orchestration branch.

The package, and the shape of a worker​

The SDK is @anthropic-ai/claude-agent-sdk — the programmatic library, distinct from the @anthropic-ai/claude-code CLI you have used all course. (It is available for both TypeScript/JavaScript and Python; the lab script is .mjs.) Its core is the query() async generator: you give it a prompt and options, and you iterate the messages it yields — the assistant turns, the tool calls, and a final result message that carries usage and cost.

One module's worker, as the lab script writes it, is a read-only auditor provisioned exactly like an M9 role:

for await (const msg of query({
  prompt: `You are a read-only IaC auditor for the '${m}' module …
           Return ONLY {"module":"${m}","security_findings":<int>,
           "cost_delta_usd":<int>,"verdict":"clean|flag|block"}.`,
  options: {
    model: "claude-haiku-4-5-20251001",   // right-sized: a mechanical read (M9 FinOps logic)
    allowedTools: ["Read", "Grep", "Glob"], // read-only worker — no write tool
    maxTurns: 6,                            // turn budget — bounded depth per worker
    cwd: REPO_ROOT,
  },
})) {
  // collect the assistant's final JSON record;
  // the SDK's result message carries usage + total_cost_usd
}

Read the provisioning against Module 9. model: haiku is the FinOps right-sizing decision — pricing a module's exposure is mechanical, so it runs the cheap model. allowedTools: ["Read","Grep","Glob"] with no write tool is the read-only Role Bundle — the worker cannot modify the module it audits, because the capability is absent, not because the prompt asks. maxTurns: 6 is the turn budget bounding the worker's depth. The orchestration does not loosen the role boundaries; it inherits them. A fan-out is only as safe as its workers, and each worker here is a provisioned specialist, not an open-ended agent.

The orchestration, made explicit​

The whole audit is three pieces you can point at: a partition with fail-closed guards, a semaphore fan-out, and a normalized join.

The semaphore is worth dwelling on because it is the one control the SDK expresses genuinely better than the shell. The lab's fanOut runs a fixed pool of maxParallel "runner" coroutines, each pulling the next module index off a shared counter and awaiting its worker before pulling again:

async function fanOut(worker) {
  const results = new Array(modules.length);
  let next = 0;
  async function runner() {
    while (true) {
      const i = next++;
      if (i >= modules.length) return;
      results[i] = await worker(modules[i]);   // write into a FIXED slot
    }
  }
  const pool = Array.from({ length: Math.min(maxParallel, modules.length) }, runner);
  await Promise.all(pool);
  return results;
}

Two properties fall out of this, and both are the lesson's controls made concrete. First, at most maxParallel workers are ever in flight — there are only that many runners, so the fan-out cannot exceed the cap even for a moment. That is the runaway-concurrency control as a hard invariant, not a batch-timing side effect. Second, each worker writes into a fixed index slot (results[i]), so the join order does not depend on which worker finished first. That is what makes the result deterministic across concurrency: the workers race, but the report does not.

Run it, and prove it agrees with the shell​

The script ships with a --simulate mode (the default) whose worker is the same deterministic evidence read the shell workflow uses, so the run is reproducible and gradeable with no API in the loop — the orchestration (partition, semaphore, join) is identical to --live; only the worker body differs. This equivalence is the deep point of the whole module: the orchestration shape (fan out over a partition, cap concurrency, join into one normalized report) is independent of the implementation. Get the shape right and you can express it in bash or in the SDK; the answer is the same. The choice between them is not about correctness — both are correct — it is about which one expresses your complexity most clearly.

The live worker, and what it fails closed on​

Switch the worker from the deterministic read to a real SDK agent with --live. Each module now gets a query() call — a real read-only auditor agent — and the SDK's result stream gives you the token cost per worker. That requires the SDK installed and an API key, so on a bare workspace --live should refuse rather than silently fall back:

node labs/m10/audit-sdk.mjs --live
echo "exit=$?"
Expected output
audit-sdk: FAIL-CLOSED: --live requires @anthropic-ai/claude-agent-sdk installed (npm i @anthropic-ai/claude-agent-sdk) and an API key
exit=1

Exit 1 — fail-closed. This is the important design choice: --live does not quietly degrade to the deterministic worker when the SDK is missing. A "live" audit that silently ran the simulated worker would report mode: live while doing no real agent work — a lie the report could not distinguish from the truth. So the live path refuses when it cannot do what it claims. The live worker is a real agent or it is nothing; it never pretends. (To run it for real: npm i @anthropic-ai/claude-agent-sdk in the workspace and export an ANTHROPIC_API_KEY, then node labs/m10/audit-sdk.mjs --live.)

Comparing the two: behavior, tokens, latency​

Now the comparison that decides which to reach for. Line the two orchestrations up on the axes that matter:

AxisShell workflow (audit-orchestrate.sh)Agent SDK (audit-sdk.mjs)
BehaviorIdentical estate verdict — proven byte-for-byte equalIdentical estate verdict — proven byte-for-byte equal
ConcurrencyBatch barrier: drains a full batch before the next starts; idle lanes while waiting on the slow workerTrue semaphore: exactly N in flight, a new worker starts the instant one finishes; no idle lanes
Cost visibilityNone — the shell has no notion of tokens (the workers are shell reads)Per-worker usage + total_cost_usd from the result stream; the fan-out's token cost is a number you sum
Per-worker modelOne model would apply to all (if agents); awkward to varyPer-worker model: — haiku for the mechanical modules, opus for a hard one, decided in code
Dependenciesbash + jq onlyNode + the SDK + an API key
Right whenThe partition is fixed and small; you want zero deps and a CI gateThe orchestration is dynamic, cost-measured, or needs per-branch provisioning

Read the crossover. For the audit exactly as specified — four fixed modules, a pass/fail gate — the shell wins on simplicity and has no dependencies, and you should use it. The SDK earns its extra explicitness the moment you need what the shell cannot express: a token budget per fan-out ("cap the whole audit at $0.50"), a per-worker model decision ("the security module is subtle, run it on opus; the rest on haiku"), a genuine work queue over a dynamic module list, or measured latency to tune the concurrency cap. Those are not hypothetical — they are exactly the requirements that show up when a one-off audit becomes a platform capability run on every PR. The SDK is where the orchestration goes when it graduates from a checklist to an engine.

The rule of thumb

Reach for the shell workflow first — it is the taped checklist, and most orchestrations never outgrow it. Move to the Agent SDK when you need one of three things the shell expresses badly: measured cost (per-worker tokens), per-branch provisioning (different model/tools per worker, computed not hardcoded), or a true semaphore over dynamic, uneven work. If you need none of those, the SDK is complexity you are paying for and not using.

Where you will use this​

This is not an academic comparison — the crossover shows up in real platform work constantly:

  • A PR-time IaC audit that must report its own cost. Finance wants the security/cost scan on every infrastructure PR to stay under a token budget. The shell workflow cannot measure its tokens; the SDK's total_cost_usd per worker is exactly the number you gate on. This is the Agent Run Ledger (Module 4) applied per orchestration branch.
  • A fan-out where workers need different models. Auditing the networking module for subtle RBAC exposure genuinely wants opus; pricing the storage tier wants haiku. In the shell that is awkward; in the SDK it is a per-worker model: field — the M9 right-sizing decision, made per fan-out branch in code.
  • A dynamic partition. When the module list is discovered at runtime (every Terraform module in a repo, however many there are), the SDK's semaphore pulls from a queue of unknown length while holding the cap; the shell's fixed batch loop is clumsier here.
  • Tuning concurrency against real latency. With measured per-worker latency from the SDK, you can pick the max-parallel that saturates your rate limit without exceeding it — a decision the shell gives you no data to make.

In every case the shape is what you learned in the core lab — fan out over a partition, cap the concurrency, join into one normalized report, and never let a duplicate or a phantom or an anchored guess through. The SDK does not change the shape; it makes the shape's controls into code you can measure, compute, and compose. That is the whole reason to reach for it — and the whole reason not to, until you need it.
