Lab — Fan-Out and Synthesis

The lesson drew the shift from "which agent" to "how do the agents relate" — the orchestration decision table, the Ops Lead pattern, parallel hypotheses with honest synthesis, and the four anti-patterns (consensus theater, hidden assumptions, runaway concurrency, duplication) each with a structural control. This lab makes all of it runnable. You will route task profiles through the decision table, fan out the retry-storm incident across three independent hypotheses and synthesize them, catch consensus theater and disagreement and missing evidence, then run the reproducible estate audit as a bounded fan-out/join — and prove the answer is identical no matter how wide it runs.

By the end you will have two orchestrations you can defend to a reviewer: an incident fan-out that cannot count an anchored guess as confirmation, and an estate audit that cannot duplicate work or produce a different answer at a different concurrency — not "we were careful," but "here is the test that fails the build if either control breaks."

Where you are working

You start at the root of the agentic-ops-lab workspace. Three deterministic orchestration scripts ship in the repo — scripts/orchestration-topology.sh (the decision table), scripts/synthesize-hypotheses.sh (parallel-hypothesis synthesis), and scripts/audit-orchestrate.sh (the fan-out/join audit) — and the output contract the investigators are bound to is contracts/hypothesis-packet.schema.json.

The incident fan-out (Steps 3–5) runs real sre-investigator subagents against a live stack: docker compose --profile core plus an injected fault, no Kubernetes. The synthesis test vectors (Steps 6–8) and the estate audit (Steps 9–11) are deterministic reads of the repo and its fixtures, so they run anywhere and grade identically on any machine. In production the audit's per-module workers would be the security-reviewer and finops-analyst subagents from Module 9; here they are deterministic, so the orchestration is the same and the run is repeatable.

jq-1.7.1

Your versions will differ. claude, jq and docker must resolve; node is used by the Deep Dive (the Agent SDK script), not the core lab.

Start Claude in acceptEdits. The fan-out is normal iterative work — the parent writes hypothesis packets under agentops/ and you approve the investigators' Bash calls as they come:

Step 1 — Route a task profile through the decision table​

Before you orchestrate anything, decide the topology. orchestration-topology.sh takes the four facts about a task — is a human waiting (interactive), are there independent parallel sub-tasks (parallel), must it be reproducible/scriptable (deterministic), does it outlive this turn (longrunning) — and returns exactly one topology with a rationale. Start with the Ops Lead's bread and butter: an interactive job with one bounded step and no parallelism.

scripts/orchestration-topology.sh y n n n
Expected output
topology=subagent
why=interactive parent delegates one bounded job to a child and waits for its return

Interactive, not parallel, not reproducible-first, not long-running → subagent: the parent delegates one job and waits. This is sequential delegation, the Ops Lead's default.

Now change one fact — make it parallel. Independent sub-tasks while a human keeps steering is a different topology:

scripts/orchestration-topology.sh y y n n
Expected output
topology=fork
why=parallel exploration while the human keeps chatting — forks share parent context, parent stays live

Flip parallel to y and the answer changes to fork — parallel exploration where the parent stays live. One fact changed, the right topology changed with it. That is the whole point of routing before building.

Run the full sweep — all eight topologies in one pass — to see the table's structure:

for spec in "subagent:y n n n" "fork:y y n n" "background:y n n y" \
            "workflow:n y y n" "headless:n n y n" "routine:n n y y" \
            "team:n y n y" "skill:n n n n"; do
  label="${spec%%:*}"; args="${spec##*:}"
  t=$(scripts/orchestration-topology.sh $args | awk -F= '/^topology=/{print $2}')
  printf '%-11s (%s) -> %s\n' "$label" "$args" "$t"
done
Expected output
subagent    (y n n n) -> subagent
fork        (y y n n) -> fork
background  (y n n y) -> background
workflow    (n y y n) -> workflow
headless    (n n y n) -> headless
routine     (n n y y) -> routine
team        (n y n y) -> team
skill       (n n n n) -> skill

Every one of the eight topologies from the lesson's decision table, resolved deterministically from four yes/no facts. Read the split: the interactive topologies (subagent, fork, background) all start with y; the reproducible/unattended topologies (workflow, headless, routine) all have deterministic=y; team is the long-running collaborative case; skill is the base case where no second agent is needed. The routing is a fixed function of the task profile, not a judgment call.

Step 2 — Confirm the decision table fails closed​

A routing decision made from an ambiguous task profile is worse than no decision — it commits you to a topology you cannot defend. Feed the table a fact that is neither yes nor no:

scripts/orchestration-topology.sh y n maybe n
echo "exit=$?"
Expected output
orchestration-topology: FAIL-CLOSED: argument 'maybe' is not y/n (task profile must be unambiguous)
exit=1

Exit 1 — fail-closed. The table did not guess a topology from an ambiguous profile; it refused. "I cannot classify this task" and "pick a default" are not the same, and the safe one is to stop and make the task profile explicit. This is the Module 8 discipline applied to routing: an undecidable input blocks, it does not fall through to a plausible-looking answer.

Step 3 — Start the incident and read the contract the investigators must satisfy​

Everything so far has been routing. Now run an actual fan-out, with real agents, against a real incident.

Bring up the stack and inject the retry storm:

docker compose --profile core up -d
scripts/inject.sh retry-storm
Expected output
==> retry-storm active. Orders-api: 10 retries, 30s timeout. Inventory-api: 5s latency, 30% errors.

Confirm the incident is real before you investigate it — an investigation into a healthy system teaches nothing:

curl -s -o /dev/null -m 60 -w "status=%{http_code} time=%{time_total}s\n" http://localhost:8080/api/v1/products
status=503 time=27.183112s

A 503 after 27 seconds. INC-002 reports 28.3 seconds, so the injected fault reproduces the ticket. Your timing will differ by a second or two.

Three investigators are about to work in parallel, and the only thing that makes their agreement worth anything is that it was reached independently. That is not a promise you can extract from a prompt — it has to be a property of the artifact each one returns. Read the contract that makes it checkable:

jq '{required, root_cause_enum: .properties.root_cause.enum, derived_from: .properties.derived_from.description}' \
  contracts/hypothesis-packet.schema.json
Expected output
{
  "required": [
    "dimension",
    "root_cause",
    "status",
    "confidence",
    "sources",
    "derived_from"
  ],
  "root_cause_enum": [
    "retry-storm",
    "upstream-fault",
    "bad-deploy",
    "resource-exhaustion",
    "config-drift",
    null
  ],
  "derived_from": "Null when this conclusion came from this dimension's own evidence. Set to another dimension's name if the conclusion was taken from that peer — which the synthesizer rejects as consensus theater. Declaring it honestly is the point of the field."
}

Two fields carry the whole design. sources forces each investigator to cite evidence it obtained itself, and derived_from makes anchoring on a peer a declared fact rather than an invisible one.

Observe that root_cause is an enum and not free text. Why would free text break the synthesizer? Because agreement is decided by comparing these values. Two investigators who reach the identical conclusion but phrase it differently — "retry-storm" and "retry/backoff amplification against a slow upstream" — would be scored as disagreeing. A control that compares prose cannot detect agreement. The reasoning belongs in sources; the label has to be one of a fixed set.

Step 4 — Fan out three independent investigators​

Dispatch the fan-out. This is the Ops Lead pattern from the lesson: the parent holds the incident, three children each take one dimension, and the parent joins what comes back.

INC-002 is open: orders-api p95 is at 28s and the error rate is over 30%.

Dispatch three sre-investigator subagents IN PARALLEL, one per dimension:
  - application-retry   — the client/retry path in app/orders-api/src/
  - platform-resource   — container and process resource pressure
  - recent-change       — the change timeline

Give each investigator ONLY its own dimension. Do not pass one investigator
another's findings — independence is the whole point of the fan-out.

Each must write agentops/hypotheses/<dimension>.json conforming to
contracts/hypothesis-packet.schema.json. Read that schema first and honour it:
  - `root_cause` is an ENUM, not prose. Put your reasoning in `sources`.
  - `sources` cites the commands you actually ran and the files you actually read.
  - `derived_from` is null unless you genuinely took your conclusion from a peer.
  - `missing` is ONLY for evidence that would change YOUR OWN dimension's verdict.

The stack is up on localhost:8080 and localhost:8081. Fix nothing.

What Claude does. It reads the schema, then launches three sre-investigator subagents at once. Each gets a fresh context containing only its own dimension — that is what makes them independent; a subagent cannot see a sibling's transcript. Each runs its own commands: curl against both services, docker logs, docker inspect, git log.

What you observe. Something the prompt did not ask for, reported back by the parent:

Note: all three agents hit the authority-matrix write block (sre-investigator role has write: []) — none could write its own file. I persisted all three manually from their reported JSON.

The investigators have no write authority. Read contracts/authority-matrix.yaml and you will see why — sre-investigator gets read on app/, observability/, incidents/ and a two-script execute list, and write: []. So the Ops Lead does the persisting. That is the correct division and worth naming: the workers produce findings, the orchestrator owns the join and the write. An investigator that could write its own conclusion into shared state could also overwrite a peer's.

Inspect what came back, and check independence before you trust any of it:

jq -r '[.dimension, .status, (.root_cause//"null"), (.derived_from|tostring), ((.sources|length|tostring)+" sources")] | @tsv' \
  agentops/hypotheses/*.json | column -t -s$'\t'
Expected output
application-retry  supported  retry-storm  null  6 sources
platform-resource  refuted    null         null  11 sources
recent-change      supported  retry-storm  null  7 sources

Point-in-time — your source counts and confidences will differ, and so may a status. Read the columns in the order that matters. derived_from is null on all three: nobody anchored on a peer. Every packet carries its own sources. Only then does the fourth column mean anything — two dimensions independently reached retry-storm, and the third refuted its own hypothesis.

That refutation is worth as much as the agreements. platform-resource went looking for resource exhaustion, found no limits, no OOM kills, no restarts, and said so. An investigator that reports a negative is doing the job; one that manufactures a supporting finding because the other two agreed is consensus theater with extra steps.

Read one packet in full to see what "its own evidence" actually means:

jq '{dimension,root_cause,status,confidence,derived_from,sources}' agentops/hypotheses/application-retry.json
Expected output
{
  "dimension": "application-retry",
  "root_cause": "retry-storm",
  "status": "supported",
  "confidence": "high",
  "derived_from": null,
  "sources": [
    "app/orders-api/src/inventory_client.py:21-39 (_request_with_retry: retry_count+1 attempts, exponential backoff delay_ms * 2**attempt)",
    "app/orders-api/src/config.py:4-14 (defaults: retry_count=3, retry_delay_ms=1000, timeout_ms=5000)",
    "curl http://localhost:8081/api/v1/products (direct to inventory-api) -> http_code=200, time_total=5.01s, repeated 3x consistently ~5.0-5.03s",
    "curl http://localhost:8080/api/v1/products (via orders-api) -> http_code=503, time_total=27.55s",

    "docker logs m10ws-orders-api-1 --tail 60 | grep -i retry -> repeated 'retry 1/3', 'retry 2/3', 'retry 3/3' for GET /api/v1/products and /api/v1/products/PROD-001, including one 'Server error 500 Internal Server Error'"
  ]
}

Your container name and numbers will differ. Every line is a command it ran or a file and line range it read, and the argument is reconstructable from them: the upstream is slow but healthy at 5.01s, the client's timeout is 5000ms, so nearly every call times out at the boundary and burns its full retry budget with exponential backoff — which sums to the 27 seconds the user sees. Nobody handed it that chain.

Step 5 — Synthesize the real packets​

Now join them. The synthesizer checks independence first, and only then looks at whether the dimensions agree:

jq -s '.' agentops/hypotheses/*.json | scripts/synthesize-hypotheses.sh
Expected output
verdict=corroborated
root_cause=retry-storm
detail=2 independent dimension(s) converged on the same root cause from their OWN evidence — real corroboration, not an echo.
follow_ups=docker exec into postgres for pg_stat_activity connection counts - denied; docker stats (live CPU%/memory% per container) - command denied by permission system; docker top for process/thread counts - denied; host disk usage (df -h) - denied; orders-api RETRY_COUNT/TIMEOUT_MS env values (docker compose exec denied by sandbox)

corroborated — two independent dimensions on the same enum label, from separate evidence, with a third dimension actively ruling out an alternative. This is the triple-blind study, not the group chat. The synthesis raises confidence precisely because independence was verified first.

Now read follow_ups, because it is the honest part. Those are gaps the investigators named themselves, and almost all of them are denied commands — docker stats, docker top, docker compose exec. The fan-out's evidence ceiling is set by the authority you gave the workers, not by how hard they tried. They are reported and they do not block, because the dimensions that named them still settled their own questions. A gap only blocks when the dimension naming it came back inconclusive — which is exactly the case you force next.

Two controls this lab had to fix to get here

Reaching corroborated from real agents took two changes to the control itself, and both are worth knowing because they are the generic failure modes of any synthesis gate.

root_cause had to become an enum. As free text, two agents that agreed perfectly emitted different strings and scored as disagreement. Agreement compared as prose is undetectable.

A missing entry now blocks only on an inconclusive packet. The guard used to block on any gap from any packet. Real investigators always name what they could not see, so the synthesis withheld forever and corroborated was unreachable — the outcome was only ever achievable with hand-written packets. A control that passes only on artifacts a human wrote is not a control.

Step 6 — Catch consensus theater​

Your real fan-out came back clean. That is the good case, and it is exactly why you cannot test a control with it — a guard you have never seen fire is a guard you are trusting, not verifying.

The next three steps feed the synthesizer hand-written test vectors: small packets crafted to trip one guard each. They are deliberately synthetic, and that is the point — you are testing the control, not investigating an incident. The packets your agents produce are the artifact; these are the unit tests around the thing that judges them.

First the dangerous case. Suppose the second investigator did not reason independently — it read the first one's conclusion and anchored on it. In the packet, that shows up as derived_from: "application-retry": the platform-resource hypothesis was derived from a peer, not from its own evidence. Run it:

printf '[
  {"dimension":"application-retry","root_cause":"retry-storm","status":"supported","confidence":"high","sources":["curl -s http://localhost:8080/metrics"],"derived_from":null},
  {"dimension":"platform-resource","root_cause":"retry-storm","status":"supported","confidence":"high","sources":["docker stats"],"derived_from":"application-retry"}
]' | scripts/synthesize-hypotheses.sh
echo "exit=$?"
Expected output
INVALID: consensus theater — packet(s) [platform-resource] are derived_from a peer's hypothesis, not independent evidence. Independent agreement requires independent evidence.
exit=4

Exit 4 — rejected as contamination. Both packets "agree" on the retry storm, and a naive synthesis would call that two confirmations. But the second one anchored on the first, so it is not a second data point — it is the first one wearing a second coat. The synthesizer refuses to let an anchored guess inflate confidence. This is the consensus-theater control from the lesson made runnable: agreement only counts when it is independent.

Step 7 — Surface disagreement, don't average it​

Sometimes independent investigators genuinely disagree — and that disagreement is signal, not a problem to smooth over. Here the application dimension says "retry storm" and the recent-change dimension says "bad deploy," both from their own evidence:

printf '[
  {"dimension":"application-retry","root_cause":"retry-storm","status":"supported","confidence":"high","sources":["curl -s /metrics"],"derived_from":null},
  {"dimension":"recent-change","root_cause":"bad-deploy","status":"supported","confidence":"high","sources":["git log --oneline -20"],"derived_from":null}
]' | scripts/synthesize-hypotheses.sh
Expected output
verdict=disagreement
root_cause=application-retry=>retry-storm; recent-change=>bad-deploy
detail=independent dimensions disagree on the root cause — a split is signal. Resolve by evidence, not by majority vote.

disagreement — and the synthesis names both positions instead of picking a winner. Two independent dimensions pointing at different causes does not mean "average them" or "majority rules"; it means the cause is subtler than either dimension saw alone, and you resolve it by gathering the evidence that discriminates between them. Hiding the split behind a confident single answer is exactly how an incident gets misdiagnosed.

Step 8 — Loop on missing evidence​

The last synthesis case: a dimension came back inconclusive. Declaring a root cause now would be concluding on partial data. Here platform-resource is inconclusive and names a gap it did not check:

printf '[
  {"dimension":"application-retry","root_cause":"retry-storm","status":"supported","confidence":"high","sources":["curl -s /metrics"],"derived_from":null},
  {"dimension":"platform-resource","root_cause":null,"status":"inconclusive","confidence":"low","sources":["docker stats"],"derived_from":null,"missing":["recent-change timeline not checked"]}
]' | scripts/synthesize-hypotheses.sh
Expected output
verdict=need-more-evidence
missing=platform-resource, recent-change timeline not checked
detail=synthesis withheld — a hypothesis is inconclusive or a dimension is unchecked; loop before concluding.

need-more-evidence — the synthesis withholds a verdict and names the gap. Even though one dimension confidently supports the retry storm, the synthesizer will not declare a winner while another dimension is inconclusive. Under incident pressure the instinct is to run with the confident answer; the control forces another pass instead. This is the missing-evidence loop from the lesson.

Compare this with the follow_ups line in Step 5 and note what is different. Both name gaps. This one blocks because the dimension that named it came back inconclusive — it never settled its own question. Those did not block because the dimensions that named them settled theirs and were simply honest about what they could not see. The distinction is the whole guard: an unsettled dimension stops the synthesis, an unanswered footnote does not.

Confirm the synthesizer fails closed when there is nothing to synthesize — a single packet is not a parallel fan-out:

printf '[{"dimension":"application-retry","root_cause":"x","status":"supported","confidence":"high","sources":["a"],"derived_from":null}]' \
  | scripts/synthesize-hypotheses.sh
echo "exit=$?"
Expected output
synthesize-hypotheses: FAIL-CLOSED: need >=2 hypothesis packets to synthesize (got 1) — one agent is not parallel
exit=1

Exit 1 — one investigator cannot corroborate anything; there is no independence to check with a single packet. The synthesizer refuses rather than rubber-stamp a lone hypothesis as if it were a synthesis.

Step 9 — Run the reproducible estate audit​

Switch topologies. The Terraform plan needs auditing across four modules — networking, database, compute, storage — for security exposure and cost blast radius, and it must run the same way every time so it can gate a merge. This is the workflow topology: a deterministic fan-out over the module partition, one bounded audit per module, joined into one normalized report. Run it:

scripts/audit-orchestrate.sh
Expected output
{
  "audit": "terraform-estate",
  "max_parallel": 2,
  "modules_audited": [
    "networking",
    "database",
    "compute",
    "storage"
  ],
  "total_security_findings": 7,
  "total_cost_delta_usd": 2847,
  "blocking": [],
  "verdict": "flag",
  "evidence": [
    { "module": "networking", "security_findings": 7, "cost_delta_usd": 0, "verdict": "flag" },
    { "module": "database", "security_findings": 0, "cost_delta_usd": 2847, "verdict": "flag" },
    { "module": "compute", "security_findings": 0, "cost_delta_usd": 0, "verdict": "clean" },
    { "module": "storage", "security_findings": 0, "cost_delta_usd": 0, "verdict": "clean" }
  ]

One normalized report from a four-way fan-out. The evidence is real and sourced: networking carries 7 0.0.0.0/0 findings (the wide-open CIDRs in infra/modules/networking/main.tf), database carries a $2847/mo cost delta (the db.r6g.4xlarge blow-up in the oversize plan), and compute and storage come back clean. The estate verdict is flag — the estate has both a security problem and a cost problem, even though no single module trips both. The join sees the whole estate; a per-module view would miss that the estate as a whole needs a human before it merges.

Step 10 — Prove the audit is deterministic across concurrency​

The property that makes a workflow CI-able is that its answer does not depend on how many workers happened to run at once. --max-parallel is the concurrency cap — the runaway-concurrency control from the lesson. Run the audit at three widths and compare the results with the max_parallel field removed:

a=$(scripts/audit-orchestrate.sh --max-parallel 1 | jq -S 'del(.max_parallel)')
b=$(scripts/audit-orchestrate.sh --max-parallel 2 | jq -S 'del(.max_parallel)')
c=$(scripts/audit-orchestrate.sh --max-parallel 4 | jq -S 'del(.max_parallel)')
[ "$a" = "$b" ] && [ "$a" = "$c" ] \
  && echo "IDENTICAL at width 1/2/4 — concurrency changes speed, not the answer" \
  || echo "DIFFER"
Expected output
IDENTICAL at width 1/2/4 — concurrency changes speed, not the answer

The cap changes how fast the audit runs, never what it concludes. That is the whole reason this can be a merge gate: an orchestration whose verdict flips depending on whether two or four workers ran is a coin flip, not a gate. The --max-parallel cap also bounds the runaway — you never spawn more than N module audits at once, so the fan-out cannot exhaust a rate limit or the machine. Width has a stopping rule, exactly like the turn budget bounded depth in Module 9.

Step 11 — Prove the structural controls: no duplication, no phantom, no bad cap​

Three fail-closed cases, one per structural control. First, duplication — fanning out over a partition where a module appears twice would audit it twice, the exact overlap the workflow exists to prevent:

scripts/audit-orchestrate.sh --modules "networking networking"
echo "exit=$?"
Expected output
audit-orchestrate: FAIL-CLOSED: duplicate module(s) in fan-out: networking
exit=1

Exit 1 — the partition must have no repeats. A repeated module is duplicated work by construction, so the orchestrator refuses the fan-out rather than audit the same ground twice.

Next, a phantom module — a fan-out over a partition unit that does not exist:

scripts/audit-orchestrate.sh --modules "networking phantom"
echo "exit=$?"
Expected output
audit-orchestrate: FAIL-CLOSED: no module directory infra/modules/phantom
exit=1

Exit 1 — the orchestrator will not silently audit a partition that includes a unit with no directory. A fan-out over a phantom is a bug; it blocks instead of returning a report that quietly covers less than you asked.

Finally, a bad concurrency cap — an orchestration with zero workers is a misconfiguration, not a valid run:

scripts/audit-orchestrate.sh --max-parallel 0
echo "exit=$?"
Expected output
audit-orchestrate: FAIL-CLOSED: --max-parallel must be >= 1 (got 0)
exit=1

Exit 1 — a cap below 1 would launch no work. The orchestrator rejects it rather than run an empty fan-out and report success on an audit it never performed.

Step 12 — Let the repository certify the orchestration​

Run the module grader. It drives the whole decision-table-and-controls matrix — every topology the table routes, the fail-closed on an ambiguous profile, all four synthesis outcomes (corroborated, consensus-theater rejected, disagreement, need-more-evidence), the audit's fan-out/join and its determinism across concurrency, and the three structural fail-closed cases.

./scripts/grade.sh m10
Expected output
Grading: Module m10
========================

  ✓ DISAGREEMENT: independent dimensions that diverge on root cause synthesize to 'disagreement' — a split is surfaced as signal, not averaged into a majority vote
  ✓ MISSING EVIDENCE: an inconclusive dimension makes the synthesis withhold a verdict ('need-more-evidence') rather than conclude on partial data

  ✓ CONTROL DESIGN: a settled dimension that names a gap yields a verdict with non-blocking follow_ups — a guard that blocked on every gap would be unsatisfiable against real investigators, who always name what they could not see
