Lab — Orchestrate Without Chaos

The lesson drew the shift from "which agent" to "how do the agents relate" — the orchestration decision table, the Ops Lead pattern, parallel hypotheses with honest synthesis, and the four anti-patterns (consensus theater, hidden assumptions, runaway concurrency, duplication) each with a structural control. This lab makes all of it runnable. You will route task shapes through the decision table, fan out the retry-storm incident across three independent hypotheses and synthesize them, catch consensus theater and disagreement and missing evidence, then run the reproducible estate audit as a bounded fan-out/join — and prove the answer is identical no matter how wide it runs.

By the end you will have two orchestrations you can defend to a reviewer: an incident fan-out that cannot count an anchored guess as confirmation, and an estate audit that cannot duplicate work or produce a different answer at a different concurrency — not "we were careful," but "here is the test that fails the build if either control breaks."

Where you are working

You start at the root of the agentic-ops-lab workspace. Three deterministic orchestration scripts ship in the repo — scripts/orchestration-topology.sh (the decision table), scripts/synthesize-hypotheses.sh (parallel-hypothesis synthesis), and scripts/audit-orchestrate.sh (the fan-out/join audit). They encode the shapes from the lesson with no model in the loop, so the orchestration is reproducible and gradeable and this lab runs anywhere — you do not need a live cluster. In production the audit's per-module workers would be the security-reviewer and finops-analyst subagents from Module 9; here they are deterministic reads of the repo's own fixtures, so the orchestration shape is identical but the run is repeatable.

Step 0 — Prerequisites​

Confirm your tools. All three scripts use jq; the topology and synthesis scripts are plain bash.

claude --version
jq --version
node --version
Expected output
2.1.197 (Claude Code)
jq-1.7.1
v22.22.2

Your versions will differ. claude and jq must resolve; node is used by the Deep Dive (the Agent SDK script), not the core lab.

Step 1 — Route a task shape through the decision table​

Before you orchestrate anything, decide the shape. orchestration-topology.sh takes the four facts about a task — is a human waiting (interactive), are there independent parallel sub-tasks (parallel), must it be reproducible/scriptable (deterministic), does it outlive this turn (longrunning) — and returns exactly one topology with a rationale. Start with the Ops Lead's bread and butter: an interactive job with one bounded step and no parallelism.

scripts/orchestration-topology.sh y n n n
Expected output
topology=subagent
why=interactive parent delegates one bounded job to a child and waits for its return

Interactive, not parallel, not reproducible-first, not long-running → subagent: the parent delegates one job and waits. This is sequential delegation, the Ops Lead's default.

Now change one fact — make it parallel. Independent sub-tasks while a human keeps steering is a different shape:

scripts/orchestration-topology.sh y y n n
Expected output
topology=fork
why=parallel exploration while the human keeps chatting — forks share parent context, parent stays live

Flip parallel to y and the answer changes to fork — parallel exploration where the parent stays live. One fact changed, the right shape changed with it. That is the whole point of routing before building.

Run the full sweep — all eight shapes in one pass — to see the table's structure:

for spec in "subagent:y n n n" "fork:y y n n" "background:y n n y" \
            "workflow:n y y n" "headless:n n y n" "routine:n n y y" \
            "team:n y n y" "skill:n n n n"; do
  label="${spec%%:*}"; args="${spec##*:}"
  t=$(scripts/orchestration-topology.sh $args | awk -F= '/^topology=/{print $2}')
  printf '%-11s (%s) -> %s\n' "$label" "$args" "$t"
done
Expected output
subagent    (y n n n) -> subagent
fork        (y y n n) -> fork
background  (y n n y) -> background
workflow    (n y y n) -> workflow
headless    (n n y n) -> headless
routine     (n n y y) -> routine
team        (n y n y) -> team
skill       (n n n n) -> skill

Every one of the eight topologies from the lesson's decision table, resolved deterministically from four yes/no facts. Read the split: the interactive shapes (subagent, fork, background) all start with y; the reproducible/unattended shapes (workflow, headless, routine) all have deterministic=y; team is the long-running collaborative case; skill is the base case where no second agent is needed. The routing is a fixed function of the task shape, not a judgment call.

Step 2 — Confirm the decision table fails closed​

A routing decision made from an ambiguous task shape is worse than no decision — it commits you to a topology you cannot defend. Feed the table a fact that is neither yes nor no:

scripts/orchestration-topology.sh y n maybe n
echo "exit=$?"
Expected output
orchestration-topology: FAIL-CLOSED: argument 'maybe' is not y/n (task shape must be unambiguous)
exit=1

Exit 1 — fail-closed. The table did not guess a topology from an ambiguous shape; it refused. "I cannot classify this task" and "pick a default" are not the same, and the safe one is to stop and make the task shape explicit. This is the Module 8 discipline applied to routing: an undecidable input blocks, it does not fall through to a plausible-looking answer.

Step 3 — Fan out the retry-storm incident​

INC-002 is open: orders-api latency is at 28 seconds, error rate over 30%. Three independent hypotheses are on the table — application/retry, platform/resource, recent-change — and you fan them out to three investigators, each on its own dimension, each reasoning from its own evidence. Each returns a hypothesis packet. When all three come back supporting the same root cause from independent sources, you synthesize:

printf '[
  {"dimension":"application-retry","root_cause":"retry-storm","status":"supported","confidence":"high","sources":["curl -s http://localhost:8080/metrics | grep upstream_retries","app/orders-api/src/client.py:44"],"derived_from":null},
  {"dimension":"platform-resource","root_cause":"retry-storm","status":"supported","confidence":"medium","sources":["docker stats --no-stream","kubectl top pods"],"derived_from":null},
  {"dimension":"recent-change","root_cause":"retry-storm","status":"supported","confidence":"medium","sources":["git log --oneline -20","incidents/INC-002-retry-storm.md"],"derived_from":null}
]' | scripts/synthesize-hypotheses.sh
Expected output
verdict=corroborated
root_cause=retry-storm
detail=3 independent dimension(s) converged on the same root cause from their OWN evidence — real corroboration, not an echo.

corroborated — and note why it counts: each of the three packets carries its own sources and derived_from is null, so the agreement is three independent investigations landing on the same cause, not one guess echoed three times. This is the triple-blind study, not the group chat. The synthesis raises confidence precisely because independence was verified first.

Step 4 — Catch consensus theater​

Now the dangerous shape. Suppose the second investigator did not reason independently — it read the first one's conclusion and anchored on it. In the packet, that shows up as derived_from: "application-retry": the platform-resource hypothesis was derived from a peer, not from its own evidence. Run it:

printf '[
  {"dimension":"application-retry","root_cause":"retry-storm","status":"supported","confidence":"high","sources":["curl -s http://localhost:8080/metrics"],"derived_from":null},
  {"dimension":"platform-resource","root_cause":"retry-storm","status":"supported","confidence":"high","sources":["docker stats"],"derived_from":"application-retry"}
]' | scripts/synthesize-hypotheses.sh
echo "exit=$?"
Expected output
INVALID: consensus theater — packet(s) [platform-resource] are derived_from a peer's hypothesis, not independent evidence. Independent agreement requires independent evidence.
exit=4

Exit 4 — rejected as contamination. Both packets "agree" on the retry storm, and a naive synthesis would call that two confirmations. But the second one anchored on the first, so it is not a second data point — it is the first one wearing a second coat. The synthesizer refuses to let an anchored guess inflate confidence. This is the consensus-theater control from the lesson made runnable: agreement only counts when it is independent.

Step 5 — Surface disagreement, don't average it​

Sometimes independent investigators genuinely disagree — and that disagreement is signal, not a problem to smooth over. Here the application dimension says "retry storm" and the recent-change dimension says "bad deploy," both from their own evidence:

printf '[
  {"dimension":"application-retry","root_cause":"retry-storm","status":"supported","confidence":"high","sources":["curl -s /metrics"],"derived_from":null},
  {"dimension":"recent-change","root_cause":"bad-deploy","status":"supported","confidence":"high","sources":["git log --oneline -20"],"derived_from":null}
]' | scripts/synthesize-hypotheses.sh
Expected output
verdict=disagreement
root_cause=application-retry=>retry-storm; recent-change=>bad-deploy
detail=independent dimensions disagree on the root cause — a split is signal. Resolve by evidence, not by majority vote.

disagreement — and the synthesis names both positions instead of picking a winner. Two independent dimensions pointing at different causes does not mean "average them" or "majority rules"; it means the cause is subtler than either dimension saw alone, and you resolve it by gathering the evidence that discriminates between them. Hiding the split behind a confident single answer is exactly how an incident gets misdiagnosed.

Step 6 — Loop on missing evidence​

The last synthesis case: a dimension came back inconclusive. Declaring a root cause now would be concluding on partial data. Here platform-resource is inconclusive and names a gap it did not check:

printf '[
  {"dimension":"application-retry","root_cause":"retry-storm","status":"supported","confidence":"high","sources":["curl -s /metrics"],"derived_from":null},
  {"dimension":"platform-resource","root_cause":null,"status":"inconclusive","confidence":"low","sources":["docker stats"],"derived_from":null,"missing":["recent-change timeline not checked"]}
]' | scripts/synthesize-hypotheses.sh
Expected output
verdict=need-more-evidence
missing=platform-resource, recent-change timeline not checked
detail=synthesis withheld — a hypothesis is inconclusive or a dimension is unchecked; loop before concluding.

need-more-evidence — the synthesis withholds a verdict and names the gap. Even though one dimension confidently supports the retry storm, the synthesizer will not declare a winner while another dimension is inconclusive. Under incident pressure the instinct is to run with the confident answer; the control forces another pass instead. This is the missing-evidence loop from the lesson.

Confirm the synthesizer fails closed when there is nothing to synthesize — a single packet is not a parallel fan-out:

printf '[{"dimension":"application-retry","root_cause":"x","status":"supported","confidence":"high","sources":["a"],"derived_from":null}]' \
  | scripts/synthesize-hypotheses.sh
echo "exit=$?"
Expected output
synthesize-hypotheses: FAIL-CLOSED: need >=2 hypothesis packets to synthesize (got 1) — one agent is not parallel
exit=1

Exit 1 — one investigator cannot corroborate anything; there is no independence to check with a single packet. The synthesizer refuses rather than rubber-stamp a lone hypothesis as if it were a synthesis.

Step 7 — Run the reproducible estate audit​

Switch shapes. The Terraform plan needs auditing across four modules — networking, database, compute, storage — for security exposure and cost blast radius, and it must run the same way every time so it can gate a merge. This is the workflow topology: a deterministic fan-out over the module partition, one bounded audit per module, joined into one normalized report. Run it:

scripts/audit-orchestrate.sh
Expected output
{
  "audit": "terraform-estate",
  "max_parallel": 2,
  "modules_audited": [
    "networking",
    "database",
    "compute",
    "storage"
  ],
  "total_security_findings": 7,
  "total_cost_delta_usd": 2847,
  "blocking": [],
  "verdict": "flag",
  "evidence": [
    { "module": "networking", "security_findings": 7, "cost_delta_usd": 0, "verdict": "flag" },
    { "module": "database", "security_findings": 0, "cost_delta_usd": 2847, "verdict": "flag" },
    { "module": "compute", "security_findings": 0, "cost_delta_usd": 0, "verdict": "clean" },
    { "module": "storage", "security_findings": 0, "cost_delta_usd": 0, "verdict": "clean" }
  ]
}

One normalized report from a four-way fan-out. The evidence is real and sourced: networking carries 7 0.0.0.0/0 findings (the wide-open CIDRs in infra/modules/networking/main.tf), database carries a $2847/mo cost delta (the db.r6g.4xlarge blow-up in the oversize plan), and compute and storage come back clean. The estate verdict is flag — the estate has both a security problem and a cost problem, even though no single module trips both. The join sees the whole estate; a per-module view would miss that the estate as a whole needs a human before it merges.

Step 8 — Prove the audit is deterministic across concurrency​

The property that makes a workflow CI-able is that its answer does not depend on how many workers happened to run at once. --max-parallel is the concurrency cap — the runaway-concurrency control from the lesson. Run the audit at three widths and compare the results with the max_parallel field removed:

a=$(scripts/audit-orchestrate.sh --max-parallel 1 | jq -S 'del(.max_parallel)')
b=$(scripts/audit-orchestrate.sh --max-parallel 2 | jq -S 'del(.max_parallel)')
c=$(scripts/audit-orchestrate.sh --max-parallel 4 | jq -S 'del(.max_parallel)')
[ "$a" = "$b" ] && [ "$a" = "$c" ] \
  && echo "IDENTICAL at width 1/2/4 — concurrency changes speed, not the answer" \
  || echo "DIFFER"
Expected output
IDENTICAL at width 1/2/4 — concurrency changes speed, not the answer

The cap changes how fast the audit runs, never what it concludes. That is the whole reason this can be a merge gate: an orchestration whose verdict flips depending on whether two or four workers ran is a coin flip, not a gate. The --max-parallel cap also bounds the runaway — you never spawn more than N module audits at once, so the fan-out cannot exhaust a rate limit or the machine. Width has a stopping rule, exactly like the turn budget bounded depth in Module 9.

Step 9 — Prove the structural controls: no duplication, no phantom, no bad cap​

Three fail-closed cases, one per structural control. First, duplication — fanning out over a partition where a module appears twice would audit it twice, the exact overlap the workflow exists to prevent:

scripts/audit-orchestrate.sh --modules "networking networking"
echo "exit=$?"
Expected output
audit-orchestrate: FAIL-CLOSED: duplicate module(s) in fan-out: networking
exit=1

Exit 1 — the partition must have no repeats. A repeated module is duplicated work by construction, so the orchestrator refuses the fan-out rather than audit the same ground twice.

Next, a phantom module — a fan-out over a partition unit that does not exist:

scripts/audit-orchestrate.sh --modules "networking phantom"
echo "exit=$?"
Expected output
audit-orchestrate: FAIL-CLOSED: no module directory infra/modules/phantom
exit=1

Exit 1 — the orchestrator will not silently audit a partition that includes a unit with no directory. A fan-out over a phantom is a bug; it blocks instead of returning a report that quietly covers less than you asked.

Finally, a bad concurrency cap — an orchestration with zero workers is a misconfiguration, not a valid run:

scripts/audit-orchestrate.sh --max-parallel 0
echo "exit=$?"
Expected output
audit-orchestrate: FAIL-CLOSED: --max-parallel must be >= 1 (got 0)
exit=1

Exit 1 — a cap below 1 would launch no work. The orchestrator rejects it rather than run an empty fan-out and report success on an audit it never performed.

Step 10 — Let the repository certify the orchestration​

Run the module grader. It drives the whole decision-table-and-controls matrix — every topology the table routes, the fail-closed on an ambiguous shape, all four synthesis outcomes (corroborated, consensus-theater rejected, disagreement, need-more-evidence), the audit's fan-out/join and its determinism across concurrency, and the three structural fail-closed cases.

./scripts/grade.sh m10
Expected output
Grading: Module m10
========================

Checking: Orchestration Topologies — decision table, parallel-hypothesis synthesis, reproducible fan-out audit

  ✓ the decision table routes an interactive, sequential, single-job task to a SUBAGENT (delegate and wait)
  ✓ an interactive task with independent parallel sub-tasks routes to a FORK (parallel, parent stays live)
  ✓ a reproducible, parallel task routes to a WORKFLOW (deterministic fan-out/join, CI-able)
  ✓ a reproducible, non-interactive, one-shot task routes to HEADLESS (claude -p)
  ✓ a reproducible, long-running task routes to a ROUTINE (scheduled workflow)
  ✓ a single interactive job with no parallelism and no long-running work needs no orchestration at all — a SKILL
  ✓ FAIL-CLOSED: the decision table refuses an ambiguous task shape (exit 1) rather than guessing a topology
  ✓ three INDEPENDENT hypotheses converging on one root cause synthesize to 'corroborated' — real agreement from independent evidence
  ✓ CONSENSUS THEATER: a hypothesis derived_from a peer (not its own evidence) is rejected as contamination (exit 4), not counted as a confirmation
  ✓ DISAGREEMENT: independent dimensions that diverge on root cause synthesize to 'disagreement' — a split is surfaced as signal, not averaged into a majority vote
  ✓ MISSING EVIDENCE: an inconclusive dimension makes the synthesis withhold a verdict ('need-more-evidence') rather than conclude on partial data
  ✓ FAIL-CLOSED: the synthesizer blocks (exit 1) on a single packet — one agent is not a parallel fan-out and cannot corroborate anything
  ✓ the estate audit fans out over all four modules and joins into one normalized report covering each module exactly once (no duplication)
  ✓ the join collects REAL, sourced evidence: the networking module's seven 0.0.0.0/0 CIDRs and the database module's cost spike sum into the estate verdict
  ✓ RUNAWAY CONTROL: the answer is identical at --max-parallel 1, 2, and 4 — the concurrency cap changes speed, never the result (that is what makes it CI-able)
  ✓ DUPLICATION GUARD: fanning out over a partition with a repeated module fails closed (exit 1) — a module must be audited exactly once
  ✓ FAIL-CLOSED: a fan-out over a module that does not exist blocks (exit 1) rather than silently auditing a phantom partition
  ✓ FAIL-CLOSED: a concurrency cap below 1 is rejected (exit 1) — an orchestration with zero workers is a misconfiguration, not a valid run

========================
RESULT: PASS (18 passed)

Eighteen green. The grader ran the same orchestration you ran by hand — the topology routing, the synthesis outcomes including the consensus-theater rejection, the deterministic fan-out audit, and every fail-closed case. This is the payoff of orchestration-as-code: the shapes and their controls are tested, not asserted. A change that lets the synthesizer count an anchored guess, or lets the audit produce a different answer at a different width, fails this build.

Step 11 — Teardown​

The three orchestration scripts are module deliverables — leave them; the Deep Dive rebuilds the audit as an Agent SDK script and compares the two. Nothing ephemeral was started: the scripts operate on the repo's files and fixtures, not on a running cluster, so no services need stopping.

git status --short scripts/orchestration-topology.sh scripts/synthesize-hypotheses.sh scripts/audit-orchestrate.sh
Expected output
?? scripts/audit-orchestrate.sh
?? scripts/orchestration-topology.sh
?? scripts/synthesize-hypotheses.sh

If you built the scripts into a base workspace, git status shows them as untracked or modified. Leave them in place — they are now part of the workspace's orchestration layer. If your workspace already shipped all three, the tree may be clean.

You routed task shapes through the decision table and watched it fail closed on an ambiguous one. You fanned out an incident across three independent hypotheses and synthesized them honestly — corroborating only independent agreement, rejecting consensus theater, surfacing disagreement instead of averaging it, and looping on missing evidence. You ran the estate audit as a bounded fan-out/join and proved it produces the same answer at every concurrency, with structural guards against duplication and phantom partitions. None of it depends on an agent choosing to behave — the controls are properties of the orchestration, tested in CI. The Deep Dive now rebuilds the audit in code with the Agent SDK, where the partition, the cap, and the join stop being shapes you trust the shell to hold and become lines you wrote and can measure — on behavior, tokens, and latency — against the shell workflow.
