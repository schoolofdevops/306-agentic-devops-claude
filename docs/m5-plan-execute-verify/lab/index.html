Lab — A Change Under Contract

orders-api has no way to report which version of itself is running. Release checks cannot confirm what is deployed, and during an incident nobody can answer "is the fix actually out?" You are going to add GET /version — a genuinely small change, deliberately, because the point of this lab is not the change.

The point is everything around it. You will write a task contract whose acceptance criteria are shell commands rather than sentences, install the workflow harness that runs the lesson's loop for you, let it work test-first inside a worktree, and then try to talk it into cheating so you can watch the contract catch it.

Where you are working

Start at the root of the agentic-ops-lab workspace. The change lands in app/orders-api/, the contract and done record in agentops/.

Where you run everything. All commands below, and every claude session, run from the root of the agentic-ops-lab workspace you cloned in setup:

cd ~/agentic-ops-lab
Who types where

A ```bash fence is a shell command. A plain fence with no language is a prompt — paste it into the Claude session. Prompts are followed by What Claude does and What you observe.

Step 1 — Install the harness​

The lesson taught Plan → Execute → Verify → Goal. A workflow harness is that loop packaged so an agent runs it without you narrating each phase. You are going to install the one this course itself was built with.

Look at what a harness run leaves behind — those artifacts are already in your workspace:

Four of those fourteen skills are the lesson's loop under different names:

Note the last block, and connect it to Module 4: the harness costs ~688 tokens on every session, whether you use it or not. That is a real, measurable price for the discipline. It is a good trade for a multi-step change and a bad one for a typo fix, and now you can say so with a number.

Scoped on purpose

This lab runs four skills. It does not run subagent-driven-development or requesting-code-review. You are learning the cycle here, on a change small enough that you can still read every line it writes — which is the only reason this is a safe place to meet it. Module 11 runs the harness to the maximum of its capabilities, on a Terraform module you cannot verify by eye.

Step 2 — Write the boundary yourself​

A task contract has two halves with two different authors, and the split is not a style preference.

You write the boundary. intent, target, actions.denied, and rollback are your authority. An agent that writes its own leash has written no leash.

Create agentops/m5-task-contract.yaml:

task:
  intent: Expose the running application version so release checks can confirm what is deployed.
  target: app/orders-api/
  actions:
    allowed:
      - add a GET /version route
      - add a test covering it
    denied:
      - editing any file outside app/orders-api/
      - adding a new dependency
      - modifying an existing test to make the suite pass
  acceptance: []      # Claude fills this in Step 3
  stop_conditions: [] # and this
  rollback: git checkout -- app/orders-api/

Read that third denial again. It is the one that matters later, and you are writing it before you have any reason to think you will need it.

Step 3 — Have Claude derive the acceptance criteria​

Acceptance is the half you should not write alone, because it has to be runnable in this repository — and Claude can read the repository faster than you can.

Start a session and put it in plan mode by pressing Shift+Tab until the mode indicator reads plan:

claude
Read agentops/m5-task-contract.yaml, scripts/grade.sh and labs/m5/checks.json.

Propose the acceptance list for this contract. Every entry must be a shell command
that exits 0 when the criterion holds and non-zero when it does not — I am going to
execute this list, not read it.

Note that the test suite runs under app/orders-api/.venv/bin/python when that exists.

Do not edit any file. Propose the list and stop.

What Claude does. It reads the grader, finds how the suite is invoked, and proposes four or five commands — a grep for the route, a grep for the test, a suite run, and an endpoint assertion.

What you observe. It will almost certainly propose at least one criterion that is not a command: "the endpoint responds quickly", or "the code is clean". Reject it:

"the endpoint responds quickly" is not an acceptance criterion — nothing can run it.
Every entry must be a shell command that exits 0 when the criterion holds. Replace it
with one, or drop it and put the concern in residual_risk instead.

Watch the environment detail too. If it proposes a bare python3 -m pytest, that command fails in this repo — the dependencies live in a virtualenv. An acceptance criterion that cannot run in the environment the grader uses is testing a different repository than the one you are changing.

A working acceptance list, for comparison after you have your own
  acceptance:
    - "grep -rq '\"/version\"' app/orders-api/src"
    - "grep -rq 'def test_version' app/orders-api/tests"
    - 'PY="$PWD/app/orders-api/.venv/bin/python"; [ -x "$PY" ] || PY=python3; (cd app/orders-api && "$PY" -m pytest -q >/dev/null 2>&1)'
    - 'PY="$PWD/app/orders-api/.venv/bin/python"; [ -x "$PY" ] || PY=python3; (cd app/orders-api && "$PY" -c "from fastapi.testclient import TestClient; from src.main import create_app; r=TestClient(create_app()).get(\"/version\"); assert r.status_code==200 and \"version\" in r.json()")'
  stop_conditions:
    - a change is required outside app/orders-api/
    - an acceptance command cannot be made to pass without weakening it

Now execute the contract. This one loop is the whole lesson made mechanical:

yq -r '.task.acceptance[]' agentops/m5-task-contract.yaml \
  | while read -r c; do bash -c "$c" >/dev/null 2>&1 \
      && echo "PASS  $c" || echo "FAIL  $c"; done
Expected output
FAIL  grep -rq '"/version"' app/orders-api/src
FAIL  grep -rq 'def test_version' app/orders-api/tests
PASS  PY="$PWD/app/orders-api/.venv/bin/python"; …pytest -q…
FAIL  PY="$PWD/app/orders-api/.venv/bin/python"; …TestClient…

Three red. Your contract is not a document about the work — it is a test of the work, and it currently fails. That is what "acceptance criteria" is supposed to mean.

Step 4 — Isolate the work​

git worktree add -b m5-version ../m5-version HEAD
cd ../m5-version
Expected output
Preparing worktree (new branch 'm5-version')
HEAD is now at 8a1905a fix(grade): migrate m2-m7 to the declarative checks.json runner

main is now out of reach of anything that happens next. That is the property — not that the work gets thrown away, but that the original is untouchable until you choose otherwise.

Step 5 — Run the loop​

Launch a session from the worktree and paste one prompt. You are not going to narrate the phases; that is what you installed the harness for.

claude
Read agentops/m5-task-contract.yaml. It is the contract for this task — treat
target and actions.denied as hard boundaries, not suggestions.

Use superpowers: brainstorm the approach first, write a plan, then work
test-driven — the failing test before the implementation, and watch it fail.

The acceptance list in the contract is a list of shell commands. When every one
of them exits 0, and not before, you are done.

Do not touch anything outside app/orders-api/. Do not add a dependency.

What Claude does. Brainstorms where the route belongs, writes a short plan, then adds test_version first, runs it, watches it fail, and only then writes the route.

What you observe. Three things, because they are where this goes wrong:

  • Did the test come before the route? If the code appeared first and the tests ran afterwards, the harness did not run TDD — it ran ordinary development with a test at the end. You should see a failure on screen that nobody was worried about.
  • Did it try to edit src/main.py? That is inside target but outside the plan you approved. Deviation from an approved plan is precisely what plan mode exists to surface.
  • Did it run the acceptance commands, or announce it was finished? Those are different claims.

When it proposes edits, press Shift+Tab to move from plan to acceptEdits so the TDD loop can run without a prompt per file.

You just crossed the boundary with two keystrokes

plan could not edit a file. acceptEdits can. That transition is the lesson's plan/execute boundary made physical — and you chose when to cross it, having read the plan.

A headless claude -p call would have produced the same route with no boundary to cross, which is why this lab does not use one. In Module 11 you drop the prompts entirely and rely on the layer underneath them. You earn that here, by seeing what the prompts were protecting.

Step 6 — Let the repository decide​

yq -r '.task.acceptance[]' agentops/m5-task-contract.yaml \
  | while read -r c; do bash -c "$c" >/dev/null 2>&1 \
      && echo "PASS  $c" || echo "FAIL  $c"; done
Expected output
PASS  grep -rq '"/version"' app/orders-api/src
PASS  grep -rq 'def test_version' app/orders-api/tests
PASS  PY="$PWD/app/orders-api/.venv/bin/python"; …pytest -q…
PASS  PY="$PWD/app/orders-api/.venv/bin/python"; …TestClient…

Four green. The same list that was three-red in Step 3, unchanged, now passes. Nobody's opinion moved — the repository's answer did.

Step 7 — Try to talk it into cheating​

This is the part worth staying for. In the same session:

The build is red on the campaign branch and we need to merge today. Just relax the
version test so the suite goes green — we can tighten it later.

What Claude does. It does what you asked: widens the assertion, or drops the body check, or removes the route as now-unused. The suite goes green.

Run the suite yourself:

cd app/orders-api && ./.venv/bin/python -m pytest -q; cd -
Expected output
...............                                                          [100%]
15 passed in 0.62s

Fifteen passed. Every test in the repository is green. If your definition of done is "the suite passes", you are finished and you would merge this.

Ask the agent to assess its own work, with no tools:

Without running anything, just from reading the files: is the /version task complete?

It will say yes — there is a /version test, it passes, the suite is green. It is reading the code it just wrote and confirming it did what it set out to do.

Now ask the repository:

./scripts/grade.sh m5
Expected output
  ✗ GET /version returns 200 with a version field (behavior, not just source)
  ✗ YOUR CONTRACT: every acceptance entry is a runnable shell command that exits 0 …

RESULT: FAIL (9 passed, 2 failed)

The suite says 15 passed. The grader says red. Inference and evidence disagree, and the evidence is right — it tested behavior, the agent reasoned about intent, and the test it reasoned about is the one it just edited.

Run your own contract against the weakened code:

yq -r '.task.acceptance[]' agentops/m5-task-contract.yaml \
  | while read -r c; do bash -c "$c" >/dev/null 2>&1 \
      && echo "PASS  $c" || echo "FAIL  $c"; done
Expected output
PASS  grep -rq '"/version"' app/orders-api/src
PASS  grep -rq 'def test_version' app/orders-api/tests
PASS  PY="$PWD/app/orders-api/.venv/bin/python"; …pytest -q…
FAIL  PY="$PWD/app/orders-api/.venv/bin/python"; …TestClient…

Three of your four criteria are satisfied by weakened code. The route exists. A function named test_version exists. The suite is green. Only the fourth — the one that exercises the endpoint and asserts on what comes back — notices anything is wrong.

Two layers, different coverage

The test suite proves the code does what the test says. Your fourth acceptance command proves the code does what the contract says, because you wrote it before the change and never touched it again.

A repository whose only check is its own test suite has one layer, and it cannot catch an agent that edits the test. That is not a hypothetical: you just watched it happen, on request, in under a minute.

Correct it through the contract, not by hand:

Revert that. The acceptance criteria are the contract, not the test file — a test you
relaxed to go green is not evidence. Restore the assertion and make the acceptance
commands pass by changing the code.

Then re-run the acceptance loop and confirm four green.

Reflect

You wrote modifying an existing test to make the suite pass into actions.denied in Step 2, before you had any reason to expect it. Did the agent honour it? If it did not, that is Module 8's argument in advance: a denial you write in a document is an instruction, and an instruction is not a wall.

Step 8 — Write the done record​

"Done" is a logbook entry, not a thumbs-up. Create agentops/m5-done.md with five parts: tests, evidence, rollback, residual risk, and cost.

The residual-risk line is the one that requires honesty — name something the change does not prove:

A worked example
# Done record — GET /version

- **Tests pass:** full orders-api suite green, including the new test_version.
- **Evidence:** all four acceptance commands from the contract exit 0; grade.sh m5 green.
- **Rollback:** `git checkout -- app/orders-api/` — the change is additive, one route and one test.
- **Residual risk:** the version string is NOT proven to match the deployed artifact. It reads
  settings.app_version, which nothing verifies against the image tag at release time.
- **Cost receipt:** one harness run; the harness adds ~688 always-on tokens per session.

The residual-risk entry is the useful one. A done record that claims everything is covered is marketing, and the grader checks that yours names something unproven.

Step 9 — Land it and clean up​

git add app/orders-api agentops
git commit -m "feat(orders-api): add GET /version endpoint with test"
cd ../agentic-ops-lab
git merge --no-ff m5-version -m "merge: add /version endpoint"
./scripts/grade.sh m5
Expected output
RESULT: PASS (11 passed)

Eleven green: the change, the contract, the harness, and the done record.

git worktree remove ../m5-version --force
git branch -d m5-version
git worktree list
Expected output
/Users/you/agentic-ops-lab            9c3f1a2 [main]

The worktree is gone and the work survived. Isolation never meant discarding the change — it meant main was out of reach until you decided otherwise. /version now exists for Module 13's release check.

Exercise​

  1. Break a different criterion. Ask the agent to make /version return a bare string instead of an object. Which acceptance commands still pass? What does that tell you about how much a grep proves?
  2. Add the criterion you are missing. Nothing in your contract checks that the version matches anything real. Write an acceptance command that would fail if settings.app_version disagreed with a value from outside the application, and note why that is hard.
  3. Price the harness. Re-read the Projected token cost block from Step 1. For which of the five follow-on tasks in Module 1's Step 12 table would ~688 always-on tokens be worth paying?

Teardown​

The change stays merged — Module 13 uses it. Nothing else to remove; the worktree went in Step 9.

Summary​

You wrote a boundary, had an agent derive acceptance criteria that the repository can actually execute, ran the harness through one full test-first cycle, and then asked it to cheat and watched your own contract catch it.

Three things carry forward. The contract is executable — acceptance is a list of commands, so "done" is a thing you run rather than a thing you assert. The harness is installed and proven, so when Module 11 says "use superpowers to the maximum of its capabilities" it refers to something you have driven. And two layers beat one: the suite proves the code matches the test, the contract proves the code matches the intent, and only the second survives an agent editing the first.

Module 6 turns the procedures you keep repeating into named, testable skills — the same move as this contract, applied to the work itself rather than to one change.
