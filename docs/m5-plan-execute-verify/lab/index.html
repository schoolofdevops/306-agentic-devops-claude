Lab — A Safe Change Under the Full Contract

In the lesson you learned to formalize Module 1's loop into an auditable procedure: a task contract agreed before the work, a plan approved before any edit, an isolated workspace to run in, and a repository that decides when the work is done. This lab runs one small, low-risk change through that whole procedure end to end. You will add a /version endpoint to orders-api — the kind of change that is safe enough to be a good teacher and real enough to matter — but you will make it the way you would make a change to something you cannot afford to break.

By the end you will have a green grader, a diff, a rollback, a residual-risk note, and a cost receipt — the five parts of "done" — and you will have watched agent self-assessment and repository verification give you two different answers to "is it finished?"

Where you are working

You start at the root of the agentic-ops-lab workspace on the main branch. The whole point of this lab is that you do not work on main — you create a worktree beside it and do everything there, so main is never touched until you choose to merge. The scripts/grade.sh shipped with the repo already knows how to grade m5.

Step 0 — Prerequisites​

Confirm Claude Code and git are available, and that you are on main with a clean tree. This lab does not need Docker or the running stack — the change is verified by the test suite, which runs offline.

claude --version
git -C . branch --show-current
git status --short
Expected output
2.1.197 (Claude Code)
main

Your Claude Code version will differ — anything recent is fine. The branch must be main, and git status --short should print nothing (a clean tree). If you have local changes from a previous lab, stash or commit them first — you want a clean starting point so the worktree branches from a known state.

Step 1 — Write the task contract​

Before the agent does anything, you write down what the task is. This is the flight plan from the lesson: intent, target, allowed and denied actions, acceptance criteria, stop conditions, and rollback — agreed now, while changing your mind is free. Write it as a committed artifact under agentops/ so it lives with the run it governs:

mkdir -p agentops
cat > agentops/m5-task-contract.yaml <<'EOF'
task:
  intent: "Add a GET /version endpoint to orders-api that returns the app version as JSON, so ops can confirm which build is deployed."
  target: "app/orders-api/ only"
  environment: "dev"
  actions:
    allowed: ["read app/", "edit app/orders-api/", "run tests"]
    denied: ["modify infra/", "modify platform/", "docker push", "kubectl apply", "edit inventory-api"]
  acceptance:
    - "GET /version returns 200 with a JSON body containing the version"
    - "A new test covers the /version endpoint"
    - "All existing orders-api tests still pass"
    - "grade.sh m5 returns PASS"
  stop_conditions:
    - "3 failed attempts to get the suite green -> stop and escalate"
    - "The change would touch a file outside app/orders-api/ -> stop and ask"
  rollback: "git checkout main -- app/orders-api/   # discard the change, restore main's version"
EOF
echo "wrote agentops/m5-task-contract.yaml"
Expected output
wrote agentops/m5-task-contract.yaml

Read back what you just wrote. None of the fields tell the agent how to write the endpoint — that is its job. Every field constrains the boundary and defines success: target and actions are the leash, acceptance is the deterministic definition of done, stop_conditions are the abort criteria, and rollback is the undo you wrote while calm. This file is the reference you will hold the agent's plan against in Step 4.

Step 2 — Create an isolated worktree​

Now build the rehearsal stage off to the side. git worktree add creates a new working directory on its own branch, sharing the same repository — the agent will work there, and main stays untouched no matter what happens.

git worktree add -b feat/orders-version ../ns-version main
git worktree list
Expected output
Preparing worktree (new branch 'feat/orders-version')
HEAD is now at 3adb15b feat: add contracts, evals, fault configs, .claude config, and project docs
/Users/you/agentic-ops-lab  3adb15b [main]
/Users/you/ns-version       3adb15b [feat/orders-version]

The commit hash and paths will differ on your machine. You now have two working directories: the original on main, and ../ns-version on a fresh feat/orders-version branch. They share history and objects but have independent working trees — an edit in one does not appear in the other. This is the isolation the lesson described: the agent is about to work on a disposable copy.

Move into the worktree. Every remaining step runs here, not in the original workspace:

cd ../ns-version
pwd
Expected output
/Users/you/ns-version

You are now standing on the rehearsal stage. If everything from here goes wrong, you delete this directory in teardown and main never knew it happened.

The orders-api dependencies live in a virtualenv that is not committed (it is git-ignored), so the fresh worktree does not have one. Build it once so the test suite can run — this is a real, isolated environment for the change:

cd app/orders-api
python3 -m venv .venv
.venv/bin/pip install -q -r requirements.txt pytest pytest-asyncio
cd ../..
echo "venv ready"
Expected output
venv ready

The install prints a pip upgrade notice you can ignore. requirements.txt gives you the app's runtime dependencies; pytest and pytest-asyncio give you the test runner. This venv lives inside the worktree, so it is torn down with it — nothing leaks back to main.

Step 3 — Run the grader first, to see red​

Before the agent touches anything, run the acceptance check from your contract. It should fail — the /version endpoint does not exist yet. Seeing red first is the point: it proves the grader actually tests for the change, so a later green means something.

./scripts/grade.sh m5
Expected output
Grading: Module m5
========================

Checking: Safe change — /version endpoint under the contract

  ✗ orders-api declares a /version route
  ✓ a test covers the /version endpoint
  ✗ orders-api test suite passes (existing + new)
  ✗ /version returns 200 with a version field

RESULT: FAIL (1 passed, 3 failed)

Your exact pass/fail split may vary slightly, but the result is FAIL. The route does not exist, no test covers it, and the behavior check fails. The one check that passes is incidental. This red is your baseline — the acceptance criteria are real, deterministic checks that currently say "not done."

Step 4 — Plan mode: review before any edit​

Now run Claude Code in plan mode. In this mode the agent can read and reason but cannot edit files or run mutating commands — it produces a plan and stops. You review that plan against the contract from Step 1 before allowing a single edit.

claude -p "In plan mode: I want to add a GET /version endpoint to orders-api that returns the app version as JSON, plus a test. Do NOT edit anything — just tell me your plan and which files you would touch." \
  --permission-mode plan
Expected output
Plan written. Summary:

**2 files, ~10 lines total:**

1. **app/orders-api/tests/test_health.py** — add test_version() (TDD red step first)
2. **app/orders-api/src/health.py** — add GET /version returning {"version": settings.app_version}

Endpoint lives in health.py alongside /healthz and /api/v1/info — same router,
settings.app_version already in scope, zero wiring needed in main.py.

Plan file at /Users/you/.claude/plans/....md. Ready to implement when you approve.

The exact wording and plan filename will differ every run — this is one real plan, not a fixed script. What matters is that you can now review the approach against your contract: it touches only app/orders-api/ (inside target), it adds a test (an acceptance criterion), and it edits two files, both allowed. No stop_condition is tripped. The plan matches the contract, so it is safe to approve. Had it proposed editing main.py config globally, or adding a dependency, you would catch it here — in the plan — not in a diff.

Confirm the agent kept its promise: plan mode does not edit. The tree should still be clean.

git status --short
Expected output

Nothing. Plan mode reasoned about the change and wrote a plan file outside the repo, but it did not touch a single tracked file. This is the separation from the lesson made concrete: thinking happened, acting did not.

Step 5 — Execute the approved change​

The plan matches the contract, so switch to execution. Now the agent may edit — but only inside the worktree, and you have already agreed the approach.

claude -p "Implement the plan: add a GET /version endpoint to orders-api in app/orders-api/src/health.py that returns {\"version\": settings.app_version} as JSON, and add a test_version test in app/orders-api/tests/test_health.py that asserts a 200 and a version field. Only touch app/orders-api/." \
  --permission-mode acceptEdits
Expected output
Added a GET /version endpoint to health.py returning {"version": settings.app_version},
and added test_version() to test_health.py asserting 200 + a version field.
Both files are under app/orders-api/ as required.

The exact wording varies. The agent made the change described in the plan. Note this is the agent telling you it is done — a claim, not yet a verified fact. Step 6 is where the repository, not the agent, decides.

Look at exactly what changed — the evidence for your definition-of-done record:

git diff --stat
Expected output
 app/orders-api/src/health.py        |  5 +++++
 app/orders-api/tests/test_health.py | 10 ++++++++++
 2 files changed, 15 insertions(+)

Two files, both inside app/orders-api/ — exactly the target from the contract. If a third file outside the target appeared here, that would be a stop_condition breach and you would roll back. The diff staying inside the boundary is the contract holding.

Step 6 — Let the repository decide it is done​

The agent said it is done. Now ask the repository. Run the full test suite first — this proves the new endpoint works and that nothing else broke:

cd app/orders-api && .venv/bin/python -m pytest -q ; cd ../..
Expected output
...............                                                          [100%]
15 passed in 0.56s

The count will differ slightly with the repo's test set; what matters is that it is green and the total went up by one (the new test_version). A passing suite is a fact about behavior, not a claim about it — this is the graded exam, not the student's hunch.

Now run the grader — the deterministic acceptance check from your contract. This is the same command that showed red in Step 3:

./scripts/grade.sh m5
Expected output
Grading: Module m5
========================

Checking: Safe change — /version endpoint under the contract

  ✓ orders-api declares a /version route
  ✓ a test covers the /version endpoint
  ✓ orders-api test suite passes (existing + new)
  ✓ /version returns 200 with a version field

RESULT: PASS (4 passed)

Red in Step 3, green now — the same checks, a different verdict, because the change is real. This is repository-owned verification: the acceptance criteria from your contract became automated checks, and green is the definition of done. You did not ask the agent whether it finished; you asked the repo, and the repo answered from evidence.

Step 7 — Compare inference against evidence​

This is the sharpest step. You already have the repository's verdict. Now get the agent's self-assessment and see where the two differ. Ask Claude Code to judge the work by inference — the way /verify does — without running the checks:

claude -p "Without running any tests or the grader, just by reading app/orders-api/src/health.py and tests/test_health.py, is the /version task complete? Answer in one or two sentences." \
  --permission-mode plan
Expected output
Yes — health.py declares GET /version returning {"version": settings.app_version},
and test_health.py has test_version asserting a 200 and a version field, so the task
looks complete.

The wording varies. Here the inference happens to agree with the grader — which is exactly the trap. The agent is reading the same code it wrote and confirming it did what it set out to do. That confidence is worth something as a gut-check, but notice what it is not: it never ran the endpoint, never ran the suite, and could not have caught a regression in a neighboring feature or an environment-specific failure. It is the student saying "I'm pretty sure I passed." When inference and the grader agree, you learned nothing new. When they disagree — the agent says done, the grader says red — the grader is right, because it tested behavior and the agent only reasoned about intent.

Inference agreeing is not inference being reliable

The danger is not that self-assessment is always wrong — it is that it is confidently right often enough that you stop checking. The one time the agent misunderstood the task, its self-assessment will confirm it completed the misunderstood task perfectly, and there is no red flag in the words. Only the external check — written independently of this run — catches that. Use the agent's judgment as a hint on the way to the verdict, never as the verdict.

Step 8 — Assemble the definition-of-done record​

"Green" is necessary but not the whole story. Close the task the way the lesson defined "done" — a logbook entry with five parts. Write it as a committed artifact so the run is accountable later:

cat > agentops/m5-done.md <<'EOF'
# Done record — add /version to orders-api

- **Tests pass:** orders-api suite green (15 passed), including new test_version.
- **Evidence:** diff below; grade.sh m5 -> PASS (4/4).
- **Rollback:** `git checkout main -- app/orders-api/`  (discard change, restore main's version)
- **Residual risk:** tests cover the happy path via TestClient only. NOT proven:
  behavior under load, the endpoint on the deployed container, or auth (endpoint is unauthenticated).
- **Cost receipt:** attach the Agent Run Ledger row for this run (Module 4).
EOF

echo "--- diff (evidence) ---"
git diff -- app/orders-api/src/health.py app/orders-api/tests/test_health.py
echo "--- done record ---"
cat agentops/m5-done.md
Expected output
--- diff (evidence) ---
diff --git a/app/orders-api/src/health.py b/app/orders-api/src/health.py
@@ -34,6 +34,11 @@ async def readyz():
     }


+@router.get("/version")
+async def version():
+    return {"version": settings.app_version}
+
+
 @router.get("/api/v1/info")
 async def info():
--- done record ---
# Done record — add /version to orders-api

- **Tests pass:** orders-api suite green (15 passed), including new test_version.
- **Evidence:** diff below; grade.sh m5 -> PASS (4/4).
- **Rollback:** `git checkout main -- app/orders-api/`  (discard change, restore main's version)
- **Residual risk:** tests cover the happy path via TestClient only. NOT proven:
  behavior under load, the endpoint on the deployed container, or auth (endpoint is unauthenticated).
- **Cost receipt:** attach the Agent Run Ledger row for this run (Module 4).

Your diff hash lines and exact wording will differ. This is the whole "done" from the lesson in one artifact: the tests passed (objective), here is what changed (evidence), here is the one-line undo (rollback), here is what green does not prove (residual risk), and a pointer to the run's cost (receipt). The first three are facts; the last two are the judgment that separates "it's done" from "it's done, and here is exactly what we're still trusting."

The cost receipt is one command away

If you kept the Agent Run Ledger from Module 4, you can attach the real receipt: run this execution with the telemetry env vars set and pipe the captured telemetry through agentops/ledger.py. The done record then carries the model, effort, tokens, and cost for the exact run that produced the change — the run itself, as evidence, closing the loop back to Module 4.

Step 9 — Teardown​

The change lives on the feat/orders-version branch inside the worktree. In real work you would now merge it to main (it is green and accountable) or open a PR. For this lab, tear the worktree down to prove the isolation property: deleting it leaves main exactly as it started.

First return to the original workspace — you cannot remove a worktree from inside it:

cd /Users/you/agentic-ops-lab   # your original workspace path, NOT ns-version
git worktree remove --force ../ns-version
git worktree list
Expected output
/Users/you/agentic-ops-lab  3adb15b [main]

The worktree directory and its venv are gone in one command — that is the disposability from the lesson. Only the original main worktree remains.

Delete the branch and confirm main's application code was never touched:

git branch -D feat/orders-version
git status --short app/orders-api/
Expected output
Deleted branch feat/orders-version (was 3adb15b).

The branch is deleted, and git status --short app/orders-api/ prints nothing — main's orders-api is byte-for-byte what it was before you started. The entire change happened, was verified, and was torn down without main ever being modified. That is the strongest form of the boundary: the agent worked on a disposable copy, and the original was out of reach the whole time.

If you wanted to keep the change instead, you would have merged feat/orders-version into main before teardown rather than deleting it — the worktree is disposable, the branch's history is not.

You ran one small change through the full contract: a task contract agreed before the work, a worktree to isolate it, plan mode to review the approach before any edit, execution inside the boundary, repository-owned verification that turned red into green, a deliberate comparison of agent inference against that verdict, a definition-of-done record you can defend, and a teardown that proved main was never at risk. Module 1 taught the loop as a habit; you just ran it as an auditable procedure. The Deep Dive goes under the hood of the two tools you used as black boxes here — how /verify inference actually works and when it quietly lies, and how /goal lets an agent drive toward an objective while still checking itself against something real.
