Plan, Execute, Verify

Module 1 gave you a loop: diagnose, change, verify. It was deliberately loose, because the bug was one wrong word and the point was to build the habit. This module takes that same loop and makes it rigorous enough to run against a system you cannot afford to break. The change is small again, a low-risk application tweak, but everything around it is formalized: you state what the task is before the agent touches anything, you review the plan before it edits, you run the change in a place where a mistake costs nothing, and you let the repository decide whether the work is done rather than asking the agent to grade its own homework.

Here is the gap this closes. In Module 1 you were in the loop the whole time: reading each step, approving each edit, watching the verify. That works when you are babysitting one small fix. It does not scale, and it does not survive the moment you hand a task to an agent and step away. The instant the agent has any autonomy, three questions become load-bearing: did it understand what it was actually asked to do, did it stay inside the lines, and is "done" a fact or the agent's opinion? A loose loop answers none of these. This module turns each into a written, checkable artifact: a task contract, a reviewed plan, an isolated workspace, and repository-owned verification, so that the loop holds even when you are not watching every step.

Why you write the task down before the agent runs​

Think about how a good change ticket works on a team that has been burned. It does not just say "fix the thing." It says what the change is for, which systems it touches, which environment it lands in, what counts as success, and what to do if it goes wrong. The ticket exists because "I thought you meant the staging database" is an expensive sentence, and the cheapest place to catch that misunderstanding is before anyone opens an editor.

An agent needs that same ticket, and for a sharper reason: the agent will do exactly what it inferred you meant, quickly, without the pause where a human colleague would say "wait, do you really want me touching production for this?" The agent's speed is the whole value and the whole danger. So you front-load the agreement. You write down the task as a contract, a structured statement of intent, scope, and acceptance that both you and the agent work from, and you do it before execution, when changing your mind is free.

Analogy: a task contract is a flight plan filed before takeoff. A pilot does not improvise the route mid-air. Before the engines start, the plan states the destination, the corridor, the fuel, the alternates, and the abort conditions, and it is reviewed on the ground where changing it costs nothing. Once airborne, the plan is the reference everyone flies against, and deviating from it is a deliberate, visible act, not a drift nobody noticed. The task contract is that filed plan for an agent run: agreed before the work, referenced during it, and a deviation from it is something you can see.

A task contract has a fixed shape. Every field answers a question that, left unanswered, is where autonomous runs go wrong:

task:
  intent: "Add a /version endpoint to orders-api so ops can confirm the deployed build"
  target: "app/orders-api/ only"
  environment: "dev"
  actions:
    allowed: ["read app/", "edit app/orders-api/", "run tests"]
    denied: ["modify infra/", "docker push", "kubectl apply", "edit other services"]
  acceptance:
    - "All existing tests still pass"
    - "A new test covers the /version endpoint"
    - "grade.sh m5 returns PASS"
  stop_conditions:
    - "3 failed attempts to make tests pass → stop and escalate"
    - "Change would touch a file outside app/orders-api/ → stop and ask"
    - "Token budget exceeded → checkpoint and stop"
  rollback: "git checkout main -- app/orders-api/"

Read down the fields and notice that none of them are about how to write the code. That is the agent's job. They are about the boundary and the definition of success, which is yours. intent keeps the agent solving the right problem. target and actions are the leash from Module 2, restated per task. acceptance is the thing most people leave implicit and then argue about: what, precisely, makes this done. stop_conditions are the abort criteria: the moments where the correct move is to stop, not to push through. rollback is the answer to "and if it's wrong?" written down while you are calm, not improvised during an incident.

The contract is per-task; the settings are per-session

Module 2's settings.json permissions are a standing boundary that applies to every run in the workspace. The task contract is narrower and sharper: it is the boundary and success criteria for this one task. They stack: the contract can only tighten what settings already allow, never loosen it. Think of settings as the building's locked doors and the contract as the specific room you are authorized to work in today.

Plan mode: separate thinking from acting​

Even with a contract, there is a moment of maximum risk: the transition from "the agent understands the task" to "the agent is editing files." In a loose loop those are fused: the agent reasons and edits in one motion, and you find out what it decided by watching the diffs appear. That is fine for a one-word fix. It is not fine when the change is large enough that a wrong approach, not a wrong line, a wrong whole strategy, is expensive to unwind.

Analogy: plan mode is the surgeon's pre-op briefing. Before the first incision, the surgeon walks the team through the procedure: this is what we will do, in this order, these are the structures we will avoid, here is where we expect trouble. The point of the briefing is that it happens while the patient is still closed: objections are cheap, the plan can change, nobody has cut anything. Executing without a briefing is not braver; it is just moving the discovery of a bad plan to the worst possible time. Plan mode is that briefing for an agent: it explores and produces the procedure, and you approve it, before any edit is made.

Concretely, plan mode is a permission mode where the agent can read, search, and reason, but cannot edit files or run mutating commands. It produces a plan: here is what I found, here is what I will change, here is the order. You read that plan against your contract. Does the approach match the intent? Does it stay inside target? Does it trip any stop_condition? Only when the plan is right do you switch to execution.

The value of plan mode is not that it catches typos. Verification does that. It catches the agent about to solve the problem the wrong way: adding a dependency you did not want, editing three files when the contract said one, choosing an approach that technically works but that you will regret. Those are cheap to fix in a plan and expensive to fix in a diff.

Isolate the work: worktrees, checkpoints, rewind​

The contract says where the agent may work; plan mode lets you approve the approach. The third layer is where the execution physically happens, because even a reviewed plan executed by a fast agent should not run directly on the branch you care about.

Analogy: a worktree is a rehearsal stage built off to the side. The main stage, your main branch, is where the real show runs, and you do not rehearse a risky new number on it while the audience is seated. You build an identical stage in the wings, rehearse there as roughly as you need, and only bring the number to the main stage once it is good. If the rehearsal is a disaster, you strike the side stage and the main stage never knew it happened. A git worktree is that side stage: a separate working directory, on its own branch, sharing the same repository, where the agent can work and fail without any of it touching main.

You create one with a single command, point the agent at it, and let it work. If the change is good, you merge it back. If it is bad, you delete the worktree and there is nothing to clean up: main was never modified. This is the strongest form of the Module 2 boundary: not "the agent is allowed to edit these files" but "the agent is editing a disposable copy, and the original is out of reach entirely."

Worktrees are the heavy isolation. Two lighter tools cover the in-flight moments:

  • Checkpoints: before a risky step, you commit or stash so there is a named point to return to. A checkpoint is cheap insurance: it costs one command and it means "whatever happens next, I can get back to exactly here." Branches themselves are checkpoints: named, revertable, free.
  • Rewind: Claude Code can roll back the last agent action when it goes wrong, so a bad edit does not require you to reconstruct the previous state by hand. It is the undo for the agent's last move.

These are not three competing tools; they are three depths of the same instinct. Rewind undoes one step. A checkpoint returns you to one saved moment. A worktree keeps the entire experiment off the branch that matters. You reach for the depth that matches the risk of what you are about to let the agent do.

Verification the repository owns, not the agent infers​

Now the sharpest idea in the module. You have a contract, an approved plan, and an isolated workspace. The agent has made the change. The last question, the one that decides whether you ship, is "is it done?" And there are two very different ways to answer it.

The first is to ask the agent. Claude Code can look at what it did and tell you whether it thinks the task is complete. This is inference: the same model that wrote the change also judges the change. Sometimes that judgment is right. But it has a structural flaw: the agent is grading its own work using the same understanding that produced the work, so any blind spot in the doing is a blind spot in the checking. If it misunderstood the task, it will confidently confirm it did the misunderstood task correctly.

The second is to let the repository decide. The acceptance criteria in your contract map to automated checks that live in the repo and do not care what the agent thinks: the existing test suite, a new test for the change, a linter, a grading script. You run them. Green is done. Red is not done. The check has no opinion and no blind spot aligned with the agent's, because it was written independently of this run.

Analogy: this is the difference between a student saying "yeah, I'm pretty sure I passed" and the graded exam coming back. The student's self-assessment is not worthless, but you do not register them for the next course on the strength of it. You wait for the graded result, because the grade is external: it was set by someone other than the person being graded, against a rubric fixed in advance, and it catches exactly the mistakes the student was too confident to notice. Repository-owned verification is the graded exam. /verify-style agent self-assessment is the student's hunch, useful as a quick gut-check, never as the thing you ship on.

Why the repository wins is worth stating plainly. Repo-owned checks are reproducible: they give the same verdict on your machine, a teammate's, and in CI, because they are just code. They do not hallucinate: a passing test is a fact about behavior, not a claim about it. And they catch what self-assessment misses: the regression in a neighboring feature, the edge case the agent did not think to consider, precisely because the check was written without this run's blind spots. The pattern is: acceptance criteria in the contract become automated checks in the repo, and green becomes the definition of done. The agent's self-assessment is demoted from the verdict to a hint on the way to the verdict.

What "done" actually means​

"The tests pass" is necessary but it is not the whole definition of done for an agent task you might have to defend later. A task you can stand behind, in a review, in a postmortem, to the person who has to trust it went out safely, closes on five things:

ElementThe question it answersWhere it comes from
Tests passDoes the change work, and did it break anything?Existing suite + a new test for the change
EvidenceWhat actually changed, and what did we check?The diff and the verification output
RollbackIf this is wrong in prod, how do we undo it?The rollback line from the contract
Residual riskWhat could still go wrong that the checks don't cover?Your honest read of what the tests don't prove
Cost receiptWhat did this run cost, and was it staffed right?The Agent Run Ledger from Module 4

The first three are objective: the suite passed, here is the diff, here is the undo command. The last two are where judgment lives. Residual risk is you stating what the green checks do not prove: the tests pass, but they do not exercise the endpoint under load, so latency under concurrency is unproven. Naming that is not admitting weakness; it is the difference between "it's done" and "it's done, and here is exactly what we're still trusting." Cost receipt closes the loop back to Module 4: the run itself is evidence, and a task that shipped without a record of what it cost is a task you cannot account for later.

Analogy: this is a pre-flight and post-flight logbook, not a thumbs-up. A pilot who lands does not just say "we made it." The logbook records the flight, the fuel burned, anything that behaved oddly, and the state the aircraft is in for the next crew. That record is what makes the operation accountable rather than merely successful: the next person can trust the aircraft because the last flight is documented, not because someone vouched for it. A finished agent task is a logbook entry: what it did, proof it worked, how to undo it, what is still uncertain, and what it cost.

What you'll do in the lab​

You will run one small, low-risk change end to end under the full contract. You will write a task contract for adding a /version endpoint to orders-api: intent, target, allowed and denied actions, acceptance criteria, stop conditions, and rollback. You will create a git worktree so the work happens off main. You will run Claude Code in plan mode and review the plan against your contract before a single file is edited. You will switch to execution and let the agent make the change inside the worktree. Then you will let the repository decide it is done: run the existing tests, the new test, and grade.sh, and deliberately compare that deterministic verdict against what agent self-assessment tells you, so you can see exactly where inference and evidence diverge. You will assemble the definition-of-done record: diff, test output, rollback, residual risk, and the cost receipt from Module 4's ledger, and finally tear the worktree down, leaving main exactly as it started.

Module 1 taught you the loop as a habit. This module makes it an auditable procedure: a contract you agreed before, a plan you approved before, an isolated place you ran it, a repository that decided it was done, and a record you can defend after. The Deep Dive then goes under the hood of the two things the lab treated as tools: how /verify inference actually works and exactly when it helps versus when it quietly lies, and how the /goal command lets an agent drive toward an objective while still checking itself against something real.
