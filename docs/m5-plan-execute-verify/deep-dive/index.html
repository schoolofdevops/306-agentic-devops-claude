Deep Dive — Inference-Based Completion and /goal

The core lab treated two things as black boxes: the moment where you asked the agent "is this done?" and got a confident yes, and the idea — gestured at but not used — that an agent could drive itself toward an objective, checking as it goes. This page opens both boxes. It is about the mechanism of inference-based completion: how an agent decides it is finished, why that judgment fails in a specific and predictable way, and how goal-directed autonomy (/goal-style loops) changes the risk profile — for better on some tasks, for much worse on others. The lab showed you that repository-owned verification wins; this page shows you why the alternative breaks, which is what lets you tell the two situations apart in the moment.

Command availability — read this first

/verify and /goal in this course name patterns, not guaranteed built-in Claude Code commands. Inference-based completion is what you get any time you ask an agent to judge its own work — whether through an installed verify-style skill, a subagent, or just a plain "is this done?" prompt. Goal-directed autonomy is the pattern of an agent looping toward an objective with periodic self-assessment; different harnesses expose it under different names and flags. Learn the mechanism and the failure mode — those are stable. The exact command surface shifts, and you re-map the reasoning onto whatever your version exposes.

How inference-based completion actually works​

When you ask an agent whether a task is complete, no test runs and no ground truth is consulted. The agent does what it always does: it predicts. It reads the current state — the files, the diff, its own prior messages — and generates the most probable continuation of "is this task done?" given everything in its context. If the context strongly implies completion, the most probable continuation is "yes." That is the entire mechanism. It is not lying and it is not checking; it is producing the likeliest answer conditioned on what it can see.

This is why the failure mode is so specific. The agent's judgment is only as good as the correspondence between its context and reality — and that correspondence has exactly the gaps you would expect from a system that reasons over a representation instead of the running system.

Analogy: inference-based completion is a proofreader checking their own manuscript from memory instead of against the printed page. They wrote it, they remember what they intended, and when they "check," they are largely re-reading their own intention — so the sentence they meant to write is the sentence they see, even when the page says something else. The errors that survive are precisely the ones where intention and reality diverged: the dropped word, the wrong figure, the paragraph they were sure they fixed. An external proofreader, reading only the page, catches those immediately — not because they are smarter, but because they have no memory of the intention to override what is actually printed. The agent grading its own work is the first proofreader. The test suite is the second.

Three gaps make inference-based completion unreliable in a predictable pattern:

  • Misunderstood intent. If the agent inferred the wrong task, its self-assessment confirms it completed that task. In the lab, if it had built a /version endpoint returning the wrong field, "is it done?" would still be "yes" — it did what it thought you asked. The grader, testing the actual contract, would say no.
  • Stale context. The agent reasons over its representation of the files, which can drift from what is on disk — an edit that partially applied, a file changed by another process, a merge it did not see. It answers about the world it remembers, not the world that exists.
  • Unobserved runtime. This is the big one for ops. The agent never ran the change. It cannot see the endpoint 500ing under concurrency, the integration failing against the real inventory-api, the container that will not start because of an environment variable. Inference reasons about code; behavior only shows up when code runs. Everything in the residual-risk line of your done record is, precisely, what inference structurally cannot see.

When inference is genuinely useful​

None of this makes inference worthless — it makes it a particular tool with a fit. Inference-based completion is fast, free of setup, and reasons about things no cheap check covers: "does this diff look like it addresses the intent," "did I obviously forget a file," "is the approach coherent." That is real value at the start of the verification funnel, as a quick gut-check that catches the coarse mistake before you spend anything running the expensive checks.

Analogy: it is the glance a chef gives a plate before it leaves the pass. That glance is fast and catches the obvious — wrong garnish, missing component, a smear on the rim — and it is worth doing every single time. But nobody confuses the glance with the health inspection. The glance uses the same eyes that plated the dish; the inspection is external, adversarial, and can shut the kitchen. You want both, in that order: the cheap glance to catch the obvious early, the external check to certify.

The rule that falls out: use inference where being wrong is cheap and fast to discover, use repository verification where being wrong is expensive or invisible. A quick "does this look complete?" before running the suite is fine — if it is wrong, the suite catches it seconds later. Shipping to production on "the agent said it looked done" is the failure, because there the three gaps are exactly the expensive, invisible ones, and no external check stood between the inference and the deploy.

Read the funnel left to right and the principle is visible: inference sits at the cheap, coarse end where its speed is an asset and its unreliability is quickly corrected; the deterministic checks sit where the verdict has to hold. Each stage catches what the stage before it structurally cannot — inference catches the obvious omission, unit tests catch broken behavior in isolation, integration tests catch the wiring, the grader certifies the contract, and human review catches the thing no automated check encodes. You do not pick one; you order them cheapest-first and let each do the job the others cannot.

/goal: autonomy that checks itself​

The core lab ran the loop with you in the seat: you approved the plan, you triggered execution, you ran the grader. Goal-directed autonomy — the /goal pattern — hands the loop itself to the agent. You state an objective, and the agent iterates toward it: act, assess progress, act again, until it judges the goal met. It compresses many rounds of "do a thing, check, do the next thing" into one instruction.

Analogy: setting a goal is the difference between giving a driver turn-by-turn directions and giving them a destination with a self-driving mode. Turn-by-turn keeps you in the loop at every junction — safe, slow, and it does not scale to a long trip. Destination mode is autonomous: the car re-plans continuously toward the goal. It is powerful exactly when the route is long and mostly routine, and it is dangerous exactly when the "am I there yet?" signal is unreliable — because the car will confidently drive to where it believes the destination is. The quality of an autonomous loop is capped entirely by the quality of the signal it checks itself against.

That last sentence is the whole point, and it connects straight back to the funnel. A goal-directed loop is only as trustworthy as its completion signal. If the agent's self-assessment is the signal — "keep going until I think I'm done" — you have wired all three inference gaps directly into the control loop. The agent can converge confidently on the wrong task, or loop forever burning tokens because its sense of "done" never quite fires, or declare victory on code it never ran. The autonomy amplifies the weakness of the signal.

The fix is to make the loop check itself against something external and deterministic — to give /goal a repository-owned completion signal instead of an inferred one:

Concretely: instead of "add a /version endpoint until you think it's right," the goal becomes "add a /version endpoint until grade.sh m5 exits zero." Now the loop's stopping condition is a fact about the running code, not a prediction about it. The agent still gets the autonomy — it iterates, it fixes its own failures, you are not clicking through every step — but the thing that decides "done" is the grader, immune to all three inference gaps. This is why the acceptance criteria in your task contract matter so much for autonomous work: they are the halt condition you hand the loop. A contract with a deterministic grade.sh m5 returns PASS acceptance line is not just documentation — it is the safety rail that makes goal-directed autonomy safe to use at all.

Autonomy without a deterministic halt is how token bills and wrong outputs happen

The two failure modes of a self-assessed loop are opposite and both expensive. It can halt too early — declare the goal met on inference, ship the wrong thing — or never halt — its inferred sense of "done" never fires, and it loops, burning tokens on a task it cannot recognize as finished. Module 4’s per-run budget alert catches the runaway after the fact; a deterministic completion signal prevents both by making "done" a fact the loop cannot argue with. Never hand an agent a goal without also handing it an external way to know it is finished.

The synthesis: contract acceptance is the completion signal​

Step back and the whole module resolves into one line. The task contract's acceptance field, the repository-owned verification from the lab, and a safe /goal completion signal are the same artifact viewed three ways. Acceptance criteria written as deterministic checks are: the definition of done you agreed up front, the verdict you ran the change against, and — if you go autonomous — the halt condition you hand the loop. Get that one artifact right and it serves the manual loop and the autonomous loop identically. Leave it as vague plain text ("make it work"), and you have nothing to verify against, nothing to grade, and nothing safe to hand an autonomous agent — you are back to trusting the proofreader's memory of the page.

Where you'll use this​

  • Deciding whether to go autonomous on a task. Before you hand an agent a goal to run unattended, ask: is there a deterministic completion signal I can give it? If yes (a grader, a passing suite), autonomy is safe and it scales you. If no, keep yourself in the loop — the missing external signal is exactly the risk. This judgment recurs constantly in later modules’ larger changes.
  • Reviewing an agent’s "it’s done." Any time an agent reports completion, place it in the funnel: treat it as the cheap glance, then ask what external check certifies it. On a low-stakes change the glance may be enough; on anything touching production, the inference is a hint and the grader is the gate.
  • Writing acceptance criteria that do double duty (M6–M9, capstone). When you build runbooks and subagent workflows, write acceptance as deterministic checks from the start — because those same checks become the halt conditions for any autonomous or delegated execution. Vague acceptance is a bug that only surfaces when you try to automate against it.
  • Diagnosing a runaway or wrong-output agent run. When an autonomous run loops or ships something wrong, the root cause is almost always the completion signal: it was inferred, not deterministic. The fix is not a better prompt — it is an external halt condition. Reach for the grader, not the rewording.
