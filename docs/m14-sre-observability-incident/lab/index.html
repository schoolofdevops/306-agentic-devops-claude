Lab — The Incident Workbench

The lesson drew the arc: SLOs and error budgets make health computable, the golden signals are the bounded evidence set, metrics → events → logs → traces is the order you reach for telemetry, every query carries three bounds, and a hypothesis is something you try to falsify — with the investigator producing an evidence packet it hands to a role that can act. This lab makes all of it runnable against Northstar's real observability stack: the Prometheus SLO rules, the orders-api metrics source, the retry client, the fault fixtures, and the two governance scripts (evidence-validate.sh, synthesize-hypotheses.sh) that enforce provenance and reject consensus theater.

By the end you will have read orders-api's SLOs as real rules, identified the four golden signals in the metrics source, written a bounded query and seen why the firehose version is a trap, driven the evidence-packet validator and the hypothesis synthesizer with real packets, and confirmed the sre-investigator role can diagnose but not apply — the exact separation the Deep Dive's retry storm relies on.

Where you are working

You start at the root of the agentic-ops-lab workspace. The observability config lives under observability/: Prometheus (prometheus.yml and rules/), Alertmanager (alertmanager.yml), and the OTel collector (collector/). The orders-api metrics are defined in app/orders-api/src/metrics.py and the retry client in app/orders-api/src/inventory_client.py. Fault fixtures are in fixtures/fault-configs/, incident tickets in incidents/, and the governance scripts in scripts/. Every graded step in this lab is a deterministic read of these files — it grades the same on any machine, no live stack required. An optional live path (the observe Docker Compose profile) is called out where it adds something; skip it on an 8 GB laptop.

Step 0 — Prerequisites​

Confirm your tools. The core lab needs jq and git; the optional live path needs Docker.

jq --version
git --version
docker version --format '{{.Client.Version}}' 2>/dev/null || echo "docker not running (optional path only)"
Expected output
jq-1.7.1
git version 2.43.0
29.5.3-rd

Your versions will differ. jq and git are required — the evidence and synthesis steps use jq heavily. Docker is only needed if you run the optional observe-profile stack in Step 3; the graded steps do not require it.

Step 1 — Read the SLOs and error budget as real rules​

Health is not a feeling. Read the objectives orders-api actually commits to — they live as Prometheus recording rules and alerts, not prose. First the recording rules that compute the SLIs continuously:

grep 'record:' observability/prometheus/rules/slo-orders.yml
Expected output
      - record: orders_api:error_rate:5m
      - record: orders_api:latency_p95:5m
      - record: orders_api:upstream_error_rate:5m

Three precomputed SLIs. orders_api:error_rate:5m is the fraction of 5xx responses over a rolling 5-minute window; orders_api:latency_p95:5m is the 95th-percentile request duration; orders_api:upstream_error_rate:5m isolates errors caused by the upstream dependency. These are recording rules — Prometheus evaluates them every 30s and stores the result as a new series, so an alert or an agent can query the SLI directly instead of rebuilding the math each time.

Now the objectives themselves — the named numbers the alerts gate on:

grep -E 'alert:|expr:|for:' observability/prometheus/rules/slo-orders.yml | grep -A2 alert
Expected output
      - alert: SLOErrorBudgetBurn
        expr: orders_api:error_rate:5m > 0.01
        for: 5m
--
      - alert: SLOLatencyBreach
        expr: orders_api:latency_p95:5m > 0.5
        for: 5m

There is your error budget, written down: error rate must stay below 0.01 (1%) and p95 latency below 0.5 seconds (500ms). The for: 5m means the breach must persist five minutes before the alert fires — a single spike is not a breach. This is the shift the lesson described: "is orders-api healthy?" is now the computable question "is orders_api:error_rate:5m above 0.01?" — a threshold a machine evaluates and an agent can answer without inventing a number.

Note the two-tier design — the budget-burn warning is separate from the page. Read the critical alerts that route to a real responder:

grep -E 'alert:|severity:' observability/prometheus/rules/alerts.yml | grep -B1 critical
Expected output
      - alert: HighErrorRate
          severity: critical
--
      - alert: LatencyBreach
          severity: critical
--
      - alert: ServiceDown
          severity: critical

HighErrorRate fires at 5% (not the 1% SLO) with severity: critical — the budget breach is a warning, but five times over budget is a page. This separation is deliberate: the SLO tells you how much budget you have spent; the critical alert tells you to drop what you are doing. An agent reading these knows the difference between "we are eating into the budget" and "wake someone up."

Step 2 — Identify the four golden signals in the metrics source​

The SLIs are computed from metrics the application actually exports. Read the source of truth — the metric definitions — and map them to the four golden signals:

grep -oE 'orders_api_[a-z_]+' app/orders-api/src/metrics.py | sort -u
Expected output
orders_api_orders_created_total
orders_api_request_duration_seconds
orders_api_requests_total
orders_api_upstream_duration_seconds
orders_api_upstream_errors_total
orders_api_upstream_retries_total

Map these to the gauges you read first. Latency → orders_api_request_duration_seconds (a histogram, so p95 is computable). Traffic → orders_api_requests_total (rate of arrivals). Errors → orders_api_requests_total{status=~"5.."} (the failing fraction of the same counter). Saturation → orders_api_upstream_retries_total climbing is the early-warning gauge for the retry storm — it is the queue backing up. The other two (upstream_duration, orders_created) are follow-up detail you earn after the four gauges point you somewhere. Six metrics total; four you read first.

Confirm the retry counter exists — it is the single most important signal for the incident ahead, because it distinguishes self-inflicted load from external load:

grep -A2 'UPSTREAM_RETRIES' app/orders-api/src/metrics.py | head -4
Expected output
UPSTREAM_RETRIES = Counter(
    "orders_api_upstream_retries_total",
    "Total retries to inventory-api",
)

orders_api_upstream_retries_total counts every retry the client makes against inventory-api. When this climbs while orders_api_requests_total (traffic) stays flat, the extra load is manufactured by orders-api itself — the retry loop — not by more customers arriving. That one distinction is what falsifies the resource hypothesis in the Deep Dive.

Step 3 — Understand a bounded query (and why the firehose is a trap)​

Every SLI query in the rules file carries the three bounds from the lesson. Read one and name them:

grep -A4 'record: orders_api:error_rate:5m' observability/prometheus/rules/slo-orders.yml
Expected output
      - record: orders_api:error_rate:5m
        expr: |
          sum(rate(orders_api_requests_total{status=~"5.."}[5m]))
          /
          sum(rate(orders_api_requests_total[5m]))

Three bounds, all present. Time window: [5m] — the question is "what is happening now," not an all-time average that would hide the spike. Metric scope: orders_api_requests_total with a status=~"5.." label filter — one named series, not .*. Cardinality limit: sum(rate(...)) collapses the per-method, per-path, per-status time series into a single number. This is a warrant: a place, a time, a thing to look for. It returns one value you can act on, and Prometheus can evaluate it continuously without drowning.

Now contrast the firehose. This is the query shape an undisciplined responder (or agent) reaches for — "show me everything":

echo 'sum(rate(orders_api_requests_total[5m])) by (method, path, status)   # BOUNDED: aggregated, windowed, scoped'
echo '{__name__=~".+"}                                                      # FIREHOSE: every series, no window, no scope'
Expected output
sum(rate(orders_api_requests_total[5m])) by (method, path, status)   # BOUNDED: aggregated, windowed, scoped
{__name__=~".+"}                                                      # FIREHOSE: every series, no window, no scope

The first line still has all three bounds even though it keeps some labels — it is a legitimate follow-up question. The second, {__name__=~".+"}, matches every metric in the system with no window and no aggregation: thousands of time series dumped at once. It is not a query, it is an abdication — the responder now has to find the signal in a haystack they built themselves. The rule of thumb: if you cannot say what place, time, and thing your query names, you are fishing, not investigating.

Optional live path — the observe profile

If you have 16 GB and want to see the stack live, bring up the observe profile and query Prometheus for real: docker compose --profile observe up -d, then curl -s 'http://localhost:9090/api/v1/query?query=orders_api:error_rate:5m' | jq '.data.result'. Prometheus is at :9090, Alertmanager at :9093. This is the same rules file you just read, now evaluating against live traffic. The graded steps below do not need it — they read the config directly — so skip this on a small laptop.

Step 4 — Validate an evidence packet: provenance or it is not evidence​

The sre-investigator agent produces exactly one thing — a structured evidence packet — and evidence-validate.sh enforces that every claim has provenance. Build a well-formed packet and validate it:

cat > /tmp/packet-good.json <<'EOF'
{
  "from_role": "sre-investigator",
  "to_role": "ops-lead",
  "evidence": {
    "service": "orders-api",
    "status": "degraded",
    "checks": { "healthz": true, "readyz": true },
    "hypothesis": "retry config amplifies upstream latency into a storm",
    "confidence": "high",
    "sources": [
      "fixtures/fault-configs/retry-storm.env",
      "app/orders-api/src/inventory_client.py:22"
    ]
  },
  "recommendations": ["lower RETRY_COUNT from 10 to 3", "add a circuit breaker"],
  "out_of_scope": ["did not check database saturation", "did not inspect node CPU"]
}
EOF
bash scripts/evidence-validate.sh /tmp/packet-good.json; echo "exit=$?"
Expected output
VALID: evidence packet from 'sre-investigator' -> 'ops-lead'; hypothesis backed by 2 source(s), out_of_scope declared.
exit=0

The packet passes because every required field is present and — critically — the hypothesis traces to two sources the investigator actually read, and the out_of_scope list is honest about what it did not check. This is what "evidence, not decoration" means mechanically: a claim the next role can act on without re-investigating, because it is traceable.

Now the contamination case — a confident hypothesis with no sources. This is the assertion-dressed-as-evidence the validator exists to reject:

cat > /tmp/packet-bad.json <<'EOF'
{
  "from_role": "sre-investigator",
  "to_role": "ops-lead",
  "evidence": {
    "service": "orders-api",
    "status": "down",
    "checks": {},
    "hypothesis": "the database is out of memory, we need a bigger instance",
    "confidence": "high",
    "sources": []
  },
  "recommendations": ["resize the database"],
  "out_of_scope": []
}
EOF
bash scripts/evidence-validate.sh /tmp/packet-bad.json; echo "exit=$?"
Expected output
INVALID: packet failed structure/provenance check — a confident claim with no sources, or a missing required field, is contamination, not evidence.
exit=4

Exit 4 — rejected. The packet looks authoritative ("high confidence, the database is out of memory"), and that is exactly why it is dangerous: a plausible claim with no provenance sends the next role resizing a database for a problem no one verified. The validator refuses it. No source, no claim — enforced, not requested.

Step 5 — Synthesize parallel hypotheses without consensus theater​

When you fan an incident out to independent investigators, the value is independence. synthesize-hypotheses.sh enforces it. First, the real corroboration case — three dimensions that reach the same root cause from their own evidence:

cat > /tmp/hyps-good.json <<'EOF'
[
  { "dimension": "application-retry", "root_cause": "retry-config", "status": "supported",
    "confidence": "high", "sources": ["inventory_client.py:22", "upstream_retries metric climbing"], "derived_from": null },
  { "dimension": "platform-resource", "root_cause": "retry-config", "status": "supported",
    "confidence": "medium", "sources": ["no resources block in values.yaml", "kubectl top: CPU high but not pinned"], "derived_from": null },
  { "dimension": "recent-change", "root_cause": "retry-config", "status": "supported",
    "confidence": "high", "sources": ["retry-storm.env: RETRY_COUNT 3->10"], "derived_from": null }
]
EOF
bash scripts/synthesize-hypotheses.sh /tmp/hyps-good.json
Expected output
verdict=corroborated
root_cause=retry-config
detail=3 independent dimension(s) converged on the same root cause from their OWN evidence — real corroboration, not an echo.

Three investigators, three different evidence trails, one root cause. verdict=corroborated is the strongest signal the synthesizer produces — and note the platform-resource dimension supported the retry-config cause by finding that CPU was high but not pinned and there was no resources block to raise. That dimension did its job by ruling its own hypothesis out and pointing at the real one. That is independent agreement, and it is worth acting on.

Now the consensus-theater case — a packet that anchored on a peer's conclusion instead of its own evidence:

cat > /tmp/hyps-theater.json <<'EOF'
[
  { "dimension": "application-retry", "root_cause": "retry-config", "status": "supported",
    "confidence": "high", "sources": ["inventory_client.py:22"], "derived_from": null },
  { "dimension": "platform-resource", "root_cause": "retry-config", "status": "supported",
    "confidence": "high", "sources": ["application-retry agent said so"], "derived_from": "application-retry" }
]
EOF
bash scripts/synthesize-hypotheses.sh /tmp/hyps-theater.json; echo "exit=$?"
Expected output
INVALID: consensus theater — packet(s) [platform-resource] are derived_from a peer's hypothesis, not independent evidence. Independent agreement requires independent evidence.
exit=4

Exit 4 — rejected. The second packet agreed, but it agreed because it read the first agent's answer (derived_from: application-retry), not because its own resource evidence pointed there. Two agents, one guess echoed. The synthesizer refuses to count that as corroboration, because an agreement built on anchoring is worth nothing — it looks like two confirmations and is really one. This is the guard that keeps parallel investigation honest.

Step 6 — Confirm the investigator can diagnose but not apply​

The whole discipline depends on separation: the role that finds the fault is not the role that fixes it. Read the sre-investigator's authority:

grep -E 'tools:|disallowedTools:' .claude/agents/sre-investigator.md
Expected output
tools: ["Read", "Grep", "Glob", "Bash"]
disallowedTools: ["Edit", "Write", "MultiEdit", "NotebookEdit"]

The investigator can Read, Grep, Glob, and run Bash (bounded read-only commands) — everything it needs to gather evidence. It has no Edit or Write tool. This is enforcement, not instruction: the agent cannot modify a file, propose a Helm change, or apply a fix even if it wanted to, because the tools are absent from its bundle. It produces an evidence packet and a recommendation; acting on the recommendation is another role's authority.

Cross-check against the authority matrix — the source of truth the role points at:

grep -A6 '^  sre-investigator:' contracts/authority-matrix.yaml | grep -E 'read:|execute:|write:'
Expected output
      read: ["app/", "observability/", "platform/", "incidents/", "runbooks/", "scripts/"]
      execute: ["scripts/preflight.sh", "scripts/grade.sh"]
      write: []

write: [] — empty. The matrix grants broad read (it can investigate anything) and a tiny execute allowlist (preflight, grade — read-only diagnostics), and no write authority at all. The diagnosis and the repair are structurally different hands. When the Deep Dive's retry storm is diagnosed, the fix is proposed through GitOps by a role that has that authority — never by the investigator that found it.

Step 7 — See the causal change: the retry-storm fixture​

The incident's root cause is a configuration change, and it is a real fixture you can diff against normal. This is "what changed" — the events question, answered from evidence:

diff fixtures/fault-configs/normal.env fixtures/fault-configs/retry-storm.env
Expected output
1,10c1,8
< # Normal — default healthy configuration
< RETRY_COUNT=3
< RETRY_DELAY_MS=1000
< TIMEOUT_MS=5000
< FAULT_ENABLED=false
< FAULT_LATENCY_MS=0
< FAULT_ERROR_RATE=0.0
< FAULT_LATENCY_JITTER_MS=0
< KUBE_CONTEXT=northstar
< KUBE_NAMESPACE=northstar
---
> # Retry Storm — aggressive retries + upstream faults
> RETRY_COUNT=10
> RETRY_DELAY_MS=500
> TIMEOUT_MS=30000
> FAULT_ENABLED=true
> FAULT_LATENCY_MS=5000
> FAULT_ERROR_RATE=0.3
> FAULT_LATENCY_JITTER_MS=2000

The diff is the incident in a handful of lines. RETRY_COUNT went 3 → 10, TIMEOUT_MS went 5000 → 30000 — the retry configuration. Simultaneously the upstream got a 5-second latency injection (FAULT_LATENCY_MS=5000) and a 30% error rate. The exact grouping of your diff output may differ, but the two knobs that matter — retries up, timeout up — are the causal change. Everything the Deep Dive does is prove these are the cause and not the CPU graph the dashboard is screaming about.

Step 8 — Grade the module​

Run the machine checks for M14:

scripts/grade.sh m14
Expected output

========================

Checking: SRE, Observability & Incident Response — SLOs and error budgets, golden-signal evidence, bounded queries, and hypothesis-driven investigation

  ✓ SLO: the error-rate recording rule orders_api:error_rate:5m exists — the SLI is precomputed from the golden-signal metric, not hand-queried per incident
  ✓ SLO: the latency recording rule orders_api:latency_p95:5m exists — p95 is a golden signal computed from the request-duration histogram
  ✓ ERROR BUDGET: the SLOErrorBudgetBurn alert fires when error rate exceeds the 1% budget — the alert is a burn threshold, not a raw count
  ✓ SLO: the latency SLO threshold is 500ms (0.5s) — the objective is a named number the alert gates on, not a vibe
  ✓ GOLDEN SIGNALS: orders-api exports the four evidence metrics — request count (traffic+errors), duration histogram (latency), upstream errors — as real Prometheus series
  ✓ EVIDENCE: the upstream retry counter orders_api_upstream_retries_total exists — the retry storm is measurable, not inferred from logs alone
  ✓ ANTI-FIREHOSE: the SLI queries are bounded by a 5m rate window and aggregated (sum/by le) — a bounded question, not sum(everything)
  ✓ RETRY STORM: the retry-storm fixture raises RETRY_COUNT to 10 and TIMEOUT_MS to 30000 — the causal change is the retry config, provable from the fixture, not a guess
  ✓ MECHANISM: the inventory client retries retry_count+1 times with exponential backoff — 10 retries + a 30s timeout is an 11x upstream amplifier, readable in source
  ✓ EVIDENCE PACKET: a well-formed sre-investigator packet (hypothesis + sources + out_of_scope) validates — a claim with provenance is evidence, not decoration
  ✓ PROVENANCE: an evidence packet with a confident hypothesis and NO sources is rejected (exit 4) — an assertion dressed as evidence is contamination
  ✓ HYPOTHESIS SYNTHESIS: three independent dimensions that converge on the retry-config root cause from their OWN evidence yield verdict=corroborated — real agreement, not an echo
  ✓ FALSIFY, DON'T ECHO: a packet derived_from a peer's hypothesis (not its own evidence) is rejected as consensus theater (exit 4) — three echoes are one guess, not three confirmations
  ✓ AUTHORITY: the sre-investigator role has no Edit/Write tool — the investigator produces evidence and recommends a fix, it never applies one

RESULT: PASS (15 passed)

Every check maps to a claim in the lesson, and all of them are deterministic reads of the repo — the SLO rules, the metrics source, the retry client, the evidence and synthesis scripts, the role's authority. grade.sh m14 passes whether or not you ran the optional live stack in Step 3. The counts and exact wording may differ on your machine; a pass means the observability discipline holds on the files alone.

Teardown​

Remove the scratch packet files. Nothing on the graded path modified the workspace or started a persistent process:

rm -f /tmp/packet-good.json /tmp/packet-bad.json /tmp/hyps-good.json /tmp/hyps-theater.json
# Only if you ran the optional live stack in Step 3:
docker compose --profile observe down 2>/dev/null || true
Expected output

The scratch files are gone and any observe-profile containers are stopped. The graded steps left nothing behind — they only read the repo — so re-running the lab from a clean slate is free.

Reset to a known state

If anything is in a strange state, scripts/reset.sh m14 returns the workspace to the module's start state, and scripts/inject.sh normal clears any fault injection left over from experimenting with the live path.
