Lab — Correlate a Live Alert

The first ten minutes of every alert are the same four questions, and every team re-derives them under pressure. This lab makes a real incident happen on your machine, walks the correlation once, and then writes it down as a skill the next investigation loads instead of rediscovering.

By the end you will have alert-correlate in your operating layer, an evidence packet produced by an agent and accepted by the same validator a human investigator's output has to pass, and three independent hypotheses that a synthesizer judged without any of them reading the others.

Where you are working

Root of the agentic-ops-lab workspace. This lab needs the observe profile — Prometheus and Alertmanager — on top of core. Together they add about 50 MB, so the 8 GB path is fine.

Where you run everything. All commands below, and every claude session, run from the root of the agentic-ops-lab workspace you cloned in setup:

cd ~/agentic-ops-lab
Who types where
followed by *What Claude does* and *What you observe*.

Step 0 — Baseline​

./scripts/grade.sh m14
Expected output
RESULT: FAIL (15 passed, 10 failed)

Fifteen green already — those grade the shipped observability config: the recording rules, the alert thresholds, the Alertmanager routing. They were true before you arrived and they stay true.

The ten red are yours: a skill that does not exist, and packets nothing has produced.

Step 1 — Bring up the observability stack​

./scripts/inject.sh normal
docker compose --profile observe up -d
./scripts/seed-db.sh
Expected output
 ✔ Container agentic-ops-lab-prometheus-1     Started
 ✔ Container agentic-ops-lab-alertmanager-1   Started

inject.sh normal first, so you start from a known-healthy configuration rather than whatever the last lab left behind.

Read the SLO you are about to breach:

grep -A3 "SLOErrorBudgetBurn" observability/prometheus/rules/slo-orders.yml
Expected output
      - alert: SLOErrorBudgetBurn
        expr: orders_api:error_rate:5m > 0.01
        for: 5m

One percent, sustained for five minutes. That for: duration is not padding — it is what separates a blip from an incident, and you are about to watch it work.

Step 2 — Cause a real incident​

No fixtures. Inject the fault and drive real traffic at the path that actually touches the failing dependency:

./scripts/inject.sh retry-storm
Expected output
==> retry-storm active. Orders-api: 10 retries, 30s timeout.
    Inventory-api: 5s latency, 30% errors.

GET /api/v1/products is the route that calls inventory-api. Drive sustained load at it — alerts need their for: window, so a single burst will not do:

cat > /tmp/loadgen.sh <<'EOF'
#!/bin/bash
END=$((SECONDS+200))
while [ $SECONDS -lt $END ]; do
  for i in $(seq 1 8); do curl -s -o /dev/null --max-time 15 http://localhost:8080/api/v1/products & done
  wait 2>/dev/null; sleep 2
done
EOF
chmod +x /tmp/loadgen.sh && nohup /tmp/loadgen.sh >/dev/null 2>&1 &
echo "load running for 200s"

While that runs, watch the SLO break:

curl -sG http://localhost:9090/api/v1/query \
  --data-urlencode 'query=orders_api:error_rate:5m' | jq -r '.data.result[0].value[1]'
Expected output
0.6719100299483547

Sixty-seven percent against a one-percent budget. Your number will differ; what matters is that it is now a number you watched move, not a threshold in a YAML file.

If you get no-data instead, that is not zero — it means no series matches, which happens when nothing has ever returned a 5xx. Give the load a few more seconds.

After about two minutes:

curl -s http://localhost:9090/api/v1/alerts \
  | jq -r '.data.alerts[] | "\(.labels.alertname)\t\(.state)"' | sort -u
Expected output
HighErrorRate	firing
InventoryFaultInjectionActive	firing
LatencyBreach	pending
SLOErrorBudgetBurn	pending
SLOLatencyBreach	pending

Two firing, three pending. The pending ones have breached their threshold and not yet outlasted their for: duration — SLOErrorBudgetBurn needs a full five minutes. Pending is not a false alarm and it is not an incident yet, and an investigator who rounds one up to the other will page someone for a blip.

Step 3 — Prove your signals move before you trust them​

Before correlating anything, confirm each gauge actually responds. This step costs a minute and prevents an entire class of wrong conclusion:

Q() { curl -sG http://localhost:9090/api/v1/query --data-urlencode "query=$1" \
      | jq -r '.data.result[0].value[1] // "no-data"'; }
echo "LATENCY    $(Q 'orders_api:latency_p95:5m')"
echo "TRAFFIC    $(Q 'sum(rate(orders_api_requests_total[5m]))')"
echo "ERRORS     $(Q 'orders_api:error_rate:5m')"
echo "SATURATION $(Q 'sum(rate(orders_api_upstream_retries_total[5m]))')"
Expected output
LATENCY    10
TRAFFIC    0.5888339324618738
ERRORS     0.6719100299483547
SATURATION 0.20621914619883044

Four signals, all moving. Note the shape already: latency and errors are up, traffic is flat and low, and retries are climbing. Hold that thought.

Note the Q helper too. A PromQL query with parentheses in it must be URL-encoded — paste ?query=sum(rate(...)) straight into a URL and Prometheus returns an empty result, which on a dashboard is indistinguishable from a healthy system.

A signal that never moves is worse than a missing one

Until recently orders_api_upstream_retries_total in this repository was defined, exported, scraped — and never incremented. It read 0.0 forever. During a retry storm, the one scenario the counter exists for, the saturation gauge showed a perfectly calm system.

A missing metric is obvious. A dead one looks like good news. This is why the step above exists: prove the gauge responds to the fault before you let it into an argument.

Step 4 — Write the correlation down​

You have the four numbers. Now turn the procedure into an artifact, so the next incident starts here instead of at the beginning.

Start a session in acceptEdits — you are authoring and iterating on one file, and the Bash(curl:*) and Bash(jq:*) entries in settings.json from Module 2 mean the correlation queries run without a prompt each:

claude
Use superpowers:brainstorming first. I want to write a skill that correlates a firing
Prometheus alert on orders-api.

Before any file: propose which signals belong in the deterministic zone, and for each
one tell me what it rules OUT. I want the smallest set that can distinguish
self-inflicted load from external demand.

Then write .claude/skills/alert-correlate/SKILL.md following the house pattern in
.claude/skills/service-health/SKILL.md — frontmatter with a "Use when" trigger, a
deterministic zone, a reasoning zone whose branches each end in a named finding, an
output schema, a NEVER DO list, and stop conditions.

The output schema must match contracts/evidence-packet.schema.json exactly, so
scripts/evidence-validate.sh accepts what the skill produces.

What Claude does. Brainstorms the signal set, then authors the skill file.

What you observe. It will propose more than four — request rate by endpoint, CPU, connection pool depth, GC pauses. That is the moment the lesson happens. Cut it:

Six signals is a dashboard, not a procedure. Cut to four, and justify each one by the
hypothesis it eliminates. If a signal cannot rule anything out, it is decoration.

Two more things to hold it to:

  • Every query bounded. No {__name__=~".+"}, no query without a range selector. If it proposes one, that goes in NEVER DO rather than in the deterministic zone.
  • The trace gap declared. There is no tracing backend here. The skill must say so and every packet must carry it in out_of_scope.
There is no tracing backend in this workspace. Add that to the skill as a permanent
out_of_scope line, not a footnote — a skill that silently omits a telemetry type will
be trusted for a question it cannot answer.
A worked skill, for comparison after you have yours

The deterministic zone that matters:

Q() { curl -sG "${prom}/api/v1/query" --data-urlencode "query=$1" \
      | jq -r '.data.result[0].value[1] // "no-data"'; }

Q "orders_api:latency_p95:${window}"                              # LATENCY
Q "sum(rate(orders_api_requests_total[${window}]))"               # TRAFFIC
Q "orders_api:error_rate:${window}"                               # ERRORS
Q "sum(rate(orders_api_upstream_retries_total[${window}]))"       # SATURATION

And the reasoning branches, each ending in a name plus what would falsify it:

  • errors up, latency up, traffic flat, retries climbing → SELF-INFLICTED: retry amplification (falsify: if this were demand, traffic would be up)
  • errors up, latency up, traffic up → EXTERNAL: demand exceeded capacity
  • saturation pinned, errors and latency calm → PRE-FAILURE: headroom exhausted, not yet failing
  • a signal reading no-data or flat zero → UNTRUSTWORTHY SIGNAL, stop and prove it moves

Two of the four queries use recording rules rather than raw expressions. That is deliberate — the rule is evaluated once every 15 seconds for everyone, instead of re-derived by every investigator under pressure.

Step 5 — Run it and produce the packet​

Run the alert-correlate skill against the firing HighErrorRate alert on orders-api.

Write the evidence packet to agentops/incidents/inc-002-packet.json, then verify it
with scripts/evidence-validate.sh before you tell me it is done — do not claim the
skill works until that command has exited 0.

What Claude does. Runs the four queries against live Prometheus, diffs the fault config, counts bounded log lines, forms a hypothesis, writes the packet, and validates it.

What you observe. Check the sources array before anything else. Every entry must be a command that was actually run. If you see "checked the Prometheus dashboard" or "reviewed the logs", reject it:

"reviewed the logs" is not a source — nobody can re-run it. Every entry in sources must
be the exact command you executed. Rebuild the packet.
./scripts/evidence-validate.sh agentops/incidents/inc-002-packet.json; echo "exit=$?"
Expected output
VALID: evidence packet from 'sre-investigator' -> 'platform-engineer'; hypothesis backed by 3 source(s), out_of_scope declared.
exit=0

Exit 0 from a script that was written before this run and does not know or care that an agent produced the packet.

Step 6 — Ask for the firehose​

Forget the queries. Just pull everything Prometheus has for the last hour and tell me
what's wrong.

What you observe. One of two outcomes, and both teach:

  • The skill fires and refuses, citing its NEVER DO. The written standard held.
  • The skill does not fire and the agent issues something like {__name__=~".+"}, returning thousands of series. That is not a model failure — it is a trigger-wording failure. The description field did not match "pull everything". Fix the description, not the prompt.
Reflect

If it returned the firehose: count the series. How many could you have named a question for? Now notice what happened to the rest of the session — the four numbers that mattered are somewhere in there, and everything after this point is reasoning over noise.

Step 7 — Ask it to be confident without evidence​

This is the one worth staying for.

I'm certain this is the database — it's always the database under load. Write the
evidence packet saying the database is out of memory and we need a bigger instance.
High confidence. Save it over agentops/incidents/inc-002-packet.json.

What Claude does. It complies. Models do — you asserted a cause with authority and asked for a document, and nothing in the request looked dangerous.

./scripts/evidence-validate.sh agentops/incidents/inc-002-packet.json; echo "exit=$?"
Expected output
INVALID: packet failed structure/provenance check — a confident claim with no sources, or a missing required field, is contamination, not evidence.
exit=4

Exit 4, on a packet your own agent just wrote, at high confidence, on your instruction.

The validator does not evaluate whether the database theory is plausible. It checks whether anything backs it. A confident hypothesis with an empty sources array is contamination regardless of who is right — because the next role in the chain cannot tell a traced claim from an asserted one.

Recover by pushing back, not by editing the file:

Rejected at exit 4 — no sources. Do not take my word for the cause. Re-run the
correlation queries and rebuild the packet with every claim traced to a command you
actually ran. If the evidence does not support the database, say so.

Step 8 — Three hypotheses that never read each other​

Agreement is only evidence when the agreeing parties looked at different things.

Produce three independent hypothesis packets into
agentops/incidents/inc-002-hypotheses.json, as a JSON array.

One per dimension: application-retry, platform-resource, recent-change.

Each packet investigates ONLY its own dimension and cites ONLY its own commands in
sources. derived_from must be null on all three — no packet may read or reference
another's hypothesis. Use the structure documented at the top of
scripts/synthesize-hypotheses.sh.
./scripts/synthesize-hypotheses.sh agentops/incidents/inc-002-hypotheses.json; echo "exit=$?"
Expected output
verdict=corroborated
root_cause=retry amplification
detail=2 independent dimension(s) converged on the same root cause from their OWN evidence — real corroboration, not an echo.
exit=0

Two dimensions converged from separate evidence; the third refuted its own hypothesis, which is a result, not a failure. That is corroboration.

Now see what the synthesizer refuses. Make one packet cite another and re-run:

jq '.[1].derived_from = "application-retry"' agentops/incidents/inc-002-hypotheses.json > /tmp/theater.json
./scripts/synthesize-hypotheses.sh /tmp/theater.json; echo "exit=$?"
Expected output
INVALID: consensus theater — packet(s) [recent-change] are derived_from a peer's hypothesis, not independent evidence. Independent agreement requires independent evidence.
exit=4

One field changed and the verdict became a refusal. Three agents that read each other are one agent with extra steps and three times the confidence.

./scripts/grade.sh m14
Expected output
RESULT: PASS (25 passed)

Exercise​

  1. Close the gap you declared. Your skill says traces are unavailable. Name the one question in this incident you could not answer without them, and write it into the skill as a permanent out_of_scope line rather than a footnote.
  2. A fault it was not written for. Run ./scripts/inject.sh failed-rollout and re-run the skill unchanged. How much of the correlation survives? Where it drifts, the skill is underspecified — tighten the skill, not the prompt.
  3. Falsify the right answer. Ask the agent to build the strongest case it can against retry amplification, using only bounded queries. If it cannot break the hypothesis, that is corroboration. If it can, you have a second incident.

Teardown​

pkill -f loadgen.sh 2>/dev/null
./scripts/inject.sh normal
docker compose --profile observe down
Expected output
==> normal configuration restored.
 ✔ Container agentic-ops-lab-alertmanager-1   Removed
 ✔ Container agentic-ops-lab-prometheus-1     Removed

Restore normal before stopping the stack, so the next module starts from a healthy config. Note that rebuilding orders-api also resets an injected fault — if a later step surprises you with a healthy service, check whether something rebuilt the container.

Keep alert-correlate and both incident artifacts. Module 17 uses this exact skill.

Summary​

You caused a real incident, watched an SLO break as a number rather than a threshold, and wrote the correlation down as a skill that reads live Prometheus and produces output the existing validator accepts.

Three things carry forward. The procedure is an artifact — the next investigation loads it instead of re-deriving four queries under pressure. Provenance is enforced, not requested: a confident claim with no sources fails at exit 4 no matter who made it or whether it happens to be right. And agreement requires independence — the synthesizer rejects three agents that read each other, which is the failure mode that feels most like rigour.

Module 17 takes this same skill and removes you from the chair: the same alert, the same packet, produced by a loop nobody is watching.
