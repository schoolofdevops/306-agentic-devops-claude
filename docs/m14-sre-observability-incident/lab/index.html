Lab — The Evidence Packet

An alert fires. Somebody asks an agent what is wrong, and ninety seconds later there is a confident paragraph naming a root cause. The question this lab is about is not whether that paragraph is impressive. It is: would you make a change based on it, and could you show anyone why?

You will run a real incident — a retry storm, injected into a live stack with Prometheus watching — and have the read-only sre-investigator role produce an evidence packet under the harness. Then you will check the packet the way a reviewer would: does every claim name the command that produced it, and does it say what it did not look at. Then you will break it in the two ways that matter, and watch a script catch both.

By the end you will have a diagnosis you can defend, a written procedure so the next one is cheaper, and a clear sense of which parts of an investigation a model should never be trusted with.

Where you are working

The agentic-ops-lab workspace, with the observability stack running. The incident ticket is incidents/INC-002-retry-storm.md; the checkers are scripts/evidence-validate.sh and scripts/synthesize-hypotheses.sh.

cd ~/agentic-ops-lab

This module needs Docker (Prometheus, Alertmanager and both services run as containers). No Kubernetes.

Step 0 — Stand up the stack and confirm you are looking at a real system​

docker compose --profile observe up -d
docker compose --profile core up -d --build
sleep 20 && bash scripts/seed-db.sh | tail -2
curl -s -o /dev/null -w 'orders=%{http_code}\n'     http://localhost:8080/healthz
curl -s -o /dev/null -w 'inventory=%{http_code}\n'  http://localhost:8081/healthz
curl -s -o /dev/null -w 'prometheus=%{http_code}\n' http://localhost:9090/-/ready
Expected output
==> Seed complete. 20 orders in database.
orders=200
inventory=200
prometheus=200

Three 200s. If Prometheus is not ready, give it another twenty seconds — it starts slower than the services it scrapes.

Confirm Prometheus is actually scraping, because an investigation against a blind Prometheus produces confident nonsense:

curl -s 'http://localhost:9090/api/v1/targets' \
  | jq -r '.data.activeTargets[] | "\(.labels.job) \(.health)"' | sort | uniq -c
Expected output
   1 inventory-api up
   1 orders-api up
   1 prometheus up

Three targets, all up. This is the step people skip. Every number you are about to reason about comes from here; if a target were down, the metric would simply be absent, and absence reads exactly like "no problem".

Step 1 — Check the role before you trust it​

grep -E '^(tools|disallowedTools):' .claude/agents/sre-investigator.md
Expected output
tools: ["Read", "Grep", "Glob", "Bash", "Skill"]
disallowedTools: ["Edit", "Write", "MultiEdit", "NotebookEdit"]

Two halves, and both are deliberate.

Skill is present, so the role can invoke the house triage procedure. Until this module was written it was missing, which meant the role whose entire job is running incident-triage could not invoke it — it would read SKILL.md as an ordinary file, improvise something similar, and produce output that looks the same. That is the third role in this course found with the same gap. Check the tools list before you trust any role with a method.

disallowedTools is the other half: this role cannot write anything. It reads, it runs read-only commands, and it hands you a packet. It cannot save that packet, cannot edit a config to test a theory, and cannot write the skill you will produce at the end. Investigating is read-only work; everything that changes the system is a different authority.

Step 2 — Cause a real incident​

bash scripts/inject.sh retry-storm | tail -2
Expected output
==> retry-storm active. Inventory-api: 5s latency, 30% errors — orders-api exhausts its retry budget against a slow upstream.

An injected fault with no traffic is invisible. Generate some:

cat > /tmp/loadgen.sh <<'EOF'
#!/bin/bash
END=$((SECONDS+200))
while [ $SECONDS -lt $END ]; do
  for i in $(seq 1 8); do curl -s -o /dev/null --max-time 15 http://localhost:8080/api/v1/products & done
  wait 2>/dev/null; sleep 2
done
EOF
chmod +x /tmp/loadgen.sh && nohup /tmp/loadgen.sh >/dev/null 2>&1 &
sleep 100
curl -sG http://localhost:9090/api/v1/query \
  --data-urlencode 'query=orders_api:error_rate:5m' | jq -r '.data.result[0].value[1]'
curl -s http://localhost:9090/api/v1/alerts \
  | jq -r '.data.alerts[] | "\(.labels.alertname) \(.state)"' | sort | uniq -c
Expected output
0.16378447906245536
   1 HighErrorRate pending
   2 InventoryFaultInjectionActive firing
   1 LatencyBreach pending
   1 SLOErrorBudgetBurn pending
   1 SLOLatencyBreach pending

Your numbers will differ — the error rate depends on how long the load has run. Sixteen percent against a one-percent budget, and five alerts in flight.

Read the states carefully, because this distinction matters during a real page. firing means the condition has held for the rule's for: duration. pending means it is true right now but has not held long enough yet. A pending alert is neither a false alarm nor an incident — it is a condition that has not yet earned a page, and treating the two as the same is how teams end up either paging on noise or missing a real one.

Step 3 — Write the brief​

The brief is short and it is about the investigation, not the fix. Write agentops/incidents/INC-002-BRIEF.md:

# INC-002 Investigation — Requirements

## Why
Alerts are firing on orders-api and somebody will ask us to change something within
the hour. Whatever we change has to be defensible afterwards, to people who were not
in the room.

## What the investigation must establish
- What is actually failing, stated as something observable.
- The chain from that symptom back to a cause, with each link attached to a command.
- What was NOT examined, so nobody mistakes silence for absence.

## Constraints
- Read-only. Nothing about the running system changes during the investigation.
- Every claim cites the exact command that produced it and what it returned.
- The evidence collected is the evidence the ticket scopes. No exploring.

## Done means
- scripts/evidence-validate.sh accepts the packet.
- The packet names what it did not look at.
- A second person could re-run every source command and get the same picture.
The requirement that does the work

"What was NOT examined, so nobody mistakes silence for absence."

An investigation that reports only what it found is indistinguishable from one that looked everywhere. In this run the agent declared that a metric returned no rows and it did not chase why — which is exactly the sort of thing that would otherwise vanish, and exactly the sort of thing that turns out to matter two hours later.

Step 4 — Hand it to the read-only role​

claude --agent sre-investigator --dangerously-skip-permissions --model claude-sonnet-5
INC-002 is live: incidents/INC-002-retry-storm.md. The observability stack is up
(Prometheus on 9090, both services running).

Use superpowers and the incident-triage skill to do this properly. Collect the bounded
evidence the ticket scopes, then emit a filled evidence packet as JSON on stdout -
every claim must cite the exact command that produced it.

Do not fix anything.

What Claude does. It invokes incident-triage, reads the ticket to learn the scope, and runs only the commands that scope names. On the captured run: turns=6, cost=$0.2378, about 35 seconds.

What you observe. It emits the packet and refuses to persist it — it has no Write tool. Save it yourself, which is the human half of the boundary:

mkdir -p agentops/incidents
# paste the JSON block the agent emitted into this file
$EDITOR agentops/incidents/INC-002-packet.json
jq -r '.evidence.sources[]' agentops/incidents/INC-002-packet.json | head -5
Expected output
curl -s -o /dev/null -w orders_healthz http://localhost:8080/healthz -> 200
curl -s -w orders_readyz http://localhost:8080/readyz -> {"status":"not ready","checks":{"inventory_api":false}}
curl -s -o /dev/null -w inventory_healthz http://localhost:8081/healthz -> 200
docker compose exec orders-api env | grep -E 'RETRY|TIMEOUT' -> RETRY_DELAY_MS=1000, TIMEOUT_MS=5000, RETRY_COUNT=3
curl -s http://localhost:8081/admin/faults | jq . -> enabled:true, latency_ms:5000, error_rate:0.3, stats.latency_injected:159, stats.errors_injected:48

Read the fourth line, because it is the one that makes the diagnosis land: three retries, a one-second delay, a five-second timeout — against an upstream that now takes five seconds to answer. The retry policy turns one slow call into four, and the storm is the client's own doing.

Every line is a command and its result. A source you cannot re-run is not a source, and this is the difference between an investigation and an opinion with good vocabulary.

Step 5 — Check it the way a reviewer would​

bash scripts/evidence-validate.sh agentops/incidents/INC-002-packet.json; echo "rc=$?"
Expected output
VALID: evidence packet from 'sre-investigator' -> 'ops-lead'; hypothesis backed by 8 source(s), out_of_scope declared.
rc=0

Now read the part nobody asks for:

jq -r '.out_of_scope[]' agentops/incidents/INC-002-packet.json
Expected output
Did not run DELETE /admin/faults (mutating action, outside investigator authority)
orders_api_upstream_errors_total metric returned no data rows — did not dig further into metric naming/labels
Did not check Prometheus alert-rule definitions or Alertmanager routing directly, relied on ticket-stated alert names
Did not inspect inventory-api source or its own logs beyond fault-state endpoint
No kubectl checks run — env is docker compose, not k8s, per ticket scope

Five declarations, and two of them are worth stopping on.

The first is the authority boundary appearing inside the artifact — the agent noting that clearing the fault would have been a mutation and therefore not its call. Nobody prompted that.

The second is the one that earns the whole requirement: a metric returned no rows, and it said so. An investigation that silently drops an empty query looks identical to one where the query came back clean. "I looked and found nothing" and "I looked and the query was broken" lead to opposite decisions.

Step 6 — Break it the first way: confidence without evidence​

This is the failure mode that makes agentic investigation dangerous, so produce it deliberately:

jq '.evidence.sources = [] | .evidence.confidence = "high"' \
   agentops/incidents/INC-002-packet.json > /tmp/unsourced.json
bash scripts/evidence-validate.sh /tmp/unsourced.json; echo "rc=$?"
Expected output
INVALID: packet failed structure/provenance check — a confident claim with no sources, or a missing required field, is contamination, not evidence.
rc=4

Exit 4, not exit 1. The file is perfectly well-formed JSON and reads convincingly — the failure is that it is unfounded, which is a different thing from unparseable, and the checker keeps them apart.

That packet is what an unbounded investigation produces on a bad day: the same vocabulary, the same confident tone, no way to re-derive any of it. A validator that accepts this is a validator that accepts everything.

Step 7 — Break it the second way: agreement that is an echo​

Three investigators on three dimensions — application retries, platform resources, recent changes — is the standard way to widen an incident. It is only worth anything if they reason independently:

bash scripts/synthesize-hypotheses.sh fixtures/capstone/hypotheses.json; echo "rc=$?"
Expected output
verdict=corroborated
root_cause=retry-amplification
detail=3 independent dimension(s) converged on the same root cause from their OWN evidence — real corroboration, not an echo.
rc=0

Now change one field — not a conclusion, a provenance marker saying the second hypothesis was derived from the first:

jq '.[1].derived_from = "h1"' fixtures/capstone/hypotheses.json > /tmp/theater.json
bash scripts/synthesize-hypotheses.sh /tmp/theater.json; echo "rc=$?"
Expected output
INVALID: consensus theater — packet(s) [platform-resource] are derived_from a peer's hypothesis, not independent evidence. Independent agreement requires independent evidence.
rc=4

The conclusions did not change. Same root cause, same three agreeing voices, same words. One field of provenance is the entire difference between corroboration and an echo — and there is no way to tell them apart by reading the text, which is why the field exists.

This is the thing to carry into any fan-out: three agents that saw each other's answers are one agent with extra steps, and the confidence you feel reading them is manufactured.

Step 8 — Close the loop: turn the investigation into a procedure​

You now have a diagnosis. The value of writing it down is that the next retry storm costs four cents instead of twenty-four.

The investigator cannot do this — writing is not its authority. Leave that session and ask in an ordinary one:

Read agentops/incidents/INC-002-packet.json and incidents/INC-002-retry-storm.md.

Write .claude/skills/alert-correlate/SKILL.md: the procedure that turns an alert on
orders-api into the packet we just produced by hand. Use superpowers - brainstorm the
design, then write it.

Requirements:
  - every query is bounded by a time window and a service; no unbounded dumps
  - it names the four golden signals and which command reads each one
  - it declares what it cannot see, including that we have no traces
  - it collects evidence and stops. It never remediates.

Then tell me what this skill would have missed on INC-002.

What Claude does. Brainstorming fires and it stops for approval before writing — on the captured run the design turn cost $0.80 and the writing turn $0.60. Approve it.

What you observe. A skill with a bounded query per signal, and then the answer to the last question, which is worth more than the skill:

  • The actual root cause. The skill only correlates golden signals by time window; it never states that orders-api's retries are amplifying load onto an already-faulted inventory-api. That inference is exactly what it is designed to hand off, not produce.
  • The fault-injection state itself. GET /admin/faults (which showed latency_ms:5000, error_rate:0.3, and injection counters) isn't one of the four golden signals or in alerts.yml, so the skill never reads it — the smoking gun in the original packet would be absent.
  • The retry config values. RETRY_DELAY_MS/TIMEOUT_MS/RETRY_COUNT aren't a metric or log line either — the skill has no step for reading service config, so the amplification detail would be missing too.

Read the second and third bullets against your own packet from Step 5. The two sources that made the diagnosis land are both things this skill would not collect. That is not a bug in the skill; it is the honest cost of bounding it. A procedure narrow enough to run unattended is narrow enough to miss the smoking gun, and knowing which one you have is the judgment.

Verify it is bounded rather than trusting the summary:

grep -c '\[[0-9]\+m\]' .claude/skills/alert-correlate/SKILL.md
grep -icE 'trace|cannot see|do not have' .claude/skills/alert-correlate/SKILL.md
Expected output
1
3

Your counts will differ — this is a snapshot of one run. What matters: at least one bounded window, and a declared gap. A correlation skill that does not say "we have no traces here" will keep producing packets that quietly assume it does.

Step 9 — Where this goes next: the alert fires it for you​

Everything so far was you deciding to investigate. Watch the trigger that would decide for you:

curl -s http://localhost:9090/api/v1/alerts \
  | jq -r '[.data.alerts[] | select(.state=="firing")] | length'
curl -s http://localhost:9093/api/v2/alerts 2>/dev/null | jq -r 'length'
Expected output
2
2

Alertmanager is holding the same firing alerts Prometheus is. Its config already names a webhook receiver — observability/alertmanager/alertmanager.yml points at http://localhost:9095/webhook, and nothing is listening on that port yet.

That gap is the next module's subject: the receiver, and the six properties an unattended loop needs that a human supplies for free — a correlation ID, deduplication, idempotency, a timeout, a bounded action set, and a way to distrust the trigger itself. What you built here is what that loop runs. Its quality is the ceiling on anything automated around it.

Which model for this lab, and why​

The triage run cost $0.2378 on Sonnet — six turns, thirty-five seconds, one model call for the whole investigation. Everything that decides whether to believe that investigation is a shell script and costs nothing: evidence-validate.sh, synthesize-hypotheses.sh, the Prometheus queries.

That ratio is the argument. Reading a system and forming a chain of reasoning is judgment, and worth a capable model. Deciding whether a packet has sources is arithmetic, and must never be a model's opinion — because the failure you are guarding against is precisely a model being convincing without being right.

Use Haiku for the skill-authoring turn in Step 8 if you want to see the difference; the procedure comes out shorter and the honest-gaps answer gets thinner.

Limits — what this lab does not give you​

  • No traces. This stack has metrics, logs and events. Every packet it produces reasons about a distributed call path without seeing one, and the skill you wrote should say so.
  • The validator checks provenance, not truth. A packet with eight sources that support a wrong conclusion passes. It guarantees you can re-derive the reasoning, not that the reasoning is right.
  • derived_from is self-reported. Consensus theater is caught only when the packet admits its lineage. Three agents that silently anchored on a shared prompt look independent.
  • One incident, one environment. The retry storm is injected and the fault endpoint tells you so. A real one has no /admin/faults to read.
  • Pending is not firing, and neither is "resolved is fixed". Alertmanager clearing an alert means the condition stopped, not that the cause was removed.

Exercise​

  1. Find what the skill would miss. Re-run Step 4's investigation against INC-001 using your new skill, and list every claim it cannot source. That list is the skill's next version.
  2. Make the empty metric loud. The packet declared a metric that returned no rows. Add a check to evidence-validate.sh that fails a packet whose sources include a query with an empty result but whose confidence is high.
  3. Try to fool the synthesiser. Produce three hypotheses that genuinely agree, with derived_from absent, but which all rest on the same single source command. Does corroborated still mean anything?

Teardown​

bash scripts/inject.sh normal | tail -1
docker compose --profile observe --profile core down
Expected output
==> All faults cleared. Services back to normal behaviour.

Leave agentops/incidents/INC-002-packet.json and the skill in place — they are the artifacts, and the grader reads them.

You ran a real incident, had a read-only role investigate it under a written procedure, and then checked its work the only way that scales: every claim re-runnable, every gap declared, and two deliberate forgeries caught by scripts rather than by judgment. The agent was worth twenty-four cents. The checkers were worth more.
