Deep Dive — The Retry Storm: Why "Add More CPU" Is the Wrong Fix

The core lab built the workbench: SLOs as computable rules, the golden signals as the bounded evidence set, the evidence-packet validator, and the hypothesis synthesizer that rejects consensus theater. This Deep Dive is the incident that machinery exists for. It is INC-002, and it is the kind of incident that gets longer the more competent the responder feels — because the dashboard hands you a confident, plausible, completely wrong answer in the first thirty seconds, and every instinct you have will want to act on it.

The symptom: orders-api p95 latency has gone from under 200ms to 28.3 seconds. Error rate is 31% against a 1% SLO. Two alerts are firing. And the resource graphs show CPU high on the orders-api pods. The wall-of-red story writes itself: we are overloaded, add capacity. This Deep Dive is about why that story is wrong, how to falsify it with bounded evidence rather than argue about it, how to prove the real causal change, and how to repair it the only way this course permits — through GitOps, by a role that is structurally unable to have caused the outage it is fixing.

Where you are working

You continue in the agentic-ops-lab workspace. This Deep Dive reasons over the real retry client (app/orders-api/src/inventory_client.py), the Helm values (platform/helm/orders-api/values.yaml), the fault fixtures (fixtures/fault-configs/), the Prometheus alert rules, and the incident ticket (incidents/INC-002-retry-storm.md). It grades against labs/m14/deep-dive.checks.json — every check is a deterministic read of source and config, so the diagnosis is reproducible on any machine, no live stack required. If you ran the observe profile in the core lab you can watch the storm live; the evidence below proves the same root cause either way.

The symptom, measured against the objective​

Start where the lesson said to start: not "the site feels broken" but "how far outside the budget are we." Read the incident ticket's evidence against the SLOs you defined:

grep -E 'p95 latency|error rate|retry count' incidents/INC-002-retry-storm.md
Expected output
- orders-api p95 latency: 28.3 seconds (normal: <200ms)
- orders-api error rate: 31% (SLO: <1%)
- orders-api retry count metric climbing rapidly

Measured against the objectives: p95 of 28.3s against a 500ms SLO is 56x over budget; a 31% error rate against a 1% SLO is 31x over. This is not "eating into the budget" — the budget is gone and the page is justified. But note the third line, the one the dashboard's CPU graph will try to make you ignore: the retry count metric is climbing rapidly. Hold that. It is the thread that unravels the wrong hypothesis.

The firing alert names the fingerprint. Read what UpstreamTimeoutSpike actually keys on:

grep -A2 'alert: UpstreamTimeoutSpike' observability/prometheus/rules/alerts.yml
Expected output
      - alert: UpstreamTimeoutSpike
        expr: rate(orders_api_upstream_errors_total{type="timeout"}[2m]) * 60 > 10
        for: 2m

The alert fires on orders_api_upstream_errors_total{type="timeout"} — more than 10 upstream timeouts per minute. This is a bounded query (2-minute window, one scoped metric, rate-aggregated) and it is pointing directly at the upstream call path, not at CPU. The evidence is already contradicting the "we are overloaded" story: an overloaded service is slow because of demand, not because its upstream calls are timing out in a pattern. Follow the alert, not the CPU graph.

Form the tempting hypothesis — then set up its falsification​

Discipline is not "never consider the obvious hypothesis." It is "consider it, then state the prediction it makes and check whether the prediction holds." The tempting hypothesis here is resource pressure:

Hypothesis R: orders-api is CPU-saturated under load. The fix is more CPU / more replicas.

If Hypothesis R is true, two predictions follow, and both are checkable from evidence:

  1. There is a resources block to raise — a CPU/memory limit that is currently the binding constraint.
  2. The extra load is external — traffic climbing — because saturation is what happens when demand exceeds capacity.

The whole difference between a thirty-minute incident and a three-hour one is that you check the predictions before you act on the hypothesis. Let the evidence try to kill Hypothesis R.

Falsify the resource hypothesis with bounded evidence​

Prediction 1 — is there a resource limit that is the constraint? Read the rendered Helm values for a resources block:

grep -n 'resources:' platform/helm/orders-api/values.yaml || echo "NO resources block in values"
Expected output
NO resources block in values

Prediction 1 fails. There is no resources block at all in the orders-api values — no CPU request, no CPU limit, no memory limit. "Add more CPU" targets a field that does not exist as a constraint. The pod is not being throttled at a limit, because there is no limit. You cannot raise a ceiling that was never set. Hypothesis R has taken its first serious wound: the fix it implies has no surface to act on.

Prediction 2 — is the load external? The retry counter is the discriminator. If load is external, orders_api_requests_total (traffic) climbs. If load is self-inflicted, orders_api_upstream_retries_total climbs while traffic stays flat. The incident ticket already told you which: "retry count metric climbing rapidly." The load is being manufactured inside orders-api, by the retry loop — not by more customers arriving. Prediction 2 fails too.

Both predictions of Hypothesis R are falsified by bounded evidence you can name: no resources block (nothing to scale), and a climbing retry counter with flat traffic (load is self-inflicted). Hypothesis R is dead. Not "unlikely" — dead, killed by evidence, before a single CPU was added. This is the move the whole module was built to make possible: the confident wrong answer does not survive contact with a falsification attempt.

Why "no resources block" is the sharpest evidence

A responder who trusts the CPU graph proposes "raise the CPU limit" and discovers — after editing a values file, opening a PR, waiting for review — that there was no limit to raise. That is thirty minutes spent proving a hypothesis was untestable. Reading for the absence of the field first (one grep) falsifies the fix in seconds. Absence is evidence: a fix that targets a field that does not exist is a fix aimed at nothing.

Prove the causal change​

Falsifying the wrong hypothesis is half the job; naming the real cause is the other half. The causal change is a configuration diff, and it is a real fixture. This is the events question — what changed — answered from evidence, not memory:

diff fixtures/fault-configs/normal.env fixtures/fault-configs/retry-storm.env | grep -E 'RETRY_COUNT|TIMEOUT_MS'
Expected output
< RETRY_COUNT=3
< TIMEOUT_MS=5000
> RETRY_COUNT=10
> TIMEOUT_MS=30000

There is the causal change, isolated to two lines. RETRY_COUNT went 3 → 10 and TIMEOUT_MS went 5000 → 30000. This is not correlation dressed as cause — it is the config release that preceded the symptom, and the mechanism connecting it to the 28-second p95 is readable in the client source.

Read the amplification mechanism — the reason two config lines produce a 56x latency breach:

sed -n '22,30p' app/orders-api/src/inventory_client.py
Expected output
        for attempt in range(self.settings.retry_count + 1):
            try:
                resp = await getattr(self._client, method)(path, **kwargs)
                resp.raise_for_status()
                return resp
            except (httpx.HTTPStatusError, httpx.ConnectError, httpx.ReadTimeout) as e:
                last_exc = e
                if attempt < self.settings.retry_count:
                    delay = (self.settings.retry_delay_ms / 1000.0) * (2 ** attempt)

Do the arithmetic the config implies. The loop runs range(retry_count + 1) — with RETRY_COUNT=10 that is 11 attempts per request. Each attempt is bounded by TIMEOUT_MS, now 30 seconds. So a single order request whose upstream is failing can occupy a worker for up to 11 × 30s before it gives up — minutes, against a 500ms SLO. And the backoff is (retry_delay_ms / 1000) * (2 ** attempt) — exponential with no cap — so the late retries wait longer and longer while the upstream, already slow from its own fault, gets hit 11 times by every failing request. That is the amplifier: one slow upstream call becomes eleven, the retries pile load onto the already-slow dependency, it gets slower, more requests time out, more retries fire. The system attacks itself. CPU is high because workers are spinning in this loop — a symptom of the storm, not its cause.

Now the diagnosis is complete and it is the mirror image of the tempting one: the load is self-inflicted (retries, not traffic), there is no resource ceiling to raise (no resources block), and the causal change is the retry config (a real diff), whose mechanism (11 attempts × 30s, uncapped backoff) explains the exact magnitude of the breach. Every claim traces to a source you read.

Synthesize the parallel investigation honestly​

In a real run you would not do this alone — you would fan it out to three independent investigators and let the synthesizer judge whether they really agree. Feed it the three independent findings:

cat > /tmp/storm-hyps.json <<'EOF'
[
  { "dimension": "application-retry", "root_cause": "retry-config", "status": "supported",
    "confidence": "high", "sources": ["inventory_client.py:22 (11 attempts)", "upstream_retries climbing"], "derived_from": null },
  { "dimension": "platform-resource", "root_cause": "retry-config", "status": "supported",
    "confidence": "medium", "sources": ["values.yaml: no resources block", "traffic flat, not external load"], "derived_from": null },
  { "dimension": "recent-change", "root_cause": "retry-config", "status": "supported",
    "confidence": "high", "sources": ["diff normal.env retry-storm.env: RETRY_COUNT 3->10, TIMEOUT 5s->30s"], "derived_from": null }
]
EOF
bash scripts/synthesize-hypotheses.sh /tmp/storm-hyps.json
Expected output
verdict=corroborated
root_cause=retry-config
detail=3 independent dimension(s) converged on the same root cause from their OWN evidence — real corroboration, not an echo.

verdict=corroborated. The resource investigator did not rubber-stamp the retry theory — it supported it by falsifying its own hypothesis (no resources block, traffic flat) and reporting where the evidence actually pointed. Three independent trails, one root cause, each from its own sources. This is the difference the module insisted on: corroboration you can act on, not three echoes of one guess.

There is a subtler discipline the synthesizer also enforces: if the resource investigator had not yet checked node saturation, the honest output is not a verdict — it is "keep looking." Prove it:

cat > /tmp/storm-partial.json <<'EOF'
[
  { "dimension": "application-retry", "root_cause": "retry-config", "status": "supported",
    "confidence": "high", "sources": ["inventory_client.py:22"], "derived_from": null },
  { "dimension": "platform-resource", "root_cause": null, "status": "inconclusive",
    "confidence": "low", "sources": ["kubectl top pending"], "derived_from": null, "missing": ["node saturation"] }
]
EOF
bash scripts/synthesize-hypotheses.sh /tmp/storm-partial.json
Expected output
verdict=need-more-evidence
missing=node saturation, platform-resource
detail=synthesis withheld — a hypothesis is inconclusive or a dimension is unchecked; loop before concluding.

need-more-evidence. When a dimension is inconclusive, the synthesizer refuses to declare a winner on partial data — it names the gap (node saturation) and loops. This is the guard against the other incident failure: declaring victory before the evidence is in, because the leading hypothesis felt strong enough. A strong hypothesis with an unchecked dimension is still a guess.

The contained repair — through GitOps, not the investigator's hands​

You have the root cause and the mechanism. The fix is to bring the retry configuration back to safe values (RETRY_COUNT down, a sane TIMEOUT_MS) and, as a systemic follow-up, add a circuit breaker so a slow upstream fails fast instead of being retried into the ground. The retry knobs live in desired state — the Helm values — which is exactly the field a GitOps proposal edits:

grep -A6 'env:' platform/helm/orders-api/values.yaml | grep -E 'RETRY_COUNT|TIMEOUT_MS'
Expected output
  RETRY_COUNT: "3"
  RETRY_DELAY_MS: "1000"
  TIMEOUT_MS: "5000"

The retry configuration lives in env in the Helm values — desired state, in Git. (The chart ships the safe defaults; the storm came from the runtime override in the fault fixture. The durable repair is to pin the safe values in desired state and add the circuit breaker so the next bad override cannot cause a storm.) This is a one-place change in a reviewable file, not a live-cluster edit.

Here is the part the whole course has been building toward, and it is not incidental to this incident — it is the safeguard that makes agentic incident response trustworthy. The sre-investigator that just diagnosed the storm cannot apply this fix, by construction. Confirm the change path it must use instead contains no cluster-write command:

grep -Ec '(kubectl (apply|delete|scale|patch)|helm upgrade|docker compose (up|restart))' scripts/gitops-propose.sh
Expected output
0

Zero cluster-write commands in the proposal script. gitops-propose.sh stages the desired-state change on a branch, shows the diff, and stops — it is the agent's structural stopping point, identical to the golden path from Module 12. The investigator produces an evidence packet recommending the retry-config fix; a role with write authority (the platform-engineer) makes the values edit and runs gitops-propose.sh; a human approves the diff; the reconciler syncs. The hands that diagnosed and the hands that repair are different — and neither of them is a kubectl edit on the live cluster.

The reason this separation matters most during an incident: the reflex to hand-fix production is strongest under pressure and most dangerous then. A stressed investigator with write access edits the live retry config, feels relief, and has now made a change no one reviewed to a system already on fire — and if the diagnosis was wrong, the "fix" is a second incident. By making the investigator structurally unable to apply, the storm's repair is forced through the same reviewed, auditable path as any other change. The incident does not get to suspend the governance; the governance is what the incident is stress-testing.

Grade the incident​

Run the Deep Dive checks. They certify the falsification (no resources block, self-inflicted load), the causal change (the retry-config diff), the mechanism (11 attempts, uncapped backoff), the honest synthesis (corroboration and the need-more-evidence loop), and the governance (the repair routes through GitOps, the investigator cannot apply):

scripts/grade.sh m14-deep-dive
Expected output
Checking: Deep Dive — Retry Storm: falsify the resource hypothesis, prove the retry config is the causal change, and contain the repair through GitOps

  ✓ SYMPTOM: the latency SLO is 500ms (p95) — the retry storm's 28s p95 is a breach an order of magnitude over budget, measured against a named objective
  ✓ SYMPTOM: the UpstreamTimeoutSpike alert keys on orders_api_upstream_errors_total{type="timeout"} — the firing alert points at upstream timeouts, the storm's fingerprint
  ✓ FALSIFY RESOURCE HYPOTHESIS: the orders-api Helm values contain NO resources block — 'raise CPU/memory limits' targets a field that does not exist, so the resource hypothesis cannot be the fix
  ✓ CAUSAL CHANGE: the retry-storm fixture is the change — RETRY_COUNT 3->10 and TIMEOUT_MS 5000->30000 — provable by diffing the fault fixture against the normal one
  ✓ MECHANISM: the client retries retry_count+1 attempts, each bounded by timeout_ms — 11 attempts x 30s is the amplifier that turns upstream latency into a self-inflicted storm, readable in source
  ✓ MECHANISM: backoff grows as 2**attempt with no cap — with 10 retries the late attempts wait minutes, so a single request can occupy a worker far longer than the SLO, readable in source
  ✓ PARALLEL FALSIFICATION: three independent dimensions (retry / resource / recent-change) that reach retry-config from their OWN evidence corroborate; the resource dimension REFUTES its own hypothesis and does not distort the verdict
  ✓ DISCIPLINE: when the resource dimension is inconclusive (saturation not yet checked), synthesis withholds a verdict (need-more-evidence) instead of declaring a winner on partial data
  ✓ CONTAINED REPAIR: the durable fix is a values change (lower RETRY_COUNT, add a timeout floor) in desired state — the env.RETRY_COUNT knob lives in Helm values, the field the GitOps proposal edits
  ✓ GOVERNANCE: gitops-propose.sh is the change path and contains no cluster-write command — the incident fix is proposed in Git and synced by the reconciler, never applied by the investigator
  ✓ SEPARATION OF DUTIES: the sre-investigator that diagnosed the storm has no write/apply authority — its authority-matrix row grants read + execute:[preflight,grade] only, so the diagnosis and the repair are different hands

========================
RESULT: PASS (11 passed)

Eleven green. The counts and exact wording may differ on your machine; a pass means you falsified the resource hypothesis from evidence, proved the retry config is the causal change with its mechanism, synthesized the parallel investigation honestly, and contained the repair through the reviewed change path — with the role that diagnosed structurally unable to apply the fix.

Where you will use this​

This is not a retry-tuning drill; it is the pattern of the incident that most reliably wastes an afternoon.

  • Any incident where the dashboard offers a plausible resource story. High CPU during a latency spike is the most common false lead there is. The habit that saves you: before you scale, state the prediction scaling implies (there is a limit that is the constraint; the load is external) and check it. If the retry counter is climbing and traffic is flat, the load is self-inflicted and capacity is the wrong lever.
  • Cascading failures with an upstream dependency. Retry storms, thundering herds, and connection-pool exhaustion all share the self-amplifying signature: a client behavior turns one slow dependency call into many, and the retries make the dependency slower. Reading the mechanism (how many attempts, what timeout, is the backoff capped) tells you whether you are looking at overload or amplification.
  • When an agent proposes a fix mid-incident. The retry config, the timeout, and the resources block are exactly the fields an agent can get confidently wrong under the pressure of a firing alert. Requiring an evidence packet that traces each claim to a source and routing the repair through a review gate is how you keep a fast wrong answer from becoming a fast wrong change.
  • Post-incident, converting the storm into a reviewed skill. The write-up that says "we tuned retries" is incomplete. The one that says "here is how to recognize a retry storm — retry counter climbing, traffic flat, CPU high with no resources block; here is how to falsify the resource hypothesis; here is why the fix is a contained values change, not a scale-up" becomes the procedure the next investigation loads and follows — which is how the team stops relearning this storm every quarter.
