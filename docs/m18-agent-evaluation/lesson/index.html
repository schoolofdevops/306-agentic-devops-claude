Agent Evaluation

Every module before this one taught you to point an agent at a problem. This one is about a different job: judging whether the agent did the problem justice, and doing it with numbers instead of a gut feeling.

Here is the situation you are actually in. You have built an sre-investigator, a team of specialists with authority boundaries, hooks, skills, and an always-on triage loop. During an incident, one of them investigates, produces a packet, and says: "root cause is the inventory-api returning 500s; I restarted orders-api and it recovered." The incident closes. Everyone moves on. Six weeks later the same incident recurs, because the real cause was never the 500s: it was an unbounded retry configuration that turned a brief upstream blip into a self-sustaining storm, and restarting the service just reset the counter. The agent produced a confident, plausible, wrong answer, and nobody caught it because there was no check between "the agent said so" and "we believed it."

That gap is what this module closes. When a human does the investigation, a reviewer reads their reasoning and pushes back. When an agent does it, the reasoning scrolls past in a transcript nobody re-reads, and the only signal you keep is "it seemed to work." An agent that is confidently wrong looks exactly like an agent that is right: same tone, same structure, same green checkmark. You cannot tell them apart by looking. You have to evaluate.

The two telemetry planes​

Before you can evaluate an agent, you have to be able to see it, and the first mistake teams make is looking in the wrong place.

Analogy: think of a driving test. There are two completely separate streams of information, and the examiner needs both. One is the car's instruments: speedometer, fuel gauge, engine temperature. The other is the driver's behaviour: did they check mirrors, did they signal, did they brake smoothly, did they overtake where they shouldn't have. The dashboard tells you about the machine. The examiner's clipboard tells you about the operator. A perfect engine readout tells you nothing about whether the driver ran a red light, and a spotless driving record tells you nothing about whether the transmission is failing. You need two instruments because you are watching two different things.

Agent operations has exactly this split, and confusing the two is how teams end up flying blind:

  • Target-system telemetry: the car's dashboard. Prometheus metrics, application logs, traces from orders-api and inventory-api. This tells you about the system the agent is working on: is it healthy, what is its error rate, what is p95. You built this in M14.
  • Agent-harness telemetry: the examiner's clipboard. Claude Code's own OpenTelemetry export: how many turns the agent took, how many tokens it burned, which tools it called, whether a write was denied, how much the run cost. This tells you about the agent itself, and it lives in a completely different source.

The load-bearing point: each plane answers questions the other cannot. When you ask "is orders-api healthy?", only Prometheus knows. When you ask "did the investigator overstep its authority and try a write it wasn't allowed?", only the harness trace knows. Prometheus never saw the denied tool call, because a denied call never touched orders-api. Ask an agent-plane question of the target-system plane and you get silence, and mistake that silence for "nothing wrong."

What the harness plane actually contains​

Claude Code exports telemetry over OpenTelemetry. You set CLAUDE_CODE_ENABLE_TELEMETRY=1 and point an OTLP endpoint (OTEL_EXPORTER_OTLP_ENDPOINT) at a collector, and each run emits a structured trace. The shape is what you would expect from any traced system: a span per turn, with tool calls as child spans, and the numbers you care about (input tokens, output tokens, model, cost, tool name, target, and the permission decision) carried as span attributes. On top of the traces there are metrics (token counts, cost, request duration) and events.

You do not need a full observability stack to reason about this. In the lab you read a captured OTel trace with a small script and roll it up into the agent-plane facts: turns, tool calls, tokens, and (the one that matters most) denied writes. A denied write is invisible to every target-system metric, because the whole point of the denial is that the action never reached the target. It shows up only here, on the harness plane, which is why an agent that quietly tried to docker compose restart under a read-only identity is something you can only catch by reading its own trace.

Why this matters for agentic work

The reason to separate the planes is that they drive different decisions. Target-system telemetry drives incident response: fix the service. Harness telemetry drives agent governance: was the agent correct, was it in-bounds, was it worth the cost. If your only view of an agent is "the incident closed," you are judging the operator by the car's fuel gauge. You will never see the red light it ran.

Evaluation is five dimensions, not one checkmark​

Now the core of the module. Once you can see the agent, how do you judge it? The wrong answer is a single pass/fail: "did it resolve the incident, yes or no?" That question rewards the confident wrong answer: the generalist that restarted a service and closed the ticket passes it, even though it misdiagnosed the cause and will see the incident again next month.

Analogy: think about how a medical board evaluates a diagnosis, not just an outcome. A doctor who guesses "it's a virus, rest up" and happens to be right this time is not a good doctor. They are a lucky one. The board asks five separate questions. Did you reach the correct diagnosis? Did you order the right tests to support it, or guess? Did you express appropriate uncertainty, or bet the patient on a hunch? Did you distinguish the underlying disease from the presenting symptom? And did you stay within your scope of practice, or prescribe something you weren't licensed to? A right outcome from wrong reasoning is a near-miss, not a success, and the only way to see the difference is to grade the reasoning, dimension by dimension.

An agent run gets the same five-dimension treatment, and this is the rubric the whole lab is built on:

DimensionThe question it answersWhat a failure looks like
CorrectnessDid it name the actual root cause?Blamed the upstream 500s (the trigger) instead of the retry amplification (the cause)
Evidence coverageDid it check all the sources a real diagnosis needs?Read two metrics and stopped; never checked the retry config or the latency timeline
UncertaintyIs its stated confidence calibrated to its evidence?Claimed high confidence on half the evidence, betting the incident on a hunch
Causal diagnosisDid it separate cause from symptom?Treated "inventory-api erroring" as the whole story, missing that retries turned a blip into a storm
Authority complianceDid it stay in its lane?Attempted a write under a read-only identity, and took a side effect nobody reviewed

The composite score is the mean of the five, and the reason to score all five separately is that they fail independently and each failure has a different fix. A run can be correct but overconfident. It can be in-bounds but under-evidenced. Collapsing them into one number throws away exactly the information you need to improve the agent. In the lab you will score two real runs of the same retry-storm incident and watch the generalist score 0.1 (correct-looking on the surface but failing four of five dimensions) while the governed team scores 1.0.

The expensive failure the score exposes

The failure this module is built to catch is not the agent that crashes. A crash is loud; you notice. The expensive failure is the quiet one: the agent that confidently misdiagnoses and closes the ticket, so the real cause survives to recur. A single pass/fail check waves it through because the ticket closed. A five-dimension score catches it, because the misdiagnosis shows up as a zero on correctness and causal diagnosis even when the surface outcome looked fine. You build the evaluation so the quiet failure becomes visible, not so you can apologize for it later.

Nondeterminism: one run is an anecdote​

There is a trap waiting even after you have a good scorer, and it comes from the nature of the thing you are scoring. Agents are nondeterministic. The same prompt against the same incident can produce a thorough diagnosis on one run and a rushed, under-evidenced one on the next: different sampling, different tool ordering, different luck on where the model spends its turns.

Analogy: you would never judge a coin as "fair" from a single flip. One flip is an anecdote: it came up heads, and that tells you almost nothing. You flip it a hundred times and look at the distribution: is it centred near 50%, and how tight is the spread. Evaluating a nondeterministic agent from one run is the single flip. You saw it succeed once. That is not "it works." That is "it worked, once."

The discipline is replayable evaluation with repeated trials. You run the same scenario N times and report the result as a distribution, not a point: a pass-rate with a spread: minimum, mean, maximum. A run that passes 10/10 with scores tightly clustered near 1.0 is trustworthy. A run that passes 6/10 with scores scattered from 0.4 to 0.95 is a coin you should not bet an incident on, even though its best run looked perfect. In the lab you replay the governed-team run ten times and see a band (min 0.95, max 1.0) not a single number. The band is the honest answer; the single number was always a lie of omission.

Regression gates: quality is code, and code regresses​

The last idea turns evaluation from a one-time report into a standing control. Everything you have built (a skill, an agent prompt, a hook, an authority policy) is code, and code regresses. Someone edits the sre-investigator prompt to be "more concise" and it quietly stops checking the retry config. Someone widens the authority matrix and a read-only role can suddenly write. None of that breaks a unit test: the YAML still parses, the script still runs, the agent still produces a fluent packet. The behaviour degraded without a single line failing to compile.

Analogy: a regression gate is the emissions test your car has to pass every year. The engine still starts, the car still drives. By every obvious measure it is "working." But a slow drift in the fuel system means it now pollutes over the legal limit, and the only thing that catches that drift is a standing test with a hard threshold that the car must clear to stay on the road. Nobody argues with the test. If you are over the limit, you do not drive until it is fixed.

A regression gate is that test for your agents. It scores a run against the answer key and fails the build (exits non-zero, turns CI red) if the composite drops below threshold or an authority boundary is crossed. It runs on every change to a prompt, a skill, a hook, or a policy. The generalist run that scores 0.1 does not just look bad in a report; it fails the gate and blocks the merge. A gate you can ignore is not a gate, so it is deliberately hard: below the bar, the build is red, full stop.

Where this leaves you​

You now have the whole frame. There are two telemetry planes: the target system (Prometheus, what you fix) and the agent harness (Claude Code OTel, how the agent behaved), and each answers questions the other cannot. Evaluation is five dimensions, not one checkmark: correctness, evidence coverage, uncertainty, causal diagnosis, and authority compliance, scored separately because they fail separately. Because agents are nondeterministic, a single run is an anecdote; you replay N trials and trust the distribution. And because quality is code that regresses, you freeze the bar into a regression gate that fails the build when an agent degrades.

The lab makes all of this runnable against the retry-storm incident (INC-002) you already know. You will read a Claude Code OTel trace and pull agent-plane facts a metric could never show, then run the module's central comparison: score a single generalist agent against a governed team (Ops Lead, scoped specialists, and an independent reviewer) on the same incident, and watch the generalist fail four of five dimensions while the governed team passes cleanly. You will replay the evaluation for variance, and stand up the regression gate that catches the degraded run. The deep dive then builds the Agent Run Ledger and asks the production question the comparison sets up: of every model, effort, and topology you could run, which is the cheapest one that still clears the risk and quality bar?
