Deep Dive — The Agent Run Ledger

The core lab scored two runs and declared the governed team the winner on quality: 1.0 versus 0.1. That is only half the decision a platform team actually makes. The other half is cost. In production you are never choosing between "the good agent" and "the bad agent" — you are choosing among many configurations that all work to some degree, at very different prices: a single strong-model agent, a mixed-model team, a cheap team on a weak model, one with an extra reviewer, one without. The real question is not "which is best?" but "which is the cheapest configuration that still clears the risk and quality bar?"

This deep dive builds the instrument that answers it — the Agent Run Ledger — and uses it to reach a result the core lab set up but did not state: the governed team is not just higher-quality than the generalist, it is also cheaper. That inversion is the whole reason this page exists, and it is not obvious until the ledger puts cost and quality in the same row.

Why the ledger has to join two numbers​

The core lab produced quality scores. M11 produced cost receipts. Neither, alone, can make a topology decision, and the reason is worth stating precisely.

Analogy: think about buying a car on a budget. A spec sheet that lists only horsepower tells you which car is fastest — and left alone it will talk you into the most expensive car on the lot. A spec sheet that lists only price tells you which is cheapest — and left alone it will talk you into a car that cannot climb your driveway. Neither number is a decision. The decision lives in the ratio: performance per dollar, and specifically the cheapest car that clears the bar you actually need. You cannot compute that ratio from two separate sheets in two separate drawers; you need one table with both columns side by side.

The Agent Run Ledger is that one table. Each row is one agent run, and it carries both planes of fact joined together: the configuration (topology, model, effort), the harness cost telemetry (turns, tool calls, dollars), and the quality verdict (composite score, pass/fail). Cost without quality picks the cheapest agent, which may be the one that misdiagnoses. Quality without cost picks the best agent, which may be the one that costs ten times what you need. The join is what lets you ask the only question that matters — cheapest-that-passes — and get a number back instead of a preference.

Recording runs into the ledger​

run-ledger.sh scores a run as it records it, so every row already carries the joined fact. Start clean and record both runs from the core lab:

scripts/run-ledger.sh reset
scripts/run-ledger.sh record fixtures/runs/generalist.json
scripts/run-ledger.sh record fixtures/runs/governed-team.json
Expected output
ledger cleared
recorded: run-generalist-001  config=generalist  composite=0.1  verdict=fail
recorded: run-governed-team-001  config=governed-team  composite=1  verdict=pass

Each record scores the run through eval-score.sh and appends one row joining its config, cost, and verdict. The ledger is a durable JSONL file under agentops/runs/ — a growing table you add to as you try configurations, not a one-shot report.

The ledger is idempotent on run_id — re-recording the same run overwrites its row instead of double-counting. That matters because you will re-score runs as you tune the rubric, and a ledger that grew a duplicate row every time you re-ran the scorer would silently corrupt every average you compute from it:

scripts/run-ledger.sh record fixtures/runs/governed-team.json
wc -l < agentops/runs/ledger.jsonl | tr -d ' '
Expected output
recorded: run-governed-team-001  config=governed-team  composite=1  verdict=pass
2

Still two rows after re-recording, not three. The row keyed by run-governed-team-001 was replaced. This is the same discipline as the M17 dedup ledger — a durable record keyed by a stable id, so a re-run is a no-op on the count.

The comparison the core lab set up but did not state​

Now the payoff. Print the two topologies side by side, with a column the core lab never computed — cost per quality point, the dollars spent for each unit of composite score:

scripts/run-ledger.sh compare
Expected output
[
  {
    "config": "generalist",
    "topology": "single-agent",
    "model": "sonnet",
    "cost_usd": 0.417,
    "composite": 0.1,
    "verdict": "fail",
    "unauthorized_attempts": 2,
    "cost_per_point": 4.17
  },
  {
    "config": "governed-team",
    "topology": "ops-lead+specialists+reviewer",
    "model": "mixed",
    "cost_usd": 0.286,
    "composite": 1,
    "verdict": "pass",
    "unauthorized_attempts": 0,
    "cost_per_point": 0.286
  }
]

Read the two cost_usd values first, because they invert the intuition. The generalist cost $0.417; the governed team cost $0.286. The team with more agents was cheaper — and it was also the only one that passed. cost_per_point makes the gap brutal: the generalist spent $4.17 per unit of quality (dollars over a near-zero score), the team $0.286. More governance did not mean more spend. Your absolute dollar figures are illustrative; the ratio and direction are the lesson.

If your intuition was "more agents must cost more," this is the result that corrects it, and the mechanism is the M9 and M11 lesson made concrete. The generalist ran everything — cheap log-reading turns and hard reasoning turns alike — on a single mid-tier model, and then thrashed: it took more turns and more tool calls because, without a scoped role telling it what "done" looks like, it wandered, tried an unauthorized write, and backtracked. The governed team put a haiku finops-style read where a cheap read belonged, a sonnet investigator where mid reasoning belonged, and an opus reviewer only on the final verdict — the mixed-model chain from M11 — and each role terminated at its turn budget instead of wandering. Governance bought quality and saved money, because scoping is also the cheapest way to spend tokens.

The production question: cheapest-passing​

The ledger answers the decision directly. cheapest-passing filters to rows that clear the quality bar, then returns the lowest-cost one — the configuration you should actually run:

scripts/run-ledger.sh cheapest-passing
Expected output
governed-team

The governed team — cheapest among the runs that pass. Note the filter order: cost is only the tiebreaker after the quality bar. The generalist is not eligible no matter how cheap it were, because it failed; a cheap wrong answer is not on the menu. This ordering is the whole risk discipline of the module — quality is a gate you must clear, and only then does cost decide.

The fail-closed behaviour matters as much as the happy path. Ask for the cheapest passing run when nothing passes and the ledger refuses to answer rather than handing you the "least bad" failure:

scripts/run-ledger.sh reset >/dev/null
scripts/run-ledger.sh record fixtures/runs/generalist.json >/dev/null
scripts/run-ledger.sh cheapest-passing; echo "exit=$?"
Expected output
run-ledger: FAIL-CLOSED: no passing run in the ledger — nothing meets the quality bar
exit=1

Exit 1, no answer. With only the failing generalist recorded, there is no passing run — and "cheapest failure" is never a valid production choice. Returning the least-bad failure would be exactly the confident-wrong-answer trap the whole module is built to avoid, one level up: a system that always returns something trains you to trust its output even when the honest answer is "none of these are good enough." Fail-closed keeps the quality bar a hard gate.

How to read the ledger when the choice is real​

In the lab there are two rows and the winner is stark. In production you will have a dozen, and the ledger turns a sprawling argument into a lookup. Here is the decision procedure it encodes.

If you are choosing between…The ledger column to sort byThe rule
Configurations that all passcost_usd (ascending)Take the cheapest — quality is already satisfied, so spend the least
A cheaper run that fails vs a costlier one that passesverdict first, then cost_usdThe failing run is ineligible; cost never rescues a run below the quality bar
Two passing runs at similar costunauthorized_attempts, then variancePrefer the one with a cleaner authority record and a tighter score distribution
Whether to add a stronger model or an extra reviewercost_per_point before and afterAdd it only if it lowers cost-per-point or is needed to cross the bar; otherwise it is waste

The last row is the one teams get wrong most often. Adding an opus reviewer feels like buying quality, but if the run already passes without it, you have raised cost without moving the verdict — cost-per-point went up. The ledger makes that visible: you record the with-reviewer and without-reviewer runs, compare cost_per_point, and keep the reviewer only where it earns its place (crossing the bar, or catching an authority overstep the cheaper run missed). This is the M11 FinOps discipline — right-size the spend to the requirement — applied to topology instead of infrastructure.

Effort is the third dial, alongside model and topology

The ledger records effort next to model because it is an independent lever. The same model at higher reasoning effort costs more per turn and sometimes crosses the quality bar a lower-effort run misses — but often does not, and then it is pure waste. Treat effort exactly like model choice: the cheapest effort level that clears the bar wins. The ledger lets you test "sonnet at medium effort" against "sonnet at high effort" as two rows and see whether the extra effort bought a verdict change or just a bigger bill.

Where you will use this​

The Agent Run Ledger is the artifact you will reach for the first time someone asks "should we run incident triage on opus or is sonnet good enough?" — the answer is not a preference, it is two rows in the ledger and a cheapest-passing query. It is the evidence you bring when a teammate wants to add a third reviewer "to be safe": record it, compare cost_per_point, and show whether it changed a verdict or just the bill. And it is the standing record that turns the core lab's regression gate into a budget gate as well as a quality gate — because once every run carries both cost and composite, "did quality regress?" and "did cost regress?" are the same lookup against the same table.

Seven checks, all about the join: the ledger exists and is idempotent, the cheapest-passing configuration is the governed team, its cost-per-point beats the generalist, its absolute cost is lower, and an empty ledger fails closed instead of inventing an answer. These are the guarantees that turn a topology argument into a lookup.

Teardown​

scripts/run-ledger.sh reset
Expected output
ledger cleared

The ledger file under agentops/runs/ is removed. Nothing in this deep dive started a process or touched a live service — every command scored fixtures and appended to a local JSONL — so a clean slate is one reset away.
