Course Introduction

You are about to learn a discipline (not a tool, not a feature set) for using AI agents as working partners in production DevOps workflows. By the end of this course, you will have a governed, observable operating layer around Claude Code, running against a real multi-service platform, with mechanically tested authority boundaries at every level.

This module shows you the destination before the journey begins.

What is Agentic DevOps​

Three terms are competing for attention in the DevOps + AI space. They describe different things.

AIOps uses machine learning to detect anomalies, correlate alerts, and predict failures. It watches your systems. It does not change them. AIOps is a sensor layer, valuable but passive.

AgentOps is observability for AI agents themselves. It tracks what your agents did, how long they took, what they spent. AgentOps tells you whether your agents are healthy. It does not do your operational work.

Agentic DevOps is the discipline of using AI agents as working partners who diagnose, change, and verify your infrastructure alongside you. The agent does operational work, within boundaries you define. You hold accountability. The agent holds the wrench.

The distinction matters because the safety model is different. AIOps can be wrong without consequence: it suggests, and a human investigates. An agentic system can act, and a wrong action against production has real blast radius. That is why Agentic DevOps is a discipline, not a feature: it demands bounded evidence, branch-based isolation, deterministic verification, and explicit authority levels.

Five operational modes​

When you work with an agent, you are always setting a dial. The question is not "can the agent do this?" but "how much authority does this task deserve?" There are five positions on the dial, from least to most autonomous.

ModeThe agent...You...Example
ExplainReads code, surfaces context, answers questionsDrive entirely, the agent is a search engine with reasoning"What does this health check actually probe?"
RecommendAnalyzes a situation and suggests a course of actionEvaluate the suggestion and decide whether to act on it"Given this alert, what should I investigate first?"
Change a branchWrites code, creates a diff on a branchReview the diff, run the grader, approve or discard"Fix the readiness probe path on a feature branch"
Execute with approvalProposes a plan, then acts step by step with your approval at each gateApprove each step, halt if any step looks wrong"Run the incident triage playbook, ask before each remediation"
Narrow closed loopDetects, acts, and verifies within fail-closed guardrails, no human in the loopMonitor outcomes, intervene only on anomalies"Watch for OOMKill events, scale the pod, verify recovery, alert if unresolved"

These five modes map into the autonomy ladder you will use throughout the course:

Strategic levelOperational modes within it
Manual(no agent involvement)
AI AugmentedExplain, Recommend
AgenticChange a branch, Execute with approval, Narrow closed loop, agent has agency; the dial between semi-autonomous and autonomous depends on how much you trust the verification

Every module in this course tells you which operational mode the lab uses. By Module 19, you will have practiced all five, and you will know which one to reach for by asking three questions: How bad if it goes wrong? How fast will I know? How easily can I undo it?

The finished system​

Before you build it module by module, look at what the final workbench looks like in action. This is the capstone: a compound production incident handled by the system you will have built.

The scenario: A campaign-traffic surge hits Northstar Commerce. Multiple services degrade simultaneously. The system you built responds:

  1. Alert fires. Prometheus detects elevated error rates across orders-api and inventory-api. Alertmanager routes the alert.
  2. Evidence gathered. An investigator agent collects bounded evidence: the alert payload, relevant metrics, recent deploy history, and the architecture context from .claude/.
  3. Parallel triage. Multiple role-scoped subagents (SRE investigator, IaC reviewer, service diagnostician) analyze the evidence independently, each scoped to their domain.
  4. Synthesis. An orchestrator merges the independent findings, deduplicates, and ranks by severity.
  5. Remediation proposed. A fix is proposed on a branch: a PR with a clear diff, linked to the evidence trail.
  6. Human review. You review the PR. The diff is small, the evidence is cited, the grader confirms the fix resolves the symptom.
  7. Approval and canary. You approve. The change deploys via canary: a small percentage of traffic first, with automated verification.
  8. Verification. The grader confirms: error rates down, probes green, SLOs restored. The incident closes with a full audit trail.

Every component in that sequence (the agent roles, the authority boundaries, the orchestration topology, the verification gates) is something you will build in a specific module. Module 1 starts with step 3 (diagnosis) on a single simple defect. Module 19 runs the entire sequence against a compound incident.

Who this course is for​

You are a DevOps, SRE, Platform, Kubernetes, DevSecOps, or MLOps engineer with working experience in:

  • Git and terminal workflows
  • Containers and Docker/Compose
  • CI/CD pipelines
  • Terraform plans and state
  • Kubernetes workloads, services, and probes

Claude Code is taught from zero. You do not need prior experience with AI coding agents. The DevOps stack is not taught, you already run it in production.

What you will build​

Every module improves the same codebase: Northstar Commerce, a platform with orders-api, inventory-api, Terraform infrastructure, Kubernetes deployments, CI/CD, Prometheus/Alertmanager observability, and incident tooling. You start with a flawed repository and progressively build a .claude/ operating layer that governs what agents can see, change, recommend, approve, and verify.
